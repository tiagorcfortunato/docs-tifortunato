The `docker-compose.evolution.yml` file outlines a self-contained Docker Compose environment for running the Evolution API, a critical component for Odys's WhatsApp integration. While the Odys `README.md` indicates that the production Evolution API is hosted on Railway with a Supabase PostgreSQL backend, this `docker-compose` configuration provides a local, isolated setup. It demonstrates how the Evolution API can be deployed with its own dedicated PostgreSQL database and Redis instance, embodying the principle of service separation. This local environment is invaluable for development and testing, allowing engineers to interact with the Evolution API without relying on external cloud services.

## Overview

This Docker Compose configuration orchestrates three core services: a PostgreSQL database, a Redis instance, and the Evolution API itself. Each service runs in its own container, interconnected via a dedicated Docker network named `evolution-net`. This isolation ensures that the Evolution API's data and cache are managed independently, preventing conflicts with other local services and providing a clear, reproducible environment. The setup uses named volumes, `evolution_pg` and `evolution_redis`, to persist data for both the database and Redis, ensuring that data is not lost when containers are stopped or restarted.

## Evolution API Service

The `evolution-api` service is the heart of this deployment, utilizing the `evoapicloud/evolution-api:v2.3.7` Docker image. This image encapsulates the entire Evolution API application, allowing for consistent deployment across different environments.

The service is configured to restart `unless-stopped`, ensuring high availability in case of failures. It explicitly depends on both the `postgres` and `redis` services, with conditions set to `service_healthy` for Postgres and `service_started` for Redis. This ensures that the Evolution API only attempts to start once its essential dependencies are ready, preventing startup errors.

Port `8080` on the host machine is mapped to port `8080` within the container, making the Evolution API accessible locally. A comprehensive set of environment variables configures the Evolution API's behavior:

*   **`SERVER_URL`**: Set to `"http://localhost:8080"`, this defines the base URL for the API, crucial for internal callbacks and external communication in a local context.
*   **Authentication**: `AUTHENTICATION_API_KEY` is set to `"odys-local-key-2026"`, providing a local API key for securing access. `AUTHENTICATION_EXPOSE_IN_FETCH_INSTANCES` is set to `"true"`, likely for debugging or specific local development needs.
*   **Database**: The `DATABASE_PROVIDER` is explicitly set to `"postgresql"`. The `DATABASE_CONNECTION_URI` points to the local `postgres` service using the credentials `evolution:odys-pg-2026` and database `evolution`, with the `schema=public` parameter. Several `DATABASE_SAVE_DATA_*` flags are set to `"true"`, indicating that the Evolution API should persist various types of data, such as instances, new messages, message updates, contacts, and chats, to its dedicated database. `DATABASE_SAVE_IS_ON_WHATSAPP` and `DATABASE_SAVE_IS_ON_WHATSAPP_DAYS` control the tracking of WhatsApp presence.
*   **Redis**: `CACHE_REDIS_ENABLED` is `"true"`, directing the Evolution API to use Redis for caching and session management. `CACHE_REDIS_URI` points to `redis://redis:6379/0`, connecting to the local Redis service. `CACHE_REDIS_PREFIX_KEY` is set to `"evolution"`, isolating Evolution API's cache keys. `CACHE_REDIS_SAVE_INSTANCES` is `"true"`, indicating that instance data should be cached. Notably, `CACHE_LOCAL_ENABLED` is `"false"`, prioritizing Redis over any in-memory caching.
*   **Logging**: `LOG_LEVEL` is configured to `"ERROR,WARN,INFO"`, providing a balance of verbosity for local debugging. `LOG_COLOR` is `"true"` for better readability in terminal output, and `LOG_BAILEYS` is set to `"error"`, focusing on critical issues from the underlying WhatsApp library.
*   **Session Configuration**: `DEL_INSTANCE` is `"false"`, preventing automatic deletion of instances. `CONFIG_SESSION_PHONE_CLIENT` and `CONFIG_SESSION_PHONE_NAME` are set to `"Odys"` and `"Chrome"` respectively, customizing the session identification.
*   **Webhooks and Telemetry**: `WEBHOOK_GLOBAL_ENABLED` is `"false"`, indicating that webhooks are managed on a per-instance basis via the API, rather than a global configuration. `TELEMETRY_ENABLED` is also `"false"`, disabling usage data collection.

## Database (Postgres)

The `postgres` service uses the `postgres:15` Docker image, providing a stable and widely used relational database. It is named `evolution-postgres` and configured to restart `unless-stopped`. Environment variables `POSTGRES_USER`, `POSTGRES_PASSWORD`, and `POSTGRES_DB` are set to `evolution`, `odys-pg-2026`, and `evolution` respectively, defining the database credentials and initial database name.

A named volume, `evolution_pg`, is mounted to `/var/lib/postgresql/data` to ensure that all database data persists across container restarts. A `healthcheck` is defined using `pg_isready -U evolution`, which periodically checks the database's readiness, crucial for the `evolution-api` service's `depends_on` condition.

## Caching and Session Management (Redis)

The `redis` service uses the lightweight `redis:7-alpine` Docker image, optimized for minimal resource consumption. It is named `evolution-redis` and configured to restart `unless-stopped`. Similar to Postgres, a named volume, `evolution_redis`, is mounted to `/data` to persist Redis data. This Redis instance serves as a high-performance cache and session store for the Evolution API, as indicated by the `CACHE_REDIS_ENABLED` environment variable in the `evolution-api` service.

## Networking and Volumes

All three services are connected to a custom bridge network named `evolution-net`. This isolated network facilitates secure and efficient communication between the services without exposing them directly to the host's network unless explicitly mapped (like port `8080` for the API).

The named volumes `evolution_pg` and `evolution_redis` are declared and used to ensure data persistence. This is a critical design choice for development environments, as it allows developers to stop and start the Docker Compose stack without losing their database or cache state.

## Design decisions

The decision to use `docker-compose` for the Evolution API, with separate Postgres and Redis containers, reflects a commitment to isolated, reproducible development environments. By encapsulating all dependencies within Docker, developers can spin up the entire Evolution API stack with a single command, minimizing setup friction and ensuring consistency across different machines.

The choice of a dedicated Postgres instance for the Evolution API, rather than sharing the main Odys application's Supabase database, aligns with the principle of service independence. This prevents the Evolution API's operational data (like WhatsApp session information) from intermingling with core application data, simplifying database management and potential future migrations. Similarly, a dedicated Redis instance ensures that the Evolution API's caching and session management do not interfere with other Redis-dependent services in the broader Odys ecosystem, such as the rate limiters managed by Upstash Redis.

The extensive environment variable configuration within `evolution-api` demonstrates a fine-grained control over the Evolution API's behavior. Disabling `WEBHOOK_GLOBAL_ENABLED` and `TELEMETRY_ENABLED` by default for this local setup suggests a focus on privacy and local control, allowing developers to enable these features only when necessary for specific testing scenarios. The explicit setting of `CACHE_LOCAL_ENABLED` to `"false"` reinforces the reliance on Redis for caching, indicating a preference for external, persistent caching over ephemeral in-memory solutions.

## Potential improvements

1.  **Externalize Sensitive Credentials**: The `docker-compose.evolution.yml` file hardcodes sensitive credentials such as `POSTGRES_PASSWORD: odys-pg-2026` and `AUTHENTICATION_API_KEY: "odys-local-key-2026"`. For any environment beyond a purely ephemeral local development setup, these should be externalized using Docker secrets or environment variables loaded from a `.env` file. This prevents credential exposure in version control and allows for different values across development, staging, and production environments.
2.  **Dynamic `SERVER_URL` Configuration**: The `evolution-api` service's `SERVER_URL` is set to `"http://localhost:8080"`. While suitable for local development, this value would need to be dynamically configured for a production deployment on a platform like Railway, where the service would have a different, potentially public, URL. This could be managed by making `SERVER_URL` an environment variable that is populated by the hosting platform or a CI/CD pipeline.
3.  **Clarify Docker Image Strategy**: The `docker-compose.evolution.yml` uses the `evoapicloud/evolution-api:v2.3.7` image, whereas the `README.md` states that the Railway deployment uses `tiagorcfortunato/evolution-api-odys`. This discrepancy suggests a custom or forked Evolution API image for production. An improvement would be to clarify the relationship between these images, document the build process for `tiagorcfortunato/evolution-api-odys`, and establish a clear versioning and update strategy to ensure consistency and traceability between local development and production deployments.
