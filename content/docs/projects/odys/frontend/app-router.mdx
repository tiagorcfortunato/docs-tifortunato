# App Router

Odys leverages the Next.js App Router to structure its frontend, embracing a modern approach to web development that prioritizes performance, developer experience, and scalability. This architecture allows for a clear separation of concerns between server-side data fetching and client-side interactivity, leading to efficient rendering and a streamlined user experience.

## Overview

The App Router in Odys is designed around the core principles of Next.js 13+, primarily focusing on Server Components, logical route grouping, and a deliberate choice regarding middleware. The application's entry point is the root layout, which establishes global configurations and wraps the entire application. Individual pages, such as the dynamic booking page for professionals, are implemented as Server Components, enabling direct database access and server-side rendering for initial page loads.

Odys defines 23 distinct API routes, handling various backend operations from user authentication to appointment management and Stripe integrations. This robust API layer complements the App Router's server-side capabilities, ensuring that complex business logic and data mutations are handled efficiently. The system also incorporates two cron jobs, `/api/cron/reminders` and `/api/cron/whatsapp-watchdog`, which are scheduled to run daily, demonstrating the App Router's flexibility in hosting server-side tasks.

## Root Layout

The application's foundation is laid in `src/app/layout.tsx`, which serves as the root layout for all pages. This file is a Server Component by default, meaning it renders on the server and can perform data fetching or other server-side operations before sending the HTML to the client.

Within this layout, global configurations are established:

*   **Metadata**: The `metadata` export defines crucial SEO information, including the site's title ("Odys — Agenda online para profissionais de saúde e bem-estar"), description, Open Graph data, and Twitter card details. This ensures that Odys pages are well-indexed by search engines and display rich previews when shared on social media. The `metadataBase` is set to `https://odys.com.br`, providing a base URL for all relative metadata paths.
*   **Fonts**: Two custom fonts, `Plus_Jakarta_Sans` and `Montserrat`, are loaded from `next/font/google`. These are configured with specific weights and subsets, then applied globally via CSS variables (`--font-sans`, `--font-montserrat`) to maintain a consistent visual identity across the application.
*   **Global Styles**: The `globals.css` file is imported here, applying base styles and utility classes across the entire application.
*   **Third-Party Integrations**: Several key services are integrated at the root level:
    *   `Toaster` from `@/components/ui/sonner` provides rich, colored notifications positioned at the top-right of the screen.
    *   `PostHogProvider` wraps the application, enabling product analytics and feature flagging.
    *   `CookieBanner` is included to manage user consent for cookies, adhering to privacy regulations.
    *   Vercel's `Analytics` and `SpeedInsights` components are added at the bottom of the `<body>`. These are used for anonymous page-view counts and real-user Core Web Vitals (LCP, INP, CLS) respectively, complementing PostHog for a comprehensive understanding of application usage and performance.
*   **Accessibility**: A "Skip to main content" link is included, hidden by default but visible on keyboard focus. This improves navigation for screen-reader and keyboard users by allowing them to bypass repetitive navigation elements.
*   **Theme Management**: An inline script is injected into the `<head>` to prevent a "flash of unstyled content" (FOUC) when applying the user's saved theme preference. It reads `odys-theme` from `localStorage` and immediately applies the `dark` class to the `documentElement` if the dark theme is preferred.

## Dynamic Booking Page

The `src/app/p/[slug]/page.tsx` file exemplifies a dynamic route implemented as a Server Component. This page is responsible for displaying a professional's public profile and allowing clients to book appointments.

*   **Dynamic Metadata Generation**: The `generateMetadata` function is an asynchronous Server Component feature that dynamically sets the page's metadata based on the `slug` parameter. It fetches professional data from the `professionals` table using Drizzle ORM (`db.select().from(professionals).where(eq(professionals.slug, slug))`) to construct a specific title and description, including the professional's name and profession. If an `avatarUrl` is available, it's used for Open Graph images.
*   **Server-Side Data Fetching**: The default export function, `BookingPage`, is also an `async` Server Component. It performs multiple database queries directly:
    *   It fetches the professional's details from the `professionals` table. If the professional is not found or inactive, it uses `notFound()` from `next/navigation` to render a 404 page.
    *   It uses `createClient()` from `@/lib/supabase/server` to get the current user's session. This allows the page to determine if the visitor is the professional themselves (`isOwner`) or a logged-in client.
    *   If a user is logged in and is not the owner, it attempts to fetch their existing client data (`clients.name`, `clients.phone`, `clients.email`) to pre-fill the booking form.
    *   It fetches related professionals from the `professionals` table based on the current professional's `profession`, then filters out the current professional and limits the results to four.
    *   It retrieves aggregated statistics (average rating and review count) for these related professionals using `getProStats`.
    *   It fetches all reviews for the current professional from the `reviews` table, joining with the `clients` table to display client names.
*   **Hybrid Rendering**: While the page itself is a Server Component, it integrates Client Components for interactive elements. For instance, `FollowButton`, `BookingWidget`, `LogoutButton`, and `ThemeToggle` are imported and rendered within this server-rendered page. The `BookingWidget` is particularly notable as it receives initial data (like `professionalName`, `sessionDuration`, `sessionPrice`, `defaultName`, `defaultPhone`, `defaultEmail`, `isLoggedIn`) as props, which are then used to hydrate its client-side logic.
*   **Database Schema Interaction**: The page interacts with several tables from the Drizzle schema: `professionals` (32 columns), `reviews` (7 columns), and `clients` (8 columns). This direct access to the database within a Server Component simplifies data fetching logic compared to traditional API routes for initial page loads.

## Route Groups

The `src/app/(auth)/layout.tsx` file is not found, indicating the `(auth)` route group is not currently implemented. This pattern allows for applying specific layouts or configurations to a subset of routes, such as authentication pages, without introducing extra segments in the URL. For example, all pages within `(auth)` could share a common layout for login, registration, and password reset forms, distinct from the main application layout.

## Absence of Middleware

Odys does not appear to use a `middleware.ts` file at the root of its App Router. This design choice implies that global request-level logic, such as authentication checks, redirects, or A/B testing, is not centralized in a single middleware function. Instead, such concerns are likely handled directly within individual Server Components or API routes. For instance, authentication checks are performed within `src/app/p/[slug]/page.tsx` using `supabase.auth.getUser()`. This approach can simplify the request lifecycle by avoiding an additional layer of abstraction, but it requires careful implementation to ensure consistent logic across all relevant routes.

## Design Decisions

The architectural choices in Odys reflect a clear preference for the App Router's capabilities:

*   **Server Components for Performance and SEO**: By making pages like `src/app/p/[slug]/page.tsx` Server Components, Odys ensures that critical data is fetched and rendered on the server. This results in faster initial page loads, improved SEO due to fully rendered HTML, and a simpler data fetching model where components can directly query the database. The extensive use of Drizzle ORM within these components (`db.select().from(...)`) is a direct consequence of this decision.
*   **Route Groups for Organization**: The `(auth)` route group is mentioned as a structural decision, but `src/app/(auth)/layout.tsx` is not found, suggesting this group is not actively used. This improves code organization and maintainability, especially as the application grows.
*   **Localized Authentication/Authorization**: The absence of a global `middleware.ts` suggests a design where authentication and authorization logic are handled closer to the components or API routes that require them. In `src/app/p/[slug]/page.tsx`, for example, the `isOwner` check and `clientData` fetching are integrated directly into the page's rendering logic. This can offer more granular control and potentially reduce the overhead of a global middleware for simpler applications.
*   **Comprehensive API Layer**: With 23 API routes, Odys clearly separates data fetching for initial page loads (Server Components) from data mutations and complex server-side operations (API routes). This separation allows for a clean client-server interaction model, where client components can interact with the backend via these well-defined API endpoints.

## Potential Improvements

1.  **Centralize Authentication and Authorization Logic**: The `src/app/p/[slug]/page.tsx` file includes logic to determine `isOwner` and fetch `clientData` based on the authenticated user. As the application grows, duplicating this logic across multiple Server Components could become cumbersome. Consider creating a reusable server utility or a custom hook that encapsulates user authentication and authorization checks, returning user-specific data or redirecting if unauthorized. This would make the logic more consistent and easier to maintain.
2.  **Optimize Related Professionals Data Fetching**: In `src/app/p/[slug]/page.tsx`, fetching `allRelated` professionals and then `relatedStats` involves two separate database calls. While `getProStats` is optimized to fetch stats for multiple IDs, the initial query for `allRelated` could potentially be combined with the review/rating aggregation using Drizzle's relational queries or subqueries to reduce the number of database roundtrips.
3.  **Explicit Error Handling and Loading States**: While `notFound()` is used for missing professionals, other potential errors during data fetching (e.g., database connection issues, network failures) might not be explicitly handled within the `BookingPage` component. Implementing more granular error boundaries or loading states for individual data sections could improve the user experience during transient issues.
