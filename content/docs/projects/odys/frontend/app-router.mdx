# App Router

Odys leverages the Next.js App Router to structure its frontend, embracing a modern approach to web development that prioritizes performance, developer experience, and scalability. This architecture allows for a clear separation of concerns, enabling server-side data fetching and rendering while maintaining client-side interactivity where needed. The App Router's design choices, including the strategic use of Server Components and route groups, shape how pages are delivered and how user interactions are managed.

## Overview

The Next.js App Router forms the backbone of Odys's user interface, dictating how routes are defined, data is fetched, and components are rendered. A fundamental aspect of this architecture is the default use of Server Components, which execute on the server, allowing direct database access and reducing the JavaScript payload sent to the client. This approach is evident in core files like `src/app/layout.tsx` and dynamic pages such as `src/app/p/[slug]/page.tsx`.

Route groups, denoted by parentheses in the file system (e.g., `(auth)`), are employed to organize routes logically without affecting the URL path. This allows for applying specific layouts or behaviors to a collection of pages, such as those related to authentication. Notably, Odys does not currently utilize Next.js middleware, suggesting that request-level interception and modification, including authentication and authorization, are handled either within individual Server Components or dedicated API routes.

## Server Components

Server Components are a cornerstone of the Odys frontend, enabling efficient data fetching and rendering directly on the server. This design choice significantly reduces the amount of JavaScript shipped to the browser, leading to faster initial page loads and improved performance.

The primary layout, defined in `src/app/layout.tsx`, is a Server Component. Here, global metadata is configured, including the site's title, description, and Open Graph properties, which are crucial for SEO and social media sharing. The layout also handles the loading of custom fonts, `Plus_Jakarta_Sans` and `Montserrat`, and integrates essential third-party utilities like `PostHogProvider` for analytics, `CookieBanner` for compliance, and Vercel's `Analytics` and `SpeedInsights` for anonymous page view tracking and performance monitoring. The inclusion of a script to prevent a flash of unstyled content (FOUC) by applying the saved theme before the page paints demonstrates attention to user experience.

A prime example of a dynamic Server Component is `src/app/p/[slug]/page.tsx`. This page is responsible for displaying a professional's public profile and booking interface. It directly interacts with the database using Drizzle ORM to fetch detailed information from the `professionals`, `reviews`, and `clients` tables based on the `slug` parameter. The `generateMetadata` function within this file also runs on the server, dynamically generating SEO-friendly titles and descriptions for each professional's page.

Crucially, `src/app/p/[slug]/page.tsx` performs server-side authentication checks using `createClient` from `@/lib/supabase/server` to determine if the visitor is the page owner or an authenticated client. This allows for conditional rendering of UI elements, such as the "My dashboard" link for owners or pre-filling booking forms for logged-in clients. While the page itself is a Server Component, it seamlessly integrates Client Components like `FollowButton`, `ProfessionalCard`, `BookingWidget`, `LogoutButton`, `ThemeToggle`, `OdysLogo`, and `ProfessionalLocationCard` to provide interactive elements to the user. The `BookingWidget` in particular is a client component that receives initial data from the server, allowing it to manage client-side state and interactions for the booking process.

## Route Groups

Odys utilizes route groups to organize its file-based routing structure without impacting the URL paths presented to the user. The presence of an `(auth)` route group, as indicated by the file system structure, suggests a logical grouping for authentication-related pages. While the specific `src/app/(auth)/layout.tsx` file is not present in the provided code, the conceptual use of such a group would typically allow for applying a distinct layout or specific logic (e.g., redirecting authenticated users away from login pages) to routes nested within it, such as `/login` or `/register`. This organizational pattern helps maintain a clean project structure and allows for consistent UI/UX across related pages.

## Absence of Middleware

Odys does not implement Next.js middleware. This design choice implies that global request interception, such as for authentication, authorization, or URL rewriting, is not handled at the edge or before a request reaches a page or API route. Instead, logic that might typically reside in middleware, particularly authentication and authorization, is handled directly within the Server Components or API routes themselves. For instance, `src/app/p/[slug]/page.tsx` explicitly calls `supabase.auth.getUser()` to determine the user's session and role, performing authorization checks (`isOwner`) directly within the page's rendering logic. This approach can simplify the request flow by centralizing logic closer to the data it affects, but it requires careful consideration to avoid duplication across multiple routes.

## Design decisions

The architectural choices within Odys's App Router implementation reflect a deliberate balance between performance, maintainability, and developer experience.

The heavy reliance on **Server Components** for pages like `src/app/p/[slug]/page.tsx` is a strategic decision to optimize initial page load times. By fetching data directly from the Drizzle ORM and Supabase on the server, the application minimizes the client-side JavaScript bundle, which is particularly beneficial for content-heavy pages or those requiring significant database interactions. This also simplifies data fetching logic, as server components can directly access backend resources without needing a separate API layer for their initial data requirements. The trade-off is that any interactivity on these pages must be encapsulated within Client Components, which are then hydrated on the client side.

The use of **route groups**, such as `(auth)`, is a structural choice aimed at improving code organization. It allows developers to group related routes and apply common layouts or behaviors to them without altering the public URL structure. This keeps the file system tidy and makes it easier to manage specific sections of the application, like authentication flows, by isolating their UI and logic.

The decision to **omit Next.js middleware** suggests a preference for handling authentication and authorization logic closer to the components that consume the data. By performing checks like `supabase.auth.getUser()` and `isOwner` directly within `src/app/p/[slug]/page.tsx`, the page explicitly controls its access and data display. This can lead to a more explicit and localized understanding of authorization for each route. However, it also means that common authorization patterns might need to be abstracted into reusable functions or hooks to prevent code duplication across multiple Server Components or API routes.

## Potential improvements

1.  **Centralize Authentication and Authorization Logic**: The `src/app/p/[slug]/page.tsx` file contains logic to check `user?.id === prof.userId` to determine `isOwner`. This pattern of checking user roles and permissions might become repetitive across various Server Components. Consider creating a reusable server utility function or a dedicated layout for authenticated routes (e.g., within the `(dashboard)` route group, if one existed) that handles these checks and redirects or throws `notFound()` if unauthorized, abstracting this logic away from individual page components.
2.  **Refine Error Handling for Data Fetching**: While `notFound()` is used effectively in `src/app/p/[slug]/page.tsx` when a professional is not found or inactive, more granular error handling could be implemented. For instance, if database queries fail due to connection issues or other transient errors, the current setup might not provide specific user feedback. Implementing error boundaries for parts of the page or returning more specific error states could enhance the user experience beyond a generic "not found" page.
3.  **Optimize Image Loading for Professional Avatars**: In `src/app/p/[slug]/page.tsx`, the `Image` component from `next/image` is used for `prof.avatarUrl`. While `next/image` provides optimizations, ensuring that the `width` and `height` attributes are always explicitly set (or derived) and that `priority` is used for critical images can further improve Core Web Vitals, especially Largest Contentful Paint (LCP). For the avatar, which is a small, non-critical image, lazy loading might be acceptable, but for larger hero images, `priority` would be beneficial.
