# App Router

The Odys frontend is built with Next.js, leveraging its App Router to structure the application. This architecture emphasizes Server Components, enabling direct database interactions and efficient data fetching on the server, while also organizing routes into logical groups. This document explores the core patterns and decisions behind Odys's App Router implementation, including the strategic choice not to employ Next.js middleware.

## Overview

The App Router in Odys provides a robust framework for building a modern web application. At its foundation, `src/app/layout.tsx` defines the global structure and shared UI elements, acting as a root Server Component. This layout wraps the entire application, ensuring consistent branding, typography, and essential third-party integrations like analytics and toast notifications.

Individual pages, such as `src/app/p/[slug]/page.tsx`, are also implemented as Server Components. This allows them to fetch data directly from the database using Drizzle ORM and Supabase authentication utilities before rendering any UI. This approach minimizes client-side JavaScript and optimizes initial page load performance.

Odys utilizes route groups, indicated by directories enclosed in parentheses like `(auth)`, to organize parts of the application without affecting the URL path. While the `(auth)` route group is present in the directory structure, its corresponding layout file `src/app/(auth)/layout.tsx` is currently not found. This pattern is typically used to apply specific layouts or behaviors to a set of routes, such as authentication-related pages, without introducing extra segments into the URL.

Notably, the Odys application does not currently use Next.js middleware. Instead, authentication and authorization checks are integrated directly into Server Components or API routes, allowing for fine-grained control over data access at the point of consumption.

## Root Layout

The `src/app/layout.tsx` file serves as the root layout for the entire Odys application. As a Server Component, it executes on the server, allowing for server-side rendering of the initial HTML. This is where global configurations are established, including:

*   **HTML Tag Attributes**: The `html` tag in `src/app/layout.tsx` sets `lang="pt-BR"` and applies global utility classes like `h-full antialiased`.
*   **Metadata**: The `metadata` object defines crucial SEO information such as `title`, `description`, `openGraph` properties, and `twitter` card details. This ensures that search engines and social media platforms correctly display information about Odys, with the `metadataBase` set to `https://odys.com.br`. The `openGraph` properties also define `url`, `siteName`, `locale`, `type`, `authors`, and `publishedTime`.
*   **Fonts**: Two distinct font families, `Plus_Jakarta_Sans` and `Montserrat`, are loaded and configured as CSS variables (`--font-sans` and `--font-montserrat`). This centralizes typography definitions and ensures consistent styling across the application.
*   **Global Styles**: The `globals.css` file is imported here, applying base styles and utility classes across all pages. The `body` tag in `src/app/layout.tsx` applies specific utility classes like `min-h-full flex flex-col font-sans`.
*   **Third-Party Integrations**: Essential client-side providers and components are wrapped around the `children` prop. This includes `PostHogProvider` for product analytics, `Toaster` for displaying notifications, and `CookieBanner` for compliance. Vercel's `Analytics` and `SpeedInsights` are also integrated here, providing anonymous page view counts and real-user performance metrics without relying on cookies.
*   **Theme Management**: A small inline script is injected into the `<head>` to prevent a "flash of unstyled content" (FOUC) by applying the user's saved theme preference (`dark` or `light`) before the page renders.
*   **Accessibility**: A "Skip to main content" link is included, hidden by default but visible on keyboard focus, to improve navigation for screen reader and keyboard users.

## Dynamic Professional Booking Page

The `src/app/p/[slug]/page.tsx` file exemplifies a dynamic route implemented as a Server Component. This page is responsible for displaying a professional's public profile and booking interface, accessible via a unique `slug`.

Upon receiving a request, the `BookingPage` component directly queries the database using Drizzle ORM. It fetches detailed information about the professional from the `professionals` table, client data from the `clients` table, and reviews from the `reviews` table. For instance, it retrieves the professional's `name`, `profession`, `sessionDuration`, `sessionPrice`, and `bio`. If a professional is not found or is inactive, the `notFound()` helper from Next.js is invoked, rendering a 404 page.

Authentication is handled server-side using `createClient()` from Supabase. This allows the page to determine if the visitor is the professional themselves (`isOwner`) or a logged-in client, enabling personalized experiences like pre-filling booking forms with `clientData` or displaying a "My dashboard" link.

The page also dynamically generates its `metadata` using the `generateMetadata` function. This function fetches the professional's details based on the `slug` and constructs a specific `title`, `description`, and `openGraph` images, enhancing the SEO for each professional's profile.

The UI is composed of various components, some of which are Server Components themselves (e.g., `ProfessionalCard`, `ProfessionalLocationCard`) and others are Client Components (e.g., `BookingWidget`, `FollowButton`, `LogoutButton`, `ThemeToggle`). The `BookingWidget` is particularly notable as it receives server-fetched data as props (`sessionDuration`, `sessionPrice`, `defaultName`, `paymentType`, `paymentPercentage`, `pixKeyType`, and `pixKey`, etc.) but handles interactive booking logic on the client.

Related professionals are fetched by querying the `professionals` table for entries with the same `profession` and then filtering out the current professional. Their statistics, including average rating and review count, are aggregated using `getProStats`.

## Route Groups

Odys uses route groups, denoted by folders like `(auth)`, to logically segment parts of the application. The primary purpose of a route group is to apply a specific layout to a subset of routes without altering the URL path. For example, if `src/app/(auth)/login/page.tsx` existed, the URL would still be `/login`, but it would inherit a layout defined in `src/app/(auth)/layout.tsx`. This is useful for creating distinct user experiences, such as a simplified layout for authentication flows that differs from the main application layout.

Currently, while the `(auth)` directory exists, the corresponding `src/app/(auth)/layout.tsx` file is not found. This suggests an intended structure for authentication-related pages that is either incomplete or handled differently.

## Absence of Middleware

The Odys application does not implement Next.js middleware. Instead of a global interception layer, authentication and authorization logic are embedded directly within the Server Components and API routes. For instance, in `src/app/p/[slug]/page.tsx`, the `supabase.auth.getUser()` call and subsequent `isOwner` check determine user permissions and tailor the UI accordingly. Similarly, API routes like `/api/account` or `/api/booking` would perform their own user validation. This approach provides explicit control over access at the resource level, ensuring that data fetching and mutations are authorized precisely where they occur.

## Design decisions

The architectural choices in Odys's App Router implementation reflect a preference for server-side rendering and direct data access:

*   **Server Components for Data Fetching**: The decision to make most pages, like `src/app/p/[slug]/page.tsx`, Server Components allows for direct database queries using Drizzle ORM (`db.select()`). This eliminates the need for a separate API layer for initial data loads, simplifying the data flow and reducing client-side JavaScript bundles. It also means that sensitive data fetching logic remains on the server, away from the client.
*   **Dynamic Metadata Generation**: Using `generateMetadata` within `page.tsx` files ensures that each dynamic page, such as a professional's profile, has accurate and specific SEO metadata. This is crucial for discoverability and proper display on search engines and social media, as the `title` and `description` can be tailored to the specific professional.
*   **No Next.js Middleware**: The absence of Next.js middleware is a deliberate choice. Instead of a centralized middleware, authentication and authorization are handled within the individual Server Components and API routes. This provides granular control, as each route can implement its specific access checks, often using `supabase.auth.getUser()` directly. This can sometimes lead to more explicit, localized security logic, but might require duplication if many routes share similar access patterns.
*   **Client Components for Interactivity**: While data fetching happens on the server, interactive elements like the `BookingWidget`, `FollowButton`, and `ThemeToggle` are implemented as Client Components. This separation allows for rich, interactive user experiences without bloating the initial server-rendered HTML with unnecessary JavaScript. Data is passed from Server Components to Client Components as props, maintaining a clear boundary.

## Potential improvements

1.  **Implement `src/app/(auth)/layout.tsx`**: The `(auth)` route group is present in the file structure, but its corresponding `layout.tsx` file is missing. If the intention is to have a distinct layout for authentication-related pages (e.g., `/login`, `/register`), creating this file would allow for a consistent UI and shared logic across these routes without affecting the main application layout. This would centralize authentication-specific UI elements and potentially simplify future maintenance.
2.  **Optimize Data Fetching in `src/app/p/[slug]/page.tsx`**: The `BookingPage` component performs five distinct database queries: for the professional, client, all related professionals, related professional stats, and reviews. While Drizzle is efficient, consider if some of these queries could be combined or optimized using Drizzle's relation capabilities or a single, more complex query to reduce database roundtrips, especially for `getProStats` which currently maps over `related` professionals to fetch their stats.
3.  **Centralize Authentication Logic**: With the current absence of Next.js middleware, authentication checks (e.g., `user?.id === prof.userId` in `src/app/p/[slug]/page.tsx`) are performed directly within individual Server Components. For a growing application, this could lead to duplicated logic. Consider creating a reusable server-side utility function or a custom hook that encapsulates common authentication and authorization patterns, making the code more DRY and easier to maintain.
4.  **Enhanced Error Handling for Data Fetching**: The `src/app/p/[slug]/page.tsx` currently uses `notFound()` if a professional is not found or is inactive. While effective for 404 scenarios, more specific error handling could be implemented for other data fetching failures (e.g., database connection issues, malformed data). Using React error boundaries or custom error pages for different types of exceptions could provide a more informative and user-friendly experience.
