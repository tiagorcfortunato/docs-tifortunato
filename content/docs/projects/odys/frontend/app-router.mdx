# App Router

Odys leverages the Next.js App Router to structure its frontend, embracing a modern approach to web development that prioritizes performance, developer experience, and scalability. This architecture allows for a clear separation of concerns between server-side and client-side logic, enabling efficient data fetching and rendering.

## Overview

The `app` directory in Odys is organized around the core principles of the Next.js App Router. This includes the default use of Server Components, the logical grouping of routes, and a streamlined approach to request handling that, notably, omits a global `middleware.ts` file. This design choice reflects a preference for handling authentication and authorization directly within the components that require it, rather than at a centralized middleware layer.

The application's root layout, defined in `src/app/layout.tsx`, establishes the global structure, metadata, and shared UI elements. Within this structure, route groups are used to organize different sections of the application. For instance, the `src/app/(auth)` directory is intended for authentication-related pages, but `src/app/(auth)/layout.tsx` is not found, so no shared layout or behavior is currently applied. Dynamic routes, such as `src/app/p/[slug]/page.tsx`, are crucial for displaying professional profiles, fetching data based on URL parameters.

## Server Components

A cornerstone of the App Router is the default behavior of components within the `app` directory to be Server Components. This means that components like `src/app/layout.tsx` and `src/app/p/[slug]/page.tsx` execute on the server, allowing them to directly interact with backend resources like the database.

In `src/app/p/[slug]/page.tsx`, for example, the `BookingPage` component directly queries the Drizzle ORM to fetch professional data:

```typescript
const [prof] = await db
  .select()
  .from(professionals)
  .where(eq(professionals.slug, slug))
  .limit(1)
```

The `BookingPage` component calls `notFound()` if the professional is not found or is not active. This pattern is repeated for fetching related professionals, client data, and reviews, all within the server component. This direct database access simplifies the data flow significantly, eliminating the need for a separate API layer for initial page loads and reducing client-side JavaScript bundles. The `generateMetadata` function, also a Server Component, fetches data to dynamically set SEO-friendly titles and descriptions for each professional's page.

Client Components are explicitly marked with the `"use client"` directive and are imported into Server Components where interactivity is required. Examples include `BookingWidget`, `FollowButton`, `Toaster`, and `CookieBanner`. This hybrid rendering approach ensures that static content is rendered efficiently on the server, while interactive elements hydrate on the client, providing a fast initial load and a dynamic user experience.

## Route Groups

Route groups in Next.js App Router allow developers to organize routes without affecting the URL structure. In Odys, the `(auth)` directory, though its `layout.tsx` file is not provided, indicates a logical grouping for authentication-related pages (e.g., login, registration). This convention allows these pages to share a specific layout or set of behaviors, such as redirecting authenticated users away from login pages, without adding `(auth)` to the URL path.

The `src/app/p/[slug]/page.tsx` file demonstrates a dynamic route, where `[slug]` is a placeholder for a professional's unique identifier. This allows Odys to generate dedicated public profile pages for each professional, such as `odys.com.br/p/dr-joao-silva`, fetching and displaying relevant data based on the `slug` parameter.

## Absence of Middleware

Unlike many Next.js applications that use a `middleware.ts` file for global request handling, Odys does not implement one. Instead, authentication and authorization checks are performed directly within the Server Components themselves.

For instance, in `src/app/p/[slug]/page.tsx`, the `BookingPage` component checks if the current user is the owner of the professional's page or an authenticated client:

```typescript
const supabase = await createClient()
const { data: { user } } = await supabase.auth.getUser()
const isOwner = user?.id === prof.userId
```

This approach centralizes the access control logic with the data fetching and rendering logic for a specific page. While it means checks are repeated across different pages, it also ensures that each page explicitly defines its access requirements, potentially simplifying debugging for page-specific authorization issues.

## Design Decisions

The architectural choices in Odys's App Router implementation reflect several key design decisions:

*   **Direct Database Access in Server Components:** By performing Drizzle ORM queries directly within `page.tsx` components, Odys minimizes the overhead of an intermediate API layer for server-rendered content. This simplifies the data fetching lifecycle and reduces network requests during initial page load.
*   **Dynamic Metadata Generation:** The use of `generateMetadata` in `src/app/p/[slug]/page.tsx` allows for highly specific and SEO-friendly titles and descriptions for each professional's public profile, dynamically generated based on database content.
*   **Granular Client Component Boundaries:** Client components like `BookingWidget` are carefully placed to encapsulate interactivity, ensuring that the majority of the page remains a Server Component. This strategy optimizes for performance by sending minimal JavaScript to the client.
*   **Component-Level Authentication:** The decision to forgo a global `middleware.ts` file and instead handle authentication checks within individual Server Components (e.g., `createClient().auth.getUser()` in `BookingPage`) prioritizes explicit, page-specific authorization logic. This can make the authorization flow easier to reason about for individual routes, even if it means some duplication.

## Potential Improvements

1.  **Centralize Authentication and User Context:** The current pattern of calling `createClient().auth.getUser()` in `src/app/p/[slug]/page.tsx` to determine `isOwner` or `clientData` is effective but could lead to repetitive code across multiple Server Components that need user information. A more centralized approach, perhaps by fetching the user in a higher-level layout (e.g., `src/app/layout.tsx` or a dedicated `(app)/layout.tsx` if one existed) and passing it down via React Context or a custom hook, could reduce duplication and provide a single source of truth for the current user's session.
2.  **Implement `(auth)/layout.tsx`:** The presence of the `(auth)` route group without an explicit `src/app/(auth)/layout.tsx` file suggests an opportunity. Implementing this layout would allow for consistent styling, authentication checks, and redirects for all pages within the authentication flow (e.g., `/login`, `/register`). This would centralize logic like redirecting already authenticated users away from login pages, improving maintainability and user experience.
3.  **Optimize Related Professionals Query:** In `src/app/p/[slug]/page.tsx`, the query for `allRelated` professionals fetches all professionals of the same `profession` and then filters them in memory (`allRelated.filter(p => p.slug !== slug && p.id !== prof.id).slice(0, 4)`). This can be inefficient if there are many professionals in a given category. The Drizzle query could be optimized to perform the filtering and limiting directly in the database, for example, by adding `where(and(eq(professionals.profession, prof.profession), ne(professionals.slug, slug), ne(professionals.id, prof.id)))` and `limit(4)` to the `db.select()` call. This would reduce the amount of data transferred from the database and processed by the server.
