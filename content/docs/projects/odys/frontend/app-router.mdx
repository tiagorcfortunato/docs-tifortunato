# App Router

Odys leverages the Next.js App Router to structure its frontend, embracing a modern React architecture that prioritizes server-side rendering and Server Components. This approach allows for efficient data fetching directly within components, streamlined routing, and a clear separation of concerns between server and client logic. The application's structure reflects a deliberate choice to handle data access and initial rendering on the server, minimizing client-side JavaScript where possible.

## Overview

The frontend architecture of Odys, built with Next.js, centers around the `src/app` directory, which is the foundation for the App Router. This directory houses the root layout, dynamic routes, and various UI components. The core philosophy here is to maximize the benefits of Server Components, allowing direct database interactions and server-side logic to coexist with React rendering.

The global structure is defined by `src/app/layout.tsx`, which wraps the entire application. This root layout is a Server Component responsible for setting up the HTML document, importing global styles, defining metadata, and integrating third-party analytics and utility providers like `PostHogProvider`, `CookieBanner`, `Analytics`, and `SpeedInsights`. It also manages font loading for `Plus_Jakarta_Sans` and `Montserrat`, and includes a small inline script to prevent theme flashing on page load.

A prominent example of a dynamic route is `src/app/p/[slug]/page.tsx`, which serves as the public booking page for individual professionals. This page demonstrates the power of Server Components by fetching all necessary data directly from the database using Drizzle ORM and Supabase authentication on the server, before rendering the HTML.

Notably, while the description mentions "route groups" and specifically `(auth)`, the provided file manifest indicates that `src/app/(auth)/layout.tsx` is not found. This suggests that while route groups might be a conceptual part of the architecture, the specific authentication layout for that group is not currently implemented or has been handled differently. The application also explicitly avoids Next.js middleware, opting instead to handle authentication and authorization checks directly within Server Components or API routes.

## Server Components in Practice

The `src/app/p/[slug]/page.tsx` file exemplifies the use of Server Components within Odys. This page is responsible for displaying a professional's public profile and booking interface. As a Server Component, it performs several critical operations directly on the server:

1.  **Data Fetching:** It queries the `professionals`, `reviews`, and `clients` tables using Drizzle ORM (`db.select()`) to retrieve detailed information about the professional, their reviews, and, if the visitor is a logged-in client, their existing client data. This direct database access eliminates the need for a separate API layer for initial page loads, simplifying the data flow and reducing latency.
2.  **Authentication and Authorization:** The page uses `createClient()` and `supabase.auth.getUser()` to determine if the current visitor is logged in and, crucially, if they are the owner of the professional profile being viewed. This check (`isOwner`) influences the UI, showing different navigation links and hiding the `FollowButton` for the owner.
3.  **Metadata Generation:** The `generateMetadata` function, also a Server Component feature, dynamically sets the page's title, description, and Open Graph images based on the fetched professional data. This is vital for SEO and social media sharing, ensuring accurate and relevant information is displayed.
4.  **Rendering Client Components:** While the page itself is a Server Component, it renders several Client Components, such as `BookingWidget`, `FollowButton`, `ProfessionalCard`, `ProfessionalLocationCard`, `LogoutButton`, `ThemeToggle`, and `OdysLogo`. Data fetched on the server is passed down as props to these client-side interactive elements, allowing them to hydrate and function on the user's browser. The `BookingWidget`, for instance, receives `sessionDuration`, `sessionPrice`, `paymentType`, and pre-filled client data.

This architecture ensures that the initial page load is fast and SEO-friendly, as the complete HTML is rendered on the server. Only the interactive parts of the page require client-side JavaScript, which is then progressively enhanced.

## Routing and Structure

Odys organizes its routes primarily through the file-system-based routing of the App Router. Dynamic segments, like `[slug]` in `src/app/p/[slug]/page.tsx`, allow for flexible URL structures that map directly to data entities.

The application's API routes, totaling `23` distinct endpoints, are also managed within the `src/app/api` directory. These routes, such as `/api/booking`, `/api/follows`, and `/api/messages`, handle various HTTP methods (GET, POST, PATCH, DELETE) and serve as the interface for client-side interactions and external services. For example, `/api/cron/reminders` and `/api/cron/whatsapp-watchdog` are designated cron jobs, indicating server-side tasks triggered on a schedule.

A notable design choice is the absence of a Next.js middleware file. Instead of a global middleware, authentication and authorization logic are often embedded directly within the Server Components or API routes themselves. For instance, the `src/app/p/[slug]/page.tsx` directly checks user authentication status. This approach can simplify the request lifecycle by keeping related logic co-located, but requires careful consideration to avoid duplication across many routes.

## Design Decisions

The architectural choices in Odys reflect a clear preference for a server-first approach, aiming for performance and developer experience benefits:

*   **Server Components for Data Fetching:** By fetching data directly within `page.tsx` files, Odys avoids the overhead of creating separate API routes for every data requirement of a page. This reduces network roundtrips during initial page load and simplifies the mental model for developers, as data requirements are declared alongside the components that consume them. This is evident in `src/app/p/[slug]/page.tsx` where `professionals`, `reviews`, and `clients` data are fetched directly.
*   **Direct Database Access:** The use of Drizzle ORM within Server Components allows for direct, type-safe interaction with the PostgreSQL database, which has `11` tables including `professionals`, `appointments`, and `clients`. This eliminates an intermediate API layer for server-rendered pages, potentially improving performance and reducing complexity.
*   **No Next.js Middleware:** The decision to forgo a global Next.js middleware suggests a strategy where route protection and request manipulation are handled either at the API route level (e.g., rate limiting on `/api/booking` or `/api/onboarding`) or directly within Server Components. This can lead to a more granular control over access logic, but requires discipline to ensure consistency across the application.
*   **Vercel Integrations:** The inclusion of `Analytics` and `SpeedInsights` from Vercel in `src/app/layout.tsx` indicates a commitment to monitoring application performance and user behavior with minimal configuration, complementing the more detailed product event tracking provided by `PostHogProvider`.
*   **Dynamic Metadata:** Implementing `generateMetadata` in dynamic routes like `src/app/p/[slug]/page.tsx` is a deliberate choice to enhance SEO. It ensures that each professional's page has unique, relevant metadata, which is crucial for discoverability.

## Potential Improvements

While the current App Router implementation is functional, several areas could be considered for refinement:

1.  **Centralized Authentication Logic for Server Components:** In `src/app/p/[slug]/page.tsx`, the `supabase.auth.getUser()` call is made directly. If many Server Components require user authentication or authorization checks, abstracting this into a reusable function or a higher-order Server Component could reduce code duplication and improve maintainability. This would make it easier to apply consistent authentication policies across the application.
2.  **Route Group Layout for Authentication:** The description mentions an `(auth)` route group, but `src/app/(auth)/layout.tsx` is not found. If the intention was to have a dedicated layout for authentication-related pages (e.g., login, register), implementing this layout would provide a consistent UI and potentially centralize authentication-specific logic or providers. Without it, each auth-related page might need to manage its own layout and dependencies, leading to inconsistencies.
3.  **Optimizing Related Professional Data Fetching:** In `src/app/p/[slug]/page.tsx`, the application first fetches `allRelated` professionals and then makes a separate call to `getProStats` for their ratings and review counts. While functional, this could be optimized. If `getProStats` could be integrated into the Drizzle query for `professionals` (e.g., using subqueries or Drizzle relations if defined), it would reduce the number of database roundtrips and simplify the data aggregation logic.
4.  **Error Handling for `notFound()`:** The `notFound()` function is used in `src/app/p/[slug]/page.tsx` if a professional is not found or is inactive. While effective for displaying a 404 page, consider adding logging or monitoring around these specific conditions, especially for `prof.active` being false, to gain insights into why inactive profiles are being accessed.
