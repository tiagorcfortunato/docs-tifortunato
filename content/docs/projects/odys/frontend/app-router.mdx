# App Router

Odys leverages the Next.js App Router to structure its frontend, embracing a modern approach to web development that prioritizes performance, developer experience, and scalability. This architecture allows for a clear separation of concerns, enabling server-side data fetching and rendering while integrating client-side interactivity where needed.

## Overview

The `odys` frontend is built around the `app` directory structure, a core feature of Next.js that introduces server components and a file-system-based routing paradigm. This design choice allows pages to be rendered on the server by default, reducing the amount of JavaScript shipped to the client and improving initial page load times.

At the root of the application, `src/app/layout.tsx` defines the global layout and metadata, wrapping the entire application. This file is a Server Component, meaning it runs exclusively on the server and can directly fetch data or interact with server-side resources.

The application also utilizes dynamic routes, such as `src/app/p/[slug]/page.tsx`, to create personalized pages for each professional. This pattern allows for clean, SEO-friendly URLs that map directly to database entities. While the `src/app/(auth)/layout.tsx` file is not present in the current codebase, the `(auth)` route group structure indicates an intention to group authentication-related routes under a common layout without affecting the URL path, a common and effective pattern in the App Router.

Notably, `odys` does not employ Next.js middleware. This decision simplifies the request lifecycle, shifting any global request-level logic, such as authentication checks or redirects, to be handled within individual server components or API routes.

## Root Layout

The `src/app/layout.tsx` file serves as the foundational layout for the entire `odys` application. As a Server Component, it's responsible for defining the `<html>` and `<body>` tags, applying global styles, and injecting essential third-party providers and analytics scripts.

The `metadata` object within this file is crucial for SEO, providing default `title`, `description`, `openGraph`, and `twitter` properties. This static metadata is augmented by dynamic metadata on specific pages, ensuring that search engines and social media platforms accurately represent the content. For instance, the `metadataBase` is set to `https://odys.com.br`, establishing the base URL for all relative metadata URLs.

Two distinct font families, `Plus_Jakarta_Sans` and `Montserrat`, are loaded and configured with specific weights, ensuring a consistent and branded typographic experience across the application. Global CSS, defined in `globals.css`, is imported here, applying base styles.

The `RootLayout` integrates several client-side components:
*   `Toaster`: Provides rich, colored toast notifications for user feedback.
*   `PostHogProvider`: Initializes PostHog for product analytics, allowing `odys` to track user interactions and feature usage.
*   `CookieBanner`: Manages cookie consent, adhering to privacy regulations.

For performance and analytics, `odys` also includes `Analytics` and `SpeedInsights` from Vercel. These tools provide anonymous page-view counts and real-user Core Web Vitals (like LCP, INP, CLS) without relying on cookies, complementing the more detailed product event tracking offered by PostHog.

An inline script is strategically placed in the `<head>` to prevent a "flash of unstyled content" (FOUC) by applying the user's saved theme (dark or light) before the page renders. Additionally, an accessibility-focused "Skip to main content" link is included, which becomes visible only on keyboard focus, allowing screen-reader and keyboard users to bypass navigation on every route.

## Professional Booking Page

The `src/app/p/[slug]/page.tsx` file is a dynamic route designed to display individual professional profiles and facilitate appointment bookings. The `[slug]` segment in the path allows each professional to have a unique, human-readable URL, such as `/p/dr-ana-silva`.

This page is a Server Component, meaning all initial data fetching occurs on the server before the page is sent to the client. This approach minimizes loading spinners and ensures that the page is fully rendered and SEO-friendly from the first byte.

### Dynamic Metadata Generation

The `generateMetadata` function is an asynchronous server function that dynamically sets the page's SEO metadata based on the professional's `slug`. It queries the `professionals` table using `drizzle-orm` to retrieve the professional's `name`, `profession`, and `bio`. If a professional is not found, it defaults to a generic "Profissional não encontrado" title. This ensures that each professional's page has accurate and descriptive metadata, which is crucial for search engine visibility and social media sharing.

### Server-Side Data Fetching

Within the `BookingPage` component, several database queries are executed to gather all necessary information for rendering the professional's profile and booking interface:

1.  **Professional Details**: The primary professional data is fetched from the `professionals` table using the `slug` parameter. This includes details like `name`, `profession`, `sessionDuration`, `sessionPrice`, `paymentType`, `pixKey`, `bio`, `avatarUrl`, and `welcomeMessage`. The `active` status is also checked, and if the professional is not found or inactive, the `notFound()` helper from Next.js is invoked, rendering a 404 page.
2.  **User Authentication**: Supabase's server-side client (`createClient`) is used to determine the current user's authentication status. This allows the page to identify if the visitor is the professional themselves (`isOwner`) or a logged-in client.
3.  **Client Data**: If a user is logged in but is not the owner of the page, their existing client data (name, phone, email) is fetched from the `clients` table. This data is then used to pre-fill the booking form, enhancing the user experience.
4.  **Related Professionals**: To offer discovery, the page fetches other professionals who share the same `profession`. This query selects a subset of professional details and then filters out the current professional. The `getProStats` utility is then used to fetch aggregated rating and review counts for these related professionals, which are displayed on their respective `ProfessionalCard` components.
5.  **Reviews**: All reviews for the current professional are fetched from the `reviews` table, performing an `innerJoin` with the `clients` table to display the client's name alongside their review. The average rating and total review count are calculated from this data.

### Client Component Integration

While the page itself is a Server Component, it seamlessly integrates several Client Components for interactive elements:
*   `FollowButton`: Allows users to follow a professional.
*   `ProfessionalCard`: Displays summary information for related professionals.
*   `BookingWidget`: The core interactive component for scheduling appointments, pre-filled with client data if available.
*   `LogoutButton` and `ThemeToggle`: Provide user-specific actions and UI preferences.
*   `OdysLogo` and `ProfessionalLocationCard`: Display static branding and location details.

This hybrid approach ensures that static content and initial data are delivered quickly from the server, while dynamic interactions are handled efficiently on the client.

## Design decisions

The architectural choices within the `odys` frontend, particularly regarding the App Router, reflect a deliberate strategy to optimize for performance, maintainability, and developer experience.

The decision to use **Server Components** for pages like `src/app/layout.tsx` and `src/app/p/[slug]/page.tsx` is fundamental. This allows `odys` to perform data fetching directly on the server, interacting with the `professionals`, `clients`, and `reviews` tables using `drizzle-orm` without exposing database credentials to the client. This reduces the client-side JavaScript bundle size, improves initial page load times, and simplifies the data fetching logic by keeping it co-located with the rendering logic. The trade-off is that server components cannot use React hooks like `useState` or `useEffect` directly, necessitating the use of client components for interactivity.

**Dynamic routes**, exemplified by `src/app/p/[slug]/page.tsx`, were chosen to provide clean, semantic URLs for professional profiles. This is a significant benefit for SEO, as search engines can easily index individual professional pages. The `generateMetadata` function further enhances this by allowing dynamic, content-specific metadata to be generated on the server, ensuring accurate titles and descriptions for each profile.

The conceptual use of **route groups**, such as `(auth)`, even if the specific layout file is not provided, demonstrates an intention to organize routes logically without impacting the URL structure. This allows for shared layouts (e.g., for authentication pages) or specific data fetching patterns to be applied to a group of routes, promoting code reuse and modularity.

The explicit choice to operate **without Next.js middleware** simplifies the request processing pipeline. Instead of a global middleware function intercepting all requests, `odys` handles authentication and authorization checks directly within the server components or API routes. For instance, `src/app/p/[slug]/page.tsx` checks `supabase.auth.getUser()` to determine if the visitor is the page owner or a logged-in client. This approach can make debugging easier by localizing logic to specific routes, though it might require duplicating some checks across multiple server components if not carefully abstracted.

Finally, the **co-location of data fetching with components** (e.g., `db.select().from(professionals).where(...)` directly in `BookingPage`) is a direct benefit of server components. This eliminates the need for client-side data fetching libraries or complex API layers for initial page loads, making the data flow more transparent and easier to reason about.

## Potential improvements

1.  **Implement `(auth)` Route Group Layout**: The `src/app/(auth)/layout.tsx` file is currently missing. Implementing this layout would allow for a dedicated UI and logic wrapper for authentication-related pages (e.g., login, registration, password reset). This would centralize common elements like authentication forms, branding, or specific navigation for authenticated users, avoiding duplication across individual authentication pages.
2.  **Parallelize Data Fetching in `BookingPage`**: In `src/app/p/[slug]/page.tsx`, the `BookingPage` component performs several asynchronous data fetches (for `prof`, `clientData`, `allRelated`, `relatedStats`, and `profReviews`). While these are `await`ed sequentially, many of them are independent and could be executed in parallel using `Promise.all`. For example, fetching `prof`, `allRelated`, and `profReviews` could happen concurrently to reduce the total server-side rendering time.
3.  **Optimize Related Professionals Query**: The current implementation in `src/app/p/[slug]/page.tsx` fetches `allRelated` professionals (all professionals with the same `profession`) and then filters out the current professional in JavaScript (`allRelated.filter(p => p.slug !== slug && p.id !== prof.id).slice(0, 4)`). This could be optimized by adding a `WHERE` clause to the Drizzle query to exclude the current professional's `id` and `slug` directly at the database level, potentially reducing the amount of data transferred and processed in memory.
4.  **Refine `generateMetadata` Error Handling**: The `generateMetadata` function in `src/app/p/[slug]/page.tsx` returns a generic title if the professional is not found. While the main `BookingPage` component correctly calls `notFound()`, the metadata function could be more explicit in its error handling or return a more specific "Not Found" metadata to better reflect the page's state before the full component renders.
