# App Router

Odys leverages the Next.js App Router to structure its frontend application, embracing a paradigm that prioritizes Server Components by default. This architectural choice aims to deliver a performant and maintainable user experience by shifting much of the rendering and data fetching logic to the server. The application organizes its routes using a file-system based approach, including dynamic segments and route groups, while notably opting out of a global `middleware.ts` file.

## Overview

The `src/app` directory forms the core of Odys's frontend, defining the application's routes and UI hierarchy. Each folder within `app` typically represents a route segment, with `page.tsx` files rendering the UI for a specific route and `layout.tsx` files defining shared UI for a segment and its children.

A key characteristic of the App Router is that components are Server Components by default. This means that components like the root `layout.tsx` and dynamic pages such as `p/[slug]/page.tsx` execute on the server, allowing direct database access and efficient data fetching before the page is sent to the client. Client Components, identified by the `"use client"` directive, are then used for interactive UI elements that require browser-side JavaScript.

Odys also utilizes route groups, indicated by parentheses in directory names, such as `(auth)`. While the specific `layout.tsx` for the `(auth)` group is not present in the provided code, the existence of such a group implies an intention to organize authentication-related routes under a common layout or set of behaviors without affecting the URL path.

Notably, Odys does not employ a global `middleware.ts` file. This suggests that authentication and authorization checks are handled either within individual Server Components or API routes, or through other mechanisms like Supabase's server-side client, rather than a centralized Next.js middleware layer.

## Root Layout

The `src/app/layout.tsx` file defines the root layout for the entire Odys application. As a Server Component, it sets up the fundamental HTML structure, including the `<html>` and `<body>` tags, and imports global CSS styles. The root `<html>` tag is configured with `lang="pt-BR"` (src/app/layout.tsx:30).

This layout is responsible for:

*   **Metadata Generation**: The `metadata` export defines static metadata for the site, including `title`, `description`, `openGraph` properties (such as `authors` and `publishedTime` as seen in `src/app/layout.tsx:20-21`), and `twitter` card details. This is crucial for SEO and social media sharing, providing a consistent brand presence across the application. The `metadataBase` is set to `https://odys.com.br`.
*   **Font Loading**: It imports and configures two Google Fonts, `Plus_Jakarta_Sans` and `Montserrat`, using Next.js's font optimization features. These fonts are then applied globally via CSS variables.
*   **Global Providers**: The layout wraps the `children` (the rest of the application) with several providers:
    *   `PostHogProvider`: For product analytics, allowing Odys to track user interactions and feature usage.
    *   `Toaster`: A UI component for displaying notifications and messages to the user, configured with `richColors` and positioned `top-right`.
    *   `CookieBanner`: A client component responsible for handling cookie consent, ensuring compliance with privacy regulations.
*   **Performance and Analytics**: It integrates Vercel's `Analytics` and `SpeedInsights` components. These provide anonymous page-view counts and real-user Core Web Vitals data, respectively, complementing the more product-event-focused `PostHogProvider`.
*   **Accessibility**: An "Skip to main content" link is included, which is visually hidden (`sr-only`) but becomes visible on keyboard focus, allowing users of assistive technologies to bypass repetitive navigation elements.
*   **Theme Initialization**: A small inline script is injected into the `<head>` to prevent a "flash of unstyled content" (FOUC) by applying the user's saved theme preference (`dark` or `light`) before the page renders.

## Dynamic Professional Page

The `src/app/p/[slug]/page.tsx` file implements a dynamic route for displaying individual professional profiles and facilitating booking. This page is a Server Component, allowing it to fetch all necessary data directly from the database before rendering.

### Metadata Generation

The `generateMetadata` function is an asynchronous Server Component feature that dynamically generates metadata for the page based on the `slug` parameter. It queries the `professionals` table to retrieve the professional's `name`, `profession`, `bio`, and `avatarUrl`. If a professional is not found, it returns a generic "Profissional não encontrado" title. Otherwise, it constructs a specific `title` and `description` for SEO, including the professional's name and profession, and uses their `avatarUrl` for Open Graph images.

### Booking Page Component

The default export, `BookingPage`, is an `async` Server Component that receives the `slug` from the URL parameters. It performs several data fetching operations:

1.  **Professional Data**: It fetches the professional's details from the `professionals` table using Drizzle ORM, filtering by `slug`. If the professional is not found or is inactive (`prof.active` is false), it calls `notFound()` from `next/navigation`, which renders the closest `not-found.tsx` file.
2.  **User Authentication**: It uses `createClient()` from `@/lib/supabase/server` to get a server-side Supabase client and then `supabase.auth.getUser()` to determine the current user. This allows the page to identify if the visitor is the owner of the profile (`isOwner`) or a logged-in client.
3.  **Client Data Pre-fill**: If a user is logged in and is not the profile owner, the component attempts to fetch their existing `clients` data (name, phone, email) to pre-fill the booking form, enhancing user experience.
4.  **Related Professionals**: It queries the `professionals` table for other professionals sharing the same `profession` as the current one, excluding the current professional. It then fetches aggregated statistics (average rating, review count) for these related professionals using `getProStats`.
5.  **Reviews**: It fetches all `reviews` for the current professional, joining with the `clients` table to display the client's name. It then calculates the `totalReviews` and `avgRating`.

The UI renders a comprehensive professional profile, including:

*   A navigation bar with the `OdysLogo`, `ThemeToggle`, and conditional links for dashboard access or login/logout. The `OdysLogo`'s `href` dynamically links to `/dashboard` if the user is the profile owner or a professional, to `/c` if the user is a client, or to `/` for unauthenticated users (`src/app/p/[slug]/page.tsx:109`).
*   An alert message if the owner is viewing their public page.
*   A header displaying the professional's `name`, `profession`, `sessionDuration`, `sessionPrice`, `avgRating`, `totalReviews`, `bio`, and `avatarUrl`.
*   A `FollowButton` (a Client Component) for non-owners to follow the professional.
*   A welcome message, either from `prof.welcomeMessage` or a default.
*   A `ProfessionalLocationCard` displaying service type and address details.
*   The `BookingWidget`, a crucial Client Component that handles the interactive booking process. It receives various professional details and pre-filled client data as props.
*   A section for displaying `reviews`, including client names, ratings, comments, and dates.
*   A "Veja também" section showcasing `ProfessionalCard` components for related professionals.

This structure demonstrates a clear separation of concerns: data fetching and initial rendering on the server, and interactive elements delegated to client components.

## Design Decisions

### Server Components First

The primary design decision is to embrace Server Components as the default. This choice offers several advantages:

*   **Performance**: Data fetching occurs on the server, often closer to the database, reducing latency compared to client-side fetches. The HTML is streamed to the client, allowing users to see content faster.
*   **Security**: Sensitive data fetching logic and API keys remain on the server, never exposed to the client browser. For instance, the `BookingPage` directly queries the `professionals` and `reviews` tables without needing a separate API layer for these reads.
*   **Simpler Data Fetching**: Direct database access within components (e.g., `db.select().from(professionals)`) simplifies the data flow, eliminating the need for client-side data fetching libraries or complex API route structures for initial page loads.

The trade-off is that interactivity requires explicit opt-in with `"use client"`, which means careful consideration of where state and event handlers are truly needed.

### Route Groups for Organization

The use of route groups like `(auth)` indicates a desire to organize routes logically without impacting the URL structure. This is beneficial for applying specific layouts, styling, or data fetching strategies to a subset of routes. For example, all authentication-related pages might share a distinct layout that differs from the main application layout. This keeps the file system clean and maintainable.

### Absence of Global Middleware

Odys's decision not to use a global `middleware.ts` file implies that route protection and request manipulation are handled at a more granular level. This could mean:

*   **Component-level checks**: As seen in `BookingPage`, authentication checks (`supabase.auth.getUser()`) are performed directly within the Server Component. This allows for fine-grained control over data access and UI rendering based on user status.
*   **API Route-level checks**: Each API route (`/api/*`) likely implements its own authentication and authorization logic.
*   **Simplicity**: For applications with less complex global routing requirements, avoiding middleware can simplify the request lifecycle and debugging.

The trade-off is that common logic (like user authentication or header manipulation) might be duplicated across multiple components or API routes, potentially leading to inconsistencies if not managed carefully.

### Dynamic Metadata with `generateMetadata`

Using `generateMetadata` for dynamic routes like `p/[slug]` is a deliberate choice to enhance SEO. Instead of static metadata, each professional's page can have a unique, descriptive title and description, directly pulled from the database. This improves search engine visibility and the quality of shared links on social media.

## Potential improvements

1.  **Centralize Authentication/Authorization Logic**: In `src/app/p/[slug]/page.tsx`, the `createClient()` and `supabase.auth.getUser()` calls are repeated. While this is a Server Component, abstracting this into a reusable server utility function or a custom hook (if applicable for server components) could reduce duplication and make authentication logic easier to manage and test across multiple pages or API routes.
2.  **Refine Data Fetching for Related Professionals**: The `BookingPage` component fetches `allRelated` professionals and then filters them in memory (`allRelated.filter(...)`). While this works for small datasets, for a large number of professionals, it would be more efficient to perform the filtering directly in the Drizzle query using `drizzle-orm`'s `notEq` operator to exclude the current professional by `slug` and `id` at the database level.
3.  **Implement Caching for `getProStats`**: The `getProStats` function is called with an array of professional IDs. If multiple pages or components require these statistics, implementing a caching layer (e.g., using `React.cache` or a custom memoization strategy) could prevent redundant database queries, especially if the stats don't change frequently.
4.  **Error Handling for `generateMetadata`**: Currently, `generateMetadata` returns a generic title if `prof` is not found. While functional, a more specific error handling mechanism could be considered, perhaps logging the missing slug or returning a more informative metadata object that indicates the resource was not found, which could be useful for debugging or specific SEO strategies.
