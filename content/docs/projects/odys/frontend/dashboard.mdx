# Professional Dashboard

The professional dashboard serves as the primary interface for Odys professionals to manage their practice. It provides an overview of daily operations, upcoming appointments, client interactions, and performance metrics. This documentation explores the architecture behind the dashboard, detailing how data is fetched, presented, and how user interactions are handled across its main components: the layout, the main dashboard page, and the persistent sidebar navigation.

## Overview

The dashboard is structured as a Next.js application, leveraging server components for efficient data fetching and client components for interactive UI elements. The `src/app/dashboard/layout.tsx` file acts as the root layout for all dashboard sub-routes, handling initial user authentication and professional profile retrieval. It then wraps the main content with a `Sidebar` component, defined in `src/app/dashboard/sidebar.tsx`, and the specific page content, such as the main dashboard view in `src/app/dashboard/page.tsx`. This separation ensures that common elements like navigation and authentication are managed consistently across the entire dashboard section.

## Dashboard Layout (`src/app/dashboard/layout.tsx`)

The `DashboardLayout` component is a server component responsible for establishing the authenticated context for all nested dashboard routes. Upon a request, it first initializes a Supabase server client using `createClient` to retrieve the current user's session. If no user is found, the request is redirected to `/login`, enforcing authentication for all dashboard access.

Once authenticated, the layout queries the `professionals` table using Drizzle ORM to fetch the professional's profile associated with the `user.id`. This is a critical step, as the entire dashboard experience is tailored to the professional's data. If a professional profile does not exist (e.g., a new user who hasn't completed onboarding), they are redirected to `/onboarding`. This ensures that only fully registered professionals can access the dashboard.

The fetched `professional` data, including their `name`, `slug`, `plan`, and `trialEndsAt`, is then passed as props to the `Sidebar` component. This allows the sidebar to display personalized information and conditionally render navigation items based on the professional's subscription plan or trial status. The layout also includes a `PostHogIdentify` component, which is likely used for analytics to associate user actions with their specific `userId`. The main content of each dashboard sub-route is rendered within the `children` prop, ensuring it's wrapped by the authenticated context and the sidebar.

## Dashboard Page (`src/app/dashboard/page.tsx`)

The `DashboardPage` component is the primary view for the professional dashboard, designed to provide a comprehensive overview of key metrics and upcoming activities. As a server component, it performs extensive data fetching directly from the database using Drizzle ORM.

The page begins by fetching the current user and their associated professional profile, similar to the layout. It then proceeds to gather various pieces of information concurrently using `Promise.all` for efficiency:

*   **Appointments**: It fetches `todayAppointments` and up to 20 `upcomingAppointments` from the `appointments` table, joining with the `clients` table to display client names and phone numbers. These queries filter appointments based on the `professionalId` and `startsAt` timestamps, using `gte` and `lte` for today's appointments and `gt` for upcoming ones.
*   **Client and Appointment Counts**: It retrieves the `totalClients` from the `clients` table and `monthlyAppointments` from the `appointments` table, both filtered by `professionalId`.
*   **Reputation**: If `reviewCount` is greater than 0, it shows the `avgRating` and up to 2 recent reviews that contain comments (from a query fetching up to 3), providing a quick overview of the professional's public perception.
*   **Profile Completeness**: It checks the `availability` table to determine if the professional has set up their availability, which is a factor in the `findProfileGaps` utility.

The page then uses this data to render a dynamic user interface:

*   **Welcome Experience**: A `WelcomeCard` is displayed only if the professional has `totalClients === 0`, guiding new users to share their public profile link.
*   **Plan and Trial Banners**: It conditionally renders banners related to the professional's subscription plan and trial status. This includes warnings if the professional is `isNearClientLimit` or `isAtClientLimit` (based on `PLANS` and `totalClients`), or `isNearMonthlyLimit` or `isAtMonthlyLimit` (based on `monthlyAppointments`). It also shows a `TrialBanner` if a trial is available, or a "Trial Pro ativo" message indicating `daysLeft` if a trial is active.
*   **Profile Completeness Nudge**: If `profileGaps` are identified by `findProfileGaps` and the professional has at least one client, a banner encourages them to complete their profile settings.
*   **Greeting and Stats**: A personalized greeting and a set of three key statistics are displayed: today's appointments, pending confirmations, and total clients.
*   **Reputation Section**: If `reviewCount` is greater than 0, it shows the `avgRating` and `recentReviews`, providing a quick overview of the professional's public perception.
*   **Appointment Lists**: `todayAppointments` and `upcomingAppointments` are rendered in separate sections. Each appointment displays time, client name, phone, and status. For `pending_confirmation` or `confirmed` appointments, the `AppointmentActions` component is included, allowing the professional to manage the appointment status.
*   **Revenue**: If revenue from today's captured payments is greater than zero, it is calculated using the `formatCurrency` helper, but not currently displayed.

Helper functions like `getToday`, `formatTime`, `formatCurrency`, and the `STATUS_LABEL` map are defined locally to assist with data presentation.

## Dashboard Sidebar (`src/app/dashboard/sidebar.tsx`)

The `Sidebar` component is a client component, indicated by `"use client"`, which allows it to manage its own state (`mobileOpen`) and interact with client-side hooks like `usePathname` and `useRouter`. It receives `professionalName`, `professionalSlug`, `plan`, and `trialEndsAt` as props from the `DashboardLayout`.

The sidebar provides persistent navigation for the dashboard. Its structure includes:

*   **Logo and Utilities**: An `OdysLogo`, `NotificationBell`, and `ThemeToggle` are present at the top, along with a close button for the mobile drawer.
*   **Trial Banner**: A compact trial banner is displayed if `daysLeft` is not null, prompting the professional to subscribe.
*   **Navigation Links**: The `NAV` array defines the dashboard's main navigation items, each with an `href`, `label`, `icon`, and a `proOnly` flag. The `isActive` function determines the styling of the current route.
    *   Crucially, if an item is marked `proOnly` and the `activePlan` is "free", the link is rendered as "locked" and redirects to the `/dashboard/plans` page, guiding users towards an upgrade.
*   **External Links**: Links to the professional's public page (`/p/[slug]`) and a "Client Mode" (`/c`) are also included.
*   **Professional Profile**: At the bottom, the sidebar displays the professional's initials, full name, and their current `plan` (e.g., "Free", "Basic", "Pro", "Premium") with a corresponding `PLAN_COLOR` and `PLAN_LABEL`.
*   **Logout Functionality**: A "Sair" button allows the professional to log out using the Supabase client, redirecting them to `/login`.

The `Sidebar` is designed to be responsive, rendering as a fixed sidebar on desktop and a slide-out drawer on mobile, controlled by the `mobileOpen` state.

## Design Decisions

The dashboard's architecture reflects several deliberate design choices:

*   **Server-Side Data Fetching**: By making `DashboardLayout` and `DashboardPage` server components, Odys centralizes data access on the server. This reduces the amount of JavaScript shipped to the client, improving initial page load performance and SEO. All database interactions, including complex queries with `drizzle-orm` using `eq`, `and`, `gte`, `lte`, `count`, `gt`, `desc`, and `sql` aggregations, occur securely on the server. This also simplifies data consistency, as the server always fetches the latest state.
*   **Client-Side Interactivity**: The `Sidebar` component is explicitly marked `"use client"` because it requires client-side state management (`useState`) for its mobile drawer functionality and client-side routing (`usePathname`, `useRouter`) for active link highlighting and navigation. The Supabase client is also used for the logout action, which is inherently a client-side interaction. This clear separation allows for dynamic UI elements without compromising the benefits of server-side rendering for static content.
*   **Drizzle ORM for Type Safety and Performance**: The use of Drizzle ORM provides a type-safe way to interact with the database schema, which includes 11 tables like `professionals`, `appointments`, `clients`, `reviews`, and `availability`. This reduces the likelihood of runtime errors due to schema mismatches and allows for complex SQL queries to be constructed programmatically, such as the aggregation for `avg` rating and `count` of reviews.
*   **Progressive Disclosure of Information and Nudges**: The dashboard employs conditional rendering extensively to guide the user experience. The `WelcomeCard`, trial banners, plan limit warnings, and profile completeness nudges (`findProfileGaps`) are all strategically displayed based on the professional's current status, plan, and profile data. This approach aims to provide relevant information and calls to action at the right time, preventing information overload for new users and highlighting critical actions for existing ones.
*   **Centralized Business Logic**: Logic related to subscription plans (`PLANS` from `@/lib/stripe`) and trial management (`trialDaysLeft`, `effectivePlan` from `@/lib/plan-guard`) is encapsulated in dedicated utility files. This ensures consistency in how plan limits and trial statuses are calculated and applied across different parts of the application, such as the dashboard page and the sidebar.

## Potential Improvements

1.  **Consolidate Appointment Rendering Logic**: The rendering of `todayAppointments` and `upcomingAppointments` in `src/app/dashboard/page.tsx` shares a significant amount of identical JSX structure and styling. This duplication, particularly within the `divide-y` sections, could be refactored into a single, reusable `AppointmentList` component. This component could accept an array of appointments and a `showDate` boolean prop to conditionally display the date for upcoming appointments, reducing code repetition and improving maintainability.
2.  **Centralize Status Labels**: The `STATUS_LABEL` object, which maps appointment statuses to their display labels and colors, is currently defined directly within `src/app/dashboard/page.tsx`. If these status definitions are used in other parts of the application (e.g., appointment detail pages, client views), centralizing this object in a shared `constants` or `utils` file would prevent inconsistencies and make updates easier. For example, moving it to `src/lib/constants/appointment-statuses.ts` would allow `src/app/dashboard/page.tsx` and other components to import it.
3.  **Optimize Initial Data Fetching for Professional Profile**: In `src/app/dashboard/layout.tsx` and `src/app/dashboard/page.tsx`, the professional's profile is fetched independently. While Next.js's caching might mitigate some redundancy, if the `professional` object is frequently needed across many server components within the dashboard, consider using a React Context (if client-side) or a dedicated data fetching hook/utility that memoizes or caches the professional data for the request lifecycle (if server-side) to avoid redundant database queries for the same `professional.id` within a single request. This could be particularly relevant if the `professional` object grows larger or if more components directly query it.
