# Professional Dashboard

The professional dashboard serves as the central hub for professionals using Odys, providing an overview of their practice, upcoming appointments, client interactions, and key metrics. It's designed to offer a quick glance at the day's agenda and highlight important actions or notifications, while also providing navigation to deeper insights and settings.

## Overview

The dashboard is structured around a persistent sidebar and a main content area, implemented using Next.js server components for efficient data fetching and rendering. The `src/app/dashboard/layout.tsx` file acts as the primary entry point, handling user authentication and fetching core professional data. This data is then passed to the `Sidebar` component, while the `DashboardPage` component (`src/app/dashboard/page.tsx`) re-fetches necessary professional data.

The `DashboardPage` itself is responsible for fetching and displaying all the dynamic content, such as today's and upcoming appointments, client statistics, and review summaries. The `src/app/dashboard/sidebar.tsx` component, a client component, provides interactive navigation and displays the professional's current plan and trial status.

## Dashboard Layout

The `src/app/dashboard/layout.tsx` file is a server component that wraps all dashboard routes. Its primary responsibilities include:

1.  **Authentication Check**: It uses `createClient` from `@/lib/supabase/server` to verify the user's session. If no user is found, it immediately redirects to `/login`, ensuring that only authenticated users can access the dashboard.
2.  **Professional Profile Retrieval**: After successful authentication, it queries the database using Drizzle ORM to fetch the `professional` record associated with the authenticated `userId`. This query targets the `professionals` table, which contains 32 columns detailing the professional's profile, settings, and subscription status.
3.  **Onboarding Redirection**: If a `professional` record is not found for the authenticated user, it implies the user has not completed the onboarding process, so they are redirected to `/onboarding`. This ensures that all dashboard users have a fully set up professional profile.
4.  **Sidebar Initialization**: The layout renders the `Sidebar` component, passing essential professional details like `professionalName`, `professionalSlug`, `plan`, and `trialEndsAt`. This allows the sidebar to display personalized information and manage navigation based on the professional's status.
5.  **Analytics Integration**: It includes the `PostHogIdentify` component, which is crucial for tracking user activity and identifying the user in PostHog analytics, providing insights into dashboard usage.

This layout structure centralizes critical authentication and initial data loading, preventing individual dashboard pages from needing to repeat these checks.

## Dashboard Page

The `src/app/dashboard/page.tsx` file is the main content area of the dashboard, also implemented as an `async` server component. It aggregates and displays various pieces of information relevant to a professional's daily operations:

1.  **Data Fetching**:
    *   It re-fetches the `professional` record, similar to the layout, to ensure it has the most up-to-date information for rendering the page content.
    *   It retrieves `todayAppointments` and `upcomingAppointments` by querying the `appointments` table, performing an `innerJoin` with the `clients` table to fetch client names and phone numbers. These queries filter appointments based on `professionalId` and `startsAt` timestamps.
    *   A `Promise.all` block efficiently fetches several aggregate statistics concurrently:
        *   `totalClients`: A count of all clients associated with the professional from the `clients` table.
        *   `monthlyAppointments`: A count of appointments within the current month from the `appointments` table.
        *   `reviewStats`: The average `rating` and total count of `reviews` from the `reviews` table.
        *   `recentReviews`: The 3 most recent reviews, including client names, from the `reviews` table, joined with `clients`.
        *   `availabilityCount`: A count of entries in the `availability` table, indicating if the professional has set up their working hours.
2.  **Derived State and Business Logic**:
    *   The page calculates `avgRating` and `reviewCount` from the fetched `reviewStats`.
    *   It uses `findProfileGaps` from `@/lib/profile-completeness` to identify missing profile information, such as `bio`, `addressLine`, or `avatarUrl`, and whether `availability` has been set.
    *   It determines `daysLeft` in the professional's trial period and their `effectivePlan` using helpers from `@/lib/plan-guard`.
    *   It checks for plan limits (`isAtClientLimit`, `isNearClientLimit`, `isAtMonthlyLimit`, `isNearMonthlyLimit`) against the `PLANS` defined in `@/lib/stripe`.
    *   It calculates `pendingCount` for appointments awaiting confirmation and `revenue` from today's captured payments.
3.  **User Interface**:
    *   **Conditional Banners**: The page dynamically displays various banners based on the professional's status:
        *   A `WelcomeCard` for new professionals with zero clients, guiding them to share their public profile.
        *   Alerts for reaching or approaching plan limits, prompting upgrades.
        *   A `TrialBanner` for free users without an active trial to opt into a trial, and a specific banner for active trials showing `daysLeft`.
        *   A profile completeness banner, suggesting missing information if `profileGaps` are found.
    *   **Key Statistics**: Displays cards for "Today's Appointments", "Pending Appointments", and "Total Clients".
    *   **Reputation Section**: If `reviewCount` is greater than 0, it shows the `avgRating` and `recentReviews`, linking to the public profile.
    *   **Appointment Lists**: Presents `todayAppointments` and `upcomingAppointments` in separate sections, each appointment showing time, client name, phone, and status.
    *   **Appointment Actions**: For `pending_confirmation` or `confirmed` appointments, the `AppointmentActions` component is rendered, allowing professionals to manage appointment statuses directly.
    *   **Revenue Display**: If `revenue` is greater than 0, it shows the total revenue for the day.
4.  **Helper Functions**: Includes `getToday` for date range calculation, `formatTime` for display, `formatCurrency` for Brazilian Real formatting, and `STATUS_LABEL` for mapping appointment statuses to human-readable labels and colors.

## Dashboard Sidebar

The `src/app/dashboard/sidebar.tsx` component is a client component responsible for the dashboard's navigation and user profile display.

1.  **Props**: It receives `professionalName`, `professionalSlug`, `plan`, and `trialEndsAt` from the `DashboardLayout` server component.
2.  **Navigation Links**: The `NAV` array defines the dashboard's primary navigation items, including their `href`, `label`, `icon`, and a `proOnly` flag.
3.  **Active Link Styling**: It uses `usePathname` from `next/navigation` to determine the currently active link and apply distinct styling.
4.  **Feature Gating**: If a navigation item has `proOnly: true` and the `activePlan` is `free`, the link is rendered as "locked" and redirects to the `/dashboard/plans` page, encouraging users to upgrade.
5.  **User Profile and Plan Display**: It displays the professional's initials, full name, and their `activePlan` (e.g., "Free", "Basic", "Pro", "Premium"), indicating if they are on a trial.
6.  **Logout Functionality**: The `handleLogout` function uses `createClient` from `@/lib/supabase/client` to sign out the user and redirects them to `/login`.
7.  **Mobile Responsiveness**: The sidebar implements a responsive design, appearing as a fixed sidebar on desktop (`md:flex`) and a toggleable drawer on mobile, controlled by the `mobileOpen` state.
8.  **Utility Components**: It integrates `NotificationBell` and `ThemeToggle` for additional dashboard functionality.

## Design decisions

The architecture of the dashboard, split across `layout.tsx`, `page.tsx`, and `sidebar.tsx`, reflects several deliberate design choices:

*   **Server-Side Data Fetching for Performance**: By making `DashboardLayout` and `DashboardPage` `async` server components, data fetching for authentication, professional details, appointments, and statistics occurs entirely on the server. This minimizes client-side JavaScript bundle size, reduces client-side data waterfalls, and allows for faster initial page loads. The database queries using Drizzle ORM are executed directly on the server, which is generally more efficient and secure than exposing API endpoints for every data requirement.
*   **Clear Separation of Concerns**:
    *   `DashboardLayout` focuses on global concerns: authentication, initial professional data loading, and providing the structural wrapper (sidebar + main content). This ensures that all dashboard routes benefit from authentication checks and initial data loading, though some data like the `professional` record is re-fetched by `DashboardPage`.
    *   `DashboardPage` is dedicated to presenting the dashboard's specific content and metrics. It aggregates various data points and orchestrates the display of conditional UI elements like banners and appointment lists.
    *   `Sidebar` is a client component, allowing for interactive elements like the mobile toggle and logout functionality, while receiving its core data (professional name, plan) as props from the server-rendered layout. This hybrid approach balances server-side rendering benefits with client-side interactivity where needed.
*   **Proactive User Guidance and Feature Gating**: The dashboard incorporates multiple banners and UI elements (`WelcomeCard`, trial banners, plan limit warnings, profile completeness nudges) to guide the professional. The `proOnly` flag in the `NAV` array, combined with `effectivePlan` and `trialDaysLeft` helpers, implements feature gating directly within the navigation. This design ensures that users are always aware of their plan's capabilities and are encouraged to complete their profile or upgrade their subscription.
*   **Optimized Data Retrieval with `Promise.all`**: The `DashboardPage` uses `Promise.all` to fetch multiple independent data sets (clients count, monthly appointments, reviews, availability) concurrently. This significantly reduces the total time spent waiting for database responses, improving the perceived performance of the dashboard.

## Potential improvements

1.  **Centralize Professional Data Fetching**: The `professional` record is fetched twice: once in `src/app/dashboard/layout.tsx` and again in `src/app/dashboard/page.tsx`. While Next.js might deduplicate identical fetches, explicitly passing the `professional` object from the layout to the page via React Context or a dedicated server-side data fetching utility could make the data flow more explicit and potentially avoid redundant database calls.
2.  **Standardize Appointment Status Labels**: The `STATUS_LABEL` object, which maps appointment statuses to display labels and colors, is currently defined directly within `src/app/dashboard/page.tsx`. If these labels and colors are used in other parts of the application (e.g., client-facing pages, reports), centralizing this definition in a shared `constants` file or a dedicated utility module would improve consistency and maintainability.
3.  **Client-Side Data Refresh after Appointment Actions**: The `AppointmentActions` component, used to change appointment statuses, is a client component. When an action (e.g., confirming an appointment) is performed, the `DashboardPage` server component's data does not automatically refresh. Implementing `router.refresh()` from `next/navigation` within the `AppointmentActions` component after a successful API call (e.g., to `/api/appointments/[id]`) would trigger a re-fetch of the server component data, ensuring the dashboard reflects the updated status without a manual page reload.
