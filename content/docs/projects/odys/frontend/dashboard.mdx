# Professional Dashboard

The professional dashboard serves as the central hub for professionals using Odys, providing a comprehensive overview of their business operations. It allows them to manage appointments, interact with clients, monitor performance, and configure their profile and services. This page details the architecture and implementation of the dashboard's main page, its persistent sidebar navigation, and the overarching layout that ties them together.

## Overview

The dashboard experience is structured around a `DashboardLayout` component, defined in `src/app/dashboard/layout.tsx`, which acts as the entry point for all professional-facing routes. This layout handles user authentication and fetches the core `professional` data, which is then passed down to the `Sidebar` component. A `Sidebar` component (`src/app/dashboard/sidebar.tsx`) provides consistent navigation across all dashboard sub-routes, displaying the professional's name, current plan, and trial status. The main content area, rendered by `src/app/dashboard/page.tsx`, presents a dynamic overview, including today's and upcoming appointments, key business metrics, and contextual banners for onboarding, plan limits, and profile completeness.

The data displayed throughout the dashboard is sourced directly from the Drizzle ORM schema, primarily interacting with the `professionals`, `appointments`, `clients`, `reviews`, and `availability` tables. The application also interacts with various API routes, such as `/api/appointments/[id]` for updating appointment statuses, and relies on utility functions like `trialDaysLeft` and `effectivePlan` from `@/lib/plan-guard` to manage subscription logic.

## Layout and Authentication

The `DashboardLayout` in `src/app/dashboard/layout.tsx` is an asynchronous server component, a design choice that enables direct and secure database access for initial data fetching. Upon loading, it first establishes a Supabase client using `createClient` from `@/lib/supabase/server` to retrieve the authenticated user's session. If no user is found, the system redirects to `/login`, ensuring that only authenticated professionals can access the dashboard.

Once authenticated, the layout queries the `professionals` table to fetch the specific professional's record using `db.select().from(professionals).where(eq(professionals.userId, user.id)).limit(1)`. This query is critical as it retrieves all necessary details about the professional, including their `name`, `slug`, `plan`, and `trialEndsAt` timestamp. If a professional record does not exist for the authenticated user, it implies they haven't completed the onboarding process, leading to a redirection to `/onboarding`. This sequential redirection flow ensures that users are always guided to the appropriate state based on their authentication and profile completeness. The fetched `professional` data is then passed as props to the `Sidebar` component, making it available for display and navigation logic.

## Sidebar Navigation

The `Sidebar` component, located in `src/app/dashboard/sidebar.tsx`, is a client component, indicated by the `"use client"` directive. This is necessary because it manages its own internal state (`mobileOpen`), uses client-side hooks like `usePathname` and `useRouter`, and performs client-side Supabase logout operations.

The sidebar presents a fixed navigation structure defined by the `NAV` array, which includes links to various dashboard sections such as "Dashboard", "Clientes", "Mensagens", "Relatórios", "Assistente IA", "Planos", and "Configurações". Each navigation item specifies its `href`, `label`, an `icon`, and a `proOnly` flag. The `proOnly` flag is a key design element for feature gating: if a navigation item is marked `proOnly` and the professional's `effectivePlan` is "free", the link is rendered as locked, directing the user to the `/dashboard/plans` page upon click. This approach clearly communicates plan-specific features and encourages upgrades.

The sidebar also dynamically displays the professional's initials, full name, and their current plan status, including any active trial period. The `trialDaysLeft` and `effectivePlan` utility functions are used here to determine the exact trial duration and the active plan, which influences the displayed plan label and color. A logout button, which calls `supabase.auth.signOut()` via a client-side Supabase instance, is also prominently featured, redirecting the user to `/login` after signing out.

## Dashboard Page Content

The `DashboardPage` (`src/app/dashboard/page.tsx`) is another asynchronous server component responsible for rendering the main content of the dashboard. It performs extensive data fetching to populate the various sections of the page.

Initial data fetches include:
*   The `professional` record, identical to the one fetched in the layout, ensuring the page has access to the professional's details.
*   `todayAppointments`: A query joining `appointments` with `clients` to retrieve all appointments scheduled for the current day for the logged-in professional. It uses `gte` and `lte` with `getToday()` to define the time range and orders them by `startsAt`.
*   `upcomingAppointments`: Similar to `todayAppointments`, but filters for appointments starting *after* the current day's end, limited to 20 results and ordered by `startsAt`.

To efficiently gather additional metrics, the page uses `Promise.all` to concurrently execute several database queries:
*   `totalClients`: Counts the total number of clients associated with the professional from the `clients` table.
*   `monthlyAppointments`: Counts appointments within the current month using `startOfMonth` and `endOfMonth` from `date-fns`.
*   `reviewStats`: Calculates the average `rating` and total `count` of reviews from the `reviews` table, using Drizzle's `sql` function for aggregation.
*   `recentReviews`: Fetches the 3 most recent reviews, joining with `clients` to display client names.
*   `availabilityCount`: Counts the number of availability slots defined for the professional.

The page then uses this data to render several dynamic UI elements:
*   **Welcome Card**: Displayed only when `totalClients` is 0, this card (`WelcomeCard`) provides a first-run nudge for new professionals to share their public profile link.
*   **Plan Limit Banners**: Conditional banners alert the professional if they are `isAtClientLimit`, `isAtMonthlyLimit`, or `isNearClientLimit`, `isNearMonthlyLimit` based on their `plan` and the `PLANS` configuration from `@/lib/stripe`. These banners encourage upgrading to a higher plan.
*   **Trial Banners**: A `TrialBanner` is shown if the professional is on the "free" plan and has not yet opted into a trial. If a trial is active, a banner displays the `daysLeft` until the trial ends, prompting subscription.
*   **Profile Completeness Nudge**: The `findProfileGaps` utility from `@/lib/profile-completeness` identifies missing profile information (e.g., `bio`, `phone`, `addressLine`, `availabilityCount`). If gaps exist and the professional has at least one client, a banner encourages them to complete their profile.
*   **Key Statistics**: Displays the number of today's appointments, pending appointments, and total clients.
*   **Reputation Section**: If `reviewCount` is greater than 0, this section shows the `avgRating` and `recentReviews`, providing social proof and feedback.
*   **Appointment Lists**: Both `todayAppointments` and `upcomingAppointments` are rendered in separate sections. Each appointment displays the client's name and phone, along with its `status` (e.g., "pending_confirmation", "confirmed", "rejected") using the `STATUS_LABEL` mapping for consistent styling. For pending or confirmed appointments, the `AppointmentActions` component is rendered, allowing professionals to manage the appointment status.
*   **Today's Revenue**: The `revenue` is calculated, but its display is not shown in the provided code excerpt.

## Design Decisions

1.  **Server Components for Initial Data Fetching**: The `DashboardLayout` and `DashboardPage` are implemented as `async` server components. This choice allows them to directly query the database using Drizzle ORM without needing an intermediate API layer for initial page loads. This reduces client-side JavaScript bundle size, improves initial page load performance, and simplifies data fetching logic by keeping it close to the rendering component. The `professional` data is fetched in both the layout and the dashboard page, resulting in a redundant fetch.
2.  **Client Component for Interactivity**: The `Sidebar` is explicitly marked as a client component. This separation is intentional, as the sidebar contains interactive elements like state management for mobile responsiveness (`useState`), client-side routing (`usePathname`, `useRouter`), and user logout functionality that requires a client-side Supabase instance. By making it a client component, the application can deliver a dynamic and responsive navigation experience while keeping the heavy data lifting on the server.
3.  **Conditional UI for User Guidance and Upselling**: The dashboard employs a highly conditional UI to guide professionals through different stages of their journey. Banners for onboarding (`WelcomeCard`), plan limits, trial status, and profile completeness are dynamically rendered based on the professional's data. This design decision aims to provide timely and relevant information, encourage feature adoption, and prompt plan upgrades, directly supporting business goals. The `proOnly` flag in the `NAV` array further reinforces feature gating, clearly indicating which features require a paid plan.

## Potential Improvements

1.  **Granular Revalidation for Appointment Actions**: The `AppointmentActions` component likely triggers a full page revalidation or a broad data refetch when an appointment status is updated. For a smoother user experience, especially in a dashboard with many appointments, consider implementing a more granular revalidation strategy. Instead of refetching all `todayAppointments` and `upcomingAppointments`, a client-side mutation with `useOptimistic` or a targeted `revalidatePath` for just the affected appointment could update the UI more efficiently without a full page reload.
2.  **Internationalization of Hardcoded Strings**: Many user-facing strings in `src/app/dashboard/page.tsx` and `src/app/dashboard/sidebar.tsx` are hardcoded in Portuguese (e.g., "Olá, {professional.name.split(" ")[0]} 👋", "Nenhum agendamento para hoje", `STATUS_LABEL` values, plan labels). To support a wider audience, integrating a robust internationalization (i18n) library (like `next-intl`) would allow these strings to be dynamically loaded based on the user's locale, making the application more adaptable and accessible.
3.  **Optimized Profile Completeness Check**: The `findProfileGaps` function is called on every dashboard load. While the current implementation might be fast, if the logic for determining profile completeness becomes more complex or involves additional database lookups, this could introduce unnecessary overhead. Consider memoizing the result of `findProfileGaps` or, for very complex checks, offloading this logic to a dedicated API endpoint that can be cached or run less frequently, especially if the profile data doesn't change often.
