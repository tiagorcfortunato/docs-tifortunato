# Dashboard

The professional dashboard serves as the primary interface for Odys users, providing a comprehensive overview of their business operations. This page, located at `src/app/dashboard/page.tsx`, is designed to be the central hub where professionals can quickly grasp their daily agenda, track client interactions, and monitor their overall performance. It integrates various data points from the database to present a concise yet informative summary, enabling professionals to make informed decisions and manage their practice effectively.

## Overview

The dashboard functionality is orchestrated across three main files: `src/app/dashboard/layout.tsx`, `src/app/dashboard/page.tsx`, and `src/app/dashboard/sidebar.tsx`. The `DashboardLayout` component acts as the root for all dashboard-related routes, handling initial authentication and fetching core professional data. It then renders the `Sidebar` component, which provides navigation, and the `DashboardPage` component, which displays the main content. This structure ensures a consistent layout and efficient data loading for the entire professional interface.

## Dashboard Layout (`src/app/dashboard/layout.tsx`)

The `DashboardLayout` component is a server component responsible for setting up the environment for all nested dashboard routes. Its primary role is to enforce authentication and fetch the professional's core profile data before any specific dashboard content is rendered.

Upon loading, it initializes a Supabase client using `createClient` and attempts to retrieve the authenticated user via `supabase.auth.getUser()`. If no user is found, the system redirects to `/login`, ensuring that only authenticated users can access the dashboard.

Once a user is authenticated, the layout queries the `professionals` table to fetch the corresponding professional profile using `db.select().from(professionals).where(eq(professionals.userId, user.id)).limit(1)`. This query is critical as it links the authenticated user to their professional profile. If no professional profile exists for the user, it implies they haven't completed the onboarding process, and the system redirects them to `/onboarding`.

The fetched professional data, including `professional.name`, `professional.slug`, `professional.plan`, is then passed as props to the `Sidebar` component. The `trialEndsAt` prop is passed to the `Sidebar` component, defaulting to `null` if not set. This allows the sidebar to display relevant professional information and tailor its navigation based on the user's plan and trial status. The layout also includes `PostHogIdentify` to track user activity, associating the authenticated user's ID with analytics events.

## Dashboard Page (`src/app/dashboard/page.tsx`)

The `DashboardPage` component is the core of the professional dashboard, displaying a dynamic overview of appointments, client statistics, and reputation. Like the layout, it's a server component, allowing it to directly interact with the database using Drizzle ORM.

It begins by re-fetching the authenticated user and professional profile, similar to the layout. This redundancy ensures the page has the most up-to-date professional data, though it could be optimized.

The page then performs several database queries to gather the necessary data for display:
*   **Today's Appointments**: It fetches appointments scheduled for the current day by joining `appointments` with `clients` and filtering by `professionalId` and a date range defined by `getToday()`. The results are ordered by `startsAt`.
*   **Upcoming Appointments**: Similar to today's appointments, but it fetches future appointments, ordered by `startsAt` and limited to 20 entries.
*   **Aggregate Statistics**: A `Promise.all` block concurrently fetches:
    *   The total number of clients (`totalClients`) associated with the professional from the `clients` table.
    *   The count of appointments for the current month (`monthlyAppointments`) from the `appointments` table.
    *   Review statistics (`reviewStats`), including the average rating and total count, by aggregating data from the `reviews` table.
    *   Recent client reviews (`recentReviews`), joining `reviews` with `clients` to display client names alongside comments.
    *   The count of availability slots (`availabilityCount`) from the `availability` table, used to assess profile completeness.

The page uses several helper functions like `formatTime` for displaying appointment times and `formatCurrency` for financial figures. A `STATUS_LABEL` object maps appointment statuses to human-readable labels and Tailwind CSS classes for consistent styling.

The UI is conditionally rendered based on the professional's status:
*   A `WelcomeCard` is shown for new professionals with zero clients, guiding them to share their public profile link.
*   Banners alert professionals if they are `isNearClientLimit` or `isAtClientLimit` for clients, or `isNearMonthlyLimit` or `isAtMonthlyLimit` for appointments, based on their `plan` and the `PLANS` configuration.
*   `TrialBanner` is displayed if the professional is on the "free" plan and hasn't started a trial. An active trial banner shows `daysLeft` if a trial is in progress.
*   A profile completeness banner, generated by `findProfileGaps`, nudges professionals to complete missing profile information, but only after they have at least one client to avoid overwhelming new users.

The main content includes a personalized greeting, a grid of key statistics (today's appointments, pending confirmations, total clients), and a "Reputation" section displaying the average rating. Recent client comments are displayed if there are comments available and are limited to the two most recent. Finally, lists of today's and upcoming appointments are rendered, each item including an `AppointmentActions` component for managing appointment statuses.

## Sidebar Component (`src/app/dashboard/sidebar.tsx`)

The `Sidebar` component is a client component (`"use client"`) responsible for the persistent navigation menu on the left side of the dashboard. It receives `professionalName`, `professionalSlug`, `plan`, and `trialEndsAt` as props from `DashboardLayout`.

The `NAV` array defines navigation links with `href`, `label`, `proOnly` status, an SVG `icon`, and an optional `exact` match property. It uses `usePathname` from `next/navigation` to determine the active link and applies appropriate styling.

A key feature of the sidebar is its handling of "Pro-only" features. If a navigation item has `proOnly: true` and the `activePlan` (derived from `plan` and `trialEndsAt` using `effectivePlan`) is "free", the link is rendered as "locked" and redirects to the `/dashboard/plans` page when clicked. This effectively gates premium features behind a subscription.

The sidebar also displays the professional's initials, full name, and their current plan status (e.g., "Free", "Pro", "Pro (trial)"). It includes a `ThemeToggle` for dark mode, a `NotificationBell` for alerts, and a logout button that uses `createClient` to sign out the user and redirects them to `/login`. For mobile devices, the sidebar implements a responsive drawer pattern, controlled by a `mobileOpen` state.

## Design decisions

The architecture of the dashboard reflects several deliberate design choices:

*   **Server Components for Initial Data Fetching**: Both `DashboardLayout` and `DashboardPage` are Next.js Server Components. This decision allows for direct, secure database access using Drizzle ORM (`db`) and Supabase (`createClient`) without exposing credentials to the client. It also means that the initial page load can be fully rendered on the server, improving perceived performance and SEO. By fetching `professional` data in the layout, it ensures that core user context is available early for global components like the `Sidebar`.
*   **Client Component for Interactive Sidebar**: The `Sidebar` is marked with `"use client"` because it manages its own UI state (e.g., `mobileOpen` for the drawer) and handles client-side interactions like navigation (`useRouter`) and user logout. This separation allows the interactive parts of the UI to be hydrated on the client while keeping the heavy data fetching on the server.
*   **Conditional UI for User Journey**: The dashboard employs extensive conditional rendering to guide professionals through different stages of their journey. The `WelcomeCard`, trial banners, plan limit warnings, and profile completeness nudges are all dynamically displayed based on the professional's `totalClients`, `plan`, `trialEndsAt`, and `profileGaps`. This approach provides a tailored experience, focusing on the most relevant next steps for the user.
*   **Drizzle ORM for Type-Safe Database Interactions**: The use of Drizzle ORM (`professionals`, `appointments`, `clients`, `reviews`, `availability` schemas) provides a type-safe way to interact with the PostgreSQL database. This reduces the likelihood of runtime errors due to schema mismatches and improves developer experience with auto-completion and compile-time checks. The queries leverage Drizzle's expressive API for filtering (`eq`, `and`, `gte`, `lte`, `gt`), aggregation (`count`, `sql`), and ordering (`desc`).

## Potential improvements

1.  **Centralize Professional Data Fetching**: The professional's data is fetched independently in both `DashboardLayout` and `DashboardPage`. While this ensures each component has its required data, it results in redundant database queries. The `professional` object could be fetched once in `DashboardLayout` and then passed down to `DashboardPage` as a prop, or stored in a server-side cache/context if more complex data sharing is needed across server components.
2.  **Optimize `pendingCount` Calculation**: The `pendingCount` for both today's and upcoming appointments is currently calculated by filtering the already fetched arrays on the client side: `[...todayAppointments, ...upcomingAppointments].filter(a => a.status === "pending_confirmation").length`. This could be more efficiently done with a dedicated Drizzle query on the server, using `db.select({ total: count() }).from(appointments).where(and(eq(appointments.professionalId, professional.id), eq(appointments.status, "pending_confirmation"), ...date_conditions))`. This would reduce the amount of data transferred to the client and offload computation to the database.
3.  **Consolidate UI Constants**: The `STATUS_LABEL` object in `src/app/dashboard/page.tsx` and `PLAN_LABEL`/`PLAN_COLOR` in `src/app/dashboard/sidebar.tsx` define UI-related mappings. If these labels or colors are used in other parts of the application, centralizing them in a shared utility file (e.g., `src/lib/ui-constants.ts`) would improve consistency and maintainability. Additionally, `PLAN_LABEL` and `PLAN_COLOR` could potentially derive their values from the `PLANS` object defined in `src/lib/stripe` to ensure consistency with pricing plans.
4.  **Configurable UI Limits**: The dashboard hardcodes display limits for `profileGaps.slice(0, 3)` and `recentReviews.filter(r => r.comment).slice(0, 2)`. These magic numbers could be moved to configuration variables or constants, making it easier to adjust the number of items displayed without modifying the core logic.
