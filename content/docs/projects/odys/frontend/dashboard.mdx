# Professional Dashboard

The professional dashboard serves as the central hub for professionals using Odys, offering a comprehensive overview of their daily operations, client interactions, and business performance. This document delves into the architecture of the dashboard, explaining how its layout, navigation, and core content are structured and interact to provide a seamless experience.

## Overview

The dashboard is built around a persistent layout, defined in `src/app/dashboard/layout.tsx`, which handles user authentication and fetches essential professional data. This data is then passed to the `Sidebar` component, located in `src/app/dashboard/sidebar.tsx`, which provides consistent navigation across all dashboard sub-routes. The main content area, rendered by `src/app/dashboard/page.tsx` for the root dashboard route, dynamically displays key information such as today's appointments, upcoming schedules, client statistics, and reputation metrics. The system relies heavily on server components for efficient data fetching using Drizzle ORM and Supabase for authentication, while the sidebar leverages client components for interactive elements.

## Dashboard Layout

The `src/app/dashboard/layout.tsx` file acts as the entry point for all routes under `/dashboard`. Its primary responsibilities include:

1.  **Authentication**: Before rendering any dashboard content, the layout uses `createClient` from `@/lib/supabase/server` to establish a server-side Supabase client and retrieve the authenticated user via `supabase.auth.getUser()`. If no user is found, the system immediately redirects to `/login`, ensuring that only authenticated professionals can access the dashboard.
2.  **Professional Profile Check**: Following successful authentication, the layout queries the database using Drizzle ORM to fetch the `professional` record associated with the `user.id`. This is a critical step, as a professional profile is required for dashboard functionality. If no corresponding `professional` record is found in the `professionals` table, the user is redirected to `/onboarding`, guiding them to set up their professional details.
3.  **Data Provisioning**: Once the professional's data is retrieved, key information such as `professional.name`, `professional.slug`, `professional.plan`, and `professional.trialEndsAt` is passed as props to the `Sidebar` component. This ensures the sidebar can display relevant user-specific details without needing to re-fetch them.
4.  **Global Components**: The layout also integrates global components like `PostHogIdentify`, which is used for analytics tracking, associating the current user's ID with their activity. The main content area for sub-routes is rendered via the `children` prop, allowing each dashboard page to manage its specific content.

## Sidebar Navigation

The `src/app/dashboard/sidebar.tsx` component provides the primary navigation for the professional dashboard. Being a client component, indicated by `"use client"`, it manages its own state for mobile responsiveness and handles client-side interactions.

The sidebar dynamically renders a list of navigation links defined in the `NAV` array. Each item includes an `href`, `label`, and an `icon`. A crucial aspect of this navigation is the `proOnly` flag, which restricts access for users on the `free` plan to certain features (like "Mensagens", "Relatórios", and "Assistente IA"). If a `free` plan user attempts to access a `proOnly` route, the link is visually locked and redirects them to the `/dashboard/plans` page, encouraging an upgrade.

The sidebar also displays the professional's initials, full name, and their current plan status (e.g., "Free", "Pro", "Trial Pro"). This information is derived from the props passed down from the `DashboardLayout`. A client-side `handleLogout` function uses `createClient` to sign the user out of Supabase and redirects them to `/login`. The component also incorporates a `NotificationBell` and `ThemeToggle` for user convenience, along with responsive design elements to switch between a persistent desktop sidebar and a mobile drawer.

## Dashboard Page Content

The `src/app/dashboard/page.tsx` file is an asynchronous server component responsible for fetching and rendering the core dashboard content. It performs several database queries using Drizzle ORM to gather the necessary data:

1.  **Professional Data**: It re-fetches the `professional` record using `user.id` to ensure it has the most up-to-date information for the current page's rendering, including details like `sessionPrice` for revenue calculations.
2.  **Appointment Data**: It fetches `todayAppointments` and `upcomingAppointments` by joining the `appointments` table with the `clients` table. This allows displaying client names and phone numbers alongside appointment details. The `todayAppointments` query uses `gte` and `lte` for date range filtering, while `upcomingAppointments` uses `gt`. Both use `orderBy` for chronological sorting.
3.  **Aggregate Statistics**: A `Promise.all` block efficiently fetches several aggregate metrics concurrently:
    *   `totalClients`: The total number of clients associated with the professional.
    *   `monthlyAppointments`: The count of appointments within the current month.
    *   `reviewStats`: The average rating (`avg`) and total count (`cnt`) of reviews from the `reviews` table.
    *   `recentReviews`: The latest three reviews, including client names, for the "Sua reputação" section. The UI displays the latest two commented reviews.
    *   `availabilityCount`: The number of availability slots configured by the professional.
4.  **Plan and Trial Management**: The page uses utility functions `trialDaysLeft` and `effectivePlan` from `@/lib/plan-guard` to determine the professional's current plan status and remaining trial days. This information drives the conditional rendering of various banners, such as `TrialBanner` and plan limit warnings (`isAtClientLimit`, `isNearClientLimit`).
5.  **Profile Completeness**: The `findProfileGaps` utility helps identify missing profile information, triggering a "Profile completeness" banner to nudge professionals to fill out their details. This banner is suppressed if the professional has no clients, to avoid overwhelming new users.
6.  **Dynamic UI Elements**: The page renders several sections based on the fetched data:
    *   A `WelcomeCard` for professionals with zero clients, encouraging them to share their public profile.
    *   Banners for plan limits (e.g., `You atingiu o limite de X clientes`) and trial status.
    *   A personalized greeting and daily statistics (appointments today, pending (today and upcoming), total clients).
    *   A "Sua reputação" section, visible only if `reviewCount` is greater than 0, displaying average rating and recent comments.
    *   Lists of today's and upcoming appointments, each showing client details, status, and `AppointmentActions` for managing `pending_confirmation` or `confirmed` appointments.
    *   A "Receita de hoje" section, visible if `revenue` is greater than 0.

Utility functions like `getToday`, `formatTime`, and `formatCurrency` are defined locally to assist with data presentation, while `STATUS_LABEL` provides consistent styling and text for appointment statuses.

## Design Decisions

The dashboard's design reflects several key architectural choices aimed at performance, maintainability, and user experience:

*   **Server Components for Initial Data**: The `DashboardLayout` and `DashboardPage` are implemented as Next.js Server Components. This allows them to directly query the database using Drizzle ORM (`db.select().from(...)`) without exposing database credentials to the client. This approach minimizes client-side JavaScript, improves initial page load times, and simplifies data fetching logic by keeping it close to the data source.
*   **Client Component for Interactivity**: The `Sidebar` is explicitly marked as a client component (`"use client"`). This is a deliberate choice to enable interactive features like the mobile menu toggle (`useState`), client-side navigation (`usePathname`, `useRouter`), theme switching (`ThemeToggle`), and the logout functionality, which requires client-side Supabase interaction.
*   **Centralized Plan Logic**: The `trialDaysLeft` and `effectivePlan` functions are abstracted into `@/lib/plan-guard`. This centralization ensures that the logic for determining a professional's active plan and trial status is consistent across both server-side components (like `page.tsx` for displaying banners) and client-side components (like `sidebar.tsx` for displaying plan labels).
*   **Drizzle ORM for Type Safety**: The use of Drizzle ORM (`@/lib/db/schema`) provides a type-safe way to interact with the PostgreSQL database. This reduces the likelihood of runtime errors due to schema mismatches and improves developer productivity by offering strong typing for database queries and results.
*   **Conditional UI for Guided Experience**: The dashboard makes extensive use of conditional rendering for various banners and sections (e.g., `WelcomeCard`, trial banners, plan limit warnings, profile completeness nudges). This design ensures that users are presented with relevant information and calls to action based on their current state, guiding them through onboarding, plan upgrades, and profile completion without cluttering the interface.

## Potential Improvements

1.  **Optimize `Sidebar` Data Fetching**: In `src/app/dashboard/layout.tsx`, the entire `professional` object (with 32 columns) is fetched, even though the `Sidebar` component only consumes `professionalName`, `professionalSlug`, `plan`, and `trialEndsAt`. The Drizzle query could be optimized to `db.select({ name: professionals.name, slug: professionals.slug, plan: professionals.plan, trialEndsAt: professionals.trialEndsAt })` to fetch only the necessary columns, reducing data transfer from the database.
2.  **Centralize Appointment Status Labels**: The `STATUS_LABEL` object in `src/app/dashboard/page.tsx` defines the display text and styling for appointment statuses. If other parts of the application (e.g., a dedicated appointments page, client view) also display appointment statuses, this object might be duplicated. Moving `STATUS_LABEL` to a shared utility file (e.g., `src/lib/constants.ts`) would promote consistency and easier maintenance.
3.  **Database-level Filtering for Pending Appointments**: The `pendingCount` is currently calculated in `src/app/dashboard/page.tsx` by filtering the `todayAppointments` and `upcomingAppointments` arrays after they have been fetched from the database. For larger datasets, it would be more efficient to push this filtering logic to the database itself by adding `eq(appointments.status, "pending_confirmation")` to the `where` clause of a dedicated query for pending appointments, reducing the amount of data transferred and processed on the server.
4.  **Refine `recentReviews` Query**: The `recentReviews` query in `src/app/dashboard/page.tsx` fetches up to 3 reviews and then filters them on the server to `filter(r => r.comment).slice(0, 2)`. If the intention is always to show only commented reviews, the Drizzle query could include `isNotNull(reviews.comment)` in its `where` clause and adjust the `limit` to `2` directly, ensuring only relevant data is retrieved from the database.
