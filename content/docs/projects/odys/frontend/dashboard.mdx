# Dashboard

The dashboard serves as the primary interface for professionals using Odys, offering a consolidated view of their business operations. It provides quick access to daily appointments, client management, performance metrics, and configuration settings, all within a structured and responsive layout. This page delves into the architecture of the dashboard, explaining how data is fetched, presented, and how user interactions are managed across its various components.

## Overview

The dashboard's structure is composed of three main parts: a layout component, a persistent sidebar, and the main content area. The `src/app/dashboard/layout.tsx` file acts as the wrapper, handling initial authentication and data fetching for the professional's profile. It then renders the `Sidebar` component, passing essential professional details, and injects the main dashboard content from `src/app/dashboard/page.tsx` as its children. This separation of concerns ensures that core data required for the entire dashboard context is loaded once, while specific page content can focus on its unique data requirements and presentation.

The `src/app/dashboard/page.tsx` component is responsible for displaying the professional's daily agenda, upcoming appointments, key business statistics, and contextual banners. It aggregates data from several database tables, including `professionals`, `appointments`, `clients`, `reviews`, and `availability`, to provide a comprehensive overview. The `src/app/dashboard/sidebar.tsx` component, a client-side interactive element, provides navigation, displays the professional's plan status, and handles user logout.

## Dashboard Page (`src/app/dashboard/page.tsx`)

The main dashboard content is rendered by `src/app/dashboard/page.tsx`, an asynchronous server component. This design choice allows it to directly interact with the database and Supabase authentication on the server, fetching all necessary data before rendering the HTML to the client.

Upon loading, the page first authenticates the user via `createClient` from `@/lib/supabase/server`. If no user is found, it redirects to `/login`. Subsequently, it queries the `professionals` table using `db.select().from(professionals).where(eq(professionals.userId, user.id)).limit(1)` to retrieve the current professional's profile. If a professional profile is not found, the user is redirected to `/onboarding`, ensuring that only registered professionals with complete profiles can access the dashboard.

The page then fetches a wealth of operational data:

*   **Today's Appointments**: It retrieves appointments scheduled for the current day by querying the `appointments` table, joining with `clients` to display client names and phones. The query uses `gte(appointments.startsAt, start)` and `lte(appointments.startsAt, end)` to filter for the current day.
*   **Upcoming Appointments**: Similar to today's appointments, this section fetches up to 20 future appointments using `gt(appointments.startsAt, end)` and orders them by `startsAt`.
*   **Key Metrics**: A `Promise.all` block concurrently fetches several aggregate statistics:
    *   `totalClients`: The total number of clients associated with the professional from the `clients` table.
    *   `monthlyAppointments`: The count of appointments within the current month from the `appointments` table.
    *   `reviewStats`: The average rating and total count of reviews from the `reviews` table, using Drizzle's `sql<number>` aggregate functions.
    *   `recentReviews`: The three most recent reviews, including client names, by joining `reviews` with `clients`.
    *   `availabilityCount`: The number of availability slots configured for the professional from the `availability` table.

The fetched data is then used to populate various sections of the dashboard. Appointment statuses are mapped to human-readable labels and colors using the `STATUS_LABEL` object. Financial figures, like today's revenue, are calculated by filtering `todayAppointments` for `paymentStatus === "captured"` and summing `professional.sessionPrice`, then formatted using `formatCurrency`.

Several conditional UI elements are displayed to guide the professional:

*   A `WelcomeCard` is shown only when `totalClients === 0`, providing a first-run nudge to share the public profile link.
*   `TrialBanner` appears if the professional is on the "free" plan and has not yet started a trial.
*   A dedicated banner indicates an active "Pro" trial, showing `daysLeft` calculated by `trialDaysLeft(professional.trialEndsAt)`.
*   Warnings for plan limits are displayed if the professional is `isNearClientLimit`, `isAtClientLimit`, `isNearMonthlyLimit`, or `isAtMonthlyLimit`, encouraging an upgrade to a higher plan like "basic", "pro", or "premium" as defined in `PLANS`.
*   A "Profile completeness" banner, driven by `findProfileGaps(professional, availabilityCount > 0)`, highlights missing profile information, and is only shown if the professional has at least one client.

Interactive elements like `AppointmentActions` allow professionals to manage the status of `pending_confirmation` or `confirmed` appointments directly from the dashboard.

## Dashboard Layout (`src/app/dashboard/layout.tsx`)

The `src/app/dashboard/layout.tsx` component wraps all dashboard routes, providing a consistent layout and handling global concerns. Like `page.tsx`, it's an `async` server component, allowing it to perform server-side operations before rendering.

Its primary responsibilities include:

*   **Authentication**: It uses `createClient` to verify the user's session. If `user` is null, it redirects to `/login`.
*   **Professional Profile Retrieval**: It fetches the `professional`'s data from the `professionals` table using `eq(professionals.userId, user.id)`. If no professional profile exists for the authenticated user, it redirects to `/onboarding`, ensuring that only fully onboarded professionals can access the dashboard.
*   **Sidebar Integration**: The `Sidebar` component is rendered, receiving crucial props such as `professionalName`, `professionalSlug`, `plan`, and `trialEndsAt` from the fetched professional data. This allows the sidebar to display personalized information and adapt its navigation based on the professional's plan.
*   **Analytics Integration**: `PostHogIdentify` is included to associate the authenticated `userId` with analytics events, providing insights into user behavior within the dashboard.
*   **Structural Wrapper**: It provides the main `div` structure with styling for the entire dashboard, including handling overflow and padding for the main content area to accommodate the fixed sidebar and mobile top bar.

## Sidebar (`src/app/dashboard/sidebar.tsx`)

The `src/app/dashboard/sidebar.tsx` component is a client component, indicated by `"use client"`, which enables interactive features like state management (`useState`) and client-side routing (`usePathname`, `useRouter`). It receives `professionalName`, `professionalSlug`, `plan`, and `trialEndsAt` as props from the `DashboardLayout`.

The sidebar features:

*   **Navigation**: A `NAV` array defines the dashboard's primary navigation links, each with an `href`, `label`, `icon`, and a `proOnly` flag. The `isActive` function dynamically highlights the current route.
*   **Plan-based Access**: Routes marked `proOnly` (e.g., "Mensagens", "Relatórios", "Assistente IA") are visually locked for users on the "free" plan. Clicking these links redirects the user to `/dashboard/plans`, encouraging an upgrade. The `effectivePlan` utility from `@/lib/plan-guard` determines the user's current plan status, considering any active trials.
*   **Trial Status Display**: If a trial is active, a banner within the sidebar displays the `daysLeft` calculated by `trialDaysLeft(trialEndsAt)`, prompting the user to subscribe.
*   **Professional Profile**: The sidebar displays the professional's initials (`initials`) and their current plan status (e.g., "Free", "Pro (trial)") using `PLAN_LABEL` and `PLAN_COLOR` mappings.
*   **External Links**: Quick access links to the professional's public page (`/p/[slug]`) and a "Client Mode" (`/c`) are provided.
*   **Logout Functionality**: The `handleLogout` function uses `createClient` from `@/lib/supabase/client` to sign out the user and redirects them to `/login`.
*   **Responsive Design**: It implements a responsive design with a hidden desktop sidebar and a mobile-friendly top bar and drawer, controlled by the `mobileOpen` state.

## Design decisions

The architecture of the dashboard reflects a deliberate choice to leverage Next.js's server components for data fetching and initial rendering, while using client components for interactivity.

*   **Server-Side Data Fetching**: By making `src/app/dashboard/layout.tsx` and `src/app/dashboard/page.tsx` `async` server components, data for the professional profile, appointments, clients, and reviews is fetched directly from the database using Drizzle ORM and Supabase on the server. This approach centralizes data access, reduces client-side JavaScript bundle size, and improves initial page load performance by delivering fully rendered HTML. It also simplifies data consistency, as all data is fresh at the time of the request.
*   **Drizzle ORM**: The use of Drizzle ORM for database interactions provides a type-safe and expressive way to construct SQL queries. This minimizes the risk of runtime errors due to schema mismatches and enhances developer productivity. The queries for `count()`, `avg()`, `gte()`, `lte()`, `eq()`, `and()`, `gt()`, `desc()`, and `sql()` demonstrate Drizzle's capabilities in fetching and aggregating complex data.
*   **Conditional UI for User Guidance**: The dashboard employs various banners and cards (`WelcomeCard`, `TrialBanner`, plan limit warnings, profile completeness nudges) to provide contextual information and guide the professional through onboarding, feature adoption, and plan upgrades. This design prioritizes user experience by proactively surfacing relevant actions and information.
*   **Client-Side Interactivity**: Components like `src/app/dashboard/sidebar.tsx` and `AppointmentActions` are marked as client components. This allows them to manage their own state, respond to user input, and perform client-side actions (e.g., navigation, logout, updating appointment statuses) without requiring a full page reload. This separation ensures that only interactive parts incur the cost of client-side JavaScript.
*   **Authentication and Authorization**: The `DashboardLayout` acts as a gatekeeper, ensuring that only authenticated users with a complete professional profile can access the dashboard. This early redirection prevents unauthorized access and ensures that subsequent components can assume the presence of user and professional data.

## Potential improvements

1.  **Centralize Plan Limit Logic**: The logic for checking plan limits (`isAtClientLimit`, `isNearClientLimit`, `isAtMonthlyLimit`, `isNearMonthlyLimit`) is currently calculated directly within `src/app/dashboard/page.tsx`. This logic could be abstracted into a dedicated utility function or a custom hook (if client-side) that takes the `professional` object and `PLANS` as input, returning the relevant limit statuses. This would improve readability and prevent duplication if similar checks are needed elsewhere.
2.  **Optimize Appointment Data Fetching**: The `todayAppointments` and `upcomingAppointments` queries in `src/app/dashboard/page.tsx` are very similar, differing only in their `startsAt` filter. While `Promise.all` is used for other queries, these two could potentially be combined into a single, more complex Drizzle query that fetches all relevant appointments and then filters them in application code, or uses a `UNION` if the database supports it efficiently. This might reduce the number of database round trips, depending on the database's query planner.
3.  **Externalize UI Constants**: The `STATUS_LABEL`, `PLAN_LABEL`, and `PLAN_COLOR` objects in `src/app/dashboard/page.tsx` and `src/app/dashboard/sidebar.tsx` contain hardcoded strings and styles. Moving these into a shared constants file or an internationalization (i18n) system would make the application easier to maintain, localize, and update UI elements consistently across the codebase.
4.  **Refine Review Statistics Query**: The `reviewStats` query in `src/app/dashboard/page.tsx` uses `sql<number>` for `avg` and `count`. While functional, Drizzle provides dedicated aggregate functions like `avg()` and `count()` that might offer a more idiomatic and type-safe way to express these operations, potentially simplifying the query and improving type inference.
