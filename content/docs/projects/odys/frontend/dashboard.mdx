# Dashboard

The professional dashboard serves as the central hub for service providers using Odys, offering a comprehensive overview of their operations, client interactions, and business performance. This documentation delves into the architecture of the dashboard, primarily focusing on the `src/app/dashboard/layout.tsx`, `src/app/dashboard/sidebar.tsx`, and `src/app/dashboard/page.tsx` files, explaining how they collaborate to deliver a dynamic and personalized user experience.

## Overview

The dashboard is structured as a Next.js App Router route group, leveraging server components for initial data fetching and client components for interactive elements. The `src/app/dashboard/layout.tsx` file acts as the entry point, handling user authentication and fetching the core professional profile data. This data is then passed to the `Sidebar` component, defined in `src/app/dashboard/sidebar.tsx`, which provides navigation and displays user-specific information. The main content of the dashboard, rendered by `src/app/dashboard/page.tsx`, presents a summary of today's and upcoming appointments, key business metrics, and contextual banners for onboarding, plan limits, and trial status.

The system interacts with several Drizzle ORM schema tables, including `professionals`, `appointments`, `clients`, `reviews`, and `availability`, to gather the necessary information for display.

## Dashboard Layout

The `src/app/dashboard/layout.tsx` file is a server component responsible for establishing the foundational context for all routes within the `/dashboard` path. Its primary responsibilities include:

1.  **Authentication and Authorization**: It initiates a Supabase client using `createClient` to retrieve the current user's session. If no user is found, it redirects them to `/login`, ensuring that only authenticated users can access the dashboard.
2.  **Professional Profile Retrieval**: Once authenticated, the layout queries the database for the professional's profile using `db.select().from(professionals).where(eq(professionals.userId, user.id)).limit(1)`. This is a critical step, as the entire dashboard experience is tailored to the specific professional.
3.  **Onboarding Enforcement**: If a user is authenticated but lacks a corresponding professional profile (meaning they haven't completed the initial setup), they are redirected to `/onboarding`. This ensures a smooth first-run experience and prevents access to a dashboard that cannot be populated with data.
4.  **Sidebar Integration**: The layout renders the `Sidebar` component, passing essential professional details such as `professional.name`, `professional.slug`, `professional.plan`, and `professional.trialEndsAt`. This allows the sidebar to display personalized information and adapt its navigation based on the professional's subscription plan and trial status.
5.  **Content Rendering**: It wraps the `children` prop, which represents the specific dashboard page being viewed (e.g., `src/app/dashboard/page.tsx`), within a flex container. This establishes the two-column layout with the sidebar on the left and the main content area on the right.
6.  **Analytics Integration**: The `PostHogIdentify` component is included to associate the current user's ID with analytics events, providing insights into user behavior within the dashboard.

## Dashboard Sidebar

The `src/app/dashboard/sidebar.tsx` component is marked with `"use client"`, indicating it's a client component. This choice is necessary because it manages its own state (`mobileOpen` for responsive navigation), interacts with client-side Next.js hooks (`usePathname`, `useRouter`), and performs client-side Supabase operations for logout.

The sidebar's key features include:

1.  **Dynamic Navigation**: It defines a `NAV` array containing all primary dashboard links, each with an `href`, `label`, `icon`, and a `proOnly` flag. The `isActive` function determines the current active link based on the `pathname`.
2.  **Plan-Based Feature Gating**: The `proOnly` flag is used in conjunction with `effectivePlan` to conditionally enable or disable navigation items. If a feature is `proOnly` and the `activePlan` is "free", the link is rendered as locked, guiding users towards plan upgrades.
3.  **Trial Status Display**: It prominently displays a trial banner if `trialDaysLeft` indicates an active trial, showing the remaining days and a call to action to subscribe.
4.  **User Profile Summary**: The sidebar shows the professional's initials (`initials`), full `professionalName`, and their current `plan` (e.g., "Free", "Pro", "Premium") with a corresponding color-coded badge.
5.  **Logout Functionality**: A `handleLogout` function uses `createClient` to sign the user out of Supabase and redirects them to the `/login` page.
6.  **Responsive Design**: It implements a mobile-first approach, rendering a simplified top bar on small screens and a full sidebar on larger screens. A mobile drawer (`mobileOpen` state) provides access to the full navigation on smaller devices.
7.  **External Links**: It includes direct links to the professional's public page (`/p/[slug]`) and a "Client Mode" (`/c`) for quick access.

## Dashboard Page

The `src/app/dashboard/page.tsx` is a server component that renders the main content area of the dashboard. It performs extensive data fetching and conditional rendering to provide a personalized and informative view for the professional.

Key aspects of this page include:

1.  **Initial Data Fetching**: It re-fetches the `professional` data, similar to the layout, to ensure it has the most up-to-date profile information. It also performs the same authentication and onboarding redirects.
2.  **Appointment Data**:
    *   `todayAppointments`: Fetches all appointments for the current day, joining with the `clients` table to display client names and phones. It uses Drizzle's `gte` and `lte` operators with `getToday()` helper for precise date range filtering.
    *   `upcomingAppointments`: Fetches the next 20 appointments scheduled after today, ordered by `startsAt`.
3.  **Aggregate Statistics**: A `Promise.all` call efficiently fetches several key metrics concurrently:
    *   `totalClients`: The total number of clients associated with the professional.
    *   `monthlyAppointments`: The count of appointments scheduled for the current month.
    *   `reviewStats`: The average `rating` and total `count` of reviews from the `reviews` table.
    *   `recentReviews`: The three most recent reviews, including comments and client names.
    *   `availabilityCount`: The number of availability slots configured by the professional.
4.  **Conditional Banners and Nudges**:
    *   `WelcomeCard`: Displayed only when `totalClients === 0`, providing a first-run experience to encourage sharing the public profile.
    *   **Plan Limit Warnings**: Dynamically displays warnings if the professional is `isNearClientLimit`, `isAtClientLimit`, `isNearMonthlyLimit`, or `isAtMonthlyLimit` based on their `plan` and the `PLANS` configuration. These banners include calls to action to upgrade.
    *   `TrialBanner`: Appears if the professional is on the "free" plan and hasn't started a trial yet.
    *   **Active Trial Banner**: Shows `daysLeft` if a trial is active, encouraging subscription.
    *   **Profile Completeness**: Uses `findProfileGaps` to identify missing profile information (e.g., bio, address, availability) and displays a banner with suggestions, but only if `totalClients > 0` to avoid overwhelming new users.
5.  **Dashboard Sections**:
    *   **Greeting**: A personalized greeting to the professional.
    *   **Stats**: Displays quick numerical summaries for "Today's appointments", "Pending" confirmations, and "Total Clients".
    *   **Reputation**: If `reviewCount > 0`, it shows the `avgRating` and recent comments, linking to the public profile.
    *   **Today's Appointments**: Lists all appointments for the current day, including time, client details, status, and `AppointmentActions` for managing `pending_confirmation` or `confirmed` appointments.
    *   **Upcoming Appointments**: Lists future appointments, similar to today's, but includes the date.
    *   **Revenue**: If `revenue > 0` for the day, it displays the total revenue from `captured` payments.
6.  **Utility Functions**: Includes `getToday`, `formatTime`, and `formatCurrency` for consistent data presentation. The `STATUS_LABEL` object maps appointment statuses to human-readable labels and Tailwind CSS classes for visual styling.

## Design Decisions

The dashboard's architecture reflects several deliberate design choices:

*   **Server-Side Data Fetching**: By making `layout.tsx` and `page.tsx` server components, Odys minimizes client-side JavaScript bundles and allows direct, secure database access using Drizzle ORM. This approach improves initial page load performance and simplifies data management by keeping sensitive logic on the server. The use of `Promise.all` for fetching multiple dashboard statistics in `page.tsx` further optimizes data retrieval by executing queries concurrently.
*   **Clear Separation of Concerns**: The division into `layout.tsx`, `sidebar.tsx`, and `page.tsx` promotes modularity. The layout handles global concerns like authentication and overall structure, the sidebar manages navigation and user context, and the page focuses on displaying specific dashboard content. The `sidebar.tsx` being a client component is a pragmatic choice to enable interactive elements like mobile menu toggling and client-side logout, while still receiving server-rendered data as props.
*   **Proactive User Guidance**: The dashboard incorporates various conditional UI elements like `WelcomeCard`, plan limit banners, trial banners, and profile completeness suggestions. This design aims to proactively guide professionals through onboarding, encourage feature adoption, and prompt plan upgrades, rather than relying solely on user-initiated actions. The `proOnly` flag in the `NAV` array is a direct implementation of this feature gating.
*   **Drizzle ORM for Type Safety and Efficiency**: Using Drizzle ORM allows for type-safe database interactions and expressive query construction, as seen with `eq`, `and`, `gte`, `lte`, `count`, `gt`, `desc`, and `sql` functions. This reduces the likelihood of runtime errors and makes database operations more readable.
*   **Localized Formatting**: The use of `toLocaleTimeString("pt-BR")` and `toLocaleString("pt-BR", { style: "currency", currency: "BRL" })` indicates a design choice to present dates, times, and currency in a format familiar to Brazilian users, aligning with the application's target audience.

## Potential Improvements

1.  **Optimize Professional Data Fetching**: The `professional` data is fetched independently in both `src/app/dashboard/layout.tsx` and `src/app/dashboard/page.tsx`. While Next.js server components can cache identical fetches, explicitly passing the `professional` object from the `DashboardLayout` to its `children` (the `DashboardPage`) could make the data flow more explicit and potentially avoid redundant database calls if caching mechanisms are not perfectly aligned.
2.  **Centralize Plan and Trial Logic**: The `trialDaysLeft` and `effectivePlan` functions are called in both `src/app/dashboard/page.tsx` and `src/app/dashboard/sidebar.tsx`. While the functions themselves are imported, the repeated calls could be consolidated. The `DashboardLayout` already fetches the `professional` object and could calculate these derived values once, then pass them down as props to both the `Sidebar` and the `DashboardPage` to ensure consistency and reduce redundant computation.
3.  **Decouple UI Styling from Data**: The `STATUS_LABEL` object in `src/app/dashboard/page.tsx` directly embeds Tailwind CSS classes (`bg-yellow-100 dark:bg-yellow-900/30 text-yellow-800 dark:text-yellow-400`). This couples presentation logic tightly with data. A cleaner approach would be to define a separate utility function or a dedicated `StatusBadge` component that takes the `status` string and returns the appropriate styled element, abstracting away the specific CSS classes from the data mapping.
4.  **Internationalization (i18n) Strategy**: The current code uses hardcoded "pt-BR" for date and currency formatting and contains many hardcoded Portuguese strings (e.g., "Olá", "agendamentos", "clientes", "Sair"). For future expansion, implementing a formal internationalization library and extracting all user-facing strings into translation files would make the application adaptable to multiple languages without modifying the core components.
