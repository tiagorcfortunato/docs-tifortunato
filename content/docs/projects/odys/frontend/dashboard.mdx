# Dashboard

The dashboard serves as the central command center for professionals using Odys, providing a comprehensive overview of their practice. It integrates critical information, from daily appointments and client statistics to subscription plan details and profile completeness, all within a unified interface. This page details the architecture and functionality of the professional dashboard, including its data fetching strategies, UI components, and the underlying logic that drives its dynamic content.

## Overview

The professional dashboard is structured around a `DashboardLayout` component, which acts as a wrapper for the main `DashboardPage` content and the persistent `Sidebar` navigation. This layout ensures a consistent user experience across all dashboard sub-routes. Both the layout and the page components are primarily server-rendered, leveraging Next.js Server Components to efficiently fetch data from the database before rendering the UI.

The system relies heavily on the `professionals` table, which stores detailed information about each professional, including their `userId`, `name`, `slug`, `plan`, and `trialEndsAt`. This table, along with 4 other tables (`appointments`, `clients`, `reviews`, and `availability`), forms the backbone of the data displayed throughout the dashboard. The application also exposes 23 API routes, some of which are utilized by interactive elements within the dashboard, such as `AppointmentActions`.

## Data Fetching and Authentication

The journey into the dashboard begins with authentication. Both `src/app/dashboard/layout.tsx` and `src/app/dashboard/page.tsx` initiate a server-side authentication check using `createClient` from `@/lib/supabase/server`. If a user is not authenticated, they are immediately redirected to the `/login` page.

Once authenticated, the system retrieves the professional's profile from the `professionals` table by matching the `user.id`. Should a professional record not exist, indicating an incomplete onboarding process, the user is redirected to `/onboarding`. This sequential redirection ensures that only authenticated and fully registered professionals can access the dashboard.

The `DashboardPage` then proceeds to fetch a rich set of data concurrently using `Promise.all` for efficiency. This includes:

*   **Today's and Upcoming Appointments:** Queries against the `appointments` table, joined with the `clients` table, to display current and future bookings. These queries filter appointments based on `professionalId` and `startsAt` timestamps, using Drizzle ORM's `gte`, `lte`, and `gt` operators.
*   **Key Metrics:** Aggregated data such as the total number of clients (`totalClients`) from the `clients` table, monthly appointments (`monthlyAppointments`) from the `appointments` table, and review statistics (`avg` rating and `cnt` count) from the `reviews` table.
*   **Recent Reviews:** A selection of the latest reviews, including comments and client names, fetched from the `reviews` table joined with `clients`.
*   **Availability Count:** A simple count of entries in the `availability` table to determine if the professional has set up their working hours.

These data points are crucial for populating the various sections of the dashboard, providing the professional with a real-time snapshot of their business.

## User Interface Components

The dashboard's user interface is composed of several key components that work together to present information and enable interaction:

### `DashboardLayout`

The `src/app/dashboard/layout.tsx` component is a Server Component that wraps the entire dashboard experience. It performs the initial user authentication and professional profile retrieval. It then renders the `PostHogIdentify` component for analytics tracking and passes the professional's details (`professionalName`, `professionalSlug`, `plan`, `trialEndsAt`) to the `Sidebar` component. The `children` prop is where the specific content of `DashboardPage` or any sub-route is rendered.

### `Sidebar`

The `src/app/dashboard/sidebar.tsx` is a client-side component responsible for the main navigation. It displays a list of links defined in the `NAV` array, which includes routes like `/dashboard`, `/dashboard/clients`, `/dashboard/messages`, and `/dashboard/settings`. Each navigation item can be marked as `proOnly`, restricting access for users on the "free" plan and redirecting them to the `/dashboard/plans` page if they attempt to access a locked feature.

The sidebar also features the professional's name and their current plan status, dynamically displaying "Free", "Basic", "Pro", or "Premium" along with a trial indicator if applicable. It incorporates a `ThemeToggle` for dark mode and a `NotificationBell` for alerts. A logout button, powered by `createClient` from `@/lib/supabase/client`, allows users to sign out and redirects them to `/login`. The component is designed to be responsive, offering a full-height sidebar on desktop and a mobile drawer for smaller screens.

### `DashboardPage`

The `src/app/dashboard/page.tsx` component renders the main content area of the dashboard. It dynamically displays various cards and lists based on the fetched data:

*   **Welcome Card:** A `WelcomeCard` component is shown exclusively to new professionals who have `totalClients === 0`, offering a direct call to action to share their public profile link (`/p/[slug]`).
*   **Plan Limit Banners:** Conditional banners alert professionals when they are `isNearClientLimit`, `isAtClientLimit`, `isNearMonthlyLimit`, or `isAtMonthlyLimit` based on their current `plan` and the limits defined in `PLANS` from `@/lib/stripe`. These banners provide clear calls to action to upgrade their subscription.
*   **Trial Banners:** If a professional is on the "free" plan and has not yet started a trial, a `TrialBanner` is displayed. If a trial is active, a distinct banner shows the `daysLeft` until the trial ends, encouraging subscription.
*   **Profile Completeness Nudge:** The `findProfileGaps` utility from `@/lib/profile-completeness` identifies missing profile information. If `profileGaps.length > 0` and `totalClients > 0`, a banner encourages the professional to complete their profile in `/dashboard/settings`.
*   **Statistics:** A grid displays key metrics such as the number of `todayAppointments`, `pendingCount` (appointments awaiting confirmation), and `totalClients`.
*   **Reputation Section:** If `reviewCount > 0`, a dedicated section showcases the professional's `avgRating` and `reviewCount`, along with recent comments from clients.
*   **Appointment Lists:** Separate sections for "Agenda de hoje" (Today's appointments) and "Próximos agendamentos" (Upcoming appointments) display detailed appointment information, including client names, phone numbers, and status labels. Each appointment includes `AppointmentActions` for managing its status.
*   **Revenue Display:** If `revenue > 0`, a banner highlights the total revenue generated from today's captured appointments.

Utility functions like `getToday`, `formatTime`, `formatCurrency`, and the `STATUS_LABEL` map are used to format and present data consistently across the page.

## Design Decisions

The architecture of the dashboard reflects several deliberate design choices aimed at performance, maintainability, and user experience:

*   **Server Components for Initial Load:** The decision to make `DashboardLayout` and `DashboardPage` Server Components allows for efficient data fetching directly on the server. This minimizes the amount of JavaScript sent to the client on initial load, leading to faster page renders and a better perceived performance. Authentication and data retrieval from the 5 database tables are handled before any UI is streamed to the browser.
*   **Client Components for Interactivity:** Interactive elements like the `Sidebar` and `AppointmentActions` are explicitly marked as client components using `"use client"`. This separation ensures that only the necessary JavaScript for interactivity is hydrated on the client, keeping the overall bundle size lean. The `Sidebar` manages its own mobile state with `useState` and handles navigation with `usePathname` and `useRouter`.
*   **Type-Safe Database Interactions with Drizzle:** The use of Drizzle ORM for database queries provides strong type safety, reducing runtime errors and improving developer productivity. The schema definitions for tables like `professionals`, `appointments`, and `clients` are directly reflected in the Drizzle queries, ensuring that data access is consistent and validated.
*   **Conditional UI for Guided Experience:** The dashboard employs extensive conditional rendering to tailor the user interface to the professional's current state. Displaying a `WelcomeCard` for new users, plan limit warnings, or profile completeness nudges ensures that professionals receive relevant information and guidance at the right time, without unnecessary clutter. This dynamic approach enhances the user journey from onboarding through daily operations.

## Potential Improvements

While the current dashboard provides a solid foundation, several areas could be enhanced to further improve performance, maintainability, and user experience:

*   **Centralize Professional Data Fetching:** The professional's data is fetched independently in both `src/app/dashboard/layout.tsx` and `src/app/dashboard/page.tsx`. Although Next.js might deduplicate identical fetches, explicitly fetching the `professional` record once in `DashboardLayout` and passing it down as a prop to `DashboardPage` would make the data flow clearer and potentially more efficient. This would eliminate the redundant `db.select().from(professionals).where(eq(professionals.userId, user.id)).limit(1)` call within `DashboardPage`.
*   **Externalize `STATUS_LABEL` for Reusability:** The `STATUS_LABEL` object, which maps appointment statuses to display labels and Tailwind CSS classes, is currently defined directly within `src/app/dashboard/page.tsx`. To promote consistency and reusability across the application, especially if appointment statuses are displayed in other contexts (e.g., client-facing pages, reports), this object could be moved to a shared utility file, such as `src/lib/constants/appointment-status.ts`.
*   **Implement Pagination for Upcoming Appointments:** The `upcomingAppointments` query in `src/app/dashboard/page.tsx` fetches up to 20 future appointments. For professionals with a very high volume of bookings, this list could still become quite long. Introducing a pagination mechanism or a "load more" button, perhaps fetching appointments in smaller batches (e.g., 5 or 10 at a time), would improve the performance and responsiveness of the UI, especially on slower connections or devices.
