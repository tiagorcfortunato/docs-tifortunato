# Dashboard

The dashboard serves as the central hub for professionals using Odys, providing an immediate overview of their practice. It integrates key information such as upcoming appointments, client statistics, and performance metrics, all accessible through a structured layout. This page details the architecture behind the professional dashboard, including its main content area, the persistent sidebar navigation, and the underlying data fetching strategies.

## Overview

The professional dashboard is composed of three primary components: `DashboardLayout`, `Sidebar`, and `DashboardPage`. The `DashboardLayout` (`src/app/dashboard/layout.tsx`) acts as the root for all dashboard-related routes, establishing the overall structure and fetching essential professional data once. This data is then passed to the `Sidebar` (`src/app/dashboard/sidebar.tsx`), which handles navigation and displays user-specific information. The `DashboardPage` (`src/app/dashboard/page.tsx`) renders the default content for the dashboard, presenting a summary of appointments, client engagement, and various contextual banners.

## `src/app/dashboard/layout.tsx`

The `DashboardLayout` component is a React Server Component responsible for setting up the foundational structure of the professional dashboard. It ensures that only authenticated and registered professionals can access the dashboard.

Upon rendering, the layout first uses `createClient` from `@/lib/supabase/server` to retrieve the current authenticated `user`. If no user session is found, it immediately redirects to `/login`, enforcing authentication. Once a user is identified, the layout queries the `professionals` table in the database, using Drizzle ORM's `eq` helper to match the `userId` with the authenticated user's ID. This query is limited to one result, as each user is expected to have a single professional profile. If no corresponding professional record is found, the user is redirected to `/onboarding`, guiding them through the initial setup process.

A key design decision here is fetching the `professional` data at this top-level layout. This allows the `professionalName`, `professionalSlug`, `plan`, and `trialEndsAt` to be passed down as props to the `Sidebar` component. This approach centralizes the initial data load for common professional details, making them available to child components without redundant database calls. The layout also includes `PostHogIdentify` to track user activity and wraps the main content in a flex container, allocating space for the sidebar and the scrollable content area.

## `src/app/dashboard/sidebar.tsx`

The `Sidebar` component, marked as a client component with `"use client"`, provides the primary navigation for the dashboard. It receives essential professional details as props from the `DashboardLayout`, such as `professionalName`, `professionalSlug`, `plan`, and `trialEndsAt`.

This component manages its own `mobileOpen` state to control the visibility of a responsive drawer menu on smaller screens. It uses Next.js hooks like `usePathname` to highlight the active navigation link and `useRouter` for client-side navigation, including handling the logout process via `supabase.auth.signOut()`.

The navigation structure is defined by the `NAV` array, which includes properties like `href`, `label`, `icon`, and crucially, `proOnly`. The `proOnly` flag, combined with the `effectivePlan` logic from `@/lib/plan-guard`, implements feature gating. If a navigation item is marked `proOnly` and the professional's `activePlan` is "free", the link is visually locked and redirects to the `/dashboard/plans` page, encouraging plan upgrades.

The sidebar also displays the professional's initials, their current plan status (e.g., "Free", "Pro"), and any active trial information, calculated using `trialDaysLeft`. It integrates `OdysLogo`, `NotificationBell`, and `ThemeToggle` components, providing consistent branding and utility features.

## `src/app/dashboard/page.tsx`

The `DashboardPage` component is the default content displayed within the dashboard layout. As an `async` React Server Component, it directly fetches all necessary data from the database to render the dashboard's various sections.

It begins by fetching the `professional` record, similar to the layout, to ensure it has the most up-to-date profile information. It then retrieves `todayAppointments` and `upcomingAppointments` by querying the `appointments` table, joining with `clients` to display client names and phone numbers. These queries filter appointments based on the `professionalId` and `startsAt` timestamps, using Drizzle ORM's `gte` and `lte` for date range filtering.

To populate the dashboard's statistical overview, `DashboardPage` uses `Promise.all` to concurrently fetch several aggregates:
- `totalClients`: The total count of clients associated with the professional.
- `monthlyAppointments`: The number of appointments scheduled for the current month.
- `reviewStats`: The average rating and total count of reviews from the `reviews` table.
- `recentReviews`: The three most recent reviews, including client names and comments.
- `availabilityCount`: The number of availability slots configured by the professional.

The page utilizes several helper functions like `getToday`, `formatTime`, and `formatCurrency` for consistent data presentation. A `STATUS_LABEL` constant maps appointment statuses to user-friendly labels and Tailwind CSS classes for visual consistency.

The `DashboardPage` dynamically renders various informational banners based on the professional's status:
- A `WelcomeCard` is shown to new professionals with zero clients, guiding them to share their public booking link.
- Plan limit banners (`isAtClientLimit`, `isNearClientLimit`, `isAtMonthlyLimit`, `isNearMonthlyLimit`) warn or block actions if the professional is approaching or has exceeded their plan's limits, prompting an upgrade.
- `TrialBanner` and an active trial banner inform users about their trial status and remaining days.
- A profile completeness banner, powered by `findProfileGaps`, nudges professionals to fill out missing profile information, but only after they have at least one client to avoid overwhelming new users.

Finally, the page displays a personalized greeting, key statistics (today's appointments, pending confirmations, total clients), a "Your Reputation" section (if `reviewCount > 0`), and detailed lists for "Today's appointments" and "Upcoming appointments". Each appointment item includes its status, client details, and `AppointmentActions` for managing its state. A "Today's Revenue" section is shown if there are captured payments.

## Design decisions

The architecture of the dashboard reflects several deliberate design choices aimed at performance, maintainability, and user experience:

-   **Server Components for Data Fetching:** Both `DashboardLayout` and `DashboardPage` are implemented as React Server Components. This allows them to fetch data directly from the database using Drizzle ORM, reducing the amount of JavaScript sent to the client, improving initial page load times, and simplifying data access logic by keeping it close to the server.
-   **Client Component for Interactivity:** The `Sidebar` is a client component because it requires client-side state management (e.g., `mobileOpen` for the responsive menu), access to browser APIs (`usePathname`, `useRouter`), and direct user interaction for actions like logout. This separation ensures that only necessary interactive logic is bundled for the client.
-   **Centralized Professional Data in Layout:** Fetching core `professional` data in `DashboardLayout` and passing relevant parts to `Sidebar` as props avoids redundant database queries for common information across different parts of the dashboard UI. While `DashboardPage` currently re-fetches the professional, the layout provides the initial context.
-   **Plan-based Feature Gating:** The `proOnly` flag within the `NAV` array in `sidebar.tsx` and the `effectivePlan` utility provide a clear and centralized mechanism for restricting access to certain features based on the user's subscription plan. This makes it straightforward to manage and communicate plan benefits.
-   **Contextual User Guidance:** The strategic use of various banners (`WelcomeCard`, trial banners, plan limit warnings, profile completeness nudges) ensures that users receive relevant information and calls to action at appropriate stages of their journey, improving onboarding and feature adoption without cluttering the UI.
-   **Drizzle ORM for Type Safety:** The consistent use of Drizzle ORM for database interactions across `layout.tsx` and `page.tsx` provides type safety for database queries, reducing potential runtime errors and improving developer experience.

## Potential improvements

1.  **Consolidate Professional Data Fetching:** The `professional` data is fetched independently in both `src/app/dashboard/layout.tsx` and `src/app/dashboard/page.tsx`. While both are Server Components, this results in two separate database queries for the same core entity.
    *   **Suggestion:** Explore patterns for sharing data fetched in a parent Server Component with its child Server Components. For instance, the `DashboardLayout` could fetch the `professional` object and pass it as a prop to its `children` if `children` were designed to accept such props, or a custom RSC data-fetching hook could be implemented to cache the result for the current request.
2.  **Extract `STATUS_LABEL` to a Shared Utility:** The `STATUS_LABEL` constant, which defines display properties for appointment statuses, is currently defined directly within `src/app/dashboard/page.tsx`. If other parts of the application (e.g., a dedicated appointments list page, or client-facing views) need to display appointment statuses, this definition would either be duplicated or require manual re-creation.
    *   **Suggestion:** Move the `STATUS_LABEL` object to a shared utility file, such as `src/lib/constants/appointment-statuses.ts`. This would promote consistency across the application and simplify maintenance.
3.  **Componentize Appointment List Rendering:** The rendering logic for "Today's appointments" and "Upcoming appointments" in `src/app/dashboard/page.tsx` is highly similar, involving mapping over an array of appointments and displaying details with `AppointmentActions`. This leads to duplicated JSX structure.
    *   **Suggestion:** Create a reusable `AppointmentList` component that accepts an array of appointments and a title. This component would encapsulate the common rendering logic, making `DashboardPage` cleaner and more modular.
4.  **Abstract Plan Limit Calculations:** The boolean flags `isNearClientLimit`, `isAtClientLimit`, `isNearMonthlyLimit`, and `isAtMonthlyLimit` are calculated directly within `src/app/dashboard/page.tsx`. These calculations involve multiple conditions and references to `plan.limits`.
    *   **Suggestion:** Encapsulate this logic within a dedicated helper function, perhaps named `getPlanLimitStatus(plan, totalClients, monthlyAppointments)`, which returns an object containing these boolean flags. This would improve readability and make the logic easier to test and reuse.
