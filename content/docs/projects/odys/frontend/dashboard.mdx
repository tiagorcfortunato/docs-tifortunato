The professional dashboard, located at `src/app/dashboard/page.tsx`, is the primary interface for professionals using Odys. It provides a comprehensive overview of their schedule, client base, and business performance. This page is designed to be highly dynamic, adapting its content and calls to action based on the professional's current status, plan, and profile completeness. It integrates deeply with the application's data layer to present up-to-date information and facilitate core actions like managing appointments.

## Overview

The dashboard experience is orchestrated by a combination of a layout component, a client-side sidebar, and the main dashboard page itself. The `src/app/dashboard/layout.tsx` acts as the root for all dashboard-related routes, handling initial authentication and fetching the core professional data. This data is then passed to the `src/app/dashboard/sidebar.tsx` component, which provides persistent navigation and user context. The main content of the dashboard, rendered by `src/app/dashboard/page.tsx`, focuses on displaying critical information such as today's and upcoming appointments, client statistics, and reputation metrics, alongside contextual banners for onboarding, trial status, and plan limits.

### Dashboard Layout (`src/app/dashboard/layout.tsx`)

The `DashboardLayout` component is a server component responsible for establishing the authenticated context for all nested dashboard routes. Upon loading, it uses `createClient` from `@/lib/supabase/server` to interact with Supabase and retrieve the current `user` session. If no user is found, it immediately redirects to `/login`, ensuring that only authenticated users can access the dashboard.

Following authentication, the layout queries the database for the professional's profile using Drizzle ORM. It selects a single record from the `professionals` table where `professionals.userId` matches the authenticated user's ID. If no professional profile is found, it redirects the user to `/onboarding`, guiding them through the initial setup process. This ensures that every user accessing the dashboard has an associated professional profile.

Crucially, the `DashboardLayout` passes essential professional details—`professionalName`, `professionalSlug`, `plan`, and `trialEndsAt`—to the `Sidebar` component. This allows the sidebar to display personalized information and adapt its navigation based on the professional's subscription plan and trial status. The layout also includes `PostHogIdentify` to track user activity, associating the current user's ID with analytics events. The main content of the dashboard, represented by `{children}`, is rendered within a scrollable area, allowing the sidebar to remain fixed.

### Sidebar Component (`src/app/dashboard/sidebar.tsx`)

The `Sidebar` is a client component, indicated by `"use client"`, which enables interactive features like state management for mobile navigation and client-side routing. It receives the professional's name, slug, plan, and trial end date as props from the `DashboardLayout`.

The sidebar's navigation is defined by the `NAV` array, which lists various dashboard sub-routes such as "Dashboard", "Clientes", "Mensagens", "Relatórios", "Assistente IA", "Planos", and "Configurações". Each navigation item includes an `href`, a `label`, an `icon`, and a `proOnly` flag. The `proOnly` flag is used to conditionally lock certain features for users on the "free" plan, redirecting them to the `/dashboard/plans` page if they attempt to access a restricted route. The `isActive` function dynamically highlights the current route based on `usePathname`.

The sidebar also displays the professional's initials, full name, and their current plan status, including whether they are on a trial. It displays a custom trial banner when `daysLeft` is not null, indicating an active trial period. Interactive elements like `NotificationBell` and `ThemeToggle` are integrated, along with a logout button that uses `createClient` from `@/lib/supabase/client` to sign out the user and redirect them to `/login`. The component implements responsive design, rendering a fixed sidebar on desktop and a mobile drawer that can be toggled open or closed using `useState`.

### Dashboard Page (`src/app/dashboard/page.tsx`)

The `DashboardPage` is a server component that fetches and displays the core operational data for the professional. It begins by authenticating the user and retrieving the professional's profile, similar to the layout, redirecting if the user is unauthenticated or lacks a profile.

The page executes several Drizzle queries to gather data:
*   `todayAppointments`: Fetches appointments scheduled for the current day, joining with the `clients` table to retrieve client names and phone numbers. It filters by `professionalId` and `startsAt` within the current day's bounds.
*   `upcomingAppointments`: Retrieves future appointments, similarly joining with `clients` and filtering for `startsAt` after the current day. It limits the results to 20.
*   Aggregate statistics: A `Promise.all` block concurrently fetches:
    *   `totalClients`: The total count of clients associated with the professional.
    *   `monthlyAppointments`: The count of appointments within the current month.
    *   `reviewStats`: The average `rating` and total count of `reviews` for the professional.
    *   `recentReviews`: The three most recent reviews, including client names and comments.
    *   `availabilityCount`: The number of availability slots configured by the professional.

The page then uses this data to render a highly contextual user interface:
*   **Welcome Card**: Shown only when `totalClients` is zero, guiding new professionals to share their public booking link.
*   **Plan Limit Banners**: Displays warnings or blocks functionality if the professional is nearing or has reached their `clients` or `appointmentsPerMonth` limits, based on their `plan` and `PLANS` configuration.
*   **Trial Banners**: Informs the professional about their active trial (`daysLeft`) or offers an option to start a trial if they are on the "free" plan.
*   **Profile Completeness**: A banner appears if `findProfileGaps` identifies missing profile information, prompting the professional to complete their settings. This is suppressed if `totalClients` is zero to avoid overwhelming new users.
*   **Greeting and Stats**: A personalized greeting and a summary of key metrics: today's appointments, pending confirmations, and total clients.
*   **Reputation Section**: If `reviewCount` is greater than zero, it displays the average rating and recent client comments, linking to the professional's public profile.
*   **Appointment Lists**: Detailed lists for `todayAppointments` and `upcomingAppointments`, showing time, client name, phone, and status. Each appointment includes `AppointmentActions` for quick status updates.
*   **Revenue Display**: If `revenue` (calculated from today's captured appointments) is greater than zero, it shows the total earnings for the day.

Utility functions like `getToday`, `formatTime`, and `formatCurrency` assist in data presentation. The `STATUS_LABEL` object maps appointment statuses to human-readable labels and Tailwind CSS classes for visual differentiation.

## Design decisions

The architecture of the dashboard reflects several key design choices aimed at performance, user experience, and maintainability:

*   **Server Components for Data Fetching**: Both `DashboardLayout` and `DashboardPage` are Next.js Server Components. This decision allows for direct database access using Drizzle ORM without exposing database credentials to the client. It also means that data fetching happens on the server, reducing the client-side JavaScript bundle size and improving the initial page load performance. The data is then passed down to client components like `Sidebar` as props, or rendered directly on the server.
*   **Drizzle ORM**: The choice of Drizzle for database interactions provides a type-safe and expressive way to construct SQL queries. This reduces the likelihood of runtime errors due to incorrect column names or types and improves developer productivity by offering strong autocompletion and compile-time checks. The use of `eq`, `and`, `gte`, `lte`, `count`, `gt`, `desc`, and `sql` demonstrates Drizzle's flexibility for various query patterns, including aggregates and joins across tables like `professionals`, `appointments`, `clients`, `reviews`, and `availability`.
*   **Conditional UI for Guided Experience**: The dashboard heavily relies on conditional rendering to present relevant information and calls to action. Banners for `WelcomeCard`, plan limits, trial status, and profile completeness are dynamically displayed based on the professional's current state. This approach creates a highly personalized and guided user experience, nudging users towards necessary actions (e.g., completing their profile, upgrading their plan) without cluttering the interface with irrelevant information.
*   **Separation of Concerns with `AppointmentActions`**: The `AppointmentActions` component is extracted as a separate client component. This encapsulates the logic and UI for confirming, rejecting, or completing appointments, keeping the main `DashboardPage` focused on data display. This separation improves readability, makes the `DashboardPage` less complex, and allows `AppointmentActions` to manage its own state and interactions independently.
*   **Client-Side Interactivity in `Sidebar`**: While the layout and page are server components, the `Sidebar` is explicitly marked `"use client"`. This is necessary because the sidebar contains interactive elements such as state for mobile menu toggling (`useState`), client-side routing (`usePathname`, `useRouter`), and event handlers for logout and navigation. This hybrid approach leverages the strengths of both Server and Client Components, ensuring a fast initial load while maintaining a dynamic and responsive user interface where needed.

## Potential improvements

1.  **Optimize `pendingCount` Calculation**: In `src/app/dashboard/page.tsx`, the `pendingCount` is calculated by filtering `[...todayAppointments, ...upcomingAppointments]` in memory. This means all appointments are fetched from the database, and then the filtering for "pending_confirmation" status happens on the server after the data is retrieved. For larger datasets, it would be more efficient to push this filtering logic down to the database query itself, potentially adding a `count` aggregate with a `WHERE` clause for `status = 'pending_confirmation'` to the existing `Promise.all` block.
2.  **Dynamic Appointment Pricing**: The `revenue` calculation in `src/app/dashboard/page.tsx` currently sums `professional.sessionPrice` for each captured appointment. This assumes all appointments have the same price, which is derived from the professional's default session price. If appointments can have individual prices (e.g., different service types, discounts), the `appointments` table would need a `price` column, and the revenue calculation should sum that column instead of `professional.sessionPrice`.
3.  **Centralize `PLAN_LABEL` and `PLAN_COLOR`**: The `PLAN_LABEL` and `PLAN_COLOR` objects are defined directly within `src/app/dashboard/sidebar.tsx`. If these mappings are used elsewhere in the application (e.g., on the plans page or in other UI components displaying plan information), they should be extracted into a shared utility file (e.g., `src/lib/plan-utils.ts`). This would reduce duplication and make it easier to manage plan-related display logic consistently across the codebase.
