# Dashboard

The professional dashboard serves as the central hub for professionals using Odys, providing an at-a-glance overview of their practice and direct access to key functionalities. This page, located at `src/app/dashboard/page.tsx`, is the primary entry point after a professional logs in, presenting a summary of appointments, client statistics, and profile completeness. It is carefully structured with a persistent sidebar (`src/app/dashboard/sidebar.tsx`) managed by the dashboard layout (`src/app/dashboard/layout.tsx`), ensuring a consistent navigation experience across all dashboard sub-routes.

## Overview

The dashboard's architecture is built upon Next.js's App Router, leveraging server components for efficient data fetching and client components for interactive UI elements. The `src/app/dashboard/layout.tsx` file acts as the root for all dashboard routes, handling initial user authentication and fetching core professional data. This data is then passed to the `Sidebar` component, which provides navigation and displays professional details. The main content area, rendered by `src/app/dashboard/page.tsx`, dynamically fetches and displays a wealth of information, including today's and upcoming appointments, client statistics, and reputation metrics.

## Dashboard Layout

The `src/app/dashboard/layout.tsx` file is a server component, making it ideal for handling authentication and initial data loading before any client-side rendering occurs. Upon a request to any `/dashboard` route, this layout first attempts to retrieve the authenticated user's session using `createClient` from `@/lib/supabase/server`. If no user is found, the request is immediately redirected to `/login`.

Once authenticated, the layout queries the `professionals` table in the Drizzle ORM database to fetch the current professional's profile, identified by `user.id`. If a professional profile does not exist (e.g., for a newly registered user), the user is redirected to the `/onboarding` flow. This ensures that only registered professionals with complete profiles can access the dashboard.

The fetched professional data, specifically `name`, `slug`, `plan`, and `trialEndsAt`, is then passed as props to the `Sidebar` component. This allows the sidebar to display personalized information and adapt its navigation based on the professional's subscription plan and trial status. The layout also includes a `PostHogIdentify` component, which is used to associate the user's activity with their `userId` for analytics purposes. The main content of the dashboard, represented by `{children}`, is rendered within a flexible container that allows for vertical scrolling, accommodating various screen sizes and content lengths.

## Dashboard Page

The `src/app/dashboard/page.tsx` file is also a server component, responsible for fetching and rendering the core dashboard content. It performs several database queries concurrently using `Promise.all` to gather all necessary data for the dashboard view:

*   **Professional Profile**: It re-fetches the professional's profile from the `professionals` table, similar to the layout, to access all 32 columns, including `sessionPrice` for revenue calculation and various profile fields for completeness checks.
*   **Appointments**: It retrieves today's appointments and upcoming appointments from the `appointments` table, joining with the `clients` table to display client names and phone numbers. These queries filter appointments based on `professionalId` and `startsAt` timestamps, using `gte` and `lte` for today's appointments and `gt` for upcoming ones.
*   **Statistics**:
    *   `totalClients`: A count of all clients associated with the professional from the `clients` table.
    *   `monthlyAppointments`: A count of appointments scheduled within the current month.
    *   `reviewStats`: Aggregated average `rating` and total `count` of reviews from the `reviews` table.
    *   `recentReviews`: The three most recent reviews, including `rating`, `comment`, `createdAt`, and the `clientName` (joined from `clients`).
    *   `availabilityCount`: A count of entries in the `availability` table, used to determine profile completeness.

Based on this data, the page calculates several derived states, such as `daysLeft` in a trial, the `effectivePlan`, and flags for `isNearClientLimit`, `isAtClientLimit`, `isNearMonthlyLimit`, `isAtMonthlyLimit`. It also determines `profileGaps` using the `findProfileGaps` utility, which checks for missing essential professional profile information.

The UI is highly conditional, displaying various banners and sections based on the professional's status:

*   **Welcome Card**: Shown only when `totalClients` is 0, guiding new professionals to share their public booking link.
*   **Plan Limit Banners**: Alerts are displayed if the professional is nearing or has reached their plan's limits for clients or monthly appointments, prompting an upgrade. The `PLANS` object from `@/lib/stripe` defines these limits for `free`, `basic`, `pro`, and `premium` plans.
*   **Trial Banners**: The page displays a banner to invite free users to start a Pro trial, and another banner informs professionals about their active Pro trial, showing `daysLeft` and encouraging subscription.
*   **Profile Completeness Banner**: Appears if `profileGaps` exist and the professional has at least one client, nudging them to complete their profile.
*   **Greeting and Stats**: Displays a personalized greeting and key metrics like today's appointments, pending confirmations, and total clients.
*   **Reputation Section**: If `reviewCount` is greater than 0, it shows the average rating and recent client comments, linking to the professional's public profile.
*   **Appointment Lists**: Separate sections for "Agenda de hoje" (Today's appointments) and "Próximos agendamentos" (Upcoming appointments). Each appointment displays time, client name, phone, and status. The `STATUS_LABEL` object maps appointment statuses to human-readable labels and Tailwind CSS classes for visual distinction.
*   **Appointment Actions**: For `pending_confirmation` or `confirmed` appointments, the `AppointmentActions` component is rendered, allowing professionals to manage the appointment status.
*   **Revenue**: If `revenue` for today's captured payments is greater than 0, it displays the total.

Utility functions like `getToday`, `formatTime`, and `formatCurrency` are used to format dates, times, and monetary values for display.

## Dashboard Sidebar

The `src/app/dashboard/sidebar.tsx` is a client component, indicated by `"use client"`. This choice is necessary because it uses React hooks like `useState` for managing mobile menu state and Next.js hooks like `usePathname` and `useRouter` for navigation and client-side redirects (e.g., after logout).

The sidebar receives `professionalName`, `professionalSlug`, `plan`, and `trialEndsAt` as props from the `DashboardLayout`. It uses these to:

*   Display the professional's initials and current plan status (e.g., "Pro (trial)"). The `PLAN_LABEL` and `PLAN_COLOR` objects provide localized names and styling for each plan.
*   Render a trial banner if `daysLeft` is not null, similar to the main dashboard page, but tailored for the sidebar's compact space.
*   Populate the navigation (`NAV` array), which includes links to `/dashboard`, `/dashboard/clients`, `/dashboard/messages`, `/dashboard/reports`, `/dashboard/assistant`, `/dashboard/plans`, and `/dashboard/settings`.
*   Crucially, some navigation items are marked `proOnly`. If the `activePlan` is "free", these links are visually "locked" and redirect to the `/dashboard/plans` page when clicked, encouraging an upgrade.
*   Provide links to the professional's public page (`/p/[slug]`) and a "Client Mode" (`/c`).
*   Offer a logout button that calls `supabase.auth.signOut()` and redirects the user to `/login`.
*   Integrate `ThemeToggle` for dark/light mode switching and `NotificationBell` for alerts.

The sidebar implements a responsive design, appearing as a fixed sidebar on desktop (`md:flex`) and transforming into a mobile drawer (`fixed top-0 left-0 z-50`) that can be toggled open and closed on smaller screens.

## Design decisions

The dashboard's design reflects a clear separation of concerns between server and client components, a common pattern in Next.js applications.

*   **Server-Side Data Fetching**: Both `layout.tsx` and `page.tsx` are server components, fetching data directly from the database using Drizzle ORM. This decision keeps sensitive database queries and business logic (like plan limit calculations or profile completeness checks) on the server, preventing them from being exposed to the client. It also reduces the JavaScript bundle size sent to the browser, improving initial page load performance. The use of `Promise.all` for concurrent queries in `page.tsx` is a deliberate choice to minimize the total data fetching time, as many independent pieces of information are required to render the dashboard.
*   **Client-Side Interactivity**: The `sidebar.tsx` component is marked `"use client"` because it requires client-side state management (`useState`) for its mobile drawer functionality and client-side routing hooks (`usePathname`, `useRouter`) for active link highlighting and navigation. This allows for a dynamic and responsive navigation experience without forcing the entire dashboard to be a client component.
*   **Drizzle ORM for Type Safety and Efficiency**: The application uses Drizzle ORM for database interactions. This provides type safety for queries and results, reducing runtime errors. The direct use of Drizzle's `eq`, `and`, `gte`, `lte`, `count`, `gt`, `desc`, and `sql` functions allows for expressive and efficient SQL queries, directly mapping to the underlying database schema with 11 tables, including `professionals`, `appointments`, `clients`, and `reviews`.
*   **Conditional UI for Guided Experience**: The extensive use of conditional rendering for banners (welcome, trial, plan limits, profile gaps) and content sections (reputation, upcoming appointments, revenue) is a design choice to provide a highly tailored and guided user experience. New users see onboarding nudges, users on trials are encouraged to subscribe, and users nearing plan limits are prompted to upgrade. This proactive communication helps users understand their status and available actions.

## Potential improvements

1.  **Optimize Redundant Data Fetching**: The `professional` data is fetched independently in both `src/app/dashboard/layout.tsx` and `src/app/dashboard/page.tsx`. While Next.js might de-duplicate some requests, passing the `professional` object as a prop from the layout to its children (`page.tsx`) would explicitly ensure the data is fetched only once at the layout level. This would reduce database load and potentially improve the performance of the dashboard page.
2.  **Centralize UI Text and Internationalization**: Many strings in `src/app/dashboard/page.tsx` and `src/app/dashboard/sidebar.tsx` are hardcoded in Portuguese (`pt-BR`), such as "Olá", "agendamentos", "Clientes", "Sair", and the date/currency formatting. Introducing an internationalization (i18n) library and centralizing these texts would make the application adaptable to multiple languages and locales without modifying component code. This would also simplify text updates and ensure consistency.
3.  **Refine `AppointmentActions` Logic**: The `AppointmentActions` component in `src/app/dashboard/page.tsx` is conditionally rendered for `pending_confirmation` or `confirmed` appointments. While the component itself is client-side, the actual status updates likely involve API calls. Explicitly defining and documenting the API routes (e.g., `/api/appointments/[id]` with a `PATCH` method) that `AppointmentActions` interacts with would clarify the data flow and allow for more granular control over permissions and validation for appointment status changes.
4.  **Implement Loading Skeletons**: For a data-rich page like the dashboard, the initial load or subsequent data refreshes can take time. Introducing loading skeletons for the various sections (stats, appointments, reviews) in `src/app/dashboard/page.tsx` would provide a better user experience by indicating that content is being loaded, rather than presenting a blank screen or abrupt content pop-ins.
