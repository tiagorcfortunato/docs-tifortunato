# Booking Widget

The `BookingWidget` component, located at `src/app/p/[slug]/booking-widget.tsx`, serves as the primary interface for clients to schedule appointments with professionals on the Odys platform. It is a client-side React component, indicated by `"use client"`, and is embedded directly within the professional's public profile page (`src/app/p/[slug]/page.tsx`). This widget guides users through a structured, multi-step process to select a date and time, provide their contact information, and receive confirmation for their booking request.

## Overview

The `BookingWidget` orchestrates the client-side booking experience through a well-defined, three-step state machine: "pick", "form", and "success". This sequential flow ensures that clients provide all necessary information in an intuitive order.

At its core, the widget relies on several key technologies and internal utilities:

*   **State Management**: React's `useState` hooks manage the widget's internal state, including the currently selected date and time, loading indicators, and the current step in the booking process.
*   **Form Handling**: `react-hook-form` is employed for managing client input fields, offering robust validation capabilities.
*   **Schema Validation**: `zod` is integrated with `react-hook-form` via `@hookform/resolvers/zod` to define and enforce the structure and validation rules for client data.
*   **Slot Generation**: The `generateSlots` utility, found in `src/lib/slots.ts`, is crucial for dynamically calculating and presenting available appointment times based on the professional's availability rules and existing bookings.
*   **API Interaction**: The widget communicates with the backend via the `/api/booking` route, both to fetch available slots (`GET`) and to submit new booking requests (`POST`).
*   **Analytics**: `posthog` is used to capture `booking_created` events upon successful submission, providing insights into booking patterns (`src/app/p/[slug]/booking-widget.tsx:89-93`).

The `BookingWidget` receives essential professional details as props from its parent `BookingPage` component, such as `slug`, `professionalName`, `sessionDuration`, `sessionPrice` (provided in cents), `paymentType`, `paymentPercentage` (which defaults to `100` if not explicitly set by the professional), `pixKeyType`, and `pixKey`. It also receives optional `defaultName`, `defaultPhone`, `defaultEmail` for pre-filling forms for logged-in clients, and an `isLoggedIn` flag for conditional UI.

## State Management and Flow

The widget's user experience is driven by its internal state, particularly the `step` variable, which can be `"pick"`, `"form"`, or `"success"`.

1.  **`step: "pick"` (Date and Time Selection)**: This is the initial state where the client selects a desired date using the `Calendar` component, which disables past dates to prevent booking in the past (`src/app/p/[slug]/booking-widget.tsx:254`). Once a date is chosen, an `useEffect` hook triggers an asynchronous call to the `/api/booking` endpoint. This API request, using the professional's `slug` and the `selectedDate`, retrieves the professional's availability rules and any existing appointments for that day. The `generateSlots` function then processes this data, along with the `sessionDuration`, to compute and display a list of available time slots. These slots are visually grouped into "Manhã" (Morning), "Tarde" (Afternoon), and "Noite" (Evening) using the `groupSlots` helper function for better readability. Clients can then select a specific `selectedSlot` from these options.
2.  **`step: "form"` (Client Information Entry)**: After a date and time slot are selected, the `step` transitions to `"form"`. Here, the client is presented with a form to enter their `name`, `phone`, and optionally `email`. This form is managed by `react-hook-form` and validated against the `clientSchema` using `zod`. The form also includes a hidden `website` field, acting as a honeypot to deter automated spam submissions. Upon successful submission, the `onSubmit` handler constructs the `startsAt` timestamp and sends a `POST` request to `/api/booking`.
3.  **`step: "success"` (Booking Confirmation)**: Following a successful booking submission, the `step` changes to `"success"`. This final view displays a confirmation message, reiterating the appointment details. If the professional's `paymentType` is not "after" and a `pixKey` is provided, a `PixQR` component is rendered, displaying a QR code for an initial payment based on the `paymentPercentage` of the `sessionPrice`. The `pixKeyType` is passed to `PixQR` as a string, defaulting to an empty string if `null` (`src/app/p/[slug]/booking-widget.tsx:121`). For unauthenticated users, the success screen also offers a link to register for an account, pre-filling the registration form with the `submittedData` (name, email, phone) to streamline the onboarding process. Logged-in users are directed to their appointments dashboard.

## Slot Generation Logic

The `generateSlots` function in `src/lib/slots.ts` is central to determining available booking times. It takes the `date`, a set of `AvailabilityRule` objects (representing the professional's weekly schedule from the `availability` table), `ExistingAppointment` objects (from the `appointments` table), and the `sessionDuration` (from the `professionals` table) as inputs.

The function first identifies the relevant `AvailabilityRule` for the given `date`'s `dayOfWeek`. It then iterates through potential `current` start times, incrementing by `sessionDuration`. For each potential slot, it performs several checks:

*   **Rule Adherence**: Ensures the `slotEnd` does not exceed the `endTime` defined in the `AvailabilityRule`.
*   **Past Slots**: Skips any slots that are in the past relative to the current `now`.
*   **Conflict Detection**: Crucially, it checks for overlaps with `existingAppointments`. A slot is considered conflicting if its start time is before an existing appointment's end time, AND its end time is after an existing appointment's start time.

Only slots that pass all these checks are added to the list of available slots, formatted as "HH:mm" strings.

## Design Decisions

The design of the `BookingWidget` reflects several deliberate choices aimed at user experience, maintainability, and performance:

*   **Client-Side Component**: Marking `BookingWidget` with `"use client"` is necessary because it manages interactive UI elements like the `Calendar`, form inputs, and dynamic state transitions. This allows for a rich, responsive user experience without full page reloads.
*   **Three-Step State Machine**: The explicit `step` state (`"pick"`, `"form"`, `"success"`) simplifies the component's logic and provides a clear, guided flow for the user. This approach makes it easier to reason about the UI at each stage and manage complex conditional rendering.
*   **`react-hook-form` and `zod`**: This combination was chosen for its efficiency in handling form state, reducing re-renders, and providing a declarative way to define validation rules. `zod` offers strong type inference and a concise API for schema definition, which integrates well with TypeScript and `react-hook-form`'s `zodResolver`.
*   **Honeypot Field**: The `website` input field, visually hidden and marked with `aria-hidden="true"`, is a common and effective technique to combat spam. Naive bots often fill all form fields, and any value in this field on the server-side (`/api/booking` POST handler) indicates a spam submission, which can then be silently dropped.
*   **`date-fns` for Date Manipulation**: The `date-fns` library is used for all date and time operations, including formatting (`format`), adding minutes (`addMinutes`), and comparisons (`isBefore`, `isAfter`). Its modularity and immutability make it a reliable choice for handling date logic, especially with locale support (`ptBR`).
*   **Dedicated API Route for Slots**: Fetching availability data via `/api/booking?slug=...&date=...` separates the data retrieval logic from the frontend UI. This allows the server to perform database queries (e.g., against `availability` and `appointments` tables) and business logic (like `generateSlots`) efficiently, reducing the client's payload and processing.
*   **Dynamic Registration Link**: The `registerUrl` generation in the success step, pre-filling client data, is a thoughtful UX touch. It reduces friction for new users by carrying over information they've already provided, encouraging account creation.

## Potential Improvements

While the `BookingWidget` provides a functional booking experience, several areas could be enhanced:

*   **Timezone Handling**: The current slot generation and booking submission rely on `new Date()` and `startsAt.setHours()`, which can be susceptible to client-side timezone discrepancies. Storing and processing all appointment times in UTC on the server and converting them to the client's local timezone for display would make the system more robust and prevent potential booking errors across different geographical locations.
*   **Real-time Slot Availability**: The `useEffect` hook fetches slots once when `selectedDate` changes. In a high-traffic scenario, a slot might become unavailable between the time a client loads the slots and when they submit the form. Implementing a more dynamic check, perhaps a quick API call to validate the `selectedSlot`'s availability just before form submission, could mitigate race conditions.
*   **Granular Loading States**: While `loadingSlots` indicates that slots are being fetched, the individual `SlotButton` components do not show a loading state when selected. If the selection of a slot involved more complex client-side validation or a minor API call, a loading indicator on the selected button could improve user feedback.
*   **Accessibility for Slot Grouping**: The visual grouping of slots into "Manhã", "Tarde", "Noite" is helpful. Ensuring these headings are semantically linked to their respective grids of `SlotButton` elements (e.g., using `aria-labelledby` or `role="group"`) would improve accessibility for screen reader users.
*   **Error Handling for Slot Fetching**: The `loadSlots` function in `useEffect` currently does not have explicit error handling for the `fetch` call. If the `/api/booking` endpoint fails to return data, the `setSlots([])` will correctly show no slots, but a `toast.error` or a more specific message could inform the user about the network issue.
