# Booking Widget

The booking widget, found in `src/app/p/[slug]/booking-widget.tsx`, is a central interactive component on a professional's public profile page. Its primary purpose is to guide a client through the process of selecting an appointment time and providing their contact details, ultimately submitting a booking request. This component orchestrates a multi-step user experience, handles client input validation, and communicates with the backend to fetch available slots and create new appointments.

## Overview

The `BookingWidget` is a client-side React component rendered within the server-side `BookingPage` (`src/app/p/[slug]/page.tsx`). It receives essential professional details as props, such as the professional's `slug`, `name`, `sessionDuration`, `sessionPrice`, and payment configuration (e.g., `paymentType`, `paymentPercentage`, `pixKeyType`, `pixKey`). It also receives pre-filled client data (`defaultName`, `defaultPhone`, `defaultEmail`) if the user is logged in, streamlining the booking process for returning clients.

The widget operates as a three-step state machine, managed by the `step` state variable: "pick" for date and time selection, "form" for client information entry, and "success" for booking confirmation. This structured approach helps break down a potentially complex interaction into manageable stages for the user.

## Slot Generation and Display

The initial step, "pick", focuses on allowing the client to choose an available date and time. The `Calendar` component facilitates date selection, and upon a date change, a `useEffect` hook triggers the `loadSlots` asynchronous function.

The `loadSlots` function makes a `GET` request to the `/api/booking` API route, passing the professional's `slug` and the `selectedDate`. The backend responds with the professional's `availability` rules (derived from the `availability` table, which defines working hours for each `dayOfWeek`) and `existingAppointments` (from the `appointments` table).

These raw data points are then fed into the `generateSlots` utility function, located in `src/lib/slots.ts`. This function is responsible for calculating all potential appointment slots for the `selectedDate`. It considers the professional's `sessionDuration` (from the `professionals` table), the defined `AvailabilityRule` for that day, and filters out any `ExistingAppointment` conflicts. It also ensures that only future slots are presented, preventing bookings in the past, and that no generated slot extends beyond the professional's defined `endTime` for the day. The `Calendar` component itself prevents selection of dates prior to the current day. The resulting available slots, formatted as "HH:mm" strings, are then stored in the component's `slots` state.

To enhance user experience, the `groupSlots` helper categorizes times: "Manhã" (before 12h), "Tarde" (12h-17h), and "Noite" (18h onwards), making it easier for clients to browse. Each slot is rendered as a `SlotButton`, allowing clients to select their preferred time. Once a slot is chosen, a "Continuar" button appears, transitioning the widget to the "form" step.

## Client Form Handling

The "form" step is where the client provides their personal details. This section utilizes `react-hook-form` for managing form state and `zod` with `@hookform/resolvers/zod` for schema-based validation. The `clientSchema` defines the expected structure and validation rules for `name`, `phone`, and `email`. The `name` field requires at least 2 characters, and `phone` requires at least 10 characters, while `email` is optional.

A notable inclusion in the form is a "honeypot" field named `website`. This input is visually hidden and inaccessible to human users (via `tabIndex={-1}`, `aria-hidden="true"`, and CSS styling). Its purpose is to deter automated spam bots, which often fill out every input field on a page. Any submission with a non-empty value in this field is intended to be silently dropped by the server, providing a simple yet effective layer of spam prevention.

Upon submission, the `onSubmit` function is invoked. It constructs the `startsAt` timestamp by combining the `selectedDate` and `selectedSlot`. A `POST` request is then sent to the `/api/booking` API route, including the professional's `slug`, the `startsAt` time, and the client's details. If the booking is successful, a `booking_created` event is captured by PostHog, including `professional_slug`, `day_of_week`, `hour`, and `is_logged_in` properties, and the widget transitions to the "success" step. Error handling is implemented using `toast.error` to provide feedback to the user if the booking fails.

## Success State and Post-Booking Experience

The final "success" step confirms the booking request to the client. It displays a summary of the appointment, including the professional's name, selected date, and time. A message informs the client that they will receive a confirmation once the professional approves the booking.

Depending on the professional's `paymentType` and whether a `pixKey` is configured, a `PixQR` component might be displayed, prompting the client for an initial payment. The `pixAmount` is calculated based on the `sessionPrice` and `paymentPercentage` from the `professionals` table.

For clients who are not logged in, the success screen presents an invitation to create a free account. This registration link (`/register`) is intelligently pre-filled with the client's submitted `name`, `email`, and `phone` to minimize friction. Logged-in clients are offered a direct link to their appointments dashboard (`/c`).

## Design Decisions

The `BookingWidget` is implemented as a client component (`"use client"`) to enable interactive features like state management (`useState`), side effects (`useEffect`), and form handling. This choice allows for a dynamic user experience without requiring full page reloads for each interaction.

The three-step state machine (`step`) was chosen to simplify the user journey. Instead of presenting a single, potentially overwhelming form, breaking it into logical stages (pick date/time, enter details, confirm) improves usability and reduces cognitive load.

The combination of `react-hook-form` and `zod` provides a robust and efficient solution for form management. `react-hook-form` minimizes re-renders and offers a clean API for form state, while `zod` ensures strong type safety and declarative validation, making the form logic predictable and maintainable. The inclusion of a honeypot field is a pragmatic trade-off, opting for a simple, client-side spam mitigation technique rather than relying solely on more complex server-side solutions.

The `generateSlots` function is extracted into `src/lib/slots.ts` to promote reusability and separation of concerns. This utility can be tested independently and potentially used by other parts of the application that need to calculate available time slots.

The `BookingWidget` receives most of its initial data as props from the parent server component (`src/app/p/[slug]/page.tsx`). This design leverages Next.js's server components for efficient data fetching (e.g., professional details, client defaults, reviews, related professionals) and rendering, reducing the amount of client-side JavaScript and improving initial page load performance. Only the dynamic data, like available slots, is fetched client-side.

## Potential Improvements

1.  **Enhanced Slot Loading Error Handling**: The `loadSlots` function within the `useEffect` hook in `src/app/p/[slug]/booking-widget.tsx` currently handles loading states but lacks explicit error handling for the `fetch` call. If the `/api/booking` endpoint fails, the `loadingSlots` state will simply become `false`, leaving the user without clear feedback. Implementing a `try...catch` block around the `fetch` call and setting an `error` state would allow for displaying a user-friendly error message, prompting them to retry or contact support.
2.  **Timezone Awareness for Slot Generation**: The `generateSlots` function in `src/lib/slots.ts` and the `BookingWidget` component use `Date` objects and `toISOString()` without explicit timezone handling. While `date-fns` functions like `format` can take a locale, the underlying `Date` object's behavior can be inconsistent across different client timezones and the server. For a global application, it would be beneficial to standardize on UTC for all backend storage and calculations, and explicitly convert to the client's local timezone only for display, using libraries like `date-fns-tz` or `luxon` to prevent potential off-by-one day or hour errors.
3.  **Accessibility for Slot Buttons**: The `SlotButton` component in `src/app/p/[slug]/booking-widget.tsx` uses a generic `button` element. While functional, adding `aria-label` attributes that clearly describe the slot (e.g., "Agendar para {slot} da manhã") would improve accessibility for users relying on screen readers, making the selection process more intuitive.
4.  **Refined Payment Flow Integration**: The `PixQR` component is displayed in the "success" step, but the current code does not explicitly show how the payment status (`paymentStatus` in the `appointments` table) is updated based on the client's interaction with the QR code. While this might be handled by a separate webhook or professional action, integrating a more direct feedback loop or instructions within the widget for payment confirmation could enhance the client experience and reduce uncertainty.
