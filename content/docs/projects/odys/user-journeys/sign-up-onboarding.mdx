# Sign-up Onboarding

The professional sign-up and onboarding journey is a critical sequence that transforms a new user into a fully configured professional ready to offer services. This process involves initial user registration, email verification, and the collection of detailed professional information, culminating in the creation of their public profile and service availability.

## Overview

This end-to-end flow orchestrates several key components to guide a professional from initial interest to an active service provider. It begins with user account creation, handled by the `/api/auth/register` API route, which integrates with Supabase for authentication. Following successful registration and email verification, the user is directed through an onboarding process managed by the `/api/onboarding` route. This route collects specific details about the professional's services and availability, persisting this information in the `professionals` and `availability` database tables. The `/auth/callback` route plays a crucial role in handling Supabase's authentication redirects, including email verification and password recovery, and also performs a "smart-linking" operation for existing clients.

The `professionals` table, with its 32 columns, serves as the central repository for a professional's profile, storing everything from their `name` and `profession` to `sessionDuration`, `sessionPrice`, and even payment-related fields like `pixKey` and `stripeCustomerId`. The `availability` table, comprising 5 columns, stores the specific `dayOfWeek`, `startTime`, and `endTime` slots when a professional is available for appointments. Throughout this journey, rate limiting is applied to key API endpoints to prevent abuse and ensure system stability.

## Registration

The initial step for any new user is creating an account, which is managed by the `POST` handler in `src/app/api/auth/register/route.ts`. This route accepts `email` and `password`, along with optional `name` and `type` fields, which are stored in Supabase's `user_metadata`. The password is required to be at least 8 characters long, aligning with Supabase's default authentication policies.

To safeguard against brute-force attacks and spam registrations, the `getRegisterLimiter()` from `src/lib/ratelimit.ts` is applied. This limiter restricts registration attempts to 5 per hour per IP address, ensuring that the system can handle legitimate sign-ups while mitigating malicious activity.

A notable design choice in this route is the conditional handling of user creation based on the environment. In a production environment, the `supabase.auth.signUp()` method is used. This approach relies on Supabase's built-in email verification flow, where a verification email is automatically dispatched to the user. If `signUp()` does not return a session, it indicates that email confirmation is required, which is communicated back to the client. Conversely, in development, the `getAdminClient().auth.admin.createUser()` method is employed with `email_confirm: true`. This allows developers to bypass the email verification step, accelerating the testing cycle by instantly confirming new users. This trade-off prioritizes developer velocity in non-production environments without compromising the security of the production flow.

## Authentication Callback

After a user interacts with an email verification link or completes a password recovery flow, Supabase redirects them to the `/auth/callback` route, defined in `src/app/auth/callback/route.ts`. This route is responsible for exchanging the Supabase-provided `code` for a user session.

A critical security measure implemented here is the `VALID_TYPES` set. This set explicitly defines the acceptable values for the `type` query parameter (`"professional"`, `"client"`, `"recovery"`). This prevents an attacker from injecting arbitrary data into the user's metadata via a crafted OAuth callback URL, which could otherwise lead to privilege escalation or data corruption.

Upon successful session exchange, the route handles different scenarios:
*   If the `type` is `"recovery"`, the user is redirected to the `/reset-password` page.
*   If the `type` is `"professional"` or `"client"`, the user's metadata in Supabase is updated to reflect their role. This is important for subsequent authorization checks and UI customization.
*   A "smart-linking" feature is implemented for clients: if a user's `email` is verified and their `type` is `"client"`, the system attempts to link their new `userId` to any existing entries in the `clients` table (8 columns) that have the same `email` but a `null` `userId`. This helps consolidate client profiles, ensuring that returning clients who sign up have their historical data associated with their new user account.

Finally, the user is redirected to `/auth/redirect` or `/login?error=auth` depending on the outcome of the authentication process.

## Professional Onboarding

Once a user has registered and verified their email, if they are a professional, they proceed to the onboarding flow handled by the `POST` method in `src/app/api/onboarding/route.ts`. This route is designed to collect comprehensive details necessary to set up a professional's profile and services.

Similar to registration, the `getOnboardingLimiter()` from `src/lib/ratelimit.ts` is applied, restricting onboarding attempts to 3 per hour per IP. This helps prevent abuse of the profile creation process.

The `onboardingSchema` defines the expected data, including the professional's `name`, `profession`, `phone`, `bio`, `sessionDuration`, `sessionPrice`, their `serviceType` (which defaults to `"both"` if not provided), and crucially, their `availability`. The `city` and `state` fields are optional; if provided, they are trimmed, and empty strings become `null` in the database. The `availability` field is an array of objects, each specifying a `dayOfWeek`, `startTime`, and `endTime`, ensuring that professionals can precisely define their working hours.

A key feature of this route is the generation of a unique `slug` for each professional. The `toSlug()` function converts the professional's `name` into a URL-friendly format. The `generateUniqueSlug()` function then ensures this slug is unique within the `professionals` table and does not conflict with any `RESERVED_SLUGS` (e.g., "api", "auth", "dashboard", "login", "explore", "privacidade"). If the generated base slug is empty or conflicts with a `RESERVED_SLUGS` entry, `generateUniqueSlug()` uses `"user"` as a base for suffixing, skipping the bare-base attempt. If a conflict occurs, a numeric suffix is appended (e.g., "john-doe-2"). This mechanism guarantees clean and predictable URLs for professional profiles.

The collected data is then inserted into the `professionals` table, creating a new entry with 32 columns of detailed information. If `availability` data is provided, it is simultaneously inserted into the `availability` table, linking specific time slots to the newly created professional via `professionalId`.

After the database operations, the user's Supabase metadata is updated to set their `type` to `"professional"` and their `name`. In a production environment, a welcome email is sent to the professional using `sendProfessionalWelcomeEmail()`. This email is sent asynchronously, meaning its failure does not block the onboarding process, though warnings are logged.

## Design decisions

The separation of the initial user registration (`/api/auth/register`) from the professional-specific onboarding (`/api/onboarding`) is a deliberate design choice. This allows for a generic user account creation process that can serve both clients and professionals, while the onboarding route focuses solely on collecting the specialized data required for a professional profile. This modularity keeps concerns separated and allows for different user journeys to branch off after initial registration.

The use of `supabase.auth.signUp()` in production and `admin.createUser()` in development within `src/app/api/auth/register/route.ts` reflects a pragmatic trade-off. While `signUp()` provides the necessary email verification flow for security in a live environment, `admin.createUser()` accelerates development by bypassing this step, allowing for quicker iteration and testing without manual email confirmation.

Rate limiting, implemented via `getRegisterLimiter()` and `getOnboardingLimiter()` from `src/lib/ratelimit.ts`, is applied at the very beginning of the respective API routes. This proactive measure prevents resource exhaustion and abuse by limiting the number of attempts an IP address can make within a given timeframe (5 attempts per hour for registration, 3 per hour for onboarding). The different limits reflect the varying resource intensity and potential for abuse at each stage.

The `generateUniqueSlug()` function in `src/app/api/onboarding/route.ts`, along with the `RESERVED_SLUGS` set, is crucial for maintaining clean and functional URLs. By ensuring that professional slugs are unique and do not conflict with existing application routes, the system avoids broken links and provides a consistent user experience. The suffixing mechanism (`-2`, `-3`, etc.) handles name collisions gracefully.

The `VALID_TYPES` set in `src/app/auth/callback/route.ts` is a direct response to a security concern. By strictly validating the `type` parameter from the callback URL, the system prevents malicious actors from injecting arbitrary data into user metadata, which could have led to unauthorized access or unexpected application behavior.

Finally, the "smart-linking" logic in `src/app/auth/callback/route.ts` for `clients.userId` aims to improve the user experience. It automatically associates a newly registered user with any pre-existing client records that share the same email, reducing data duplication and providing a more unified view of client interactions for professionals.

## Potential improvements

1.  **Refine optional metadata handling in `src/app/api/auth/register/route.ts`**: The `name` and `type` fields in `registerSchema` are optional. While `supabase.auth.signUp` and `admin.createUser` handle `undefined` values gracefully, explicitly filtering out `undefined` or `null` values from the `data` or `user_metadata` objects before passing them to Supabase could make the intent clearer and prevent sending unnecessary fields if they are truly absent.
2.  **Implement retry mechanism for welcome emails in `src/app/api/onboarding/route.ts`**: The `sendProfessionalWelcomeEmail` call is currently fire-and-forget, with failures only logged to `console.warn`. While this prevents blocking the onboarding flow, it means a professional might not receive their welcome email if the email service temporarily fails. Introducing a simple retry mechanism (e.g., using a background job or a dedicated queue) for email sending could improve reliability without impacting the user's immediate experience.
3.  **Expand smart-linking to include professionals as clients in `src/app/auth/callback/route.ts`**: The current smart-linking logic for `clients.userId` only executes if `type === "client"`. It might be beneficial to consider scenarios where a user registers as a "professional" but also exists as a client in another professional's `clients` table. Extending this logic to link `clients.userId` for professionals could provide a more complete view of user relationships across the platform, if that is a desired feature.
4.  **Centralize `RESERVED_SLUGS` management in `src/app/api/onboarding/route.ts`**: The `RESERVED_SLUGS` set is hardcoded within the `onboarding` route. As the application grows and new top-level routes are added, this list could become outdated or difficult to maintain. Consider moving this list to a shared configuration file or even dynamically generating it from the application's route manifest (if available) to ensure it always reflects the current routing structure.
