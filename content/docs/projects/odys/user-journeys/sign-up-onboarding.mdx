# Professional Onboarding

The professional sign-up and onboarding flow is a critical journey for Odys, enabling service providers to register, verify their identity, and set up their profile to begin offering services. This process is designed to be guided and secure, ensuring that new professionals can quickly establish their presence while adhering to platform standards. It encompasses user registration, email verification, and the initial setup of a professional profile, including service details and availability.

## Overview

The end-to-end professional onboarding experience is orchestrated across three primary API routes and their underlying database interactions. It begins with a user initiating registration via the `/api/auth/register` endpoint. Upon successful registration, Supabase handles email verification, which then directs the user to the `/auth/callback` route. This callback is crucial for finalizing the authentication process and performing initial user data updates. Finally, the professional completes their profile setup through the `/api/onboarding` endpoint, populating their service details and availability.

The core database tables involved in this flow are `professionals` and `availability`. The `professionals` table, with its `32` columns, stores comprehensive details about each service provider, ranging from personal information like `name` and `email` to business-specific data such as `profession`, `sessionDuration`, `sessionPrice`, and even payment-related fields like `pixKey` and `stripeCustomerId`. The `availability` table, comprising `5` columns, captures the professional's working hours, linking directly to the `professionals` table via `professionalId` with an `onDeleteCascade` rule, ensuring data integrity. Additionally, the `clients` table plays a role in "smart-linking" existing client entries to a newly registered user during the authentication callback.

## Registration

The registration process is handled by the `src/app/api/auth/register/route.ts` file, which exposes a `POST` endpoint at `/api/auth/register`. This route is the entry point for new users to create an account.

Upon receiving a registration request, the system first applies a rate limit using `getRegisterLimiter` from `src/lib/ratelimit.ts`. This limiter permits `5` registration attempts per IP address within a `1 h` window, identified by the `rl:register` prefix, mitigating brute-force attacks or spam registrations. If the limit is exceeded, a `429` status code is returned.

The incoming request body is validated against the `registerSchema`, a Zod schema that enforces the presence of a valid `email` and a `password` of at least `8` characters. It also optionally accepts `name` and `type` fields. This schema ensures that only well-formed data proceeds to user creation.

A key design choice here differentiates between `production` and `development` environments. In `production`, the `supabase.auth.signUp` method is used. This approach leverages Supabase's built-in email verification flow, where a confirmation email is automatically dispatched to the user. The response includes a `requiresEmailConfirmation` flag, indicating whether a session was immediately established or if verification is pending. Conversely, in `development`, an `adminClient` (initialized with the `SUPABASE_SERVICE_ROLE_KEY`) is used to call `admin.createUser` with `email_confirm: true`. This bypasses the email verification step, allowing developers to rapidly test the onboarding flow without needing to interact with email inboxes. This trade-off prioritizes developer velocity in non-production environments.

If user creation is successful, the endpoint returns a `200` status with `success: true`, the `type` of user, and the `requiresEmailConfirmation` status. Any errors during this process, such as invalid data or Supabase-related issues, result in appropriate `400` or `500` status codes.

## Authentication Callback

After a user clicks an email verification link (or completes a password recovery flow), they are redirected to the `src/app/auth/callback/route.ts` endpoint. This `GET` route is responsible for exchanging the Supabase authentication code for a user session and performing any necessary post-authentication setup.

The callback extracts a `code` and an optional `type` parameter from the URL's search parameters. The `type` parameter is crucial for distinguishing between different authentication flows, such as `professional` registration, `client` registration, or `recovery` for password resets. A `VALID_TYPES` set (`"professional"`, `"client"`, `"recovery"`) and the `parseType` function are used to strictly validate this parameter. This validation is a direct mitigation against a potential vulnerability (L4 finding) where an attacker could inject arbitrary data into user metadata via a crafted OAuth callback URL.

The `supabase.auth.exchangeCodeForSession(code)` call is the core of this route, converting the temporary code into a persistent user session. If this exchange is successful:
*   For `type === "recovery"`, the user is redirected to `/reset-password`.
*   If `type` is either `"professional"` or `"client"`, the user's Supabase `user_metadata` is updated to reflect their account type.
*   A "smart-linking" mechanism is then executed. If the user is a `client` and has a verified `email`, the system attempts to link their new `userId` to any existing entries in the `clients` table where `userId` is currently `null` and `email` matches the newly authenticated user's email. This is particularly useful if a professional created a client entry for someone who later signs up themselves, preventing duplicate client records.
*   Finally, the user is redirected to `/auth/redirect` for further client-side routing.

If the code exchange fails, the user is redirected to `/login?error=auth`.

## Professional Onboarding

Once a professional has registered and verified their email, they proceed to the onboarding flow, managed by the `src/app/api/onboarding/route.ts` file, which exposes a `POST` endpoint at `/api/onboarding`. This route allows professionals to complete their profile by providing detailed information about their services and availability.

Similar to registration, this endpoint is protected by a rate limiter, `getOnboardingLimiter`, which allows `3` attempts per IP address within a `1 h` window, identified by the `rl:onboarding` prefix. This prevents abuse during the profile creation phase.

The route first authenticates the user using `getUser()`. If no authenticated user is found, an `unauthorized` response is returned. A crucial idempotency check follows: the system queries the `professionals` table to see if an entry already exists for the current `user.id`. If it does, the existing professional data is returned, preventing duplicate profile creation if the user attempts to onboard multiple times.

The request body is validated against the `onboardingSchema`, which requires `name`, `profession`, `phone`, `sessionDuration`, `sessionPrice`, and at least one `availability` slot. Optional fields include `bio`, `serviceType`, `city`, and `state`. `sessionDuration` is constrained to a positive integer up to `480` minutes, and `sessionPrice` must be non-negative. The `availability` array requires `dayOfWeek`, `startTime`, and `endTime` for each entry.

A unique `slug` is generated for the professional's public profile URL. The `toSlug` function converts the professional's `name` into a URL-friendly format. The `generateUniqueSlug` function then ensures this slug is unique within the `professionals` table and does not conflict with any `RESERVED_SLUGS` (e.g., "api", "auth", "dashboard"). If a conflict occurs, a numeric suffix is appended (e.g., "john-doe-2").

Finally, the professional's data is inserted into the `professionals` table, and their specified `availability` slots are inserted into the `availability` table, both using Drizzle ORM. The user's Supabase `user_metadata` is also updated to set their `type` to `"professional"` and their `name`.

In `production` environments, a welcome email is sent to the professional using `sendProfessionalWelcomeEmail`. This is a fire-and-forget operation, meaning any failure in sending the email does not block the onboarding process, but a warning is logged.

## Design decisions

*   **Conditional Supabase User Creation**: The choice to use `admin.createUser` in `development` and `supabase.auth.signUp` in `production` for `/api/auth/register` is a pragmatic trade-off. In development, it significantly accelerates testing by bypassing the email verification step, which can be cumbersome locally. In production, `signUp` ensures that Supabase's built-in email verification flow is utilized, adding a layer of security and user confirmation that is essential for a live application.
*   **Rate Limiting**: Implementing rate limits via `@upstash/ratelimit` for both `/api/auth/register` (`5` attempts per `1 h`) and `/api/onboarding` (`3` attempts per `1 h`) is a fundamental security and stability measure. It protects these critical endpoints from abuse, such as brute-force attacks on registration or excessive resource consumption during profile creation, by preventing a single IP from overwhelming the system.
*   **Strict `type` Validation in Auth Callback**: The `VALID_TYPES` set and `parseType` function in `src/app/auth/callback/route.ts` demonstrate a commitment to security. By explicitly whitelisting accepted values for the `type` query parameter, the system prevents malicious actors from injecting arbitrary data into user metadata, which could lead to privilege escalation or other vulnerabilities. This directly addresses a potential L4 finding.
*   **Idempotency in Onboarding**: The `professionals` table check at the beginning of the `/api/onboarding` `POST` handler ensures that the onboarding process is idempotent. This means that if a user accidentally or intentionally submits the onboarding form multiple times, the system will simply return the existing professional profile rather than creating duplicate entries, leading to a more robust and user-friendly experience.
*   **Unique Slug Generation**: The `generateUniqueSlug` function, coupled with `RESERVED_SLUGS`, is designed to create user-friendly and unique public profile URLs (`/p/[slug]`) while preventing conflicts with existing application routes. This ensures that every professional has a distinct and accessible public presence without requiring manual intervention for slug management.
*   **Smart-linking Clients**: The logic in `src/app/auth/callback/route.ts` to update `clients.userId` for existing `clients` with a matching `email` is a thoughtful design choice to improve data consistency and user experience. It automatically associates a newly registered user with any client records that might have been created for them by a professional, streamlining the client management process.

## Potential improvements

1.  **Atomic Onboarding Database Operations**: The current `/api/onboarding` route performs two separate database `insert` operations: one for `professionals` and another for `availability`. If the second insertion fails, the `professionals` entry would still exist without its associated availability, leading to an inconsistent state. Wrapping these two Drizzle operations within a single database transaction would ensure atomicity, meaning either both succeed or both fail, maintaining data integrity.
2.  **Refined Slug Generation Fallback**: In `src/app/api/onboarding/route.ts`, the `generateUniqueSlug` function uses `"user"` as a fallback for `effectiveBase` if the `name` slugifies to an empty string or conflicts with a reserved slug. While functional, this could be made more descriptive or configurable. For instance, if a professional's name is "...", the slug might become "user-2". Consider a more context-aware fallback, perhaps incorporating a unique ID or a more generic placeholder that doesn't imply a generic "user" profile.
3.  **Enhanced Welcome Email Error Handling**: The `sendProfessionalWelcomeEmail` call in `src/app/api/onboarding/route.ts` currently uses a generic `.catch((err) => console.warn(...))` for error handling. While it prevents blocking the onboarding flow, a more sophisticated approach could involve integrating with a dedicated error monitoring service (e.g., Sentry, DataDog) or queuing the email for retry, ensuring that welcome emails are reliably delivered even if there are transient issues with the email service.
4.  **Explicit `clients.userId` Management**: The `clients.userId` column in the `clients` table is nullable, which facilitates the "smart-linking" feature in `src/app/auth/callback/route.ts`. However, this nullability could also lead to a proliferation of client entries that are not directly linked to a user account. While this might be intentional for clients added by professionals, it's worth evaluating if there are scenarios where a `userId` should be strictly enforced or if a background process could periodically identify and prompt linking for unlinked clients.
