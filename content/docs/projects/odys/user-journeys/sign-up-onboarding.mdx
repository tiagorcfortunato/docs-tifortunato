# Professional Onboarding

The professional onboarding journey in Odys is a critical sequence that guides new service providers from initial registration to a fully configured profile, ready to accept clients. This process is carefully structured to ensure data integrity, user experience, and system security, leveraging Supabase for authentication and Drizzle ORM for database interactions. It involves distinct steps for user account creation, email verification, and the subsequent population of professional-specific details and availability.

## Overview

The journey begins with a user registering an account, typically providing an email and password. This initial step is handled by the `/api/auth/register` endpoint, which integrates directly with Supabase's authentication system. Upon successful registration, an email verification flow is initiated (in production environments). Once the user's email is confirmed, they are redirected through the `/auth/callback` route, which finalizes the authentication session and performs some initial data linking.

The second major phase is the professional onboarding itself, managed by the `/api/onboarding` endpoint. Here, the authenticated user, now identified as a potential professional, provides detailed information about their services, pricing, and availability. This data is then persisted in the `professionals` and `availability` tables, establishing their presence within the Odys ecosystem. Throughout these steps, rate limiting is applied to prevent abuse, and careful data validation ensures that only well-formed information enters the system.

## User Registration

The `/api/auth/register` API route is the entry point for new users to create an account. It accepts `POST` requests and expects a JSON payload containing `email`, `password`, and optionally `name` and `type`.

Before processing any registration request, the system applies a rate limit using `getRegisterLimiter`. This limiter allows for 5 registration attempts per hour per IP address, a measure designed to mitigate brute-force attacks or spam registrations. If the limit is exceeded, the request is rejected with a `429 Too Many Requests` status.

The incoming data is validated against the `registerSchema`, a Zod schema that enforces basic constraints: `email` must be a valid email format, `password` must be at least 8 characters long (matching Supabase's default), and `name` must be at least 2 characters. The `type` field is an enum, accepting either `"client"` or `"professional"`.

A key design choice here differentiates between development and production environments. In production, the `supabase.auth.signUp()` method is used. This method automatically triggers Supabase's email verification flow, sending a confirmation email to the user. If no session is returned, it indicates that email confirmation is required. In contrast, for development, an `adminClient` is used to call `admin.createUser()` with `email_confirm: true`. This bypasses the email verification step, allowing developers to rapidly test the onboarding flow without needing to check inboxes. This distinction significantly accelerates the development cycle while maintaining production security.

Upon successful account creation, the route returns a `200 OK` response, indicating whether email confirmation is required.

## Authentication Callback

After a user interacts with a Supabase-generated email link (e.g., for email verification or password recovery), they are redirected to the `/auth/callback` route. This `GET` endpoint is responsible for exchanging the Supabase `code` for a user session and performing any necessary post-authentication actions.

The route extracts a `code` and an optional `type` parameter from the URL's search parameters. The `type` parameter is crucial for distinguishing the purpose of the callback. To prevent security vulnerabilities like arbitrary metadata injection, the `type` value is strictly validated against a `VALID_TYPES` set, which includes `"professional"`, `"client"`, and `"recovery"`. Any value outside this set is ignored.

The core of this route is the call to `supabase.auth.exchangeCodeForSession(code)`. If successful, it establishes the user's session. For password recovery (`type === "recovery"`), the user is redirected to `/reset-password`. If the `type` is `"professional"` or `"client"`, the user's Supabase metadata is updated to reflect their role using `supabase.auth.updateUser({ data: { type } })`. If `supabase.auth.exchangeCodeForSession` fails, the user is redirected to `/login?error=auth`.

A "smart-linking" feature is also implemented here for clients. If the authenticated user has an `email` and their `type` is `"client"`, the system attempts to link their `userId` to any existing entries in the `clients` table where the `userId` is currently `null` and the `email` matches. This allows pre-existing client records (perhaps created by a professional) to be associated with a newly registered user account once they verify their email. Finally, the user is redirected to `/auth/redirect` to complete the flow.

## Professional Onboarding

Once a user has registered and verified their email, they proceed to the professional onboarding process, handled by the `/api/onboarding` API route. This `POST` endpoint allows authenticated users to provide the specific details required to operate as a professional on the platform.

Similar to registration, this endpoint is protected by a rate limiter, `getOnboardingLimiter`, which permits 3 attempts per hour per IP address. This prevents excessive submissions or potential abuse during the profile setup phase.

The first step within the route is to authenticate the user using `getUser()`. If no user session is found, an `unauthorized()` response is returned. The system then checks for idempotency: if a `professionals` record already exists for the current `userId`, it simply returns the existing professional data, preventing duplicate entries and allowing users to re-submit the form without error.

The request body is validated against the `onboardingSchema`, which defines the required fields for a professional profile. This includes `name`, `profession`, `phone`, `sessionDuration` (an integer up to 480 minutes), `sessionPrice` (a non-negative integer), `serviceType` (an enum of `"in_person"`, `"online"`, or `"both"`), optional `city` and `state`, and an array of `availability` slots. Each availability slot requires a `dayOfWeek` (0-6) and `startTime`/`endTime` in `HH:MM` format.

A unique `slug` is generated for the professional's public profile URL. The `toSlug` function converts the professional's `name` into a URL-friendly format. If `toSlug` results in an empty string (e.g., from a name consisting only of diacritics), "user" is used as the base for slug generation. The `generateUniqueSlug` function then ensures this slug is unique within the `professionals` table, appending a numeric suffix (e.g., `john-doe-2`) if the base slug is already taken or if it conflicts with any of the `RESERVED_SLUGS` (e.g., "api", "auth", "dashboard", "login", "register", "onboarding", "explore", "c", "p", "privacidade", "termos", "admin", "monitoring", "sitemap", "robots", "opengraph-image").

The validated data is then inserted into the `professionals` table, which has 32 columns, including `userId`, `name`, `slug`, `phone`, `profession`, `bio`, `sessionDuration`, `sessionPrice`, `serviceType`, `city`, and `state`. Concurrently, if `availability` data is provided, it is inserted into the `availability` table, linking each entry to the newly created `professionalId`. The `availability` table stores `dayOfWeek`, `startTime`, and `endTime` for each professional.

Finally, the user's Supabase metadata is updated to set their `type` to `"professional"` and their `name`. In production, a welcome email is sent to the professional using `sendProfessionalWelcomeEmail`, providing them with their profile `slug`. This email sending is a fire-and-forget operation, with errors logged but not blocking the main request.

## Design decisions

Several key design decisions shape this professional onboarding flow:

*   **Separation of Concerns**: The registration (`/api/auth/register`) and onboarding (`/api/onboarding`) processes are distinct API routes. This separation allows for a multi-stage user journey, where basic authentication is handled first, followed by the collection of professional-specific data. It also enables different user types (e.g., clients) to register without needing to complete the professional onboarding.
*   **Environment-Specific Supabase Authentication**: The conditional use of `supabase.auth.signUp()` in production versus `admin.createUser()` in development for `/api/auth/register` is a pragmatic choice. It prioritizes a realistic email verification flow for production users while offering a streamlined, verification-skipped experience for developers, accelerating local testing.
*   **Robust Slug Generation**: The `toSlug` and `generateUniqueSlug` functions, coupled with the `RESERVED_SLUGS` set, ensure that every professional receives a unique, clean, and non-conflicting URL slug. This prevents issues where a professional's name might accidentally shadow a system route or another professional's profile.
*   **Rate Limiting for Abuse Prevention**: Implementing `@upstash/ratelimit` on both `/api/auth/register` and `/api/onboarding` is a critical security and stability measure. It protects against automated attacks like spam registrations or excessive profile creation attempts, ensuring fair resource usage. The specific limits (5 attempts/hour for register, 3 attempts/hour for onboarding) are tailored to the expected frequency of these actions.
*   **Idempotency in Onboarding**: The check for an existing `professionals` record based on `userId` in `/api/onboarding` makes the endpoint idempotent. This means a user can safely resubmit the onboarding form without creating duplicate professional profiles, which improves the user experience and simplifies client-side logic.
*   **Strict Type Validation in Auth Callback**: The `VALID_TYPES` set in `/auth/callback` is a direct security measure. By explicitly whitelisting accepted values for the `type` query parameter, the system prevents an attacker from injecting arbitrary data into the user's Supabase metadata via a crafted OAuth callback URL.
*   **Smart-Linking for Clients**: The logic in `/auth/callback` to update `clients.userId` for existing client records with a matching email and a `null` `userId` is a thoughtful feature. It allows professionals to add clients by email, and if those clients later register an account, their existing records are automatically linked, providing a more unified experience.

## Potential improvements

*   **`professionals.email` Nullability**: The `professionals` table includes an `email` column that is nullable. This onboarding flow does not populate `professionals.email`, as the user's primary email is managed by Supabase authentication. While `professionals.userId` is unique and non-nullable, it might be beneficial to ensure `professionals.email` is also non-nullable and unique, mirroring the `userId`'s role as a primary identifier and ensuring consistency with the registration process. If a professional's email can change in Supabase, a mechanism to update this column in `professionals` would also be needed.
*   **Optimizing `generateUniqueSlug`**: The `generateUniqueSlug` function currently uses a `while(true)` loop with individual database queries to find a unique slug. For extremely high concurrency or a large number of name collisions, this could lead to multiple sequential database calls. A more optimized approach might involve a single Drizzle query that attempts to find the first available suffix by checking for multiple potential slugs (e.g., `base`, `base-2`, `base-3`) in one go, or by using a database-level unique constraint with a retry mechanism.
*   **Welcome Email Reliability**: The `sendProfessionalWelcomeEmail` call in `/api/onboarding` is a fire-and-forget operation with a `.catch()` block that only logs a warning. For critical communications like welcome emails, a more robust error handling strategy could be considered. This might involve integrating with a dedicated queueing system (e.g., a message broker) for email delivery, which could handle retries, dead-letter queues, and provide better observability into delivery failures.
*   **`serviceType` Default Consistency**: The `onboardingSchema` defines `serviceType` as optional, and the `professionals` table has a default value. The `POST` handler in `/api/onboarding` explicitly sets `serviceType: body.serviceType ?? "both"`. While consistent, making `serviceType` a required field in the `onboardingSchema` would simplify the handler by removing the nullish coalescing operator and ensuring the client always provides this value, potentially leading to a more explicit user experience during onboarding.
