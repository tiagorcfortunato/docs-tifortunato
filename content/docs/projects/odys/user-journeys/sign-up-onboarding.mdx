# Professional Onboarding

The professional onboarding process is a critical user journey, guiding new service providers from initial registration to a fully configured profile ready to accept clients. This flow is designed to be intuitive while gathering essential information and ensuring the integrity of the platform. It involves several distinct steps, leveraging Supabase for authentication and Drizzle ORM for database interactions, all orchestrated through Next.js API routes.

## Overview

The journey for a new professional begins with account registration, typically involving an email and password. Once authenticated, the user proceeds to a dedicated onboarding flow where they provide details about their services, pricing, and availability. This two-stage approach separates core authentication from business-specific profile setup, allowing for a cleaner user experience and more focused data collection.

The primary database tables involved in this process are `professionals` and `availability`. The `professionals` table, with its 32 columns, stores the core identity and business details of each service provider, including their `name`, `profession`, `phone`, `sessionDuration`, `sessionPrice`, and location details like `city` and `state`. A unique `slug` is generated for each professional, forming the basis of their public profile URL. The `availability` table, comprising 5 columns, captures the professional's working hours across different days of the week, linking back to the `professionals` table via `professionalId`.

The process is managed through two key API routes: `/api/auth/register` handles the initial account creation, while `/api/onboarding` manages the subsequent profile setup. An authentication callback route, `/auth/callback`, plays a crucial role in verifying email addresses and linking user accounts. To prevent abuse and ensure system stability, both registration and onboarding endpoints are protected by rate limits, configured via Upstash Redis.

## Registration Flow

The initial step for any new professional is to create an account, handled by the `POST` endpoint at `/api/auth/register`. This route is designed to be the gateway for new users, collecting basic credentials and initiating the authentication process.

Upon receiving a request, the system first applies a rate limit using `getRegisterLimiter()`, which permits up to 5 registration attempts per hour per IP address. This helps mitigate brute-force attacks and spam registrations. The incoming data is then validated against the `registerSchema`, a Zod schema that enforces requirements for `email` (must be a valid email format), `password` (minimum 8 characters), and optionally `name` and `type`.

A key design decision here is the conditional logic for user creation based on the environment. In `production`, the `supabase.auth.signUp()` method is used. This approach automatically triggers Supabase's email verification flow, sending a confirmation email to the user. The `requiresEmailConfirmation` flag in the response indicates whether a session was immediately established or if email verification is pending. Conversely, in `development` environments, an `adminClient` (using the Supabase service role key) is employed to call `admin.createUser()` with `email_confirm: true`. This bypasses the email verification step, allowing developers to rapidly test the onboarding flow without needing to check inboxes. This trade-off prioritizes development speed over mimicking the full production authentication flow.

If any errors occur during validation or user creation, appropriate HTTP status codes (400 for invalid data, 429 for rate limiting, 500 for internal errors) and descriptive messages are returned.

## Authentication Callback

After a user clicks the verification link in their email (sent by Supabase during `signUp()`), they are redirected to the `/auth/callback` route. This route is crucial for completing the authentication handshake with Supabase and performing post-verification actions.

The route extracts a `code` and an optional `type` parameter from the URL's search parameters. The `type` parameter is carefully parsed using `parseType` against a `VALID_TYPES` set (`"professional"`, `"client"`, `"recovery"`) to prevent arbitrary data injection into user metadata, a critical security measure.

The core of this route is `supabase.auth.exchangeCodeForSession(code)`, which exchanges the verification code for an authenticated user session. If successful, the user's `type` metadata in Supabase is updated to `"professional"` or `"client"` if specified in the callback URL. This ensures the user's role is correctly reflected in their authentication profile.

A notable feature of this callback is "smart-linking" for clients. If the user's `type` is `"client"` and they have a verified `email`, the system attempts to link their new `userId` to any existing entries in the `clients` table that match their `email` but currently have a `null` `userId`. This is a convenience feature, allowing users who might have been added as clients by a professional to seamlessly claim their existing client profile upon registration. Finally, the user is redirected to `/auth/redirect` to complete the login process.

## Professional Onboarding

Once a professional has registered and verified their email, they proceed to the onboarding stage, managed by the `POST` endpoint at `/api/onboarding`. This route is responsible for collecting detailed professional information and populating the `professionals` and `availability` tables.

Similar to registration, this route is protected by `getOnboardingLimiter()`, allowing 3 attempts per hour per IP. The first step within the route is to authenticate the user using `getUser()`. If no authenticated user is found, an `unauthorized()` response is returned. The system then checks if a `professional` record already exists for the current `userId`. This check makes the onboarding process idempotent; if a professional has already completed onboarding, their existing data is simply returned, preventing duplicate entries and simplifying client-side retry logic.

The incoming request body is validated against the `onboardingSchema`, which is significantly more detailed than the registration schema. It requires `name`, `profession`, `phone`, `sessionDuration`, `sessionPrice`, and `availability` details. Optional fields include `bio`, `serviceType`, `city`, and `state`. The `availability` array is particularly important, requiring at least one entry with `dayOfWeek`, `startTime`, and `endTime`.

A unique `slug` is generated for the professional's public profile URL using `generateUniqueSlug(toSlug(body.name))`. The `toSlug` function converts the professional's name into a URL-friendly format. `generateUniqueSlug` then checks for collisions with existing slugs in the `professionals` table and also against a `RESERVED_SLUGS` set (e.g., `"api"`, `"auth"`, `"dashboard"`) to prevent conflicts with application routes. If a collision occurs, a numeric suffix is appended (e.g., `john-doe-2`).

After successful validation and slug generation, a new record is inserted into the `professionals` table with all the provided details. Concurrently, if `availability` data is present, multiple records are inserted into the `availability` table, each linked to the new professional's `id`. Finally, the user's Supabase metadata is updated via `supabase.auth.updateUser()` to set their `type` to `"professional"` and update their `name`.

As a final step, in `production` environments, a welcome email is sent to the professional using `sendProfessionalWelcomeEmail()`. This is a fire-and-forget operation, meaning any failure in sending the email does not block the onboarding process, but a warning is logged.

## Design Decisions

### Separation of Registration and Onboarding
The decision to separate user registration (`/api/auth/register`) from professional profile onboarding (`/api/onboarding`) allows for a clear distinction between establishing an identity and configuring a service offering. This modularity simplifies the user interface, reduces the complexity of each API endpoint, and allows for different validation rules and rate limits to be applied to each stage. For instance, a user might register but decide not to complete onboarding immediately, or they might be a client who never needs to onboard as a professional.

### Conditional Supabase Authentication in Development
The use of `admin.createUser` with `email_confirm: true` in `development` environments for `/api/auth/register` is a pragmatic choice. It significantly accelerates the development cycle by allowing developers to bypass the email verification step, which can be cumbersome during rapid iteration. The trade-off is that the development environment doesn't perfectly mirror the production authentication flow, but for the purpose of testing the subsequent onboarding steps, this is an acceptable compromise.

### Robust Slug Generation
The `generateUniqueSlug` function, coupled with `RESERVED_SLUGS`, demonstrates a forward-thinking approach to URL management. By ensuring slugs are unique and do not conflict with existing application routes, the system prevents broken links and provides clean, predictable URLs for professional profiles. The iterative suffixing (`-2`, `-3`, etc.) is a common and effective strategy for handling name collisions, prioritizing user-friendly slugs while maintaining uniqueness.

### Idempotency in Onboarding
The check for an existing professional record at the beginning of the `/api/onboarding` `POST` handler makes the operation idempotent. This means that if a client-side error occurs or a user accidentally submits the form multiple times, the system will not create duplicate professional profiles. Instead, it simply returns the existing professional data, which simplifies error recovery and retry logic on the frontend.

### Smart-Linking Clients
The "smart-linking" logic in `src/app/auth/callback/route.ts` where a newly verified user's `userId` is linked to existing `clients` records with a matching `email` (and `null` `userId`) is a user-centric design. It improves the experience for clients who might have been added to the system by a professional before they created their own account. This avoids data duplication and ensures a unified client profile, though it relies on email addresses remaining consistent.

## Potential Improvements

1.  **`professionals.email` Column Redundancy**: The `professionals` table does not include an `email` column in its current insertion logic. However, the `userId` column is also present and unique, and the `getUser()` function (used in `/api/onboarding/route.ts`) relies on Supabase for user authentication, which inherently provides an email. If the `professionals.email` column is intended to store the *primary* email associated with the professional's account, it could be made non-nullable and potentially derived from the Supabase user's email, or its purpose clarified. If it's for an *alternative* contact email, its nullable status is appropriate, but this distinction could be documented.

2.  **Foreign Key Constraint for `professionals.userId`**: The `professionals.userId` column is of type `text` and marked as `unique`, but it does not have a formal foreign key constraint to a `users` table within the Drizzle schema. While it implicitly refers to a Supabase user ID, adding a local `users` table (if one were to exist for internal user management) and establishing a foreign key relationship would enforce referential integrity at the database level, preventing orphaned professional records if a Supabase user were to be deleted.

3.  **`availability` Time Data Type**: In the `availability` table, `startTime` and `endTime` are stored as `text` with a `^\d{2}:\d{2}$` regex validation. While functional, using a dedicated `time` or `interval` data type (if supported by the underlying database, e.g., PostgreSQL's `TIME WITHOUT TIME ZONE`) would offer more robust time-based querying, sorting, and calculation capabilities directly within the database, potentially simplifying application-level logic for scheduling and conflict detection.
