# Professional Onboarding

The professional sign-up and onboarding flow is a critical user journey, guiding new professionals from initial account creation to a fully configured profile ready to accept clients. This process involves several distinct steps, each handled by dedicated API routes and database interactions, ensuring data integrity and a smooth user experience. The journey begins with user registration, proceeds through email verification, and culminates in the collection of detailed professional information and availability.

## Overview

The end-to-end flow for a professional joining the platform is orchestrated across three primary API endpoints: `/api/auth/register`, `/src/app/auth/callback`, and `/api/onboarding`. Initially, a user creates an account via the registration endpoint. Upon successful registration, Supabase handles email verification, redirecting the user to the authentication callback. This callback verifies the user's email and performs crucial metadata updates. Finally, the user proceeds to the onboarding endpoint, where they provide detailed information about their services, pricing, and availability, establishing their public professional profile. Throughout this process, rate limiting is applied to prevent abuse, and database interactions are carefully managed using Drizzle ORM to persist professional and availability data.

## Registration

The initial step for any new user, including professionals, is account creation, managed by the `/api/auth/register` API route. This route is designed to handle `POST` requests, accepting user credentials and basic profile information.

The incoming request body is validated against the `registerSchema`, which mandates an `email` and a `password` (minimum 8 characters). Optionally, a `name` (minimum 2 characters) and `type` (either "client" or "professional") can be provided. This schema ensures that only well-formed data proceeds to user creation.

Before processing the registration, the system employs a rate limiter, `getRegisterLimiter`, which permits a maximum of 5 registration attempts per hour from a single IP address. This measure helps mitigate brute-force attacks and spam registrations. If the limit is exceeded, a `429 Too Many Requests` status is returned.

A key design choice in this route is the conditional logic for user creation based on the `NODE_ENV` environment variable. In a `production` environment, the `supabase.auth.signUp` method is used. This approach leverages Supabase's built-in email verification flow, automatically sending a confirmation email to the user. The `options.data` field is used to store the `name` and `type` in the user's metadata. If `signUp` does not return a session, it indicates that email confirmation is required, which is communicated back to the client.

Conversely, in `development` environments, an `adminClient` (initialized with the Supabase service role key) is used to call `admin.createUser`. This method allows for immediate user creation with `email_confirm: true`, bypassing the email verification step. This significantly accelerates the development and testing cycle by allowing developers to quickly create confirmed users without needing to interact with email inboxes. This trade-off prioritizes developer convenience over mimicking the full production flow locally.

Upon successful user creation, the route returns a `200 OK` response, indicating success and whether email confirmation is required. Any validation errors or Supabase errors result in a `400 Bad Request` response, while unexpected server issues trigger a `500 Internal Server Error`.

## Authentication Callback

Following email verification or password recovery, Supabase redirects the user to the `/src/app/auth/callback` route. This `GET` endpoint is crucial for completing the authentication handshake and performing post-verification actions.

The route extracts a `code` and an optional `type` parameter from the URL's search parameters. The `type` parameter is carefully parsed using the `parseType` function, which validates it against a `VALID_TYPES` set (`"professional"`, `"client"`, `"recovery"`). This strict validation is a security measure to prevent an attacker from injecting arbitrary values into the user's metadata via a crafted callback URL.

The `code` is then exchanged for a user session using `supabase.auth.exchangeCodeForSession`. If this exchange is successful:
*   If the `type` is `"recovery"`, the user is redirected to the `/reset-password` page to set a new password.
*   If the `type` is `"professional"` or `"client"`, the user's metadata in Supabase is updated to reflect their designated role. This ensures that the user's profile accurately reflects their intended use of the platform.
*   A "smart-linking" mechanism is triggered if the user is a `"client"` and has a verified email. The system attempts to link the newly authenticated `user.id` to any existing entries in the `clients` table that have the same `email` but a `null` `userId`. This is particularly useful for clients who might have been added to the system by a professional before creating their own account.

Finally, the user is redirected to `/auth/redirect` for further application-level routing or to `/login?error=auth` if the session exchange fails. The `origin` for redirects is dynamically constructed using `x-forwarded-host` and `x-forwarded-proto` headers to ensure correct redirection in various deployment environments, such as Vercel.

## Professional Onboarding

Once a user has registered and verified their email, a professional user proceeds to the `/api/onboarding` route to complete their profile. This `POST` endpoint is where the detailed information required for a professional's public profile is collected and persisted.

Similar to registration, the `getOnboardingLimiter` is applied, allowing only 3 onboarding attempts per hour per IP address to prevent abuse.

The route first checks if a professional profile already exists for the authenticated user's `userId`. This makes the onboarding process idempotent; if a professional has already completed onboarding, their existing profile is returned, preventing duplicate entries and allowing for safe retries.

The incoming request body is validated against the `onboardingSchema`, which requires:
*   `name`: The professional's full name.
*   `profession`: Their area of expertise.
*   `phone`: Contact phone number (minimum 10 characters).
*   `sessionDuration`: The standard duration of a session in minutes, with a maximum of 480.
*   `sessionPrice`: The price of a session (non-negative integer).
*   `availability`: An array of objects defining their weekly schedule, including `dayOfWeek`, `startTime`, and `endTime`. This array must contain at least one entry.
*   Optional fields include `bio`, `serviceType` (in-person, online, or both; defaults to `both`), `city`, and `state`.

A crucial part of the onboarding process is the generation of a unique `slug` for the professional's public profile URL. The `toSlug` function converts the professional's `name` into a URL-friendly format. The `generateUniqueSlug` function then ensures this slug is unique within the `professionals` table. It also checks against a `RESERVED_SLUGS` set (e.g., "api", "auth", "dashboard") to prevent collisions with application routes. If a collision occurs or the base slug is reserved, a numeric suffix is appended (e.g., "john-doe-2") until a unique slug is found.

After validation and slug generation, the professional's data is inserted into the `professionals` table. If availability data is provided, it is then inserted into the `availability` table, linked to the new professional's `id`.

Finally, the user's metadata in Supabase is updated to set their `type` to "professional" and their `name`. In `production` environments, a welcome email is sent to the professional using `sendProfessionalWelcomeEmail`. This email is sent asynchronously, and any failures are logged as warnings, ensuring the onboarding flow itself is not blocked by email delivery issues.

The route returns a `200 OK` response with the newly created professional's data on success, or appropriate error responses for invalid data (`400 Bad Request`), unauthorized access (`401 Unauthorized`), or server errors (`500 Internal Server Error`).

## Design Decisions

The design of the professional sign-up and onboarding flow reflects several deliberate choices aimed at balancing user experience, security, and development efficiency:

*   **Separation of Concerns (Registration vs. Onboarding)**: The decision to split user account creation (`/api/auth/register`) from professional profile setup (`/api/onboarding`) allows for a staged onboarding process. This means users can create an account without immediately committing to being a professional, and the system can support different user types (clients vs. professionals) with distinct data requirements. It also allows for a simpler initial registration form, reducing friction for new users.
*   **Conditional Supabase User Creation**: Using `supabase.auth.signUp` in production and `admin.createUser` in development for `/api/auth/register` is a pragmatic trade-off. It ensures that the production environment benefits from Supabase's secure and automated email verification flow, while developers can bypass this step locally for faster iteration, acknowledging the different security postures required for each environment.
*   **Strict Type Validation in Auth Callback**: The `VALID_TYPES` set in `/src/app/auth/callback` is a direct security enhancement. By explicitly defining and validating accepted `type` values, the system prevents malicious actors from injecting arbitrary data into user metadata through URL manipulation, which could lead to privilege escalation or other vulnerabilities.
*   **Idempotent Onboarding**: The check for an existing professional profile at the beginning of the `/api/onboarding` `POST` request makes the operation idempotent. This is crucial for client-side resilience, allowing users or front-end applications to safely retry onboarding requests without creating duplicate professional entries in the database.
*   **Automated Unique Slug Generation**: The `generateUniqueSlug` function, coupled with the `RESERVED_SLUGS` list, ensures that every professional gets a unique, human-readable URL for their public profile. This prevents URL collisions with existing application routes and other professionals, contributing to a clean and predictable URL structure.
*   **Rate Limiting for Abuse Prevention**: Implementing `@upstash/ratelimit` for both registration and onboarding (`getRegisterLimiter`, `getOnboardingLimiter`) is a fundamental security and stability measure. It protects against automated attacks like spam registrations, brute-force attempts, and resource exhaustion, ensuring fair usage of the API.
*   **Smart-Linking Clients**: The logic in `/src/app/auth/callback` to link existing `clients` records to a newly verified `userId` (if `clients.userId` is `null` and `clients.email` matches `user.email`) is a user experience enhancement. It allows professionals to add clients by email even before those clients have created an account, and then automatically associates the client record when they eventually sign up with the same email.

## Potential Improvements

1.  **`professionals.email` Column Redundancy**: The `professionals` table includes an `email` column, which is nullable. However, the `userId` column is also present and unique, and `user.email` is guaranteed to exist for an authenticated user during onboarding. If the professional's contact email is always the same as their login email, this column could be removed, and the email derived from the associated Supabase user via `userId`. If it's intended for a *different* contact email, the purpose should be clarified.
2.  **`professionals.userId` Type Consistency**: The `userId` column in the `professionals` table is defined as `text`, while the `id` column is `uuid`. Supabase user IDs are typically UUIDs. Aligning `userId` to `uuid` would improve type consistency and could potentially allow for database-level foreign key constraints if Supabase's `auth.users` table were directly accessible within the same Drizzle schema, enhancing data integrity.
3.  **Dynamic `RESERVED_SLUGS` Management**: The `RESERVED_SLUGS` set in `src/app/api/onboarding/route.ts` is hardcoded. As the application grows, this list might need frequent updates to prevent new route collisions. Consider externalizing this list into a configuration file or a database table, allowing for more flexible and dynamic management without requiring code changes and redeployments for every new reserved path.
4.  **Welcome Email Delivery Assurance**: The `sendProfessionalWelcomeEmail` call in `src/app/api/onboarding/route.ts` uses a `.catch` block that only logs a warning. While fire-and-forget is acceptable for non-critical notifications, for a welcome email, a more robust delivery mechanism might be beneficial. This could involve integrating with a dedicated queueing system or a transactional email service that offers retry logic and delivery status tracking, ensuring that welcome emails are eventually sent even if the initial attempt fails.
