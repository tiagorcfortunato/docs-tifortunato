# Professional Onboarding

The professional onboarding journey is a critical sequence of steps that allows service providers to register with Odys and configure their initial profile, making them discoverable and ready to accept appointments. This process involves user authentication, data validation, database persistence, and system-level configurations like slug generation and email notifications. Understanding this flow is key to grasping how new professionals are integrated into the platform.

## Overview

The professional onboarding process is orchestrated across three primary API routes and their associated logic:

1.  **`/api/auth/register`**: Handles the initial user registration, creating an account in Supabase.
2.  **`/auth/callback`**: Processes the email verification link from Supabase, authenticating the user and performing initial data linking.
3.  **`/api/onboarding`**: Captures detailed professional profile information and availability, populating the `professionals` and `availability` tables.

This modular approach separates authentication concerns from profile creation, allowing for a clear progression through the user journey. The system relies heavily on Supabase for authentication and Drizzle ORM for database interactions with a PostgreSQL backend, which currently manages 11 distinct tables, including `professionals` and `availability`.

## Registration Flow

The journey begins with a `POST` request to the `/api/auth/register` endpoint. This route is responsible for creating a new user account within the Supabase authentication system.

The incoming request body is rigorously validated against the `registerSchema`, a Zod object that mandates an `email` and a `password` of at least 8 characters, aligning with Supabase's default password policy. Optionally, a `name` and `type` (either `client` or `professional`) can be provided, which are stored in the user's metadata.

To prevent abuse, the endpoint employs rate limiting via `getRegisterLimiter`, allowing only 5 registration attempts per IP address per hour. If this limit is exceeded, a `429 Too Many Requests` response is returned.

A notable design choice here is the conditional logic for user creation based on the `NODE_ENV` environment variable. In `production`, the `supabase.auth.signUp()` method is used. This triggers Supabase's built-in email verification flow, which is essential for confirming user identity before granting full access. If `signUp()` does not return a session, it indicates that email confirmation is required. Conversely, in `development` environments, the `getAdminClient().auth.admin.createUser()` method is utilized with `email_confirm: true`. This bypasses the email verification step, allowing developers to rapidly test the onboarding flow without needing to check inboxes. The `_adminClient` itself is lazily initialized to ensure that environment variables like `SUPABASE_SERVICE_ROLE_KEY` are only accessed when needed, which is particularly useful in build environments where secrets might be stripped.

Upon successful registration, the API returns a `200 OK` response, indicating whether email confirmation is required, which guides the frontend's subsequent user experience.

## Authentication Callback and Smart-Linking

After a user registers and clicks the verification link sent to their email, they are redirected to the `/auth/callback` route. This route is crucial for completing the authentication process and performing initial data synchronization.

The callback extracts a `code` and an optional `type` parameter from the URL's search parameters. The `type` parameter is carefully parsed using `parseType` against a `VALID_TYPES` set (`professional`, `client`, `recovery`) to prevent arbitrary data injection into user metadata, a concrete security measure.

The core function of this route is to exchange the `code` for a user session using `supabase.auth.exchangeCodeForSession()`. If successful, the user is authenticated. For password recovery flows (`type === "recovery"`), the user is redirected to a dedicated password reset page.

Crucially, if the `type` is `professional` or `client`, the user's Supabase metadata is updated with this role. This ensures that the user's role is consistently reflected in their authentication profile.

A "smart-linking" mechanism is also implemented for clients. If a user with `type === "client"` authenticates and their email is known, the system attempts to link their new `userId` to any existing `clients` records that share the same `email` but currently have a `NULL` `userId`. This is achieved by an `UPDATE` statement on the `clients` table, setting `userId` where `isNull(clients.userId)` and `eq(clients.email, user.email)`. This allows clients who might have interacted with the platform (e.g., through a booking made by a professional) to seamlessly claim their existing client profile upon registration.

Finally, the user is redirected to `/auth/redirect` or `/login?error=auth` if the authentication fails.

## Professional Onboarding Data Capture

Once a professional has registered and verified their email, they proceed to the `/api/onboarding` endpoint to complete their profile. This route handles a `POST` request containing detailed information about the professional.

Similar to registration, this endpoint is protected by rate limiting, allowing only 3 onboarding attempts per IP address per hour via `getOnboardingLimiter`. It also requires an authenticated user, verified by `getUser()`, returning `401 Unauthorized` if no user session is found.

The route first performs an idempotency check: if a `professionals` record already exists for the authenticated `userId`, it simply returns the existing professional data, preventing duplicate entries and allowing for safe re-submission.

The incoming data is validated against `onboardingSchema`, which expects fields such as `name`, `profession`, `phone`, `bio`, `sessionDuration`, `sessionPrice`, `serviceType`, `city`, `state`, and an array of `availability` slots. The `availability` array requires at least one entry, each specifying a `dayOfWeek`, `startTime`, and `endTime`.

A key feature of this route is the generation of a unique `slug` for the professional's public profile URL. The `toSlug` function converts the professional's `name` into a URL-friendly format. The `generateUniqueSlug` function then checks for uniqueness against existing `professionals.slug` values and a `RESERVED_SLUGS` set (e.g., `api`, `auth`, `dashboard`). If a conflict or a reserved slug is encountered, it appends a numeric suffix (e.g., `john-doe-2`) until a unique slug is found.

After validation and slug generation, a new record is inserted into the `professionals` table with the provided details. If `availability` data is present, corresponding entries are also inserted into the `availability` table, linking them to the new professional via `professionalId`.

Finally, the user's Supabase metadata is updated again, explicitly setting their `type` to `professional` and updating their `name`. In `production` environments, a welcome email is sent to the professional using `sendProfessionalWelcomeEmail`, providing them with their public profile slug. This email sending is fire-and-forget, with basic error logging to avoid blocking the onboarding flow.

## Design Decisions

The design of the professional onboarding flow reflects several deliberate choices aimed at security, user experience, and maintainability:

*   **Separation of Concerns**: The registration, email verification callback, and detailed onboarding steps are handled by distinct API routes. This modularity simplifies each component's logic and allows for independent development and testing. For instance, `/api/auth/register` focuses solely on user account creation, while `/api/onboarding` handles the application-specific profile data.
*   **Environment-Specific Authentication**: The use of `process.env.NODE_ENV` to conditionally use `supabase.auth.signUp()` in production and `admin.createUser()` in development is a pragmatic trade-off. It prioritizes a secure, verified user base in production while enabling rapid iteration and testing in development by bypassing email verification.
*   **Robust Input Validation**: Zod schemas (`registerSchema`, `onboardingSchema`) are used extensively to validate all incoming API data. This prevents malformed data from reaching the database and provides clear, actionable error messages to the client, improving the developer and user experience.
*   **Rate Limiting**: Implementing `getRegisterLimiter` and `getOnboardingLimiter` with specific limits (5 attempts/hour for register, 3 attempts/hour for onboarding) is a crucial security measure to mitigate brute-force attacks and resource exhaustion.
*   **Unique Slug Generation**: The `generateUniqueSlug` function, with its `RESERVED_SLUGS` list and suffixing logic, ensures that every professional has a unique, human-readable URL for their public profile. This prevents URL collisions and maintains a clean public-facing structure.
*   **Idempotency for Onboarding**: The `/api/onboarding` route checks for an existing professional record before attempting an insert. This makes the API idempotent, meaning multiple identical requests will have the same effect as a single request, which is beneficial for client-side retry logic and preventing duplicate data.
*   **Smart-Linking for Clients**: The logic in `/auth/callback` to link an authenticated user's `userId` to pre-existing `clients` records (where `clients.userId` is `NULL` but `clients.email` matches) is a user experience enhancement. It allows clients who might have been added by a professional to seamlessly claim their profile when they eventually sign up.

## Potential Improvements

1.  **Centralize `RESERVED_SLUGS` Management**: The `RESERVED_SLUGS` set in `src/app/api/onboarding/route.ts` is hardcoded. As the application grows, maintaining this list manually could become cumbersome and prone to errors if new top-level routes are added. Consider dynamically generating this list from the Next.js page/API route structure or defining it in a shared configuration file that can be easily updated and referenced across the codebase.
2.  **Enhanced Welcome Email Error Handling**: The `sendProfessionalWelcomeEmail` call in `src/app/api/onboarding/route.ts` uses a `.catch((err) => console.warn(...))` block. While it prevents blocking the main flow, `console.warn` is not ideal for production error monitoring. Implementing a more robust error reporting mechanism (e.g., sending errors to a dedicated logging service like Sentry or integrating with a message queue for retries) would provide better visibility into email delivery failures and improve system reliability.
3.  **Refine `clients.userId` Nullability and Synchronization**: The `userId` column in the `clients` table is nullable, enabling the "smart-linking" feature in `src/app/auth/callback/route.ts`. While useful, this design means a `clients` record can exist without a linked user account. This could lead to scenarios where client data exists but is not directly manageable by an authenticated user if the smart-linking fails or is never triggered. A potential improvement could involve a background job to periodically identify and flag unlinked client records, or a more explicit UI flow for clients to claim their profiles. Additionally, consider if `user_metadata.type` is strictly necessary if the `professionals` table already serves as the authoritative source for a user's professional status, to avoid potential data divergence.
