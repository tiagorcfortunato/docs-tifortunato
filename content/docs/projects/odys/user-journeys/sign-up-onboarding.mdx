# Professional Onboarding

The professional sign-up and onboarding flow is a critical journey for Odys, guiding new service providers from initial registration to a fully configured profile ready to accept clients. This process is designed to progressively gather necessary information, ensuring a smooth experience while establishing the foundational data for a professional's presence on the platform. It involves several API routes and database interactions, carefully orchestrated to manage user authentication, profile creation, and service availability.

## Overview

The journey for a new professional begins with account registration, typically involving an email and password. Upon successful registration and email verification, the professional proceeds to an onboarding flow where they provide detailed information about their services, pricing, and availability. This two-stage approach separates basic account creation from comprehensive profile setup, allowing for a focused user experience at each step.

The core components of this flow include:

*   **`/api/auth/register`**: Handles the initial user account creation, integrating with Supabase for authentication.
*   **`/auth/callback`**: Processes the callback from Supabase after email verification or magic link authentication, linking the user's identity to their profile.
*   **`/api/onboarding`**: Manages the creation of the professional's detailed profile, including service specifics and availability.

Throughout these steps, rate limiting is applied to prevent abuse, and database schemas are designed to capture the rich data required for professional profiles and their associated schedules.

## Registration

The `/api/auth/register` API route is the entry point for new users to create an account. It accepts `POST` requests and is protected by a rate limit, allowing only `5` registration attempts per `1 h` from a single IP address, as defined by `getRegisterLimiter` in `src/lib/ratelimit.ts`. This helps mitigate brute-force attacks or spam registrations.

Upon receiving a request, the route first validates the incoming data against the `registerSchema`. This schema, defined using `zod`, enforces that an `email` is a valid email format, a `password` is at least `8` characters long (matching Supabase's default minimum), and `name` is at least `2` characters. An optional `type` field, which can be either `"client"` or `"professional"`, allows for initial role assignment.

A key design choice here differentiates between development and production environments:

*   In **production**, the route uses `supabase.auth.signUp()`. This method triggers Supabase's built-in email verification flow, sending a confirmation email to the user. The `requiresEmailConfirmation` flag in the response indicates whether a session was immediately created or if email verification is pending.
*   In **development**, to accelerate testing cycles, the route uses an `adminClient` (initialized with `SUPABASE_SERVICE_ROLE_KEY`). This client's `auth.admin.createUser()` method is called with `email_confirm: true`, which bypasses the email verification step and immediately marks the user's email as confirmed. This trade-off prioritizes developer convenience in non-production environments.

If any errors occur during validation or user creation, appropriate `400` or `500` status responses are returned, providing feedback to the client.

## Authentication Callback

After a user completes an action like email verification or a magic link login via Supabase, they are redirected to the `/auth/callback` route. This `GET` route is crucial for exchanging the `code` provided by Supabase for an authenticated session.

The route extracts a `code` and an optional `type` from the URL's search parameters. The `type` parameter is carefully parsed using `parseType` and validated against a `VALID_TYPES` set (`"professional"`, `"client"`, `"recovery"`). This strict validation is a security measure to prevent an attacker from injecting arbitrary data into the user's metadata via a crafted callback URL.

Once the session is established using `supabase.auth.exchangeCodeForSession(code)`, the route performs several actions:

*   **Password Recovery**: If the `type` is `"recovery"`, the user is redirected to `/reset-password`.
*   **User Metadata Update**: If `type` is `"professional"` or `"client"`, the user's metadata in Supabase is updated to reflect their role.
*   **Client Smart-Linking**: For users registering as a `"client"`, a "smart-linking" mechanism is triggered. This logic attempts to associate the newly verified `user.id` with any existing records in the `clients` table that have the same `email` but a `null` `userId`. This is particularly useful if a professional created a client record for someone who later decides to sign up for the platform themselves, allowing their existing data to be linked.

Finally, the user is redirected to `/auth/redirect` or `/login?error=auth` depending on the outcome.

## Professional Onboarding

Once a user has registered and verified their email, they proceed to the `/api/onboarding` route to complete their professional profile. This `POST` endpoint is also rate-limited by `getOnboardingLimiter`, allowing `3` attempts per `1 h` per IP address to prevent excessive submissions.

The onboarding process is designed to be idempotent: if a professional record already exists for the authenticated `user.id`, the existing record is returned, preventing duplicate entries.

The `onboardingSchema` defines the comprehensive set of data required from a professional:

*   `name`: The professional's full name.
*   `profession`: Their area of expertise.
*   `phone`: Contact phone number.
*   `bio`: An optional biography.
*   `sessionDuration`: The standard duration of a session, an integer up to `480` minutes.
*   `sessionPrice`: The price of a session, a non-negative integer.
*   `serviceType`: Whether services are `"in_person"`, `"online"`, or `"both"`.
*   `city`, `state`: Optional location details.
*   `availability`: A crucial array of objects, each specifying a `dayOfWeek` (0-6) and `startTime`/`endTime` in `HH:MM` format. This allows professionals to define their working hours.

A unique `slug` is generated for each professional based on their `name` using the `toSlug` and `generateUniqueSlug` functions. The `RESERVED_SLUGS` set ensures that generated slugs do not conflict with existing application routes like `"api"`, `"auth"`, or `"dashboard"`, appending a numeric suffix if a collision occurs.

The collected data is then inserted into the `professionals` table, creating a new record with `32` columns, including `userId`, `name`, `slug`, `phone`, `profession`, `sessionDuration`, `sessionPrice`, and default values for `plan`, `paymentType`, and `autoConfirm`. If `availability` data is provided, it is inserted into the `availability` table, linking each time slot to the new professional via `professionalId`. The `availability` table has `5` columns, including `dayOfWeek`, `startTime`, and `endTime`.

Finally, the user's Supabase metadata is updated to set their `type` to `"professional"` and their `name`. In a production environment, a welcome email is sent to the professional using `sendProfessionalWelcomeEmail`, providing them with their profile details and slug.

## Design decisions

*   **Separation of Registration and Onboarding**: The flow is split into two distinct phases: `register` for account creation and `onboarding` for profile setup. This progressive disclosure approach reduces cognitive load for new users, allowing them to first establish an identity before committing to detailed profile configuration. It also cleanly separates authentication concerns from business logic.
*   **Conditional Supabase Client Usage**: The `src/app/api/auth/register/route.ts` file uses `supabase.auth.signUp()` in production for email verification and `admin.createUser()` in development. This choice prioritizes security and proper user lifecycle management in production, while offering a streamlined, faster testing experience for developers by skipping email verification during local development.
*   **Strict Type Validation in Auth Callback**: The `VALID_TYPES` set in `src/app/auth/callback/route.ts` is a direct security measure. By explicitly whitelisting accepted `type` values, the system prevents malicious actors from injecting arbitrary data into user metadata via URL query parameters, which could lead to privilege escalation or other vulnerabilities.
*   **Automated Slug Generation**: The `toSlug` and `generateUniqueSlug` functions in `src/app/api/onboarding/route.ts` ensure that each professional has a unique, human-readable URL slug. The `RESERVED_SLUGS` set is a pragmatic approach to prevent URL conflicts with core application routes, ensuring that a professional's profile URL (`/p/[slug]`) doesn't accidentally shadow or get shadowed by a system page.
*   **Rate Limiting on Critical Endpoints**: Both `/api/auth/register` and `/api/onboarding` are protected by distinct rate limiters (`getRegisterLimiter` and `getOnboardingLimiter`). This is a fundamental defense against automated abuse, such as spam registrations or attempts to exhaust system resources during profile creation.
*   **`ON DELETE CASCADE` for Availability**: The `availability` table's `professionalId` column has a foreign key constraint with `ON DELETE CASCADE` referencing the `professionals` table. This design choice ensures data integrity: if a professional's record is deleted, all their associated availability slots are automatically removed, preventing orphaned data.

## Potential improvements

*   **`professionals.email` Nullability**: The `professionals.email` column is currently nullable, yet the `registerSchema` in `src/app/api/auth/register/route.ts` strictly requires an email for registration. This creates a slight inconsistency where a professional *always* has an email upon creation, making the column's nullability potentially unnecessary or indicative of a future feature (e.g., phone-only registration) that is not yet implemented. Re-evaluating this could simplify data models or clarify future intent.
*   **`professionals.userId` Type Consistency**: The `userId` column in the `professionals` table is defined as `text`, while Supabase user IDs are typically UUIDs. For consistency and potential future foreign key relationships with a dedicated `users` table (if one were to be introduced outside of Supabase's internal user management), changing `professionals.userId` to `uuid` type would align it better with the actual data type.
*   **Enhanced Availability Validation**: The `onboardingSchema` in `src/app/api/onboarding/route.ts` validates `startTime` and `endTime` using a regex (`/^\d{2}:\d{2}$/`) to ensure format. However, it does not enforce logical constraints such as `startTime` being chronologically before `endTime`, or prevent overlapping time slots for the same `dayOfWeek`. Adding server-side validation for these business rules would improve data quality and prevent invalid schedules from being stored.
*   **Dynamic `RESERVED_SLUGS` Management**: The `RESERVED_SLUGS` set in `src/app/api/onboarding/route.ts` is a hardcoded list. As the application grows and new top-level routes are added, this list requires manual updates. A more dynamic approach, perhaps by querying existing route definitions or maintaining the list in a centralized configuration, could reduce maintenance overhead and prevent potential slug collisions if the list is not kept up-to-date.
