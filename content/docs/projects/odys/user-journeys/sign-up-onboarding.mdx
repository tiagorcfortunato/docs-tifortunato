# Professional Onboarding

The professional onboarding process is a critical user journey within Odys, guiding new professionals from initial registration through setting up their profile and availability. This sequence of interactions ensures that professionals can quickly establish their presence and begin offering services, integrating seamlessly with the platform's core functionalities. The journey involves several distinct API routes and database interactions, carefully orchestrated to provide a smooth experience while maintaining data integrity and security.

## Overview

The end-to-end flow for a professional joining Odys begins with account registration, typically via email and password. Upon successful registration, an email verification step is initiated by Supabase. Once the email is confirmed, the user is redirected back to the application, where their user metadata is updated. The final step is the onboarding process itself, where the professional provides detailed information about their services, pricing, and availability.

This process primarily interacts with the `professionals` and `availability` tables in the database. The `professionals` table stores core profile information such as `name`, `profession`, `phone`, `bio` (which can be `null`), `sessionDuration`, `sessionPrice`, `serviceType`, and location details like `city` and `state` (which are trimmed and stored as `null` if empty). A unique `slug` is also generated for each professional, forming part of their public profile URL. The `availability` table, on the other hand, captures the professional's working hours across different days of the week, linking back to the `professionals` table via `professionalId`.

The key API routes involved are `/api/auth/register` for account creation, `/auth/callback` for handling Supabase authentication redirects (including email verification), and `/api/onboarding` for submitting the professional's detailed profile. Each of these routes incorporates rate limiting to prevent abuse and ensures data validation using Zod schemas.

## Registration

The `/api/auth/register` endpoint handles the initial creation of a user account. When a `POST` request is made to this route, the system first applies a rate limit using `getRegisterLimiter`, allowing a maximum of 5 registration attempts per hour from a single IP address. This helps mitigate brute-force attacks or spam registrations.

The incoming request body is validated against the `registerSchema`, which mandates a valid `email`, a `password` of at least 8 characters (matching Supabase's default minimum), and optionally accepts a `name` (minimum 2 characters) and `type` for the user. This schema ensures that only well-formed data proceeds to the authentication layer.

A key design choice here differentiates between production and development environments. In production, the `supabase.auth.signUp()` method is used with the anonymous Supabase client. This triggers Supabase's built-in email verification flow, which is crucial for confirming user identity. If `data.session` is not returned, it indicates that email confirmation is required, and the `requiresEmailConfirmation` flag is set accordingly.

For development, to accelerate testing cycles, an `adminClient` (initialized with the `SUPABASE_SERVICE_ROLE_KEY`) is used to call `admin.createUser()` with `email_confirm: true`. This bypasses the email verification step, allowing developers to immediately log in with newly created accounts. The `_adminClient` is lazy-initialized to avoid requiring sensitive environment variables during build processes where they might not be present. Any errors during user creation, whether in production or development, result in a `400` status with an informative error message.

## Authentication Callback

The `/auth/callback` route is a crucial intermediary, designed to process redirects from Supabase after authentication events like email verification or password recovery. It extracts a `code` and an optional `type` parameter from the URL's `searchParams`. The `type` parameter is carefully parsed using `parseType` against a `VALID_TYPES` set (`"professional"`, `"client"`, `"recovery"`) to prevent an attacker from injecting arbitrary data into user metadata, a security measure implemented after an L4 finding.

Upon receiving a valid `code`, the route exchanges it for a user session using `supabase.auth.exchangeCodeForSession()`. If successful, the user is redirected based on the `type`:
*   If `type` is `"recovery"`, the user is sent to `/reset-password`.
*   If `type` is `"professional"` or `"client"`, the user's metadata in Supabase is updated to reflect their designated role. This is important for subsequent authorization checks and UI rendering.

A "smart-linking" mechanism is also implemented for clients. If a user's email is verified and their `type` is `"client"`, the system attempts to link their new `userId` to any existing entries in the `clients` table that have the same `email` but a `NULL` `userId`. This allows pre-existing client records (perhaps created by a professional) to be associated with a newly registered user account once they verify their email. Finally, the user is redirected to `/auth/redirect` to complete the flow. If any errors occur during the session exchange, the user is redirected to `/login?error=auth`.

## Professional Onboarding

After a professional has registered and verified their email, they proceed to the `/api/onboarding` endpoint to complete their profile. This route, accessed via a `POST` request, is protected by `getOnboardingLimiter`, which restricts requests to 3 attempts per hour per IP address.

The first step within this route is to authenticate the user using `getUser()`. If no authenticated user is found, an `unauthorized()` response is returned. The system then checks for idempotency: if a `professionals` record already exists for the current `user.id`, it simply returns the existing professional data, preventing duplicate entries and allowing users to safely re-submit the form.

The request body, containing details like `name`, `profession`, `phone`, `bio`, `sessionDuration`, `sessionPrice`, `serviceType` (defaults to `"both"` if not provided), `city`, `state`, and `availability`, is validated against the `onboardingSchema`. This schema enforces constraints such as minimum string lengths, positive integers for `sessionDuration`, non-negative integers for `sessionPrice`, and a structured array for `availability` with `dayOfWeek`, `startTime`, and `endTime`.

A unique `slug` is generated from the professional's `name` using `toSlug` and `generateUniqueSlug`. This function handles diacritics, spaces, and special characters, converting them into a URL-friendly format. It also checks against a `RESERVED_SLUGS` set (e.g., `"api"`, `"auth"`, `"dashboard"`) to prevent collisions with application routes. If a slug is not unique or conflicts with a reserved name, a numeric suffix is appended (e.g., `john-doe-2`).

Once validated, the professional's data is inserted into the `professionals` table. If `availability` data is provided, it is then inserted into the `availability` table, with each entry linked to the newly created `professional.id`. Finally, the user's Supabase metadata is updated to set their `type` to `"professional"` and their `name`. In production environments, a welcome email is sent to the professional using `sendProfessionalWelcomeEmail`, though this is a fire-and-forget operation that logs warnings for failures rather than blocking the onboarding flow.

## Design decisions

The design of the professional sign-up and onboarding flow reflects several deliberate choices aimed at balancing developer experience, security, and user experience:

*   **Separation of Concerns**: The process is broken down into distinct API routes (`/api/auth/register`, `/auth/callback`, `/api/onboarding`). This modularity simplifies development, testing, and maintenance, as each route has a clear, single responsibility. Registration handles account creation, the callback manages authentication redirects, and onboarding focuses solely on professional profile setup.
*   **Conditional Supabase Client Usage**: The choice to use `supabase.auth.signUp()` with the anonymous client in production and `admin.createUser()` with the service role client in development for registration is a trade-off between security and development speed. Production benefits from Supabase's built-in email verification flow, which enhances security and user trust. Development gains efficiency by bypassing email verification, allowing for quicker iteration.
*   **Granular Rate Limiting**: Different rate limiters (`getRegisterLimiter`, `getOnboardingLimiter`) are applied to specific endpoints. This allows for fine-grained control over potential abuse. For instance, registration has a higher limit than onboarding, acknowledging that users might make more attempts to create an account than to complete an onboarding form.
*   **Robust Slug Generation**: The `toSlug` and `generateUniqueSlug` functions are designed to create human-readable, unique URLs for professional profiles. The inclusion of `RESERVED_SLUGS` prevents critical application routes from being shadowed by user-generated slugs, which is a forward-thinking approach to URL management.
*   **Idempotency in Onboarding**: The `/api/onboarding` route includes an early check for an existing professional record associated with the user. This makes the onboarding process idempotent, meaning that submitting the form multiple times will not create duplicate professional entries, improving the user experience and simplifying client-side logic.
*   **Strict Data Validation with Zod**: The use of Zod schemas (`registerSchema`, `onboardingSchema`) at each API boundary ensures that incoming data conforms to expected types and constraints. This prevents malformed data from reaching the database and reduces the risk of application errors.
*   **Smart-linking for Clients**: The logic in `/auth/callback` to link existing `clients` records to a newly verified `userId` is a thoughtful feature. It addresses the scenario where a professional might create a client record, and that client later decides to register an account, ensuring their historical data is preserved and linked.
*   **Security for Callback Parameters**: The `VALID_TYPES` set and `parseType` function in `/auth/callback` directly address a security vulnerability (L4 finding) by strictly controlling which values from the URL query string can be written to user metadata. This prevents attackers from injecting arbitrary data.

## Potential improvements

1.  **`professionals.email` Column Purpose Clarification**: The `email` column in the `professionals` table is currently `nullable` and *not unique*. However, the `userId` column is `nullable: false` and `unique: true`, linking directly to the Supabase user's ID, which inherently has a unique email. If `professionals.email` is intended to store the primary contact email for the professional, it should likely be `nullable: false` and `unique: true` to mirror the Supabase user's email or at least ensure consistency. If it's for an *alternative* contact email, its current nullable and non-unique status is acceptable, but its purpose could be explicitly documented or renamed for clarity.
2.  **`professionals.userId` Type Alignment**: The `userId` column in the `professionals` table is defined as `text`, while `id` columns (like `professionals.id` or `availability.id`) are `uuid`. Supabase user IDs are typically UUIDs. Aligning the `professionals.userId` type to `uuid` would improve type consistency across the schema and could facilitate future foreign key relationships if direct database access to Supabase's `auth.users` table were ever implemented.
3.  **Dynamic `RESERVED_SLUGS` Management**: The `RESERVED_SLUGS` set in `src/app/api/onboarding/route.ts` is hardcoded. As the application grows, this list might need frequent updates, and there's a risk of developers forgetting to add new top-level routes. Consider moving this list to a centralized configuration file or even a database table. This would allow for easier management, reduce the need for code changes when new routes are introduced, and potentially enable dynamic updates without redeploying the application.
4.  **Enhanced Welcome Email Error Reporting**: The `sendProfessionalWelcomeEmail` call in `src/app/api/onboarding/route.ts` uses a `.catch((err) => console.warn(...))` block. While this prevents the onboarding flow from failing due to an email issue, `console.warn` is a basic form of error reporting. For production, integrating this with a dedicated error monitoring service (e.g., Sentry, Datadog) would provide better visibility into email delivery failures, allowing for proactive troubleshooting and ensuring critical communications are sent.
