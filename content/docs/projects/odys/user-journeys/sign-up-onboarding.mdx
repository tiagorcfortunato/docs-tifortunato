# Professional Onboarding

The professional sign-up and onboarding journey is a critical path for new service providers joining the platform. This process guides a new user from initial account creation through to setting up their professional profile and availability, ensuring they are ready to accept clients. It involves several distinct steps, each handled by dedicated API routes and database interactions, designed to progressively gather necessary information while maintaining a smooth user experience.

## Overview

The journey begins with a user registering an account, typically via email and password. Upon successful registration, an email verification step is initiated by Supabase. Once the email is confirmed, the user is redirected back to the application, where their account type is potentially updated, and they are then guided to complete their professional profile. This profile setup, or "onboarding," involves providing details about their services, pricing, and availability.

At a high level, the flow involves three primary components:

1.  **Account Registration**: Handled by the `/api/auth/register` API route, this creates the core user account in Supabase.
2.  **Authentication Callback**: The `/auth/callback` route processes the response from Supabase after email verification or password recovery, establishing the user's session and performing initial data linking.
3.  **Professional Onboarding**: The `/api/onboarding` API route captures the detailed professional information and populates the `professionals` and `availability` tables.

Throughout this process, rate limiting is applied to prevent abuse, and data validation ensures the integrity of the information being stored.

## Account Registration

The `/api/auth/register` route is responsible for creating new user accounts. When a user submits their email and password, this endpoint first applies a rate limit using `getRegisterLimiter`, which permits up to 5 registration attempts per hour from a single IP address. This helps mitigate brute-force attacks or spam registrations.

The incoming request body is validated against the `registerSchema`, which mandates a valid email, a password of at least 8 characters (matching Supabase's default minimum), and optionally accepts a `name` and `type` for the user. This schema ensures that only well-formed data proceeds to account creation.

A key design choice here differentiates between `production` and `development` environments:

*   In `production`, the `supabase.auth.signUp()` method is used. This approach leverages Supabase's built-in email verification flow, automatically sending a confirmation email to the user. The `requiresEmailConfirmation` flag in the response indicates whether a session was immediately established or if email verification is pending.
*   In `development`, an `adminClient` is used with `admin.createUser()` and `email_confirm: true`. This bypasses the email verification step, allowing developers to rapidly test the onboarding flow without needing to check inboxes. The `_adminClient` is lazily initialized to ensure that environment variables like `SUPABASE_SERVICE_ROLE_KEY` are only accessed when needed, which is important for build environments where secrets might not be present.

Upon successful account creation, the route returns a success message, indicating whether email confirmation is required.

## Authentication Callback

After a user clicks a verification link in an email (or completes a password recovery flow), Supabase redirects them to the `/auth/callback` route. This route's primary function is to exchange the `code` provided by Supabase for a user session.

The route extracts the `code` and a `type` parameter from the URL. The `type` parameter is crucial for directing the user to the correct post-authentication experience. A `VALID_TYPES` set (`"professional"`, `"client"`, `"recovery"`) is used to strictly control which values are accepted. This is a security measure, explicitly noted as an "L4 finding," to prevent an attacker from injecting arbitrary data into the user's metadata via a crafted callback URL.

Once the session is established, the route handles different scenarios:

*   If the `type` is `"recovery"`, the user is redirected to the `/reset-password` page.
*   If the `type` is `"professional"` or `"client"`, the user's Supabase metadata is updated to reflect their designated role. This ensures the user's profile accurately reflects their intent.
*   A "smart-linking" mechanism is implemented for clients: if a user with a verified email logs in as a `"client"`, the system attempts to link their new `userId` to any existing entries in the `clients` table that share the same `email` but currently have a `null` `userId`. This helps consolidate client profiles if they previously interacted with the platform without a full account.

Finally, the user is redirected to `/auth/redirect`, which typically handles further routing within the application.

## Professional Onboarding

Once a professional has registered and verified their email, they proceed to the `/api/onboarding` route to complete their profile. This route is protected by `getOnboardingLimiter`, allowing 3 attempts per hour per IP, and requires an authenticated user session, verified by `getUser()`.

The onboarding process is designed to be idempotent: if a `professionals` entry already exists for the current `userId`, the existing profile is returned, preventing duplicate records and allowing users to re-submit the form without error.

The request body is validated against the `onboardingSchema`, which collects essential professional details:

*   `name`: The professional's full name.
*   `profession`: Their area of expertise.
*   `phone`: Contact number.
*   `bio`: An optional textual description.
*   `sessionDuration`: The standard length of a session, an integer up to 480 minutes.
*   `sessionPrice`: The cost of a session, a non-negative integer.
*   `serviceType`: Whether services are `in_person`, `online`, or `both`.
*   `city`, `state`: Optional location details.
*   `availability`: An array of objects, each specifying a `dayOfWeek` (0-6) and `startTime`/`endTime` in `HH:MM` format. This array must contain at least one entry.

A unique `slug` is generated for each professional based on their `name`. The `toSlug` function normalizes the name into a URL-friendly format. The `generateUniqueSlug` function then checks for conflicts against existing `professionals.slug` values and a `RESERVED_SLUGS` set (e.g., `"api"`, `"auth"`, `"dashboard"`). If a conflict occurs, a numeric suffix is appended (e.g., `john-doe-2`) until a unique slug is found. This ensures clean, human-readable URLs for professional profiles.

The collected data is then inserted into the `professionals` table, which has 32 columns, including `id` (UUID primary key), `userId` (unique text), `name`, `slug` (unique text), `phone`, `profession`, `sessionDuration`, `sessionPrice`, and various optional fields like `bio`, `avatarUrl`, and location details. Default values are provided for `sessionDuration`, `sessionPrice`, `plan`, `paymentType`, `autoConfirm`, `serviceType`, `active`, `createdAt`, and `updatedAt`.

If `availability` data is provided, it is inserted into the `availability` table, which has 5 columns, linking each entry to the new professional via `professionalId` (a UUID foreign key with `ON DELETE CASCADE`).

Finally, the user's Supabase metadata is updated to set their `type` to `"professional"` and their `name`. In `production` environments, a welcome email is sent to the professional using `sendProfessionalWelcomeEmail`, operating as a fire-and-forget task to avoid blocking the response.

## Design decisions

The separation of registration and onboarding into distinct API routes (`/api/auth/register` and `/api/onboarding`) reflects a progressive profiling strategy. Users can quickly create an account, and then take their time to complete the more detailed professional profile. This reduces initial friction and allows for a more focused data collection experience at each stage.

The conditional use of `supabase.auth.signUp()` in production versus `admin.createUser()` in development for registration is a pragmatic trade-off. It prioritizes a realistic email verification flow for end-users while providing developers with a faster iteration cycle by bypassing email checks during local development.

The `VALID_TYPES` set in `/auth/callback` is a direct response to a security concern, preventing malicious actors from injecting arbitrary data into user metadata. This explicit whitelist approach is more secure than simply accepting any query parameter value.

Rate limiting on both registration (`getRegisterLimiter`) and onboarding (`getOnboardingLimiter`) routes is a fundamental security and resource management decision. It protects against automated abuse, such as creating many fake accounts or repeatedly attempting to onboard.

The `generateUniqueSlug` function, coupled with the `RESERVED_SLUGS` set, is a thoughtful design to ensure user-friendly and conflict-free public profile URLs. It balances the desire for clean slugs with the need to prevent collisions with existing routes or other professionals.

The `professionals` table includes a `userId` column which is `text` and unique, serving as the direct link to the Supabase authentication system. The `userId` is not nullable, implying that a professional account is always tied to a Supabase user, which in turn requires an email. This structure allows for flexibility if, for example, a professional's email changes in Supabase but the `professionals` record needs to retain a historical or secondary email.

## Potential improvements

1.  **Enhanced Phone Number Validation**: The `onboardingSchema` for `phone` currently only enforces `z.string().min(10)`. This is a basic check. Consider adding more specific regex validation for phone numbers, or integrating a library for international phone number parsing and validation, to ensure data quality and improve user experience during sign-up. This would be applied in `src/app/api/onboarding/route.ts` within the `onboardingSchema`.
2.  **Asynchronous Welcome Email Handling**: The `sendProfessionalWelcomeEmail` in `src/app/api/onboarding/route.ts` is currently a fire-and-forget operation with a `console.warn` for errors. While this prevents blocking the API response, a more robust solution might involve queuing these emails (e.g., using a dedicated message queue or a serverless function) and implementing retry logic. This would ensure higher deliverability rates and better error visibility for critical communications.
3.  **Refine `generateUniqueSlug` Edge Cases**: The `generateUniqueSlug` function in `src/app/api/onboarding/route.ts` handles empty base names by defaulting to "user". While functional, consider if there are other edge cases for `toSlug` (e.g., names that normalize to only reserved words, or very short names) that could lead to less intuitive slugs or require many suffixes. A more sophisticated slug generation could prioritize readability for common names.
4.  **Explicit `type` for `professionals` table**: The `professionals.serviceType` column is defined as `text` in the schema, but the `onboardingSchema` uses `z.enum(["in_person", "online", "both"])`. While the application code enforces this, making the database column an `ENUM` type (if supported by the underlying database) would provide stronger type safety and data integrity at the database level, preventing invalid values from being inserted directly.
