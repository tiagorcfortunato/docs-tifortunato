# Sign-up and Onboarding

The professional sign-up and onboarding flow is a critical user journey for Odys, enabling new service providers to create an account, establish their professional profile, and begin offering their services. This process is carefully structured across several API endpoints and database interactions to ensure a smooth, secure, and efficient experience, from initial registration to a fully configured professional profile.

## Overview

The end-to-end flow for a professional joining Odys involves three primary stages, each handled by a dedicated API route:

1.  **Account Registration**: A new user provides basic credentials (email, password) to create an account. This is managed by the `/api/auth/register` endpoint.
2.  **Email Verification and Session Exchange**: After registration, Supabase handles email verification. Upon successful verification, the user is redirected to the `/auth/callback` route, which exchanges the verification code for a user session and performs initial user data updates.
3.  **Professional Onboarding**: Once authenticated, the user completes their professional profile, including details like their name, profession, contact information, service rates, and availability. This is handled by the `/api/onboarding` endpoint, which populates the `professionals` and `availability` tables.

Throughout this journey, rate limiting is applied to prevent abuse, and specific logic is implemented to differentiate between development and production environments, streamlining testing while maintaining security.

## Account Registration

The `/api/auth/register` endpoint is the entry point for new users to create an account. It expects an `email` and `password`, with optional `name` (minimum 2 characters) and `type` (either `client` or `professional`) fields, validated by the `registerSchema`. The `password` is enforced to be a minimum of 8 characters, aligning with Supabase's default authentication requirements.

A crucial aspect of this endpoint is its rate limiting, implemented using `getRegisterLimiter`. This limits registration attempts to 5 per hour per IP address, a measure designed to mitigate brute-force attacks and prevent spam registrations. If the limit is exceeded, the request is rejected with a `429` status code.

The account creation logic intelligently adapts to the environment:

*   In `production`, the `supabase.auth.signUp()` method is used. This approach leverages Supabase's built-in email verification flow, automatically sending a confirmation email to the user. The response indicates whether email confirmation is required, which is typically true for new sign-ups.
*   In `development`, an `_adminClient` (initialized lazily to avoid requiring sensitive environment variables during build steps) is used to call `admin.createUser()` with `email_confirm: true`. This bypasses the email verification step, allowing developers to quickly test the onboarding flow without needing to check inboxes.

This dual approach balances production security with development efficiency, a common trade-off in application design.

## Authentication Callback

The `/auth/callback` route serves as the destination for Supabase's OAuth redirects, primarily after a user verifies their email or completes a password recovery flow. It receives a `code` and an optional `type` parameter from the URL.

A significant security measure here is the `VALID_TYPES` set, which explicitly defines accepted values for the `type` parameter (`"professional"`, `"client"`, `"recovery"`). This prevents an attacker from injecting arbitrary data into the user's metadata via a crafted callback URL, addressing a potential L4 security finding.

Upon receiving a valid `code`, the route exchanges it for a user session using `supabase.auth.exchangeCodeForSession()`. If successful:

*   For `type === "recovery"`, the user is redirected to `/reset-password` to set a new password.
*   If `type` is `"professional"` or `"client"`, the user's metadata in Supabase is updated to reflect their role. This is important for subsequent authorization checks and UI rendering.
*   A "smart-linking" mechanism is triggered for `type === "client"`. If a user with the same email already exists in the `clients` table but without an associated `userId`, their `userId` is updated to link them to their newly verified Supabase account. This handles scenarios where a professional might have added a client's details before the client themselves signed up.

Finally, the user is redirected to `/auth/redirect` for further application-level routing, or to `/login?error=auth` if the session exchange fails.

## Professional Onboarding

After a professional has registered and verified their email, the `/api/onboarding` endpoint facilitates the creation of their detailed professional profile. This is a `POST` request that expects a comprehensive set of data, including `name`, `profession`, `phone`, `bio`, `sessionDuration`, `sessionPrice`, `serviceType`, `city`, `state`, and `availability`. The `onboardingSchema` ensures all incoming data adheres to defined types and constraints, such as `sessionDuration` being a positive integer up to 480 minutes, `sessionPrice` being a non-negative integer, `serviceType` being one of `in_person`, `online`, or `both`, and `availability` being an array of at least one time slot.

Similar to registration, this endpoint is protected by `getOnboardingLimiter`, allowing only 3 attempts per hour per IP address to prevent abuse during profile creation.

The onboarding process includes several key steps:

1.  **User Authentication**: It first verifies the user's identity using `getUser()`. An unauthenticated request is rejected with a `401` status.
2.  **Idempotency Check**: Before creating a new profile, the system checks if a `professionals` entry already exists for the current `userId`. If so, it returns the existing professional's data, making the operation idempotent and preventing duplicate profiles if the user accidentally submits the form multiple times.
3.  **Slug Generation**: A unique, human-readable `slug` is generated from the professional's `name`. The `toSlug()` function normalizes the name, removing special characters and spaces. The `generateUniqueSlug()` function then ensures this slug is unique within the `professionals` table and does not conflict with any `RESERVED_SLUGS` (e.g., "api", "auth", "dashboard", "login", "register", "explore") that are part of the application's routing structure. If a conflict occurs, a numeric suffix is appended (e.g., `john-doe-2`).
4.  **Database Insertion**: The professional's details are inserted into the `professionals` table. If `availability` data is provided, corresponding entries are created in the `availability` table, linked to the new professional's `id`.
5.  **Supabase Metadata Update**: The user's Supabase metadata is updated to set their `type` to `"professional"` and their `name`, ensuring consistency across authentication and application data.
6.  **Welcome Email**: In `production` environments, a welcome email is sent to the professional using `sendProfessionalWelcomeEmail`. This is a fire-and-forget operation, meaning the API response doesn't wait for the email to be sent, but any errors are logged.

This structured approach ensures that a professional's profile is created correctly, with appropriate data validation, uniqueness constraints, and user feedback.

## Design decisions

The design of the sign-up and onboarding flow reflects several deliberate choices:

*   **Separation of Concerns**: The process is broken into distinct API routes (`/api/auth/register`, `/auth/callback`, `/api/onboarding`). This modularity makes each step easier to understand, test, and maintain. `register` focuses solely on account creation, `callback` on session management and initial metadata, and `onboarding` on profile data.
*   **Rate Limiting for Security and Stability**: Implementing `Ratelimit.slidingWindow` via `@upstash/ratelimit` for `register` (5 attempts per hour) and `onboarding` (3 attempts per hour) is a critical decision to prevent automated abuse, such as spam registrations or denial-of-service attacks, without overly restricting legitimate users.
*   **Environment-Specific Logic**: The conditional use of `supabase.auth.signUp()` in production versus `admin.createUser()` in development for registration is a pragmatic trade-off. It prioritizes a streamlined developer experience by skipping email verification locally, while maintaining the full security and verification flow required for live users.
*   **Robust Slug Generation**: The `toSlug` and `generateUniqueSlug` functions demonstrate a thoughtful approach to creating user-friendly and unique profile URLs. The inclusion of `RESERVED_SLUGS` prevents potential routing conflicts, ensuring that a professional's chosen name doesn't accidentally shadow an application route like `/dashboard`.
*   **Idempotency in Onboarding**: The check for an existing professional profile in `/api/onboarding` ensures that if a user accidentally or intentionally submits the onboarding form multiple times, a duplicate profile is not created. This improves data integrity and user experience.
*   **Security Hardening for Callback**: The explicit `VALID_TYPES` set in `src/app/auth/callback/route.ts` is a direct response to a security finding (L4 finding). It prevents malicious actors from injecting arbitrary data into user metadata through URL parameters, demonstrating a commitment to secure coding practices.
*   **Smart-Linking for Client Experience**: The logic in `src/app/auth/callback/route.ts` to link a newly verified user's `userId` to an existing `clients` record based on email (`isNull(clients.userId)` and `eq(clients.email, user.email)`) is a user-centric design choice. It anticipates scenarios where a professional might add a client's details before the client creates their own account, providing a more connected experience.

## Potential improvements

1.  **`professionals.email` Redundancy**: The `professionals` table includes an `email` column, which is nullable. However, the onboarding process (`src/app/api/onboarding/route.ts`) retrieves the `user.email` from Supabase, which is guaranteed to exist and be verified at that stage. If the professional's public-facing email is always intended to be the same as their login email, this column could be removed from the `professionals` table and derived directly from the authenticated user's session, reducing data duplication and potential for inconsistency. If it's meant for a *different* contact email, its purpose should be clarified.
2.  **`_adminClient` Environment Variable Handling**: In `src/app/api/auth/register/route.ts`, the `getAdminClient` function uses non-null assertions (`!`) for `process.env.NEXT_PUBLIC_SUPABASE_URL` and `process.env.SUPABASE_SERVICE_ROLE_KEY`. While this is acceptable in environments where these are guaranteed, in some build or test environments, these might be missing, leading to a runtime error. A more explicit check and graceful error handling (e.g., throwing a custom error or returning a specific message if `NODE_ENV !== "production"` but keys are missing) could make the system more resilient.
3.  **Welcome Email Error Handling**: The `sendProfessionalWelcomeEmail` call in `src/app/api/onboarding/route.ts` uses a `.catch()` block that only `console.warn`s if the email fails. Depending on the business criticality of welcome emails, this fire-and-forget approach might be insufficient. Implementing a more robust error handling strategy, such as retrying the email send, logging to a dedicated error tracking system, or even using a dead-letter queue for failed emails, could improve reliability and ensure professionals receive their initial communication.
