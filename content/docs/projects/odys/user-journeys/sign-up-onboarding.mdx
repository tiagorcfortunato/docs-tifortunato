# Professional Onboarding

The professional sign-up and onboarding flow is a critical journey for new users to establish their presence and begin offering services on the platform. This process guides a new professional from initial account creation through setting up their profile, defining their services, and configuring their availability, ultimately making them discoverable and bookable.

## Overview

The end-to-end flow for a professional involves several distinct stages, each handled by specific API routes and database interactions. It begins with user registration, followed by an authentication callback that verifies the user's email and potentially links them to existing client data. Finally, the onboarding process collects detailed professional information and configures their service offerings.

The primary API routes orchestrating this journey are:
*   `/api/auth/register` (POST): Handles the initial user account creation.
*   `/auth/callback` (GET): Processes the redirect from Supabase after email verification or password recovery.
*   `/api/onboarding` (POST): Collects and persists the professional's detailed profile and availability.

These routes interact with the database schema, primarily populating the `professionals` table, which holds 32 columns of detailed information, and the `availability` table, which defines their working hours across 5 columns. Rate limiting is applied at key stages to prevent abuse and ensure system stability.

## Registration

The journey begins with a `POST` request to the `/api/auth/register` endpoint. This route is responsible for creating a new user account within Supabase. The incoming request body is validated against the `registerSchema`, which mandates an `email` and a `password` of at least 8 characters, aligning with Supabase's default authentication requirements. Optional fields like `name` and `type` (specifying if the user is a "client" or "professional") can also be provided at this stage.

To safeguard against malicious or accidental overuse, this endpoint is protected by a rate limit, allowing only 5 registration attempts per hour from a single IP address, managed by `getRegisterLimiter`.

A notable design choice in this route is the conditional logic for user creation based on the `NODE_ENV` environment variable. In a production environment, the system uses `supabase.auth.signUp()`. This method is crucial because it automatically triggers Supabase's email verification flow, ensuring that new accounts are legitimate. If `signUp()` does not return a session, it indicates that email confirmation is required. Conversely, in a development environment, the system uses an administrative Supabase client (`getAdminClient()`) to call `admin.createUser()` with `email_confirm: true`. This bypasses the email verification step, significantly accelerating the testing cycle for developers.

Upon successful account creation, the route returns a success message, indicating whether email confirmation is required, which guides the frontend's subsequent user experience.

## Authentication Callback

Following registration and email verification (or password recovery), Supabase redirects the user to the `/auth/callback` endpoint. This `GET` route is designed to exchange the authentication `code` provided by Supabase for a user session. It also parses a `type` parameter from the URL, which can indicate the user's role or the purpose of the callback (e.g., "professional", "client", or "recovery").

A critical security measure implemented here is the `VALID_TYPES` set, which explicitly defines the only accepted values for the `type` parameter. This prevents an attacker from injecting arbitrary data into the user's metadata via a crafted callback URL, addressing a potential vulnerability.

If a session is successfully established:
*   For password recovery (`type === "recovery"`), the user is redirected to the `/reset-password` page.
*   If a `type` of "professional" or "client" is present, the user's Supabase metadata is updated to reflect their designated role.
*   A "smart-linking" mechanism is then executed for clients. If the user's email is verified and their `type` is "client", the system attempts to link their new Supabase `userId` to any existing `clients` records that share the same email but currently have a `null` `userId`. This helps unify user identities, especially if a client was added by a professional before they created their own account.

Finally, the user is redirected to `/auth/redirect` for further application-level routing, or to `/login?error=auth` if an error occurred during the session exchange.

## Onboarding

Once a professional's account is registered and verified, they proceed to the onboarding flow, handled by the `/api/onboarding` `POST` endpoint. This is where the professional provides the detailed information necessary to set up their public profile and service offerings.

Similar to registration, this endpoint is protected by `getOnboardingLimiter`, allowing only 3 attempts per hour per IP address to prevent excessive submissions.

The route first performs an idempotency check: it queries the `professionals` table to see if a record already exists for the current `userId`. If so, it returns the existing professional's data, allowing users to safely retry or revisit the onboarding process without creating duplicate entries.

The incoming request body is validated against the `onboardingSchema`, which requires essential details such as `name`, `profession`, `phone`, `sessionDuration`, `sessionPrice`, and at least one `availability` slot. Optional fields include `bio`, `serviceType` (e.g., "in_person", "online", "both"), `city`, and `state`.

A unique `slug` is generated for the professional's public profile URL. The `toSlug` function converts the professional's `name` into a URL-friendly format. The `generateUniqueSlug` function then ensures this slug is unique within the `professionals` table, handling potential collisions by appending a numeric suffix (e.g., `john-doe-2`). It also checks against a `RESERVED_SLUGS` set to prevent conflicts with core application routes like "api" or "dashboard".

Upon successful validation and slug generation, a new record is inserted into the `professionals` table, populating its 32 columns with the provided data. Concurrently, the professional's weekly availability, specified as an array of `dayOfWeek`, `startTime`, and `endTime`, is inserted into the `availability` table, which has 5 columns.

The professional's Supabase user metadata is also updated to set their `type` to "professional" and their `name`. Finally, a welcome email is dispatched to the professional via `sendProfessionalWelcomeEmail`. This email is sent only in production environments to avoid unnecessary emails during development and is handled asynchronously as a fire-and-forget operation.

## Design decisions

The design of the professional onboarding flow reflects several deliberate choices aimed at balancing user experience, security, and development efficiency:

*   **Separation of Registration and Onboarding**: The decision to split account creation (`/api/auth/register`) from profile setup (`/api/onboarding`) allows for a clear separation of concerns. Registration focuses solely on authentication, while onboarding gathers business-specific details. This modularity makes each step simpler to manage and test.
*   **Environment-Specific Supabase User Creation**: Using `supabase.auth.signUp()` in production ensures email verification, a critical security and anti-spam measure. The `admin.createUser()` in development, however, prioritizes developer velocity by bypassing this step, acknowledging the different needs of development and production environments.
*   **Custom Slug Generation**: Implementing `toSlug` and `generateUniqueSlug` ensures that each professional has a unique, human-readable, and URL-friendly identifier for their public profile. The `RESERVED_SLUGS` list prevents conflicts with core application routes, maintaining a clean URL structure.
*   **Idempotency in Onboarding**: The check for an existing professional record in `/api/onboarding` makes the endpoint idempotent. This means that if a user or system retries the onboarding request, it won't create duplicate professional profiles, leading to a more resilient and user-friendly experience.
*   **Strict Type Validation in Auth Callback**: The `VALID_TYPES` set in `/auth/callback` is a direct security measure. By explicitly allowing only known types, the system prevents malicious actors from injecting arbitrary data into user metadata, which could otherwise be exploited.
*   **Smart-Linking Clients**: The logic in `/auth/callback` to link a newly verified user's `userId` to existing `clients` records with matching emails is a user experience enhancement. It automatically connects pre-existing client data (perhaps created by a professional or an AI agent) to the client's actual user account once they register, providing a unified view of their interactions.
*   **Granular Rate Limiting**: Applying specific rate limits like 5 attempts per hour for registration (`rl:register`) and 3 attempts per hour for onboarding (`rl:onboarding`) helps protect the system from brute-force attacks, spam, and resource exhaustion, ensuring fair usage for all.

## Potential improvements

1.  **Availability Time Data Types**: The `startTime` and `endTime` columns in the `availability` table are currently defined as `text`. While functional, using a more specific database type like `time` or `interval` (if supported by the database) could offer better data integrity, allow for more efficient time-based queries, and enable database-level validation of time formats and ranges. This would shift some validation burden from the application layer to the database.
2.  **Optimized Slug Generation**: The `generateUniqueSlug` function in `src/app/api/onboarding/route.ts` currently performs database queries in a `while` loop to find a unique slug. In scenarios with very high concurrency or frequent name collisions, this iterative querying could become a performance bottleneck. An improvement could involve attempting to insert the initial slug and handling a unique constraint violation, then falling back to the iterative approach, or pre-generating a batch of potential slugs to reduce database roundtrips.
3.  **Robust Welcome Email Delivery**: The `sendProfessionalWelcomeEmail` call in `src/app/api/onboarding/route.ts` is implemented as a fire-and-forget operation with a `console.warn` for errors. For critical communications like welcome emails, a more robust delivery mechanism could be beneficial. This might involve using a dedicated message queue, a retry mechanism, or integrating with a transactional email service that provides delivery guarantees and analytics, ensuring that emails are sent even if there are transient failures.
4.  **Name Field Consistency**: The `name` field is optional in the `registerSchema` in `src/app/api/auth/register/route.ts` but required in the `onboardingSchema` in `src/app/api/onboarding/route.ts`. While this allows for a minimal initial registration, it means a professional might register without a name, only to be prompted for it later. Making `name` a required field during registration could streamline the initial user data collection and ensure a more complete user profile from the outset, assuming a name is always expected for a professional.
