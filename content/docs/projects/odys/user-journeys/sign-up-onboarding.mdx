# Professional Sign-up and Onboarding

The professional sign-up and onboarding journey is a critical user flow, guiding new professionals from initial registration to setting up their profile and availability. This process involves several distinct steps, each handled by dedicated API routes and database interactions, ensuring a smooth and secure entry into the Odys platform. This document details the architecture and design choices behind this end-to-end flow, from user authentication to profile creation.

## Overview

The professional sign-up and onboarding process is orchestrated across three primary API routes: `/api/auth/register`, `/app/auth/callback`, and `/api/onboarding`.

1.  **Registration**: A new user initiates the process by providing basic credentials (email, password) via the `/api/auth/register` endpoint. This creates a user account in Supabase and handles email verification.
2.  **Authentication Callback**: After email verification (typically by clicking a link in an email), Supabase redirects the user to `/app/auth/callback`. This route exchanges the authentication code for a session, updates user metadata, and performs "smart-linking" for existing client profiles.
3.  **Onboarding**: Once authenticated, the user proceeds to the onboarding flow, submitting their professional details and availability to the `/api/onboarding` endpoint. This populates the `professionals` and `availability` tables, completing their profile setup.

Throughout this journey, rate limiting is applied to prevent abuse, and data validation ensures the integrity of user-provided information.

## Registration Flow

The initial step for any new professional is creating an account, managed by the `POST` handler in `src/app/api/auth/register/route.ts`. This route is designed to handle the creation of new user accounts within the Supabase authentication system.

Before processing any registration request, the system applies rate limiting using `getRegisterLimiter` from `src/lib/ratelimit.ts`. This limiter permits a maximum of 5 registration attempts per hour per IP address, identified by `rl:register`, mitigating potential brute-force attacks or spam registrations. If the limit is exceeded, the API responds with a `429 Too Many Requests` status.

Input validation is performed using `registerSchema`, a Zod schema that enforces requirements for `email` (must be a valid email format), `password` (minimum 8 characters, aligning with Supabase's default), and optional `name` and `type` fields. This ensures that only well-formed data proceeds to user creation.

A key design decision here is the conditional logic for user creation based on the `NODE_ENV` environment variable.
*   In `production`, the `supabase.auth.signUp()` method is used. This approach leverages Supabase's built-in email verification flow, automatically sending a confirmation email to the user. The `requiresEmailConfirmation` flag in the response indicates whether a session was immediately established or if email verification is pending.
*   In `development`, to accelerate testing cycles, the `getAdminClient().auth.admin.createUser()` method is employed. This uses a Supabase service role key to create a user with `email_confirm: true`, bypassing the email verification step. The `_adminClient` is lazily initialized to avoid requiring sensitive environment variables during build time, which is particularly useful for CI/CD environments like Dependabot.

Upon successful user creation, the API returns a `200 OK` response, indicating success and whether email confirmation is required. Any errors during this process, such as invalid data or Supabase-related issues, are caught and returned with appropriate HTTP status codes (e.g., `400 Bad Request`, `500 Internal Server Error`).

## Authentication Callback

The `GET` handler in `src/app/auth/callback/route.ts` serves as the destination for Supabase's OAuth callbacks, primarily after a user verifies their email or initiates a password recovery. This route is crucial for completing the authentication handshake and performing post-verification actions.

The route extracts a `code` and an optional `type` parameter from the URL's search parameters. The `type` parameter is carefully parsed using `parseType` against a `VALID_TYPES` set (`"professional"`, `"client"`, `"recovery"`). This strict validation is a direct result of an L4 finding, preventing an attacker from injecting arbitrary JSON into user metadata via a crafted callback URL.

The `supabase.auth.exchangeCodeForSession(code)` call is the core of this route, converting the temporary code into a persistent user session. If this exchange is successful:
*   For a `type` of `"recovery"`, the user is redirected to the `/reset-password` page to set a new password.
*   If the `type` is `"professional"` or `"client"`, the user's metadata in Supabase is updated to reflect their role.
*   A "smart-linking" mechanism is triggered if the user's `email` is available and the `type` is `"client"`. This logic queries the `clients` table for any existing client entries that have the same email but are not yet linked to a `userId`. If found, the `userId` of the newly authenticated user is associated with these pre-existing client records. This is a convenience feature, allowing users who might have been added as clients by a professional to seamlessly link their existing client profile upon signing up.

Finally, the user is redirected to `/auth/redirect` for further application-level routing or to `/login?error=auth` if any errors occurred during the session exchange. The `origin` for redirection is dynamically constructed using `x-forwarded-host` and `x-forwarded-proto` headers to ensure correct redirects in production environments, especially when deployed behind proxies like Vercel.

## Professional Onboarding

After a professional has registered and verified their email, they proceed to the onboarding phase, handled by the `POST` handler in `src/app/api/onboarding/route.ts`. This route is responsible for collecting detailed professional information and creating their profile within the Odys database.

Similar to registration, this route is protected by rate limiting using `getOnboardingLimiter`, allowing 3 attempts per hour per IP address, identified by `rl:onboarding`. This prevents excessive submissions during the onboarding process.

The route first authenticates the user using `getUser()`. If no authenticated user is found, an `unauthorized()` response is returned. A crucial idempotency check follows: the system queries the `professionals` table to see if a professional profile already exists for the current `userId`. If one is found, the existing profile is returned, preventing duplicate entries and allowing users to safely re-submit the form without adverse effects.

The `onboardingSchema` defines the expected structure and validation rules for the professional's data, including:
*   `name`, `profession`, `phone`: Required strings.
*   `bio`: Optional text.
*   `sessionDuration`: An integer representing session length, capped at 480 minutes.
*   `sessionPrice`: A non-negative integer for pricing.
*   `serviceType`: An enum (`"in_person"`, `"online"`, `"both"`) for service delivery.
*   `city`, `state`: Optional location details.
*   `availability`: A required array of objects, each specifying `dayOfWeek`, `startTime`, and `endTime`. This array must contain at least one entry.

A unique `slug` is generated for the professional's public profile URL. The `toSlug` function converts the professional's name into a URL-friendly format. The `generateUniqueSlug` function then ensures this slug is unique within the `professionals` table, checking against `RESERVED_SLUGS` (e.g., "api", "auth", "dashboard") to prevent collisions with application routes. If a collision occurs, a numeric suffix is appended (e.g., "john-doe-2").

Upon successful validation and slug generation, a new record is inserted into the `professionals` table with the provided details. If `availability` data is present, corresponding entries are created in the `availability` table, linked to the new professional's `id`.

Finally, the user's Supabase metadata is updated via `supabase.auth.updateUser` to set their `type` to `"professional"` and their `name`. In `production` environments, a welcome email is sent to the professional using `sendProfessionalWelcomeEmail`, providing them with their profile slug. This email sending is fire-and-forget, meaning any failure in sending the email does not block the onboarding process, though a warning is logged.

## Design decisions

*   **Separation of Concerns**: The registration, authentication callback, and onboarding processes are handled by distinct API routes (`/api/auth/register`, `/app/auth/callback`, `/api/onboarding`). This modular approach improves maintainability, allows for specific rate limiting, and clearly delineates responsibilities.
*   **Rate Limiting**: Dedicated rate limiters (`getRegisterLimiter`, `getOnboardingLimiter`) are implemented using Upstash Redis, with specific limits (5 attempts/hour for register, 3 attempts/hour for onboarding) to protect against abuse and ensure service stability. The prefixes `rl:register` and `rl:onboarding` clearly identify the purpose of each limiter.
*   **Environment-Specific Authentication**: The `src/app/api/auth/register/route.ts` differentiates between `production` and `development` environments for user creation. In production, `supabase.auth.signUp()` is used to trigger email verification, aligning with security best practices. In development, `admin.createUser()` with `email_confirm: true` is used to streamline testing by bypassing email verification. This trade-off prioritizes developer experience in non-production environments.
*   **Idempotency for Onboarding**: The `/api/onboarding` route includes an early check for an existing professional profile associated with the `userId`. If found, it returns the existing profile, making the onboarding process idempotent. This prevents errors if a user accidentally or intentionally submits the onboarding form multiple times.
*   **Robust Slug Generation**: The `generateUniqueSlug` function in `src/app/api/onboarding/route.ts` ensures that every professional gets a unique, human-readable slug for their public profile. It handles empty or all-diacritic names, checks against a `RESERVED_SLUGS` set to avoid conflicts with application routes, and appends numeric suffixes (`-2`, `-3`, etc.) for collisions. This design balances user-friendliness with system integrity.
*   **Strict Type Validation in Callback**: The `VALID_TYPES` set and `parseType` function in `src/app/auth/callback/route.ts` explicitly restrict the `type` parameter to a closed set of values. This was a critical security enhancement (L4 finding) to prevent malicious actors from injecting arbitrary data into user metadata via URL query parameters.
*   **Smart-Linking Clients**: The `auth/callback` route includes logic to link unassociated `clients` records to a newly verified `userId` if their emails match and the user is registering as a `client`. This provides a convenient way for existing client data to be automatically associated with a user account upon sign-up.

## Potential improvements

*   **`_adminClient` Error Handling**: In `src/app/api/auth/register/route.ts`, the `getAdminClient` function uses non-null assertions (`!`) for environment variables. While lazy initialization helps, if `process.env.NEXT_PUBLIC_SUPABASE_URL` or `process.env.SUPABASE_SERVICE_ROLE_KEY` are missing at runtime in a development environment, it will still throw an unhandled error. Consider adding explicit checks for these environment variables and throwing a more descriptive error or returning a `500` response if they are not configured, rather than relying on the non-null assertion.
*   **`generateUniqueSlug` Database Query Optimization**: The `generateUniqueSlug` function in `src/app/api/onboarding/route.ts` performs a database query inside a `while (true)` loop to find a unique slug. While effective, if the `professionals` table grows very large or if there's a high rate of sign-ups with similar names, this could lead to multiple sequential database calls, potentially impacting performance. For very high-volume scenarios, a more optimized approach might involve generating a random suffix initially or using a more sophisticated collision resolution strategy that minimizes database round trips.
*   **Welcome Email Failure Reporting**: The `sendProfessionalWelcomeEmail` call in `src/app/api/onboarding/route.ts` uses a `.catch()` block that only logs a warning to `console.warn` if the email fails to send. While this is acceptable for a fire-and-forget operation, a more robust system would integrate with an error tracking service (e.g., Sentry, Datadog) to capture and alert on email delivery failures, providing better visibility into potential issues with user communication.
*   **Cross-Role Smart-Linking**: The "smart-linking" logic in `src/app/auth/callback/route.ts` for updating `clients.userId` is currently restricted to `type === "client"`. If a user registers as a "professional" but also has a pre-existing client entry with the same email, that client entry's `userId` would not be linked. Depending on product requirements, it might be beneficial to extend this smart-linking to professionals as well, allowing them to manage their own client profile if one exists.
