# Booking Flow

The booking flow is a core customer journey, enabling individuals to discover professionals, select available time slots, provide their details, and secure an appointment. This process is designed to be intuitive for the customer while handling complex logic for availability, conflict resolution, and notifications on the backend.

## Overview

The customer booking flow is orchestrated across several key components:

*   **`src/app/p/[slug]/page.tsx`**: This Next.js server component serves as the public landing page for a professional. It fetches and displays the professional's profile, reviews, and related services, then renders the interactive booking widget.
*   **`src/app/p/[slug]/booking-widget.tsx`**: A client-side React component responsible for the interactive elements of booking, including date selection, slot display, and the client information form.
*   **`src/app/api/booking/route.ts`**: This API route handles both fetching available slots (via `GET` requests) and processing new appointment submissions (via `POST` requests). It interacts with the database, applies business logic, and dispatches notifications.
*   **`src/lib/slots.ts`**: A utility module that calculates available time slots based on a professional's defined availability rules and existing appointments.

The database schema plays a central role, with the `professionals` table storing core professional data, `availability` defining their working hours, `appointments` tracking all scheduled sessions, `clients` managing customer information, and `notifications` handling alerts for both professionals and clients. The system also integrates with WhatsApp for critical communications and Posthog for analytics.

## Professional Profile Landing Page

When a customer navigates to a professional's public profile, such as `/p/dr-alice-smith`, the `src/app/p/[slug]/page.tsx` server component takes over. This component is responsible for:

1.  **Data Fetching**: It queries the `professionals` table using the `slug` parameter to retrieve the professional's details. If the professional is not found or is inactive, it triggers a `notFound()` redirect.
2.  **Metadata Generation**: The `generateMetadata` function dynamically sets the page title and description for SEO purposes, using the professional's `name`, `profession`, and `bio`.
3.  **User Context**: It checks if the current visitor is logged in and, if so, whether they are the owner of the page (`isOwner`) or an existing client. This allows for personalized UI elements, like pre-filling the booking form with client data from the `clients` table if available.
4.  **Displaying Information**: The page renders the professional's `avatarUrl`, `name`, `profession`, `sessionDuration`, `sessionPrice`, `bio`, `welcomeMessage`, and `serviceType`. It also fetches and displays `reviews` from the `reviews` table, joining with `clients` to show client names, and calculates an `avgRating`.
5.  **Related Professionals**: To enhance discoverability, the page fetches and displays up to four other professionals with the same `profession`, using `getProStats` to include their average ratings and review counts.
6.  **Booking Widget Integration**: The most critical part for the booking flow is the inclusion of the `<BookingWidget />` client component. Essential professional details like `slug`, `sessionDuration`, `sessionPrice`, `paymentType`, `paymentPercentage`, `pixKeyType`, and `pixKey` are passed as props to this client component, along with any pre-filled client data.

## Slot Selection and Availability

The interactive heart of the booking process resides within the `src/app/p/[slug]/booking-widget.tsx` client component.

1.  **Date Selection**: The widget presents a `<Calendar />` component, allowing the customer to select a desired date. Dates in the past are disabled to prevent invalid bookings.
2.  **Fetching Availability**: When a `selectedDate` is chosen, a `useEffect` hook triggers a `GET` request to the `/api/booking` endpoint, passing the `slug` and the selected `date`.
3.  **Server-Side Availability Logic (`GET /api/booking`)**:
    *   The API handler first retrieves the `professional.id` and `professional.sessionDuration` from the `professionals` table. Notably, it only selects these specific columns, avoiding the accidental exposure of sensitive professional data that was present in a previous iteration.
    *   It then fetches the professional's `availability` rules from the `availability` table for the given `professionalId`. These rules define the general working hours for each `dayOfWeek`.
    *   Concurrently, it queries the `appointments` table for `existingAppointments` within the selected day, filtering out appointments with `rejected` or `cancelled` statuses. This ensures that only active or pending appointments are considered conflicts.
    *   The API returns these `rules` and `existingAppointments` to the client.
4.  **Client-Side Slot Generation**: Back in the `<BookingWidget />`, the `generateSlots` function from `src/lib/slots.ts` processes the received `rules` and `existingAppointments`. It iterates through the professional's defined working hours for the selected day, creating potential time slots based on the `sessionDuration`. For each potential slot, it checks for overlaps with `existingAppointments` and filters out any slots that are in the past.
5.  **Displaying Slots**: The generated available slots are then grouped into `morning`, `afternoon`, and `evening` categories for a user-friendly display. Customers can then select their preferred `selectedSlot`. Once a slot is chosen, a "Continuar" button appears, leading to the client information form.

## Booking Submission

After selecting a date and time, the customer proceeds to fill out their details in the booking form within `src/app/p/[slug]/booking-widget.tsx`.

1.  **Client Form**: The form uses `react-hook-form` with `zodResolver` for client-side validation based on `clientSchema`. It collects `name`, `phone`, and optionally `email`.
2.  **Honeypot**: A hidden `website` field acts as a honeypot. This field is visually hidden, skipped by tab navigation, and marked `aria-hidden`. If a bot fills this field, the server will detect it and silently drop the submission, returning a fake success response to prevent the bot from learning it's a trap.
3.  **`POST /api/booking` Request**: Upon submission, the `onSubmit` function sends a `POST` request to the `/api/booking` endpoint with the selected `slug`, `startsAt` time, and client details.
4.  **Server-Side Processing (`POST /api/booking`)**:
    *   **Rate Limiting**: The request is first subjected to rate limiting using `getBookingLimiter()` from `src/lib/ratelimit.ts`, allowing a maximum of 5 booking attempts per IP address every 10 minutes. If the limit is exceeded, a `429 Too Many Requests` response is returned.
    *   **Timing Oracle Mitigation**: A `respondAfterFloor` function introduces a minimum response time of 250ms. This is a deliberate security measure to prevent timing attacks that could differentiate between database operations (e.g., finding an existing client vs. inserting a new one) and potentially leak information.
    *   **Input Validation**: The incoming JSON body is validated against `bookingSchema` using Zod.
    *   **Honeypot Check**: The `website` field is checked; if it contains any value, the request is treated as spam and a fake success response is returned without touching the database.
    *   **Professional Lookup**: The professional's details are fetched from the `professionals` table.
    *   **Plan Limit Checks**: The system verifies if the professional's current plan (determined by `effectivePlan` from `src/lib/stripe`) allows for the new booking. It checks `clientCount` against `plan.limits.clients` and `monthlyCount` of appointments against `plan.limits.appointmentsPerMonth`. If limits are exceeded for a new client or monthly appointments, a `403 Forbidden` response is returned.
    *   **Atomic Transaction**: The core booking logic is wrapped in a Drizzle `transaction` with `serializable` isolation level. This is crucial for data integrity:
        *   **Conflict Check**: It first checks for any `appointments` that would conflict with the proposed `startsAt` and `endsAt` times, excluding `rejected` or `cancelled` appointments. If a conflict is found, it throws a "SLOT_TAKEN" error.
        *   **Client Upsert**: It attempts to find an existing client in the `clients` table using `phone` or `email` for the given `professionalId`. If a client is found, their `email` is updated if a new one is provided. If no client is found, a new entry is inserted into the `clients` table.
        *   **Appointment Insertion**: Finally, the new appointment is inserted into the `appointments` table. The `status` is set to `confirmed` if `professional.autoConfirm` is true, otherwise `pending_confirmation`. The `paymentStatus` is initialized to `none`.
    *   **Conflict Handling**: If the transaction fails due to "SLOT_TAKEN" or a `40001` SQLSTATE (indicating a serialization conflict, typically from concurrent writes), a `409 Conflict` response is returned, informing the user that the slot was just taken.

## Confirmation and Notifications

Upon successful booking, the system provides immediate feedback and dispatches various notifications.

1.  **Client-Side Success**: The `<BookingWidget />` transitions to the "success" step, displaying a confirmation message to the customer. If the `paymentType` is not "after" and a `pixKey` is configured, a `<PixQR />` component is rendered, showing the amount due for immediate payment.
2.  **Registration Prompt**: For unauthenticated users, the success screen offers a prompt to create a free account, with a link to `/register` that pre-fills their `name`, `phone`, and `email` for convenience.
3.  **Professional Notification**: A new entry is inserted into the `notifications` table for the professional, alerting them to a new booking request or a confirmed appointment.
4.  **WhatsApp Messages**:
    *   If the professional has `autoConfirm` enabled, a `msgBookingConfirmed` message is sent to the client, and a `msgBookingConfirmedReceipt` is sent to the professional.
    *   If `autoConfirm` is false, a `msgBookingRequest` is sent to the professional, prompting them to review and confirm the booking.
    *   These messages are sent via the `sendWhatsApp` utility, using templates defined in `src/lib/whatsapp`.
5.  **Email Notification**: If the professional has an `email` configured, a booking request email is sent to them via `sendBookingRequestEmailToProfessional` from `src/lib/email`.
6.  **Analytics**: Posthog events, such as `booking_received_server` and `first_booking_at`, are captured to track booking volume and professional engagement.
7.  **Generic Success Response**: The `POST /api/booking` endpoint returns a simple `{ success: true }` to the client. This generic response is a security measure, preventing an attacker from inferring information (like `clientId`) from the response body.

Further actions on an appointment, such as `confirm`, `reject`, `cancel`, `paid`, `complete`, or `no_show`, are handled by the `PATCH /api/appointments/[id]` API route. This route performs authorization checks (ensuring the user is either the professional or the client, depending on the action) and updates the `appointments` table status. It also dispatches specific WhatsApp messages and notifications relevant to each status change, such as `msgBookingRejected` or `msgAppointmentCompletedToClient`.

## Design Decisions

*   **Atomic Booking Transaction**: The decision to wrap the conflict check, client upsert, and appointment insertion within a Drizzle `transaction` with `serializable` isolation level in `src/app/api/booking/route.ts` is fundamental. This prevents race conditions where multiple concurrent booking attempts for the same slot could bypass individual checks and lead to double bookings. The `serializable` level forces the database to re-evaluate conditions if underlying data changes, ensuring that only one booking can succeed for a given slot at any moment. The explicit handling of `SQLSTATE 40001` (serialization failure) reinforces this by returning a user-friendly conflict message.
*   **Honeypot for Spam Prevention**: The inclusion of a hidden `website` field in the `bookingSchema` and its server-side validation in `src/app/api/booking/route.ts` is a pragmatic approach to combat bot spam. By returning a `200 OK` with a generic success message for bot submissions, the system avoids signaling to automated scripts that the field is a trap, making it a more persistent defense.
*   **Response-Time Floor for Security**: The `respondAfterFloor` utility in `POST /api/booking` introduces a minimum delay before sending a response. This is a security measure to mitigate timing attacks. Without it, an attacker could potentially measure the difference in response times between a booking request that finds an existing client record (faster) and one that inserts a new client record (slower), thereby inferring whether a given phone number or email is already associated with a client of that professional.
*   **Selective Data Exposure**: The `GET /api/booking` endpoint explicitly selects only `id` and `sessionDuration` from the `professionals` table. This is a crucial security enhancement, preventing the accidental leakage of sensitive professional data (like `email`, `phone`, `userId`, `plan`, `stripeCustomerId`) to unauthenticated users who might query the availability API directly.
*   **Rate Limiting on Booking API**: Applying `getBookingLimiter()` to the `POST /api/booking` route is a direct defense against abuse. It prevents malicious actors from flooding the system with booking requests, which could otherwise lead to denial-of-service, excessive database load, or unnecessary calls to external services like the WhatsApp API.
*   **Client-Side vs. Server-Side Rendering**: The professional profile (`src/app/p/[slug]/page.tsx`) is a server component, which is beneficial for SEO and initial page load performance. The interactive booking widget (`src/app/p/[slug]/booking-widget.tsx`) is a client component, allowing for dynamic date/time selection and form interactions without full page reloads, providing a smoother user experience.

## Potential Improvements

1.  **Refine `generateSlots` Timezone Handling**: The `generateSlots` function in `src/lib/slots.ts` relies on `Date` objects and `date-fns` functions, which are inherently sensitive to the server's local timezone. While `startsAt` and `endsAt` in the `appointments` table are `timestamp` (typically UTC), the `availability.startTime` and `availability.endTime` are stored as `text` strings like "09:00". This discrepancy can lead to subtle bugs, especially for professionals operating in different timezones or during daylight saving transitions. A concrete improvement would be to store `availability` times with explicit timezone information or to consistently convert all time-related data to a canonical timezone (e.g., UTC) at the application boundary before any calculations.
2.  **Centralize Messaging Orchestration**: The logic for sending WhatsApp messages and emails is currently distributed across `src/app/api/booking/route.ts` (for initial booking) and `src/app/api/appointments/[id]/route.ts` (for status updates). This leads to some duplication and makes it harder to manage, test, or extend the messaging capabilities. A dedicated messaging service or utility could be introduced that takes an event type (e.g., `BOOKING_REQUESTED`, `APPOINTMENT_CONFIRMED`) and the relevant appointment/professional/client data, then orchestrates the sending of appropriate WhatsApp messages and emails. This would consolidate the `sendWhatsApp` and `sendBooking...EmailTo...` calls into a single, more maintainable location.
3.  **Enhance Error Logging and Monitoring**: The `serverError` utility in `src/app/api/booking/route.ts` provides a generic catch-all for errors. While this is acceptable for public responses, the internal logging could be more granular. For instance, specific `console.warn` calls are used for WhatsApp/email failures, but other potential issues within the Drizzle transaction (e.g., a failure during client upsert that isn't a `SLOT_TAKEN` or `40001` error) might be less clearly identified in logs. Adding more specific logging points or custom error types within the transaction could provide better insights into the root cause of failures without changing the user-facing error message.
