# Booking Flow

The customer booking flow is a core interaction within Odys, enabling clients to discover professionals, check their availability, and schedule appointments. This process is designed to be intuitive for the client while handling complex logic on the backend, including availability checks, conflict resolution, and various notification pathways.

## Overview

The booking journey begins when a customer navigates to a professional's public profile page, typically at a URL like `/p/[slug]`. This page, rendered by `src/app/p/[slug]/page.tsx`, serves as the entry point, displaying the professional's details and embedding the interactive `BookingWidget`.

The `BookingWidget`, a client-side component, orchestrates the user's interaction. It first allows the customer to select a date using a calendar. Upon date selection, it fetches available time slots from the `/api/booking` API route via a `GET` request. Once a slot is chosen, the customer proceeds to a form to enter their personal details. Finally, a `POST` request to the same `/api/booking` endpoint attempts to finalize the appointment. The backend handles critical steps such as validating the request, checking for overlapping appointments, applying rate limits, and managing plan-based restrictions before persisting the booking and triggering appropriate notifications.

## Professional Profile Page

The `src/app/p/[slug]/page.tsx` file is a Next.js Server Component responsible for rendering a professional's public profile. It fetches comprehensive details about the professional using their unique `slug` from the `professionals` table. This includes their `name`, `profession`, `sessionDuration`, `sessionPrice`, `bio`, and `avatarUrl`. The page also retrieves associated `reviews` from the `reviews` table, joining with `clients` to display client names alongside their feedback.

A key aspect of this page is its dynamic nature based on the viewer's authentication status. It uses `createClient()` from `@/lib/supabase/server` to determine if the visitor is logged in and, if so, whether they are the professional themselves (`isOwner`) or a registered client. For logged-in clients, their existing `name`, `phone`, and `email` from the `clients` table are pre-filled into the booking form, streamlining the process.

The `BookingWidget` component is then rendered, passing essential professional data as props, such as `slug`, `professionalName`, `sessionDuration`, `sessionPrice`, `paymentType`, `paymentPercentage`, `pixKeyType`, and `pixKey`. This ensures the client-side widget has all the necessary information to function without additional server roundtrips for static professional data.

## Slot Selection

Within the `BookingWidget` (`src/app/p/[slug]/booking-widget.tsx`), the customer first interacts with a calendar to choose a desired date. The calendar disables past dates using `isBefore(date, startOfDay(new Date()))`, preventing bookings for already elapsed times.

When a date is selected, the widget initiates a `GET` request to `/api/booking`, passing the `slug` of the professional and the chosen `date`. This API route is designed to return the professional's `availability` rules and any `existingAppointments` for that specific day. Crucially, the `GET` endpoint for `/api/booking` has been carefully scoped to only return `id` and `sessionDuration` from the `professionals` table, preventing the accidental exposure of sensitive professional data like `email`, `phone`, or `userId` to unauthenticated visitors.

The `generateSlots` function, located in `src/lib/slots.ts`, then takes these rules and existing appointments to compute the actual bookable time slots. It iterates through the professional's defined `startTime` and `endTime` for the selected `dayOfWeek`, creating potential slots based on the `sessionDuration`. For each potential slot, it checks for conflicts against `existingAppointments` where the status is not `rejected` or `cancelled`. Slots that fall in the past or overlap with existing bookings are filtered out. The remaining available slots are then grouped into "Manhã", "Tarde", and "Noite" for better presentation in the UI.

## Booking Submission

Once a client selects a time slot and fills out their contact information in the `BookingWidget`, the data is submitted via a `POST` request to `/api/booking`. This endpoint is protected by a rate limit, `getBookingLimiter()`, which restricts requests to 5 attempts per IP address every 10 minutes, mitigating brute-force attacks or excessive spam.

The incoming request body is validated using `bookingSchema` from `zod`, ensuring that `slug`, `startsAt`, `clientName`, and `clientPhone` are present and correctly formatted. An optional `clientEmail` is also validated. A "honeypot" field named `website` is included in the form; if this hidden field is populated by a bot, the server silently drops the submission and returns a fake success response, preventing database interaction while appearing successful to the bot.

To further obscure timing attacks, the `POST` endpoint implements a response-time floor. The server waits for a minimum of 250ms before responding, regardless of how quickly the database operations complete. This helps to prevent attackers from distinguishing between "known client" (faster SELECT) and "new client" (slower SELECT + INSERT) scenarios by timing the response.

Before creating the appointment, the system checks the professional's subscription `plan` and `trialEndsAt` date using `effectivePlan` from `@/lib/plan-guard`. It verifies if the professional has reached their `clients` limit or `appointmentsPerMonth` limit, returning a `403` status if a limit is exceeded for a new client or a new appointment.

The core of the booking logic resides within a Drizzle `db.transaction` with an `isolationLevel: "serializable"`. This is a critical design choice to prevent race conditions. Previously, conflict checks and insertions were separate, allowing two simultaneous booking requests for the same slot to potentially both pass the check and then both insert, leading to double bookings. By wrapping these operations in a serializable transaction, the database guarantees that concurrent transactions are executed as if they were run sequentially. If a conflict is detected (either an explicit `SLOT_TAKEN` error or a `40001` SQLSTATE from Postgres), the transaction is rolled back, and the client receives a `409 Conflict` error, informing them the slot was just taken.

Within this transaction:
1.  An overlap check is performed against the `appointments` table for the `professionalId` and the proposed `startsAt` and `endsAt` times, excluding `rejected` or `cancelled` appointments.
2.  The client is upserted into the `clients` table. It first attempts to find an existing client for the professional using `clientPhone` or `clientEmail`. If found, the client's `email` is updated if it was previously null. If no client is found, a new `client` record is inserted.
3.  Finally, the new appointment is inserted into the `appointments` table with a `status` of `confirmed` if `professional.autoConfirm` is true, or `pending_confirmation` otherwise. The `paymentStatus` is initially set to `none`.

## Confirmation and Notifications

After a successful booking, the system dispatches various notifications:

*   **Notifications Table**: A new entry is added to the `notifications` table for the professional, indicating a `booking_confirmed` or `booking_request` depending on the `autoConfirm` setting.
*   **WhatsApp Messages**:
    *   If `autoConfirm` is true, the client receives a `msgBookingConfirmed` message, and the professional receives a `msgBookingConfirmedReceipt`.
    *   If `autoConfirm` is false, the professional receives a `msgBookingRequest` message, prompting them to confirm or reject the booking from their dashboard.
*   **Email**: If the professional has an `email` configured, an email notification is sent to them via `sendBookingRequestEmailToProfessional`.
*   **Analytics**: Posthog events (`booking_created` on the client, `booking_received_server` and `first_booking_at` on the server) are captured to track booking volume and professional engagement.

The `BookingWidget` then transitions to a "success" step, displaying a message indicating the booking request has been sent and is awaiting professional approval. If the `paymentType` is not "after" and a `pixKey` is available, a `PixQR` component is shown for immediate payment. For unauthenticated clients, a prompt to `Criar conta grátis` is displayed, with pre-filled registration data from their booking submission.

The `/api/appointments/[id]` `PATCH` route handles subsequent actions on an appointment, such as `confirm`, `reject`, `cancel`, `paid`, `complete`, or `no_show`. This route is also rate-limited by `getApiLimiter()` and requires authentication. It ensures that only the professional or the client (for cancellation) can perform these actions. Unknown actions are explicitly rejected by returning a `400` status with an "Unknown action" error; this check is placed after ownership computation so an unauthorized caller receives a `403` first. Each action triggers specific WhatsApp messages and, in some cases, email notifications to keep both parties informed of status changes.

If `action === "confirm"`, the client receives `msgBookingConfirmed` (with an appended `msgRegistrationInvite` if they are not a registered user) and the professional receives `msgBookingConfirmedReceipt`.

## Design decisions

1.  **Atomic Booking Transaction**: The decision to wrap the conflict check, client upsert, and appointment insertion in a `db.transaction` with `isolationLevel: "serializable"` in `src/app/api/booking/route.ts` is a critical choice for data integrity. This prevents race conditions where two users might attempt to book the same slot simultaneously. Without this, both could pass an initial availability check and then both insert, leading to an overbooked slot. The serializable isolation level forces the database to ensure that the outcome is the same as if transactions were run one after another, effectively preventing "phantom reads" that could lead to conflicts. The trade-off is a slight increase in transaction overhead and the need to handle `409 Conflict` errors gracefully on the client side.

2.  **Honeypot Field for Spam Prevention**: The `website` field in `bookingSchema` (`src/app/api/booking/route.ts` and `src/app/p/[slug]/booking-widget.tsx`) is a simple yet effective anti-spam measure. The server's response of a fake success (`NextResponse.json({ success: true })`) for honeypot submissions, and for all successful bookings, is a clever way to deter bots and obscure timing attacks by not including appointment details. This avoids the complexity and potential false positives of more advanced CAPTCHA systems.

3.  **Response-Time Floor**: The implementation of a minimum 250ms response time in the `POST /api/booking` handler is a deliberate choice to mitigate timing attacks. Without it, an attacker could potentially distinguish between existing clients and new clients by observing subtle differences in response times (e.g., a faster response if a client record already exists, as it avoids an `INSERT` operation). By normalizing the response time, this side-channel information is obscured, enhancing privacy for client data. The trade-off is a slightly slower perceived response for some legitimate requests, though 250ms is generally imperceptible to human users.

4.  **Scoped Data Fetching for Availability**: The `GET /api/booking` route explicitly selects only `id` and `sessionDuration` from the `professionals` table. This is a significant improvement over a `SELECT *` approach, which would have exposed sensitive professional data (like `email`, `phone`, `userId`, `plan`, `trialEndsAt`, `stripeCustomerId`, `stripeSubscriptionId`) to any unauthenticated visitor. This adheres to the principle of least privilege, ensuring that only the data strictly necessary for calculating available slots is exposed, minimizing potential data leakage.

## Potential improvements

1.  **Refine `generateSlots` for Edge Cases**: The `generateSlots` function in `src/lib/slots.ts` currently checks `isAfter(current, now)` to skip past slots. This is good for preventing bookings in the absolute past. However, it might not account for a professional's "preparation time" or "buffer time" between appointments, or if a slot is technically available but too close to the current time to be realistically booked (e.g., a slot starting in the next 5 minutes). An improvement could be to introduce a configurable buffer, perhaps `minBookingLeadTimeMinutes`, to `generateSlots` that ensures slots are only offered if they are, for example, at least 30 minutes in the future.

2.  **Centralize Client Upsert Logic**: The client upsert logic in `src/app/api/booking/route.ts` is currently embedded directly within the `POST` handler's transaction. While functional, this logic (`select` by phone/email, then `insert` or `update`) could be extracted into a dedicated utility function or service. This would improve readability, make the logic reusable if other parts of the application need to create or update clients, and simplify testing. For example, a function like `upsertClientForProfessional(tx, professionalId, clientName, clientPhone, clientEmail)` could encapsulate this.

3.  **Enhance Error Handling for WhatsApp/Email Notifications**: The `sendWhatsApp` and `sendBookingRequestEmailToProfessional` calls in `src/app/api/booking/route.ts` and `src/app/api/appointments/[id]/route.ts` currently use `.catch(console.warn)`. While this prevents the main booking transaction from failing due to a notification error, it only logs a warning. For critical notifications, a more robust error handling strategy might be beneficial. This could involve:
    *   Retrying failed notifications with a backoff strategy.
    *   Storing failed notifications in a dedicated queue or table for later processing or manual review.
    *   Alerting administrators for persistent notification failures.
    This would ensure higher reliability for communication with clients and professionals, which is crucial for a booking system.
