# Booking Flow

The booking flow is a core customer journey within Odys, enabling clients to discover professionals, view their availability, and schedule appointments. This process spans multiple components, from the public-facing professional page to backend API endpoints responsible for validating and persisting bookings, and finally, notifying all parties involved.

## Overview

The customer booking flow begins when a client navigates to a professional's public profile page, typically at `/p/[slug]`. This page, rendered by `src/app/p/[slug]/page.tsx`, serves as the entry point, displaying the professional's details, reviews, and an interactive booking widget.

The booking widget, implemented in `src/app/p/[slug]/booking-widget.tsx`, is a client-side component that orchestrates the slot selection process. It communicates with the `/api/booking` API route to fetch available time slots for a given date. Once a slot is selected and client details are provided, the widget dispatches a `POST` request to the same `/api/booking` endpoint.

The backend logic for booking, residing in `src/app/api/booking/route.ts`, handles several critical steps:
1.  **Rate Limiting**: Protects against abuse using `getBookingLimiter`.
2.  **Input Validation**: Ensures data integrity with `bookingSchema` (Zod).
3.  **Bot Detection**: Employs a honeypot field to filter out automated submissions.
4.  **Professional Lookup**: Retrieves the `professionals` record based on the provided `slug`.
5.  **Plan Limit Checks**: Verifies if the professional's current plan (`PLANS`) allows for new `clients` or `appointments` within the month.
6.  **Atomic Transaction**: Crucially, a serializable database transaction is used to prevent race conditions, ensuring that a selected slot is still available before a new `appointments` record is created. This transaction also handles upserting the `clients` record.
7.  **Notifications**: After a successful booking, various notifications are dispatched via WhatsApp (`sendWhatsApp`), email (`sendBookingRequestEmailToProfessional`), and in-app notifications (`notifications` table insert).
8.  **Analytics**: Events are captured using `capture` and `setOnce` for tracking booking activity.

Finally, the system also provides an API route at `/api/appointments/[id]` for professionals to manage the status of these bookings (e.g., confirm, reject, cancel, mark as paid, complete, or no-show), triggering further notifications as needed.

## Professional Profile Page

The public professional profile page, located at `src/app/p/[slug]/page.tsx`, is a Next.js Server Component responsible for rendering a comprehensive view of a professional. It fetches data directly from the database to display:
*   **Professional Details**: Information from the `professionals` table, including `name`, `profession`, `bio`, `avatarUrl`, `sessionDuration`, `sessionPrice`, `paymentType`, `paymentPercentage`, `pixKeyType`, `pixKey`, `welcomeMessage`, and location details.
*   **Reviews**: Aggregated `reviews` for the professional, joining with the `clients` table to display client names. The page calculates `totalReviews` and `avgRating`.
*   **Related Professionals**: A selection of other `professionals` in the same `profession`, fetched to offer alternatives to the client.
*   **Client Data Pre-fill**: If a logged-in user (who is not the professional themselves) visits the page, their existing `clients` data (name, phone, email) is fetched to pre-populate the booking form, enhancing user experience.

The page also includes navigation elements, a `ThemeToggle`, and conditional UI for owners versus regular users, such as a "My dashboard" link for the professional.

## Slot Selection and Availability

The interactive part of the booking process is handled by the `BookingWidget` client component in `src/app/p/[slug]/booking-widget.tsx`. This widget presents a calendar for date selection and then dynamically loads available time slots.

When a client selects a date on the calendar, the `useEffect` hook in `BookingWidget` triggers a `GET` request to `/api/booking`. This API endpoint, `src/app/api/booking/route.ts`, retrieves two crucial pieces of information:
1.  **Availability Rules**: From the `availability` table, it fetches the `dayOfWeek`, `startTime`, and `endTime` rules defined by the professional. To prevent data leakage, only `id` and `sessionDuration` are selected from the `professionals` table.
2.  **Existing Appointments**: It queries the `appointments` table for the selected day, filtering out `rejected` or `cancelled` appointments, to identify already booked slots.

The `generateSlots` utility function in `src/lib/slots.ts` then takes these rules and existing appointments, along with the professional's `sessionDuration`, to compute a list of truly available time slots. It iterates through potential slots within the professional's defined working hours, checking for conflicts with existing bookings and ensuring slots are in the future. These slots are then grouped into "Morning", "Afternoon", and "Evening" for better presentation in the UI.

## Booking Submission and Conflict Resolution

Once a client selects a slot and fills out their contact information, the `BookingWidget` sends a `POST` request to `src/app/api/booking/route.ts`. This endpoint is designed with several layers of protection and data integrity:

*   **Rate Limiting**: The `getBookingLimiter()` from `src/lib/ratelimit.ts` restricts booking attempts to 5 per IP address every 10 minutes, mitigating brute-force attacks or spam.
*   **Honeypot**: A hidden `website` field in the `bookingSchema` acts as a honeypot. If a bot populates this field, the request is silently dropped, returning a fake success response to deter further attempts without engaging the database.
*   **Plan Limits**: Before creating a booking, the system checks the professional's `plan` (e.g., `basic`, `pro`, `premium`) against defined `PLANS` limits. It queries the `clients` table to count existing clients and the `appointments` table for monthly appointment counts. If limits are exceeded for a new client or monthly appointments, the booking is rejected with a `403` status.
*   **Atomic Transaction**: The most critical part of the booking submission is the use of a `db.transaction({ isolationLevel: "serializable" })`. This ensures that the entire operation—checking for slot conflicts, upserting client data, and inserting the new appointment—is treated as a single, indivisible unit.
    *   **Conflict Check**: Inside the transaction, the system re-checks for any overlapping `appointments` that are not `rejected` or `cancelled`. If a conflict is found (e.g., another client booked the same slot milliseconds earlier), the transaction is rolled back, and a `SLOT_TAKEN` error is thrown, resulting in a `409` (Conflict) response.
    *   **Client Upsert**: The system attempts to find an existing client by `phone` or `email` for the given `professionalId`. If found, the client's `email` is updated if it was previously null. If no client is found, a new record is inserted into the `clients` table.
    *   **Appointment Insert**: Finally, a new record is inserted into the `appointments` table with the `professionalId`, `clientId`, `startsAt`, `endsAt`, and an initial `status` (either `confirmed` if `professional.autoConfirm` is true, or `pending_confirmation`).
*   **Response-Time Floor**: To prevent timing attacks that could distinguish between existing and new clients, the `respondAfterFloor` utility ensures that all `POST` responses take at least 250ms. This blunts any timing oracle that might arise from faster database operations for existing records.

## Post-Booking Notifications and Management

Upon successful booking, the system dispatches a series of notifications:
*   **In-App Notifications**: A new record is inserted into the `notifications` table for the professional, informing them of a `booking_confirmed` or `booking_request`.
*   **WhatsApp Messages**: `sendWhatsApp` is used to send messages to both the client and the professional. The content varies based on whether the booking was `autoConfirm`ed or is `pending_confirmation`, using templates like `msgBookingConfirmed`, `msgBookingConfirmedReceipt`, or `msgBookingRequest`.
*   **Email Notifications**: If the professional has an `email` configured, `sendBookingRequestEmailToProfessional` is used to send an email notification.

For managing appointments after they are created, the `src/app/api/appointments/[id]/route.ts` API route handles `PATCH` requests. This route allows both professionals and clients (with appropriate authorization checks via `getUser`) to perform actions such as:
*   `cancel`: Allows either party to cancel a `pending_confirmation` or `confirmed` appointment.
*   `confirm`, `reject`: Professional-only actions to change the `status` of a `pending_confirmation` appointment.
*   `paid`, `complete`, `no_show`: Professional-only actions to update `paymentStatus` or `status` after the appointment.

Each of these actions triggers specific WhatsApp and email notifications to keep both the client and professional informed.

## Design decisions

The booking flow incorporates several key design decisions to ensure data integrity, prevent abuse, and provide a smooth user experience:

*   **Atomic Transaction for Booking**: The decision to wrap the conflict check, client upsert, and appointment insertion in a `db.transaction({ isolationLevel: "serializable" })` in `src/app/api/booking/route.ts` is fundamental. This choice directly addresses the classic "double-booking" problem in concurrent systems. Without it, two simultaneous requests could both pass a `SELECT` check for availability and then both proceed to `INSERT` an appointment for the same slot, leading to an invalid state. The `serializable` isolation level forces the database to re-evaluate the read set if any concurrent writes occur, ensuring that only one booking for a given slot succeeds. While `serializable` transactions can introduce higher contention, for a critical operation like booking, the correctness guarantee outweighs the potential for increased retries.
*   **Honeypot and Response-Time Floor**: The inclusion of a `website` honeypot field and the `respondAfterFloor` utility in `src/app/api/booking/route.ts` are deliberate measures against bots and timing attacks. The honeypot is a simple yet effective way to filter out unsophisticated spam bots without requiring complex CAPTCHAs. The response-time floor, by artificially delaying responses to a minimum of 250ms, mitigates the risk of an attacker using subtle timing differences (e.g., faster response for an existing client record vs. a new one) to infer information about the database. This adds a small, imperceptible delay for legitimate users but significantly reduces the value of timing as an attack vector.
*   **Selective Column Fetching**: In the `GET` request for `/api/booking/route.ts`, the system explicitly selects only `id` and `sessionDuration` from the `professionals` table. This is a crucial security and privacy decision. The previous version returned `SELECT *`, which could have exposed sensitive professional data like `email`, `phone`, `userId`, `plan`, `trialEndsAt`, `stripeCustomerId`, and `stripeSubscriptionId` to any unauthenticated visitor. By limiting the columns, the system adheres to the principle of least privilege, only exposing data strictly necessary for the client-side slot generation.
*   **Client-Side Slot Generation with Server-Side Validation**: The `BookingWidget` uses `generateSlots` in `src/lib/slots.ts` to display available times, but the final booking `POST` request performs a rigorous server-side conflict check within a transaction. This separation allows for a responsive UI experience (client-side calculation) while maintaining the ultimate source of truth and integrity on the server. It prevents clients from bypassing validation or exploiting client-side logic.

## Potential improvements

1.  **Granular Availability Management**: The `availability` table currently defines `startTime` and `endTime` as `text` for each `dayOfWeek`. This structure is simple but limits the ability to define more complex availability patterns, such as breaks within a day, specific dates of unavailability (holidays, vacations), or varying session durations for different services. Consider introducing a separate `unavailability` table or enhancing the `availability` schema to support date ranges and specific time blocks, allowing professionals more flexibility in managing their schedules beyond fixed daily rules.
2.  **Refined Client Upsert Logic**: In `src/app/api/booking/route.ts` (POST handler), the client upsert logic attempts to find an existing client by `phone` OR `email`. While this can be convenient, it might lead to unintended merging of client identities if, for example, two distinct clients share a phone number (e.g., a family phone) or if a client uses different emails for different bookings. Review whether the `or(...clientConditions)` clause is the desired behavior, or if a stricter matching (e.g., `phone` AND `email` for existing users, or a unique identifier) is more appropriate to prevent accidental data merging.
3.  **Enhanced Error Feedback in Booking Widget**: The `BookingWidget` in `src/app/p/[slug]/booking-widget.tsx` currently uses a generic `toast.error("Erro ao realizar agendamento. Tente novamente.")` for any `!res.ok` response from the `/api/booking` POST endpoint. The backend, however, provides more specific error messages, such as "Este horário acabou de ser preenchido por outra pessoa" (status `409`) or "Limite de clientes atingido" (status `403`). The client-side widget could parse these specific error messages from the API response body and display them to the user, providing clearer and more actionable feedback than a generic error.
