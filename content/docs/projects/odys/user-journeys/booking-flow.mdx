# Customer Booking Flow

The customer booking flow is a core interaction within Odys, enabling clients to discover professionals and schedule appointments. This document details the journey from a customer landing on a professional's public profile to successfully booking a session, covering the underlying data interactions, validation, and notification mechanisms.

## Overview

The booking process is orchestrated across several key components: a public-facing professional profile page, a client-side booking widget, and a server-side API endpoint. The database schema, particularly the `professionals`, `availability`, `clients`, and `appointments` tables, forms the backbone of this flow.

When a customer visits a professional's unique URL, the `src/app/p/[slug]/page.tsx` component fetches the professional's details. This page then renders the `BookingWidget`, a client-side component responsible for guiding the user through date and time selection. The widget interacts with the `/api/booking` route to fetch available slots and submit the final booking request. Upon successful submission, the system performs several critical operations, including conflict checks, client management, appointment creation, and sending out various notifications.

## Professional Profile and Initial Load

The journey begins when a customer navigates to a professional's public profile, identified by a unique `slug` (e.g., `/p/dr-ana-silva`). The `src/app/p/[slug]/page.tsx` server component is responsible for rendering this page.

Upon receiving a request, this component queries the `professionals` table using the provided `slug` to retrieve the professional's public details. It also checks if the professional is `active`. If the professional is not found or inactive, the `notFound()` helper from Next.js is invoked, returning a 404 page.

For logged-in users, the system attempts to pre-fill the booking form. It uses `createClient()` from `@/lib/supabase/server` to get the current user's session. If a user is logged in and is not the owner of the professional page (`isOwner`), the system queries the `clients` table to fetch their `name`, `phone`, and `email` based on their `userId`. This data is then passed to the `BookingWidget` as `defaultName`, `defaultPhone`, and `defaultEmail`, enhancing user experience by reducing manual input.

The page also fetches related professionals from the `professionals` table based on the current professional's `profession`, and retrieves `reviews` for the current professional by joining `reviews` with `clients` to display client names. This rich context helps customers make informed decisions.

## Slot Selection

The interactive part of the booking flow is handled by the `BookingWidget` component, located in `src/app/p/[slug]/booking-widget.tsx`. This is a client-side component, indicated by `"use client"`, allowing for dynamic date and time selection.

1.  **Date Selection**: The customer first selects a date using the `Calendar` component. The calendar disables past dates using `isBefore(date, startOfDay(new Date()))` to prevent bookings in the past.
2.  **Fetching Availability**: When a date is selected, an `useEffect` hook triggers a `GET` request to `/api/booking`. This request includes the professional's `slug` and the selected `date`.
    *   The `GET` handler in `src/app/api/booking/route.ts` retrieves the `professionalId` and `sessionDuration` from the `professionals` table. Crucially, it only selects these two columns, preventing the accidental leakage of sensitive professional data like `email`, `phone`, or `userId` to unauthenticated users.
    *   It then fetches two sets of data concurrently using `Promise.all`:
        *   `availability` rules for the professional, filtered by `professionalId`. These rules define the professional's general working hours for each `dayOfWeek`.
        *   `existingAppointments` for the selected day, filtered by `professionalId` and excluding `rejected` or `cancelled` appointments. This provides the occupied time slots.
    *   The API returns these `rules` and `existingAppointments` to the client.
3.  **Generating Slots**: Back on the client, the `generateSlots` function from `src/lib/slots.ts` takes the selected `date`, the `availability` rules, `existingAppointments`, and the `sessionDuration` to compute the actual available time slots. It iterates through potential start times within the professional's defined availability, checking for conflicts with existing appointments and ensuring slots are in the future. The generated slots are then grouped into "morning", "afternoon", and "evening" for better presentation.
4.  **Time Slot Selection**: The customer then selects one of the available time slots. Once both a date and a slot are chosen, a "Continuar" button becomes active, transitioning the widget to the "form" step.

## Booking Submission

After selecting a date and time, the customer proceeds to fill out their personal details in the `BookingWidget`. This form is validated client-side using Zod and `react-hook-form` with the `clientSchema`.

1.  **Honeypot**: The form includes a hidden `website` field, acting as a honeypot. This field is visually hidden and inaccessible to human users but is often filled by automated bots. If this field contains any value upon submission, the server will silently drop the request, returning a fake success response to mislead the bot without touching the database.
2.  **Rate Limiting**: Before processing the request, the `POST` handler in `src/app/api/booking/route.ts` applies rate limiting using `getBookingLimiter()` from `src/lib/ratelimit.ts`. This limits booking attempts to 5 per IP address every 10 minutes, protecting against abuse. If the limit is exceeded, a `429 Too Many Requests` response is returned.
3.  **Response-Time Floor**: To mitigate timing attacks (M2), where an attacker could distinguish between existing and new clients by timing the database operations, the server introduces a `respondAfterFloor` function. This ensures that all `POST` responses take at least 250ms, masking any subtle timing differences in database operations.
4.  **Validation**: The incoming request body is validated server-side using `bookingSchema` (a Zod schema), ensuring data integrity and rejecting malformed requests with a `400 Bad Request` status.
5.  **Professional Lookup**: The professional is retrieved from the `professionals` table using the `slug`. If not found, a `404 Not Found` is returned.
6.  **Plan Limits**: The system checks the professional's subscription plan (`professional.plan` and `professional.trialEndsAt`) using `effectivePlan` and `PLANS` to enforce limits on the number of clients and appointments per month. If a limit is exceeded, a `403 Forbidden` response is sent.
7.  **Atomic Transaction**: The core of the booking logic is wrapped in a Drizzle `db.transaction` with `isolationLevel: "serializable"`. This is a critical design choice to prevent race conditions.
    *   **Conflict Check**: Inside the transaction, the system first checks for any overlapping appointments for the professional within the proposed `startsAt` and `endsAt` timeframe, excluding `rejected` or `cancelled` appointments. If a conflict is found, it throws a `SLOT_TAKEN` error, which is caught and translated into a `409 Conflict` response. The `serializable` isolation level ensures that if two concurrent requests try to book the same slot, one will fail due to a phantom read detection by Postgres.
    *   **Client Upsert**: The system then attempts to find an existing client for the professional based on `clientPhone` or `clientEmail`. If a client is found, their `email` is updated if it was previously null. If no client is found, a new entry is inserted into the `clients` table. The `POST /api/booking` route does not set the `client.userId` column during client upsert or creation.
    *   **Appointment Creation**: Finally, a new appointment is inserted into the `appointments` table, linking it to the professional and the (new or existing) client. The `status` is set to `confirmed` if `professional.autoConfirm` is true, otherwise `pending_confirmation`. `paymentStatus` is initially `none`.
8.  **Notifications and Analytics**: After a successful booking (or request), the system dispatches several notifications:
    *   An in-app notification is inserted into the `notifications` table for the professional.
    *   WhatsApp messages are sent to the client (confirmation or request) and the professional (receipt or request) using templates like `msgBookingConfirmed`, `msgBookingConfirmedReceipt`, or `msgBookingRequest` from `src/lib/whatsapp`.
    *   An email notification is sent to the professional if their `email` is available, using `sendBookingRequestEmailToProfessional`.
    *   PostHog analytics events (`booking_created` client-side, `booking_received_server` server-side) are captured to track booking volume and user behavior. For the server-side `booking_received_server` event, the `distinctId` is set to `professional.id` for accurate attribution.
9.  **Success Response**: The server returns a generic `NextResponse.json({ success: true })` to the client, again after the response-time floor. This avoids leaking sensitive `clientId` information that could be used by an attacker to map phone/email pairs to existing clients.

## Confirmation and Post-Booking Experience

Upon receiving a successful response from the `POST /api/booking` endpoint, the `BookingWidget` transitions to the "success" step.

This step displays a confirmation message to the user. If the `paymentType` is not "after" and a `pixKey` is configured for the professional, a `PixQR` component is displayed, showing the amount due (calculated as `sessionPrice * (paymentPercentage / 100)`).

For clients who are not logged in, the widget offers an option to create a free account, pre-filling the registration link with their submitted `name`, `email`, and `phone`. This encourages client retention and provides them with a dashboard to manage their appointments. Logged-in clients are directed to their appointments dashboard.

## Design decisions

The booking flow incorporates several deliberate design decisions to balance user experience, data integrity, and security:

*   **Minimal Data Exposure on GET**: The `GET /api/booking` endpoint only returns `id` and `sessionDuration` for the professional. This prevents sensitive information like `email`, `phone`, or `userId` from being publicly accessible, even though the `professionals` table contains 32 columns. The `BookingWidget` receives other necessary professional details (like `sessionPrice`, `paymentType`, `pixKey`) directly as props from the server-rendered `page.tsx`, which has authenticated access to the full professional object.
*   **Atomic Transaction for Booking**: The use of a Drizzle `transaction` with `isolationLevel: "serializable"` for the `POST /api/booking` route is a critical choice. It ensures that the conflict check, client upsert, and appointment insertion happen as a single, indivisible operation. This prevents race conditions where two users might simultaneously attempt to book the same slot, guaranteeing that only one succeeds and maintaining data consistency. Without this, a simple `SELECT` followed by an `INSERT` could lead to double bookings.
*   **Honeypot for Spam Prevention**: The `website` field in the `bookingSchema` and the `BookingWidget` is a simple yet effective measure against automated spam bots. By silently dropping submissions that fill this hidden field, the system reduces noise without requiring complex CAPTCHAs or user friction. Returning a `200 OK` with `success: true` further ensures bots don't learn the trap.
*   **Response-Time Floor**: The `respondAfterFloor` function in the `POST /api/booking` handler is a subtle but important security measure. It helps prevent timing oracle attacks, where an attacker could infer information (e.g., whether a client already exists) by measuring minute differences in response times between different database operations. By normalizing the response time, this signal is effectively blunted.
*   **Rate Limiting**: Implementing `getBookingLimiter()` from `@upstash/ratelimit` directly in the `POST /api/booking` route protects the endpoint from brute-force attacks and excessive requests, ensuring system stability and fair usage.
*   **Client Upsert Logic**: The booking flow intelligently handles client data. If a client with the given phone or email already exists for the professional, their record is updated (e.g., adding a missing email). Otherwise, a new client record is created. This prevents duplicate client entries and streamlines the booking process for returning customers.
*   **Comprehensive Notification System**: The system integrates multiple notification channels (in-app, WhatsApp, email) to keep both clients and professionals informed about booking status changes. This multi-channel approach increases the likelihood of messages being received and acted upon.

## Potential improvements

1.  **Refine Client Upsert Logic for `userId`**: The `clients` table has a nullable `userId` column. Currently, the `POST /api/booking` route does not set the `client.userId` column during client upsert or creation. If a client books as a guest and then registers later, their `clients.userId` might remain `null`, leading to a disconnected experience. The system could be improved by:
    *   When a user registers, check if any existing `clients` records match their `phone` or `email` and update `clients.userId` accordingly. This would link guest bookings to registered accounts.
    *   Alternatively, when a client logs in, check for existing `clients` records without a `userId` that match their `phone` or `email` and associate them.
    *   This would require modifications in the registration flow (e.g., `/api/auth/register`) or a dedicated client profile update mechanism.

2.  **Optimize Slot Generation for Performance**: The `generateSlots` function in `src/lib/slots.ts` iterates minute by minute (`addMinutes(current, sessionDuration)`) to find available slots. While functional, for professionals with very long `sessionDuration` values or complex `availability` rules spanning many hours, this iterative approach could be computationally intensive.
    *   Consider an interval-based approach where available time blocks are calculated by subtracting occupied `existingAppointments` from `availability` rules. This would involve working with time ranges rather than discrete minute-by-minute checks, potentially reducing the number of iterations, especially for sparse schedules.

3.  **Enhance Honeypot Feedback for Bots**: The current honeypot implementation in `POST /api/booking` returns a generic `NextResponse.json({ success: true })` if the `website` field is populated. While effective at silently dropping spam, a more sophisticated bot might eventually learn that this specific response indicates a honeypot.
    *   To make it harder for bots to detect the honeypot, the response could be varied slightly, perhaps by returning a `200 OK` with a slightly different (but still non-revealing) JSON structure, or by introducing a small, random delay before responding, making it indistinguishable from a legitimate, slow request. This would require modifying the `respondAfterFloor` function to allow for more flexible "fake" success responses.
