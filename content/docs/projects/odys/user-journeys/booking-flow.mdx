# Booking Flow

The customer booking flow is a central interaction within Odys, enabling clients to discover professionals, view their availability, and schedule appointments. This process spans multiple components, from the public-facing professional profile page to backend API endpoints responsible for validating and persisting bookings. It involves careful coordination between client-side UI for slot selection and server-side logic for conflict resolution, rate limiting, and notification delivery.

## Overview

The booking journey begins on a professional's public profile page, rendered by `src/app/p/[slug]/page.tsx`. This page displays the professional's details and embeds the interactive `BookingWidget` component. The widget guides the user through selecting a date and time slot, then collecting client information.

When a client selects a date, the `BookingWidget` makes a `GET` request to `/api/booking` to fetch the professional's availability rules and existing appointments for that specific day. This data is then processed client-side by `src/lib/slots.ts` to generate a list of available time slots.

Upon selecting a slot and providing their details, the client submits a `POST` request to the same `/api/booking` endpoint. This server-side handler is responsible for a series of critical steps: validating the input, applying rate limits, checking the professional's plan limits, performing an atomic conflict check to prevent double-bookings, upserting client data, and finally, creating the appointment. Post-booking, the system dispatches various notifications via WhatsApp and email and records analytics events.

## Professional Profile Page

The `src/app/p/[slug]/page.tsx` file serves as the entry point for clients to discover and book with a professional. This Next.js server component dynamically fetches professional details based on the `slug` parameter. It queries the `professionals` table to retrieve information such as `name`, `profession`, `sessionDuration`, `sessionPrice`, `bio`, and `avatarUrl`. If the professional is not found or is marked as `active: false`, the page returns a `notFound()` response.

The page also performs checks to determine if the visitor is the professional themselves (`isOwner`) or a logged-in client. If a logged-in client is visiting, their existing `name`, `phone`, and `email` are fetched from the `clients` table to pre-fill the booking form, enhancing user experience.

Beyond the professional's core information, the page displays aggregated `reviews` by joining the `reviews` and `clients` tables, calculating an `avgRating` and `totalReviews`. It also suggests `related` professionals by querying others with the same `profession`, providing additional options for the client. The `BookingWidget` is then rendered as a client component, receiving essential professional data as props to manage the interactive booking process.

## Slot Selection and Availability

The interactive part of the booking flow is handled by the `src/app/p/[slug]/booking-widget.tsx` client component. This component presents a calendar for date selection and, once a date is chosen, displays available time slots.

When a user selects a date, a `useEffect` hook triggers a `GET` request to the `/api/booking` endpoint. This request includes the professional's `slug` and the `date` string. The `GET` handler in `src/app/api/booking/route.ts` then queries the database for two key pieces of information:
1.  **Availability Rules**: It fetches the `dayOfWeek`, `startTime`, and `endTime` from the `availability` table for the specified professional. This defines when the professional is generally available.
2.  **Existing Appointments**: It retrieves `startsAt` and `endsAt` for all existing appointments for that professional on the selected day, excluding those with `status` of `"rejected"` or `"cancelled"`.

Crucially, the `GET` request for professional data only selects `id` and `sessionDuration` from the `professionals` table. This design choice prevents sensitive professional information like `email`, `phone`, or `userId` from being exposed to unauthenticated visitors, which would have been a data leakage vulnerability in previous iterations of the code.

The fetched `rules` and `existingAppointments` are then passed to the `generateSlots` utility function in `src/lib/slots.ts`. This function calculates all potential time slots for the day based on the professional's `sessionDuration` and filters out any slots that conflict with existing appointments or fall in the past. The `BookingWidget` then groups these slots into "Manhã", "Tarde", and "Noite" for a user-friendly display.

## Booking Submission

Once a client selects a slot and fills out their contact information, the `BookingWidget` sends a `POST` request to `/api/booking`. This endpoint is designed with several layers of validation and protection:

1.  **Rate Limiting**: The `getBookingLimiter()` from `src/lib/ratelimit.ts` is applied, restricting booking attempts to `5` per `10 m` per IP address, identified by the `rl:booking` prefix. This helps prevent abuse and denial-of-service attacks.
2.  **Timing Oracle Defense**: A `respondAfterFloor` function introduces a minimum `250ms` response time. This mitigates a potential timing attack where an attacker could infer whether a client (identified by phone/email) already exists for a professional by observing slight differences in response times between database `SELECT` (faster) and `INSERT` (slower) operations.
3.  **Input Validation**: The request body is validated using `bookingSchema` from `zod`. This schema ensures that `slug`, `startsAt`, `clientName`, and `clientPhone` are present and correctly formatted. `clientEmail` is optional.
4.  **Honeypot**: A hidden `website` field in the form acts as a honeypot. If a bot populates this field, the server silently drops the submission and returns a fake success response, preventing the bot from learning that the field is a trap and avoiding database writes.
5.  **Professional Lookup**: The professional's full details are fetched from the `professionals` table using the provided `slug`.
6.  **Plan Limits**: The system checks the professional's `effectivePlan` against configured `PLANS` (e.g., `basic`, `pro`, `premium`). It verifies if the professional has exceeded limits for `clients` or `appointmentsPerMonth`. If a limit is hit and the client is new, the request is rejected with a `403` status.
7.  **Atomic Transaction**: The core booking logic is wrapped in a Drizzle ORM `db.transaction` with `isolationLevel: "serializable"`. This is a critical design choice to prevent race conditions:
    *   **Conflict Check**: Before creating a new appointment, the transaction checks for any existing appointments that would overlap with the proposed `startsAt` and `endsAt` times, excluding `rejected` or `cancelled` appointments. If a conflict is detected, it throws a `"SLOT_TAKEN"` error.
    *   **Client Upsert**: The system attempts to find an existing client for the professional using `clientPhone` or `clientEmail`. If found, it updates the client's email if it was previously null. If no client is found, a new entry is inserted into the `clients` table.
    *   **Appointment Insertion**: Finally, a new appointment is inserted into the `appointments` table. The `status` is set to `"confirmed"` if `professional.autoConfirm` is true, otherwise `"pending_confirmation"`. The `paymentStatus` defaults to `"none"`.
    If the transaction fails due to a `SLOT_TAKEN` error or a `40001` SQLSTATE (serialization failure due to concurrent writes), the client receives a `409` conflict response.

## Confirmation and Notifications

After a successful booking, the system dispatches various notifications and records analytics:

*   **In-App Notifications**: A new entry is inserted into the `notifications` table for the professional, informing them of a new booking request or confirmation.
*   **WhatsApp Messages**: Depending on whether the professional has `autoConfirm` enabled, different WhatsApp messages are sent:
    *   If `autoConfirm` is true, the client receives `msgBookingConfirmed` (a confirmation and receipt), and the professional receives `msgBookingConfirmedReceipt`.
    *   If `autoConfirm` is false, the professional receives `msgBookingRequest`, prompting them to confirm or reject the booking from their dashboard.
    These messages are sent via the `sendWhatsApp` utility, which uses templates like `msgBookingRequest`, `msgBookingConfirmed`, and `msgBookingConfirmedReceipt`.
*   **Email Notifications**: If the professional has an `email` configured, `sendBookingRequestEmailToProfessional` is used to send an email notification.
*   **Analytics**: Posthog events (`booking_received_server`) are captured, attributing the booking to the professional (`distinctId: professional.id`). A `first_booking_at` property is set once to track the professional's initial booking.
*   **Equalized Response**: The `POST` endpoint returns a generic `success: true` without including the newly created appointment details. This is another measure to prevent information leakage, as an attacker could otherwise infer client existence by observing the presence or absence of `clientId` in the response.

## Design decisions

*   **Atomic Transaction for Booking (`src/app/api/booking/route.ts` POST)**: The decision to wrap the conflict check, client upsert, and appointment insertion in a `serializable` transaction is fundamental. This prevents race conditions where two clients might simultaneously attempt to book the same slot. Without this, both could pass an initial availability check and then both attempt to insert, leading to double-bookings. The `serializable` isolation level ensures that concurrent transactions behave as if they were executed sequentially, correctly detecting and rejecting conflicts.
*   **Honeypot Field (`src/app/api/booking/route.ts` POST, `src/app/p/[slug]/booking-widget.tsx`)**: The `website` field serves as a simple yet effective bot mitigation strategy. Instead of complex CAPTCHAs that degrade user experience, this hidden field catches naive bots that fill all form inputs. Returning a `200 OK` with `success: true` for bot submissions is a clever way to prevent bots from learning that the field is a trap, encouraging them to continue submitting to the honeypot.
*   **Rate Limiting (`src/lib/ratelimit.ts`, `src/app/api/booking/route.ts` POST)**: Implementing `getBookingLimiter()` with a `slidingWindow(5, "10 m")` for booking requests directly addresses potential abuse. This prevents a single IP from flooding the system with booking attempts, protecting against spam and resource exhaustion.
*   **Timing Oracle Defense (`src/app/api/booking/route.ts` POST)**: The `respondAfterFloor` function, which enforces a minimum `250ms` response time, is a subtle but important security measure. It blunts timing attacks that could otherwise allow an attacker to distinguish between existing and non-existing client records by measuring minute differences in database query execution times. This makes it harder for malicious actors to enumerate client data.
*   **Minimal Data Fetching for Availability (`src/app/api/booking/route.ts` GET)**: The `GET` endpoint for availability explicitly selects only `id` and `sessionDuration` from the `professionals` table. This is a deliberate choice to prevent accidental data leakage. Previous versions might have returned `SELECT *`, exposing sensitive professional details to any unauthenticated visitor. This focused selection adheres to the principle of least privilege, only exposing data strictly necessary for slot generation.

## Potential improvements

1.  **Optimize `generateSlots` for past dates**: In `src/lib/slots.ts`, the `generateSlots` function iterates through potential slots and checks `if (isAfter(current, now))` to skip past slots. An early exit could be added at the beginning of the function to immediately return an empty array if the `date` parameter itself is in the past (e.g., `if (isBefore(endOfDay(date), now)) return []`). This would avoid unnecessary computation for entire days that are no longer bookable.
2.  **Enhance client ownership for `PATCH /api/appointments/[id]`**: The `isClient` check in `src/app/api/appointments/[id]/route.ts` relies on `client.userId === user.id`. The `clients` table allows `userId` to be `nullable: true`. If a client books anonymously (without a `userId` linked) and later logs in, their `clients.userId` might still be null. This would prevent them from performing client-specific actions like cancelling their own appointment via the UI, as `isClient` would always be false. Consider a mechanism to link anonymous bookings to a logged-in user's `userId` if their phone/email matches, or allow clients to claim past bookings.
3.  **Refine client email update logic in `POST /api/booking`**: In `src/app/api/booking/route.ts`, the logic to update a client's email (`else if (!client.email && clientEmail)`) only applies if the existing client record has a `null` email. If a client already has an email, but the new booking submission provides a *different* email, the existing email is not updated. This might be a deliberate choice to prevent accidental overwrites, but it could also lead to stale email information if a client's email changes. Evaluate if the system should allow updating an existing email, perhaps with additional verification.
