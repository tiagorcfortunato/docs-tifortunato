# Booking Flow

The booking flow is a central customer journey within Odys, enabling clients to discover professionals, select available time slots, and schedule appointments. This process involves several interconnected components, from the public-facing professional profile page to backend API routes handling data validation, conflict checking, and notification delivery.

## Overview

The journey begins when a potential client navigates to a professional's public profile page, rendered by `src/app/p/[slug]/page.tsx`. This page serves as the entry point, displaying the professional's details and embedding the interactive `BookingWidget` component. The `BookingWidget`, a client-side React component, orchestrates the date and time selection process, communicating with the backend via the `GET /api/booking` endpoint to fetch availability and existing appointments.

Once a client selects a slot and provides their details, the `BookingWidget` submits this information to the `POST /api/booking` API route. This critical backend endpoint handles data validation, enforces rate limits, checks for plan-based booking restrictions on the total number of clients and monthly appointments, and performs an atomic transaction to prevent scheduling conflicts. Upon successful booking, it manages notifications to both the client and the professional. Finally, the `PATCH /api/appointments/[id]` route allows professionals or clients to manage the status of an appointment, such as confirming, rejecting, or canceling it, triggering further notifications.

## Professional Profile and Initial Data Loading

The `src/app/p/[slug]/page.tsx` file is a Next.js Server Component responsible for rendering a professional's public booking page. When a user visits `/p/[slug]`, this component fetches all necessary professional details from the `professionals` table using Drizzle ORM. It retrieves information such as `name`, `profession`, `sessionDuration`, `sessionPrice`, `bio`, and `avatarUrl`. The `slug` parameter in the URL is used to identify the specific professional.

A key design choice here is to fetch comprehensive professional data on the server. This allows for rich metadata generation via `generateMetadata`, improving SEO by providing detailed titles and descriptions for search engines. It also pre-renders the static parts of the page, like the professional's bio and contact information, ensuring a fast initial load for the user.

The page also intelligently detects if the visitor is the professional themselves (`isOwner`) or a logged-in client. If a logged-in client is detected, their existing `name`, `phone`, and `email` are fetched from the `clients` table and passed as `defaultName`, `defaultPhone`, and `defaultEmail` props to the `BookingWidget`. This pre-fills the booking form, enhancing user experience by reducing data entry.

The page further enriches the user experience by displaying reviews, fetched by joining the `reviews` and `clients` tables, and suggesting related professionals based on `profession`.

## Slot Selection and Availability

The interactive core of the booking process resides within the `src/app/p/[slug]/booking-widget.tsx` client component. This component manages the user's selection of a date and time slot.

When a user selects a date in the calendar, a `useEffect` hook within `BookingWidget` triggers a `GET` request to `/api/booking`. This API route is designed to provide the necessary data for slot generation without exposing sensitive professional information. It queries the `professionals` table, but crucially, it only selects the `id` and `sessionDuration` columns. This prevents accidental data leakage of fields like `email`, `phone`, or `userId` to unauthenticated visitors, a significant improvement over previous iterations that might have returned all professional data.

The `GET /api/booking` endpoint then fetches two crucial sets of data:
1.  **Availability Rules**: From the `availability` table, it retrieves `dayOfWeek`, `startTime`, and `endTime` for the professional. These define the general working hours.
2.  **Existing Appointments**: From the `appointments` table, it fetches `startsAt` and `endsAt` for all appointments on the selected day, filtering out those with `rejected` or `cancelled` statuses. This ensures that only active or pending appointments are considered when checking for conflicts.

These two datasets are then passed to the `generateSlots` utility function in `src/lib/slots.ts`. This function takes the selected `date`, the `availability` rules, `existingAppointments`, and the professional's `sessionDuration` to compute all truly available time slots. It iterates through potential slots within the professional's defined working hours, checking each against existing appointments to identify and exclude any overlaps. It also filters out slots that are in the past relative to the current time. The `BookingWidget` then groups these available slots into "Morning," "Afternoon," and "Evening" categories for a more user-friendly display.

## Booking Submission and Conflict Resolution

Once a client selects a slot and fills out their contact information, the `BookingWidget` submits this data via a `POST` request to `/api/booking`. This endpoint is a critical transaction boundary, designed with several layers of protection and business logic.

First, a rate limit is applied using `getBookingLimiter` from `src/lib/ratelimit.ts`, allowing only 5 booking attempts per IP every 10 minutes. This helps mitigate spam and abuse.

A "honeypot" field, `website`, is included in the `bookingSchema` validation. This hidden field, invisible to human users but often filled by naive bots, allows the server to silently drop bot submissions without engaging in database operations, returning a fake success response to deter further attempts.

To prevent timing attacks that could reveal whether a client's phone or email already exists in the system, the `POST /api/booking` route implements a response-time floor using `respondAfterFloor`. This ensures that all responses, regardless of the underlying database operations, take at least 250ms, masking any timing differences between database lookups and inserts.

The core of the booking logic is wrapped in a Drizzle ORM database transaction with `isolationLevel: "serializable"`. This is a crucial design decision. Previously, the conflict check, client upsert, and appointment insert were separate queries. This created a race condition where two simultaneous booking requests for the same slot could both pass the conflict check before either had committed, leading to double bookings. By using a serializable transaction, the database guarantees that concurrent transactions behave as if they were executed sequentially. If a conflict is detected (e.g., another booking fills the slot during the transaction), Postgres will return a `SQLSTATE 40001` error, which is caught and translated into a `SLOT_TAKEN` error, informing the user to pick another time.

Within this transaction:
1.  **Conflict Check**: The system checks for any existing appointments that overlap with the proposed `startsAt` and `endsAt` times, excluding `rejected` or `cancelled` appointments.
2.  **Client Upsert**: It attempts to find an existing client for the professional using either the provided `clientPhone` or `clientEmail`. If found, the existing client record is used; otherwise, a new client is inserted into the `clients` table. If an existing client is found without an email but one is provided, the client's email is updated.
3.  **Appointment Insert**: A new appointment is created in the `appointments` table. Its `status` is set to `confirmed` if the professional has `autoConfirm` enabled, or `pending_confirmation` otherwise. The `paymentStatus` is initially set to `none`.

After the transaction, various notifications are dispatched:
*   A new entry is added to the `notifications` table for the professional.
*   WhatsApp messages are sent to the client (confirmation or request) and the professional (receipt or request) using templates like `msgBookingConfirmed` or `msgBookingRequest`.
*   An email notification is sent to the professional if their `email` is available.

Finally, analytics events (`booking_received_server`, `first_booking_at`) are captured using PostHog, providing insights into booking activity and professional engagement.

## Appointment Management

The `PATCH /api/appointments/[id]` API route handles changes to an appointment's status. This endpoint is secured by first authenticating the user via `getUser()` and then verifying their authorization based on whether they are the professional (`isProfessional`) or the client (`isClient`) associated with the appointment.

The route supports a predefined set of `ALLOWED_ACTIONS`: `confirm`, `reject`, `cancel`, `paid`, `complete`, and `no_show`. Any unknown action is explicitly rejected with a `400 Bad Request` status, preventing silent failures.

*   **Cancellation**: Both professionals and clients can cancel appointments, provided the current status is `pending_confirmation` or `confirmed`. The `appointments` table is updated, and appropriate WhatsApp messages are sent to both parties (e.g., `msgCancelledByClientToPro`, `msgBookingCancelled`).
*   **Professional-only Actions**: Actions like `paid`, `complete`, and `no_show` are restricted to the professional. These update the `paymentStatus` or `status` columns in the `appointments` table and trigger specific WhatsApp notifications (e.g., `msgPaymentConfirmedToClient`, `msgAppointmentCompletedToPro`).
*   **Confirmation/Rejection**: These actions are also restricted to the professional. They update the `status` and `paymentStatus` of the appointment. Notifications are sent to the client via the `notifications` table, WhatsApp (e.g., `msgBookingConfirmed`, `msgBookingRejected`), and email (`sendBookingConfirmedEmailToClient`, `sendBookingRejectedEmailToClient`). If the client is not a registered user, the confirmation message includes an invitation to register.

## Design decisions

*   **Server-Side Rendering for Initial Load**: The `src/app/p/[slug]/page.tsx` is a Server Component, which means the initial HTML for the professional's profile is rendered on the server. This improves perceived performance and SEO, as search engines can easily crawl the content. The interactive `BookingWidget` is then hydrated on the client.
*   **Minimal Data Exposure in `GET /api/booking`**: The `GET /api/booking` endpoint explicitly selects only `id` and `sessionDuration` from the `professionals` table. This is a deliberate security measure to prevent sensitive professional data (like `email`, `phone`, `userId`, `plan`, `trialEndsAt`, `stripeCustomerId`, `stripeSubscriptionId`) from being exposed to unauthenticated users, which was a vulnerability in earlier versions.
*   **Atomic Booking Transaction**: The `POST /api/booking` route uses a Drizzle ORM transaction with `isolationLevel: "serializable"`. This is a critical choice to prevent race conditions where two users might attempt to book the same slot simultaneously. The serializable isolation level ensures that concurrent transactions are executed as if they were sequential, preventing phantom reads and ensuring data integrity.
*   **Honeypot for Bot Detection**: The `website` field in the `bookingSchema` and `BookingWidget` is a simple yet effective anti-spam measure. By returning a `200 OK` with a fake success message for bot submissions, it discourages bots from learning that the field is a trap, making it more effective over time.
*   **Timing Oracle Protection**: The `respondAfterFloor` function in `POST /api/booking` adds a minimum response time. This is a security measure to obscure timing differences between database operations (e.g., a fast lookup for an existing client versus a slower insert for a new client), preventing attackers from inferring information about existing data through timing analysis.
*   **Rate Limiting**: The `getBookingLimiter` from `src/lib/ratelimit.ts` is applied to the `POST /api/booking` endpoint. This protects the API from abuse and brute-force attacks by limiting the number of requests an IP address can make within a given time window.
*   **Clear Separation of Concerns**: The `generateSlots` utility is a pure function, decoupled from database access or HTTP concerns. It focuses solely on the logic of calculating available slots based on provided rules and existing appointments, making it testable and reusable.

## Potential improvements

*   **Enhanced Error Feedback in `BookingWidget`**: The `BookingWidget.tsx` currently uses a generic `toast.error("Erro ao realizar agendamento. Tente novamente.")` for most API errors. The `POST /api/booking` endpoint, however, returns more specific `details: result.error.flatten().fieldErrors` for Zod validation failures. The client-side `onSubmit` function could be improved to parse these `details` and display more precise error messages to the user, guiding them to correct their input.
*   **Sophisticated Recurring Schedule Integration**: The `generateSlots` function in `src/lib/slots.ts` currently relies on `availability` rules, which define general daily working hours. The database schema includes a `recurringSchedules` table with fields like `frequency`, `dayOfWeek`, and `secondDayOfWeek`. Integrating these more complex recurring schedules into the slot generation logic would allow professionals to define more nuanced and flexible availability patterns, such as bi-weekly appointments or specific recurring client bookings.
*   **Comprehensive Client Data Upsert**: In `POST /api/booking`, when an existing client is found, only their `email` is updated if it was previously `null` and a new email is provided. The `name` and `phone` fields are not updated. This could lead to stale client data if a client's name or phone number changes and they book again. The upsert logic could be extended to update `name` and `phone` as well, perhaps with a flag to indicate if the client is logged in or if the professional explicitly allows client data updates.
*   **Full Payment Lifecycle Integration**: The `appointments` table includes a `stripePaymentIntentId` column, and `paymentStatus` can be `authorized` or `refunded`. However, the current booking flow primarily sets `paymentStatus` to `none` or `authorized` based on `autoConfirm`. A more complete payment integration would involve creating Stripe Payment Intents, handling pre-authorization, capture, and refund processes, and updating `stripePaymentIntentId` and `paymentStatus` throughout the appointment lifecycle. This would enable more robust payment handling directly within the booking flow.
