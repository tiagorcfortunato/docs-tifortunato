# Booking Flow

The booking flow is the core interaction for customers seeking to schedule services with professionals. It encompasses the entire journey from a customer discovering a professional's public profile to successfully requesting or confirming an appointment. This process is designed to be intuitive for the customer while providing professionals with the necessary tools to manage their schedules and client relationships.

## Overview

The booking flow is orchestrated across several key components:

*   **`src/app/p/[slug]/page.tsx`**: This Next.js Server Component renders the public profile page for a professional, identified by their unique `slug`. It fetches the professional's details, reviews, and related professionals, setting the stage for the booking experience.
*   **`src/app/p/[slug]/booking-widget.tsx`**: A Client Component embedded within the professional's page, this widget handles the interactive elements of the booking process, including date and time selection, and client information submission.
*   **`src/app/api/booking/route.ts`**: This API route serves two primary functions:
    *   **GET requests**: Provide the `BookingWidget` with the professional's availability rules and existing appointments for a given date, enabling the client-side generation of available time slots.
    *   **POST requests**: Process new booking submissions, performing validation, conflict checks, client upserts, and initiating notifications.
*   **`src/lib/slots.ts`**: A utility function that takes availability rules and existing appointments to compute the actual bookable time slots for a specific day.

The database schema plays a central role, with the `professionals` table storing core professional data, `availability` defining their working hours, `appointments` tracking scheduled sessions, and `clients` managing customer information. The `notifications` table is used to alert professionals about new booking requests.

## Professional Profile Page

The journey begins when a customer navigates to a professional's public profile, rendered by `src/app/p/[slug]/page.tsx`. This page is a Next.js Server Component, meaning it fetches data directly on the server before rendering, which benefits SEO and initial page load performance.

Upon loading, the page queries the `professionals` table using the `slug` from the URL to retrieve the professional's details. If the professional is not found or is inactive, the `notFound()` helper from Next.js is invoked. The page also checks if the logged-in user is the owner of the profile (`isOwner`), which subtly alters the navigation links and displays an informational banner.

For logged-in users who are not the professional, the system attempts to pre-fill the booking form with their existing client data by querying the `clients` table using their `userId`. This enhances user experience by reducing data entry.

The page further enriches the professional's profile by fetching:
*   Related professionals from the `professionals` table based on the same `profession`.
*   Reviews from the `reviews` table, joining with `clients` to display client names, and calculates an average rating and total review count.

All this information is then presented to the user, including the professional's name, profession, session duration, price, bio, welcome message, and location details via the `ProfessionalLocationCard`.

## Slot Selection

The interactive part of the booking process is handled by the `BookingWidget` component in `src/app/p/[slug]/booking-widget.tsx`. This is a Client Component, allowing for dynamic interactions like date selection and real-time slot updates without full page reloads.

When a customer selects a date on the calendar, the `useEffect` hook within `BookingWidget` triggers a `GET` request to `/api/booking`. This request includes the professional's `slug` and the `date` selected.

The `GET` handler in `src/app/api/booking/route.ts` then performs two crucial database queries in parallel using `Promise.all`:
1.  It fetches the professional's `availability` rules for the given `professionalId`. These rules specify the `dayOfWeek`, `startTime`, and `endTime` for when the professional is generally available.
2.  It retrieves `existingAppointments` for that professional on the selected date, filtering out `rejected` or `cancelled` appointments. Importantly, this query only selects `startsAt` and `endsAt` to avoid leaking sensitive appointment details.

The results of these queries (`rules` and `existingAppointments`) are then passed to the `generateSlots` utility function in `src/lib/slots.ts`. This function takes the professional's `sessionDuration` and iterates through potential time slots within the defined availability rule for the selected day. For each potential slot, it checks if it overlaps with any `existingAppointments` or if it's in the past relative to the current time. Only non-conflicting, future slots are returned to the `BookingWidget`, which then groups them into "Manhã", "Tarde", and "Noite" for display.

## Booking Submission

Once a customer selects a date and time slot, they proceed to a form to enter their details. This form is validated client-side using Zod and `react-hook-form` with `clientSchema`. A `POST` request is then sent to `/api/booking`.

The `POST` handler in `src/app/api/booking/route.ts` is designed with several considerations:

1.  **Rate Limiting**: The `getBookingLimiter()` from `src/lib/ratelimit.ts` is applied, restricting booking attempts to 5 per IP address every 10 minutes (`rl:booking`). This helps prevent abuse and denial-of-service attacks.
2.  **Timing Oracle Mitigation**: A response-time floor of 250ms is implemented. This means the server will wait at least 250ms before responding, regardless of how quickly the database operations complete. This design choice aims to obscure timing differences between database operations (e.g., selecting an existing client vs. inserting a new one), making it harder for attackers to infer information about existing clients through timing attacks.
3.  **Zod Validation**: The incoming request body is validated against `bookingSchema` to ensure data integrity and prevent malformed requests.
4.  **Honeypot**: A hidden `website` field is included in the form. If a bot populates this field, the server silently drops the submission and returns a fake success response. This effectively traps naive bots without alerting them that their submission was rejected.
5.  **Professional Lookup**: The professional is retrieved from the `professionals` table using the provided `slug`.
6.  **Plan Limits**: The system checks the professional's `effectivePlan` against `PLANS` defined in `src/lib/stripe`. It verifies if the professional has reached their `clients` limit or `appointmentsPerMonth` limit. If a limit is hit and the client is new, the booking is rejected with a 403 status.
7.  **Atomic Transaction**: The most critical part of the booking submission is the database transaction. The `db.transaction` block, configured with `isolationLevel: "serializable"`, ensures that the conflict check, client upsert, and appointment insertion happen atomically. This prevents race conditions where two simultaneous booking requests for the same slot might both pass an initial conflict check before one of them commits. If a conflict is detected (either by the explicit `SLOT_TAKEN` check or a `40001` serialization error from Postgres), the transaction is rolled back, and a 409 Conflict status is returned.
    *   **Conflict Check**: The transaction first checks the `appointments` table for any existing appointments that overlap with the proposed `startsAt` and `endsAt` times, excluding `rejected` or `cancelled` statuses.
    *   **Client Upsert**: It then attempts to find an existing client in the `clients` table based on `clientPhone` or `clientEmail` for the given `professionalId`. If found, the client's email is updated if it was previously null. If no client is found, a new entry is inserted into the `clients` table.
    *   **Appointment Insert**: Finally, a new appointment is inserted into the `appointments` table with a `status` of `confirmed` if `professional.autoConfirm` is true, or `pending_confirmation` otherwise. The `paymentStatus` is initially set to `none`.

## Confirmation and Follow-up

After a successful booking, the system initiates several follow-up actions:

*   **Notifications**: A new entry is added to the `notifications` table, alerting the professional about the new booking. The type and title of the notification depend on whether the appointment was `autoConfirm`ed.
*   **WhatsApp Messages**: Depending on the `autoConfirm` status, different WhatsApp messages are sent using `sendWhatsApp` from `src/lib/whatsapp`.
    *   If confirmed: `msgBookingConfirmed` is sent to the client (as a receipt and reminder anchor) and `msgBookingConfirmedReceipt` is sent to the professional.
    *   If pending: `msgBookingRequest` is sent to the professional, prompting them to confirm or reject the booking from their dashboard.
*   **Email Notifications**: If the professional has an email address, an email notification is sent using `sendBookingRequestEmailToProfessional` or `sendBookingConfirmedEmailToClient`/`sendBookingRejectedEmailToClient` from `src/lib/email`.
*   **Analytics**: Funnel events (`booking_received_server`) are captured using PostHog, attributing the booking to the professional and setting a `first_booking_at` property for cohort analysis.
*   **Success Response**: The API returns a generic `success: true` response, intentionally omitting sensitive appointment details to prevent information leakage.

On the client side, the `BookingWidget` transitions to a "success" step, displaying a confirmation message. If the `paymentType` is not "after" and a `pixKey` is available, a `PixQR` component is shown for immediate payment. For unauthenticated users, a prompt to create a free account is displayed, with pre-filled registration links using the submitted client data.

## Design Decisions

*   **Server-Side Rendering for Profile (`page.tsx`)**: Using a Next.js Server Component for the professional's profile page allows for better SEO and faster initial load times, as the content is rendered on the server and sent as HTML. This is crucial for public-facing pages that benefit from search engine indexing.
*   **Client-Side Interactivity for Widget (`booking-widget.tsx`)**: The `BookingWidget` is a Client Component, enabling rich, dynamic user interactions like calendar date selection and real-time slot filtering without requiring full page reloads. This provides a smoother user experience for the interactive booking process.
*   **Zod for Validation**: Zod is used for both client-side and server-side validation (`bookingSchema`, `clientSchema`). This provides a single source of truth for schema definitions, reducing the chance of discrepancies and improving developer experience.
*   **Honeypot for Bot Mitigation**: The inclusion of a hidden `website` field in the booking form is a simple yet effective technique to filter out spam bots. By returning a fake success response, it prevents bots from learning that the field is a trap, making them less likely to adapt.
*   **Rate Limiting (`getBookingLimiter`)**: Implementing rate limiting via Upstash Redis (`@upstash/ratelimit`) on the `POST /api/booking` route is a pragmatic choice to protect against brute-force attacks and resource exhaustion. The limit of 5 requests per IP every 10 minutes (`rl:booking`) is a reasonable balance between preventing abuse and allowing legitimate users to correct errors.
*   **Atomic Transaction for Booking**: Wrapping the conflict check, client upsert, and appointment insertion in a `serializable` database transaction is a critical design decision. This guarantees data consistency and prevents race conditions, ensuring that two users cannot simultaneously book the same slot. The explicit `SLOT_TAKEN` error and handling of Postgres's `40001` serialization error provide clear feedback in such scenarios.
*   **Timing Oracle Mitigation**: The `respondAfterFloor` function introduces a minimum response time for the `POST` request. This is a security measure to prevent attackers from using subtle differences in response times (e.g., faster response for existing clients vs. new clients) to infer information about the database contents.
*   **Selective Column Fetching in GET**: The `GET /api/booking` route explicitly selects only `id` and `sessionDuration` from the `professionals` table, and `startsAt`/`endsAt` from `appointments`. This minimizes data exposure, preventing sensitive professional or appointment details from being leaked to unauthenticated users who might query the API directly.
*   **Branching Logic for `autoConfirm`**: The system's behavior (sending confirmation vs. request messages) is dynamically adjusted based on the `professional.autoConfirm` setting. This allows professionals flexibility in how they manage new bookings, either instantly confirming or requiring manual approval.
*   **Equalized POST Response**: The `POST /api/booking` route returns a simple `{ success: true }` without including the newly created appointment details. This prevents an attacker from using the response body to infer information about the client or appointment, further enhancing security.

## Potential Improvements

1.  **Enhanced Client Email Update Logic**: In `src/app/api/booking/route.ts`, within the atomic transaction, the logic to update a client's email (`if (!client.email && clientEmail)`) only updates the `email` column if it is currently `null`. This means if a client previously provided an email, and then books again with a *different* email, the `clients.email` field will not be updated. This could lead to stale or incorrect email addresses being stored for existing clients, potentially causing communication issues. A more robust approach might involve updating the email if a new one is provided, or at least logging a discrepancy.
2.  **Granular Error Feedback in `BookingWidget.tsx`**: The `BookingWidget` currently uses a generic `toast.error("Erro ao realizar agendamento. Tente novamente.")` for all `POST /api/booking` failures. The API route, however, provides specific error messages for scenarios like `SLOT_TAKEN` (status 409) or plan limits (status 403). The `BookingWidget` could parse the `res.json()` from the API response and display these more specific, user-friendly error messages (e.g., "Este horário acabou de ser preenchido por outra pessoa. Por favor, escolha outro horário.") to guide the user more effectively.
3.  **Explicit Timezone Handling**: The current implementation in `src/lib/slots.ts` and `src/app/api/booking/route.ts` relies on `Date` objects and `date-fns` functions like `startOfDay`, `endOfDay`, `toLocaleDateString`, and `toLocaleTimeString`. These functions operate based on the local timezone of the environment where the code is executed (server or client). The `availability` table stores `startTime` and `endTime` as `text` (e.g., "09:00"), which are inherently timezone-agnostic. This implicit timezone handling can lead to inconsistencies if the server's timezone differs from the professional's or the client's, potentially causing slots to be generated or booked incorrectly. Implementing explicit timezone handling, such as storing all times in UTC and converting to the professional's preferred timezone for display and slot generation, would prevent these issues.
4.  **Linking Unauthenticated Bookings to User Accounts**: When a client books an appointment without being logged in, their `clients.userId` remains `null`. If this client later registers an account using the same phone number or email, the system does not automatically link their new `userId` to their existing `clients` entry. This can result in duplicate client records for the same individual (one with `userId` and one without) and prevent the client from seeing their past bookings when logged into their account. The `BookingWidget` does offer a registration link with pre-filled data, but the `POST /api/booking` route does not perform the linking. A post-registration process or an update within the booking transaction could check for an existing `clients` entry by phone/email and update its `userId` if a match is found.
