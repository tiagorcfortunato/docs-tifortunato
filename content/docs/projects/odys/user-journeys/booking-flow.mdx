# Customer Booking Flow

The customer booking flow is a core interaction within Odys, enabling users to discover professionals and schedule appointments. This document details the technical implementation behind this journey, covering the initial display of a professional's profile, the selection of an available time slot, the submission of booking details, and the subsequent confirmation and notification processes. Understanding this flow is crucial for maintaining data integrity, ensuring a smooth user experience, and managing professional availability effectively.

## Overview

The booking process is orchestrated across several components: a Next.js server component for the professional's public profile page, a client-side React component for interactive slot selection and form submission, and a dedicated API route to handle booking requests. The database schema, particularly the `professionals`, `availability`, `appointments`, and `clients` tables, underpins all data operations. Rate limiting, input validation, and atomic database transactions are employed to ensure the system's reliability and prevent common issues like double-bookings or bot spam.

## Professional Profile and Initial Display

A customer's journey begins by navigating to a professional's public profile page, handled by `src/app/p/[slug]/page.tsx`. This is a Next.js server component, meaning it fetches data and renders the initial HTML on the server before sending it to the client.

Upon loading, the page uses the `slug` from the URL parameters to query the `professionals` table. It retrieves essential details such as `name`, `profession`, `sessionDuration`, `sessionPrice`, `bio`, `avatarUrl`, and `welcomeMessage`. A critical check ensures that the professional exists and is `active`; otherwise, the `notFound()` helper redirects to a 404 page.

The page also fetches related data:
*   **Client Data**: If the visitor is a logged-in user but not the professional themselves, the system attempts to pre-fill the booking form with their `name`, `phone`, and `email` by querying the `clients` table using their `userId`. This enhances convenience for returning customers.
*   **Reviews**: Customer feedback is displayed by joining the `reviews` table with the `clients` table to show `rating`, `comment`, `createdAt`, and the `clientName` for the specific professional. This provides social proof and helps new customers make informed decisions.
*   **Related Professionals**: To encourage further exploration, the page fetches up to four other professionals from the `professionals` table who share the same `profession`. Their basic details and aggregated `reviews` statistics are displayed using the `ProfessionalCard` component.

The `BookingWidget` component, a client-side interactive element, is then rendered on this page, receiving key professional details as props, including `slug`, `sessionDuration`, `sessionPrice`, and payment information.

## Slot Selection and Availability

The `BookingWidget` component in `src/app/p/[slug]/booking-widget.tsx` manages the interactive selection of a date and time slot. It uses React's `useState` hook to track the `selectedDate` and `selectedSlot`.

When a user selects a date from the `Calendar` component, an `useEffect` hook triggers a `GET` request to the `/api/booking` endpoint. This API route is responsible for providing the available time slots for the chosen day.

The `GET /api/booking` endpoint:
1.  Receives `slug` and `date` parameters from the request URL.
2.  Queries the `professionals` table to retrieve the `id` and `sessionDuration` for the given `slug`. Importantly, it only selects these two columns, preventing the accidental exposure of sensitive professional data like `email` or `userId` to unauthenticated users.
3.  Fetches `availability` rules from the `availability` table for the professional's `id`. These rules define the professional's general working hours for each `dayOfWeek`, specified by `startTime` and `endTime`.
4.  Retrieves `existingAppointments` for the selected date from the `appointments` table, filtering out `rejected` or `cancelled` appointments. This ensures that only truly occupied slots are considered.

The fetched `rules` and `existingAppointments` are then passed to the `generateSlots` utility function in `src/lib/slots.ts`. This function calculates all potential time slots for the `selectedDate` based on the professional's `sessionDuration` and `availability` rules. It then iterates through these potential slots, filtering out any that are in the past or conflict with `existingAppointments`. The resulting list of available time strings (`HH:mm`) is returned to the `BookingWidget` for display.

## Booking Submission

Once a customer selects a date and time, they proceed to a form to enter their `name`, `phone`, and optionally `email`. This form submission is handled by a `POST` request to the `/api/booking` endpoint.

The `POST /api/booking` endpoint implements several critical steps:

1.  **Rate Limiting**: The `getBookingLimiter()` from `src/lib/ratelimit.ts` is applied, restricting booking attempts to 5 per IP address every 10 minutes (`rl:booking` prefix). This helps prevent abuse and denial-of-service attacks.
2.  **Timing Oracle Mitigation**: A `respondAfterFloor` function introduces a minimum response time of 250ms. This is a security measure designed to obscure timing differences between database operations (e.g., looking up an existing client vs. inserting a new one), making it harder for attackers to infer information about existing client data.
3.  **Input Validation**: The request body is validated using `zod` against the `bookingSchema`. This ensures that `slug`, `startsAt`, `clientName`, `clientPhone`, and `clientEmail` (if provided) meet the expected format and length constraints.
4.  **Honeypot**: A hidden `website` field in the form acts as a honeypot. If a bot populates this field, the request is silently dropped, and a fake success response is returned. This effectively thwarts many automated spam attempts without alerting the bot to the trap.
5.  **Professional Lookup**: The professional's details are fetched from the `professionals` table using the provided `slug`.
6.  **Plan Limit Checks**: The system verifies if the professional's current plan (`PLANS` from `src/lib/stripe.ts`) allows for the new booking. It checks against `plan.limits.clients` and `plan.limits.appointmentsPerMonth` by querying the `clients` and `appointments` tables, respectively. If limits are exceeded for new clients or monthly appointments, a 403 Forbidden response is returned.
7.  **Atomic Transaction**: To prevent race conditions and ensure data consistency, the core booking logic is wrapped in a Drizzle ORM transaction with `isolationLevel: "serializable"`. This is crucial for:
    *   **Conflict Check**: Before creating a new appointment, the transaction checks the `appointments` table for any existing appointments that would overlap with the proposed `startsAt` and `endsAt` times, excluding `rejected` or `cancelled` statuses. If a conflict is detected, a `SLOT_TAKEN` error is thrown, resulting in a 409 Conflict response.
    *   **Client Upsert**: The system attempts to find an existing client in the `clients` table associated with the professional using the provided `clientPhone` or `clientEmail`. If found, the client's `email` is updated if it was previously null. If no client is found, a new entry is created in the `clients` table.
    *   **Appointment Creation**: Finally, a new entry is inserted into the `appointments` table with the `professionalId`, `clientId`, `startsAt`, `endsAt`, and an initial `status` of either `confirmed` or `pending_confirmation` based on the `professional.autoConfirm` setting. The `paymentStatus` is set to `none`.
8.  **Notifications**: After a successful booking, the system dispatches various notifications:
    *   An entry is added to the `notifications` table for the professional.
    *   WhatsApp messages are sent to the professional (using `msgBookingConfirmedReceipt` or `msgBookingRequest`) and, if auto-confirmed, to the client (using `msgBookingConfirmed`).
    *   If the professional has an `email`, an email notification is sent via `sendBookingRequestEmailToProfessional`.
9.  **Analytics**: Both client-side (`booking_created`) and server-side (`booking_received_server`) Posthog events are captured, providing detailed analytics on booking initiation and reception. The server-side event attributes the booking to the professional's `id` and sets `first_booking_at` for new professionals.
10. **Equalized Response**: The success response is intentionally generic (`{ success: true }`) and does not include sensitive appointment details like `clientId`. This further protects against information leakage, as the `BookingWidget` only checks for `res.ok`.

## Confirmation and Next Steps

Upon a successful `POST` request, the `BookingWidget` transitions to a "success" step. It displays a confirmation message to the customer, reiterating the appointment details.

If the `paymentType` is not "after" and a `pixKey` is configured for the professional, a `PixQR` component is displayed, showing the amount due for immediate payment.

For unauthenticated users, the widget presents an option to create a free client account, pre-filling the registration link with the `submittedData` (`name`, `email`, `phone`). This encourages user retention and allows clients to track their appointments and receive reminders through the platform. Logged-in users are directed to their client dashboard.

## Design decisions

*   **Server-Side Rendering for Profile**: The `src/app/p/[slug]/page.tsx` component uses Next.js server components to fetch initial professional data and reviews. This improves initial page load performance and SEO, as the content is rendered on the server and sent as static HTML.
*   **Client-Side Interactivity**: The `BookingWidget` is a client component (`"use client"`), allowing for dynamic date and slot selection without full page reloads. This provides a more responsive and interactive user experience.
*   **Dedicated API Route for Booking**: Separating the booking logic into `/api/booking` (GET and POST) provides a clear interface for the client component to interact with the backend. This also allows for independent scaling and security measures like rate limiting.
*   **Drizzle ORM and Atomic Transactions**: The use of Drizzle ORM simplifies database interactions. Crucially, the `POST /api/booking` endpoint wraps the conflict check, client upsert, and appointment insertion in a `db.transaction` with `isolationLevel: "serializable"`. This is a strong isolation level that prevents race conditions (like two users booking the same slot simultaneously) by ensuring that concurrent transactions appear to execute serially, guaranteeing data integrity.
*   **Rate Limiting with Upstash Redis**: The `Ratelimit` library from Upstash, backed by Redis, is used to protect API endpoints like `/api/booking` from excessive requests. This prevents abuse and ensures fair usage.
*   **Honeypot for Bot Detection**: The `website` field in the booking form is a simple yet effective anti-bot measure. It's visually hidden but present in the DOM, catching naive bots that fill all form fields.
*   **Timing Oracle Mitigation**: The `respondAfterFloor` function in `POST /api/booking` adds a small, variable delay to responses. This makes it harder for attackers to distinguish between different database query paths (e.g., client found vs. client not found) by timing the response, thus protecting against information leakage.
*   **Selective Data Fetching**: The `GET /api/booking` endpoint explicitly selects only the `id` and `sessionDuration` columns from the `professionals` table. This minimizes data exposure, preventing sensitive information from being inadvertently sent to the client.
*   **Comprehensive Notification System**: Integrating WhatsApp (`sendWhatsApp`) and email notifications, alongside in-app notifications (`notifications` table), ensures that both professionals and clients are kept informed about booking status changes, regardless of their preferred communication channel. For initial bookings, email notifications are sent to the professional (if `professional.email` is set). Client email notifications (e.g., `sendBookingConfirmedEmailToClient`, `sendBookingRejectedEmailToClient`) are dispatched when a professional manually confirms or rejects an appointment.
*   **Zod for Validation**: Using Zod for schema validation (`bookingSchema`, `clientSchema`) provides a robust and type-safe way to ensure incoming data conforms to expected structures, catching malformed requests early.

## Potential improvements

1.  **Granular Slot Unavailability Feedback**: The `generateSlots` function in `src/lib/slots.ts` currently returns an empty array if no slots are available. While functional, it could be enhanced to provide more specific reasons for unavailability (e.g., "No availability rules for this day," "All slots are booked," "Professional is on holiday"). This would allow the `BookingWidget` to display more informative messages to the user, improving the user experience beyond a generic "Sem horários disponíveis."
2.  **Pre-fetching Availability for Nearby Dates**: The `BookingWidget` fetches slots for a `selectedDate` only when it changes. To improve perceived performance, especially for users browsing multiple days, the `useEffect` hook could be modified to pre-fetch availability for a few days surrounding the currently selected date (e.g., the next 3-5 days). This would make the slot selection feel snappier as users navigate the calendar.
3.  **Refined Client Upsert Logic**: In `src/app/api/booking/route.ts`, the client upsert logic in the `POST` handler checks for an existing client by `phone` OR `email`. If a client is found by phone but has no email, and the booking request includes an email, the existing client's email is updated. This is good, but the logic could be made more explicit about handling cases where a client exists with a phone but a *different* email is provided, or vice-versa, to prevent accidental data overwrites or creation of duplicate client entries under slightly different identifiers.
4.  **Centralized Notification Dispatch**: The notification logic in `src/app/api/booking/route.ts` and `src/app/api/appointments/[id]/route.ts` involves multiple `sendWhatsApp` and email calls, along with `db.insert(notifications)`. While functional, this could be abstracted into a dedicated service or utility function that takes an event (e.g., `bookingConfirmed`, `bookingRejected`) and handles all associated notification channels (WhatsApp, email, in-app) in a single call. This would reduce duplication, improve maintainability, and make it easier to add new notification channels in the future.
