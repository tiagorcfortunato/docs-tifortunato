# Customer Booking Flow

The customer booking flow is a core interaction within Odys, enabling clients to discover professionals and schedule appointments. This process spans several components, from the public-facing professional profile page to backend API services that handle availability checks, appointment creation, and notifications. Understanding this flow requires examining how the frontend presents information, how the client-side widget interacts with the API, and how the server-side logic manages data integrity and external communications.

## Overview

The booking journey begins when a customer navigates to a professional's public profile page, rendered by `src/app/p/[slug]/page.tsx`. This page serves as the entry point, displaying the professional's details, reviews, and an interactive `BookingWidget`. The widget, a client-side component, orchestrates the selection of a date and time slot.

When a date is chosen, the widget makes a `GET` request to `/api/booking` to fetch available slots for that day. This API route consults the `professionals`, `availability`, and `appointments` tables to determine which time slots are genuinely free. Once a slot is selected and client details are provided, a `POST` request is sent to the same `/api/booking` endpoint.

The `POST` handler is responsible for a series of critical operations: validating the booking request, checking the professional's plan limits, performing an atomic conflict check to prevent double-bookings, upserting client information into the `clients` table, and finally, inserting the new appointment into the `appointments` table. Depending on the professional's `autoConfirm` setting, the appointment's initial status will be either `"confirmed"` or `"pending_confirmation"`. The system then dispatches various notifications via WhatsApp and email, and records analytics events.

After an appointment is created, its status can be managed by the professional (or client, for cancellations) through `PATCH` requests to `/api/appointments/[id]`. This route handles actions like confirming, rejecting, cancelling, marking as paid, completing, or noting a no-show, triggering further notifications as appropriate.

## Professional Profile Page

The `src/app/p/[slug]/page.tsx` file is a Next.js server component responsible for rendering a professional's public profile. It dynamically fetches data based on the `slug` parameter in the URL.

Upon loading, the page queries the `professionals` table to retrieve the professional's details, including their `name`, `profession`, `bio`, `avatarUrl`, `sessionDuration`, `sessionPrice`, and `welcomeMessage`. It also checks the `active` status of the professional, returning a `notFound()` response if the professional is not found or inactive.

To enrich the profile, the page fetches `reviews` associated with the professional, joining with the `clients` table to display client names alongside their feedback. It calculates the `totalReviews` and `avgRating` to provide social proof. Additionally, it identifies and displays up to four `related` professionals based on the same `profession`, fetching their aggregated statistics using `getProStats`.

A key aspect of this page is its awareness of the current user's context. It uses `createClient()` from `@supabase/server` to determine if the visitor is logged in and, if so, whether they are the `isOwner` of the page or an `isClient`. If the visitor is a logged-in client, their existing `name`, `phone`, and `email` from the `clients` table are fetched to pre-fill the booking form, enhancing user experience.

The page integrates several UI components, including `FollowButton` for clients to follow professionals, `ProfessionalCard` for displaying related professionals, and `ProfessionalLocationCard` to show service type and address details. The central interactive element is the `BookingWidget`, a client component that handles the core booking logic.

## Slot Selection and Availability

The `BookingWidget` in `src/app/p/[slug]/booking-widget.tsx` is a client-side component that guides the user through selecting an appointment date and time. It maintains its state using `useState` hooks for `selectedDate`, `selectedSlot`, and the current `step` in the booking process (pick date/time, fill form, or success).

When a user selects a `selectedDate` from the `Calendar` component, an `useEffect` hook triggers a `GET` request to the `/api/booking` endpoint. This request includes the professional's `slug` and the chosen `date`.

The `GET` handler in `src/app/api/booking/route.ts` then performs two main database queries in parallel using `Promise.all`:
1.  It retrieves the professional's `id` and `sessionDuration` from the `professionals` table, filtering by `slug`. Importantly, it only selects these two columns, avoiding the accidental exposure of sensitive professional data like `email`, `phone`, `userId`, `plan`, `trialEndsAt`, `stripeCustomerId`, or `stripeSubscriptionId` to unauthenticated users, which was a previous vulnerability.
2.  It fetches the professional's `availability` rules from the `availability` table for the given `professionalId`. These rules define the general working hours for each `dayOfWeek` using `startTime` and `endTime` text fields (e.g., "09:00", "18:00").
3.  It also retrieves `existingAppointments` for that professional on the selected date, filtering out appointments with `status` of `"rejected"` or `"cancelled"`. This ensures that only truly occupied slots are considered.

The fetched `rules` and `existingAppointments` are then passed to the `generateSlots` utility function in `src/lib/slots.ts`. This function calculates all potential `sessionDuration`-long slots within the professional's `startTime` and `endTime` for the `dayOfWeek`. It meticulously checks each potential slot against `now` (to exclude past slots) and `existingAppointments` to identify and remove any conflicting times. The resulting `slots` (e.g., "09:00", "09:30") are then returned to the `BookingWidget`, which groups them into `morning`, `afternoon`, and `evening` for display.

Once a `selectedSlot` is chosen, the widget transitions to the "form" step, prompting the user for their `name`, `phone`, and `email`.

## Booking Submission

The `POST` handler in `src/app/api/booking/route.ts` is the central point for creating new appointments. It is designed with several considerations for security, data integrity, and user experience:

1.  **Rate Limiting**: The `getBookingLimiter()` from `src/lib/ratelimit.ts` is applied at the very beginning, restricting booking attempts to 5 per IP address every 10 minutes (`rl:booking`). This helps prevent abuse and denial-of-service attacks.
2.  **Timing Oracle Mitigation**: A `respondAfterFloor` function is used to introduce a minimum response time of 250ms. This is a deliberate choice to obscure whether a client's phone/email combination already exists in the database, preventing potential timing attacks that could distinguish between existing and new clients.
3.  **Input Validation**: The incoming request body is validated using `bookingSchema`, a Zod schema that enforces minimum lengths for `slug`, `clientName`, `clientPhone`, and validates `startsAt` as a datetime and `clientEmail` as an email.
4.  **Honeypot**: A hidden `website` field is included in the `bookingSchema` and the client-side form. If this field is populated, the request is silently dropped, and a fake success response is returned. This effectively thwarts naive spam bots without alerting them that their submission was rejected.
5.  **Professional Lookup**: The professional is retrieved from the `professionals` table using the provided `slug`.
6.  **Plan Limits**: The system checks the professional's active plan using `effectivePlan` and `PLANS`. It verifies if the professional has reached their `clients` limit or `appointmentsPerMonth` limit. If a limit is hit, and the client is new, the booking is rejected with a `403` status.
7.  **Atomic Transaction**: The core booking logic is wrapped in a Drizzle `db.transaction` with `isolationLevel: "serializable"`. This is a critical design choice to prevent race conditions. Inside the transaction:
    *   **Conflict Check**: It first checks for any `appointments` that would overlap with the proposed `startsAt` and `endsAt` (calculated using `sessionDuration`). It specifically excludes `"rejected"` and `"cancelled"` appointments from this check. If a conflict is found, it throws a `"SLOT_TAKEN"` error.
    *   **Client Upsert**: It attempts to find an existing client for the `professionalId` using either `clientPhone` or `clientEmail`. If found, it updates the client's `email` if it was previously null. If no client is found, a new entry is inserted into the `clients` table.
    *   **Appointment Insert**: Finally, the new appointment is inserted into the `appointments` table with a `status` of `"confirmed"` or `"pending_confirmation"` based on the professional's `autoConfirm` setting, and `paymentStatus` as `"none"`.
    *   If the `SLOT_TAKEN` error or a PostgreSQL `40001` (serialization failure) error occurs, the transaction is rolled back, and a `409` (Conflict) response is returned to the client, informing them the slot was just taken.
8.  **Notifications**: After a successful booking, the system sends:
    *   A `notifications` entry to the professional's dashboard.
    *   WhatsApp messages to the client (confirmation or pending) and the professional (receipt or request), using templates like `msgBookingConfirmed` or `msgBookingRequest`.
    *   An email to the professional if their `email` is available, using `sendBookingRequestEmailToProfessional`.
9.  **Analytics**: Posthog events (`booking_received_server`, `first_booking_at`) are captured to track booking volume and professional onboarding metrics.
10. **Equalized Response**: The success response (`{ success: true }`) does not include the newly created appointment details. This is another security measure to prevent information leakage that could aid an attacker in distinguishing client types.

## Appointment Management

The `PATCH` handler in `src/app/api/appointments/[id]/route.ts` allows authorized users to update the status and payment status of an appointment.

1.  **Rate Limiting**: The `getApiLimiter()` is applied, allowing 60 requests per minute per IP address (`rl:api`).
2.  **Authentication and Authorization**: The `getUser()` function verifies the user's identity. It then fetches the `appointment`, `professional`, and `client` records. Authorization logic determines if the current user is the `isProfessional` or `isClient` associated with the appointment.
3.  **Action Validation**: The `action` parameter from the request body is strictly validated against an `ALLOWED_ACTIONS` set (`"confirm"`, `"reject"`, `"cancel"`, `"paid"`, `"complete"`, `"no_show"`). Invalid actions are rejected with a `400` status.
4.  **Status Transitions**:
    *   **Cancel**: Both professionals and clients can cancel appointments if the status is `"pending_confirmation"` or `"confirmed"`. Notifications are sent to the other party via WhatsApp.
    *   **Professional-only Actions**: Actions like `"paid"`, `"complete"`, and `"no_show"` are restricted to the professional. These update the `paymentStatus` or `status` accordingly and trigger specific WhatsApp notifications to both client and professional.
    *   **Confirm/Reject**: These actions are also professional-only. They update the `status` to `"confirmed"` or `"rejected"` and `paymentStatus` to `"authorized"` or `"refunded"`. Notifications are sent to the client (via `notifications` table, WhatsApp, and email) and the professional (via WhatsApp). For clients without an existing user account, a `msgRegistrationInvite` is appended to the WhatsApp confirmation message.

This route ensures that appointment lifecycle changes are properly recorded and communicated, maintaining consistency across the platform and keeping both parties informed.

## Design decisions

The design of the booking flow reflects several key decisions aimed at balancing functionality, security, and user experience:

*   **Separation of Concerns**: The clear division between the server-rendered `page.tsx`, the client-side `booking-widget.tsx`, and the API routes (`route.ts`, `[id]/route.ts`) allows for efficient data fetching on the server, interactive UI on the client, and robust business logic on the API. This aligns with Next.js's architecture for hybrid applications.
*   **Database Schema for Flexibility**: The `professionals`, `availability`, `appointments`, and `clients` tables are designed to support a flexible booking system. `availability` rules define general working hours, while `appointments` track specific bookings. The `sessionDuration` on the `professionals` table allows each professional to define their standard appointment length, simplifying slot generation.
*   **Atomic Transactions for Integrity**: The use of a Drizzle `db.transaction` with `isolationLevel: "serializable"` for the `POST /api/booking` endpoint is a critical choice. It ensures that the conflict check, client upsert, and appointment insertion happen as a single, indivisible operation. This prevents race conditions where two users might simultaneously attempt to book the same slot, guaranteeing that only one succeeds and maintaining data consistency. Without this, a simple `SELECT` followed by `INSERT` could lead to double-bookings.
*   **Rate Limiting for Abuse Prevention**: Implementing `Ratelimit` from `@upstash/ratelimit` across various API endpoints, including `getBookingLimiter()` and `getApiLimiter()`, is a proactive measure against spam, brute-force attacks, and resource exhaustion. The specific limits (e.g., 5 bookings per 10 minutes per IP) are tailored to expected user behavior.
*   **Honeypot and Timing Oracle Mitigation**: The inclusion of a hidden `website` field (honeypot) and the `respondAfterFloor` function in the `POST /api/booking` route are subtle but effective security measures. The honeypot filters out automated spam, while the response-time floor prevents attackers from using timing differences to infer information about existing client data, enhancing privacy.
*   **Selective Data Fetching**: The `GET /api/booking` route explicitly selects only `id` and `sessionDuration` from the `professionals` table. This prevents sensitive data like `email`, `phone`, or `userId` from being exposed to unauthenticated clients who are merely checking availability, adhering to the principle of least privilege.
*   **Comprehensive Notification System**: The integration with WhatsApp (`sendWhatsApp`) and email (`sendBookingRequestEmailToProfessional`, `sendBookingConfirmedEmailToClient`, etc.) ensures that both clients and professionals receive timely updates throughout the booking lifecycle. The use of specific message templates (e.g., `msgBookingRequest`, `msgBookingConfirmed`) provides clear and consistent communication.

## Potential improvements

1.  **Enhance Slot Generation with Recurring Schedules**: The `generateSlots` function in `src/lib/slots.ts` currently considers `availability` rules and `existingAppointments`. To provide a more accurate view of a professional's true availability, it could be enhanced to also factor in `recurringSchedules`. This would prevent clients from attempting to book a slot that, while not yet an `appointment`, is reserved for a recurring client. The `recurringSchedules` table contains `dayOfWeek` and `time` information that could be used to pre-block these slots.
2.  **Robust External Notification Handling**: The `POST /api/booking` and `PATCH /api/appointments/[id]` routes send WhatsApp messages and emails using `sendWhatsApp` and various `send...EmailTo...` functions. While these calls are wrapped in `catch` blocks that `console.warn` on failure, there's no retry mechanism or persistent queue. For critical notifications like booking confirmations or rejections, a more robust system could involve pushing these messages to a dedicated queue (e.g., Redis, a message broker) that handles retries and ensures eventual delivery, rather than potentially losing a notification due to a transient network error or API rate limit.
3.  **Centralize Date/Time Formatting**: Date and time formatting, particularly for display in messages and UI, is currently handled in multiple places (e.g., `route.ts` for notifications, `booking-widget.tsx` for display). For instance, `toLocaleDateString("pt-BR", { weekday: "long", day: "numeric", month: "long" })` appears in both `src/app/api/booking/route.ts` and `src/app/api/appointments/[id]/route.ts`. Creating a shared utility function for common date and time display formats could reduce duplication, improve consistency, and simplify future localization efforts.
