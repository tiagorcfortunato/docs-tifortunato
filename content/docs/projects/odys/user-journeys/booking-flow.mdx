title: Booking Flow
description: The customer journey for booking an appointment, from landing on a professional's page to slot selection, submission, and confirmation.

The booking flow is a core interaction within Odys, enabling customers to discover professionals and schedule appointments. This process encompasses the public-facing professional profile page, the interactive booking widget, the API endpoints for fetching availability and submitting bookings, and the underlying logic for managing time slots and preventing conflicts. Understanding this flow reveals how Odys handles user interaction, data validation, concurrency, and external communication.

## Overview

The customer booking journey begins on a professional's public profile page, rendered by `src/app/p/[slug]/page.tsx`. This page displays details about the professional, their services, and reviews. Crucially, it embeds the `BookingWidget` component, which guides the customer through selecting a date and time.

When a customer interacts with the `BookingWidget`, it communicates with the `/api/booking` endpoint. A `GET` request to this endpoint retrieves the professional's availability rules and existing appointments for a given day. This data is then processed client-side by the `generateSlots` utility to present available time slots.

Once a slot is chosen and client details are provided, a `POST` request is sent to `/api/booking`. This server-side handler performs critical validation, checks against plan limits, and executes an atomic database transaction to create the appointment. Upon successful booking, the system dispatches notifications via WhatsApp and email, and records analytics events.

## Professional Profile Page

The `src/app/p/[slug]/page.tsx` file serves as the public entry point for customers to view a professional's profile and initiate a booking. This Next.js page component is responsible for fetching all necessary data to render a comprehensive view of the professional.

Upon loading, the page queries the `professionals` table using the `slug` from the URL to retrieve the professional's details, including their `name`, `profession`, `sessionDuration`, `sessionPrice`, `bio`, and `avatarUrl`. It also checks the `active` status of the professional; if the professional is not found or inactive, the `notFound()` helper redirects to a 404 page.

To enrich the profile, the page fetches `reviews` associated with the professional, joining with the `clients` table to display client names alongside their ratings and comments. It also retrieves a selection of related professionals based on the `profession` field, providing customers with alternative options.

A key aspect of this page is its ability to detect if the current visitor is the professional themselves (`isOwner`). This is determined by comparing the authenticated user's `id` with the professional's `userId`. If the visitor is logged in but not the owner, their existing `client` data (name, phone, email) is fetched from the `clients` table to pre-fill the booking form, streamlining the user experience.

The `BookingWidget` component is then rendered, passing essential professional data as props, such as `slug`, `professionalName`, `sessionDuration`, `sessionPrice`, and payment-related information like `paymentType`, `paymentPercentage`, `pixKeyType`, and `pixKey`.

## Booking Widget

The `src/app/p/[slug]/booking-widget.tsx` is a client-side React component that orchestrates the interactive booking experience. It manages the state of the booking process, guiding the user through three steps: `pick` (date and time selection), `form` (client details input), and `success` (confirmation).

Initially, the widget displays a calendar for date selection. When a date is chosen, an effect hook triggers a `GET` request to `/api/booking`, passing the `slug` and the selected `date`. The response, containing availability rules and existing appointments, is then fed into the `generateSlots` utility function. This function, described below, calculates and returns a list of available time slots for the chosen day, which are then grouped into morning, afternoon, and evening sections for easier selection.

Once a time slot is selected, the user proceeds to the `form` step. Here, a form built with `react-hook-form` and `zod` collects the client's `name`, `phone`, and optional `email`. Client-side validation ensures the data meets basic requirements before submission. A hidden "honeypot" field named `website` is included in the form. This field is visually hidden and inaccessible to human users but is often filled by automated bots. If this field contains any value upon submission, the server will silently drop the request, effectively filtering out spam without alerting the bot.

Upon successful submission, the widget transitions to the `success` step, displaying a confirmation message. If the professional's `paymentType` is not "after" and a `pixKey` is configured, a `PixQR` component is shown, allowing the client to make an immediate payment for a percentage of the session price. For unauthenticated users, the success screen also offers an invitation to create a free account, pre-filling registration details from the submitted booking form.

## Availability API (`GET /api/booking`)

The `GET` handler in `src/app/api/booking/route.ts` is responsible for providing the data necessary for the `BookingWidget` to display available time slots. It expects `slug` and `date` as query parameters.

Upon receiving a request, the API first queries the `professionals` table to retrieve the `id` and `sessionDuration` for the specified professional. A deliberate design choice here is to select *only* these two columns, rather than the entire professional record. This prevents sensitive information like `email`, `phone`, `userId`, `plan`, `trialEndsAt`, `stripeCustomerId`, and `stripeSubscriptionId` from being exposed to unauthenticated visitors, which was a potential data leak in previous iterations.

Next, it performs two concurrent database queries:
1.  Fetches `availability` rules for the professional, specifically `dayOfWeek`, `startTime`, and `endTime`. These rules define the professional's general working hours.
2.  Retrieves `existingAppointments` for the selected date, filtering out appointments with `status` of "rejected" or "cancelled". This ensures that only active or pending appointments are considered when calculating availability.

The fetched `rules` and `existingAppointments` are then returned to the client, where the `BookingWidget` uses them to render the available slots.

## Slot Generation

The `src/lib/slots.ts` utility file contains the `generateSlots` function, which is the core logic for determining which time slots are genuinely available for booking. This function takes the `date`, `AvailabilityRule`s, `ExistingAppointment`s, and the `sessionDuration` as input.

It first identifies the relevant `AvailabilityRule` for the given `dayOfWeek`. If no rule exists, no slots are generated. It then iterates through potential start times, beginning from the `startTime` defined in the rule and incrementing by the `sessionDuration`. For each potential slot, it performs two crucial checks:
1.  **Past Check**: It ensures the `current` slot start time is in the future relative to the current `now` timestamp. This prevents users from trying to book appointments that have already passed.
2.  **Conflict Check**: It iterates through all `existingAppointments` to determine if the potential slot (`current` to `slotEnd`) overlaps with any already booked appointment (`aptStart` to `aptEnd`). An overlap is detected if the potential slot starts before an existing appointment ends AND the potential slot ends after an existing appointment starts.

Only slots that pass both these checks are added to the list of available slots, which are then returned in `HH:mm` format.

## Booking Submission API (`POST /api/booking`)

The `POST` handler in `src/app/api/booking/route.ts` is the central point for creating new appointments. It is designed with several layers of validation and concurrency control to ensure data integrity and prevent abuse.

1.  **Rate Limiting**: The first line of defense is `getBookingLimiter().limit(getIp(req))`, which restricts booking attempts to 5 per IP address every 10 minutes. This helps mitigate spam and denial-of-service attacks.
2.  **Response-Time Floor**: A `startTime` is recorded, and the `respondAfterFloor` helper ensures that all responses, regardless of success or failure, take at least 250ms. This is a security measure to blunt timing oracle attacks, where an attacker might infer information (e.g., if a client exists) by observing subtle differences in response times between different database operations.
3.  **Input Validation**: The incoming request body is validated using `bookingSchema` from `zod`. This schema enforces requirements for `slug`, `startsAt`, `clientName`, `clientPhone`, and an optional `clientEmail`.
4.  **Honeypot Check**: The `website` field, a hidden honeypot, is checked. If it contains any data, the request is silently dropped, returning a fake success response to mislead bots.
5.  **Professional Lookup**: The professional is retrieved from the `professionals` table using the provided `slug`.
6.  **Plan Limits**: The system checks the professional's `effectivePlan` against defined `PLANS`. It verifies if the professional has reached their `clients` limit or `appointmentsPerMonth` limit. If the `clients` limit is hit and the client is new, or if the `appointmentsPerMonth` limit is hit, the booking is rejected with a 403 status.
7.  **Atomic Transaction**: The most critical part of the booking process is wrapped in a Drizzle `db.transaction` with `isolationLevel: "serializable"`. This ensures that the entire sequence of operations—conflict checking, client upsert, and appointment insertion—is treated as a single, indivisible unit.
    *   **Conflict Check**: Inside the transaction, a query checks for any existing appointments that overlap with the proposed `startsAt` and `endsAt` times, excluding "rejected" or "cancelled" appointments. If a conflict is found, the transaction is aborted with a "SLOT_TAKEN" error. This prevents race conditions where two users might simultaneously try to book the same slot.
    *   **Client Upsert**: The system attempts to find an existing client for the professional based on `clientPhone` or `clientEmail`. If found, the existing client record is used; otherwise, a new client is inserted into the `clients` table. If an existing client is found but lacks an email and one is provided, the client's email is updated.
    *   **Appointment Insertion**: Finally, the new appointment is inserted into the `appointments` table with the appropriate `professionalId`, `clientId`, `startsAt`, `endsAt`, and an initial `status` of "confirmed" or "pending_confirmation" based on `professional.autoConfirm`.
8.  **Notifications**: After a successful transaction, the system sends various notifications:
    *   An entry is inserted into the `notifications` table for the professional.
    *   WhatsApp messages are sent to the client (if confirmed) and the professional (request or receipt) using templates like `msgBookingConfirmed`, `msgBookingConfirmedReceipt`, or `msgBookingRequest`.
    *   An email notification is sent to the professional if their `email` is available.
9.  **Analytics**: Posthog events (`booking_received_server`) are captured, and `first_booking_at` is set as a user property to track booking volume and professional onboarding metrics.
10. **Equalized Response**: The API returns a generic `{ success: true }` without including the newly created appointment details. This is another security measure to prevent information leakage, especially the `clientId`, which could be used by an attacker to map phone/email pairs to existing clients.

## Appointment Status Updates (`PATCH /api/appointments/[id]`)

The `PATCH` handler in `src/app/api/appointments/[id]/route.ts` allows for modifying the status of an existing appointment. This route is primarily used by professionals to manage their bookings.

It first applies a general API rate limit (`getApiLimiter`) to prevent abuse. After authenticating the user, it fetches the appointment and its associated professional and client records. It then determines if the authenticated user is the `isProfessional` or `isClient` for the appointment.

The route defines a set of `ALLOWED_ACTIONS` (e.g., "confirm", "reject", "cancel", "paid", "complete", "no_show"). Any action not in this set results in a 400 error, preventing unexpected state transitions.

Actions like "paid", "complete", and "no_show" are restricted to the professional. The "cancel" action can be initiated by either the professional or the client. For "confirm" and "reject" actions, only the professional is authorized.

For each action, the `appointments` table is updated with the new `status` or `paymentStatus`. Corresponding notifications are then sent:
*   Entries are inserted into the `notifications` table for the relevant recipient (client or professional).
*   WhatsApp messages are sent using specific templates (e.g., `msgBookingConfirmed`, `msgBookingRejected`, `msgCancelledByClientToPro`, `msgPaymentConfirmedToClient`, etc.) to both the client and the professional.
*   Emails are sent to the client for confirmation or rejection.

This centralized handling of status updates ensures consistency in state changes and notification delivery across the platform.

## Design decisions

The booking flow incorporates several deliberate design choices to enhance security, data integrity, and user experience:

*   **Minimal Data Exposure in `GET /api/booking`**: The `GET` request for availability explicitly selects only `id` and `sessionDuration` from the `professionals` table. This is a crucial security decision to prevent the accidental leakage of sensitive professional data (like `email`, `phone`, `userId`, or Stripe IDs) to unauthenticated users who might simply browse the API. The previous implementation returned `SELECT *`, which was a significant vulnerability.
*   **Honeypot Field for Spam Prevention**: Both the `bookingSchema` in `src/app/api/booking/route.ts` and `clientSchema` in `src/app/p/[slug]/booking-widget.tsx` include a `website` field. This field is hidden from human users but is often filled by automated bots. By checking for a non-empty value in this field, the system can silently drop spam submissions without engaging in complex CAPTCHA challenges, providing a smoother experience for legitimate users.
*   **Response-Time Floor for Timing Oracle Protection**: The `POST /api/booking` handler introduces a minimum response time of 250ms using `respondAfterFloor`. This measure is designed to obscure timing differences in database operations. Without it, an attacker could potentially distinguish between "client exists" (faster `SELECT`) and "client does not exist" (slower `SELECT` + `INSERT`) by timing responses, thereby creating an existence oracle for client data.
*   **Atomic Transaction with Serializable Isolation**: The booking creation in `POST /api/booking` is wrapped in a Drizzle `db.transaction` with `isolationLevel: "serializable"`. This is paramount for concurrency control. In a high-traffic scenario, multiple users might attempt to book the same slot simultaneously. A serializable transaction ensures that these operations are executed as if they happened one after another, preventing phantom reads and ensuring that only one booking can successfully claim a slot. If a conflict is detected (SQLSTATE `40001` or the custom "SLOT_TAKEN" error), the transaction is rolled back, and the user receives an appropriate error message.
*   **Equalized Success Response**: The `POST /api/booking` endpoint returns a generic `{ success: true }` upon successful booking, intentionally omitting details of the newly created appointment, such as the `clientId`. This prevents an attacker from using the booking endpoint as an information oracle to confirm the existence of specific client records by observing differences in the response body.
*   **Centralized Rate Limiting**: The `src/lib/ratelimit.ts` module provides dedicated rate limiters for different API endpoints, including `getBookingLimiter` (5 requests per 10 minutes per IP) and `getApiLimiter` (60 requests per minute per IP). This protects the backend from various forms of abuse, from spam bookings to brute-force attacks, by leveraging Upstash Redis.

## Potential improvements

1.  **Refine Availability Time Representation**: The `availability` table stores `startTime` and `endTime` as `text` (e.g., "09:00"). While `generateSlots` parses these strings, using an integer representation (e.g., minutes from midnight) would simplify time arithmetic, reduce parsing overhead, and eliminate potential issues with string-based time comparisons or locale differences. This change would primarily affect the `availability` schema and the `generateSlots` function in `src/lib/slots.ts`.
2.  **Centralize Notification Logic**: The `POST /api/booking` and `PATCH /api/appointments/[id]` routes contain significant duplication in their notification logic, with multiple conditional `sendWhatsApp` and `sendBookingRequestEmailToProfessional` calls. Abstracting this into a dedicated notification service or utility function (e.g., `sendAppointmentNotifications(appointment, professional, client, action)`) would reduce code duplication, improve maintainability, and make it easier to add new notification channels or modify existing templates.
3.  **Structured Error Handling for External Services**: The `sendWhatsApp` and email functions currently use `.catch(console.warn)`. While this prevents the main booking transaction from failing due to a notification error, it can lead to silent failures that are difficult to monitor and debug. Implementing a more structured approach, such as integrating a retry mechanism, logging to a dedicated error tracking system, or pushing failed notifications to a dead-letter queue for asynchronous processing, would improve the reliability of external communications. This would involve modifying the `.catch` blocks in `src/app/api/booking/route.ts` and `src/app/api/appointments/[id]/route.ts`.
4.  **Client-Side Slot Re-validation Before Submission**: The `BookingWidget` in `src/app/p/[slug]/booking-widget.tsx` fetches slots once a date is selected. However, a significant delay between slot selection and form submission could lead to a race condition where a slot becomes unavailable. While the server-side atomic transaction in `POST /api/booking` ultimately handles this, adding a quick client-side re-validation (e.g., re-fetching slots or checking if the `selectedSlot` is still present in the `slots` array just before `onSubmit`) could provide faster feedback to the user, improving perceived responsiveness.
