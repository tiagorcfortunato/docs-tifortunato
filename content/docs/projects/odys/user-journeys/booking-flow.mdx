# Booking Flow

The customer booking flow is a central interaction within Odys, enabling clients to discover professionals, view their availability, and schedule appointments. This process spans multiple components, from the public-facing professional profile page to backend API endpoints responsible for validating availability, handling submissions, and orchestrating notifications. Understanding this flow requires examining how the frontend renders booking options, how the backend processes requests, and the database interactions that ensure data integrity.

## Overview

The booking journey begins when a customer navigates to a professional's public profile page, rendered by `src/app/p/[slug]/page.tsx`. This page dynamically fetches professional details and embeds the `BookingWidget` client component. The `BookingWidget` is responsible for the interactive date and time selection, communicating with the `/api/booking` route to retrieve available slots.

When a customer selects a slot and provides their details, the `BookingWidget` dispatches a `POST` request to `/api/booking`. This API endpoint performs critical validations, including rate limiting, honeypot checks, plan limit enforcement, and an atomic transaction to prevent booking conflicts. Upon successful booking, the system dispatches various notifications via WhatsApp and email, and records analytics events.

Post-booking, the status of an appointment can be managed by either the professional or, in some cases, the client, through the `PATCH /api/appointments/[id]` endpoint. This endpoint handles actions like confirming, rejecting, cancelling, marking as paid, or completing an appointment, each triggering its own set of notifications.

## Professional Profile and Widget Initialization

The `src/app/p/[slug]/page.tsx` file serves as the entry point for a customer viewing a professional's public profile. It uses Next.js's `generateMetadata` to dynamically set SEO-friendly titles and descriptions based on the professional's `name`, `profession`, and `bio` from the `professionals` table.

Upon rendering, the page fetches the professional's details using `db.select().from(professionals).where(eq(professionals.slug, slug))`. It also determines if the current visitor is the professional themselves (`isOwner`) or a logged-in client, pre-populating the booking form with `clientData` if available from the `clients` table. This pre-population streamlines the booking process for returning users.

The core booking functionality is encapsulated within the `BookingWidget` client component. This component receives essential professional data as props, such as `slug`, `professionalName`, `sessionDuration`, `sessionPrice`, and payment-related details. This prop-drilling approach ensures the client-side widget has all necessary information without making additional API calls for static professional data. The `BookingWidget` does not display aggregated `reviews` and `avgRating`; these are displayed by the parent page component.

## Slot Selection and Availability

The `BookingWidget` component manages the interactive calendar and time slot selection. When a user selects a date, an `useEffect` hook triggers a `GET` request to `/api/booking`. This request includes the `slug` of the professional and the `date` selected.

The `GET` handler in `src/app/api/booking/route.ts` first validates these parameters. It then queries the database for the professional's `id` and `sessionDuration` from the `professionals` table. Crucially, it only selects these specific columns, avoiding the accidental exposure of sensitive professional data like `email` or `userId` to unauthenticated requests.

Next, it fetches two sets of data concurrently using `Promise.all`:
1.  `availability` rules for the professional, specifically `dayOfWeek`, `startTime`, and `endTime`.
2.  `existingAppointments` for the selected date, filtering out `rejected` and `cancelled` appointments to ensure only active bookings are considered.

These `rules` and `existingAppointments` are then returned to the `BookingWidget`. On the client side, the `generateSlots` utility function, located in `src/lib/slots.ts`, is executed by the `BookingWidget` to compute available time slots. This function iterates through the professional's defined availability for the chosen day, creating potential slots at `sessionDuration` intervals. It then filters out any slots that are in the past or conflict with `existingAppointments`, ensuring that only truly available and future slots are presented to the user. The `BookingWidget` then groups these slots into "Morning", "Afternoon", and "Evening" for better user experience.

## Booking Submission

Once a client selects a date and time slot and fills in their personal details, the `BookingWidget` submits a `POST` request to `/api/booking`. This endpoint is protected by a rate limiter, `getBookingLimiter`, which restricts requests to 5 attempts per IP address every 10 minutes, preventing abuse. If the limit is exceeded, a `429 Too Many Requests` response is returned.

A subtle but important design choice here is the `respondAfterFloor` function, which introduces a minimum response time of 250ms. This helps mitigate timing attacks, where an attacker might infer information about the existence of a client record by observing slight differences in response times between database `SELECT` and `INSERT` operations.

The request body is validated using `bookingSchema`, a Zod schema that ensures `slug`, `startsAt`, `clientName`, `clientPhone` are present and correctly formatted, and `clientEmail` is a valid email if provided. A "honeypot" field named `website` is included in the schema and the form. If a bot populates this hidden field, the server silently drops the submission and returns a fake success response, preventing spam without revealing the trap.

Before creating the appointment, the system performs several checks:
*   **Professional Existence**: Verifies the `professional` exists using their `slug`.
*   **Plan Limits**: It checks the professional's `effectivePlan` against `PLANS` defined in `src/lib/stripe`. If the plan has limits on `clients` or `appointmentsPerMonth`, it queries the `clients` and `appointments` tables to ensure these limits are not exceeded. If a new client would exceed the `clients` limit, or a new appointment would exceed the `appointmentsPerMonth` limit, a `403 Forbidden` error is returned.

The core booking logic is wrapped in a Drizzle `db.transaction` with `isolationLevel: "serializable"`. This is a critical design decision to prevent race conditions. Without it, two simultaneous booking requests for the same slot could both pass an initial conflict check and then both attempt to insert an appointment, leading to an overbooking. The serializable isolation level forces the database to re-check conditions before committing, ensuring that only one transaction succeeds if a conflict arises. If a conflict is detected (either `SLOT_TAKEN` or a `40001` SQLSTATE), a `409 Conflict` response is returned.

Inside the transaction:
1.  **Conflict Check**: It queries the `appointments` table to ensure no existing, non-rejected, non-cancelled appointment overlaps with the proposed `startsAt` and `endsAt` times.
2.  **Client Upsert**: It attempts to find an existing client for the professional based on `clientPhone` or `clientEmail`. If found, it updates the client's `email` if a new one is provided. If not found, a new client record is inserted into the `clients` table.
3.  **Appointment Insert**: Finally, a new record is inserted into the `appointments` table with the `professionalId`, `clientId`, `startsAt`, `endsAt`, and an initial `status` of `confirmed` or `pending_confirmation` based on `professional.autoConfirm`.

After a successful booking, the system dispatches a series of notifications:
*   An entry is added to the `notifications` table for the professional.
*   WhatsApp messages are sent to the client and/or professional using templates like `msgBookingConfirmed`, `msgBookingRequest`, or `msgBookingConfirmedReceipt` from `src/lib/whatsapp`.
*   An email notification is sent to the professional via `sendBookingRequestEmailToProfessional` if `professional.email` is present.
*   PostHog analytics events (`booking_received_server`, `first_booking_at`) are captured to track booking volume and professional onboarding.

## Appointment Management

The `PATCH /api/appointments/[id]/route.ts` endpoint allows for managing the status of an appointment. This route is also rate-limited by `getApiLimiter` (60 requests/minute per IP). It requires authentication via `getUser()` and checks if the authenticated user is either the `professional` or the `client` associated with the appointment.

The endpoint supports a predefined set of `ALLOWED_ACTIONS`: `confirm`, `reject`, `cancel`, `paid`, `complete`, `no_show`. Any other action results in a `400 Bad Request`.

*   **Cancel**: Both professionals and clients can cancel appointments, provided the current status is `pending_confirmation` or `confirmed`. Notifications are sent to the other party via WhatsApp (`msgCancelledByClientToPro`, `msgCancelledByProToClient`, `msgBookingCancelled`) and a notification is inserted into the `notifications` table for the professional if the client cancels.
*   **Professional-only actions**: `paid`, `complete`, `no_show` can only be performed by the professional. Each action updates the `appointments` table and triggers specific WhatsApp notifications to both the client and the professional (e.g., `msgPaymentConfirmedToClient`, `msgAppointmentCompletedToPro`, `msgNoShowToClient`).
*   **Confirm/Reject**: These actions are also professional-only. They update the `status` and `paymentStatus` in the `appointments` table. Notifications are sent to the client via the `notifications` table, WhatsApp (`msgBookingConfirmed`, `msgBookingRejected`), and email (`sendBookingConfirmedEmailToClient`, `sendBookingRejectedEmailToClient`). If the client does not have a `userId` (meaning they booked as a guest), the confirmation WhatsApp message includes a `msgRegistrationInvite` to encourage account creation.

## Design decisions

1.  **Separation of Concerns (Client vs. Server Slot Generation)**: The `BookingWidget` (client) fetches availability rules and existing appointments from `/api/booking` (server), but the actual slot generation logic resides in `src/lib/slots.ts` (server-side utility, but conceptually a pure function). This design choice allows the server to provide raw data, while the client handles the presentation and interactive filtering. A trade-off is that the client needs to re-fetch data for each date change, but this keeps the API lean and the `generateSlots` logic reusable and testable outside of a request context.
2.  **Atomic Transaction for Booking (`POST /api/booking`)**: The decision to wrap the conflict check, client upsert, and appointment insert in a `db.transaction` with `isolationLevel: "serializable"` is crucial for data integrity. This prevents race conditions where multiple users might attempt to book the same slot simultaneously. The trade-off is a slight increase in database contention and potentially higher latency for transactions, but this is acceptable for ensuring that no double-bookings occur.
3.  **Honeypot Field (`website` in `bookingSchema`)**: The inclusion of a hidden `website` field in the booking form and its validation in `src/app/api/booking/route.ts` is a simple yet effective anti-spam measure. Instead of relying on complex CAPTCHAs that degrade user experience, this passive defense catches naive bots. The trade-off is that it might not stop more sophisticated bots, but it's a low-cost, high-return solution for common spam.
4.  **Response-Time Floor (`respondAfterFloor` in `POST /api/booking`)**: Introducing a minimum response time for the `POST /api/booking` endpoint helps obscure timing differences between database operations (e.g., finding an existing client vs. inserting a new one). This is a security-conscious design to prevent timing oracle attacks, where an attacker could infer information about the system's state (like whether a phone number is associated with an existing client) by precisely measuring response times. The trade-off is a slightly slower response for legitimate users in the fastest path, but the impact is minimal (250ms floor).
5.  **Selective Column Retrieval (`GET /api/booking`)**: The `GET` handler for `/api/booking` explicitly selects only `id` and `sessionDuration` from the `professionals` table. This prevents accidental data leakage of sensitive professional information (like `email`, `phone`, `userId`, `stripeCustomerId`) to unauthenticated users who might query the API directly. This adheres to the principle of least privilege, only exposing data strictly necessary for the client-side slot generation.

## Potential improvements

1.  **Refine `generateSlots` for Recurring Schedules**: The current `generateSlots` function in `src/lib/slots.ts` only considers `availability` rules and `existingAppointments`. It does not account for `recurringSchedules` stored in the database. If a professional has recurring appointments, these should also be factored into the available slots to prevent conflicts. The `recurringSchedules` table has `dayOfWeek`, `time`, and `frequency` columns that could be used to generate recurring "blocked" slots.
2.  **Improve Client Upsert Logic in `POST /api/booking`**: The client upsert logic in `src/app/api/booking/route.ts` currently searches by `phone` OR `email`. While this is functional, it could lead to a client record being updated with a new email if a different client uses the same phone number but provides an email that matches an existing client. A more robust approach might be to prioritize matching by `userId` if the booking is made by an authenticated user, or to ensure that `phone` and `email` are unique *per professional* or globally, depending on business rules.
3.  **Centralize Notification Logic**: The notification logic in both `src/app/api/booking/route.ts` and `src/app/api/appointments/[id]/route.ts` involves multiple `sendWhatsApp` calls, `db.insert(notifications)` calls, and `sendBooking...EmailToClient` calls. This duplication makes it harder to maintain and extend. A dedicated notification service or utility function could encapsulate this logic, taking an event type (e.g., `BOOKING_CONFIRMED`, `APPOINTMENT_CANCELLED`) and relevant data, then dispatching all necessary notifications (DB, WhatsApp, Email) in a consistent manner. This would reduce boilerplate and improve testability.
