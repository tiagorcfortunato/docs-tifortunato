# Security Fixes

This document details recent security enhancements and structural improvements implemented across several core API routes and authentication flows within the Odys application. These changes address specific findings related to input validation, unauthorized actions, and data integrity, ensuring a more robust and predictable system behavior. The focus has been on tightening data schemas, enforcing access controls, and preventing unexpected state transitions, particularly in user-facing and administrative endpoints.

## Overview

The Odys application is built on a Next.js framework, utilizing Supabase for authentication and Drizzle ORM for database interactions. The system manages 11 distinct database tables, including central entities like `professionals`, `clients`, and `appointments`. These tables are interconnected, with `professionalId` and `clientId` serving as foreign keys across many related entities such as `availability`, `clientNotes`, `recurringSchedules`, `appointments`, `messages`, `follows`, and `reviews`.

The application exposes 23 API routes, handling various operations from user authentication and profile management to scheduling and notifications. Key routes discussed here include `/api/auth/register` for user creation, `/app/auth/callback` for handling authentication redirects, `/api/onboarding` for professional profile setup, and `/api/appointments/[id]` for managing appointment lifecycles.

To mitigate abuse and ensure system stability, several endpoints are protected by rate limits. For instance, `getRegisterLimiter` restricts registration attempts to 5 per hour, `getOnboardingLimiter` allows 3 onboarding attempts per hour, and `getApiLimiter` sets a general limit of 60 requests per minute for API access. The system also integrates with external services like Stripe for payments and WhatsApp for notifications, utilizing 19 distinct WhatsApp message templates to communicate with users.

## User Registration

The `/api/auth/register` route handles new user sign-ups. A critical improvement here is the introduction of Zod for input validation. The `registerSchema` object strictly defines the expected format for `email` (validated as an email string), `password` (minimum 8 characters, aligning with Supabase's default), `name` (minimum 2 characters, optional), and `type` (an optional enum of `"client"` or `"professional"`). This ensures that only well-formed data proceeds, preventing common injection vectors and malformed requests.

Before processing any registration, the route applies a rate limit using `getRegisterLimiter` based on the client's IP address. If the limit is exceeded, a `429 Too Many Requests` response is returned.

A notable design choice in this route is the conditional handling of user creation based on the `NODE_ENV`. In production, the `supabase.auth.signUp()` method is used, which automatically triggers email verification flows. In development, to accelerate testing, an `_adminClient` (initialized lazily to avoid requiring secrets during build) is used with `admin.createUser()` and `email_confirm: true`, bypassing the email verification step. This pragmatic approach balances development efficiency with production security requirements.

## Authentication Callback

The `/app/auth/callback` route is crucial for completing authentication flows, particularly after magic link or OAuth redirects. A significant security enhancement here addresses a previous vulnerability (L4 finding) where an attacker could inject arbitrary JSON into `user_metadata` via the `type` query parameter.

Now, the `type` parameter is strictly validated against a `VALID_TYPES` set, which includes `"professional"`, `"client"`, and `"recovery"`. The `parseType` function ensures that any `type` value not explicitly in this set is ignored, preventing malicious data from being written to the user's session metadata.

After exchanging the authentication code for a session, the route handles different redirection scenarios. For password recovery (`type === "recovery"`), it redirects to `/reset-password`. If a valid `type` (`"professional"` or `"client"`) is present, the user's metadata is updated accordingly.

A "smart-linking" feature is also implemented: if a newly authenticated user (whose email has just been verified by Supabase) has an existing `clients` record with the same email but no associated `userId`, that `clients` record is updated to link to the new `user.id`. This helps consolidate user data when a client registers after previously interacting with the system anonymously or via a professional.

## Professional Onboarding

The `/api/onboarding` route allows new professionals to set up their profiles. This endpoint is also protected by `getOnboardingLimiter` to prevent abuse.

Input validation is enforced by the `onboardingSchema`, a Zod object that mandates fields like `name`, `profession`, `phone`, `sessionDuration`, `sessionPrice`, and `availability`. It also includes optional fields such as `bio`, `serviceType`, `city`, and `state`, with specific constraints like `max(480)` for `sessionDuration` and regex validation for `startTime` and `endTime` in the `availability` array.

A key improvement here is the robust slug generation logic. The `RESERVED_SLUGS` set contains a list of application-level routes (e.g., `"api"`, `"auth"`, `"dashboard"`) that professional profile slugs must not conflict with. The `generateUniqueSlug` function first converts the professional's name to a slug using `toSlug`. It then checks if this base slug is reserved or already exists in the `professionals` table. If a conflict occurs, it appends a numeric suffix (e.g., `user-2`, `john-doe-3`) until a unique, non-reserved slug is found. This prevents URL shadowing and ensures clean, predictable profile URLs.

The onboarding process is idempotent: if a professional record already exists for the authenticated `userId`, the existing record is returned without creating a duplicate. Upon successful creation, the user's Supabase metadata is updated to reflect their `type` as "professional" and their `name`. A welcome email is sent to the professional in production environments, leveraging the `sendProfessionalWelcomeEmail` utility.

## Appointment Management

The `/api/appointments/[id]` PATCH route is responsible for updating appointment statuses. This critical endpoint is protected by `getApiLimiter`.

A significant security fix here involves explicitly whitelisting allowed actions. The `ALLOWED_ACTIONS` set (`"confirm"`, `"reject"`, `"cancel"`, `"paid"`, `"complete"`, `"no_show"`) ensures that only predefined state transitions can occur. Previously, an unknown action (e.g., a typo) could lead to an unintended state change. Now, any action not in `ALLOWED_ACTIONS` results in a `400 Bad Request` response, preventing silent failures or unexpected behavior. This check is performed after ownership verification, ensuring that unauthorized users receive a `403 Forbidden` before an "unknown action" error, avoiding an existence oracle.

The route performs thorough authorization checks, determining if the authenticated user is the `isProfessional` or `isClient` associated with the appointment. Different actions have different ownership requirements:
*   **Cancel**: Both professional and client can cancel, but only if the appointment status is `"pending_confirmation"` or `"confirmed"`.
*   **Paid, Complete, No Show**: Only the professional can perform these actions.
*   **Confirm/Reject**: Only the professional can perform these actions.

Upon a successful status update, the system sends various notifications. This includes inserting records into the `notifications` table for client-side alerts and sending WhatsApp messages using specific templates (e.g., `msgCancelledByClientToPro`, `msgBookingConfirmed`, `msgPaymentConfirmedToClient`). Email notifications are also dispatched for booking confirmations and rejections if the client's email is available.

## Design decisions

*   **Zod for Schema Validation**: The adoption of Zod for defining `registerSchema` and `onboardingSchema` provides a declarative, type-safe way to validate incoming request bodies. This decision significantly improves data integrity, reduces the risk of malformed data entering the system, and centralizes validation logic, making it easier to understand and maintain.
*   **Rate Limiting on Critical Endpoints**: Implementing `getRegisterLimiter`, `getOnboardingLimiter`, and `getApiLimiter` on respective routes is a proactive measure to prevent brute-force attacks, denial-of-service attempts, and general API abuse. This protects system resources and ensures fair usage.
*   **Explicit Action Whitelisting (`ALLOWED_ACTIONS`)**: In the `/api/appointments/[id]` route, defining a `Set` of `ALLOWED_ACTIONS` is a direct security hardening. It prevents the system from entering undefined states due to unexpected or malicious input, ensuring that only valid state transitions are permitted. This eliminates a class of bugs and potential vulnerabilities.
*   **Reserved Slugs for Onboarding**: The `RESERVED_SLUGS` set and the `generateUniqueSlug` function in `/api/onboarding` prevent professionals from choosing profile URLs that conflict with core application routes. This design choice avoids routing ambiguities, potential SEO issues, and ensures a consistent user experience.
*   **Conditional Supabase Authentication Flow**: The `NODE_ENV` check in `/api/auth/register` to use `supabase.auth.signUp()` in production (with email verification) and `admin.createUser()` in development (skipping verification) is a pragmatic trade-off. It prioritizes developer velocity during local testing while maintaining the necessary security posture for live environments.
*   **Strict Type Validation in Auth Callback**: The `VALID_TYPES` set and `parseType` function in `/app/auth/callback` directly address a security finding by preventing arbitrary values from being written to user metadata. This decision protects the integrity of user profiles and prevents potential privilege escalation or data corruption.

## Potential improvements

1.  **Centralized API Response Handling**: The current API routes frequently return `NextResponse.json({ error: "..." }, { status: ... })` directly. While functional, this pattern is repeated across `src/app/api/auth/register/route.ts`, `src/app/api/onboarding/route.ts`, and `src/app/api/appointments/[id]/route.ts`. A more centralized error handling utility or a custom `Response` class could standardize error formats, simplify error reporting, and reduce boilerplate, making the API more consistent and easier to maintain.
2.  **Decoupling Notification Logic**: In `src/app/api/appointments/[id]/route.ts`, the logic for sending WhatsApp messages and emails is tightly coupled with the appointment status update logic. This leads to many direct calls to `sendWhatsApp` and `sendBookingConfirmedEmailToClient`. Decoupling this into a dedicated notification service or event-driven system could improve modularity, allow for easier testing of notification flows, and enable future expansion to other notification channels without modifying core business logic.
3.  **Enhanced Slug Generation for Internationalization**: The `toSlug` function in `src/app/api/onboarding/route.ts` uses `normalize("NFD").replace(/[\u0300-\u036f]/g, "")` to handle diacritics. While effective for many Latin-based languages, it might not be sufficient for names in non-Latin scripts or more complex character sets. Depending on the target audience, expanding the slug generation to support a wider range of international characters or offering manual slug customization could be beneficial.
4.  **Broader Client Smart-Linking**: The smart-linking feature in `src/app/auth/callback/route.ts` currently only links `clients` records to a `userId` if the `type` is explicitly `"client"`. It might be valuable to consider if a professional registering could also have an existing client record that should be linked, especially if they previously interacted with the platform as a client. This would ensure a more complete user profile across different roles.
