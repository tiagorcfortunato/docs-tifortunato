# Security Fixes

This document details recent enhancements to Odys's security posture, focusing on critical fixes and the implementation of more rigorous validation and access control mechanisms. These updates span user registration, authentication callbacks, professional onboarding, and appointment management, ensuring data integrity and preventing unauthorized actions. The system relies on a Drizzle ORM schema with `11` tables, exposing `23` API routes, and integrating with external services like Supabase, Stripe, and WhatsApp.

## Overview

The Odys platform manages a variety of entities, central to which are `professionals` and `clients`. The `professionals` table, with its `32` columns, stores comprehensive details including `userId`, `slug`, `phone`, `email`, and various service-related configurations like `sessionDuration` and `sessionPrice`. The `clients` table, with `8` columns, tracks client information, notably linking to a `professionalId` and optionally a `userId`. Appointments are managed in the `appointments` table, which has `13` columns and references both `professionalId` and `clientId`.

The API surface includes `23` routes, with critical endpoints like `/api/auth/register`, `/api/onboarding`, and `/api/appointments/[id]` being central to user and professional lifecycle management. Rate limiting is applied to several key routes, including `booking`, `api`, `onboarding`, `register`, `whatsapp`, and `aichat`, to mitigate abuse. The system also uses `19` distinct WhatsApp message templates for various notifications and interactions, and integrates with Stripe for payment processing, handling events like `checkout.session.completed` and `customer.subscription.updated`.

## User Registration

The `/api/auth/register` route handles new user sign-ups. It employs Zod for input validation, ensuring that incoming data for `email`, `password`, `name`, and `type` adheres to predefined schemas. For instance, the `registerSchema` mandates a minimum password length of `8` characters, aligning with Supabase's default authentication requirements.

Before processing any registration request, the system applies rate limiting using `getRegisterLimiter`, which permits only `5` registration attempts per hour from a given IP address. This helps prevent brute-force attacks or excessive account creation.

A key design choice in this route is the conditional user creation logic based on the `NODE_ENV` environment variable. In `production`, the `supabase.auth.signUp()` method is used, which automatically triggers email verification flows. This ensures that users confirm their email addresses before gaining full access, a standard security practice. Conversely, in `development`, an `adminClient` (initialized with the `SUPABASE_SERVICE_ROLE_KEY`) is used to call `admin.createUser` with `email_confirm: true`. This bypasses the email verification step, accelerating the development and testing cycle by allowing developers to quickly create pre-confirmed users. The `requiresEmailConfirmation` flag in the response informs the client-side application whether further verification steps are needed.

## Authentication Callback

The `/auth/callback` route is crucial for handling redirects from Supabase after authentication events, such as email verification or password recovery. A significant security enhancement here addresses a previous vulnerability (L4 finding) where an attacker could inject arbitrary JSON into user metadata via the `type` query parameter.

To mitigate this, the `VALID_TYPES` set explicitly defines the only accepted values for the `type` parameter: `"professional"`, `"client"`, and `"recovery"`. The `parseType` function strictly filters the incoming `type` value, ignoring anything outside this closed set. This prevents malicious data from being written into `user_metadata` during the `supabase.auth.updateUser` call.

Upon successful session exchange, the route handles different scenarios:
*   If `type` is `"recovery"`, the user is redirected to `/reset-password`.
*   If `type` is `"professional"` or `"client"`, the user's `user_metadata` in Supabase is updated to reflect their role.
*   A "Smart-linking" mechanism is implemented for clients: if a user's email is verified (which happens during this callback) and they are identified as a `"client"`, the system attempts to link their new `userId` to any existing entries in the `clients` table that have the same `email` but a `null` `userId`. This ensures that pre-existing client records, perhaps created through an appointment booking without a prior user account, are correctly associated with a registered user.

## Professional Onboarding

The `/api/onboarding` route facilitates the creation of professional profiles. It is protected by `getOnboardingLimiter`, allowing only `3` attempts per hour to prevent abuse.

The `onboardingSchema` uses Zod to validate all incoming professional data, including `name`, `profession`, `phone`, `bio`, `sessionDuration`, `sessionPrice`, `serviceType`, `city`, `state`, and `availability`. This ensures that all required fields are present and conform to expected types and constraints (e.g., `sessionDuration` must be a positive integer up to `480` minutes).

A critical feature is the `generateUniqueSlug` function, which creates a URL-friendly identifier for the professional's public profile. This function incorporates the `RESERVED_SLUGS` set, which contains `15` predefined routes like `"api"`, `"auth"`, and `"dashboard"`. If a professional's name would slugify into one of these reserved paths, or if the base slug is already taken, `generateUniqueSlug` automatically appends a numeric suffix (e.g., `user-2`) to ensure uniqueness and prevent URL collisions with core application routes. This prevents a professional's profile from shadowing or being shadowed by a system route.

The onboarding process is idempotent: if a professional profile already exists for the authenticated `userId`, the existing profile is returned, preventing duplicate entries. If a new profile is created, it's inserted into the `professionals` table, and their `availability` is recorded in the `availability` table. Finally, the user's Supabase `user_metadata` is updated to reflect their `"professional"` type and name. A welcome email is sent to the professional in `production` environments via `sendProfessionalWelcomeEmail`.

## Appointment Management

The `/api/appointments/[id]` route, specifically its `PATCH` method, allows for managing the status and payment status of appointments. This route is also rate-limited by `getApiLimiter`, allowing `60` requests per minute.

A significant fix here addresses the "unknown action 400" issue. Previously, an unrecognized `action` parameter could lead to unexpected behavior. Now, the `ALLOWED_ACTIONS` set explicitly defines the `6` permissible actions: `"confirm"`, `"reject"`, `"cancel"`, `"paid"`, `"complete"`, and `"no_show"`. Any request with an `action` not in this set will explicitly return a `400` status with an "Unknown action" error. This prevents silent failures and ensures that only intended state transitions occur.

Before any action is processed, the system verifies that the authenticated user has the necessary permissions, checking if they are the `professional` associated with the appointment or the `client`. This prevents unauthorized users from manipulating appointment statuses.

The route handles various actions:
*   **Cancel**: Both clients and professionals can cancel appointments, provided the status is `"pending_confirmation"` or `"confirmed"`. Notifications are sent to the counterparty via `notifications` table insertion and WhatsApp messages (e.g., `msgCancelledByClientToPro`, `msgBookingCancelled`).
*   **Paid, Complete, No Show**: These actions are restricted to the `professional`. They update the `paymentStatus` or `status` of the appointment and trigger relevant WhatsApp notifications to both client and professional (e.g., `msgPaymentConfirmedToClient`, `msgNoShowToPro`).
*   **Confirm / Reject**: These actions are also restricted to the `professional`. They update the appointment's `status` and `paymentStatus` accordingly. Notifications are sent to the client via the `notifications` table, WhatsApp (e.g., `msgBookingConfirmed`, `msgBookingRejected`), and email (`sendBookingConfirmedEmailToClient`). If a client does not have a `userId` yet, a `msgRegistrationInvite` is appended to the WhatsApp message to encourage registration.

## Design decisions

*   **Zod for Input Validation**: The choice to use Zod for schemas like `registerSchema` and `onboardingSchema` provides a declarative and type-safe way to define expected data structures and constraints. This centralizes validation logic, making it easier to understand what constitutes valid input and automatically generates detailed error messages for invalid requests, improving API usability and preventing malformed data from reaching the database.
*   **Rate Limiting**: Implementing rate limits via `getRegisterLimiter` and `getApiLimiter` is a fundamental security measure. It protects against various forms of abuse, such as brute-force attacks on registration, denial-of-service attempts, and excessive resource consumption, by controlling the frequency of requests from individual IP addresses.
*   **Explicit Action Whitelisting**: The `ALLOWED_ACTIONS` set in the `PATCH /api/appointments/[id]` route is a direct response to a potential vulnerability. By explicitly whitelisting acceptable actions, the system prevents unexpected state changes or silent failures that could arise from typos or malicious attempts to invoke non-existent actions. This "deny by default" approach enhances the predictability and security of critical state-changing operations.
*   **Reserved Slugs**: The `RESERVED_SLUGS` set in the onboarding process is a proactive measure to maintain URL integrity and prevent conflicts. It ensures that public professional profile URLs (`/p/[slug]`) do not clash with core application routes, which could lead to routing errors or obscure legitimate content. This design prioritizes system stability and user experience.
*   **Conditional Supabase Admin Client**: The distinction between using `supabase.auth.signUp()` in production and `admin.createUser()` in development for user registration reflects a pragmatic trade-off. In production, the emphasis is on security and proper user lifecycle management (email verification). In development, the priority shifts to developer velocity, allowing quick testing without the overhead of email confirmation. This balances security needs with practical development realities.
*   **Smart-linking Clients**: The logic in `/auth/callback` to link unauthenticated `clients` to newly verified `userId`s is a user experience enhancement. It allows users who booked appointments as guests to seamlessly associate their past interactions with their new account once they register and verify their email, reducing data fragmentation and improving the client's historical view.

## Potential improvements

*   **Centralized Error Handling**: While `serverError` is used in some places (e.g., `POST /api/onboarding`), other routes like `POST /api/auth/register` and `PATCH /api/appointments/[id]` still use `NextResponse.json({ error: ... }, { status: ... })` directly. Consolidating all error responses through a single helper function could ensure consistent error formats, logging, and status codes across the API, making client-side error handling more predictable.
*   **Robust Slug Generation for Edge Cases**: The `toSlug` function in `src/app/api/onboarding/route.ts` might produce an empty string for names consisting solely of diacritics or special characters (e.g., "---"). While `generateUniqueSlug` handles this by falling back to `"user"`, `toSlug` could be enhanced to ensure a non-empty base string is always produced, perhaps by including a fallback character or a more aggressive transliteration if the initial slug is empty.
*   **Structured WhatsApp/Email Error Handling**: The current `sendWhatsApp(...).catch(console.warn)` and `sendProfessionalWelcomeEmail(...).catch(console.warn)` patterns in `src/app/api/onboarding/route.ts` and `src/app/api/appointments/[id]/route.ts` are basic. For critical communications, implementing more structured error handling, such as retries with exponential backoff, dead-letter queues, or dedicated logging to an error monitoring service, would improve reliability and observability.
*   **`type` Parameter Security in `auth/callback`**: While the `VALID_TYPES` set in `src/app/auth/callback/route.ts` effectively prevents arbitrary data injection, the `type` parameter itself is still passed via a URL query string. For highly sensitive operations, consider passing such context via a signed JWT in the `state` parameter of the OAuth flow, or storing it server-side and retrieving it with a short-lived token, to prevent tampering or leakage of even valid, but potentially sensitive, context.
