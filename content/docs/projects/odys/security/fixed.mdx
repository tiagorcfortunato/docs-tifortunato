# Security Fixes

This document details recent security enhancements and structural improvements implemented across key API routes and authentication flows within the Odys platform. These changes focus on tightening input validation, preventing unauthorized actions, and ensuring data integrity, building upon previous findings and proactive development.

## Overview

The Odys platform is built around a PostgreSQL database managed by Drizzle ORM, featuring 11 distinct tables such as `professionals`, `clients`, `appointments`, and `messages`. Interactions with this data are primarily facilitated through 23 API routes, including critical paths for user authentication, onboarding, and appointment management. The system also integrates with external services like Supabase for authentication, Stripe for payments, and WhatsApp for notifications, utilizing 19 distinct message templates. To maintain stability and prevent abuse, various rate limits are in place, covering actions like `booking`, `api` calls, `onboarding`, and `register` attempts.

The recent updates specifically target several areas identified for improvement, including the secure handling of user registration, the integrity of authentication callbacks, the robustness of professional onboarding, and the precise control over appointment state transitions.

## User Registration

The `/api/auth/register` API route handles new user sign-ups. A critical aspect of this route is its input validation and rate limiting.

The route employs `getRegisterLimiter()` to restrict registration attempts from a single IP address to 5 requests per hour, mitigating brute-force or spam registration attacks. This is a crucial first line of defense against abuse.

Input validation is performed using Zod, with the `registerSchema` defining the expected structure and constraints for user data. For instance, `email` must be a valid email format, and `password` must be at least 8 characters long, aligning with Supabase's default authentication requirements. The `name` and `type` fields are optional, allowing for flexible registration flows. If validation fails, the API responds with a `400` status and detailed field errors, providing clear feedback without exposing internal server details.

A notable design choice is the conditional user creation logic based on the `NODE_ENV` environment variable. In `production`, the `supabase.auth.signUp()` method is used with the anonymous key. This approach automatically triggers Supabase's email verification flow, which is essential for confirming user identities. Conversely, in `development`, an `adminClient` (initialized lazily to avoid build-time environment variable issues) is used with `admin.createUser({ email_confirm: true })`. This bypasses email verification, accelerating the development and testing cycle. The `requiresEmailConfirmation` flag in the response informs the client whether an email verification step is necessary.

## Authentication Callback

The `/app/auth/callback` route is responsible for processing Supabase authentication redirects, particularly after magic link or OAuth flows. A significant security enhancement here addresses a previous L4 finding related to arbitrary metadata injection.

The `type` query parameter, which indicates the user's role (e.g., "professional", "client", "recovery"), is now strictly validated against a `VALID_TYPES` `Set`. The `parseType` function ensures that only explicitly allowed values are accepted, preventing an attacker from crafting a malicious callback URL to inject arbitrary JSON into the user's session metadata. Any unrecognized `type` is simply ignored, defaulting to `null`.

After exchanging the authentication code for a session, the route handles different redirection scenarios:
*   If `type` is "recovery", the user is redirected to `/reset-password`.
*   If `type` is "professional" or "client", the user's Supabase metadata is updated to reflect their role.
*   A "smart-linking" mechanism is implemented for clients: if a user's email is verified and they are identified as a "client", the system attempts to link their `userId` to any existing `clients` records that have the same email but no associated `userId`. This helps consolidate user profiles after email verification.

Finally, the user is redirected to `/auth/redirect` or `/login?error=auth` depending on the outcome. The `origin` for redirection is carefully constructed using `x-forwarded-host` headers to prevent open redirect vulnerabilities.

## Professional Onboarding

The `/api/onboarding` route facilitates the initial setup for professionals joining the platform. This route also incorporates rate limiting via `getOnboardingLimiter()`, allowing 3 attempts per hour to prevent abuse during the onboarding process.

The endpoint is designed to be idempotent: if a professional record already exists for the authenticated user, it simply returns the existing data, avoiding duplicate entries.

Input validation for onboarding data is handled by the `onboardingSchema` using Zod. This schema enforces detailed constraints, such as `name` having a minimum length of 2 characters, `sessionDuration` being a positive integer up to 480 minutes, and `sessionPrice` being non-negative. The `availability` array is also validated, ensuring each entry has a valid `dayOfWeek` (0-6) and correctly formatted `startTime` and `endTime` strings.

A key security and usability improvement is the `generateUniqueSlug` function. This function creates a URL-friendly slug from the professional's name. It incorporates a `RESERVED_SLUGS` `Set` containing critical application routes (e.g., "api", "auth", "dashboard"). If the generated slug conflicts with a reserved route or an existing professional's slug, it automatically appends a numeric suffix (e.g., "john-doe-2") to ensure uniqueness and prevent URL shadowing. This prevents malicious users from registering slugs that could impersonate or interfere with core application paths.

Upon successful validation and slug generation, a new record is inserted into the `professionals` table, and their availability is stored in the `availability` table. The user's Supabase metadata is also updated to reflect their "professional" type and name. A welcome email is sent to the professional in production environments, but skipped in development to avoid unnecessary email traffic.

## Appointment Management

The `/api/appointments/[id]` PATCH route allows professionals and clients to update the status of appointments. This route is protected by `getApiLimiter()`, restricting general API calls to 60 per minute.

A significant security fix here addresses the "unknown action 400" issue. The `action` parameter, sent in the request body, is now explicitly validated against an `ALLOWED_ACTIONS` `Set` (e.g., "confirm", "reject", "cancel", "paid", "complete", "no_show"). If an unknown action is provided, the API returns a `400` status. This prevents unexpected state transitions due to typos or malicious input. This check is performed *after* ownership verification, ensuring that unauthorized users receive a `403` error before any `400` response that might reveal information about the appointment's existence.

The route performs comprehensive authorization checks, determining if the requesting user is the `isProfessional` or `isClient` associated with the appointment. Different actions have different authorization requirements:
*   **Cancel**: Both professionals and clients can cancel, but only if the appointment status is "pending_confirmation" or "confirmed". Notifications are sent via WhatsApp to the relevant parties.
*   **Paid, Complete, No Show**: These actions are restricted to the `isProfessional`. Each action updates the appointment status or payment status and triggers specific WhatsApp messages to both the client and professional.
*   **Confirm/Reject**: These actions are also restricted to the `isProfessional`. They update the appointment's `status` and `paymentStatus` accordingly. Notifications are sent to the client (if they have a `userId`) and WhatsApp messages, along with emails, are dispatched to both parties, providing updates on the booking status.

The use of `toLocaleDateString` and `toLocaleTimeString` ensures that date and time strings in messages are localized for "pt-BR", enhancing user experience.

## Design decisions

*   **Zod for Input Validation**: The consistent use of Zod schemas (e.g., `registerSchema`, `onboardingSchema`) across API routes is a deliberate choice to enforce data integrity and type safety at the API boundary. This provides clear, structured error messages to clients and prevents malformed data from reaching the application logic or database. It shifts validation left, catching issues early.
*   **Rate Limiting**: Implementing specific rate limiters (`getRegisterLimiter`, `getOnboardingLimiter`, `getApiLimiter`) for different types of operations reflects a nuanced approach to resource protection. Instead of a single global limit, critical or resource-intensive operations are individually throttled, balancing user experience with system resilience against abuse.
*   **Explicit Action Whitelisting**: The `ALLOWED_ACTIONS` `Set` in the appointment PATCH route is a strong security pattern. By explicitly defining and checking against a whitelist of permissible actions, the system prevents unexpected behavior from arbitrary or malformed requests, directly addressing the "unknown action 400" finding.
*   **Reserved Slugs**: The `RESERVED_SLUGS` `Set` and the `generateUniqueSlug` function in the onboarding process are designed to protect the application's URL structure. This prevents users from creating profiles with slugs that could conflict with or impersonate core application routes, maintaining navigational integrity and preventing potential phishing vectors.
*   **Conditional Supabase Client Usage**: The distinction between using `supabase.auth.signUp()` in production and `admin.createUser()` in development for user registration is a pragmatic trade-off. It allows for a streamlined, email-verification-free development workflow while maintaining the full security posture of email confirmation in production.
*   **Sanitized Callback Parameters**: The `VALID_TYPES` `Set` and `parseType` function in the authentication callback are crucial for preventing arbitrary data injection into user metadata. This directly addresses a security finding by ensuring that only expected and safe values from external redirects are processed, protecting the integrity of user profiles.

## Potential improvements

1.  **Centralize API Error Handling**: While `serverError`, `unauthorized`, `forbidden`, `notFound`, `badRequest`, and `tooManyRequests` helpers are used in `src/app/api/appointments/[id]/route.ts` and `src/app/api/onboarding/route.ts`, the `src/app/api/auth/register/route.ts` file still directly uses `NextResponse.json({ error: ... }, { status: ... })` for various error conditions (429, 400, 500). Consolidating all API error responses through a consistent set of helper functions would improve maintainability, ensure uniform error formats, and reduce the chance of accidentally exposing sensitive information.
2.  **Robust Communication Error Handling**: The `sendWhatsApp` and `sendBookingConfirmedEmailToClient` calls in `src/app/api/appointments/[id]/route.ts` and `src/app/api/onboarding/route.ts` use `.catch(console.warn)`. For critical communications like appointment confirmations or rejections, a simple `console.warn` might not be sufficient. Consider implementing a more robust error handling strategy, such as logging to a dedicated error tracking service, retrying failed messages, or notifying an administrator, especially for production environments.
3.  **Refine `generateUniqueSlug` Fallback**: In `src/app/api/onboarding/route.ts`, the `generateUniqueSlug` function uses `effectiveBase = base || "user"`. While this handles cases where `toSlug(body.name)` results in an empty string, the choice of "user" as a fallback is somewhat generic. Depending on product requirements, a more descriptive or randomized fallback (e.g., "professional-uuid") could be considered to further differentiate these edge cases, or a more explicit error could be thrown if a name cannot yield a meaningful slug.
