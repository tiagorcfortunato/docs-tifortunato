# Security Fixes

Odys has recently implemented a series of enhancements to bolster the application's security posture and overall stability. These changes address critical areas such as input validation, API authorization, and resource protection, ensuring a more predictable and secure user experience. This document explores the architectural decisions and specific code implementations behind these improvements, providing a comprehensive understanding of their impact.

## Overview

The Odys platform is built upon a modern stack, leveraging Next.js for its API routes, Supabase for authentication, and Drizzle ORM for database interactions. The system manages a total of 11 distinct database tables, including `professionals`, `clients`, `appointments`, and `notifications`, which are central to the application's functionality. Interactions with these tables are primarily facilitated through 23 API routes, with critical operations protected by rate limits on endpoints like `/api/booking`, `/api/onboarding`, and `/api/auth/register`. The application also incorporates scheduled tasks via cron jobs, such as `/api/cron/reminders` and `/api/cron/whatsapp-watchdog`, to automate essential processes.

The recent fixes focus on hardening several key API endpoints, particularly those involved in user registration, authentication callbacks, professional onboarding, and appointment management. These improvements introduce stricter input validation using Zod, implement explicit whitelisting for sensitive actions, and refine authorization checks to prevent unauthorized data manipulation.

## Registration Endpoint Hardening

The `/api/auth/register` endpoint, responsible for new user sign-ups, has received significant attention to prevent abuse and ensure data integrity.

The route begins by applying a rate limit using `getRegisterLimiter()`, which restricts registration attempts based on the client's IP address. This mechanism, configured with a limit of 5 attempts per hour, helps mitigate brute-force attacks and spam registrations. If the limit is exceeded, the API responds with a `429 Too Many Requests` status.

Input validation is now strictly enforced using the `registerSchema` Zod object. This schema defines the expected structure and constraints for registration data:
*   `email`: Must be a valid email string.
*   `password`: Requires a minimum length of 8 characters, aligning with Supabase's default authentication requirements. This parity ensures that client-side validation matches server-side enforcement.
*   `name`: Optional, but if provided, must be at least 2 characters long.
*   `type`: Optional, but if present, must be one of `"client"` or `"professional"`.

Any request body that fails to conform to this schema results in a `400 Bad Request` response, detailing the specific field errors. This early validation prevents malformed data from reaching the authentication layer.

The user creation process is conditionally handled based on the environment:
*   In `production`, `supabase.auth.signUp()` is used. This method automatically triggers Supabase's email verification flow, which is crucial for confirming user identities. The `requiresEmailConfirmation` flag is set based on whether a session is immediately returned.
*   In `development`, an `adminClient` (initialized with the `SUPABASE_SERVICE_ROLE_KEY`) is used to call `admin.createUser()` with `email_confirm: true`. This bypasses the email verification step, accelerating the development and testing cycle. The `_adminClient` is lazy-initialized to avoid requiring environment variables during build processes where secrets might be stripped.

This dual approach balances the need for strong security in production with efficient development workflows.

## Authentication Callback Refinements

The `/src/app/auth/callback/route.ts` endpoint handles redirects from Supabase after authentication events, such as email verification or password resets. A key improvement here addresses a potential vulnerability (identified as an L4 finding) where an attacker could inject arbitrary JSON into a user's `user_metadata` via a crafted OAuth callback URL.

To mitigate this, the `type` query parameter is now strictly validated against a `VALID_TYPES` `Set`, which explicitly allows only `"professional"`, `"client"`, and `"recovery"`. The `parseType` function ensures that any `type` value not present in this set is ignored, preventing the injection of unauthorized or malformed data into the user's session metadata.

After successfully exchanging the authentication code for a session, the route performs several actions:
*   If `type` is `"recovery"`, the user is redirected to `/reset-password`.
*   If `type` is `"professional"` or `"client"`, the user's `user_metadata` in Supabase is updated to reflect their role.
*   A "smart-linking" mechanism is implemented for clients: if a `user.id` is available (meaning the email has just been verified by Supabase) and the `type` is `"client"`, the system attempts to link the new `userId` to any existing `clients` records that have the same email but a `null` `userId`. This helps consolidate user accounts and prevent duplicate client entries.

Finally, the user is redirected to `/auth/redirect` or `/login?error=auth` if an error occurs. The `origin` for redirects is carefully constructed using `x-forwarded-host` and `x-forwarded-proto` headers to ensure correct routing in production environments, particularly when deployed on platforms like Vercel.

## Professional Onboarding Validation

The `/api/onboarding` endpoint facilitates the initial setup for new professionals. This route is also protected by `getOnboardingLimiter()`, allowing only 3 attempts per hour to prevent abuse.

The `onboardingSchema` uses Zod to validate all incoming data, ensuring that professional profiles are created with complete and correctly formatted information. Key validations include:
*   `name`, `profession`, `phone`: Required strings with minimum lengths.
*   `bio`, `city`, `state`: Optional strings with maximum lengths.
*   `sessionDuration`: An integer representing minutes, positive and capped at 480.
*   `sessionPrice`: A non-negative integer.
*   `serviceType`: An enum restricted to `"in_person"`, `"online"`, or `"both"`.
*   `availability`: An array of objects, each defining `dayOfWeek` (0-6), `startTime`, and `endTime` (both regex-validated to `HH:MM` format). At least one availability slot is required.

A critical aspect of onboarding is the generation of a unique, user-friendly `slug` for the professional's public profile page. The `toSlug` function converts the professional's name into a URL-safe format. The `generateUniqueSlug` function then ensures this slug is unique and does not conflict with any of the `RESERVED_SLUGS`. This `Set` contains a predefined list of application routes (e.g., `"api"`, `"auth"`, `"dashboard"`) to prevent URL collisions and maintain routing integrity. If a generated slug is empty or conflicts with a reserved route or an existing professional's slug, a numeric suffix is appended (e.g., `user-2`, `john-doe-3`) until a unique slug is found.

The onboarding process is idempotent: if a professional already exists for the current `user.id`, the existing record is returned, preventing duplicate entries. Upon successful validation and slug generation, a new record is inserted into the `professionals` table, and their `availability` is added to the `availability` table. The user's Supabase metadata is also updated to reflect their `professional` type and `name`. In production, a welcome email is sent to the professional.

## Appointment Action Whitelisting

The `/api/appointments/[id]` PATCH endpoint allows professionals and clients to update the status of an appointment. This route is protected by `getApiLimiter()`, which permits 60 requests per minute.

A significant improvement here is the introduction of the `ALLOWED_ACTIONS` `Set`, which explicitly whitelists permissible actions: `"confirm"`, `"reject"`, `"cancel"`, `"paid"`, `"complete"`, and `"no_show"`. This prevents an "unknown action" from being processed, which previously could lead to silent failures or unintended state changes if a typo occurred in the action parameter. Now, any action not in this set results in a `400 Bad Request` response. This check is performed after determining user ownership (`isProfessional`, `isClient`) to avoid leaking information about appointment existence to unauthorized callers.

The route performs robust authorization checks:
*   `cancel` action can be performed by either a professional or a client, but only if the appointment status is `pending_confirmation` or `confirmed`.
*   `paid`, `complete`, and `no_show` actions are restricted to professionals only.
*   `confirm` and `reject` actions are also restricted to professionals.

Each action triggers specific updates to the `appointments` table (e.g., `status`, `paymentStatus`), sends relevant `notifications` to the client or professional, and dispatches WhatsApp messages using various templates like `msgBookingConfirmed` or `msgCancelledByClientToPro`. Email notifications are also sent for booking confirmations and rejections when a client email is available. This comprehensive messaging ensures all parties are informed of status changes.

## Design decisions

Several core design decisions underpin these recent security and robustness improvements:

*   **Zod for Schema Validation**: The choice of Zod for defining `registerSchema` and `onboardingSchema` provides a declarative, type-safe way to validate incoming request bodies. This approach shifts validation logic to the edge of the API, rejecting malformed requests early and reducing the attack surface. It also provides clear error messages, aiding both developers and users.
*   **Rate Limiting**: Implementing rate limits via `getRegisterLimiter()` and `getOnboardingLimiter()` on sensitive endpoints like registration and onboarding is a fundamental defense against automated abuse, such as account enumeration or denial-of-service attempts. The specific limits (e.g., 5/hour for registration, 3/hour for onboarding) are chosen to allow legitimate usage while deterring malicious activity.
*   **Conditional Supabase Client Usage**: The distinction between using `supabase.auth.signUp()` with an anonymous key in production and `admin.createUser()` with a service role key in development for user creation is a pragmatic trade-off. It allows for the full email verification flow in production, which is a security best practice, while enabling faster, unencumbered testing in development.
*   **Explicit Whitelisting for Input and Actions**: The use of `Set`s for `VALID_TYPES` in the auth callback and `ALLOWED_ACTIONS` in the appointments API is a strong security pattern. Instead of trying to blacklist potentially harmful inputs or actions, this approach explicitly defines what is permitted, making it much harder for unexpected or malicious values to bypass checks. This directly addresses the L4 finding regarding arbitrary `user_metadata` injection.
*   **Reserved Slugs for URL Integrity**: The `RESERVED_SLUGS` `Set` and the `generateUniqueSlug` function are crucial for maintaining the integrity of the application's URL structure. By preventing user-generated slugs from conflicting with internal routes, the system avoids broken links, routing ambiguities, and potential SEO issues.
*   **Idempotency in Onboarding**: Checking for an existing professional before creating a new one in the `/api/onboarding` route ensures that repeated requests from the same user do not lead to duplicate data or unexpected side effects. This makes the API more resilient to network retries and client-side errors.

## Potential improvements

While the recent fixes significantly enhance the application's security and stability, several areas present opportunities for further refinement:

1.  **Enhanced Password Policy**: In `src/app/api/auth/register/route.ts`, the `password: z.string().min(8)` validation currently only enforces a minimum length. A more comprehensive password policy could be implemented within the Zod schema to require a mix of character types (e.g., uppercase, lowercase, numbers, symbols). This would strengthen user account security beyond what Supabase enforces by default, making passwords harder to guess or crack.
2.  **Centralized URL Construction**: The `src/app/auth/callback/route.ts` constructs the `origin` URL using `req.headers.get("x-forwarded-host") ?? req.headers.get("host") ?? req.nextUrl.host`. While functional, this logic is duplicated or similar across various routes that perform redirects. Centralizing this URL construction into a utility function or a configuration object would reduce redundancy, improve maintainability, and ensure consistent behavior across the application, potentially preventing subtle bugs related to environment-specific header variations.
3.  **Dynamic Reserved Slugs**: The `RESERVED_SLUGS` `Set` in `src/app/api/onboarding/route.ts` is a hardcoded list. As the application grows, new top-level routes might be added, requiring manual updates to this list. A more dynamic approach could involve programmatically extracting top-level route paths from the Next.js routing configuration at build time or runtime. This would ensure the `RESERVED_SLUGS` list is always up-to-date, preventing future slug collisions without manual intervention.
4.  **Consolidate Messaging Logic**: In `src/app/api/appointments/[id]/route.ts`, the logic for sending WhatsApp messages and emails is repeated across multiple `if` blocks for different actions (e.g., `cancel`, `confirm`, `reject`). This leads to code duplication and makes it harder to modify or extend messaging capabilities. Consolidating the message sending into a dedicated service or helper function that takes the appointment, professional, client, and action as parameters would improve readability, reduce redundancy, and allow for more centralized error handling and retry mechanisms for external communication.
