# Database

Odys relies on a PostgreSQL database, hosted on Supabase, to store all application data. This document explores the database schema, its underlying design choices, and how Drizzle ORM is used to define and interact with it. Understanding this foundation is crucial for comprehending how Odys manages professionals, clients, appointments, and all related interactions.

## Overview

The Odys database schema is defined using Drizzle ORM, providing a type-safe and declarative way to interact with the PostgreSQL instance. The schema, located in `src/lib/db/schema.ts`, comprises 11 distinct tables, each designed to manage a specific aspect of the application's data. The core connection logic is encapsulated in `src/lib/db/index.ts`, which initializes Drizzle with a `postgres` client, connecting to the database via the `DATABASE_URL` environment variable.

The `drizzle.config.ts` file orchestrates the schema migrations, pointing Drizzle Kit to the schema definition and specifying PostgreSQL as the dialect. This setup allows for seamless schema evolution as the application grows.

At the heart of the system is the `professionals` table, which serves as the central entity around which most other tables revolve. Relationships are established through foreign keys, many of which include `onDelete: "cascade"` to simplify data cleanup when a parent record is removed.

## Schema Details

Let's delve into the structure and purpose of each table:

### Professionals

The `professionals` table is the most extensive, containing 32 columns that define the core attributes of each service provider. Each professional is uniquely identified by a `uuid` `id` and linked to a Supabase authentication `userId` via a `text` column, which is `notNull` and `unique`. A `slug` column, also `notNull` and `unique`, is provided for public profile URLs, such as `odys.com.br/p/dr-ana`.

Key business-related columns include `profession`, `sessionDuration`, and `sessionPrice`. The `plan` column, defaulting to `"free"`, tracks the professional's subscription level, while `paymentType` and `paymentPercentage` dictate how they receive payments from clients. Integration with Stripe is supported through `stripeCustomerId` and `stripeSubscriptionId` columns.

For professionals offering in-person services, detailed location information like `addressLine`, `neighborhood`, `city`, `state`, `postalCode`, `latitude`, and `longitude` are stored. These are typically geocoded upon entry. The `serviceType` column, defaulting to `"both"`, indicates whether services are `"in_person"`, `"online"`, or both.

Several columns, such as `createdAt` and `updatedAt`, automatically track record lifecycle, defaulting to the current timestamp. Indexes on `profession` and `city` are defined to optimize common search queries for professionals.

### Availability

The `availability` table stores the regular working hours for each professional. It links to the `professionals` table via `professionalId`, with `onDelete: "cascade"` ensuring that a professional's availability is removed if their profile is deleted. Each entry specifies a `dayOfWeek` (0 for Sunday to 6 for Saturday) and `startTime` and `endTime` as `text` strings (e.g., "09:00", "18:00"). An index on `professionalId` facilitates quick lookups of a professional's schedule.

### Clients

The `clients` table holds information about the individuals who book appointments with professionals. Each client has a `uuid` `id` and is associated with a `professionalId` via a foreign key with `onDelete: "cascade"`. A `userId` column, referencing a Supabase auth ID, is optional, allowing clients to book without necessarily having an Odys account. Essential contact details like `name`, `phone`, and `email` are stored, along with an optional `avatarUrl`. Indexes on `professionalId` and `userId` support efficient client retrieval.

### Client Notes

The `clientNotes` table provides a private space for professionals to record observations about their clients. These notes are linked to both `professionalId` and `clientId`, with `onDelete: "cascade"` ensuring notes are removed if either the professional or client record is deleted. The `content` of the note is stored as `text`, and `createdAt` and `updatedAt` timestamps track changes.

### Recurring Schedules

For clients who book regular sessions, the `recurringSchedules` table captures the pattern of these appointments. It links to `professionalId` and `clientId` with `onDelete: "cascade"`. The `frequency` column (e.g., `"weekly"`, `"biweekly"`, `"twice_weekly"`) defines the recurrence, while `dayOfWeek` and `secondDayOfWeek` specify the days, and `time` (e.g., "14:00") indicates the daily start time. An `active` boolean, defaulting to `true`, allows for pausing or resuming recurring schedules.

### Appointments

The `appointments` table is central to the booking system, detailing each individual session. It includes foreign keys to `professionalId`, `clientId`, and optionally `recurringScheduleId`. The `startsAt` and `endsAt` columns, both `timestamp` types, define the appointment's duration.

The `status` column tracks the appointment's lifecycle, moving from `"pending_confirmation"` to `"confirmed"`, `"rejected"`, `"completed"`, `"cancelled"`, or `"no_show"`. Similarly, `paymentStatus` tracks the financial state, from `"none"` to `"authorized"`, `"captured"`, or `"refunded"`. Stripe payment intent IDs are stored in `stripePaymentIntentId`.

To manage client communication, `reminderSent24h` and `reminderSent1h` booleans track whether automated reminders have been dispatched. A `notes` field allows for additional details.

Crucially, the `appointments` table includes a `uniqueIndex` named `appointments_pro_starts_at_active_uidx` on `professionalId` and `startsAt`. This index is filtered to only apply where `status` is not `'rejected'` or `'cancelled'`, serving as a database-level defense against double-booking for active appointments.

### Messages

The `messages` table facilitates direct communication between professionals and clients. Each message is linked to a `professionalId` and `clientId` with `onDelete: "cascade"`. The `sender` column identifies whether the message came from the `"professional"` or `"client"`. Messages can be of `type` `"text"`, `"link"`, or `"pdf"`, with `content` storing the message body and `fileUrl` for attachments. A `readAt` timestamp indicates when the message was viewed. An index on `professionalId` and `clientId` optimizes message retrieval for specific conversations.

### Follows

The `follows` table tracks when a client (identified by `userId`) chooses to follow a professional (identified by `professionalId`). This simple table includes `onDelete: "cascade"` for `professionalId` and indexes on both `professionalId` and `userId` for efficient querying.

### Reviews

After an appointment, clients can leave a review in the `reviews` table. Each review is linked to `professionalId`, `clientId`, and `appointmentId`, with `onDelete: "cascade"` for all references. The `appointmentId` is `unique`, ensuring only one review per appointment. A `rating` (1-5 integer) and an optional `comment` are stored. An index on `professionalId` allows for aggregating reviews for a given professional.

### Notifications

The `notifications` table stores alerts for both professionals and clients. It identifies the `recipientId` (a Supabase user ID) and `recipientType` (`"professional"` or `"client"`). The `type` column categorizes the notification (e.g., `"booking_request"`, `"new_message"`), while `title` and `body` provide the content. A `read` boolean, defaulting to `false`, tracks whether the notification has been seen. An index on `recipientId` enables quick retrieval of a user's notifications.

### Agent Metrics

The `agentMetrics` table is dedicated to telemetry for the WhatsApp intake agent. It captures detailed information about each conversational turn, including a `traceId`, `conversationPhone`, `promptVersion`, and `promptHash`. Performance metrics like `totalCostUsd`, `totalCostBrl`, `totalLatencyMs`, and `toolCallCount` are recorded. The `providersUsed` column, stored as a `text` array, lists the AI services engaged. The `outcome` column categorizes the result of the turn (e.g., `"booked"`, `"cancelled"`, `"searched"`), which is invaluable for analyzing agent performance and conversion rates. Indexes on `traceId`, `createdAt`, and `outcome` support analytical queries.

## Design Decisions

The database schema reflects several deliberate design choices aimed at balancing development velocity, data integrity, and application performance:

*   **Drizzle ORM**: The selection of Drizzle ORM provides a type-safe interface to the PostgreSQL database. This significantly reduces the likelihood of runtime errors related to schema mismatches and offers a pleasant developer experience with its SQL-like query builder. The schema-first approach, defined in `src/lib/db/schema.ts`, makes the database structure explicit and version-controlled.
*   **Supabase PostgreSQL**: Using Supabase as the managed PostgreSQL provider simplifies database operations, handling infrastructure, backups, and scaling. PostgreSQL itself is a feature-rich and reliable relational database, well-suited for transactional workloads and complex queries.
*   **UUID Primary Keys**: All tables use `uuid` for their primary keys, generated with `defaultRandom()`. This choice helps avoid issues with sequential IDs in distributed systems, prevents information leakage through predictable IDs, and simplifies merging data from different sources if needed.
*   **Referential Integrity with `onDelete: "cascade"`**: Many foreign key relationships, such as `availability.professionalId` referencing `professionals.id`, are configured with `onDelete: "cascade"`. This is a pragmatic choice to automatically clean up dependent records when a parent record is deleted. For instance, if a professional's account is removed, all their associated availability slots, clients, notes, and appointments are automatically purged from the database, simplifying application logic and preventing orphaned data.
*   **Application-Specific Indexes**: Beyond primary keys, specific indexes like `professionals_profession_idx` and `appointments_professional_id_idx` are defined to optimize common query patterns. The `uniqueIndex` on `appointments_pro_starts_at_active_uidx` is a particularly important design decision. By applying a partial unique index that only considers appointments with non-terminal statuses (`'rejected'`, `'cancelled'`), the database itself enforces that a professional cannot have two active appointments at the exact same `startsAt` time. This provides a strong, low-level defense against race conditions and double-booking, complementing any application-level validation.
*   **`timestamp` with `defaultNow()`**: Columns like `createdAt` and `updatedAt` are consistently defined as `timestamp` with `notNull` and `defaultNow()`. This is a standard practice for auditing and tracking the lifecycle of records, providing valuable metadata without requiring explicit application code to set these values on insertion.

## Potential Improvements

While the current schema is functional and well-structured, several areas could be considered for further refinement to enhance data integrity, developer experience, and future extensibility:

1.  **Introduce `pgEnum` for constrained `text` columns**: Many `text` columns in the schema effectively act as enums, such as `professionals.plan`, `professionals.paymentType`, `appointments.status`, `messages.sender`, and `agentMetrics.outcome`. Drizzle ORM's `pgEnum` feature allows defining these as actual PostgreSQL enum types. This would enforce valid values at the database level, preventing invalid data from being inserted, improving type safety in the application, and making the schema's intent clearer. For example, `professionals.plan` could be `pgEnum("plan_type", ["free", "pro", "premium"])`.
2.  **Strengthen `userId` referential integrity**: The `userId` columns in `professionals` and `clients` are currently `text` fields, intended to reference Supabase's `auth.users.id`. While Supabase handles authentication, exploring options to establish a formal foreign key relationship to the `auth.users` table (if Supabase's managed Postgres allows this, or by mirroring relevant user data into a local `users` table) would provide database-level referential integrity. This would ensure that `professionalId` and `clientId` always point to existing user accounts, preventing orphaned records if a user is deleted from Supabase auth.
3.  **Utilize dedicated `time` types for time-only fields**: Columns like `availability.startTime`, `availability.endTime`, and `recurringSchedules.time` are currently stored as `text`. While functional, using a dedicated PostgreSQL `TIME` type (if Drizzle supports it directly or via custom type mapping) would offer better semantic meaning, allow for database-level validation of time formats, and potentially simplify time-based calculations or comparisons within SQL queries. This would make the schema more expressive and robust for time-related data.
