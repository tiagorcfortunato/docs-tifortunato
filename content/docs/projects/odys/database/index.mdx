# Database

The database serves as the central repository for all Odys application data, meticulously structured to support the interactions between professionals and clients, manage appointments, and track system-level metrics. This document explores the architecture of Odys's data layer, which relies on Drizzle ORM to interact with a Supabase Postgres instance, providing a type-safe and efficient way to manage the application's persistent state.

## Overview

Odys employs a PostgreSQL database hosted on Supabase, a choice that provides a managed, scalable, and feature-rich relational database solution. Interacting with this database is Drizzle ORM, a modern TypeScript ORM that emphasizes type safety and a SQL-like query builder experience.

The database connection is established in `src/lib/db/index.ts`. This file initializes the `postgres` client, pointing it to the `DATABASE_URL` environment variable, and then wraps it with Drizzle's `drizzle` function. The entire database schema, comprising 11 distinct tables, is imported from `src/lib/db/schema.ts` and passed to Drizzle, ensuring that all database operations are strongly typed and reflect the defined schema. For managing schema changes and migrations, Drizzle Kit is configured via `drizzle.config.ts`, which points to the schema definition and database credentials.

## Schema Details

The Odys database schema is designed to capture the multifaceted relationships within the platform, from professional profiles and their availability to client interactions, appointments, and system telemetry.

The core of the application revolves around the `professionals` table, which holds 32 columns detailing each professional's profile. This includes essential contact information like `name`, `phone`, and `email`, alongside business-specific attributes such as `profession`, `sessionDuration`, and `sessionPrice`. Crucially, it tracks the professional's subscription `plan` (`free`, `pro`, `premium`), their preferred `paymentType`, `paymentPercentage`, and integration details for `pixKeyType`, `pixKey`, `stripeCustomerId`, and `stripeSubscriptionId`. Location data, including `addressLine`, `neighborhood`, `city`, `state`, `postalCode`, `latitude`, and `longitude`, supports location-based services, alongside `serviceType` (`in_person`, `online`, or `both`). The `userId` column, marked as unique, links directly to the Supabase authentication system, while a unique `slug` column facilitates public profile URLs. Indexes on `profession` and `city` are defined to optimize common search queries.

A professional's working hours are defined in the `availability` table, which links to `professionals` via `professionalId`. This table specifies `dayOfWeek`, `startTime`, and `endTime` for each professional, allowing the system to determine when a professional is open for bookings. The `onDelete: "cascade"` rule ensures that if a professional's record is removed, their associated availability slots are automatically cleaned up.

Clients are managed in the `clients` table, which stores their `name`, `phone`, and `email`. Notably, the `userId` column is nullable, reflecting a design choice to allow clients to book appointments even without a registered user account. Each client is associated with a `professionalId`, indicating which professional manages them, again with `onDelete: "cascade"` for data integrity. Professionals can maintain private `clientNotes` for each client, a separate table linked to both `professionals` and `clients` with cascading deletes.

The `recurringSchedules` table handles repeat appointments, such as weekly therapy sessions. It captures the `frequency` (e.g., `weekly`, `biweekly`), specific `dayOfWeek` or `secondDayOfWeek`, and `time`. This table also links to `professionals` and `clients` with cascading deletion.

Individual appointments are recorded in the `appointments` table, a critical component of the system with 13 columns. Each appointment links to a `professionalId` and `clientId`, and optionally to a `recurringScheduleId` if it's part of a recurring series. Key fields include `startsAt` and `endsAt`, `status` (tracking the appointment lifecycle from `pending_confirmation` to `completed` or `cancelled`), and `paymentStatus`. The `stripePaymentIntentId` stores transaction references. To prevent double-booking, a partial unique index, `appointments_pro_starts_at_active_uidx`, is defined on `professionalId` and `startsAt`, specifically filtering for appointments not in `rejected` or `cancelled` statuses. This provides a database-level defense against concurrent booking attempts.

Communication between professionals and clients is stored in the `messages` table, which includes the `sender` (`professional` or `client`), `type` (`text`, `link`, `pdf`), `content`, and `fileUrl` for attachments. The `readAt` timestamp tracks when a message was viewed. The `follows` table allows users to express interest in professionals, linking a `userId` to a `professionalId`.

Post-appointment feedback is captured in the `reviews` table, where clients can provide a `rating` (1-5) and an optional `comment`. Each review is uniquely tied to an `appointmentId`, ensuring that only one review can be submitted per completed appointment.

System-generated alerts are managed by the `notifications` table, which targets a `recipientId` (a Supabase user ID) and `recipientType` (`professional` or `client`), with fields for `type`, `title`, and `body`.

Finally, the `agentMetrics` table provides telemetry for the WhatsApp intake agent. It records details like `traceId`, `conversationPhone`, `promptVersion`, `promptHash`, and cost metrics (`totalCostUsd`, `totalCostBrl`). It also tracks `totalLatencyMs`, `toolCallCount`, `providersUsed` (as a text array), and the `outcome` of each agent interaction (e.g., `booked`, `cancelled`, `searched`). This table is designed for best-effort insertion, ensuring that metric collection failures do not impede core application functionality.

## Design Decisions

The architectural choices for Odys's database layer reflect a balance between developer experience, data integrity, and future extensibility.

The adoption of **Drizzle ORM** was a deliberate choice to bring strong type safety to database interactions. By defining the schema in TypeScript, Drizzle generates types that flow through the application, catching potential errors at compile time rather than runtime. This significantly reduces the likelihood of SQL injection vulnerabilities and type mismatches, making the codebase more maintainable and easier to refactor. While Drizzle is a newer ORM compared to some alternatives, its focus on a thin, SQL-like abstraction layer means developers retain a clear understanding of the underlying database operations, avoiding the "magic" often associated with heavier ORMs.

Using **UUIDs as primary keys** with `defaultRandom()` for all tables, such as `professionals.id` and `appointments.id`, offers several advantages. UUIDs are globally unique, which simplifies data merging across distributed systems and prevents ID collisions. Their non-sequential nature also makes them less predictable than auto-incrementing integers, which can be a minor security benefit by obscuring the total number of records.

The widespread use of **`onDelete: "cascade"`** for foreign key relationships, seen in tables like `availability`, `clients`, and `appointments` referencing `professionals.id`, streamlines data management. When a parent record, such as a professional, is deleted, all associated child records are automatically removed by the database. This maintains referential integrity without requiring explicit application-level cleanup logic, reducing the risk of orphaned data. The trade-off is that this powerful feature must be used carefully, as an accidental deletion of a parent record can lead to significant data loss across related tables.

Many "enum-like" fields, such as `professionals.plan`, `appointments.status`, and `agentMetrics.outcome`, are implemented using **`text` columns** rather than native PostgreSQL `ENUM` types. This provides flexibility, allowing new values to be introduced without requiring database migrations, which can be complex in production environments. The application relies on TypeScript string literal types and runtime validation to ensure that only expected values are used, balancing database schema rigidity with development agility.

The **partial unique index `appointments_pro_starts_at_active_uidx`** on the `appointments` table is a critical defense-in-depth mechanism. While application logic typically handles preventing double-bookings, race conditions can still occur. By adding a unique constraint on `professionalId` and `startsAt` for appointments not yet `rejected` or `cancelled`, the database itself will refuse a second booking for the exact same slot, returning a `23505` error code. This ensures data integrity even if application-level checks fail under heavy load.

Finally, the use of **`timestamp` columns with `defaultNow()`** for `createdAt` and `updatedAt` in most tables provides essential auditing capabilities. These columns automatically record when a record was created and last modified, which is invaluable for debugging, compliance, and understanding data evolution over time. For monetary values like `totalCostUsd` and `totalCostBrl` in `agentMetrics`, the `numeric` type with specified `precision` and `scale` is used to prevent floating-point inaccuracies, ensuring exact calculations for financial data.

## Potential Improvements

While the current database schema is well-structured and functional, several areas could be considered for further refinement to enhance data integrity, query performance, or schema clarity.

1.  **Introduce PostgreSQL `ENUM` types for categorical fields**: Many columns currently use `text` to store a limited set of predefined values, such as `professionals.plan`, `appointments.status`, `messages.type`, `notifications.type`, and `agentMetrics.outcome`. Converting these to native PostgreSQL `ENUM` types would enforce data integrity at the database level, preventing the insertion of invalid values that might bypass application-level validation. This would make the schema more self-documenting and provide stronger guarantees about data quality. For example, `professionals.plan` in `src/lib/db/schema.ts` could be an `enum('plan_type', ['free', 'pro', 'premium'])` instead of `text("plan")`.

2.  **Strengthen `notifications.recipientId` foreign key constraints**: The `notifications` table uses `recipientId` (a `text` field) and `recipientType` (`professional` or `client`) to identify the notification target. While flexible, this design means the database cannot enforce referential integrity for `recipientId`. If `recipientId` consistently refers to either `professionals.id` or `clients.id`, a more robust solution could involve conditional foreign keys (if supported by Drizzle/Postgres extensions) or, more simply, splitting `notifications` into `professionalNotifications` and `clientNotifications` tables, each with a direct `uuid` foreign key to the respective parent table. This would ensure that notifications are always linked to valid recipients.

3.  **Optimize `messages` table indexing for common queries**: The `messages` table currently has an index on `(professionalId, clientId)`. Depending on how messages are typically retrieved (e.g., "show me the latest messages for this client with this professional"), adding an index on `createdAt` or a composite index like `(professionalId, clientId, createdAt)` could significantly improve performance for queries that sort or filter by time. This is particularly relevant given the comment in `src/lib/db/schema.ts` about clients only being able to send one message at a time, implying a need to quickly identify the latest message in a conversation.

4.  **Normalize `agentMetrics.providersUsed`**: The `agentMetrics` table stores `providersUsed` as a `text().array()`. While convenient for simple storage, if there's a need to query or analyze individual providers frequently (e.g., "how many times was 'OpenAI' used?"), this array structure can be less efficient. Normalizing this into a separate `agentMetricProviders` table, with each row linking to an `agentMetrics.id` and containing a single provider name, would allow for more efficient querying and better data consistency for provider names.
