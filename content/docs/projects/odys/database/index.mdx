The Odys application relies on a PostgreSQL database, managed through Supabase, with its schema defined and interacted with using Drizzle ORM. This architecture provides a type-safe and developer-friendly way to manage data, while leveraging the capabilities of a managed cloud database service.

## Overview

The core of Odys's data persistence layer is built around PostgreSQL, a powerful relational database, hosted and managed by Supabase. Drizzle ORM serves as the TypeScript-first object-relational mapper, providing a declarative way to define the database schema and interact with it programmatically.

The database connection is established in `src/lib/db/index.ts`, where the `drizzle` function from `drizzle-orm/postgres-js` is initialized with a `postgres` client. This client connects to the database using the `DATABASE_URL` environment variable, configured to not prepare statements by default, which can be a performance consideration for some workloads. The entire database schema, comprising 11 distinct tables, is then imported from `src/lib/db/schema.ts` and passed to Drizzle, making all table definitions available for queries.

For schema migrations and database management, the project utilizes Drizzle Kit, configured via `drizzle.config.ts`. This configuration points to `src/lib/db/schema.ts` as the source of truth for the schema, specifies PostgreSQL as the dialect, and uses the same `DATABASE_URL` for database credentials.

### Schema Structure

The `src/lib/db/schema.ts` file meticulously defines all 11 tables, outlining their columns, data types, constraints, and relationships. Each table is designed to support specific functionalities within the Odys platform:

*   **`professionals`**: This central table stores detailed profiles for service providers, featuring 32 columns. It includes essential information like `name`, `phone`, `email`, `profession`, and a unique `slug` for public profile URLs. Financial details such as `sessionDuration`, `sessionPrice`, `plan`, `paymentType`, and `pixKey` are also stored here. Integration with Stripe is evident through `stripeCustomerId` and `stripeSubscriptionId`. Location data, including `addressLine`, `city`, `state`, `latitude`, and `longitude`, supports in-person service types. The `userId` column, a `text` type with a `unique` constraint, is intended to link to an external authentication system, likely Supabase's own user management.
*   **`availability`**: This table defines the working hours for each professional, linking to `professionals.id` with an `onDelete: "cascade"` rule. It captures `dayOfWeek` (0-6 for Sunday-Saturday), `startTime`, and `endTime` as `text` fields.
*   **`clients`**: Represents the clients interacting with professionals. It includes `name`, `phone`, `email`, and an optional `userId` for authenticated clients. It also links to `professionals.id` with `onDelete: "cascade"`.
*   **`clientNotes`**: Stores private notes that professionals keep about their clients, ensuring these are only visible to the respective professional. It links to both `professionals.id` and `clients.id` with `onDelete: "cascade"`.
*   **`recurringSchedules`**: Manages recurring appointments for clients, specifying `frequency` (e.g., "weekly", "biweekly"), `dayOfWeek`, `secondDayOfWeek`, and `time`. It also links to `professionals.id` and `clients.id` with `onDelete: "cascade"`.
*   **`appointments`**: This critical table tracks individual appointments, with 13 columns. It records `startsAt`, `endsAt`, `status` (e.g., "pending_confirmation", "confirmed"), and `paymentStatus`. It includes foreign keys to `professionals.id`, `clients.id` (both with `onDelete: "cascade"`), and an optional `recurringScheduleId`. A notable `uniqueIndex("appointments_pro_starts_at_active_uidx")` is defined on `professionalId` and `startsAt`, filtered to exclude 'rejected' or 'cancelled' appointments, serving as a database-level safeguard against double-booking.
*   **`messages`**: Facilitates communication between professionals and clients, storing `sender`, `type` (e.g., "text", "link"), `content`, and a `readAt` timestamp. It links to `professionals.id` and `clients.id` with `onDelete: "cascade"`.
*   **`follows`**: Records when a user "follows" a professional, linking `userId` (from the external auth system) to `professionalId` with `onDelete: "cascade"`.
*   **`reviews`**: Stores client ratings and comments for completed appointments. It links to `professionals.id`, `clients.id`, and `appointmentId` (with a `unique` constraint) with `onDelete: "cascade"`.
*   **`notifications`**: Manages in-app notifications for users, specifying `recipientId`, `recipientType` ("professional" or "client"), `type`, `title`, `body`, and `read` status.
*   **`agentMetrics`**: This table is dedicated to storing telemetry data for the WhatsApp intake agent. It captures details like `traceId`, `conversationPhone`, `promptVersion`, `totalCostUsd`, `totalLatencyMs`, `toolCallCount`, `providersUsed` (as an array), and the `outcome` of each interaction. The cost columns `totalCostUsd` and `totalCostBrl` use the `numeric` type with specified precision and scale for accurate financial tracking.

Across the schema, `uuid` is consistently used for primary keys, defaulting to `defaultRandom()` for automatic generation. Timestamp columns like `createdAt` and `updatedAt` frequently use `defaultNow()` to automatically record creation and modification times.

## Design decisions

The database design reflects several deliberate choices aimed at balancing development efficiency, data integrity, and application requirements:

*   **Drizzle ORM for Type Safety and Developer Experience**: The selection of Drizzle ORM over raw SQL or other ORMs was likely driven by its strong emphasis on type safety. By defining the schema in TypeScript (`src/lib/db/schema.ts`), developers gain compile-time checks for queries, reducing runtime errors and improving code maintainability. Drizzle's SQL-like query builder syntax also offers a familiar and intuitive way to interact with the database.
*   **PostgreSQL on Supabase for Managed Scalability**: Opting for PostgreSQL provides a feature-rich, ACID-compliant relational database. Hosting it on Supabase offloads significant operational burden, including backups, scaling, and security patching, allowing the development team to focus on application features rather than infrastructure. Supabase's integration with authentication and other services also streamlines development.
*   **UUID Primary Keys**: The consistent use of `uuid` for primary keys across all tables, generated with `defaultRandom()`, is a common practice for distributed systems. It avoids potential issues with sequential integer IDs, such as predictability, merge conflicts in distributed environments, and performance bottlenecks in highly concurrent insert scenarios.
*   **`onDelete: "cascade"` for Referential Integrity**: Many foreign key relationships, such as `availability.professionalId` referencing `professionals.id`, are configured with `onDelete: "cascade"`. This choice simplifies data management by automatically deleting dependent records when a parent record is removed. For instance, deleting a professional will automatically remove all their associated availability slots, clients, notes, recurring schedules, appointments, messages, follows, and reviews. This reduces the need for complex application-level logic to maintain data consistency.
*   **Partial Unique Index for Double-Booking Prevention**: The `uniqueIndex("appointments_pro_starts_at_active_uidx")` on the `appointments` table is a critical design decision for preventing race conditions in booking. By applying a unique constraint on `professionalId` and `startsAt` *only for appointments not in 'rejected' or 'cancelled' statuses*, the database itself enforces that a professional cannot have two active appointments at the exact same time. This acts as a "defense-in-depth" mechanism, complementing any application-level checks and ensuring data integrity even under high concurrency.
*   **`text` for Time and Enum-like Fields**: While dedicated time types exist, using `text` for `availability.startTime` and `endTime` simplifies storage and retrieval, especially if time parsing is handled at the application layer. Similarly, many fields like `professionals.plan`, `appointments.status`, and `messages.type` use `text` to represent what are effectively enumerated values. This offers flexibility but shifts validation responsibility to the application.
*   **`numeric` for Financial Data**: The `agentMetrics` table uses `numeric` types with explicit `precision` and `scale` for `totalCostUsd` and `totalCostBrl`. This is a standard and crucial practice for financial data to prevent floating-point inaccuracies that can occur with `float` or `doublePrecision` types.

## Potential improvements

While the current database schema is functional and well-structured, several areas could be enhanced to further improve data integrity, type safety, and query efficiency:

1.  **Introduce Drizzle `pgEnum` for Status and Type Columns**: Many `text` columns, such as `professionals.plan`, `professionals.paymentType`, `appointments.status`, `messages.type`, `notifications.type`, `agentMetrics.outcome`, and `professionals.serviceType`, represent a finite set of predefined values. Converting these to Drizzle's `pgEnum` type would enforce valid values at the database level, preventing the insertion of arbitrary strings and improving data consistency. This would also provide stronger type inference in TypeScript queries. For example, `professionals.plan` could be `pgEnum("plan_enum", ["free", "pro", "premium"])`.
2.  **Formalize `professionals.userId` as a Foreign Key**: The `professionals.userId` column is currently a `text` type with a `unique` constraint, intended to link to Supabase's authentication user IDs. While this works, adding a formal foreign key constraint to a `users` table (if one were defined in the Drizzle schema, perhaps representing the `auth.users` table) would enforce referential integrity directly within the database. This would ensure that every professional record is always associated with a valid user account, preventing orphaned professional profiles if a user is deleted from the authentication system.
3.  **Utilize More Specific Time Types for `availability.startTime` and `endTime`**: The `availability.startTime` and `availability.endTime` columns are currently defined as `text`. While functional, using a more specific PostgreSQL time type (e.g., `time` if Drizzle's `pg-core` offers it directly, or a custom type) could provide better validation, allow for more efficient time-based queries (e.g., range checks without string parsing), and improve clarity. This would shift time validation from the application layer to the database.
