# Database

The `odys` application relies on a PostgreSQL database hosted by Supabase, with Drizzle ORM serving as the primary interface for interacting with the data. This setup provides a type-safe, schema-first approach to database management, ensuring that application code and database structure remain synchronized and robust. This document explores the database schema, the Drizzle configuration, and the underlying design principles.

## Overview

The `odys` database comprises 11 distinct tables, each designed to manage specific aspects of the platform's operations, from professional profiles and client appointments to messaging and internal metrics. Supabase provides the managed PostgreSQL instance, handling infrastructure concerns like backups, scaling, and basic authentication integration. Drizzle ORM then layers on top, offering a TypeScript-native way to define the schema and construct queries, moving away from raw SQL strings and towards a more maintainable, type-checked codebase. The `drizzle-kit` tool, configured via `drizzle.config.ts`, facilitates schema migrations, allowing for controlled evolution of the database structure.

## Schema Definition

The core of the database structure is defined in `src/lib/db/schema.ts`. Each table is declared using Drizzle's `pgTable` function, mapping directly to PostgreSQL tables and their respective columns.

The `professionals` table is central, storing comprehensive details about each service provider. It includes fields like `userId` (linking to Supabase authentication), a unique `slug` for public profile URLs, contact information, `profession`, `bio`, and `avatarUrl`. Crucially, it defines `sessionDuration` and `sessionPrice`, along with `plan` (e.g., "free", "pro", "premium") and `paymentType` (e.g., "upfront", "percentage", "after") to manage business logic. Payment integration details, such as `stripeCustomerId` and `stripeSubscriptionId`, are also stored here. The `autoConfirm` boolean column (default `false`) indicates if appointments are automatically confirmed. The `serviceType` field (default "both") indicates if services are "in_person", "online", or "both". For professionals offering in-person services, location details like `addressLine`, `city`, `state`, `postalCode`, and geocoded `latitude` and `longitude` are included. The table also tracks `active` status (default `true`) and standard `createdAt` and `updatedAt` timestamps. Several indices, such as `professionals_profession_idx` and `professionals_city_idx`, are defined to optimize common search queries.

Supporting the `professionals` table are several related entities:

-   **`availability`**: Defines the working hours for each professional, linking via `professionalId`. It specifies `dayOfWeek`, `startTime`, and `endTime`.
-   **`clients`**: Stores information about clients, including an optional `userId` (allowing unauthenticated bookings), `professionalId`, `name`, `phone`, and `email`.
-   **`clientNotes`**: Private notes maintained by a professional about a specific client, linked by `professionalId` and `clientId`.
-   **`recurringSchedules`**: Manages recurring appointments, specifying `frequency` (e.g., "weekly", "biweekly"), `dayOfWeek`, `secondDayOfWeek`, and `time`.
-   **`appointments`**: Represents individual bookings, linking `professionalId`, `clientId`, and optionally `recurringScheduleId`. It tracks `startsAt`, `endsAt`, `status` (e.g., "pending_confirmation", "confirmed", "rejected"), and `paymentStatus`. Important for preventing double-booking, a unique index `appointments_pro_starts_at_active_uidx` is applied to `professionalId` and `startsAt`, filtered to exclude 'rejected' or 'cancelled' appointments.
-   **`messages`**: Facilitates communication between professionals and clients, recording `sender`, `type`, `content`, and `fileUrl`.
-   **`follows`**: Tracks when a user follows a professional, linking `userId` and `professionalId`.
-   **`reviews`**: Stores client feedback after an appointment, including `rating` and `comment`, uniquely linked to an `appointmentId`.
-   **`notifications`**: A generic table for sending notifications to users, with `recipientId`, `recipientType`, `type`, `title`, `body`, and `read` status.
-   **`agentMetrics`**: Captures telemetry data for the WhatsApp intake agent, including `traceId`, `conversationPhone`, `promptVersion`, `promptHash`, `totalCostUsd`, `totalCostBrl`, `totalLatencyMs`, `toolCallCount`, `providersUsed` (an array of text), and `outcome` of the conversation.

Most tables use `uuid` as their primary key, generated with `defaultRandom()`, and include `createdAt` with `defaultNow()`, with some also including `updatedAt`. Foreign key relationships are established using Drizzle's `references` helper, with `onDelete: "cascade"` configured for many relationships to ensure dependent records are automatically removed when a parent record is deleted.

## Drizzle Configuration

The Drizzle ORM instance is initialized in `src/lib/db/index.ts`. It uses the `postgres` client library to establish a connection to the PostgreSQL database. The connection string is sourced from `process.env.DATABASE_URL!`, a standard practice for environment-specific configurations. The `prepare: false` option is passed to the `postgres` client, which can sometimes be necessary for compatibility or performance with specific database setups, including some managed services. The `drizzle` function then wraps this client, associating it with the defined schema from `src/lib/db/schema.ts` to create the `db` object, which is then exported for use throughout the application.

For managing schema changes, `drizzle-kit` is configured in `drizzle.config.ts`. This configuration points to `src/lib/db/schema.ts` as the source of truth for the database schema, specifies `./drizzle` as the output directory for migration files, and declares `postgresql` as the dialect. It also retrieves the database URL from `process.env.DATABASE_URL!`, ensuring consistency between the application's runtime connection and the migration tool's connection.

## Design Decisions

The choice of Drizzle ORM with Supabase PostgreSQL reflects a deliberate set of trade-offs aimed at developer experience, data integrity, and operational simplicity.

Using **Supabase Postgres** as the database backend offloads significant operational burden. It provides a fully managed PostgreSQL instance, eliminating the need for manual database provisioning, scaling, and maintenance. This allows the development team to focus on application features rather than infrastructure. Its integration with Supabase Auth also simplifies user management and access control.

**Drizzle ORM** was selected for its type-safety and schema-first approach. By defining the schema directly in TypeScript in `src/lib/db/schema.ts`, the application gains compile-time checks for database interactions, significantly reducing runtime errors related to incorrect column names or types. This contrasts with string-based SQL queries or less type-strict ORMs, which often defer such errors to runtime. The lightweight nature of Drizzle also contributes to better performance compared to some larger, more opinionated ORMs.

The widespread use of **UUIDs as primary keys** (e.g., `professionals.id`, `appointments.id`) with `defaultRandom()` is a common pattern in distributed systems. UUIDs avoid sequential IDs, which can sometimes be guessed or expose information about data volume. They also simplify merging data from different sources and reduce contention in high-insert scenarios compared to auto-incrementing integers.

The inclusion of **`onDelete: "cascade"`** for many foreign key relationships, such as `availability.professionalId` referencing `professionals.id`, simplifies data management. When a professional is deleted, all their associated availability slots, clients, notes, recurring schedules, messages, follows, and reviews are automatically removed by the database. This prevents orphaned records and ensures data consistency without requiring complex application-level cleanup logic.

The `appointments` table includes a **partial unique index `appointments_pro_starts_at_active_uidx`**. This index, applied to `professionalId` and `startsAt`, is filtered to only consider appointments where `status` is not 'rejected' or 'cancelled'. This is a crucial defense-in-depth mechanism. While application logic typically prevents double-booking, concurrent requests could theoretically bypass these checks. This database-level constraint provides a final safeguard, ensuring that a professional cannot have two active appointments at the exact same time slot, even if application-level checks fail.

The `postgres` client is initialized with `prepare: false` in `src/lib/db/index.ts`. This setting disables the client's automatic prepared statement caching. While prepared statements can offer performance benefits, some database proxies or managed services (like parts of Supabase's connection pooler) might handle prepared statements differently or have their own caching mechanisms, making client-side preparation redundant or even problematic. Disabling it ensures broader compatibility and avoids potential issues.

For fields like `professionals.phone`, `professionals.email`, `availability.startTime`, and `availability.endTime`, the `text` type is used. This offers flexibility, allowing various formats for phone numbers or times. The trade-off is that database-level validation for specific formats (e.g., E.164 for phone numbers, HH:MM for times) is not enforced, relying instead on application-level validation.

## Potential Improvements

1.  **Introduce `pgEnum` for categorical `text` columns**: Many columns currently use `text` to store categorical values, such as `professionals.profession`, `professionals.plan`, `professionals.paymentType`, `professionals.serviceType`, `appointments.status`, `appointments.paymentStatus`, `messages.type`, `notifications.type`, and `agentMetrics.outcome`. Converting these to Drizzle's `pgEnum` would provide stricter type checking at the TypeScript level and enforce valid values directly within the PostgreSQL database. This would enhance data integrity and prevent invalid data from being inserted. For example, `professionals.profession` could be `pgEnum("profession_enum", ["psychologist", "personal_trainer", "nutritionist"])`.

2.  **Utilize PostgreSQL `TIME` type for `startTime` and `endTime`**: The `availability.startTime` and `availability.endTime` columns are currently defined as `text`. While functional, using PostgreSQL's native `TIME` type would allow for database-level validation of time formats and enable more efficient time-based queries or calculations directly within the database. This would make the schema more semantically accurate and potentially simplify future time-related logic.

3.  **Refine indexing strategy based on API access patterns**: While several indices are present, a deeper analysis of the `apiRoutes` (e.g., `/api/messages`, `/api/notifications`) could reveal opportunities for additional or refined indices. For instance, if messages are frequently queried by `clientId` alone, an index on `clients.id` in the `messages` table might be beneficial, in addition to the existing `messages_professional_client_idx`. Similarly, for `notifications`, if `recipientType` is often used in conjunction with `recipientId` for filtering, a compound index on `(recipientId, recipientType)` could improve query performance.
