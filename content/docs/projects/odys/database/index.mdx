# Database

The Odys application relies on a PostgreSQL database hosted on Supabase to manage all its persistent data. This document explores the structure and interaction patterns with this database, focusing on the Drizzle ORM definitions that shape our data models and the underlying design choices. Understanding the database schema is fundamental to grasping how Odys stores information about professionals, clients, appointments, and the various interactions that drive the platform.

## Overview

Odys uses [Drizzle ORM](https://orm.drizzle.team/) to define and interact with its PostgreSQL database. This choice provides a type-safe and declarative way to manage the schema and perform database operations. The database connection is established in `src/lib/db/index.ts`, where `drizzle` is initialized with a `postgres` client, pointing to the `DATABASE_URL` environment variable. This setup ensures that all database interactions throughout the application benefit from Drizzle's capabilities and the defined schema.

The entire database schema, comprising 11 distinct tables, is meticulously defined in `src/lib/db/schema.ts`. This file serves as the single source of truth for the database structure, detailing each table, its columns, data types, constraints, and relationships. For managing schema changes over time, `drizzle-kit` is configured via `drizzle.config.ts`, pointing to the schema file and specifying PostgreSQL as the dialect.

The tables are organized around the core entities of the Odys platform:
*   **`professionals`**: The central entity representing service providers.
*   **`clients`**: Individuals who book services from professionals.
*   **`availability`**: Defines when professionals are available.
*   **`appointments`**: Records specific bookings between clients and professionals.
*   **`recurringSchedules`**: Manages repeating appointments.
*   **`clientNotes`**: Private notes professionals keep about their clients.
*   **`messages`**: Facilitates communication between clients and professionals.
*   **`follows`**: Tracks when a user follows a professional.
*   **`reviews`**: Stores client feedback on appointments.
*   **`notifications`**: Manages in-app notifications for users.
*   **`agentMetrics`**: Collects telemetry data from the AI intake agent.

## Schema Deep Dive

The `src/lib/db/schema.ts` file defines the blueprint for all data stored in Odys. Each table is declared using Drizzle's `pgTable` function, specifying its SQL name and a detailed definition of its columns.

The `professionals` table is arguably the most comprehensive, containing 32 columns that capture a wide array of information about each service provider. It includes basic contact details like `name`, `phone`, and `email`, alongside unique identifiers such as `id` (a UUID primary key) and `userId` (a unique text field linked to Supabase authentication). Crucially, it defines `slug` for public profile URLs, `profession`, `sessionDuration`, and `sessionPrice`. Payment-related fields like `plan`, `paymentType`, `paymentPercentage`, `pixKeyType`, `pixKey`, `stripeCustomerId`, and `stripeSubscriptionId` are also present, indicating a sophisticated payment integration. For professionals offering in-person services, location details such as `addressLine`, `neighborhood`, `city`, `state`, `postalCode`, `latitude`, and `longitude` are stored. The table also includes `createdAt` and `updatedAt` timestamps, which are common for tracking record lifecycle. Two indices, `professionals_profession_idx` and `professionals_city_idx`, are defined to optimize queries based on profession and location.

The `availability` table, with 5 columns, captures the working hours for each professional. It links directly to the `professionals` table via `professionalId`, with an `onDelete: "cascade"` rule ensuring that a professional's availability is removed if their profile is deleted. It uses `dayOfWeek` (an integer from 0 for Sunday to 6 for Saturday) and `startTime` and `endTime` as text fields to define time slots.

`clients` stores information about the individuals receiving services. It has 8 columns, including an optional `userId` (for authenticated clients) and a mandatory `professionalId` foreign key, also with `onDelete: "cascade"`. This design allows for clients to be associated with a professional even if they don't have a full Odys user account.

The core of the booking system resides in the `appointments` table, which has 13 columns. It links `professionalId` and `clientId`, and optionally `recurringScheduleId` for appointments generated from recurring schedules. Key fields include `startsAt` and `endsAt` timestamps, `status` (tracking the appointment lifecycle from `pending_confirmation` to `completed` or `cancelled`), and `paymentStatus` (from `none` to `captured` or `refunded`). The `appointments` table also includes a unique index, `appointments_pro_starts_at_active_uidx`, on `professionalId` and `startsAt`, specifically filtered to exclude appointments with `rejected` or `cancelled` statuses. This index is a critical defense against double-booking, allowing the database to enforce uniqueness for active appointments.

The `agentMetrics` table is dedicated to collecting telemetry for the WhatsApp intake agent. It records details like `traceId`, `conversationPhone`, `promptVersion`, `promptHash`, and various cost and latency metrics (`totalCostUsd`, `totalCostBrl`, `totalLatencyMs`). The `providersUsed` column is stored as a `text` array, and `outcome` tracks the resolution of each agent interaction. This table is designed for best-effort insertion, ensuring that metric collection failures do not impede the primary function of sending replies.

## Design Decisions

The database schema reflects several deliberate design choices aimed at balancing flexibility, data integrity, and performance:

*   **Drizzle ORM and PostgreSQL**: The combination of Drizzle ORM with PostgreSQL on Supabase was chosen for its strong type safety, declarative schema definition, and the robust features of a managed PostgreSQL service. Drizzle's ability to infer types from the schema definitions significantly reduces runtime errors and improves developer experience. Supabase provides a scalable and secure hosting environment, along with integrated authentication that simplifies user management.
*   **UUID Primary Keys**: All tables consistently use `uuid("id").primaryKey().defaultRandom()` for their primary keys. This approach generates unique identifiers without relying on sequential integers, which can be beneficial in distributed systems and prevents information leakage through predictable IDs.
*   **Referential Integrity with `onDelete: "cascade"`**: Many foreign key relationships, such as `availability.professionalId` referencing `professionals.id`, are defined with `onDelete: "cascade"`. This ensures that when a parent record (e.g., a professional) is deleted, all associated child records (e.g., their availability, clients, appointments) are automatically removed by the database. This simplifies application logic for deletions and helps maintain data consistency.
*   **Application-level "Enums" via `text` columns**: Many columns, such as `professionals.profession`, `professionals.plan`, `appointments.status`, and `messages.type`, are defined as `text` but are intended to hold a limited set of predefined values. This offers flexibility in adding new states or types without requiring schema migrations, though it shifts validation responsibility to the application layer.
*   **Concurrency Control with Partial Unique Index**: The `appointments_pro_starts_at_active_uidx` on the `appointments` table is a sophisticated design choice. By creating a unique index on `professionalId` and `startsAt` *only for appointments not in 'rejected' or 'cancelled' statuses*, the database provides a strong guarantee against double-booking. This complements application-level checks by providing a final, atomic enforcement mechanism.
*   **Flexible Client Association**: The `clients.userId` column is nullable, allowing clients to book appointments without needing a full user account. This lowers the barrier to entry for new clients while still allowing authenticated users to be linked to their client profiles.
*   **Telemetry for AI Agent**: The `agentMetrics` table is designed to capture detailed performance and outcome data for the AI agent. The use of `numeric` types for costs (`totalCostUsd`, `totalCostBrl`) with specified precision and scale, and `text().array()` for `providersUsed`, indicates a need for granular tracking and analysis of AI operations. The "best-effort" insertion strategy for these metrics prioritizes the user experience over absolute data capture for non-critical telemetry.

## Potential Improvements

While the current database schema is functional and well-structured, several areas could be considered for further refinement to enhance data integrity, query efficiency, or developer experience:

1.  **Introduce Native Enum Types for Statuses and Types**: Many `text` columns, such as `professionals.profession`, `professionals.plan`, `appointments.status`, `appointments.paymentStatus`, `recurringSchedules.frequency`, `messages.sender`, `messages.type`, `notifications.recipientType`, `notifications.type`, and `agentMetrics.outcome`, effectively function as enums. Migrating these to native PostgreSQL `ENUM` types (which Drizzle supports) would enforce data integrity at the database level, preventing invalid values from being inserted. This would also improve discoverability of valid options and potentially optimize storage.
2.  **Utilize PostgreSQL `TIME` Type for Time-Only Fields**: The `availability.startTime`, `availability.endTime`, and `recurringSchedules.time` columns are currently defined as `text`. Using PostgreSQL's native `TIME` type would provide stronger type validation, allow for more natural temporal comparisons and calculations directly within SQL queries, and ensure consistent formatting without relying on application-level parsing.
3.  **Consider Foreign Key for `userId` to Supabase `auth.users`**: The `professionals.userId` and `clients.userId` columns are `text` fields intended to link to Supabase's authentication system. While Supabase handles the authentication aspect, these `userId` columns do not have a database-level foreign key constraint. If the `auth.users` table (or a suitable view of it) were accessible and mapped within the Drizzle schema, adding a foreign key constraint could provide an additional layer of referential integrity, ensuring that `userId` values always correspond to existing users. This would require careful consideration of Supabase's internal schema management.
4.  **Normalize `agentMetrics.providersUsed`**: The `agentMetrics.providersUsed` column is currently a `text().array()`. While convenient for simple storage, if there's a need to query or analyze individual provider usage more deeply (e.g., "how many times was provider X used?"), normalizing this into a separate `agent_metric_providers` table with a foreign key to `agentMetrics.id` would be more efficient for complex queries and reporting.
