# Database

The database serves as the central data store for Odys, meticulously structuring all information related to professionals, clients, appointments, and the operational metrics of the AI agent. This document explores the architecture of the database, which is built on Supabase Postgres and managed through the Drizzle ORM, providing a deep understanding of its schema and underlying design principles.

## Overview

Odys utilizes a PostgreSQL database hosted on Supabase, a choice that provides a managed, scalable backend with integrated authentication and storage capabilities. Interacting with this PostgreSQL instance is Drizzle ORM, a TypeScript-first ORM that allows for defining the database schema and performing queries with strong type safety.

The database connection is established in `src/lib/db/index.ts`, where the `postgres` client is initialized using the `DATABASE_URL` environment variable. This client is then passed to Drizzle to create the `db` instance, configured with the schema definitions found in `src/lib/db/schema.ts`. This separation of concerns keeps the connection logic distinct from the schema definitions, promoting modularity. The `drizzle.config.ts` file, driven by `drizzle-kit`, manages schema migrations, ensuring that changes to `src/lib/db/schema.ts` can be safely applied to the production database.

The Odys database comprises 11 distinct tables, each designed to manage a specific aspect of the application's data.

## Schema Details

### Professionals

The `professionals` table is the foundational entity, representing the service providers within the Odys ecosystem. It contains 32 columns, capturing a wide array of information about each professional.

Each professional is uniquely identified by a `uuid` `id` and linked to a Supabase authentication user via the `userId` column, which is a `text` type and enforced as unique. A `slug` column, also unique, is provided for creating user-friendly public profile URLs. Essential contact information like `name` and `phone` are stored, with `email` being optional, alongside professional details such as `profession` and a `bio`.

The table also tracks business-specific configurations: `sessionDuration` (in minutes, defaulting to 50) and `sessionPrice` (in cents, defaulting to 0). The `plan` column, defaulting to "free", indicates the professional's subscription level. Payment preferences are detailed through `paymentType` (defaulting to "upfront") and `paymentPercentage` (defaulting to 100). For direct payments, `pixKeyType` and `pixKey` are available. Stripe integration is supported with `stripeCustomerId` and `stripeSubscriptionId` columns. The table also includes `trialEndsAt` to manage trial periods and a `welcomeMessage` for new clients. An `autoConfirm` boolean, defaulting to `false`, determines if appointments are automatically confirmed.

Location data for in-person services includes `addressLine`, `neighborhood`, `city`, `state`, `postalCode`, and `latitude`/`longitude` coordinates, which are populated via geocoding. The `serviceType` column, defaulting to "both", indicates whether services are "in_person", "online", or "both".

Timestamps `createdAt` and `updatedAt` automatically track record creation and modification, while `active` (defaulting to `true`) indicates the professional's operational status. Two indexes, `professionals_profession_idx` and `professionals_city_idx`, are defined to optimize queries based on profession and location.

### Availability

The `availability` table defines the time slots when a professional is available for appointments. It contains 5 columns. Each entry is linked to a professional via `professionalId`, which is a `uuid` foreign key referencing `professionals.id` with an `onDelete: "cascade"` rule. This ensures that a professional's availability records are automatically removed if the professional's profile is deleted. The `dayOfWeek` (0=Sunday, 6=Saturday), `startTime`, and `endTime` columns specify the recurring availability. An index `availability_professional_id_idx` is present to speed up queries for a professional's schedule.

### Clients

The `clients` table stores information about individuals who book services. It has 8 columns. Each client is associated with a `professionalId` (FK to `professionals.id` with `onDelete: "cascade"`), reflecting the professional who manages this client. The `userId` column, a `text` type, is optional, allowing clients to book appointments without needing a full Supabase user account. Basic client details like `name` and `phone` are stored, with `email` and `avatarUrl` being optional. The `createdAt` timestamp tracks when the client record was created. Indexes `clients_professional_id_idx` and `clients_user_id_idx` facilitate efficient lookups.

### Client Notes

The `clientNotes` table provides a private space for professionals to record observations about their clients. It contains 6 columns. Each note is linked to both a `professionalId` and a `clientId` (both `uuid` foreign keys with `onDelete: "cascade"`). The `content` column stores the actual note, and `createdAt`/`updatedAt` timestamps track its lifecycle.

### Recurring Schedules

The `recurringSchedules` table manages appointments that repeat over time, such as weekly therapy sessions. It has 9 columns. It links a `professionalId` and `clientId` (both `uuid` foreign keys with `onDelete: "cascade"`). The `frequency` column (e.g., "weekly", "biweekly", "twice_weekly") defines the recurrence pattern, while `dayOfWeek` and `secondDayOfWeek` specify the days. The `time` column stores the appointment time. An `active` boolean, defaulting to `true`, controls whether the schedule is currently in effect.

### Appointments

The `appointments` table is central to the scheduling functionality, detailing each individual service booking. It contains 13 columns. Each appointment is tied to a `professionalId` and `clientId` (both `uuid` foreign keys with `onDelete: "cascade"`). It can also be linked to a `recurringScheduleId` (FK to `recurringSchedules.id`), though this reference does not cascade deletions.

The `startsAt` and `endsAt` timestamps define the appointment's duration. The `status` column, defaulting to "pending_confirmation", tracks the appointment's lifecycle through states like "confirmed", "rejected", "completed", "cancelled", or "no_show". Similarly, `paymentStatus`, defaulting to "none", tracks payment states such as "authorized", "captured", or "refunded". Stripe payment intent IDs are stored in `stripePaymentIntentId`.

To manage reminders, `reminderSent24h` and `reminderSent1h` boolean flags, both defaulting to `false`, indicate whether automated reminders have been dispatched. An optional `notes` field allows for additional details.

Several indexes are defined for efficient querying: `appointments_professional_id_idx`, `appointments_client_id_idx`, `appointments_starts_at_idx`, and `appointments_status_idx`. A critical `uniqueIndex`, `appointments_pro_starts_at_active_uidx`, is defined on `professionalId` and `startsAt`, with a `WHERE` clause filtering for statuses `NOT IN ('rejected', 'cancelled')`. This index acts as a database-level safeguard against double-booking, preventing two active appointments from occupying the same slot for a professional.

### Messages

The `messages` table facilitates communication between professionals and clients. It has 9 columns. Each message is associated with a `professionalId` and `clientId` (both `uuid` foreign keys with `onDelete: "cascade"`). The `sender` column indicates whether the message originated from the "professional" or "client". The `type` column, defaulting to "text", can also be "link" or "pdf", with `fileUrl` storing the path for file attachments. The `content` holds the message body, and `readAt` tracks when the message was viewed. An index `messages_professional_client_idx` optimizes message retrieval for specific professional-client conversations.

### Follows

The `follows` table tracks when a user expresses interest in a professional. It contains 4 columns. It links a `userId` (a `text` type) to a `professionalId` (a `uuid` foreign key with `onDelete: "cascade"`). The `createdAt` timestamp records when the follow occurred. Indexes `follows_professional_id_idx` and `follows_user_id_idx` support efficient lookups.

### Reviews

The `reviews` table stores client feedback after an appointment. It has 7 columns. Each review is linked to a `professionalId`, `clientId`, and `appointmentId` (all `uuid` foreign keys with `onDelete: "cascade"`). The `appointmentId` is also unique, ensuring only one review per appointment. The `rating` (1-5 integer) and an optional `comment` capture the feedback. An index `reviews_professional_id_idx` is provided for querying reviews by professional.

### Notifications

The `notifications` table manages system-generated alerts for users. It contains 8 columns. It targets a `recipientId` (a `text` type, typically a Supabase user ID) and `recipientType` ("professional" or "client"). The `type` column categorizes the notification (e.g., "booking_request", "new_message"), while `title` and `body` provide the message content. A `read` boolean, defaulting to `false`, tracks whether the notification has been viewed. An index `notifications_recipient_id_idx` allows for quick retrieval of notifications for a specific user.

### Agent Metrics

The `agentMetrics` table is dedicated to storing telemetry data for the WhatsApp intake agent. It has 12 columns. These metrics are inserted on a best-effort basis at the end of each `handleIncomingMessage` call, ensuring that metric collection failures do not impede message delivery.

Key columns include `traceId` for correlating agent turns, `conversationPhone` to identify the client, and `promptVersion`/`promptHash` to track the AI model's configuration. Financial and performance metrics like `totalCostUsd`, `totalCostBrl` (both `numeric` with specified precision), and `totalLatencyMs` are recorded. `toolCallCount` tracks the number of external tools invoked, and `providersUsed` is a `text().array()` column to store a list of AI providers. The `outcome` column categorizes the result of an agent turn (e.g., "booked", "cancelled", "searched"). Indexes `agent_metrics_trace_id_idx`, `agent_metrics_created_at_idx`, and `agent_metrics_outcome_idx` are defined for analytical queries.

## Design Decisions

The choice of Drizzle ORM with Supabase Postgres reflects a deliberate set of trade-offs aimed at developer experience, data integrity, and operational simplicity.

**Drizzle ORM for Type Safety and Developer Experience:** Drizzle was selected for its TypeScript-first approach, which provides compile-time type safety for database interactions. This significantly reduces the likelihood of runtime errors related to schema mismatches and improves developer productivity by offering strong autocompletion and validation. Unlike some ORMs, Drizzle generates SQL directly, avoiding runtime reflection overhead and offering a more direct control over the generated queries, which can be beneficial for performance tuning.

**Supabase Postgres for Managed Infrastructure:** Hosting the database on Supabase simplifies infrastructure management. Supabase handles database provisioning, backups, and scaling, allowing the Odys team to focus on application development rather than database operations. Its integration with Supabase Auth also streamlines user management and access control.

**UUID Primary Keys:** All tables use `uuid("id").primaryKey().defaultRandom()` for their primary keys. This choice provides globally unique identifiers, which is advantageous in distributed systems and prevents potential issues with sequential integer IDs, such as predictability or contention in high-insert scenarios.

**`onDelete: "cascade"` for Referential Integrity:** Many foreign key relationships, such as `availability.professionalId` referencing `professionals.id`, are defined with `onDelete: "cascade"`. This design decision simplifies data management by automatically deleting dependent records when a parent record is removed. For instance, deleting a professional will automatically remove all their associated availability, clients, client notes, recurring schedules, appointments, messages, follows, and reviews. While convenient, this requires careful consideration to avoid unintended data loss. The `appointments.recurringScheduleId` column, notably, does *not* have `onDelete: "cascade"`, indicating that recurring schedules might persist even if an individual appointment linked to them is deleted.

**Defense-in-Depth for Appointment Booking:** The `appointments` table includes a `uniqueIndex("appointments_pro_starts_at_active_uidx")` on `professionalId` and `startsAt`, with a `WHERE` clause filtering for `status NOT IN ('rejected', 'cancelled')`. This is a crucial design choice for preventing double-booking. While application-level logic and transactional safeguards are typically in place, this partial unique index provides a database-level guarantee. If two concurrent requests attempt to book the same slot for the same professional, the database will reject the second attempt with a `23505` (unique violation) error, even if application-level checks might have momentarily missed the conflict. The `WHERE` clause ensures that once an appointment is rejected or cancelled, the slot becomes available again without needing to remove the historical record.

**`text` for Time and Day Representation:** Columns like `availability.startTime`, `availability.endTime`, and `recurringSchedules.time` are stored as `text`. This simplifies the representation of time without needing to deal with complex `Date` objects or timezones at the database level for simple time-of-day values. The application layer is responsible for parsing and interpreting these strings. Similarly, `dayOfWeek` is an `integer`, mapping to 0-6, which is a straightforward way to represent days.

**`numeric` for Financial Precision:** For financial data such as `agentMetrics.totalCostUsd` (`precision: 10, scale: 6`) and `agentMetrics.totalCostBrl` (`precision: 10, scale: 4`), the `numeric` type is used. This ensures exact decimal representation, avoiding floating-point inaccuracies that can occur with `doublePrecision` when dealing with monetary values.

## Potential Improvements

1.  **Introduce `pgEnum` for Status and Type Fields**: Many columns currently use `text` to represent a finite set of states or types, such as `professionals.profession`, `professionals.plan`, `professionals.paymentType`, `appointments.status`, `appointments.paymentStatus`, `messages.type`, `notifications.type`, and `agentMetrics.outcome`. Migrating these to Drizzle's `pgEnum` would provide stricter type checking at the TypeScript level and enforce valid values directly within the PostgreSQL database. This would enhance data integrity by preventing invalid states from being inserted and improve code clarity by making the allowed values explicit in the schema definition.

2.  **Add Compound Unique Index for `follows` Table**: The `follows` table allows a `userId` to follow a `professionalId`. While the current schema does not explicitly prevent a user from following the same professional multiple times, adding a unique index on `(userId, professionalId)` to the `follows` table in `src/lib/db/schema.ts` would enforce this constraint at the database level. This would prevent duplicate follow entries and simplify application logic by offloading this validation to the database.

3.  **Utilize PostgreSQL `TIME` Type for Time-of-Day Columns**: The `availability.startTime`, `availability.endTime`, and `recurringSchedules.time` columns are currently defined as `text`. PostgreSQL offers a dedicated `TIME` type which is designed for storing time-of-day values without date or timezone information. Using Drizzle's `time` column type would provide database-level validation for time formats and potentially enable more efficient time-based queries or calculations directly within the database, reducing the need for application-side parsing and validation.
