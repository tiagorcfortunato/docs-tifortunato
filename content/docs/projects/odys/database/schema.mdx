# Database Schema

The Odys application relies on a PostgreSQL database to manage all its core data, from professional profiles and client information to appointment schedules and communication logs. This document provides a deep dive into the 11 tables that constitute the Odys schema, explaining their purpose, the rationale behind their structure, and how they interrelate. Understanding this schema is fundamental to comprehending how Odys organizes and persists information, enabling its various features for professionals and clients.

## Overview

The Odys database schema is designed to support a platform connecting professionals with clients for various services. At its heart are the `professionals` and `clients` tables, representing the two primary user types. These entities are linked through various transactional tables such as `appointments`, `messages`, and `reviews`, which capture the interactions and services provided. Supporting these core interactions are tables like `availability` for professional scheduling, `recurringSchedules` for ongoing appointments, and `clientNotes` for private professional records. Finally, `follows`, `notifications`, and `agentMetrics` provide additional functionality for user engagement, communication, and system telemetry.

The schema uses `uuid` for primary keys across all tables, ensuring globally unique identifiers. Many relationships are enforced with foreign keys, often employing `onDelete: "cascade"` to simplify data cleanup when parent records are removed.

## Professionals

The `professionals` table is central to the application, storing comprehensive details about each service provider. With 32 columns, it's the largest table, reflecting the extensive information required for a professional's profile and operational settings.

Each professional is identified by a `uuid` `id` and linked to an external authentication system via `userId` (a `text` column, implying an external identity provider like Supabase). A `slug` column provides a human-readable, unique URL path for public profiles, like `odys.com.br/p/dr-ana`. Essential contact information includes `name`, `phone`, and `email`.

Operational details are extensive: `profession` (e.g., "psychologist"), `bio`, `avatarUrl`, `sessionDuration` (defaulting to 50 minutes), and `sessionPrice` (defaulting to 0 cents). The `plan` column tracks their subscription level ("free", "pro", "premium"), while `paymentType` and `paymentPercentage` define how they receive payments from clients. For direct payments, `pixKeyType` and `pixKey` store Brazilian Pix details. Integration with Stripe is managed via `stripeCustomerId` and `stripeSubscriptionId`.

The table also includes fields for managing professional availability and service delivery: `trialEndsAt`, `welcomeMessage`, and `autoConfirm` for appointment automation. Location-based services are supported by `serviceType` ("in_person", "online", "both") and detailed address fields (`addressLine`, `neighborhood`, `city`, `state`, `postalCode`), along with `latitude` and `longitude` for geocoding. Finally, `active` indicates profile visibility, and `createdAt` and `updatedAt` track record lifecycle.

Indexes on `profession` and `city` are defined to optimize searches for professionals based on their specialty or location, which are common filtering criteria for clients.

## Availability

The `availability` table stores the regular working hours for each professional. It has 5 columns, capturing specific time slots a professional is generally available.

Each record includes an `id`, a `professionalId` (referencing `professionals.id` with `onDelete: "cascade"`), `dayOfWeek` (an integer from 0 for Sunday to 6 for Saturday), `startTime`, and `endTime`. The `startTime` and `endTime` are stored as `text` (e.g., "09:00"), which simplifies storage but requires careful parsing and validation in the application layer.

An index on `professionalId` ensures efficient retrieval of a professional's schedule.

## Clients

The `clients` table, with 8 columns, stores information about individuals who book appointments with professionals.

Similar to professionals, clients have a `uuid` `id` and an optional `userId` (a `text` column, indicating they might have an external account or be guest users). Each client is associated with a specific `professionalId` (referencing `professionals.id` with `onDelete: "cascade"`), reflecting that clients are managed within the context of a professional's practice. Key client details include `name`, `phone`, `email`, and `avatarUrl`. The `createdAt` timestamp tracks when the client record was created.

Indexes on `professionalId` and `userId` facilitate quick lookups of clients by their associated professional or external user ID.

## Client Notes

The `clientNotes` table provides a private space for professionals to record observations about their clients. This table has 6 columns.

Each note has an `id`, `professionalId` (referencing `professionals.id` with `onDelete: "cascade"`), `clientId` (referencing `clients.id` with `onDelete: "cascade"`), and the `content` of the note. `createdAt` and `updatedAt` track the note's lifecycle. The `onDelete: "cascade"` ensures that if a professional or client record is removed, their associated notes are also deleted, maintaining data integrity.

## Recurring Schedules

The `recurringSchedules` table manages appointments that repeat over time, such as weekly therapy sessions. It contains 9 columns.

A recurring schedule is identified by an `id`, linked to a `professionalId` and `clientId` (both with `onDelete: "cascade"`). The `frequency` column (e.g., "weekly", "biweekly", "twice_weekly") defines the recurrence pattern. `dayOfWeek` and `secondDayOfWeek` (both nullable integers) specify the days, accommodating different frequencies. The `time` column stores the appointment time (e.g., "14:00"). An `active` boolean flag controls whether the schedule is currently generating appointments, and `createdAt` records its creation.

## Appointments

The `appointments` table is a core transactional table, detailing every scheduled interaction between a professional and a client. It has 13 columns.

Each appointment has an `id`, `professionalId`, and `clientId` (both with `onDelete: "cascade"`). It can optionally be linked to a `recurringScheduleId`. The `startsAt` and `endsAt` timestamps define the appointment duration. The `status` column tracks the appointment's lifecycle ("pending_confirmation", "confirmed", "rejected", "completed", "cancelled", "no_show"), while `paymentStatus` tracks payment progress ("none", "authorized", "captured", "refunded"). `stripePaymentIntentId` stores the ID for Stripe transactions.

The table also includes `reminderSent24h` and `reminderSent1h` boolean flags to manage automated reminders. A `notes` field allows for specific details about the appointment, and `createdAt` marks its creation.

Several indexes are defined to optimize common queries: `professionalId`, `clientId`, `startsAt`, and `status`. A particularly important design choice is the `appointments_pro_starts_at_active_uidx` unique partial index on `professionalId` and `startsAt`. This index is filtered to only apply to appointments with statuses *not* in ('rejected', 'cancelled'). This "defense-in-depth" mechanism prevents double-booking by ensuring that no two active appointments can exist for the same professional at the exact same start time, even if application-level checks fail in a concurrent scenario.

## Messages

The `messages` table facilitates communication between professionals and clients, containing 9 columns.

Each message has an `id`, `professionalId`, and `clientId` (both with `onDelete: "cascade"`). The `sender` column identifies who sent the message ("professional" or "client"). The `type` column (defaulting to "text") allows for different message formats ("text", "link", "pdf"). The `content` holds the message body, and `fileUrl` is used for attachments like PDFs. `readAt` tracks when the message was viewed, and `createdAt` records its timestamp.

An index on `professionalId` and `clientId` optimizes retrieving message threads between a specific professional and client.

## Follows

The `follows` table tracks when a client (identified by `userId`) expresses interest in a professional. It has 4 columns.

Each record includes an `id`, the `userId` of the follower, and the `professionalId` of the followed professional (with `onDelete: "cascade"`). `createdAt` marks when the follow relationship was established.

Indexes on `professionalId` and `userId` allow for efficient querying of who a professional is followed by, or which professionals a user follows.

## Reviews

The `reviews` table stores feedback provided by clients after an appointment. It has 7 columns.

A review has an `id`, `professionalId`, `clientId`, and `appointmentId` (all with `onDelete: "cascade"`). The `appointmentId` is also unique, ensuring only one review per appointment. `rating` (an integer from 1-5) and an optional `comment` capture the feedback. `createdAt` records when the review was submitted.

An index on `professionalId` allows for easy aggregation of reviews for a given professional.

## Notifications

The `notifications` table manages alerts and updates for both professionals and clients. It has 8 columns.

Each notification has an `id`, a `recipientId` (a `text` column, likely an external user ID), and `recipientType` ("professional" or "client") to distinguish the target. The `type` column categorizes the notification (e.g., "booking_request", "booking_confirmed", "new_message"). `title` and `body` provide the notification content. A `read` boolean flag tracks whether the notification has been viewed, and `createdAt` records its timestamp.

An index on `recipientId` allows for efficient retrieval of all notifications for a specific user.

## Agent Metrics

The `agentMetrics` table is dedicated to telemetry for the WhatsApp intake agent, capturing performance and outcome data for each conversation turn. It has 12 columns.

Each metric record has an `id`, a `traceId` to link related turns, and `conversationPhone` to identify the client. `promptVersion` and `promptHash` track the AI model's configuration. `totalCostUsd` and `totalCostBrl` (both `numeric` with specified precision and scale) record the monetary cost of the turn. `totalLatencyMs` and `toolCallCount` measure performance. `providersUsed` is an array of `text` to list the AI services engaged. The `outcome` column (e.g., "booked", "cancelled", "searched", "help") categorizes the result of the interaction, crucial for conversion analysis. `createdAt` marks when the metric was recorded.

Indexes on `traceId`, `createdAt`, and `outcome` support analytical queries on agent performance and conversation flows.

## Design decisions

The schema reflects several deliberate design choices:

*   **UUID Primary Keys**: The consistent use of `uuid("id").primaryKey().defaultRandom()` across all tables provides globally unique identifiers, simplifying distributed system concerns and preventing ID collisions.
*   **External User IDs**: Instead of a single `users` table within this schema, `professionals.userId` and `clients.userId` are `text` columns, strongly suggesting integration with an external authentication service (like Supabase, as noted in comments). This decouples authentication from core application data, allowing the external service to manage user accounts while Odys manages profiles and relationships.
*   **`onDelete: "cascade"` for Core Relationships**: Many foreign key relationships, such as `availability.professionalId` referencing `professionals.id`, use `onDelete: "cascade"`. This is a pragmatic choice for data integrity, ensuring that when a parent record (e.g., a professional) is deleted, all dependent records (e.g., their availability, clients, appointments) are automatically removed. This simplifies application logic for cleanup but requires careful consideration to avoid accidental data loss.
*   **`text` for Enumerated Values**: Many columns like `professionals.profession`, `professionals.plan`, `appointments.status`, `messages.sender`, and `notifications.type` are defined as `text`. While flexible, this choice defers validation of allowed values to the application layer rather than enforcing them at the database level with PostgreSQL `ENUM` types.
*   **Timestamp Defaults**: `createdAt` columns consistently use `defaultNow()`, and `updatedAt` columns also default to `defaultNow()`, ensuring automatic timestamping for record creation and modification.
*   **Partial Unique Index for Concurrency**: The `appointments_pro_starts_at_active_uidx` on the `appointments` table is a sophisticated use of a partial unique index. By applying the uniqueness constraint only to appointments that are not yet in a terminal state (`'rejected'`, `'cancelled'`), it provides a database-level guarantee against double-booking for active appointments, complementing application-level concurrency controls.
*   **`numeric` for Financial Data**: `agentMetrics.totalCostUsd` and `totalCostBrl` use the `numeric` type with explicit precision and scale. This is the correct choice for storing monetary values, avoiding floating-point inaccuracies that can arise with `doublePrecision`.
*   **Array Type for `providersUsed`**: The `agentMetrics.providersUsed` column is defined as `text().array()`, directly leveraging PostgreSQL's native array type. This is an efficient way to store multiple values (e.g., a list of AI providers) within a single column without needing a separate join table.

## Potential improvements

1.  **Introduce Database Enums for Fixed-Value `text` Columns**: Many `text` columns, such as `professionals.profession`, `professionals.plan`, `professionals.paymentType`, `appointments.status`, `appointments.paymentStatus`, `recurringSchedules.frequency`, `messages.sender`, `messages.type`, `notifications.recipientType`, `notifications.type`, and `agentMetrics.outcome`, represent a finite set of predefined values. Converting these to PostgreSQL `ENUM` types would enforce data integrity at the database level, prevent invalid values from being inserted, and improve type safety in the application code. For example, `professionals.profession` could be an enum `('psychologist', 'personal_trainer', 'nutritionist')`.
2.  **Centralize User Management with a `users` Table**: The current schema uses `userId` (a `text` column) in both `professionals` and `clients` tables, implying an external authentication system. While functional, introducing a dedicated `users` table within the Odys schema, with `id` as a `uuid` and `userId` as a foreign key to this new `users` table, could centralize user identity management. This would allow for a single point of reference for all users, regardless of whether they are professionals or clients, and enable more explicit relationships and potentially shared user attributes. The `clients.userId` column is currently nullable, which could be a point of divergence in user identity management.
3.  **Add Missing Foreign Key Indexes**: While many foreign keys are indexed, some are not. For instance, the `clientNotes` table has `clientId` as a foreign key to `clients.id`, but there is no explicit index defined on `clientNotes.clientId`. Similarly, `recurringSchedules` has `clientId` as a foreign key, but no index is defined on `recurringSchedules.clientId`. Adding indexes to these foreign key columns would significantly improve query performance when joining or filtering on these relationships, which is a common access pattern.
4.  **Refine Polymorphic Association in `notifications`**: The `notifications` table uses `recipientId` (text) and `recipientType` (text) to point to either a professional or a client. This is a common pattern for polymorphic associations but means the database cannot enforce referential integrity. If the number of recipient types is small and stable, consider creating separate notification tables for each recipient type (e.g., `professionalNotifications`, `clientNotifications`) or using a more advanced pattern like a `users` table with a single foreign key.
