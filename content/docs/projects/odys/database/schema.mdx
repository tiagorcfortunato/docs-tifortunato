# Database Schema

The `src/lib/db/schema.ts` file defines the foundational data model for the Odys application, outlining the structure of its 11 PostgreSQL tables using Drizzle ORM. This schema dictates how core entities like professionals, clients, and appointments are stored and related, forming the backbone of the platform's operations. Understanding this schema is crucial for anyone working with Odys's data layer, as it reveals the relationships and constraints that govern the application's behavior.

## Overview

The Odys database schema is centered around the interaction between `professionals` and `clients`, facilitating the booking and management of `appointments`. A `professionals` table serves as the primary entity for service providers, holding extensive details about their profile, services, payment preferences, and physical location. `clients` are associated with specific professionals, allowing for personalized management, including `clientNotes` and `messages`.

The system supports `recurringSchedules` for regular appointments and tracks individual `appointments` with detailed status and payment information. `availability` defines when a professional is open for bookings. Beyond core scheduling, the schema includes tables for `reviews` to capture feedback, `follows` to track client interest in professionals, and `notifications` to keep users informed. Finally, `agentMetrics` provides telemetry for the platform's automated intake agent, capturing operational data about its interactions.

## Professionals

The `professionals` table is the central entity for service providers on the Odys platform, containing 32 columns that describe a professional's profile, services, and operational settings. Each professional is uniquely identified by a `uuid` `id` and linked to an external authentication system via a `userId` (a `text` column that is `notNull` and `unique`). A `slug` column, also `notNull` and `unique`, is provided for generating public-facing URLs, such as `odys.com.br/p/dr-ana`.

Key service-related columns include `profession` (e.g., "psychologist", "nutritionist"), `sessionDuration` (defaulting to 50 minutes), and `sessionPrice` (defaulting to 0 cents). The `plan` column tracks the professional's subscription level ("free", "pro", "premium"), while `paymentType` and `paymentPercentage` define how they prefer to receive payments from clients. For direct payments, `pixKeyType` and `pixKey` store Brazilian Pix details, and `stripeCustomerId` and `stripeSubscriptionId` link to Stripe accounts for integrated payment processing.

The table also captures location details like `addressLine`, `city`, `state`, `postalCode`, and `latitude`/`longitude` for professionals offering "in-person" services, indicated by the `serviceType` column (which defaults to "both" for online and in-person). Timestamps `createdAt` and `updatedAt` automatically track record creation and modification, defaulting to the current time. Two non-unique indexes are defined on `profession` and `city` to facilitate searching and filtering professionals.

## Availability

The `availability` table defines the time slots when a `professional` is available for appointments. It contains 5 columns, with each entry specifying a `dayOfWeek` (0 for Sunday to 6 for Saturday) and `startTime` and `endTime` as `text` fields (e.g., "09:00", "18:00"). The `professionalId` column is a `uuid` foreign key, linking back to the `professionals` table. A crucial design choice here is the `onDelete: "cascade"` action, which means that if a professional's record is deleted, all their associated availability entries are automatically removed. An index on `professionalId` helps optimize queries for a professional's schedule.

## Clients

The `clients` table stores information about individuals who book appointments with professionals. It has 8 columns, including a `uuid` `id` and a `professionalId` foreign key, also with `onDelete: "cascade"`, ensuring that client records are cleaned up if their associated professional is removed. Clients are identified by `name` and `phone`, both `notNull`. An `email` and `avatarUrl` are optional. A `userId` column, a `text` field, is present but `nullable`, indicating that clients can book appointments without necessarily having a user account in the external authentication system. Indexes are provided on both `professionalId` and `userId` to speed up lookups.

## Client Notes

The `clientNotes` table provides a private space for professionals to record observations about their clients. This table has 6 columns, including `professionalId` and `clientId` foreign keys, both configured with `onDelete: "cascade"`. This ensures that notes are automatically deleted if either the professional or the client record is removed. The `content` column, a `text` field, stores the actual note. `createdAt` and `updatedAt` timestamps track the lifecycle of each note.

## Recurring Schedules

The `recurringSchedules` table manages appointments that repeat over time, such as weekly therapy sessions. It comprises 9 columns, linking to `professionalId` and `clientId` with `onDelete: "cascade"`. The `frequency` column (e.g., "weekly", "biweekly", "twice_weekly") dictates the recurrence pattern. `dayOfWeek` and `secondDayOfWeek` (both `nullable` integers) specify the days for weekly or twice-weekly schedules, while `time` (a `text` field like "14:00") sets the daily appointment time. An `active` boolean column, defaulting to `true`, allows for toggling the schedule's status.

## Appointments

The `appointments` table is central to the scheduling functionality, detailing each individual booking. With 13 columns, it links to `professionalId` and `clientId` (both with `onDelete: "cascade"`), and optionally to `recurringScheduleId`. The `startsAt` and `endsAt` columns, both `timestamp` and `notNull`, define the appointment's duration.

The `status` column tracks the appointment's lifecycle, moving from "pending_confirmation" to "confirmed", "rejected", "completed", "cancelled", or "no_show". Similarly, `paymentStatus` progresses from "none" to "authorized", "captured", or "refunded", with `stripePaymentIntentId` storing the Stripe transaction ID. The table also includes `reminderSent24h` and `reminderSent1h` booleans to manage notification delivery.

A notable design choice is the `appointments_pro_starts_at_active_uidx` unique index. This partial index, applied to `professionalId` and `startsAt`, specifically filters for appointments where `status` is *not* 'rejected' or 'cancelled'. This prevents double-booking the same time slot for a professional while allowing cancelled or rejected slots to be re-booked later.

## Messages

The `messages` table facilitates communication between professionals and clients. It has 9 columns, including `professionalId` and `clientId` foreign keys, both with `onDelete: "cascade"`. The `sender` column identifies who sent the message ("professional" or "client"), and `type` (defaulting to "text") indicates the message format (e.g., "text", "link", "pdf"). The `content` of the message is stored as `text`, and `fileUrl` is available for attachments. A `readAt` timestamp tracks when a message was viewed. An index on `(professionalId, clientId)` optimizes message retrieval for specific conversations.

## Follows

The `follows` table records when a client expresses interest in a professional. It contains 4 columns: a `uuid` `id`, `userId` (a `text` field for the client's external authentication ID), and `professionalId` (a `uuid` foreign key with `onDelete: "cascade"`). The `createdAt` timestamp marks when the follow occurred. Indexes on `professionalId` and `userId` support efficient querying of follows.

## Reviews

The `reviews` table stores client feedback after an appointment. It has 7 columns, linking to `professionalId`, `clientId`, and `appointmentId` (all with `onDelete: "cascade"`). The `appointmentId` column is also `unique`, ensuring that only one review can be submitted per appointment. The `rating` (an integer from 1-5) and an optional `comment` capture the client's feedback. An index on `professionalId` allows for quick aggregation of reviews for a given professional.

## Notifications

The `notifications` table manages alerts sent to users. With 8 columns, it includes `recipientId` (a `text` field for the external user ID) and `recipientType` ("professional" or "client"). The `type` column categorizes the notification (e.g., "booking_request", "new_message"), while `title` and `body` provide the message content. A `read` boolean, defaulting to `false`, tracks whether the notification has been viewed. An index on `recipientId` allows for efficient retrieval of notifications for a specific user.

## Agent Metrics

The `agentMetrics` table is dedicated to storing telemetry data for the WhatsApp intake agent. This table, with 12 columns, captures operational details for each agent interaction. Key columns include `traceId` for correlating events, `conversationPhone` to identify the client, and `promptVersion` and `promptHash` to track the agent's configuration. Financial metrics like `totalCostUsd` and `totalCostBrl` (both `numeric` with specific precision and scale) and performance metrics like `totalLatencyMs` and `toolCallCount` are recorded. `providersUsed` is an array of `text` to list the services consumed during a turn. The `outcome` column (e.g., "booked", "cancelled", "searched") categorizes the result of the agent's interaction. Indexes on `traceId`, `createdAt`, and `outcome` support analytical queries.

## Design Decisions

The schema for Odys reflects several deliberate design choices aimed at balancing data integrity, query performance, and application flexibility.

The consistent use of `uuid` for primary keys across all 11 tables, coupled with `defaultRandom()`, provides globally unique identifiers that are easy to generate client-side or in distributed environments, reducing potential conflicts compared to sequential integer IDs.

Foreign key relationships are extensively used to maintain referential integrity. The frequent application of `onDelete: "cascade"` for relationships like `availability.professionalId`, `clients.professionalId`, `clientNotes.clientId`, `recurringSchedules.clientId`, `appointments.clientId`, `messages.clientId`, `follows.professionalId`, and `reviews.appointmentId` simplifies data management. This choice means that when a parent record (e.g., a professional) is deleted, all associated child records (e.g., their availability, clients, appointments) are automatically removed by the database. This prevents orphaned records and simplifies application logic for deletion, though it requires careful consideration to avoid unintended data loss.

The `appointments` table includes a partial unique index, `appointments_pro_starts_at_active_uidx`, on `(professionalId, startsAt)` filtered by `status NOT IN ('rejected', 'cancelled')`. This is a crucial "defense-in-depth" mechanism. While application logic typically prevents double-booking, this database-level constraint provides an additional layer of protection against race conditions, ensuring that a professional cannot have two active appointments at the exact same time slot.

Many categorical fields, such as `professionals.profession`, `professionals.plan`, `appointments.status`, `appointments.paymentStatus`, `messages.sender`, `messages.type`, `notifications.recipientType`, `notifications.type`, and `agentMetrics.outcome`, are defined as `text` columns. This offers flexibility, allowing new categories to be added without requiring schema migrations.

Timestamp columns like `createdAt` and `updatedAt` are consistently used across tables, often with `defaultNow()`, to provide automatic auditing of record lifecycles.

The `agentMetrics` table's design, including `numeric` types with specific `precision` and `scale` for costs and `text().array()` for `providersUsed`, demonstrates a pragmatic approach to storing telemetry data. It prioritizes capturing detailed, potentially varied, information about agent interactions without over-normalizing, acknowledging that this data is primarily for analysis rather than transactional integrity.

## Potential Improvements

1.  **Introduce `pgEnum` for categorical `text` fields**: Many columns like `professionals.profession`, `professionals.plan`, `appointments.status`, `appointments.paymentStatus`, `messages.sender`, `messages.type`, `notifications.recipientType`, `notifications.type`, and `agentMetrics.outcome` currently use `text` types. While flexible, this lacks type safety and can lead to data inconsistencies if invalid values are inserted. Drizzle ORM supports `pgEnum`, which would allow defining these categories as explicit enum types in the schema, providing compile-time checks and better data integrity. For example, `professionals.profession` could be `pgEnum("profession_type", ["psychologist", "personal_trainer", "nutritionist"])("profession").notNull()`.

2.  **Add a unique constraint to `follows` on `(userId, professionalId)`**: The `follows` table currently has indexes on `professionalId` and `userId` separately, but lacks a unique constraint on the combination of `userId` and `professionalId`. This means a single user could theoretically "follow" the same professional multiple times, creating redundant records. Adding `uniqueIndex("follows_user_professional_uidx").on(t.userId, t.professionalId)` to the `follows` table definition in `src/lib/db/schema.ts` would prevent duplicate follow entries, ensuring that each user can only follow a professional once.

3.  **Refine `clients.userId` column definition**: The `clients.userId` column is currently `text` and `nullable`, with a comment indicating it's an "optional Supabase auth id". If this `userId` is intended to link to a unique user account in Supabase, it should ideally be `unique` when present. As it stands, multiple client records could potentially link to the same `userId` if they are managed by different professionals, or if the `userId` refers to the client's *own* Supabase ID, which would be unique. Clarifying its exact purpose and adding a `unique` constraint (possibly a partial unique index `where(t.userId.isNotNull())`) if it represents a unique external user would enhance data integrity.
