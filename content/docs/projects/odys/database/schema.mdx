# Database Schema

The `src/lib/db/schema.ts` file defines the foundational data model for the Odys application, outlining the structure of its 11 PostgreSQL tables using Drizzle ORM. This schema is central to how Odys manages professionals, clients, appointments, and internal operations, dictating data storage, relationships, and integrity constraints. Understanding this file is key to grasping the application's core functionality and how different pieces of information interrelate.

## Overview

The Odys database schema is designed around the interactions between professionals and their clients. At its heart, the `professionals` table stores detailed information about service providers, while the `clients` table tracks individuals who book services. These two entities form the basis for most other operations, including `availability` management, `clientNotes`, `recurringSchedules`, and `appointments`. Communication is handled via `messages`, and user engagement is tracked through `follows` and `reviews`. Finally, `notifications` provide a general mechanism for informing users, and `agentMetrics` captures telemetry from automated conversational agents.

## Professionals

The `professionals` table is the central entity for service providers within the Odys platform. It contains 32 columns, capturing a wide array of information from basic contact details to payment preferences and service location.

Each professional is uniquely identified by a `uuid` `id`, which is automatically generated. A `userId` column, a `text` field, links to an external authentication system (likely Supabase), and is marked as unique to ensure a one-to-one mapping between an external user account and a professional profile. The `name` and `phone` are mandatory, while `email` is optional, reflecting scenarios where communication might primarily occur via phone.

A `slug` column, also unique, is provided for creating user-friendly public profile URLs, such as `odys.com.br/p/dr-ana`. The `profession` column categorizes the professional (e.g., "psychologist", "personal_trainer"), and `bio` and `avatarUrl` allow for rich profile customization.

Operational details include `sessionDuration` (in minutes, defaulting to 50) and `sessionPrice` (in cents, defaulting to 0). The `plan` column tracks the professional's subscription level ("free", "pro", "premium"). Payment preferences are detailed with `paymentType` ("upfront", "percentage", "after") and `paymentPercentage` (defaulting to 100%). For direct payments, `pixKeyType` and `pixKey` store Brazilian Pix details. Integration with Stripe is supported via `stripeCustomerId` and `stripeSubscriptionId`.

The table also includes fields for managing trials (`trialEndsAt`), a `welcomeMessage`, and `autoConfirm` for appointments. Location-based services are supported with `serviceType` ("in_person", "online", "both"), `addressLine`, `neighborhood`, `city`, `state`, `postalCode`, and `latitude`/`longitude` for geocoding.

Finally, `active` indicates the professional's status, and `createdAt`/`updatedAt` timestamps track record lifecycle. Indexes on `profession` and `city` are defined to optimize searches for professionals based on their specialty or location.

## Availability

The `availability` table defines when a professional is available for appointments. It has 5 columns and is directly linked to the `professionals` table via `professionalId`.

Each entry has a `uuid` `id`. The `professionalId` is a foreign key referencing `professionals.id`, with an `onDelete: "cascade"` rule, meaning that if a professional is removed, all their availability slots are automatically deleted. `dayOfWeek` stores the day (0 for Sunday, 6 for Saturday), and `startTime` and `endTime` are `text` fields representing specific times (e.g., "09:00", "18:00"). An index on `professionalId` speeds up queries for a professional's schedule.

## Clients

The `clients` table stores information about individuals who book services with professionals. It contains 8 columns.

Similar to professionals, clients have a `uuid` `id`. A `userId` column, a `text` field, is optional, allowing clients to book appointments without needing a full user account. The `professionalId` links a client to a specific professional, also with `onDelete: "cascade"`. `name` and `phone` are mandatory, while `email` and `avatarUrl` are optional. `createdAt` tracks when the client record was created. Indexes are provided for `professionalId` and `userId` to facilitate client lookups.

## Client Notes

The `clientNotes` table allows professionals to keep private notes about their clients. It has 6 columns.

Each note has a `uuid` `id` and is linked to both a `professionalId` and a `clientId`, both with `onDelete: "cascade"` rules. The `content` of the note is a mandatory `text` field. `createdAt` and `updatedAt` timestamps track the note's lifecycle.

## Recurring Schedules

The `recurringSchedules` table manages appointments that happen repeatedly, such as weekly therapy sessions. It has 9 columns.

Each recurring schedule has a `uuid` `id` and is linked to a `professionalId` and `clientId`, both with `onDelete: "cascade"`. The `frequency` column specifies how often the appointment occurs ("weekly", "biweekly", "twice_weekly"). `dayOfWeek` and `secondDayOfWeek` (both nullable integers from 0-6) define the specific days for weekly or twice-weekly schedules. The `time` column stores the appointment time (e.g., "14:00"). An `active` boolean (defaulting to `true`) allows schedules to be temporarily disabled. `createdAt` tracks the creation time.

## Appointments

The `appointments` table is arguably the most critical, detailing every scheduled interaction between a professional and a client. It contains 13 columns.

Each appointment has a `uuid` `id` and is linked to a `professionalId` and `clientId` (both with `onDelete: "cascade"`). It can also optionally link to a `recurringScheduleId` if it's part of a recurring series. `startsAt` and `endsAt` define the appointment's duration.

The `status` column tracks the appointment's lifecycle ("pending_confirmation", "confirmed", "rejected", "completed", "cancelled", "no_show"). The `paymentStatus` tracks payment progress ("none", "authorized", "captured", "refunded"), and `stripePaymentIntentId` stores the Stripe identifier for payments.

Reminder flags (`reminderSent24h`, `reminderSent1h`) help manage automated notifications. An optional `notes` field allows for additional details. `createdAt` tracks the record's creation.

Several indexes are defined for efficient querying: on `professionalId`, `clientId`, `startsAt`, and `status`. A particularly important `uniqueIndex`, `appointments_pro_starts_at_active_uidx`, is defined on `professionalId` and `startsAt`. This index is filtered to only apply where `status` is *not* 'rejected' or 'cancelled', serving as a database-level defense against double-booking by preventing two active appointments from occupying the same slot for a professional.

## Messages

The `messages` table facilitates communication between professionals and clients. It has 9 columns.

Each message has a `uuid` `id` and is linked to a `professionalId` and `clientId` (both with `onDelete: "cascade"`). The `sender` column indicates who sent the message ("professional" or "client"). The `type` column specifies the message format ("text", "link", "pdf"), with "text" as the default. The `content` is the message body, and `fileUrl` is used for attachments like PDFs. `readAt` tracks when the message was viewed, and `createdAt` records its creation. An index on `professionalId` and `clientId` optimizes conversation retrieval.

## Follows

The `follows` table tracks when a client (identified by `userId`) follows a professional. It has 4 columns.

Each follow relationship has a `uuid` `id`. The `userId` (a `text` field) identifies the follower, and `professionalId` (with `onDelete: "cascade"`) identifies the professional being followed. `createdAt` records when the follow occurred. Indexes on `professionalId` and `userId` support efficient querying of followers and followed professionals.

## Reviews

The `reviews` table stores client feedback after a completed appointment. It has 7 columns.

Each review has a `uuid` `id` and is linked to a `professionalId`, `clientId`, and `appointmentId`. The `appointmentId` is unique and also has an `onDelete: "cascade"` rule, ensuring that a review is tied to a specific, existing appointment and is removed if the appointment is deleted. The `rating` is an integer (expected to be 1-5), and `comment` is an optional `text` field. `createdAt` tracks the review's submission. An index on `professionalId` allows for easy retrieval of all reviews for a given professional.

## Notifications

The `notifications` table provides a generic mechanism for sending alerts to users. It has 8 columns.

Each notification has a `uuid` `id`. `recipientId` (a `text` field, likely a Supabase user ID) and `recipientType` ("professional" or "client") identify who should receive the notification. The `type` column categorizes the notification (e.g., "booking_request", "reminder_24h", "new_message"). `title` and `body` provide the notification content. A `read` boolean (defaulting to `false`) tracks whether the notification has been seen. `createdAt` records the notification's creation. An index on `recipientId` helps retrieve all notifications for a specific user.

## Agent Metrics

The `agentMetrics` table is dedicated to storing telemetry data from the WhatsApp intake agent. It has 12 columns and is designed for best-effort insertion, meaning failures to write metrics should not impede the agent's primary function.

Each metric entry has a `uuid` `id`. `traceId` and `conversationPhone` help link metrics to specific conversations. `promptVersion` and `promptHash` track the AI agent's configuration. `totalCostUsd` and `totalCostBrl` (both `numeric` with specified precision and scale) record the monetary cost of the interaction. `totalLatencyMs` and `toolCallCount` provide performance insights. `providersUsed` is an `array` of `text` to list the AI providers engaged. The `outcome` column categorizes the result of the agent's turn (e.g., "booked", "cancelled", "searched", "info"). `createdAt` records when the metric was logged. Indexes on `traceId`, `createdAt`, and `outcome` facilitate analysis of agent performance and conversion.

## Design decisions

Several key design decisions are evident in the Odys database schema:

*   **UUID Primary Keys**: All tables use `uuid` for their primary keys, generated with `defaultRandom()`. This choice provides globally unique identifiers, which simplifies distributed system design and merging data from different sources, as there's no risk of ID collisions. It also avoids exposing sequential IDs that could be used to infer data volume or for enumeration attacks.
*   **`onDelete: "cascade"` for Relationships**: Many foreign key relationships, particularly those linking to `professionals.id` and `clients.id`, employ `onDelete: "cascade"`. This means that if a professional or client record is deleted, all associated records (e.g., `availability`, `clientNotes`, `appointments`, `messages`, `follows`, `reviews`) are automatically removed by the database. This simplifies application logic for cleanup and helps maintain referential integrity, but it requires careful consideration to prevent accidental data loss.
*   **`text` for "Enum-like" Fields**: Columns like `profession`, `plan`, `paymentType`, `serviceType`, `frequency`, `status`, `paymentStatus`, `sender`, `type` (messages), `recipientType`, `type` (notifications), and `outcome` are defined as `text` rather than using Drizzle's `pgEnum` or database-level `ENUM` types. This approach offers flexibility, allowing new values to be introduced without requiring schema migrations. The trade-off is that data integrity for these fields relies solely on application-level validation, as the database itself does not enforce the allowed set of values.
*   **External `userId` as `text`**: The `userId` in `professionals` and `clients`, and `recipientId` in `notifications`, are stored as `text` and do not have direct foreign key constraints within the Odys schema. This is a common pattern when integrating with external authentication providers (like Supabase), where the external system manages user identities. The `text` type accommodates various external ID formats, and referential integrity is typically managed at the application layer or by the external service itself.
*   **`timestamp` with `defaultNow()`**: Most tables include `createdAt` and `updatedAt` columns of type `timestamp` with `defaultNow()`. This is a standard practice for auditing and tracking the lifecycle of records, providing automatic timestamps for creation and allowing application logic to update `updatedAt` on modifications.
*   **Partial Unique Index for `appointments`**: The `appointments` table includes a `uniqueIndex` named `appointments_pro_starts_at_active_uidx` on `professionalId` and `startsAt`, with a `WHERE` clause filtering out appointments with `status` 'rejected' or 'cancelled'. This is a sophisticated database-level constraint designed as a "defense-in-depth" mechanism. While application logic typically handles double-booking prevention, this partial unique index ensures that even if two concurrent transactions attempt to book the same slot for a professional, the database will reject the second attempt, preventing data corruption.
*   **Precision for Financial and Geographic Data**: `agentMetrics` uses `numeric` with specific `precision` and `scale` for `totalCostUsd` and `totalCostBrl`, which is crucial for accurate financial calculations, avoiding floating-point inaccuracies. Similarly, `professionals` uses `doublePrecision` for `latitude` and `longitude`, providing sufficient accuracy for geographic coordinates.

## Potential improvements

1.  **Enforce Enum Values with `pgEnum` or `CHECK` Constraints**: Many `text` columns, such as `professionals.profession`, `professionals.plan`, `appointments.status`, `messages.type`, and `agentMetrics.outcome`, represent a fixed set of predefined values. While using `text` offers flexibility, it sacrifices database-level data integrity. Migrating these to Drizzle's `pgEnum` or adding `CHECK` constraints directly in the Drizzle schema (e.g., `text("status").notNull().check(inArray(['pending_confirmation', 'confirmed', 'rejected', 'completed', 'cancelled', 'no_show']))`) would ensure that only valid values are stored, reducing potential application bugs and improving data quality. This would apply to columns like `professionals.profession`, `professionals.plan`, `professionals.paymentType`, `professionals.serviceType`, `recurringSchedules.frequency`, `appointments.status`, `appointments.paymentStatus`, `messages.sender`, `messages.type`, `notifications.recipientType`, `notifications.type`, and `agentMetrics.outcome` in `src/lib/db/schema.ts`.
2.  **Automate `updatedAt` with Database Triggers**: The `updatedAt` columns in `professionals` and `clientNotes` currently rely on application logic to update their values. A more robust approach for auditing and data integrity is to implement database triggers that automatically update the `updatedAt` timestamp whenever a row is modified. This ensures that the timestamp is always accurate, regardless of whether the application explicitly sets it, and prevents accidental omissions. This would involve adding Drizzle-specific trigger definitions to the schema or managing them as separate migration scripts.
3.  **Refine `recurringSchedules` Day Representation**: The `recurringSchedules` table uses `dayOfWeek` and `secondDayOfWeek` as separate nullable integer columns to handle different frequencies. This design can become cumbersome if more complex recurrence patterns are introduced (e.g., monthly, specific dates). Consider consolidating these into a single `integer[]` array column for `daysOfWeek` or adopting a more standardized recurrence rule (e.g., iCalendar's RRULE format stored as `text`) to offer greater flexibility and simplify the logic for managing diverse recurring patterns. This would affect the `dayOfWeek` and `secondDayOfWeek` columns in `src/lib/db/schema.ts`.
