# Database Schema

The Odys application relies on a PostgreSQL database, with its schema defined using Drizzle ORM in `src/lib/db/schema.ts`. This file serves as the single source of truth for the database structure, outlining the relationships and constraints that govern how data is stored and retrieved. Understanding this schema is fundamental to comprehending the application's data model and its core functionalities, from managing professional profiles and client appointments to handling messages and tracking agent metrics.

## Overview

The Odys database schema comprises 11 distinct tables, each designed to manage a specific aspect of the platform's operations. At its heart are the `professionals` and `clients` tables, representing the two primary user types interacting with the system. These central entities are linked to various auxiliary tables that manage their schedules, communications, and interactions. For instance, `availability` defines when a professional can take appointments, while `appointments` tracks the actual bookings between professionals and clients. Communication is handled via `messages`, and feedback is captured in `reviews`. The schema also includes tables for managing recurring schedules, client notes, user follows, and a generic notification system. A specialized `agentMetrics` table provides telemetry for the platform's automated intake agent.

## Professionals

The `professionals` table is a cornerstone of the Odys application, storing comprehensive details about each service provider. With 32 columns, it's the largest table in the schema, reflecting the multifaceted information required for a professional's profile and operational settings. Each professional is uniquely identified by a `uuid` `id` and a `userId` (a `text` field likely referencing an external authentication system like Supabase). A `slug` column ensures a unique, human-readable URL for their public profile.

Beyond basic contact information like `name`, `phone`, and `email`, the table captures critical business logic: `profession` (e.g., "psychologist"), `sessionDuration`, and `sessionPrice`. It also defines the professional's `plan` ("free", "pro", "premium") and their preferred `paymentType` ("upfront", "percentage", "after"), along with `paymentPercentage` and details for `pixKeyType` and `pixKey`. Integration with Stripe is evident through `stripeCustomerId` and `stripeSubscriptionId` columns.

For professionals offering in-person services, location details such as `addressLine`, `neighborhood`, `city`, `state`, `postalCode`, `latitude`, and `longitude` are stored. The `serviceType` column ("in_person", "online", "both") indicates how they conduct sessions. Timestamps `createdAt` and `updatedAt` track the lifecycle of each professional's record, and `active` indicates their current status on the platform. The table includes indexes on `profession` and `city` to facilitate efficient searching and filtering of professionals.

## Availability

The `availability` table defines the time slots when a professional is generally available for appointments. It contains 5 columns, with each record specifying a `dayOfWeek` (0 for Sunday to 6 for Saturday), a `startTime`, and an `endTime`. This table is directly linked to the `professionals` table via `professionalId`, with an `onDelete: "cascade"` rule ensuring that a professional's availability records are automatically removed if their profile is deleted. An index on `professionalId` optimizes queries for a specific professional's schedule.

## Clients

The `clients` table stores information about individuals who book appointments with professionals. It has 8 columns, including a `uuid` `id` and a `professionalId` foreign key, also with `onDelete: "cascade"`. This means a client record is tied to a specific professional, and if that professional is removed, their associated client records are also deleted. The `userId` column is `text` and nullable, indicating that clients can book appointments without necessarily having a full user account on the platform, likely referencing an external authentication system if they do. Essential client details like `name`, `phone`, `email`, and `avatarUrl` are stored, along with a `createdAt` timestamp. Indexes on `professionalId` and `userId` support efficient client lookups.

## Client Notes

The `clientNotes` table provides a private space for professionals to record observations or important information about their clients. This table has 6 columns and is designed to be visible only to the professional who created the note. It links to both `professionals` and `clients` via `professionalId` and `clientId` respectively, both with `onDelete: "cascade"`. This ensures that notes are cleaned up if either the professional or the client record is deleted. The `content` column stores the actual note, and `createdAt` and `updatedAt` track its history.

## Recurring Schedules

For clients who require regular sessions, the `recurringSchedules` table manages these ongoing arrangements. This table, with 9 columns, links a `professionalId` and a `clientId` (both with `onDelete: "cascade"`) to define a recurring booking pattern. It specifies the `frequency` ("weekly", "biweekly", "twice_weekly"), the `dayOfWeek` (and `secondDayOfWeek` for twice-weekly schedules), and the `time` of the appointment. An `active` boolean flag allows professionals to temporarily pause or reactivate a recurring schedule, and `createdAt` records when the schedule was established.

## Appointments

The `appointments` table is central to the booking functionality, detailing each individual session between a professional and a client. It contains 13 columns, linking to `professionals` and `clients` with `onDelete: "cascade"`, and optionally to `recurringSchedules`. Key columns include `startsAt` and `endsAt` timestamps, defining the appointment's duration.

The `status` column tracks the appointment's lifecycle ("pending_confirmation", "confirmed", "rejected", "completed", "cancelled", "no_show"), while `paymentStatus` ("none", "authorized", "captured", "refunded") manages the financial aspect, including a `stripePaymentIntentId`. The `reminderSent24h` and `reminderSent1h` boolean flags help manage automated notifications. An important `uniqueIndex` named `appointments_pro_starts_at_active_uidx` is defined on `professionalId` and `startsAt`, filtered to exclude 'rejected' or 'cancelled' statuses. This index provides a database-level safeguard against double-booking, ensuring that a professional cannot have two active appointments at the exact same time.

## Messages

The `messages` table facilitates direct communication between professionals and clients within the platform. With 9 columns, each message is linked to a `professionalId` and a `clientId` (both with `onDelete: "cascade"`). It records the `sender` ("professional" or "client"), the `type` of message ("text", "link", "pdf"), the `content` of the message, and an optional `fileUrl` for attachments. A `readAt` timestamp indicates when the message was viewed, and `createdAt` marks its creation. An index on `professionalId` and `clientId` supports efficient retrieval of conversation history.

## Follows

The `follows` table tracks when a user expresses interest in a professional by "following" them. This table has 4 columns, linking a `userId` (a `text` field) to a `professionalId` (with `onDelete: "cascade"`). The `createdAt` timestamp records when the follow occurred. Indexes on both `professionalId` and `userId` allow for quick lookups of who a professional is followed by, and which professionals a user follows.

## Reviews

After an appointment, clients can provide feedback through the `reviews` table. This table, with 7 columns, captures a `rating` (1-5) and an optional `comment`. Each review is uniquely tied to an `appointmentId` (with `onDelete: "cascade"` and a `unique` constraint), ensuring that only one review can be submitted per appointment. It also links to `professionalId` and `clientId` (both with `onDelete: "cascade"`). A `createdAt` timestamp records when the review was submitted, and an index on `professionalId` helps aggregate reviews for a given professional.

## Notifications

The `notifications` table provides a generic mechanism for sending alerts and updates to users. It has 8 columns, storing a `recipientId` (a `text` field, likely a Supabase user ID) and `recipientType` ("professional" or "client"). The `type` column categorizes the notification (e.g., "booking_request", "reminder_24h"), while `title` and `body` provide the message content. A `read` boolean flag tracks whether the notification has been viewed, and `createdAt` records its generation time. An index on `recipientId` allows for efficient retrieval of notifications for a specific user.

## Agent Metrics

The `agentMetrics` table is dedicated to telemetry for the WhatsApp intake agent, capturing performance and outcome data for each conversation turn. With 12 columns, it records a `traceId` to link related agent interactions, the `conversationPhone` of the client, and details about the AI model used (`promptVersion`, `promptHash`). Financial metrics like `totalCostUsd` and `totalCostBrl` (using `numeric` types for precision) and performance metrics like `totalLatencyMs` and `toolCallCount` are stored. It also tracks `providersUsed` (as an array of `text`) and the `outcome` of the turn ("booked", "cancelled", "rescheduled", "searched", "info", "help", "reset", "other"). This data is crucial for monitoring the agent's effectiveness and optimizing its performance. Indexes on `traceId`, `createdAt`, and `outcome` facilitate analytical queries.

## Design decisions

The schema reflects several deliberate design choices:

*   **UUID Primary Keys**: Every table uses `uuid("id").primaryKey().defaultRandom()`. This approach generates unique identifiers at the application or database level, which is beneficial in distributed systems as it avoids contention issues common with sequential integer IDs and makes merging data from different sources simpler.
*   **External User IDs as `text`**: Columns like `professionals.userId`, `clients.userId`, `follows.userId`, and `notifications.recipientId` are defined as `text` rather than `uuid` or a foreign key to a local `users` table. This suggests an integration with an external authentication provider (like Supabase, as indicated by comments), where user IDs are managed externally. The trade-off is that database-level referential integrity cannot be enforced for these external IDs, relying instead on application logic.
*   **`onDelete: "cascade"` for Core Relationships**: Many foreign keys, particularly those linking to `professionals.id` and `clients.id`, are configured with `onDelete: "cascade"`. This simplifies data management by automatically cleaning up related records (e.g., a professional's availability, clients, appointments, messages, follows, and reviews) when the parent professional or client record is deleted. While convenient, this powerful feature requires careful handling at the application layer to prevent unintended data loss.
*   **Database-level Double-Booking Prevention**: The `appointments` table includes a `uniqueIndex("appointments_pro_starts_at_active_uidx")` on `professionalId` and `startsAt`, with a `WHERE` clause filtering out 'rejected' or 'cancelled' appointments. This is a robust defense-in-depth mechanism. Even if application-level checks or race conditions occur, the database will prevent two active appointments from being scheduled for the same professional at the exact same time, returning a `23505` error code.
*   **`text` for Enum-like Fields**: Many columns that represent a fixed set of choices (e.g., `professionals.profession`, `professionals.plan`, `appointments.status`, `messages.type`, `agentMetrics.outcome`) are defined as `text`. This offers flexibility, allowing new values to be added without requiring schema migrations. However, it shifts the responsibility for validating these values entirely to the application layer, as the database itself does not enforce the allowed set of values.
*   **`numeric` for Financial Data**: The `agentMetrics` table uses `numeric` types with specified precision and scale for `totalCostUsd` and `totalCostBrl`. This is a critical choice for financial data, as `numeric` types provide exact precision, avoiding the potential floating-point inaccuracies that can arise with `float` or `doublePrecision` types.

## Potential improvements

1.  **Introduce PostgreSQL `ENUM` types for categorical data**: Many `text` columns, such as `professionals.profession`, `professionals.plan`, `appointments.status`, `appointments.paymentStatus`, `messages.sender`, `messages.type`, `notifications.recipientType`, `notifications.type`, and `agentMetrics.outcome`, represent a finite set of predefined values. Converting these to PostgreSQL `ENUM` types would enforce data integrity at the database level, preventing invalid values from being inserted and making the schema more self-documenting. This would improve data quality and simplify application-level validation.
2.  **Add a composite unique index to `follows` table**: The `follows` table currently has indexes on `professionalId` and `userId` separately. To prevent a user from following the same professional multiple times, a composite unique index on `(userId, professionalId)` should be added to the `follows` table. This would enforce uniqueness at the database level, ensuring that each user-professional follow relationship is recorded only once.
3.  **Use PostgreSQL `TIME` type for time-only columns**: Columns like `availability.startTime`, `availability.endTime`, and `recurringSchedules.time` are currently stored as `text`. Using PostgreSQL's native `TIME` type would provide database-level validation for time formats, allow for easier time-based calculations and comparisons directly in SQL queries, and potentially reduce parsing overhead in the application.
4.  **Consider a `users` table for external `userId` references**: While `userId` columns (e.g., `professionals.userId`, `clients.userId`) are `text` due to external authentication, introducing a local `users` table that mirrors essential external user IDs could allow for database-level foreign key constraints. Alternatively, if a full `users` table is not desired, a PostgreSQL `DOMAIN` type could be created to at least enforce a consistent format for these `userId` values across tables. This would improve data consistency and make relationships more explicit within the database schema.
5.  **Add `updatedAt` to `recurringSchedules`**: The `recurringSchedules` table currently only has a `createdAt` timestamp. Adding an `updatedAt` column, similar to `professionals` and `clientNotes`, would provide valuable auditing information, allowing tracking of when recurring schedules are modified (e.g., when their `active` status changes or frequency is adjusted).
