# Database Schema

The Odys database schema, defined in `src/lib/db/schema.ts`, lays the foundation for managing interactions between professionals and their clients. It encompasses 11 distinct tables, meticulously designed to track professional profiles, client information, appointment schedules, communication, and system-level metrics. Understanding this schema is crucial for anyone looking to build upon or integrate with the Odys platform, as it dictates how data is stored, related, and accessed.

## Overview

The Odys database is structured around a central `professionals` table, which serves as the anchor for most other entities. Professionals offer various services, and their availability is managed in the `availability` table. Clients, who may or may not have a user account, are stored in the `clients` table and are linked to a specific professional. Professionals can maintain private `clientNotes` and establish `recurringSchedules` for their clients.

The core interaction of the platform revolves around `appointments`, which link professionals and clients for specific time slots. Communication between these parties is captured in the `messages` table, while `follows` tracks client interest in professionals. Post-appointment feedback is recorded in `reviews`. A general `notifications` table handles system alerts for both professionals and clients. Finally, the `agentMetrics` table provides crucial telemetry for the platform's automated intake agent, offering insights into its performance and interactions.

## Professionals

The `professionals` table is the cornerstone of the Odys application, holding comprehensive details for each service provider. With 32 columns, it's the largest table, reflecting the breadth of information required to manage a professional's profile and operations.

Each professional is uniquely identified by a `uuid` `id` and linked to an external authentication system via a `userId` of type `text`, which is marked as unique and not nullable. This `userId` is likely a reference to a Supabase authentication ID, allowing for seamless integration with the platform's user management. A human-readable `slug` is also provided, ensuring unique and friendly URLs for public professional pages.

Beyond basic contact information like `name`, `phone`, and `email` (which is nullable, offering flexibility), the table captures professional-specific details such as `profession` (e.g., "psychologist", "personal_trainer"), `bio`, and `avatarUrl`. Operational parameters like `sessionDuration` (defaulting to 50 minutes) and `sessionPrice` (defaulting to 0 cents) are stored as integers.

The table also manages the professional's subscription `plan` (defaulting to "free"), their preferred `paymentType` (defaulting to "upfront"), and `paymentPercentage`. For direct payments, `pixKeyType` and `pixKey` are available. Integration with Stripe is supported through `stripeCustomerId` and `stripeSubscriptionId`.

Location-based services are supported with `serviceType` (defaulting to "both" for online and in-person), and detailed address fields (`addressLine`, `neighborhood`, `city`, `state`, `postalCode`) along with `latitude` and `longitude` for geocoding. The `active` boolean column, defaulting to `true`, allows for toggling a professional's visibility. Standard `createdAt` and `updatedAt` timestamps track record lifecycle.

To optimize queries, indexes are defined on `profession` and `city`, facilitating efficient searching for professionals based on their specialty or location.

## Availability

The `availability` table defines the time slots when a professional is available for appointments. It contains 5 columns, linking directly to the `professionals` table.

Each entry has a `uuid` `id` and a `professionalId` which is a foreign key referencing `professionals.id`. The `onDelete: "cascade"` rule ensures that if a professional's record is removed, all their associated availability entries are automatically deleted, maintaining data consistency.

Availability is specified by `dayOfWeek` (an integer from 0 for Sunday to 6 for Saturday), `startTime`, and `endTime` (both stored as `text` in "HH:MM" format). An index on `professionalId` allows for quick retrieval of a professional's schedule.

## Clients

The `clients` table stores information about individuals who book appointments with professionals. It has 8 columns and is linked to the `professionals` table.

Similar to professionals, clients have a `uuid` `id`. A `userId` of type `text` is present but nullable, indicating that clients can book appointments without necessarily having a full Supabase user account. Each client is associated with a `professionalId`, a foreign key to `professionals.id` with `onDelete: "cascade"`, meaning a professional's deletion will also remove their clients.

Essential client details include `name`, `phone`, and an optional `email` and `avatarUrl`. The `createdAt` timestamp tracks when the client record was created. Indexes on `professionalId` and `userId` enable efficient lookups for clients associated with a specific professional or a Supabase user.

## Client Notes

The `clientNotes` table provides a private space for professionals to record observations and information about their clients. This table has 6 columns.

Each note has a `uuid` `id` and is linked to both a `professionalId` and a `clientId`, both with `onDelete: "cascade"` foreign key constraints. This ensures that notes are automatically removed if either the professional or the client they pertain to is deleted. The actual note content is stored in the `content` column as `text`. `createdAt` and `updatedAt` timestamps track the note's lifecycle.

## Recurring Schedules

The `recurringSchedules` table manages appointments that repeat on a regular basis, such as weekly therapy sessions. It has 9 columns.

Each recurring schedule has a `uuid` `id` and is linked to a `professionalId` and a `clientId`, both with `onDelete: "cascade"` foreign key constraints. The `frequency` column (e.g., "weekly", "biweekly", "twice_weekly") defines how often the appointment occurs. `dayOfWeek` and `secondDayOfWeek` (both nullable integers) specify the days, while `time` (text, e.g., "14:00") indicates the time of day. An `active` boolean, defaulting to `true`, allows for enabling or disabling a recurring schedule. The `createdAt` timestamp records when the schedule was established.

## Appointments

The `appointments` table is central to the booking functionality, detailing every scheduled interaction between a professional and a client. It comprises 13 columns.

Each appointment has a `uuid` `id` and is linked to a `professionalId` and a `clientId`, both with `onDelete: "cascade"` foreign key constraints. It can also optionally be linked to a `recurringScheduleId`, which does not cascade on delete, allowing individual appointments to persist even if their recurring schedule is removed.

The `startsAt` and `endsAt` timestamps define the appointment's duration. The `status` column, defaulting to "pending_confirmation", tracks the appointment's lifecycle through states like "confirmed", "rejected", "completed", "cancelled", or "no_show". Similarly, `paymentStatus` (defaulting to "none") tracks payment states such as "authorized", "captured", or "refunded". A `stripePaymentIntentId` is stored for Stripe integration.

The table also includes `reminderSent24h` and `reminderSent1h` booleans, defaulting to `false`, to track whether automated reminders have been dispatched. An optional `notes` field allows for additional details. The `createdAt` timestamp records when the appointment was created.

Several indexes are defined for efficient querying: on `professionalId`, `clientId`, `startsAt`, and `status`. A particularly important design choice is the `appointments_pro_starts_at_active_uidx` unique index, which combines `professionalId` and `startsAt`. This index is filtered to apply only where `status` is not "rejected" or "cancelled", serving as a database-level defense against double-booking by preventing two active appointments from occupying the same slot for a professional.

## Messages

The `messages` table facilitates communication between professionals and clients within the platform. It has 9 columns.

Each message has a `uuid` `id` and is linked to both a `professionalId` and a `clientId`, with `onDelete: "cascade"` foreign key constraints. The `sender` column (e.g., "professional" or "client") identifies who sent the message. The `type` column, defaulting to "text", can also indicate "link" or "pdf". The message content is stored in the `content` column, and a `fileUrl` is available for attachments like PDFs. A `readAt` timestamp tracks when the message was viewed, and `createdAt` records its creation time. An index on `professionalId` and `clientId` allows for efficient retrieval of conversation history.

## Follows

The `follows` table tracks when a client expresses interest in a professional by "following" them. It has 4 columns.

Each follow record has a `uuid` `id`, a `userId` (text, not nullable, likely a Supabase ID), and a `professionalId` (foreign key to `professionals.id` with `onDelete: "cascade"`). The `createdAt` timestamp records when the follow occurred. Indexes on `professionalId` and `userId` enable quick lookups of who is following whom.

## Reviews

The `reviews` table stores feedback provided by clients after an appointment. It has 7 columns.

Each review has a `uuid` `id` and is linked to a `professionalId`, a `clientId`, and an `appointmentId`, all with `onDelete: "cascade"` foreign key constraints. The `appointmentId` is also marked as unique, ensuring that only one review can be submitted per appointment. The `rating` (an integer from 1 to 5) and an optional `comment` capture the client's feedback. The `createdAt` timestamp records when the review was submitted. An index on `professionalId` allows for aggregating reviews for a specific professional.

## Notifications

The `notifications` table provides a generic mechanism for sending alerts and updates to users within the Odys platform. It has 8 columns.

Each notification has a `uuid` `id`. The `recipientId` (text, not nullable, likely a Supabase user ID) and `recipientType` (e.g., "professional" or "client") identify who should receive the notification. The `type` column categorizes the notification (e.g., "booking_request", "reminder_24h", "new_message"). A `title` and `body` provide the content of the notification. The `read` boolean, defaulting to `false`, tracks whether the notification has been viewed. The `createdAt` timestamp records when the notification was generated. An index on `recipientId` allows for efficient retrieval of a user's notifications.

## Agent Metrics

The `agentMetrics` table is dedicated to storing telemetry data for the WhatsApp intake agent, providing insights into its operational performance and user interactions. It contains 12 columns.

Each metric entry has a `uuid` `id` and a `traceId` to link related agent interactions. `conversationPhone` identifies the client's phone number. `promptVersion` and `promptHash` track the specific AI prompt used, which is crucial for A/B testing and debugging agent behavior.

Performance and cost metrics include `totalCostUsd` (numeric with precision 10, scale 6), `totalCostBrl` (numeric with precision 10, scale 4), and `totalLatencyMs` (integer). `toolCallCount` tracks how many external tools the agent invoked. `providersUsed` is stored as a `text` array, listing the AI providers engaged during the interaction.

The `outcome` column captures the resolution of the agent's turn (e.g., "booked", "cancelled", "searched", "help"), which is vital for measuring conversion and agent effectiveness. The `createdAt` timestamp records when the metric was logged. Indexes on `traceId`, `createdAt`, and `outcome` facilitate analysis of agent performance over time and by interaction type.

## Design decisions

Several key design decisions shape the Odys database schema:

*   **UUID Primary Keys**: All tables use `uuid` for their primary keys. This choice is common in distributed systems, as UUIDs can be generated independently without coordination, reducing contention and simplifying merges. They also prevent information leakage that might occur with sequential integer IDs.
*   **External User IDs**: The `userId` columns in `professionals`, `clients`, and `follows`, as well as `recipientId` in `notifications`, are defined as `text` rather than UUIDs or integers with foreign key constraints. This design explicitly accommodates an external authentication system, likely Supabase, where user IDs are managed outside the core application database. This decouples user authentication from the application's domain data, offering flexibility but shifting referential integrity enforcement for these IDs to the application layer.
*   **`onDelete: "cascade"` for Related Entities**: Many foreign key relationships, particularly those stemming from `professionals` (e.g., `availability`, `clients`, `clientNotes`, `recurringSchedules`, `messages`, `follows`, `reviews`), employ `onDelete: "cascade"`. This ensures that when a professional's record is deleted, all associated data (their availability, clients, notes, etc.) is automatically removed. This simplifies application logic for deletion and helps maintain data consistency, preventing orphaned records.
*   **`text` for Time Components**: Columns like `availability.startTime`, `availability.endTime`, and `recurringSchedules.time` are stored as `text` (e.g., "09:00"). While `timestamp` types are used for full date-time values, using `text` for just the time component simplifies storage and retrieval when only the time of day is relevant, avoiding the complexities of date components or timezones for these specific fields.
*   **Partial Unique Index for Appointments**: The `appointments_pro_starts_at_active_uidx` on `appointments` is a crucial defense-in-depth mechanism. By creating a unique index on `professionalId` and `startsAt` *only for appointments not in 'rejected' or 'cancelled' status*, the database itself prevents concurrent attempts to book the same time slot for a professional. This complements application-level checks and transaction management, providing a robust guarantee against double-booking.
*   **`numeric` for Financial Data**: The `agentMetrics` table uses `numeric` types (`totalCostUsd` with precision 10, scale 6; `totalCostBrl` with precision 10, scale 4) for storing monetary values. This is a standard practice to ensure exact precision for financial calculations, avoiding the floating-point inaccuracies that can arise with `doublePrecision` types.
*   **`text` for Enumerated Values**: Many columns that represent a fixed set of choices (e.g., `professionals.plan`, `appointments.status`, `messages.sender`, `agentMetrics.outcome`) are defined as `text`. This offers flexibility to add new values without schema migrations, but it relies on application-level validation to ensure data integrity.

## Potential improvements

1.  **Introduce `pgEnum` for Categorical `text` Columns**: Many columns like `professionals.profession`, `professionals.plan`, `professionals.paymentType`, `professionals.pixKeyType`, `professionals.serviceType`, `appointments.status`, `appointments.paymentStatus`, `recurringSchedules.frequency`, `messages.sender`, `messages.type`, `notifications.recipientType`, `notifications.type`, and `agentMetrics.outcome` currently use `text` types. While flexible, this approach lacks database-level validation for allowed values. Converting these to Drizzle's `pgEnum` would enforce type safety at the database level, preventing invalid data from being inserted and making the schema more self-documenting. For example, `professionals.plan` could be `pgEnum("plan_enum", ["free", "pro", "premium"])`.
2.  **Strengthen `userId` References**: The `userId` columns in `professionals`, `clients`, and `follows`, and `recipientId` in `notifications`, are `text` columns without explicit foreign key constraints. This implies reliance on an external authentication system (like Supabase). If Odys were to ever manage users internally, or if a robust foreign key mechanism could be established with the external system, converting these to a proper foreign key type (e.g., `uuid` if Supabase IDs are UUIDs) and adding a `references` constraint would provide stronger referential integrity and prevent orphaned records if external user accounts are deleted.
3.  **Explicit Timezone Handling for Timestamps**: All `timestamp` columns (e.g., `appointments.startsAt`, `appointments.endsAt`, `createdAt`, `updatedAt`) are defined without explicit timezone information. By default, Drizzle's `timestamp` maps to PostgreSQL's `timestamp without time zone`. For an application that might operate across different timezones or needs to precisely track event times globally, it would be beneficial to explicitly use `timestamp with time zone` and store all times in UTC, converting to local time at the application layer. This prevents ambiguity and simplifies time-based calculations.
4.  **Normalize `agentMetrics.providersUsed`**: The `providersUsed` column in `agentMetrics` is stored as a `text().array()`. While convenient for simple storage, querying for metrics related to a specific provider (e.g., "find all metrics where 'OpenAI' was used") can be less efficient. If the set of providers is finite and grows slowly, a more normalized approach could involve a separate `providers` table and a many-to-many join table (`agentMetricProviders`) to link metrics to providers. This would improve query performance and data integrity for provider-specific analysis.
5.  **Consider `professionals.email` as `notNull`**: The `email` column in the `professionals` table is nullable. While `userId` serves as the primary link to an external auth system, an email address is often a fundamental piece of contact information and a common identifier for professionals. Making it `notNull` would ensure that every professional has a primary email for communication and account recovery, potentially simplifying features that rely on email. If some professionals genuinely do not have an email, this would be a trade-off against that flexibility.
