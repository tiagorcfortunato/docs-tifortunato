# Shared Drizzle Schema

The Odys application architecture relies on a shared database schema to maintain data consistency across its various services. This document delves into how the Drizzle ORM schema is defined and consumed, particularly focusing on its use within the `mcp-server` component, and the underlying design decisions and potential areas for refinement.

## Overview

The core database schema for Odys is centrally defined in `src/lib/db/schema.ts`. This single file acts as the authoritative source for all database table definitions, leveraging Drizzle ORM to provide a type-safe and declarative way to describe the PostgreSQL database structure. The schema encompasses 11 distinct tables, including `professionals`, `clients`, `appointments`, and `agentMetrics`, which collectively manage the application's core entities and operational data.

The `mcp-server` service, responsible for various backend operations, interacts with this database. To do so, it imports the shared schema directly from its canonical location. This is achieved through a relative import statement in `mcp-server/src/db.ts`, which then initializes the Drizzle client with the complete schema. For TypeScript to correctly resolve this import, especially since the schema file resides outside the `mcp-server/src` directory, the `mcp-server/tsconfig.json` explicitly includes the path to the shared schema.

## Schema Definition

The `src/lib/db/schema.ts` file is a comprehensive declaration of the Odys database. It uses Drizzle ORM's `pgTable` function to define each table, specifying column names, types, nullability, uniqueness, primary key status, and default values.

For instance, the `professionals` table, central to the application, is defined with 32 columns. It includes an `id` column of type `uuid` serving as the primary key, automatically generated with `defaultRandom()`. A `userId` column, typed as `text`, is marked as `notNull` and `unique`, likely linking to an external authentication system like Supabase. Other critical columns include `name`, `slug` (a unique identifier for public profile URLs), `phone`, `email`, and `profession`. The table also tracks financial details like `sessionDuration` and `sessionPrice`, payment configurations (`plan`, `paymentType`, `pixKeyType`, `stripeCustomerId`), and geographical information (`addressLine`, `latitude`, `longitude`) for in-person services. Timestamps `createdAt` and `updatedAt` are automatically managed with `defaultNow()`.

Relationships between tables are established using Drizzle's `references` function. For example, the `availability` table, which stores a professional's working hours, includes a `professionalId` column that references `professionals.id`. Crucially, many of these foreign key relationships, such as those from `availability`, `clients`, `clientNotes`, `recurringSchedules`, `appointments`, `messages`, `follows`, and `reviews` to `professionals.id` or `clients.id`, are configured with `onDelete: "cascade"`. This design choice simplifies data management by automatically removing dependent records when a parent record is deleted.

A notable design detail is found in the `appointments` table. Beyond standard indexing on `professionalId`, `clientId`, `startsAt`, and `status`, it features a partial unique index named `appointments_pro_starts_at_active_uidx`. This index enforces uniqueness on the combination of `professionalId` and `startsAt` only for appointments whose `status` is not `'rejected'` or `'cancelled'`. This is a defense-in-depth mechanism to prevent double-booking at the database level, complementing application-side checks.

The `agentMetrics` table captures telemetry for the WhatsApp intake agent, recording details like `traceId`, `conversationPhone`, `promptVersion`, `promptHash`, `totalCostUsd`, `totalLatencyMs`, and the `outcome` of each interaction. This data is vital for monitoring the performance and effectiveness of the AI agent.

## Schema Consumption in `mcp-server`

The `mcp-server` service, located in the `mcp-server` directory, needs access to this shared schema to perform database operations. The `mcp-server/src/db.ts` file is responsible for establishing the database connection and initializing Drizzle.

It begins by importing the schema using a relative path: `import * as schema from "../../src/lib/db/schema.js"`. This path indicates that the schema file is two directories up from `mcp-server/src` and then into `src/lib/db`. The `.js` extension is used in the import path, reflecting the ES module resolution behavior in Node.js environments where TypeScript files are compiled to JavaScript.

Before connecting to the database, `mcp-server/src/db.ts` loads environment variables using `dotenv`, specifically looking for `.env.local` and `.env` files relative to the repository root. It then checks for the presence of `DATABASE_URL`, exiting with an error if it's not defined. The `postgres` client is initialized with this URL, and then `drizzle` is configured with the client and the imported `schema` object. Both the `db` instance and the `schema` object are exported for use throughout the `mcp-server` codebase.

## TypeScript Configuration

For TypeScript to correctly understand and compile the `mcp-server` project, especially when importing files from outside its immediate source directory, the `mcp-server/tsconfig.json` file plays a crucial role.

The `include` array within this `tsconfig.json` explicitly lists `../src/lib/db/schema.ts`. This inclusion tells the TypeScript compiler to process the shared schema file as part of the `mcp-server` project's compilation context. Without this explicit inclusion, TypeScript might fail to resolve the relative import in `mcp-server/src/db.ts`, leading to compilation errors. This setup is a common pattern in monorepos to share code between distinct TypeScript projects without resorting to more complex package management solutions.

## Design Decisions

The current structure reflects several deliberate design choices:

*   **Centralized Schema Definition**: By defining all 11 tables in a single `src/lib/db/schema.ts` file, the project ensures a single source of truth for the database structure. This minimizes the risk of schema drift and promotes consistency across all services that interact with the database.
*   **Monorepo-Friendly Sharing**: The use of relative imports and explicit `tsconfig.json` `include` directives is a pragmatic approach for sharing code within a monorepo. It avoids the overhead of publishing internal packages while still providing type safety and code reuse.
*   **Drizzle ORM for Type Safety**: Drizzle ORM was chosen for its ability to provide end-to-end type safety, from schema definition to query construction. This reduces runtime errors and improves developer experience by catching database-related issues at compile time.
*   **UUID Primary Keys**: Using `uuid` for primary keys (`id` columns) ensures global uniqueness, which is beneficial in distributed systems and simplifies merging data from different sources if needed. The `defaultRandom()` function automates this generation.
*   **Cascading Deletes**: The widespread use of `onDelete: "cascade"` for foreign key relationships simplifies application logic by delegating the cleanup of dependent records to the database. This is particularly useful for entities like `clients` and `appointments` that are tightly coupled to a `professional`.
*   **Database-Level Double-Booking Prevention**: The `appointments_pro_starts_at_active_uidx` partial unique index is a robust measure to prevent concurrent attempts to book the same slot. By filtering on `status NOT IN ('rejected', 'cancelled')`, it allows re-booking of slots that were previously occupied but are no longer active.

## Potential Improvements

While the current setup is functional, several areas could be considered for further refinement:

*   **Schema Modularity**: The `src/lib/db/schema.ts` file currently defines all 11 tables. As the application grows, this single file could become quite large and challenging to navigate. Splitting the schema definition into multiple, domain-specific files (e.g., `professionals.ts`, `appointments.ts`, `clients.ts`) and then re-exporting them from an `index.ts` within `src/lib/db` would significantly improve modularity and readability.
*   **Enhanced Type Safety for Enum-like Columns**: Many `text` columns, such as `professionals.plan`, `professionals.paymentType`, `appointments.status`, `messages.sender`, `notifications.recipientType`, and `agentMetrics.outcome`, represent a fixed set of predefined values. These could be defined using Drizzle's `pgEnum` feature. This would enforce type safety at both the database and application levels, preventing the insertion of invalid string values and providing better autocompletion in the codebase.
*   **Centralized Environment Variable Loading**: The `dotenv` configuration in `mcp-server/src/db.ts` is specific to this service. For a monorepo with multiple services, a more centralized or shared utility for loading environment variables could be beneficial. This would ensure consistent loading logic, reduce boilerplate, and simplify configuration management across the entire Odys application.
*   **Referential Integrity for `notifications.recipientId`**: The `notifications` table uses `recipientId` (a `text` column) and `recipientType` (a `text` column indicating 'professional' or 'client') to identify the notification target. This design relies on application logic to ensure `recipientId` correctly maps to either `professionals.userId` or `clients.userId`. Introducing a more explicit foreign key relationship, possibly through a polymorphic association pattern or by creating separate notification tables for each recipient type, could enforce referential integrity at the database level, reducing potential data inconsistencies.
