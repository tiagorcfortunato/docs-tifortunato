# Shared Drizzle Schema

The core of Odys's data model is defined in a single Drizzle ORM schema file, `src/lib/db/schema.ts`. This file serves as the authoritative source for all database table definitions, ensuring consistency and type safety across different parts of the application, including the `mcp-server` component. By centralizing the schema, the development team maintains a unified view of the database structure, simplifying migrations and feature development.

## Overview

The application's database schema is comprehensively defined within `src/lib/db/schema.ts`, encompassing a total of 11 tables. This shared definition is then consumed by various services, notably the `mcp-server`, which relies on it to interact with the PostgreSQL database. The `mcp-server/src/db.ts` file is responsible for establishing the database connection and initializing Drizzle with this shared schema. To ensure proper TypeScript compilation and type inference within `mcp-server`, its `tsconfig.json` explicitly includes the schema file, bridging the module boundary created by the relative import.

### Schema Definition in `src/lib/db/schema.ts`

The `src/lib/db/schema.ts` file uses Drizzle ORM's `pgTable` function to define each table and its columns. This approach provides a declarative way to represent the database structure directly in TypeScript.

The `professionals` table, for instance, is a central entity, featuring 32 columns. It includes essential details such as `id` (a UUID primary key with a default random value), a unique `userId` for integration with authentication systems, and a unique `slug` for public profile URLs. Business-specific fields like `sessionDuration`, `sessionPrice`, `plan`, and `paymentType` are also defined, along with geographical information like `latitude` and `longitude` for location-based services. Several columns, such as `sessionDuration`, `sessionPrice`, `plan`, `paymentType`, `autoConfirm`, `serviceType`, `active`, `createdAt`, and `updatedAt`, are configured with default values, streamlining data insertion.

Relationships between tables are established using Drizzle's `references` function. For example, the `availability`, `clients`, `clientNotes`, `recurringSchedules`, `appointments`, `messages`, `follows`, and `reviews` tables all include a `professionalId` column that references `professionals.id`. Many of these foreign key relationships are configured with `onDelete: "cascade"`, meaning that if a professional record is deleted, all associated records in these dependent tables will also be automatically removed by the database.

The `appointments` table, with its 13 columns, manages the scheduling of sessions. It tracks `startsAt` and `endsAt` timestamps, along with `status` and `paymentStatus` fields, both of which have default values. A notable feature is the `uniqueIndex("appointments_pro_starts_at_active_uidx")`, which is a partial unique index on `professionalId` and `startsAt`. This index includes a `WHERE` clause filtering for appointments where `status` is not `'rejected'` or `'cancelled'`, providing a database-level defense against double-booking for active appointments.

For telemetry and monitoring of the AI agent, the `agentMetrics` table captures 12 columns of data per conversation turn. This includes `traceId`, `conversationPhone`, `promptVersion`, `promptHash`, and `outcome`. It also tracks `totalCostUsd` and `totalCostBrl` using `numeric` types with specified precision and scale, and `providersUsed` as a `text().array()` column, allowing for multiple providers to be recorded for a single turn.

The `notifications` table, comprising 8 columns, is designed to deliver various alerts to users. It uses generic `recipientId` and `recipientType` fields, allowing notifications to be sent to either professionals or clients without requiring a direct foreign key to a specific user table.

### Database Connection in `mcp-server/src/db.ts`

The `mcp-server/src/db.ts` file is responsible for initializing the Drizzle ORM instance. It begins by loading environment variables, first from `.env.local` (with `quiet: true` to suppress errors if not found) and then from `.env` (without overriding existing variables). This ensures that the `DATABASE_URL` is available. If `DATABASE_URL` is not set, the process exits, preventing database connection failures.

The file then imports the shared schema using a relative path: `import * as schema from "../../src/lib/db/schema.js"`. This import statement is critical for bringing the table definitions into the `mcp-server` context. A `postgres-js` client is created using the `DATABASE_URL`, and this client is then passed to Drizzle along with the imported `schema` object to create the `db` instance, which is subsequently exported for use throughout the `mcp-server`.

### TypeScript Configuration in `mcp-server/tsconfig.json`

To enable TypeScript to correctly resolve and type-check the shared schema, the `mcp-server/tsconfig.json` file includes a specific entry in its `include` array: `"../src/lib/db/schema.ts"`. This explicit inclusion is necessary because the schema file resides outside the default `src` directory of the `mcp-server` package. Without this configuration, TypeScript might not recognize the types defined in `src/lib/db/schema.ts`, leading to compilation errors or a loss of type safety when `mcp-server/src/db.ts` attempts to import and use the schema.

## Design decisions

The architecture of sharing the Drizzle schema across different parts of the Odys application, particularly with `mcp-server`, reflects several deliberate design choices:

*   **Single Source of Truth for Schema**: By defining all 11 tables in `src/lib/db/schema.ts`, the project establishes a single, canonical representation of its database structure. This decision minimizes the risk of schema drift, where different services might operate on slightly varied understandings of the database. It simplifies database migrations, as changes only need to be applied and validated in one place.
*   **Relative Import for Monorepo Structure**: The use of a relative import path, `../../src/lib/db/schema.js`, in `mcp-server/src/db.ts` indicates a monorepo setup. This allows `mcp-server` to directly consume code from the main application's `src` directory without needing to publish `src/lib/db/schema.ts` as a separate package. This reduces overhead in package management and deployment, making it easier to share common utilities and definitions.
*   **Explicit `tsconfig.json` Inclusion**: The decision to add `"../src/lib/db/schema.ts"` to `mcp-server/tsconfig.json`'s `include` array is a pragmatic one. While relative imports work at runtime, TypeScript's compiler needs to be explicitly told to process files outside its immediate project root for type checking. This ensures that `mcp-server` benefits from the full type safety provided by Drizzle and TypeScript when interacting with the database.
*   **`onDelete: "cascade"` for Referential Integrity**: The widespread use of `onDelete: "cascade"` on foreign keys (e.g., `availability.professionalId`, `clients.professionalId`, `appointments.clientId`) simplifies data management. When a parent record, such as a professional, is deleted, all associated child records are automatically removed by the database. This choice trades explicit application-level cleanup logic for database-enforced referential integrity, which can be efficient but requires careful consideration to prevent unintended data loss.
*   **Partial Unique Index for Concurrency Control**: The `uniqueIndex("appointments_pro_starts_at_active_uidx")` on the `appointments` table, with its `WHERE` clause, is a sophisticated design choice. It provides a database-level guarantee against double-booking for active appointments. This acts as a defense-in-depth mechanism, complementing application-level checks and serializable transactions, by ensuring that even in highly concurrent scenarios, the database will reject attempts to book the same slot for the same professional if the existing appointment is not yet rejected or cancelled.

## Potential improvements

While the current schema sharing mechanism is functional, several areas could be considered for further refinement:

1.  **Centralize Environment Variable Loading**: The `mcp-server/src/db.ts` file currently includes logic for loading `.env.local` and `.env` files. This pattern is often duplicated across different services or entry points. A more centralized approach, perhaps a dedicated utility function or a configuration module, could abstract this logic. This would reduce boilerplate and ensure consistent environment variable loading behavior across the entire Odys codebase, making it easier to manage and update.
2.  **Introduce `pgEnum` for Type Safety and Database Constraints**: Many `text` columns in the schema represent a finite set of values, such as `professionals.plan` (`"free" | "pro" | "premium"`), `appointments.status` (`"pending_confirmation" | "confirmed" | "rejected" | "completed" | "cancelled" | "no_show"`), `messages.type` (`"text" | "link" | "pdf"`), and `agentMetrics.outcome`. Drizzle's `pgEnum` feature allows defining these as PostgreSQL enum types. This would provide stronger type safety at the TypeScript level and enforce valid values directly within the database, preventing invalid data from being inserted.
3.  **Refine `notifications` Recipient Handling**: The `notifications` table uses generic `recipientId` (text) and `recipientType` (text) columns. While flexible, this approach lacks database-enforced referential integrity. If `recipientId` always refers to either `professionals.userId` or `clients.userId`, consider a more structured approach. This could involve creating a dedicated `users` table that `professionals` and `clients` link to, and then having `notifications.recipientId` reference `users.id`. Alternatively, if a polymorphic relationship is truly needed, ensure application-level logic consistently validates these references.
4.  **Schema Validation with Zod**: While Drizzle provides type safety for database interactions, incoming API requests or data from external sources might not conform to the schema. Integrating a validation library like Zod, which Drizzle often pairs with, could provide runtime validation for data before it hits the database. This would involve creating Zod schemas derived from the Drizzle table definitions (e.g., `createInsertSchema(professionals)`), which could then be used to validate inputs to API routes like `/api/onboarding` or `/api/booking`.
