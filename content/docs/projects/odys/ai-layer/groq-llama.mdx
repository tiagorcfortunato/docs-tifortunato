Odys integrates artificial intelligence to enhance user experience for both clients seeking professionals and professionals managing their practice. This document explores the architectural choices behind the AI layer, focusing on the selection of Groq and Llama 3.3 70B, and the two-pass tool-calling pattern that underpins its functionality. These decisions aim to balance performance, cost-efficiency, and the ability to interact with the platform's data and services.

## Overview

The AI layer in Odys is composed of two primary agents, each serving a distinct purpose:

1.  **WhatsApp Concierge (`src/lib/ai-intake.ts`)**: This agent acts as a marketplace-wide assistant, helping clients discover professionals, browse schedules, and book appointments directly through WhatsApp. It operates with a broad understanding of the Odys ecosystem, capable of searching across all `professionals` in the database.
2.  **Professional Assistant (`src/app/api/ai/chat/route.ts`)**: Designed for professionals, this agent provides insights into their practice, such as appointment statistics, client no-show rates, and upcoming schedules. It interacts with a professional's specific data, drawing from tables like `appointments` and `clients`.

Both agents share a common underlying strategy for interacting with large language models (LLMs) and executing tools, leveraging a two-pass tool-calling pattern and a flexible provider chain.

## LLM Provider Strategy: Groq and Llama 3.3 70B

Odys employs a strategic combination of LLM providers, primarily utilizing Groq's inference engine with models like Llama 3.3 70B. This choice is driven by the need for rapid response times, especially critical for conversational interfaces like the WhatsApp Concierge, while maintaining high-quality reasoning.

The system abstracts LLM interactions through the `chatWithFallback` utility from `@/lib/llm`. This abstraction allows Odys to define a provider chain (e.g., Groq → Cerebras → Gemini), providing resilience and flexibility. If the primary provider (Groq) experiences issues or rate limits, the system can gracefully fall back to alternative providers, ensuring continuous service availability. This approach also enables dynamic cost optimization, potentially routing requests to cheaper models for less complex tasks or during off-peak hours, though the current implementation focuses on a sequential fallback.

## The Two-Pass Tool-Calling Pattern

A core design pattern across both AI agents is the "two-pass" approach for tool execution. This pattern enhances the reliability and control over how LLMs interact with external functions and data.

1.  **First Pass: Tool Request**: The LLM receives the user's query and a list of available `TOOLS`. Its primary task in this pass is to determine if any tool is necessary to fulfill the request. If a tool is identified, the LLM generates a `tool_calls` object, specifying the tool's `name` and `parameters`. Crucially, it does *not* generate a final user-facing response at this stage.
2.  **Second Pass: Final Response with Tool Results**: If the first pass resulted in a tool call, the application executes the requested tool(s) and captures their output. This output, along with the original messages and the LLM's tool call, is then sent back to the LLM as part of an extended conversation history. In this second pass, the LLM's role is to synthesize the tool results into a coherent, natural language response for the user.

This two-pass pattern offers several advantages:
*   **Improved Reliability**: It separates the decision-making (which tool to call) from the response generation, reducing the chance of the LLM hallucinating tool outputs or misinterpreting complex results.
*   **Enhanced Control**: The application maintains control over tool execution, allowing for pre- and post-processing, error handling, and logging (e.g., via `AgentLogger` in `ai-intake.ts`).
*   **Cost Efficiency**: By only performing the second LLM call when a tool is actually executed, it can save tokens compared to approaches where the LLM might attempt to generate a response and tool call simultaneously.

## WhatsApp Concierge (`src/lib/ai-intake.ts`)

The WhatsApp Concierge is a sophisticated agent designed to guide clients through the process of finding and booking appointments with professionals. It manages conversation state, moving from discovery to focused interaction and allowing for resets.

Its toolset is extensive, reflecting its broad responsibilities:
*   `search_professionals`: Queries the `professionals` table, filtering by `profession`, `city`, `name`, and `service_type`. It uses `resolveProfessionAlias` to handle Portuguese profession names and `getProStats` to enrich results with `avg_rating`, `review_count`, and `completed_count`. For location-based searches, it can use `geocodeCity` and `findNearestProfessionals` to suggest alternatives if no local matches are found.
*   `list_professions`: Dynamically lists only those professions from the `PROFESSIONS` constant that have at least one active professional registered, preventing dead-end searches.
*   `select_professional`: Transitions the conversation state to focus on a specific professional.
*   `get_professional_info`: Retrieves detailed information about a professional, including `bio`, `address`, `schedule` (from the `availability` table), `avg_rating`, `review_count`, `completed_count`, `payment_policy`, and `recent_reviews` (from the `reviews` and `clients` tables).
*   `get_available_slots`: Computes real-time availability for a given professional and date, considering their `availability` rules and existing `appointments`. It also proactively suggests alternative dates if the requested date has no slots.
*   `book_appointment`: Orchestrates the booking process, creating a new entry in the `appointments` table. It handles client creation (if new), checks for conflicts using a Drizzle `transaction` with `serializable` isolation, and dispatches `notifications` via WhatsApp and email using `sendWhatsApp`, `msgBookingRequest`, `msgBookingConfirmed`, `msgBookingConfirmedReceipt`, `sendBookingRequestEmailToProfessional`, and `sendBookingConfirmedEmailToClient`. It also generates `paymentInstructions` using `buildPaymentPolicy` and `buildPixPayload` if applicable.
*   `list_my_appointments`, `cancel_appointment`, `reschedule_appointment`: Allow clients to manage their existing bookings.

The agent uses specific timezone helpers like `saoPauloDate`, `formatSaoPauloTime`, and `formatSaoPauloDate` to ensure all date and time operations are correctly localized for Brazil (UTC-3).

## Professional Assistant (`src/app/api/ai/chat/route.ts`)

This API route provides an AI assistant for authenticated professionals, offering insights into their business performance. It is protected by authentication (`getUser`, `getProfessional`), plan-based feature gating (`canUseFeature`), and rate limiting (`getAiChatLimiter`) to manage resource usage, with a limit of 20 requests per 1 hour for the `aichat` prefix.

The assistant's behavior is guided by a `SYSTEM_PROMPT` that instructs it to respond in Portuguese, use tools for data retrieval, format values in BRL, and adhere to specific output formats for statistics.

Its toolset is focused on reporting and analytics:
*   `get_stats`: Gathers comprehensive statistics for the last 6 months, including global and month-by-month breakdowns of `totalAppointments`, `completed`, `noShows`, `noShowRate`, and `revenueBRL`. It queries the `appointments` table and uses `date-fns` utilities like `startOfMonth`, `endOfMonth`, and `subMonths` for temporal filtering.
*   `get_upcoming`: Fetches appointments scheduled for the next 7 days, joining `appointments` with `clients` to display client names.
*   `get_no_show_clients`: Identifies clients with the highest number of no-shows over the past 6 months, providing `totalAppointments`, `noShows`, and `noShowRate` per client. This involves a grouped query on `appointments` and `clients`.

## Design Decisions

*   **Separation of Concerns**: Two distinct AI agents (`ai-intake.ts` and `api/ai/chat/route.ts`) were created to serve different user personas (clients vs. professionals) and their specific needs. This allows for tailored prompts, toolsets, and data access patterns.
*   **Terse Tool Descriptions**: The `description` fields for `TOOLS` are intentionally kept short (e.g., "Busca pros. SEMPRE antes de listar.") to minimize token usage on every LLM call. The expectation is that the main system prompt provides the detailed guidance on when and how to use each tool.
*   **Database-Driven Tooling**: The AI agents directly interact with the Drizzle ORM and the PostgreSQL database, accessing 11 tables such as `professionals`, `appointments`, `clients`, and `availability`. This direct integration ensures that AI responses are always based on the most current and accurate application data.
*   **Defensive Date/Time Parsing**: Functions like `parsePtDate` and `parsePtTime` are used to robustly handle natural language date/time inputs from users, even if the LLM fails to convert them to ISO format in the first pass.
*   **Transaction for Booking**: The `bookAppointment` tool uses a Drizzle `transaction` with `serializable` isolation to prevent race conditions when multiple users might attempt to book the same slot concurrently. This is a critical choice for data integrity.
*   **Proactive Slot Alternatives**: The `getAvailableSlots` tool proactively searches for and suggests alternative booking dates if the requested date is unavailable. This reduces user friction and the number of turns required in a conversation.
*   **Ranking for Search Results**: `searchProfessionalsTool` incorporates a `rankScore` that considers `avgRating`, `reviewCount`, `completedCount`, `plan` tier, and even geographical proximity (when a city centroid can be resolved) to present the most relevant professionals first.

## Potential Improvements

1.  **Centralized Tool Call Logging**: The `agentMetrics` table, with columns like `totalCostUsd`, `totalLatencyMs`, and `toolCallCount`, is defined in the schema but not explicitly populated by the provided `ai-intake.ts` or `api/ai/chat/route.ts` code. Integrating calls to persist these metrics within the `chatWithFallback` function or immediately after tool execution would provide valuable operational insights and cost tracking.
2.  **Asynchronous Tool Execution for Multiple Calls**: In `src/app/api/ai/chat/route.ts`, if the LLM requests multiple tool calls, they are currently executed sequentially within the `for (const call of choice.tool_calls)` loop. For tools that are independent, executing them concurrently using `Promise.all` could reduce the overall `totalLatencyMs` for the AI response.
3.  **Enhanced Error Handling in Tools**: While tools like `searchProfessionalsTool` and `getAvailableSlots` return structured error objects (e.g., `{ error: "Profissional não encontrado" }`), the `bookAppointment` tool sometimes throws generic errors (e.g., `SLOT_TAKEN`) or relies on Drizzle's error codes. Standardizing tool error responses to always be structured objects with specific `reason` codes would allow the LLM to interpret and respond to failures more gracefully and consistently.
