# AI Layer with Groq and Llama 3.3 70B

Odys employs a sophisticated AI layer to enhance user experience for both clients seeking professionals and professionals managing their practice. This layer is built upon a strategic combination of Groq's inference engine and the Llama 3.3 70B model, utilizing a two-pass tool-calling pattern to ensure reliable and context-aware interactions. This document delves into the architecture, design choices, and operational details of this AI implementation.

## Overview

The AI layer in Odys is bifurcated into two primary components, each serving distinct user groups with specialized functionalities:

1.  **WhatsApp Concierge**: Implemented in `src/lib/ai-intake.ts`, this agent acts as a multi-professional discovery and booking assistant for clients interacting via WhatsApp. It guides users through finding suitable professionals, checking their availability, and booking appointments across the entire Odys marketplace.
2.  **Professional Assistant**: Located in `src/app/api/ai/chat/route.ts`, this component provides an AI chat interface within the professional's dashboard. It helps professionals analyze their business data, such as appointments, client behavior, and revenue, by querying the underlying database.

Both components share a common philosophy: leveraging large language models (LLMs) for natural language understanding and generation, coupled with a robust tool-calling mechanism to interact with Odys's operational data. The system relies on a Drizzle ORM-backed PostgreSQL database, featuring 11 tables, including `professionals`, `appointments`, `clients`, and `agentMetrics`, which store the core business logic and AI interaction logs.

## WhatsApp Concierge (`src/lib/ai-intake.ts`)

The WhatsApp Concierge is designed to be a single AI persona capable of handling all inbound messages on the corporate Odys WhatsApp number. Its core responsibility is to facilitate the client journey from discovery to booking.

The conversation flow operates as a state machine: initially in a "Discovery" state where the AI helps find professionals, transitioning to a "Focused" state once a `selectedProfessionalId` is established, allowing for detailed inquiries and booking. Users can "reset" the conversation to clear their selection and start a new search.

### Tooling and Data Interaction

The concierge uses 9 distinct tools, all defined in an OpenAI-compatible format, enabling seamless integration with various LLM providers. These tools are intentionally given terse descriptions, as the main prompt provides detailed instructions on their usage, saving valuable tokens on each API call.

Key tools include:

*   `search_professionals`: This tool is fundamental for discovery. It queries the `professionals` table, filtering by `profession`, `city`, `name`, and `service_type`. It also incorporates a ranking system (`rankScore`) that considers average ratings, review counts, completed appointments, and even geographical proximity (using `geocodeCity` and `distanceKm` to penalize distance from a city centroid for in-person services). If no direct matches are found in a requested city, it can fall back to `findNearestProfessionals` to suggest alternatives.
*   `list_professions`: This tool dynamically queries the `professionals` table to return only those professions that have at least one active professional registered, preventing the AI from suggesting unavailable services.
*   `get_professional_info`: Retrieves detailed information about a selected professional, including their `bio`, `address`, `schedule` (from the `availability` table), `avg_rating`, and `review_count` (from `reviews` and `clients` tables). It also constructs a `payment_policy` and fetches recent review snippets.
*   `get_available_slots`: This critical tool computes real-time availability by cross-referencing the professional's weekly `availability` rules with existing `appointments` for a given date. It handles Brazilian timezones (`saoPauloDate`, `formatSaoPauloTime`) and can suggest alternative dates if the requested one is fully booked.
*   `book_appointment`: Orchestrates the booking process. It performs checks for past dates and duplicate active bookings, then uses a Drizzle transaction with `serializable` isolation to prevent race conditions when creating new `appointments` and `clients` entries. Post-booking, it triggers notifications via WhatsApp (`sendWhatsApp` using templates like `msgBookingConfirmed`) and email (`sendBookingRequestEmailToProfessional`). It also generates `paymentInstructions` including a PIX payload if the professional has upfront payment configured.

### Conversation Logging and Metrics

The `agentMetrics` table is used to log details of AI interactions, including `traceId`, `promptVersion`, `totalCostUsd`, `totalLatencyMs`, and `toolCallCount`, providing valuable data for monitoring and optimization.

## Professional Assistant (`src/app/api/ai/chat/route.ts`)

The Professional Assistant provides a chat interface for professionals to gain insights into their practice. It is secured by user authentication (`getUser`) and enforces feature access based on the professional's subscription `plan` and `trialEndsAt` date using `canUseFeature`. A rate limit (`getAiChatLimiter`) is applied per user to manage resource consumption.

### System Prompt and Tools

The `SYSTEM_PROMPT` explicitly defines the AI's persona and output requirements, particularly for statistical summaries. It guides the AI to respond in Portuguese, use tools for data retrieval, and format financial values in BRL.

The assistant uses 4 specialized tools:

*   `get_stats`: Retrieves comprehensive statistics for the last 6 months, including global and month-by-month summaries of total appointments, completed sessions, no-shows, no-show rates, and revenue. It queries the `appointments` table and calculates metrics based on `sessionPrice` from the `professionals` table.
*   `get_upcoming`: Fetches appointments scheduled for the next 7 days, joining `appointments` with `clients` to display client names.
*   `get_no_show_clients`: Identifies clients with the highest number of no-shows over the past 6 months, providing a ranking with individual no-show rates. This involves a grouped query on `appointments` and `clients`.

## Design Decisions

### Groq and Llama 3.3 70B

The choice of Groq's inference engine paired with the Llama 3.3 70B model is a deliberate trade-off favoring speed and cost-efficiency for tool-calling agents. Groq's specialized Language Processing Unit (LPU) architecture offers significantly lower latency compared to traditional GPU-based inference, which is critical for interactive applications like a WhatsApp concierge where quick responses are paramount. Llama 3.3 70B provides a strong balance of capability and cost-effectiveness for complex reasoning and tool use, especially when combined with Groq's performance. The `chatWithFallback` mechanism in `src/lib/llm.ts` further enhances resilience by allowing the system to gracefully degrade to other providers (Cerebras, Gemini) if the primary Groq service experiences issues.

### Two-Pass Tool-Calling Pattern

Both AI components implement a two-pass tool-calling pattern. In the first pass, the LLM receives the user's query and the available `TOOLS`. It then decides whether to call a tool and, if so, which one and with what arguments. The system executes the requested tool(s), and the results are then injected back into the conversation history as `tool` messages. In the second pass, the LLM receives the original messages, its own tool call, and the tool's output, allowing it to generate a final, informed response.

This pattern offers several advantages:

*   **Reliability**: It separates the decision to call a tool from the generation of the final user-facing response. This reduces the chance of the LLM hallucinating tool outputs or misinterpreting complex results.
*   **Control**: The application has explicit control over tool execution, allowing for pre- and post-processing, error handling, and logging (`agentMetrics`).
*   **Contextual Accuracy**: By providing the LLM with the actual tool results, the final response is more accurate and directly addresses the information retrieved, rather than relying on the LLM's internal "knowledge" of what a tool *might* return.

### Terse Tool Descriptions

The `TOOLS` array in `src/lib/ai-intake.ts` and `src/app/api/ai/chat/route.ts` uses intentionally brief descriptions. This decision is a token-saving measure. Since the entire `TOOLS` array is sent with every LLM request, minimizing its size reduces both cost and latency. The detailed instructions on when and how to use each tool are instead embedded within the main `SYSTEM_PROMPT`, which is typically longer but sent less frequently or only once per conversation.

### Database Schema Integration

The Drizzle ORM schema, with its 11 tables, is central to the AI's functionality. Tables like `professionals`, `availability`, `appointments`, and `clients` are directly queried and manipulated by the AI's tools. The schema design, including `uuid` primary keys, `text` fields for names and descriptions, and `timestamp` for temporal data, provides a flexible and performant foundation for the AI to access and update business-critical information. For instance, the `professionals.sessionPrice` (integer, cents) is consistently divided by 100 to present values in BRL to the user, ensuring correct financial representation.

## Potential Improvements

1.  **Enhanced Tool Argument Validation**: In `src/lib/ai-intake.ts`, functions like `bookAppointment` and `getAvailableSlots` include defensive parsing for `dateStr` and `time` (e.g., `parsePtDate`, `parsePtTime`). While helpful, the tool definitions themselves could be augmented with stricter JSON schema patterns or even Zod schemas to provide more explicit guidance to the LLM and catch malformed inputs earlier, reducing the need for extensive in-function validation.
2.  **Structured Error Responses from Tools**: Many tool implementations, such as `searchProfessionalsTool` or `getProfessionalInfo`, return generic `{ error: string }` objects. Introducing more specific error codes (e.g., `PROFESSIONAL_NOT_FOUND`, `SLOT_TAKEN`, `INVALID_DATE_FORMAT`) would allow the LLM to interpret and respond to failures with greater nuance and potentially suggest more targeted recovery actions to the user, rather than just echoing a generic error message.
3.  **Parallel Tool Execution**: In `src/app/api/ai/chat/route.ts`, the `for (const call of choice.tool_calls)` loop executes tool calls sequentially. If the LLM requests multiple independent tools (e.g., `get_stats` and `get_upcoming` simultaneously), these could be executed in parallel using `Promise.all` to reduce the overall latency of the second LLM call, especially for complex queries.
4.  **Dynamic Tool `enum` for Professions**: The `search_professionals` tool in `src/lib/ai-intake.ts` takes a `profession` string. While `listProfessionsTool` provides a list of active professions, the `search_professionals` tool definition does not dynamically constrain its `profession` parameter to this list. If the LLM provider supports dynamic `enum` values in tool definitions, or if a pre-processing step could inject this list, it would prevent the LLM from attempting to search for professions that have no active professionals, leading to more efficient and successful searches.
