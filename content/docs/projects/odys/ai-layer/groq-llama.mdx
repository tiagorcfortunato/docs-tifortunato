The AI layer in Odys orchestrates intelligent interactions, primarily through two distinct agents: a WhatsApp Concierge for client-facing discovery and booking, and a Professional Assistant for providing business insights to professionals. Both agents are designed for responsiveness and accuracy, relying on a strategic combination of high-performance language models and a structured two-pass tool-calling pattern.

## Overview

Odys employs a sophisticated AI architecture to automate and enhance user interactions. At its core, the system utilizes a `chatWithFallback` mechanism, prioritizing Groq's optimized inference engine for the Llama 3.3 70B model, with Cerebras and Gemini serving as resilient fallbacks. This setup is critical for maintaining low latency, especially for the interactive WhatsApp Concierge.

The AI layer is composed of two primary agents:

1.  **WhatsApp Concierge** (`src/lib/ai-intake.ts`): This agent acts as a marketplace-wide discovery and booking assistant. It handles all inbound WhatsApp messages on the corporate Odys number, guiding clients through finding professionals, browsing schedules, and making appointments. Its operation is structured around a conversation state machine that transitions between a "Discovery" phase (when no professional is selected), a "Focused" phase (after a professional is chosen), and a "Reset" state. This agent is equipped with 9 distinct tools, enabling it to interact deeply with the platform's data.
2.  **Professional Assistant** (`src/app/api/ai/chat/route.ts`): This agent provides professionals with insights into their business, such as appointment summaries, client behavior, and revenue. It operates within the context of a single professional and uses 4 specialized tools to query and analyze their specific data. Access to this assistant is gated by the user's subscription plan, requiring a Pro or Premium plan, or an active trial, as enforced by the `canUseFeature` guard.

Both agents implement a two-pass tool-calling pattern, where the Language Model (LLM) first decides on tool usage and then, in a second pass, generates a final response after executing the chosen tools and incorporating their results. This pattern is fundamental to the reliability and accuracy of the AI's interactions.

The agents interact with 11 database tables, including `professionals`, `availability`, `appointments`, `clients`, `notifications`, `reviews`, and `agentMetrics`, ensuring they have access to comprehensive and up-to-date information.

## Design Decisions

### Two-Pass Tool-Calling Pattern

The decision to implement a two-pass tool-calling pattern, as seen in `src/app/api/ai/chat/route.ts`, is a deliberate trade-off favoring accuracy and reliability over a single, potentially faster, LLM call. In the first pass, the LLM (`chatWithFallback`) analyzes the user's query and determines if any of the available tools are necessary. If a tool is identified, the LLM generates a `tool_calls` object. The application then executes these tools, gathering concrete data. In the second pass, the LLM receives the original messages, its own `tool_calls`, and the `content` (results) from the tool executions. This allows the LLM to synthesize a final, informed response.

This approach mitigates common LLM challenges such as hallucination, where models might invent data or misinterpret tool capabilities. By separating the "thinking" (tool selection) from the "acting" (tool execution) and then "reporting" (final response), the LLM has a clearer context and a higher chance of producing factually correct and relevant answers. While it incurs the latency of two LLM calls, the enhanced reliability is crucial for applications that directly impact user actions, like booking appointments or providing financial summaries.

### Groq and Llama 3.3 70B

The choice of Groq for running the Llama 3.3 70B model is driven by a need for exceptional inference speed and cost-efficiency. Groq's specialized Language Processing Units (LPUs) are designed to deliver significantly lower latency compared to traditional GPU-based inference, which is paramount for interactive conversational agents like the WhatsApp Concierge. A slow response time can degrade the user experience, making the conversation feel unnatural or frustrating.

Llama 3.3 70B, as a powerful open-source model, offers a strong balance of general intelligence and specific task performance. Running it on Groq allows Odys to leverage a highly capable model without incurring the higher costs or latencies often associated with proprietary models or less optimized inference hardware. The `chatWithFallback` strategy further enhances this by providing resilience: if Groq experiences an outage or rate limit, the system can seamlessly fall back to Cerebras or Gemini, ensuring continuous service availability, albeit potentially with slightly higher latency or cost.

### Terse Tool Descriptions

The `TOOLS` array in `src/lib/ai-intake.ts` and `src/app/api/ai/chat/route.ts` features intentionally terse descriptions for each function. For instance, `search_professionals` is described simply as "Busca pros. SEMPRE antes de listar." This design choice aims to minimize token usage on every API request. Since the entire `TOOLS` array is sent with each LLM call, keeping descriptions short reduces the overall prompt length, which directly translates to lower operational costs and faster inference times. The system relies on a more detailed `SYSTEM_PROMPT` to guide the LLM on *when* and *how* to use these tools effectively, offloading the descriptive burden from the tool definitions themselves.

### Transactional Booking and Conflict Resolution

The `bookAppointment` function in `src/lib/ai-intake.ts` utilizes a database transaction with `isolationLevel: "serializable"`. This is a critical design decision to ensure data integrity and prevent race conditions in a multi-user environment. When multiple clients attempt to book the same slot concurrently, the serializable isolation level guarantees that transactions are processed as if they occurred sequentially, preventing phantom reads or non-repeatable reads. The explicit `SLOT_TAKEN` error and the handling of `40001` (serialization_failure) and `23505` (unique_violation) SQL error codes provide robust conflict resolution, informing the user if a slot has just been filled. This ensures that only one appointment can be successfully created for a given time slot, maintaining the integrity of the professional's schedule.

### Proactive Data Fetching and Ranking

In `searchProfessionalsTool` within `src/lib/ai-intake.ts`, the system proactively fetches `getProStats` for all matched professionals. This allows for a composite `rankScore` to be calculated, incorporating `avgRating`, `reviewCount`, `completedCount`, `plan` tier, and even `distanceKm` from a city centroid. This design ensures that search results are not merely a list of matching professionals but are intelligently ordered to present the most relevant and highly-regarded options first. This enhances the user experience by surfacing quality professionals more effectively, even when the user's exact location is unknown.

## Potential Improvements

1.  **Stricter Tool Parameter Validation in Schema**: The `bookAppointment` function in `src/lib/ai-intake.ts` currently performs defensive parsing and validation for `dateStr` and `time` using `parsePtDate` and `parsePtTime`. While effective, this validation happens *after* the LLM has already generated the tool call. A more robust approach would be to incorporate stricter `pattern` or `format` properties directly into the `parameters` schema of the `book_appointment` tool definition. This would guide the LLM to generate correctly formatted dates and times from the outset, reducing the likelihood of invalid inputs and subsequent parsing errors, and shifting validation closer to the input source.

2.  **Dynamic Tool Descriptions for Context**: The current terse tool descriptions, as noted in `src/lib/ai-intake.ts`, save tokens but might occasionally limit the LLM's contextual understanding. For tools like `get_available_slots`, if a `selectedProfessionalId` is already established in the conversation state, the tool description could be dynamically augmented to explicitly mention that it will fetch slots *for that specific professional*. This would provide more precise guidance to the LLM without significantly increasing token usage across all turns, improving tool selection accuracy in focused conversational states.

3.  **Enhanced Geocoding for `search_professionals`**: The `searchProfessionalsTool` in `src/lib/ai-intake.ts` uses `geocodeCity` to find a city centroid for distance-based ranking when multiple in-city matches are found. While useful, it doesn't allow the user to specify a more granular location like a neighborhood. Introducing an optional `neighborhood` parameter to the `search_professionals` tool and integrating a more precise geocoding service (e.g., for street addresses or specific points of interest) would enable more accurate "in-person" professional discovery, especially in large cities where neighborhoods can be tens of kilometers apart.
