The Odys platform incorporates an AI layer designed to automate interactions and provide intelligent assistance, serving both external clients via a WhatsApp concierge and internal professionals through a chat assistant. This layer is built around the Groq inference engine running the Llama 3.3 70B model, employing a two-pass tool-calling pattern to ensure reliable and efficient execution of complex tasks.

## Overview

Odys's AI capabilities are primarily split into two distinct agents, each tailored for specific use cases:

1.  **WhatsApp Concierge (`src/lib/ai-intake.ts`)**: This agent acts as a multi-professional discovery and booking system, handling all inbound WhatsApp messages on the corporate Odys number. It guides clients through finding professionals, browsing schedules, and booking appointments across the entire marketplace.
2.  **Professional Assistant (`src/app/api/ai/chat/route.ts`)**: Integrated into the professional dashboard, this assistant helps professionals understand their business data, such as appointments, client information, and revenue summaries. It is accessible via the `/api/ai/chat` API route.

Both agents utilize the `chatWithFallback` utility, which orchestrates calls to large language models (LLMs), prioritizing Groq for its speed and cost-effectiveness with the Llama 3.3 70B model. A key architectural decision for both agents is the "two-pass tool-calling" pattern, where the LLM first determines if a tool is needed, and then, after the tool's execution, generates a final response incorporating the tool's output. This approach enhances reliability and control over the AI's interactions.

The AI layer interacts extensively with the Drizzle ORM-backed PostgreSQL database, leveraging tables such as `professionals`, `availability`, `appointments`, `clients`, `reviews`, and `agentMetrics` to perform its functions.

## WhatsApp Concierge (`src/lib/ai-intake.ts`)

The WhatsApp Concierge is a sophisticated agent designed to manage the entire client journey from discovery to booking. Its conversation flow is structured around a state machine:
*   **Discovery**: When no `selectedProfessionalId` is set, the AI helps clients find a professional based on criteria like profession, city, or name.
*   **Focused**: Once a `selectedProfessionalId` is established, the AI focuses on fetching available slots and facilitating bookings for that specific professional.
*   **Reset**: Clients can initiate a reset by asking for "outro profissional," clearing the current selection and returning to the discovery phase.

### Tool Definitions and Implementations

The agent is equipped with 9 distinct tools, each designed to perform a specific action by interacting with the Odys database or external services. The tool descriptions are intentionally terse to conserve tokens, as the system prompt provides detailed guidance on their usage.

1.  **`search_professionals`**: This tool is crucial for the discovery phase. It queries the `professionals` table, filtering by `profession`, `city`, `name`, and `service_type`. It uses `resolveProfessionAlias` to map common Portuguese terms (e.g., "psicologa") to canonical English profession keys. For location-based searches, it can use `geocodeCity` to find city centroids and `findNearestProfessionals` to suggest alternatives if no local matches are found. Results are ranked using `rankScore`, which considers average rating, review count, completed appointments, and the professional's plan tier, with an optional distance penalty.
2.  **`list_professions`**: This tool dynamically lists only the professions that have at least one active professional registered in the `professionals` table, preventing the AI from suggesting unavailable services.
3.  **`select_professional`**: This tool sets the `selectedProfessionalId` in the conversation state, transitioning the agent into the "Focused" mode.
4.  **`get_professional_info`**: Retrieves detailed information about a specific professional from the `professionals` table, including their `bio`, `addressLine`, `sessionDuration`, `sessionPrice`, and `serviceType`. It also fetches `availability` rules, `reviews`, and aggregated statistics using `getProStats` to provide a comprehensive profile.
5.  **`get_available_slots`**: This tool is critical for booking. It first validates the requested date, then calls `computeSlotsForDate` to determine actual available time slots based on the professional's `availability` rules and existing `appointments`. It also proactively looks for and suggests alternative dates if the requested date has no availability.
6.  **`book_appointment`**: This is the core booking tool. It performs several checks, including preventing bookings in the past and detecting duplicate active appointments for the same client and professional. The booking process is wrapped in a Drizzle transaction with `serializable` isolation to prevent race conditions. It handles client creation if necessary, inserts into the `appointments` table, and triggers various notifications (WhatsApp messages via `sendWhatsApp` and emails via `sendBookingRequestEmailToProfessional` or `sendBookingConfirmedEmailToClient`) based on the professional's `autoConfirm` setting. It also computes payment instructions, including PIX details, using `buildPaymentPolicy` and `buildPixPayload`.
7.  **`list_my_appointments`**: Fetches future appointments for the current client from the `appointments` table.
8.  **`cancel_appointment`**: Updates the status of an existing appointment in the `appointments` table to "cancelled".
9.  **`reschedule_appointment`**: Modifies an existing appointment's date and time, typically after `get_available_slots` has been used to find new suitable times.

The agent also includes timezone helpers (`saoPauloDate`, `formatSaoPauloTime`, `formatSaoPauloDate`) to correctly handle dates and times in the "America/Sao_Paulo" timezone, reflecting Brazil's abolition of DST.

## Professional Assistant (`src/app/api/ai/chat/route.ts`)

The Professional Assistant provides data insights to professionals through a chat interface. It is exposed via the `/api/ai/chat` API route, which accepts POST requests containing a history of messages.

### Security and Authorization

*   **Authentication**: The route requires an authenticated user, verified by `getUser()`.
*   **Authorization**: It checks if the authenticated user is a registered professional using `getProfessional(user.id)`.
*   **Feature Guard**: Access to the AI assistant feature is controlled by the user's subscription plan and trial status, enforced by `canUseFeature(professional.plan, "assistant", professional.trialEndsAt)`. Only "Pro" and "Premium" plans, or users within their trial period, can use it.
*   **Rate Limiting**: To prevent abuse and manage LLM costs, the `getAiChatLimiter()` applies a rate limit of 20 requests per hour per authenticated user (`user.id`), not per IP address.

### System Prompt and Tools

The `SYSTEM_PROMPT` explicitly instructs the AI on its role, language, and how to use its tools, including specific formatting requirements for responses related to no-show rates and monthly summaries.

The assistant has 3 specialized tools:

1.  **`get_stats`**: This tool queries the `appointments` table to provide a comprehensive summary of a professional's activity over the last 6 months. It calculates global and month-by-month statistics, including total appointments, completed sessions, no-shows, cancellation rates, and estimated revenue based on `professionals.sessionPrice`.
2.  **`get_upcoming`**: Fetches and lists appointments scheduled for the next 7 days from the `appointments` table, joining with `clients` to display client names.
3.  **`get_no_show_clients`**: Identifies and ranks clients who have the highest number of no-shows over the past 6 months. It queries `appointments` and `clients`, grouping by client to calculate individual no-show counts and rates.

### Two-Pass Tool-Calling in Action

The `POST` handler for `/api/ai/chat` exemplifies the two-pass pattern:

1.  **First Pass**: `chatWithFallback` is called with the user's messages and the `TOOLS` array, with `tool_choice: "auto"`. The LLM decides whether to generate a direct text response or invoke one or more tools.
2.  **Tool Execution**: If the LLM requests tool calls, the server executes these functions (`getStats`, `getUpcoming`, `getNoShowClients`) locally. The results are then formatted as `tool` messages.
3.  **Second Pass**: `chatWithFallback` is called again, this time with the original messages, the LLM's tool call request, and the `tool` messages containing the execution results. The LLM then synthesizes a final, human-readable response based on the tool outputs.

This pattern ensures that the LLM's final output is grounded in factual data retrieved by the tools, rather than hallucinated information.

## Design Decisions

*   **Groq + Llama 3.3 70B**: The selection of Groq as the primary inference engine for Llama 3.3 70B is a strategic choice driven by the need for low-latency responses in interactive chat scenarios, especially for the WhatsApp Concierge. Groq's specialized hardware offers significantly faster inference speeds compared to other providers, which is critical for a fluid user experience. The `chatWithFallback` mechanism provides a safety net, allowing the system to gracefully degrade to other LLM providers if Groq experiences issues, thus maintaining service availability.
*   **Two-Pass Tool-Calling**: This pattern was adopted to enhance the reliability and accuracy of AI interactions. By separating the tool-calling decision from the final response generation, the system gains several advantages:
    *   **Reduced Hallucinations**: The LLM's final response is based on concrete data from tool outputs, minimizing the risk of generating incorrect information.
    *   **Improved Control**: The application layer has explicit control over tool execution, allowing for validation, error handling, and logging of tool calls.
    *   **Cost Optimization**: In some cases, a simpler LLM call might suffice for the first pass (tool decision), and only if a tool is invoked, a more capable (and potentially more expensive) model might be used for the second pass, or the same model can be used more efficiently.
*   **Terse Tool Descriptions**: The tool descriptions within the `TOOLS` array are kept short and to the point (e.g., "Busca pros. SEMPRE antes de listar."). This design decision aims to reduce the token count sent with each API request, thereby lowering operational costs and potentially improving inference latency, especially with models like Llama 3.3 70B where context window size and cost are factors. The detailed instructions for tool usage are instead embedded in the system prompt, which is sent once per conversation.
*   **Explicit Timezone Handling**: Brazil's unique timezone situation (no DST since 2019) necessitated explicit timezone management. Functions like `saoPauloDate`, `formatSaoPauloTime`, and `formatSaoPauloDate` ensure that all date and time operations are consistently handled in "America/Sao_Paulo" (UTC-3), preventing common off-by-one errors or misinterpretations of local times.
*   **Per-User Rate Limiting**: For the Professional Assistant, rate limiting is applied per `user.id` rather than per IP address. This is a deliberate choice to prevent a single user from exhausting the AI budget, while allowing multiple users from the same network (e.g., an office) to use the service without collectively hitting a shared limit.
*   **Observability with `agentMetrics`**: The `agentMetrics` table is designed to capture critical data about AI interactions, including `traceId`, `totalCostUsd`, `totalCostBrl`, `totalLatencyMs`, `toolCallCount`, `providersUsed`, and `outcome`. This allows for monitoring the performance, cost, and effectiveness of the AI agents, providing valuable insights for optimization and debugging.

## Potential Improvements

1.  **Enhanced Tool Parameter Validation**: In `src/lib/ai-intake.ts`, the `getAvailableSlots` and `bookAppointment` functions include defensive parsing for `dateStr` and `time` (e.g., `if (!/^\d{4}-\d{2}-\d{2}$/.test(dateStr))`). While functional, moving this validation to a more structured, schema-based approach at the tool-calling layer could provide clearer error messages to the LLM and prevent malformed inputs from reaching the core business logic. This would make the tool definitions more robust and less reliant on defensive coding within each implementation.
2.  **Asynchronous Notification Processing**: The `bookAppointment` function in `src/lib/ai-intake.ts` sends WhatsApp messages and emails using `sendWhatsApp` and `sendBookingRequestEmailToProfessional` with `.catch` blocks. While this makes them fire-and-forget, it couples the booking transaction's response time to the notification sending and offers limited retry mechanisms. Decoupling these notifications into a dedicated message queue or background worker system would improve the responsiveness of the booking API, enhance reliability (with retries), and provide better observability for notification delivery status.
3.  **Dynamic Tool Descriptions for LLM**: The current tool descriptions are terse to save tokens. While effective with a well-tuned system prompt, generating more descriptive tool descriptions dynamically (e.g., from a JSON schema or OpenAPI spec) could potentially improve the LLM's understanding of when and how to use tools, especially if the system prompt changes or if new, similar tools are added. This could reduce the need for extensive prompt engineering to guide tool usage.
4.  **Granular Location Search in `searchProfessionalsTool`**: The `searchProfessionalsTool` currently supports `city` as a search parameter. While it attempts to use `geocodeCity` for ranking, it lacks a `neighborhood` or more granular `near` parameter. Adding such a parameter, which could leverage the `latitude` and `longitude` columns in the `professionals` table, would allow clients to find professionals with greater precision, especially in large metropolitan areas where "city" alone is too broad.
