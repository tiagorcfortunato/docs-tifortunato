# AI Layer

Odys integrates artificial intelligence to enhance both client interaction and professional management. This document explores the architectural choices behind the AI layer, focusing on the selection of Groq and Llama 3.3 70B, and the implementation of a two-pass tool-calling pattern. These decisions aim to deliver responsive, accurate, and cost-effective AI capabilities across the platform.

## Overview

The AI layer in Odys is composed of two primary agents, each serving a distinct purpose but built upon a shared foundation:

1.  **WhatsApp Concierge**: Implemented in `src/lib/ai-intake.ts`, this agent acts as a multi-professional discovery and booking assistant for clients interacting via WhatsApp. It guides users through finding professionals, checking availability, and scheduling appointments across the entire marketplace.
2.  **Professional Assistant**: Located at the `/api/ai/chat` API route (`src/app/api/ai/chat/route.ts`), this agent provides insights and data summaries to professionals within their dashboard. It helps them understand their appointments, client behavior, and revenue trends.

Both agents utilize a common strategy for interacting with large language models (LLMs), abstracting the underlying provider chain through `chatWithFallback`. This allows Odys to dynamically select the most suitable LLM, currently favoring Groq with Llama 3.3 70B for its performance characteristics. A critical architectural pattern shared by both agents is the "two-pass tool-calling" mechanism, which enhances the reliability and control over AI-driven workflows.

The system interacts with a total of 11 database tables, including `professionals`, `appointments`, `clients`, and `agentMetrics`, and exposes 23 API routes, with `/api/ai/chat` being one of them.

## LLM Selection: Groq and Llama 3.3 70B

The choice of Groq, paired with the Llama 3.3 70B model, for the core LLM inference is a deliberate one, driven by a balance of performance, cost, and capability.

Groq specializes in extremely fast inference for LLMs, which is crucial for interactive applications like the WhatsApp Concierge. When a client is chatting with the AI, minimizing latency is paramount to a natural and engaging conversation. Groq's low-latency processing directly contributes to a more fluid user experience, preventing frustrating delays.

Llama 3.3 70B, on the other hand, provides a powerful and capable model suitable for complex reasoning and tool-calling tasks. Its large parameter count allows it to understand nuanced requests and generate high-quality responses. As an open-source model, it also offers flexibility and potential for future fine-tuning or deployment strategies, while still delivering competitive performance against proprietary alternatives.

The `chatWithFallback` utility, imported from `@/lib/llm`, encapsulates the logic for selecting and interacting with the LLM providers. This abstraction allows Odys to define a provider chain (e.g., Groq → Cerebras → Gemini), ensuring resilience and potentially optimizing costs by attempting cheaper or faster providers first, then falling back to others if necessary. This design ensures that the AI layer remains operational even if a primary provider experiences issues, and allows for easy experimentation with new models or providers without rewriting core agent logic.

## The Two-Pass Tool-Calling Pattern

A fundamental design pattern employed by both the WhatsApp Concierge and the Professional Assistant is the "two-pass tool-calling" mechanism. This pattern enhances the reliability and accuracy of AI agents that need to interact with external systems or retrieve specific data.

The process unfolds in two distinct steps:

1.  **First Pass: Tool Request**: The LLM receives the user's message along with a list of available tools and their descriptions. In this initial pass, the LLM's primary task is to determine if any of the provided tools are relevant to fulfill the user's request. If a tool is deemed necessary, the LLM generates a "tool call" specifying the tool's name and the arguments to be passed to it. It does *not* generate a final user-facing response at this stage.
2.  **Second Pass: Tool Execution and Final Response**: If the first pass resulted in a tool call, the application intercepts this call, executes the specified tool function with the provided arguments, and captures its result. This result, along with the original conversation history and the LLM's initial tool call, is then fed back to the LLM. In this second pass, the LLM's role is to synthesize the tool's output into a coherent, natural language response for the user.

This two-pass approach offers several advantages:

*   **Reduced Hallucinations**: By separating the decision to call a tool from the generation of the final response, the LLM is less likely to "hallucinate" data or invent tool outputs. It only generates a response *after* it has concrete, factual results from the tool.
*   **Improved Control and Error Handling**: The application has an explicit point to intercept, validate, and execute tool calls. This allows for robust error handling (e.g., if a tool fails or returns an unexpected result) and ensures that sensitive operations are performed correctly.
*   **Optimized Token Usage**: Tool descriptions, while terse, are sent with every request. By only sending tool results back to the LLM in the second pass, the context window for the initial decision-making is kept cleaner, and the LLM can focus on interpreting the results without being distracted by the tool's internal logic.

For instance, in `src/app/api/ai/chat/route.ts`, when a professional asks for "Taxa de no-show", the first LLM call identifies the need for the `get_stats` tool. The application then executes `getStats(professional.id, professional.sessionPrice)`, and the structured data returned by this function is fed back to the LLM for generating the final, formatted response about no-show rates. Similarly, the WhatsApp Concierge in `src/lib/ai-intake.ts` uses this pattern for complex operations like `search_professionals` and `book_appointment`, ensuring that database queries and external notifications are handled reliably before the LLM crafts a reply.

## WhatsApp Concierge (`src/lib/ai-intake.ts`)

The WhatsApp Concierge is a sophisticated agent designed to handle client interactions on the main Odys WhatsApp number. Its primary goal is to facilitate professional discovery and appointment booking across the entire platform.

The agent maintains a `ConversationState` to track the user's intent and context, such as whether a `selectedProfessionalId` has been set. This state machine allows the AI to transition between a "Discovery" phase (searching for professionals) and a "Focused" phase (interacting with a specific professional's schedule).

A comprehensive set of tools, defined in the `TOOLS` array, enables the concierge to perform various actions:

*   `search_professionals`: This tool is central to the discovery phase. It queries the `professionals` table, applying filters for `profession`, `city`, `name`, and `service_type`. Notably, it includes logic for resolving Portuguese profession aliases (e.g., "psicologa" to "psychologist") and performs geo-ranking using `findNearestProfessionals` and `geocodeCity` to suggest relevant professionals, even when no exact matches are found in a requested city.
*   `list_professions`: This tool dynamically lists only those professions that have active professionals registered in the system, preventing dead-end searches.
*   `get_professional_info`: Retrieves detailed information about a selected professional, including their `bio`, `address`, `schedule` (from the `availability` table), `avg_rating`, and `recent_reviews` (from the `reviews` and `clients` tables). It also constructs a `payment_policy` and `profile_url`.
*   `get_available_slots`: This critical tool computes actual available appointment slots for a given professional and date, considering their `availability` rules and existing `appointments`. It intelligently suggests `alternatives` if the requested date has no slots, reducing conversational turns.
*   `book_appointment`: This transactional tool handles the core booking logic. It uses `db.transaction` with a `serializable` isolation level to prevent race conditions and ensure data integrity when creating new `appointments` and `clients`. It also manages sending various WhatsApp notifications (`msgBookingRequest`, `msgBookingConfirmed`, `msgBookingConfirmedReceipt`) and emails (`sendBookingRequestEmailToProfessional`) to both clients and professionals, and generates PIX payment instructions if applicable.
*   `list_my_appointments`, `cancel_appointment`, `reschedule_appointment`: These tools allow clients to manage their existing bookings.

The agent also includes robust date and time handling functions like `saoPauloDate`, `formatSaoPauloTime`, `parsePtDate`, and `parsePtTime` to accurately interpret and display times in the "America/Sao_Paulo" timezone, which is critical for a Brazilian-focused application.

## Professional Assistant (`src/app/api/ai/chat/route.ts`)

The Professional Assistant is exposed via the `/api/ai/chat` API route and is designed to provide data-driven insights to professionals within their dashboard. It operates under a strict `SYSTEM_PROMPT` that guides its responses, ensuring it uses tools to fetch data and formats output in Portuguese, specifically for financial values in BRL.

Key tools available to this assistant include:

*   `get_stats`: This tool fetches comprehensive statistics for the last 6 months, including global summaries (total appointments, completed, no-shows, revenue) and a month-by-month breakdown. It queries the `appointments` table to aggregate this data. The `SYSTEM_PROMPT` explicitly instructs the LLM on how to format the no-show rate and monthly summary responses.
*   `get_upcoming`: Retrieves a list of appointments scheduled for the next 7 days, joining `appointments` with `clients` to display client names.
*   `get_no_show_clients`: Identifies and ranks clients who have missed the most appointments over the past 6 months, providing individual no-show rates. This involves a grouped query on `appointments` and `clients`.

To prevent abuse and manage costs, the `/api/ai/chat` endpoint implements rate limiting using `getAiChatLimiter`. This limit is applied per authenticated `user.id`, ensuring that individual professionals cannot exhaust the AI budget through excessive requests. Access to this feature is also gated by the professional's `plan` and `trialEndsAt` date, as checked by `canUseFeature`.

## Design Decisions

1.  **Separation of AI Agents**: Odys employs two distinct AI agents (`ai-intake.ts` and `api/ai/chat/route.ts`) for different user types (clients vs. professionals) and contexts (WhatsApp concierge vs. dashboard assistant). This separation allows for highly specialized prompts, tailored toolsets, and optimized performance for each use case, rather than attempting to build a single, monolithic AI that serves all functions.
2.  **Tool-First Orchestration**: The LLM is primarily used as an intelligent orchestrator of predefined tools, rather than a free-form text generator. This "tool-first" approach, especially with the two-pass pattern, grounds the AI's responses in factual data retrieved from the database or external services. This significantly reduces the risk of hallucinations and ensures that the AI's actions are predictable and auditable.
3.  **Concise Tool Descriptions**: The `TOOLS` array in `src/lib/ai-intake.ts` uses intentionally terse descriptions (e.g., "Busca pros. SEMPRE antes de listar."). This decision is a token-saving optimization. Since the entire `TOOLS` array is sent with every LLM request, keeping descriptions short minimizes the input token count, directly reducing inference costs and potentially improving latency. The LLM is expected to learn the nuances of tool usage from the main system prompt rather than verbose tool descriptions.
4.  **Transactional Booking Logic**: The `bookAppointment` function in `src/lib/ai-intake.ts` utilizes a Drizzle `db.transaction` with a `serializable` isolation level. This is a critical design choice for maintaining data integrity in a multi-user system. It ensures that concurrent booking attempts for the same time slot are correctly handled, preventing double-bookings and guaranteeing that either all database operations (client creation, appointment insertion) succeed or none do.
5.  **User-Specific Rate Limiting**: The `/api/ai/chat` endpoint implements rate limiting based on `user.id` rather than IP address. This is a deliberate choice to protect against individual user abuse or runaway scripts, ensuring that one professional's activity does not negatively impact others sharing the same network or IP address. It provides a fairer distribution of AI resources and helps manage operational costs.

## Potential Improvements

1.  **Structured Tool Output Validation**: The current implementation of tool execution, particularly in `src/app/api/ai/chat/route.ts`, uses `JSON.stringify(result)` to pass tool outputs back to the LLM. While functional, this can lead to the LLM receiving verbose or potentially malformed JSON if the tool's output structure changes or contains unexpected data. Introducing a schema validation layer (e.g., using Zod) for tool outputs, and potentially a summarization step, could make the tool results more digestible for the LLM, reduce token usage, and improve the reliability of the second-pass response generation. This would apply to functions like `getStats`, `getUpcoming`, and `getNoShowClients`.
2.  **Dynamic Tool Filtering for Concierge**: The `TOOLS` array in `src/lib/ai-intake.ts` is static and includes all possible tools at every turn. For the WhatsApp Concierge, some tools (e.g., `get_available_slots`, `book_appointment`) are only relevant once a `professional_id` has been selected. Dynamically filtering the `TOOLS` array based on the `ConversationState` (e.g., only showing booking-related tools when `selectedProfessionalId` is set) could reduce the LLM's context window, potentially saving tokens and reducing the chance of the LLM attempting to call irrelevant tools.
3.  **Parallel Tool Execution**: In `src/app/api/ai/chat/route.ts`, the `for (const call of choice.tool_calls)` loop executes tool calls sequentially. If the LLM requests multiple independent tools in a single turn, executing them in parallel using `Promise.all` could significantly reduce the overall latency of the API response. This would be particularly beneficial if tool functions involve database queries or external API calls that can run concurrently.
4.  **Granular Error Reporting from Tools**: Several tool implementations, such as `getProfessionalInfo` and `getAvailableSlots` in `src/lib/ai-intake.ts`, return generic `{ error: string }` messages. While the LLM can interpret these, providing more structured error codes or types (e.g., `error: { type: "not_found", message: "..." }` or `error: { type: "invalid_date_format", details: "..." }`) could enable the LLM to generate more specific, helpful, and actionable responses to the user, rather than generic error messages.
5.  **Comprehensive Agent Metric Tracking for Concierge**: The `agentMetrics` table is defined in the schema, and `calculateCost` is imported in `src/lib/ai-intake.ts`. However, the provided code snippet does not explicitly show where the cost and other metrics (like `totalLatencyMs`, `toolCallCount`, `outcome`) for each turn of the WhatsApp Concierge are calculated and persisted to the `agentMetrics` table. Implementing this tracking would be crucial for monitoring the performance, cost-effectiveness, and success rate of this complex, user-facing agent.
