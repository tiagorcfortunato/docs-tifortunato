Odys employs a sophisticated AI layer to enhance both client interaction and professional productivity. This layer is primarily composed of two distinct AI agents, each tailored to a specific user persona and set of tasks. The core of this architecture relies on the `chatWithFallback` mechanism, which prioritizes high-performance models like Groq's Llama 3.3 70B for speed and cost-efficiency, while providing fallbacks to other providers for resilience. A key design pattern across both agents is the two-pass tool-calling approach, which significantly improves the reliability and accuracy of AI-driven interactions.

## Overview

The AI capabilities within Odys are bifurcated into two main components: a public-facing WhatsApp Concierge and an internal Professional Dashboard Assistant. These agents, while sharing underlying LLM infrastructure, operate with distinct system prompts, toolsets, and objectives, reflecting a clear separation of concerns.

The **WhatsApp Concierge**, implemented in `src/lib/ai-intake.ts`, acts as a multi-professional discovery and booking agent. It handles all inbound WhatsApp messages to the corporate Odys number, guiding clients through finding a professional, browsing schedules, and booking appointments across the entire marketplace. This agent manages a conversation state machine, transitioning between discovery, focused interaction with a selected professional, and reset states. It interacts with several database tables, including `professionals`, `availability`, `appointments`, `clients`, `notifications`, `reviews`, and `agentMetrics`, which collectively represent 11 tables in the Odys schema. The concierge utilizes 9 distinct tools, such as `search_professionals` and `book_appointment`, to fulfill user requests.

Conversely, the **Professional Dashboard Assistant**, exposed via the `/api/ai/chat` route, serves Odys professionals directly. Its purpose is to help professionals understand their business data, including appointments, clients, and revenue. This assistant uses a more focused set of 3 tools, including `get_stats` for financial and no-show metrics, `get_upcoming` for future appointments, and `get_no_show_clients` to identify clients with high no-show rates. Access to this assistant is gated by the user's subscription plan, requiring a Pro or Premium plan, and is subject to a rate limit of 20 requests per hour per user to manage resource consumption.

Both agents implement a two-pass tool-calling pattern. In the first pass, the LLM processes the user's message and decides if a tool call is necessary. If a tool is requested, the system executes the tool and then, in a second pass, feeds the tool's results back to the LLM. This allows the LLM to generate a final, informed response, minimizing hallucinations and improving the quality of interaction.

## Design Decisions

The architectural choices for Odys's AI layer reflect a pragmatic approach to balancing performance, cost, and reliability.

The decision to use `chatWithFallback`, which leverages Groq's Llama 3.3 70B as the primary model, is driven by its exceptional inference speed and competitive cost. For conversational agents, low latency is paramount to provide a fluid user experience, especially in real-time messaging contexts like WhatsApp. Groq's specialized hardware accelerates LLM inference, making it an ideal choice for the initial, rapid response generation and tool-calling decisions. The fallback mechanism ensures service continuity even if the primary provider experiences issues.

The **two-pass tool-calling pattern** is a critical design choice for both the WhatsApp Concierge and the Dashboard Assistant. This pattern addresses a common challenge with LLMs: their tendency to sometimes hallucinate tool outputs or struggle with complex multi-step reasoning. By separating the tool invocation from the final response generation, the system gains several advantages:
1.  **Reliability**: The LLM is not asked to predict tool results; it receives actual, verified data.
2.  **Control**: The application maintains control over tool execution, allowing for validation, error handling, and logging (as seen with `AgentLogger` in `ai-intake.ts`).
3.  **Accuracy**: The final response is grounded in concrete facts returned by the tools, leading to more precise and trustworthy answers.
4.  **Token Efficiency**: Tool descriptions are intentionally terse, as noted in `src/lib/ai-intake.ts` comments ("Tool descriptions are intentionally terse... Keeping them short saves tokens on every turn"). This minimizes the token count for the initial prompt, reducing both latency and cost.

The separation of the WhatsApp Concierge (`src/lib/ai-intake.ts`) and the Professional Dashboard Assistant (`src/app/api/ai/chat/route.ts`) into distinct modules and API routes (`/api/ai/chat`) is a deliberate choice for **modularity and clear responsibility**. Each agent has a unique system prompt, a specialized set of tools, and different operational constraints (e.g., public access vs. authenticated access, different rate limits). This separation simplifies development, testing, and maintenance, as changes to one agent's logic or toolset do not directly impact the other. For instance, the concierge's tools are focused on discovery and booking, while the dashboard assistant's tools are centered on data analytics, reflecting their divergent purposes.

The use of Drizzle ORM, as indicated by `pkg.drizzle: "^0.45.2"`, for database interactions provides type safety and a fluent API for building SQL queries. This helps prevent common database-related errors and improves developer productivity when interacting with the 11 tables in the Odys schema.

## Potential Improvements

1.  **Enhanced Fuzzy Matching for Professional Search**: In `src/lib/ai-intake.ts`, the `searchProfessionalsTool` function falls back to an `ilike` (substring) match if `resolveProfessionAlias` fails to find a canonical profession key. While functional, this can lead to less precise results. A more sophisticated fuzzy matching algorithm or a dedicated search index (e.g., using a full-text search engine) could be implemented to handle variations in user input more intelligently, ensuring higher relevance even for misspelled or colloquial profession names.
2.  **Structured Tool Output for Dashboard Assistant**: The `SYSTEM_PROMPT` in `src/app/api/ai/chat/route.ts` includes explicit formatting instructions for "TAXA DE NO-SHOW" and "RESUMO DO MÊS". This places a burden on the LLM to adhere to a specific output structure. Instead, the `getStats` and `getNoShowClients` tools could return more structured data, and a post-processing step could format this data into the desired human-readable output, reducing the LLM's cognitive load and improving consistency.
3.  **Centralized Date Utility for `ai-intake.ts`**: The `ai-intake.ts` file contains several custom date manipulation functions like `saoPauloDate`, `formatSaoPauloTime`, `formatSaoPauloDate`, and `addDaysToDateStr`. While `date-fns` is imported, not all date logic uses it. Consolidating all date and time operations into a single, `date-fns`-based utility module would improve consistency, reduce potential for bugs related to timezone or date arithmetic, and enhance readability.
4.  **Granular Error Logging in `bookAppointment`**: In `src/lib/ai-intake.ts`, the `bookAppointment` function uses `logger.warn("notification_failed", { err: String(err).slice(0, 200) })` for notification failures. While it captures the error, truncating the error message to 200 characters might obscure critical details. Passing the full error object or more specific context (e.g., the `professionalId`, `clientId`, or the specific notification type) to the logger would provide richer diagnostic information for debugging.
