# AI Tool Calling

The Odys platform incorporates artificial intelligence through two distinct agents, each designed to serve different user needs: the WhatsApp Concierge and the Professional Assistant. Both agents leverage a sophisticated tool-calling pattern, allowing them to interact with the underlying Odys system and external services to fulfill user requests. This document delves into the architecture of these AI agents, explaining how tools are defined, implemented, and dispatched, along with the considerations for error handling and potential areas for enhancement.

## Overview

Odys employs a multi-agent architecture where specialized AI personas handle specific domains. The WhatsApp Concierge, defined in `src/lib/ai-intake.ts`, acts as a public-facing agent, assisting clients in discovering professionals, browsing schedules, and booking appointments across the entire marketplace. In contrast, the Professional Assistant, implemented in `src/app/api/ai/chat/route.ts`, provides internal support to professionals, offering insights into their appointments, clients, and revenue.

Both agents follow a "two-pass tool-calling" mechanism:
1.  The Large Language Model (LLM) first analyzes the user's query and decides if a tool call is necessary. If so, it suggests one or more tools and their parameters.
2.  The application executes the suggested tools, feeding their results back to the LLM.
3.  The LLM then generates a final, human-readable response, incorporating the tool outputs into the conversation context.

This separation of concerns allows the LLM to focus on natural language understanding and generation, while the application layer handles the precise execution of business logic and data retrieval.

## Tool Definitions

The tools available to each AI agent are explicitly defined using an OpenAI-compatible schema, which facilitates interoperability with various LLM providers like Groq, Cerebras, and Gemini via the `chatWithFallback` utility. The descriptions for these tools are intentionally kept terse to minimize token usage, as the full `TOOLS` array is sent with every LLM request.

### WhatsApp Concierge Tools (`src/lib/ai-intake.ts`)

The WhatsApp Concierge is equipped with nine distinct tools, enabling a wide range of client interactions:

*   `search_professionals`: Used to find professionals based on criteria such as `profession`, `city`, `name`, and `service_type` (e.g., "online" or "in_person"). This tool is crucial for the initial discovery phase.
*   `list_professions`: Provides a dynamic list of professions that currently have active professionals on the platform, preventing the AI from suggesting unavailable services.
*   `select_professional`: Allows the AI to "focus" the conversation on a specific professional by setting their `professional_id`.
*   `get_professional_info`: Retrieves detailed information about a selected professional, including their `bio`, `address`, `schedule`, `rating`, and `payment_policy`.
*   `get_available_slots`: Fetches real-time appointment slots for a given `professional_id` and `date`, with an optional `time_preference`. It also proactively suggests alternative dates if the requested date has no availability.
*   `book_appointment`: Facilitates the booking of an appointment, requiring `professional_id`, `date`, `time`, `client_name`, and `client_phone`.
*   `list_my_appointments`: Shows future appointments for the current client.
*   `cancel_appointment`: Enables the cancellation of an existing appointment using its `appointment_id`.
*   `reschedule_appointment`: Allows modification of an appointment's `new_date` and `new_time`.

### Professional Assistant Tools (`src/app/api/ai/chat/route.ts`)

The Professional Assistant, accessed via the `/api/ai/chat` route, offers three tools focused on business analytics for the professional:

*   `get_stats`: Provides a comprehensive summary of the last six months, including global and month-by-month breakdowns of total appointments, no-shows, completion rates, and revenue.
*   `get_upcoming`: Lists appointments scheduled for the next seven days, showing client names, dates, and statuses.
*   `get_no_show_clients`: Ranks clients by their no-show count over the last six months, along with their total sessions and individual no-show rates.

## Tool Implementations and Dispatch

The implementation of these tools involves direct interaction with the Drizzle ORM and various utility functions.

In `src/lib/ai-intake.ts`, the `searchProfessionalsTool` queries the `professionals` table, applying filters and then enriching results with `getProStats` for `avgRating`, `reviewCount`, and `completedCount`. It uses `geocodeCity` and `distanceKm` to calculate proximity to a city centroid, influencing the `rankScore` for sorting results. The `bookAppointment` function is particularly complex, executing within a Drizzle `transaction` with a `serializable` isolation level to prevent race conditions. It performs checks for past dates and duplicate bookings, creates new clients if necessary, and handles notifications via `sendWhatsApp` and email utilities, branching logic based on the professional's `autoConfirm` setting. Date and time handling is localized to São Paulo (UTC-3) using custom helpers like `saoPauloDate` and `formatSaoPauloTime`, and `date-fns` for manipulations.

The `src/app/api/ai/chat/route.ts` API route handles the dispatch for the Professional Assistant. After receiving user messages, it constructs a `SYSTEM_PROMPT` to guide the LLM's behavior. The `POST` handler first calls `chatWithFallback` to determine if a tool is needed. If `choice.tool_calls` are present, it iterates through them, executing the corresponding `getStats`, `getUpcoming`, or `getNoShowClients` function. These functions perform Drizzle queries against the `appointments` and `clients` tables, using aggregation functions and `date-fns` utilities like `startOfMonth` and `subMonths` to generate the required analytical data. The results are then stringified and sent back to the LLM for the second pass, allowing it to formulate the final reply.

## Error Handling

Both agents incorporate error handling at various levels. Within tool implementations, specific error objects (e.g., `{ error: string }` or `{ success: false, reason: string }`) are returned to the LLM, allowing it to communicate issues to the user in natural language. For instance, `bookAppointment` explicitly returns `SLOT_TAKEN` or Drizzle-specific error codes like `40001` (serialization failure) or `23505` (unique violation) to indicate booking conflicts. The `chat/route.ts` API also includes general error handling with `serverError` for unexpected issues during the AI interaction.

## Design Decisions

The current design reflects several deliberate choices:

*   **Specialized Agents**: Creating two distinct AI agents, the WhatsApp Concierge and the Professional Assistant, allows for highly tailored prompts and toolsets, optimizing each agent for its specific domain and user base. This avoids a monolithic AI that would struggle with context switching between client-facing and professional-facing tasks.
*   **Terse Tool Descriptions**: The decision to keep tool descriptions short in the `TOOLS` array minimizes token consumption on every LLM call. The expectation is that the main system prompt provides sufficient context for the LLM to understand when and how to use each tool, making verbose descriptions redundant and costly.
*   **Two-Pass Tool Calling**: This pattern separates tool invocation from final response generation. It provides a clear boundary between the LLM's reasoning and the application's execution, making the system more predictable and debuggable. It also allows the LLM to synthesize multiple tool results into a coherent narrative.
*   **Drizzle ORM and `date-fns`**: The use of Drizzle for database interactions provides a type-safe and expressive way to query the `professionals`, `availability`, `appointments`, `clients`, `notifications`, `reviews`, and `agentMetrics` tables. `date-fns` is chosen for its comprehensive and immutable date manipulation capabilities, essential for handling complex scheduling logic and time zone considerations (e.g., São Paulo's UTC-3).
*   **`serializable` Transaction Isolation**: For critical operations like `bookAppointment`, using a `serializable` isolation level ensures the highest degree of data consistency, preventing concurrent bookings from clashing. While this can introduce retries, it prioritizes data integrity for financial and scheduling accuracy.
*   **Dynamic Profession Listing**: The `listProfessionsTool` and `resolveProfessionAlias` ensure that the AI only suggests professions that are actually available on the platform and can understand common Portuguese aliases, improving user experience and reducing dead ends.
*   **Professional Ranking**: The `rankScore` function in `searchProfessionalsTool` combines multiple factors (rating, review count, completed appointments, plan tier, and optional distance) to present the most relevant professionals first, enhancing the quality of search results.

## Potential Improvements

1.  **Centralized Tool Dispatch**: The `if/else if` chain for tool dispatch in `src/app/api/ai/chat/route.ts` and `src/lib/ai-intake.ts` can become unwieldy as more tools are added. A more maintainable approach would be to create a `Map<string, Function>` that maps tool names to their respective implementation functions. This would simplify the dispatch logic and make it easier to add or remove tools.
2.  **Standardized Tool Output Schema**: While tools return structured data, the error handling is somewhat ad-hoc (e.g., `{ error: string }` vs. `{ success: false, reason: string }`). Defining a consistent output schema for all tools, especially for error conditions, could make it easier for the LLM to reliably parse and interpret tool results, leading to more consistent and accurate AI responses.
3.  **Caching for Static Data**: Functions like `listProfessionsTool` and `getProStats` (which is called in `searchProfessionalsTool` and `getProfessionalInfo`) query data that changes infrequently. Implementing a caching layer (e.g., Redis or an in-memory cache with a short TTL) for these results could significantly reduce database load and improve response times for frequently accessed information.
4.  **Enhanced Location Search**: The `searchProfessionalsTool` currently uses `geocodeCity` to find a city centroid for ranking. While effective, it could be improved by allowing users to specify a `neighborhood` or a more precise `near` parameter, which would then be used as the reference point for `distanceKm`, providing more accurate local search results.
