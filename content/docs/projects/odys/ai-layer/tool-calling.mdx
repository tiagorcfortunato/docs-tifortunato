The Odys platform incorporates artificial intelligence agents to enhance user experience, both for clients interacting with a concierge service and for professionals managing their practice. A core component of these agents is the "tool-calling" pattern, which allows the AI to interact with the underlying application logic and data. This document explores the architecture, design choices, and implementation details of how these AI agents define, dispatch, and handle the results of various tools.

## Overview

Odys employs two primary AI agents, each with a distinct purpose and a tailored set of tools:

1.  **WhatsApp Concierge**: Implemented in `src/lib/ai-intake.ts`, this agent serves as a multi-professional discovery and booking assistant. It handles inbound WhatsApp messages on the corporate Odys number, guiding clients through finding professionals, browsing schedules, and booking appointments across the entire marketplace. Its tools are designed for external client interaction, focusing on search, information retrieval, and transactional operations like booking.
2.  **Professional Assistant**: Located at `src/app/api/ai/chat/route.ts`, this agent provides internal support to professionals. Accessible via the `/api/ai/chat` API route, it helps professionals understand their appointments, clients, and revenue by querying their specific data. Its tools are geared towards analytics and reporting, offering insights into practice performance.

Both agents leverage a two-pass tool-calling mechanism, where the Large Language Model (LLM) first suggests a tool call, and then, after the application executes the tool, the LLM generates a final response incorporating the tool's output. This pattern provides a controlled and robust way to integrate AI reasoning with application functionality.

The underlying database schema, managed by Drizzle ORM, provides the data foundation for these tools. Key tables frequently accessed include `professionals` (with 32 columns, including `id`, `name`, `profession`, `sessionDuration`, `sessionPrice`, `city`, `latitude`, `longitude`, and `active`), `availability` (5 columns, linked to `professionals` via `professionalId`), `appointments` (13 columns, tracking `professionalId`, `clientId`, `startsAt`, `endsAt`, and `status`), `clients` (8 columns, with `professionalId`, `name`, and `phone`), `reviews` (7 columns, including `rating` and `comment`), and `agentMetrics` (12 columns, used for logging AI interactions).

## WhatsApp Concierge (`src/lib/ai-intake.ts`)

The `ai-intake.ts` file defines the core logic for the WhatsApp Concierge. This agent is designed to be a comprehensive booking and discovery assistant, capable of navigating the entire Odys professional network.

### Tool Definitions

The `TOOLS` array in `ai-intake.ts` declares 9 distinct tools, each structured as an `OpenAI.Chat.Completions.ChatCompletionTool`. The descriptions for these tools are intentionally terse, such as "Busca pros. SEMPRE antes de listar." for `search_professionals` or "Horários reais. SEMPRE antes de sugerir." for `get_available_slots`. This brevity is a deliberate design choice to minimize token usage on every LLM request, as the entire `TOOLS` array is sent with each turn of the conversation. The prompt itself is responsible for teaching the LLM when and how to use each tool effectively.

Key tools include:

*   `search_professionals`: For finding professionals based on `profession`, `city`, `name`, and `service_type`.
*   `list_professions`: To list available professions with active professionals.
*   `select_professional`: To set the context for a specific professional.
*   `get_professional_info`: To retrieve detailed information about a selected professional.
*   `get_available_slots`: To find real-time availability for booking.
*   `book_appointment`: To create new appointments.
*   `list_my_appointments`: To retrieve a client's upcoming appointments.
*   `cancel_appointment`: To cancel an existing appointment.
*   `reschedule_appointment`: To modify an existing appointment's date and time.

### Tool Implementations

The implementations of these tools interact directly with the Drizzle ORM database layer and other utility functions.

The `searchProfessionalsTool` function, for instance, queries the `professionals` table, applying filters for `serviceType`, `profession` (using `resolveProfessionAlias` for Portuguese terms like "psicologa"), `city`, and `name`. A notable feature is its ranking mechanism: it fetches `getProStats` for each professional and then sorts results using `rankScore`, which considers average rating, review count, completed appointment count, and plan tier. For in-person services, it attempts to `geocodeCity` to find a city centroid and applies a `distanceKm` penalty in the `rankScore` to favor professionals closer to the city's center, even if the user's exact location is unknown. If no matches are found in a specific city, it attempts to find `findNearestProfessionals` in other cities, providing a fallback for the AI to suggest alternatives.

The `getAvailableSlots` function is critical for booking. It first normalizes the `dateStr` using `parsePtDate` to handle natural language inputs like "amanhã". It then calls `computeSlotsForDate` to calculate available slots based on the professional's `availability` rules and existing `appointments`. If no slots are found for the requested date, it proactively looks for alternatives in the next 7 days, returning up to 3 alternative dates with available slots. This reduces conversational turns and improves user experience.

The `bookAppointment` function handles the complex logic of creating an appointment. It performs several checks: validating date/time formats, rejecting past appointments, and checking for existing active appointments for the same client and professional to prevent duplicates. The booking itself occurs within a Drizzle `db.transaction` with `isolationLevel: "serializable"` to prevent race conditions, specifically checking for `SLOT_TAKEN` or database-level unique constraint violations (`23505`) or serialization failures (`40001`). Upon successful booking, it dispatches notifications via `sendWhatsApp` and `sendBookingRequestEmailToProfessional`, adapting the message based on the professional's `autoConfirm` setting. It also computes `paymentInstructions` using `buildPixPayload` if the professional has upfront payment requirements and a PIX key.

Timezone handling is crucial for accurate scheduling. Functions like `saoPauloDate`, `formatSaoPauloTime`, and `formatSaoPauloDate` ensure all date and time operations are correctly localized to "America/Sao_Paulo" (UTC-3), reflecting Brazil's abolition of DST.

## Professional Assistant (`src/app/api/ai/chat/route.ts`)

The `route.ts` file defines the API endpoint for the professional-facing AI assistant, accessible via `/api/ai/chat`.

### System Prompt and Tool Definitions

This agent operates under a `SYSTEM_PROMPT` that explicitly defines its persona ("assistente do Odys"), language ("português"), and strict rule to "Use ferramentas para buscar dados — nunca invente números." It also provides specific formatting instructions for responses related to "TAXA DE NO-SHOW" and "RESUMO DO MÊS".

The `TOOLS` array for this agent is much smaller, containing 3 functions tailored to professional analytics:

*   `get_stats`: Retrieves statistics for the last 6 months, including global and month-by-month summaries of total appointments, no-shows, rates, and revenue.
*   `get_upcoming`: Lists appointments for the next 7 days.
*   `get_no_show_clients`: Ranks clients by their no-show count over the last 6 months.

### API Route Logic

The `POST` handler for `/api/ai/chat` first authenticates the user using `getUser()` and `getProfessional()`. It then applies rate limiting via `getAiChatLimiter().limit(user.id)` (20 requests per hour per user) and checks the professional's subscription plan using `canUseFeature` to ensure they are on a "Pro" or "Premium" plan to access the "assistant" feature.

The core of the handler implements the two-pass tool-calling pattern. It sends the user's messages along with the `SYSTEM_PROMPT` and `TOOLS` to `chatWithFallback` for the first LLM call. If the LLM suggests tool calls, these are executed by an `if/else if` block that dispatches to `getStats`, `getUpcoming`, or `getNoShowClients`. The results are then added back to the message history as `role: "tool"` messages, and a second call to `chatWithFallback` is made to generate the final, human-readable response.

The `getStats` function calculates various metrics by querying the `appointments` table for the last 6 months. It aggregates data to provide both a global summary and a month-by-month breakdown, including `noShowRate` and `revenueBRL` (calculated from `sessionPrice`). `getUpcoming` fetches future appointments, joining with the `clients` table to include client names. `getNoShowClients` performs a grouped query on `appointments` and `clients` to count no-shows and total appointments per client, ranking them by no-show frequency.

## Design Decisions

### Two-Pass Tool Calling

The decision to implement a two-pass tool-calling pattern (LLM suggests tool -> application executes -> LLM generates final response) is a trade-off. It introduces additional latency due to two separate LLM calls per tool interaction. However, this approach offers significant benefits:

*   **Control and Reliability**: It allows the application to fully control tool execution, including input validation, error handling, and complex business logic (like transactional booking or external API calls). This prevents the LLM from directly manipulating the database or external services, enhancing security and data integrity.
*   **Contextual Error Handling**: If a tool execution fails (e.g., a slot is taken, or an invalid ID is provided), the application can inject a structured error message back into the LLM's context. This enables the LLM to gracefully explain the failure to the user and suggest alternative actions, rather than simply returning a generic error.
*   **Complex Logic Injection**: The application can perform operations that are too complex or stateful for the LLM to manage directly, such as the `bookAppointment` transaction with its conflict resolution and notification dispatch.

### Separate Agents and Toolsets

Maintaining distinct AI agents (`ai-intake.ts` for concierge, `route.ts` for professional assistant) with their own `TOOLS` arrays is a deliberate choice to keep each agent focused and efficient.

*   **Reduced Complexity**: Each agent's prompt and tool definitions are specific to its domain, preventing a single, monolithic agent that would be harder to manage and prone to confusion.
*   **Token Efficiency**: By only sending the relevant tool definitions for a given context, token usage is optimized. The concierge doesn't need to know about professional revenue stats, and the professional assistant doesn't need booking tools.
*   **Clearer Responsibilities**: This separation aligns with the principle of single responsibility, making each AI component easier to develop, test, and maintain.

### Terse Tool Descriptions

The concise `description` fields within the `TOOLS` arrays (e.g., "Busca pros. SEMPRE antes de listar.") are a direct optimization for token usage. While more verbose descriptions might theoretically help the LLM understand the tools better, the primary guidance for tool usage is provided within the main system prompt. This approach saves tokens on every API call, reducing operational costs and potentially improving response times.

### Drizzle ORM for Database Interactions

The use of Drizzle ORM provides a type-safe and expressive way to interact with the PostgreSQL database. This choice contributes to code maintainability and reduces the likelihood of SQL injection vulnerabilities or runtime errors due to schema mismatches. The `db.transaction` with `isolationLevel: "serializable"` in `bookAppointment` demonstrates a commitment to data consistency in critical operations.

## Potential Improvements

1.  **Centralized Tool Dispatcher**: Both `src/lib/ai-intake.ts` and `src/app/api/ai/chat/route.ts` contain `if/else if` blocks to dispatch tool calls. This logic could be extracted into a shared utility function or class that maps tool names to their respective implementations. This would reduce duplication, simplify adding new tools, and provide a single point for common tool-related concerns like logging or input validation.
2.  **Enhanced Tool Input Validation**: While some tools perform internal validation (e.g., `bookAppointment` checks date/time formats), a more robust, centralized input validation layer using a schema validation library (like Zod) could be introduced. This would validate tool arguments *before* the tool implementation logic is invoked, providing clearer error messages to the LLM and preventing malformed inputs from reaching the core business logic.
3.  **Caching for `listProfessionsTool`**: The `listProfessionsTool` in `src/lib/ai-intake.ts` queries the `professionals` table to determine active professions on every call. Since the list of active professions is unlikely to change frequently, caching this result (e.g., using an in-memory cache with a short TTL or a Redis cache) could significantly reduce database load and improve response times for this common query.
4.  **Standardized Tool Error Objects**: Currently, tools return `{ error: string }` for failures. A more structured error object (e.g., `{ type: "validation_error" | "resource_not_found" | "conflict", message: string, details?: Record<string, unknown> }`) would allow the LLM to interpret and respond to different error types more intelligently, leading to more nuanced and helpful user interactions.
