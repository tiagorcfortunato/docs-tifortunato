# AI Tool Calling

The Odys platform integrates artificial intelligence to enhance user interactions, both for clients seeking services and professionals managing their practice. A core component of this AI layer is the tool-calling mechanism, which allows the language model to interact with the application's backend systems to retrieve or modify data. This document explores the design and implementation of this pattern, focusing on how tools are defined, executed, and how their results are integrated into the AI's conversational flow.

## Overview

Odys employs two primary AI agents, each tailored to a distinct user persona and set of objectives, yet both leveraging a similar tool-calling architecture.

1.  **WhatsApp Concierge (`src/lib/ai-intake.ts`)**: This agent serves external clients interacting with the corporate WhatsApp number. Its purpose is to facilitate multi-professional discovery, allow clients to browse schedules, and book appointments across the entire marketplace. It operates with a conversation state machine that transitions between discovery and focused modes, allowing users to find professionals by criteria like profession, city, or name, and then proceed to booking.
2.  **Professional Assistant (`src/app/api/ai/chat/route.ts`)**: This agent is designed for authenticated professionals within the Odys application. It helps them understand their business metrics, such as appointments, clients, and revenue. This agent provides insights into past performance and upcoming events, acting as a data analyst for the professional.

Both agents utilize a "two-pass tool-calling" pattern. In the first pass, the Large Language Model (LLM) analyzes the user's query and decides if a tool is necessary. If so, it generates a tool call. In the second pass, the tool is executed, its results are fed back to the LLM, which then generates a final, informed response to the user. This separation allows the LLM to reason about the tool's output before formulating a reply, leading to more accurate and contextually relevant answers.

The underlying data for these tools is managed by a Drizzle ORM schema comprising 11 tables, including `professionals`, `appointments`, `clients`, `availability`, `reviews`, and `agentMetrics`. These tables provide the rich dataset necessary for the AI agents to perform their functions.

## Tool Definitions

Tools are defined using an OpenAI-compatible schema, which allows for flexibility across different LLM providers like Groq, Cerebras, and Gemini via the `chatWithFallback` utility. The descriptions for these tools are intentionally concise to minimize token usage, as the entire `TOOLS` array is sent with each LLM request. The prompt itself is designed to guide the LLM on when to invoke each tool.

### WhatsApp Concierge Tools (`src/lib/ai-intake.ts`)

The `ai-intake.ts` agent defines 9 distinct tools to manage client interactions:

*   `search_professionals`: Used to find professionals based on criteria like `profession`, `city`, `name`, and `service_type` (e.g., "online", "in_person"). This is always the first step before listing professionals.
*   `list_professions`: Provides a list of professions that have active professionals on the platform, preventing the AI from suggesting unavailable services.
*   `select_professional`: Fixes the chosen professional for subsequent interactions, transitioning the conversation state.
*   `get_professional_info`: Retrieves detailed information about a professional, including their bio, address, schedule, and ratings.
*   `get_available_slots`: Fetches real-time availability for a professional on a given `date`, optionally considering a `time_preference`. This is always called before suggesting booking times.
*   `book_appointment`: Schedules an appointment after confirming all necessary details like `professional_id`, `date`, `time`, `client_name`, and `client_phone`.
*   `list_my_appointments`: Lists future appointments for the current client.
*   `cancel_appointment`: Cancels an existing appointment, requiring `appointment_id`.
*   `reschedule_appointment`: Allows rescheduling an appointment to a `new_date` and `new_time`, typically after `get_available_slots` has been used.

### Professional Assistant Tools (`src/app/api/ai/chat/route.ts`)

The `api/ai/chat/route.ts` agent defines 3 tools focused on providing business insights to professionals:

*   `get_stats`: Returns comprehensive statistics for the last 6 months, including global summaries (total appointments, no-shows, rates, revenue) and a month-by-month breakdown. This tool is used for general monthly summaries, no-show rates, and revenue analysis.
*   `get_upcoming`: Fetches appointments scheduled for the next 7 days, providing client names, dates, and times.
*   `get_no_show_clients`: Identifies and ranks clients with the highest number of no-shows over the past 6 months, including individual no-show rates.

## Tool Implementations

Each tool definition is backed by a corresponding asynchronous function that interacts with the database or other services.

### WhatsApp Concierge Implementations

*   **`searchProfessionalsTool`**: This function queries the `professionals` table, applying filters for `serviceType`, `profession` (using `resolveProfessionAlias` for Portuguese terms), `city`, and `name`. It then enriches the results with `getProStats` (fetching average ratings, review counts, and completed appointment counts) and ranks them using `rankScore`. For city-based searches, it attempts to `geocodeCity` to calculate distances and prioritize professionals closer to the city's centroid. If no matches are found in a specific city, it uses `findNearestProfessionals` to suggest alternatives.
*   **`listProfessionsTool`**: This function queries the `professionals` table to identify and return only those professions that have at least one active professional, ensuring the AI suggests viable options.
*   **`getProfessionalInfo`**: This function retrieves a professional's details from the `professionals` table. It concurrently fetches their `availability` rules, `getProStats`, and recent `reviews` from the `reviews` and `clients` tables to provide a comprehensive profile. It also constructs a `payment_policy` and a `profile_url`.
*   **`getAvailableSlots`**: This function orchestrates the slot calculation. It first normalizes the requested `date` using `parsePtDate`. It then calls `computeSlotsForDate` to determine actual available slots based on the professional's `availability` rules and existing `appointments`. Crucially, if no slots are found for the requested date, it proactively checks the next 7 days for `alternatives` to provide a better user experience.
*   **`bookAppointment`**: This is a critical transactional function. It first validates the `date` and `time` and normalizes the `clientPhone`. It includes a pre-check for duplicate active bookings to prevent stacking appointments. The core booking logic runs within a Drizzle transaction with `serializable` isolation to prevent race conditions. It checks for slot conflicts, either creates a new client or finds an existing one, and then inserts the new appointment. Post-booking, it dispatches `notifications` (via `notifications` table, `sendWhatsApp`, and `sendBookingRequestEmailToProfessional`) to both the client and professional, adapting the message based on the professional's `autoConfirm` setting. It also generates `paymentInstructions` and `pix_payload` if applicable, and provides the `appointmentAddress` for in-person services.

### Professional Assistant Implementations

*   **`getStats`**: This function queries all appointments for a given `professionalId` over the last 6 months. It then processes this data to calculate global and per-month summaries, including total appointments, completed sessions, no-shows, cancellation counts, no-show rates, and estimated revenue based on `sessionPrice`.
*   **`getUpcoming`**: This function retrieves appointments for a professional that are scheduled within the next 7 days, joining with the `clients` table to include client names.
*   **`getNoShowClients`**: This function aggregates appointment data for a professional over the last 6 months, grouping by client to count total appointments and no-shows, and then calculates individual no-show rates.

## Two-Pass Tool Calling Mechanism

Both AI agents implement a two-pass tool-calling mechanism:

1.  **First LLM Call**: The initial user message, along with the system prompt and any previous conversation history, is sent to the LLM via `chatWithFallback`. The `tools` array is included, and `tool_choice: "auto"` allows the LLM to decide whether to call a tool.
2.  **Tool Execution**: If the LLM's response (`first.choices[0].message`) contains `tool_calls`, these calls are extracted. The system then iterates through each requested tool, identifies the corresponding implementation function (e.g., `getStats`, `bookAppointment`), and executes it with the provided arguments. The results of these tool executions are captured.
3.  **Second LLM Call**: The original messages, the LLM's tool call request, and the `content: JSON.stringify(result)` of each tool's output are appended to the message history. This augmented history is then sent back to the LLM for a second inference pass. With the tool results now in context, the LLM can formulate a coherent and data-informed final response to the user.

This two-pass approach is crucial for complex interactions, allowing the AI to perform actions and then synthesize the outcomes into natural language.

## Error Handling

Tool implementations are designed to return structured error objects (e.g., `{ error: "Profissional não encontrado" }`) when an operation fails or a resource is not found. These errors are then passed back to the LLM in the second pass, enabling it to communicate specific issues to the user.

For critical operations like `bookAppointment`, specific database errors are caught and translated into user-friendly messages. For instance, a `SLOT_TAKEN` error (either from an application-level check or a Drizzle `unique_violation` with code `23505` or `serialization_failure` with code `40001` during concurrent transactions) results in a message indicating the slot was just filled.

The `/api/ai/chat` route also incorporates rate limiting using `getAiChatLimiter` to prevent abuse, returning a `tooManyRequests()` response if the limit of `20` requests per `1 h` for a given user is exceeded.

## Design Decisions

*   **Specialized Agents**: The decision to create two distinct AI agents (`ai-intake.ts` and `api/ai/chat/route.ts`) reflects a clear separation of concerns. Each agent is optimized for its specific user persona (client vs. professional) and domain (discovery/booking vs. analytics), allowing for tailored prompts, tools, and conversational flows.
*   **Terse Tool Descriptions**: The `description` fields within the `TOOLS` array are kept intentionally short. This is a token-saving measure, as the entire tool schema is sent with every LLM request. The expectation is that the main system prompt provides sufficient context and guidance for the LLM to understand when and how to use each tool.
*   **Two-Pass Tool Calling**: This pattern was chosen to enhance the LLM's reasoning capabilities. By first generating a tool call and then receiving the tool's output before formulating a final response, the LLM can integrate real-world data more effectively, leading to more accurate and contextually rich answers.
*   **Direct Drizzle ORM Interaction**: Tool implementations directly interact with the Drizzle ORM. This provides direct, type-safe access to the database schema, minimizing abstraction layers and ensuring data consistency. For example, `bookAppointment` uses a Drizzle transaction with `serializable` isolation to prevent concurrent booking conflicts.
*   **Brazilian Localization**: Extensive localization support is built into the AI layer, including `normalizeBrazilianPhone`, `parsePtDate`, `parsePtTime`, `formatSaoPauloDate`, `formatSaoPauloTime`, and `resolveProfessionAlias`. This ensures the AI can understand and respond accurately to users in Portuguese, handling local date/time formats and professional aliases.
*   **Proactive Alternatives**: The `getAvailableSlots` tool's ability to suggest alternative dates when the requested date has no availability is a key design choice for improving user experience. Instead of a dead-end "no slots found" response, the AI can immediately offer actionable alternatives, reducing conversational turns.
*   **Comprehensive Notification System**: The `bookAppointment` function integrates multiple notification channels (WhatsApp and email) and adapts messages based on the professional's `autoConfirm` setting. This ensures timely and appropriate communication for both clients and professionals regarding booking status.

## Potential Improvements

1.  **Unified Tool Definition and Dispatch**: The `TOOLS` array and the subsequent `if/else if` dispatch logic are duplicated across `src/lib/ai-intake.ts` and `src/app/api/ai/chat/route.ts`. Creating a shared tool registry or a more generic tool dispatcher could reduce boilerplate, improve maintainability, and ensure consistency in tool definitions and execution across different AI agents.
2.  **Standardized Tool Output Schemas**: While tool outputs are JSON, their structures vary. Implementing explicit Zod schemas for each tool's output (similar to how input parameters are defined) would provide stronger type safety, improve developer experience, and potentially make the LLM's parsing of tool results more reliable. This would be particularly beneficial for complex outputs like those from `searchProfessionalsTool` or `getProfessionalInfo`.
3.  **Asynchronous Notification Handling**: In `bookAppointment` within `src/lib/ai-intake.ts`, the `sendWhatsApp` and `sendBookingRequestEmailToProfessional` calls are `await`ed directly. This means the booking confirmation process is blocked until these external services respond. Moving these notifications to an asynchronous queue (e.g., a background job system) would improve the responsiveness of the `bookAppointment` function, making the booking process faster for the user and more resilient to transient issues with notification providers.
4.  **Rate Limiting for AI Intake Agent**: The `src/app/api/ai/chat/route.ts` agent has a `aichat` rate limit of `20` requests per `1 h` per user, which is a good practice. However, the `src/lib/ai-intake.ts` agent, which handles public-facing WhatsApp interactions, does not appear to have explicit rate limiting in the provided code. Implementing a rate limit for the `ai-intake` agent, perhaps per phone number or IP, could prevent abuse, control LLM costs, and protect against denial-of-service attempts.
