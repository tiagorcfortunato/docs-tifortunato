# AI Tool Calling

The AI layer within Odys empowers large language models (LLMs) to interact with the application's backend services, enabling sophisticated conversational agents. This document explores the design and implementation of the tool-calling pattern, which allows these agents to execute specific functions, retrieve data, and perform actions based on user requests. We will examine two primary agents: the multi-professional discovery and booking concierge (`src/lib/ai-intake.ts`) and the professional assistant (`src/app/api/ai/chat/route.ts`), highlighting their distinct toolsets and operational flows.

## Overview

At its core, the tool-calling mechanism in Odys follows a "two-pass" approach. In the first pass, the LLM receives a user query and a list of available tools, along with their descriptions and parameter schemas. The LLM then decides whether to call a tool and, if so, which one and with what arguments. If a tool call is suggested, the application executes the tool, and the results are fed back to the LLM in a second pass. This second pass allows the LLM to synthesize a coherent, context-aware response to the user, incorporating the information or outcomes from the tool execution. This separation ensures that the LLM's primary role remains conversational generation, while the application handles the deterministic execution of business logic.

The tool definitions themselves adhere to an OpenAI-compatible schema, which is a strategic choice to maintain flexibility and allow for easy switching between different LLM providers, as evidenced by the `chatWithFallback` utility that can use Groq, Cerebras, or Gemini.

## Concierge Agent: `src/lib/ai-intake.ts`

The `ai-intake.ts` file defines the "Odys WhatsApp Concierge," a single AI persona designed to manage all inbound WhatsApp messages on the corporate number. Its primary function is to help clients discover professionals, browse schedules, and book appointments across the entire Odys marketplace.

### Tool Definitions

The concierge agent's capabilities are encapsulated in a `TOOLS` array, which is an array of `OpenAI.Chat.Completions.ChatCompletionTool` objects. Each tool specifies a `name`, a `description`, and a `parameters` schema. The descriptions are intentionally terse, such as "Busca pros. SEMPRE antes de listar." for `search_professionals`, to conserve tokens during each LLM request, as the full `TOOLS` array is sent with every turn.

Key tools include:

*   `search_professionals`: Facilitates finding professionals by `profession`, `city`, `name`, and `service_type` (online/in_person). This tool queries the `professionals` table, applying filters and then enriching results with `getProStats` (for `avg_rating`, `review_count`, `completed_count`) and ranking them using `rankScore`. A notable feature is its fallback mechanism: if no professionals are found in a requested city, it attempts to `geocodeCity` and then `findNearestProfessionals` to suggest alternatives, enhancing user experience.
*   `list_professions`: Returns only professions that have at least one active professional registered, preventing the AI from suggesting unavailable services. This involves querying the `professionals` table and filtering against the `PROFESSIONS` constant.
*   `select_professional`: Allows the AI to "focus" the conversation on a specific professional by setting a `selectedProfessionalId` in the conversation state.
*   `get_professional_info`: Retrieves detailed information about a selected professional, including their `bio`, `address`, `schedule` (from the `availability` table), `rating` (from `reviews`), and `payment_policy`. This tool performs parallel database queries for efficiency.
*   `get_available_slots`: Computes and returns real-time available appointment slots for a given professional and date. It considers the professional's `sessionDuration` and existing `appointments` to avoid conflicts. Crucially, if no slots are found for the requested date, it proactively searches for and suggests slots on the next 7 days, reducing conversational turns. Date parsing (`parsePtDate`, `parsePtTime`) and timezone handling (`saoPauloDate`, `formatSaoPauloTime`, `formatSaoPauloDate`) are critical here, reflecting Brazil's UTC-3 timezone.
*   `book_appointment`: Handles the core booking logic. It performs several checks, including validating the date/time, normalizing the client's phone number, and preventing duplicate active bookings. The booking process is wrapped in a Drizzle `transaction` with `serializable` isolation to ensure data consistency and prevent race conditions when multiple bookings might contend for the same slot. Upon successful booking, it dispatches various notifications via WhatsApp (`sendWhatsApp` with `msgBookingConfirmed`, `msgBookingRequest`, `msgBookingConfirmedReceipt`) and email (`sendBookingRequestEmailToProfessional`), and generates `paymentInstructions` including a PIX payload if applicable.
*   `list_my_appointments`, `cancel_appointment`, `reschedule_appointment`: These tools manage existing appointments for a client, allowing them to view, cancel, or change their bookings.

## Professional Assistant: `src/app/api/ai/chat/route.ts`

The `api/ai/chat/route.ts` file implements an AI assistant specifically for professionals, accessible via the `/api/ai/chat` API route. This assistant helps professionals understand their business data, such as appointments, clients, and revenue.

### Tool Definitions

The professional assistant's `TOOLS` array is tailored to provide business insights:

*   `get_stats`: Provides a comprehensive summary of the professional's business over the last 6 months. This includes global totals for appointments, completed sessions, no-shows, and revenue, along with a month-by-month breakdown. It queries the `appointments` table and calculates metrics based on `appointments.status` and `professional.sessionPrice`.
*   `get_upcoming`: Fetches and lists appointments scheduled for the next 7 days, providing details like client name, date, time, and status by querying `appointments` and joining with `clients`.
*   `get_no_show_clients`: Identifies and ranks clients who have missed the most appointments over the last 6 months. It aggregates data from `appointments` and `clients` to show total appointments, no-shows, and individual no-show rates.

### API Route Logic

The `POST` handler for `/api/ai/chat` orchestrates the interaction:

1.  **Authentication and Authorization**: It first authenticates the user (`getUser`) and verifies they are a professional (`getProfessional`).
2.  **Rate Limiting**: A `getAiChatLimiter` is applied per authenticated user (`user.id`) with a limit of 20 requests per 1 hour, preventing excessive usage and managing LLM costs.
3.  **Plan Guard**: It checks if the professional's subscription plan (`professional.plan`) allows access to the AI assistant feature (`canUseFeature`), enforcing monetization tiers.
4.  **Message Preparation**: User messages are combined with a `SYSTEM_PROMPT` that guides the AI's persona, language, and expected output format, especially for statistical summaries.
5.  **Two-Pass LLM Interaction**: Similar to the concierge, it performs a first `chatWithFallback` call to determine if a tool is needed. If so, the tool is executed (e.g., `getStats`, `getUpcoming`, `getNoShowClients`), and its `JSON.stringify`ed result is added back to the messages. A second `chatWithFallback` call then generates the final, human-readable response.
6.  **Error Handling**: Catches and returns appropriate API errors like `unauthorized`, `forbidden`, `badRequest`, `tooManyRequests`, and `serverError`.

## Design Decisions

*   **Two-Pass Tool Calling**: This architecture separates the LLM's decision-making from the actual execution of business logic. The first pass allows the LLM to "think" about which tool to use, and the second pass provides the LLM with concrete, factual results to formulate a precise answer. This reduces hallucination and gives the application full control over side effects.
*   **OpenAI-Compatible Tool Schema**: By adhering to a widely adopted standard, Odys ensures that its AI agents are not locked into a single LLM provider. The `chatWithFallback` utility demonstrates this flexibility, allowing the system to dynamically choose between providers like Groq, Cerebras, and Gemini based on availability or performance.
*   **Terse Tool Descriptions**: The decision to keep tool descriptions short in the `TOOLS` array is a direct optimization for token usage. Since the entire tool schema is sent with every LLM request, minimizing its size reduces operational costs and potentially improves latency. The LLM is expected to learn the nuances of tool usage from the main system prompt.
*   **Transactional Booking (`bookAppointment`)**: The `bookAppointment` function uses a Drizzle transaction with `serializable` isolation. This is a critical choice for maintaining data integrity in a multi-user system where concurrent booking attempts could lead to double-bookings. The explicit checks for `SLOT_TAKEN` and database-level unique constraint violations (`23505`, `40001`) provide robust conflict resolution.
*   **Proactive Information Retrieval**: Tools like `getAvailableSlots` (suggesting alternative dates) and `searchProfessionalsTool` (suggesting nearest professionals if none are found in the requested city) are designed to anticipate user needs. This reduces the number of conversational turns required, leading to a more efficient and satisfying user experience.
*   **Rate Limiting and Plan Guard**: The `getAiChatLimiter` and `canUseFeature` checks in the professional assistant are essential for managing infrastructure costs associated with LLM usage and enforcing subscription plan benefits. This ensures that AI features are only accessible to eligible users and prevents abuse.

## Potential Improvements

1.  **Centralized Tool Parameter Validation**: While some tools like `bookAppointment` and `getAvailableSlots` perform input validation (e.g., `dateStr` format), this is done ad-hoc within each tool implementation. A more centralized, schema-driven validation layer, perhaps leveraging Zod or similar, could be introduced. This would reduce boilerplate, ensure consistency across all tools, and provide clearer error messages before tool execution in `src/lib/ai-intake.ts` and `src/app/api/ai/chat/route.ts`.
2.  **Asynchronous Notification Dispatch**: In `bookAppointment` within `src/lib/ai-intake.ts`, the `sendWhatsApp` and `sendBookingRequestEmailToProfessional` calls are `await`ed. This means the booking response to the LLM (and subsequently the user) is delayed until all notifications are sent. Moving these notification dispatches to a background job queue (e.g., using a message broker or a dedicated cron job) would allow the `bookAppointment` function to return faster, improving the perceived responsiveness of the AI agent.
3.  **Enhanced `agentMetrics` for Tool Usage**: The `agentMetrics` table currently tracks `toolCallCount`. To gain deeper insights into agent behavior and performance, it could be extended to log the specific `name` of each tool called, its `parameters`, and the `result` (or a summary thereof). This would provide valuable data for debugging, optimizing tool usage, and understanding which tools are most frequently invoked by the LLM in `src/lib/ai-intake.ts` and `src/app/api/ai/chat/route.ts`.
