The AI layer in Odys is designed to augment user experience and professional efficiency through intelligent, conversational interfaces. It comprises two primary agents, each tailored to a specific persona and set of tasks, leveraging advanced language models and a rich suite of custom tools. This architecture allows Odys to handle complex natural language requests, from marketplace discovery and booking to providing detailed business analytics for professionals.

## Overview

Odys employs a dual-agent strategy to address distinct user needs:

1.  **WhatsApp Concierge (`ai-intake.ts`)**: This agent serves external clients interacting with the Odys platform via WhatsApp. Its primary role is to facilitate the discovery of professionals, browse their availability, and manage appointment bookings across the entire marketplace. It operates as a multi-professional discovery and booking agent, guiding clients through a conversation state machine that transitions from general discovery to focused interaction with a selected professional.
2.  **Professional Assistant (`src/app/api/ai/chat/route.ts`)**: This agent is an internal tool for authenticated professionals, accessible via the `/api/ai/chat` endpoint. It helps professionals understand their business data, such as appointments, client behavior, and revenue summaries.

Both agents utilize a two-pass tool-calling mechanism, where the language model first decides if a tool is needed, and then, with the tool's results in context, generates a final, informed response. This approach enhances the reliability and accuracy of AI-driven interactions. The underlying language model infrastructure, managed by `chatWithFallback` in `@/lib/llm`, supports multiple providers like Groq, Cerebras, and Gemini, ensuring resilience and performance. All AI interactions are logged to the `agentMetrics` table, which tracks details like `traceId`, `totalCostUsd`, `totalLatencyMs`, and `toolCallCount`.

## WhatsApp Concierge (`ai-intake.ts`)

The `ai-intake.ts` file defines the core logic for the Odys WhatsApp Concierge. This agent is designed to be a single AI persona handling all inbound WhatsApp messages on the corporate Odys number. It helps clients find professionals by `profession`, `city`, or `name`, browse schedules, and book appointments.

The agent's conversation flow is structured around a state machine:
*   **Discovery**: When no professional is selected, the AI assists in finding one, often calling the `search_professionals` tool.
*   **Focused**: Once a `selectedProfessionalId` is set, the AI focuses on fetching slots or booking appointments for that specific professional.
*   **Reset**: Users can explicitly ask to search for "outro profissional" to clear the current selection and return to discovery.

The Concierge agent is equipped with 9 distinct tools, each designed for a specific interaction:

*   `search_professionals`: The most complex tool, it allows filtering by `profession`, `city`, `name`, and `service_type` (`online` or `in_person`). It incorporates sophisticated logic for resolving profession aliases (e.g., "psicologa" to "psychologist"), geocoding cities, and ranking professionals using a `rankScore` that considers `avgRating`, `reviewCount`, `completedCount`, `plan` tier, and even geographical `distanceKm` from a city centroid.
*   `list_professions`: Provides a list of professions that have at least one active professional registered, preventing the AI from suggesting unavailable services.
*   `select_professional`: Explicitly sets the `selectedProfessionalId` to focus the conversation.
*   `get_professional_info`: Retrieves detailed information about a professional, including `bio`, `address`, `schedule`, `avg_rating`, `review_count`, and `payment_policy`. It also fetches recent review snippets.
*   `get_available_slots`: Crucial for booking, this tool computes actual available time slots for a given professional and date, considering their `availability` rules and existing `appointments`. It also proactively suggests alternative dates if the requested date has no slots.
*   `book_appointment`: Handles the creation of new appointments. It includes robust concurrency checks to prevent double-bookings, creates new client records if necessary, and triggers various notifications (WhatsApp messages to client and professional, email to professional) based on the professional's `autoConfirm` setting. It also generates PIX payment instructions if applicable.
*   `list_my_appointments`: Fetches future appointments for the current client.
*   `cancel_appointment`: Allows clients to cancel an existing appointment.
*   `reschedule_appointment`: Facilitates rescheduling appointments, typically after `get_available_slots` has been used to find new times.

The agent uses specific timezone helpers (`saoPauloDate`, `formatSaoPauloTime`, `formatSaoPauloDate`) to ensure all date and time operations are correctly localized for São Paulo (UTC-3).

## Professional Assistant (`src/app/api/ai/chat/route.ts`)

The Professional Assistant is exposed via the `/api/ai/chat` API route and is designed to provide business insights to professionals. Access to this feature is gated by the user's subscription `plan` and `trialEndsAt` date, requiring at least a "Pro" or "Premium" plan. The endpoint also implements rate limiting per `user.id` using `getAiChatLimiter()` to manage resource consumption.

This agent operates with a `SYSTEM_PROMPT` that instructs it to act as the Odys assistant, helping professionals understand their `appointments`, `clients`, and `revenue`. It is equipped with 3 specialized tools:

*   `get_stats`: Retrieves comprehensive statistics for the last 6 months, including global summaries (total appointments, completed, no-shows, revenue) and a month-by-month breakdown. This tool is used for queries about "Taxa de no-show" or "resumo do mês".
*   `get_upcoming`: Lists appointments scheduled for the next 7 days, providing client names, dates, and statuses.
*   `get_no_show_clients`: Identifies and ranks clients who have missed the most appointments over the last 6 months, detailing their individual no-show rates. This tool is specifically invoked when the professional asks "Quais clientes faltam mais".

The implementation of these tools involves Drizzle ORM queries against the `appointments` and `clients` tables, performing aggregations and filtering to generate the requested business metrics.

## Design decisions

The AI layer's design reflects several deliberate choices:

*   **Specialized Agents**: Creating two distinct agents (`ai-intake.ts` for clients, `src/app/api/ai/chat/route.ts` for professionals) allows for highly tailored `SYSTEM_PROMPT`s and tool sets. This prevents a single, monolithic agent from becoming overly complex or confused by conflicting personas and objectives. The client-facing agent focuses on discovery and booking, while the professional-facing agent focuses on data analysis.
*   **Two-Pass Tool Calling**: Both agents implement a two-pass approach for tool execution. The LLM first generates a response that *might* include tool calls. If tools are called, their results are then injected back into the conversation history, and the LLM makes a second call to generate a final, informed reply. This pattern, explicitly noted in `ai-intake.ts` comments, improves the quality and reliability of responses by giving the LLM concrete data to work with before formulating its final output.
*   **Terse Tool Descriptions**: The `TOOLS` array in `ai-intake.ts` uses intentionally short descriptions (e.g., "Busca pros. SEMPRE antes de listar."). This choice aims to save tokens on every API request, as the entire tool schema is sent with each turn. The expectation is that the `SYSTEM_PROMPT` provides the necessary context and guidance for when to use each tool, making verbose descriptions redundant and costly.
*   **Drizzle ORM for Data Access**: All database interactions within the AI tools use Drizzle ORM. This provides a type-safe and expressive way to query and manipulate data, reducing the likelihood of SQL injection vulnerabilities and improving developer experience compared to raw SQL. The schema, including tables like `professionals`, `availability`, `appointments`, `clients`, `notifications`, `reviews`, and `agentMetrics`, is extensively utilized.
*   **Rate Limiting for API Stability**: The `/api/ai/chat` endpoint implements rate limiting using `getAiChatLimiter()` based on the `user.id`. This is a critical measure to protect the backend from abuse, prevent a single user from incurring excessive LLM costs, and ensure fair usage across all professionals.

## Potential improvements

1.  **Enhanced `agentMetrics` Logging**: The `agentMetrics` table is present in the schema, but the provided `ai-intake.ts` code snippet only shows `logger.warn` calls for notification failures. To gain deeper insights into agent performance and cost, each tool call and the overall conversation flow could explicitly log to `agentMetrics`. This would allow tracking `totalCostUsd`, `totalLatencyMs`, and `toolCallCount` for every interaction, providing a clearer picture of AI usage and efficiency.
2.  **Standardized Tool Output Schema**: Currently, tool results are `JSON.stringify(result)`. While functional, explicitly defining JSON schemas for tool outputs could provide the LLM with more structured and predictable data. This could reduce instances of the LLM misinterpreting tool results or hallucinating information due to ambiguous output formats, especially for complex tools like `searchProfessionalsTool` or `getProfessionalInfo`.
3.  **Centralized Prompt Management**: The `SYSTEM_PROMPT` for the Professional Assistant is hardcoded in `src/app/api/ai/chat/route.ts`, while `ai-intake.ts` references `activePrompt`. Consolidating prompt definitions into a dedicated module or even a database-backed system would allow for easier versioning, A/B testing, and dynamic updates of agent personas and instructions without requiring code deployments. This would improve the agility of iterating on AI behavior.
