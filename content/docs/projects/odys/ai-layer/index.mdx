# AI Layer

Odys incorporates an AI layer designed to automate interactions and provide intelligent assistance, serving both end-users seeking services and professionals managing their practice. This layer is built around two distinct AI agents, each with a specialized persona and set of capabilities, powered by a multi-provider Large Language Model (LLM) setup and an extensive suite of tool-calling functions.

## Overview

The AI layer in Odys is composed of two primary agents:

1.  **WhatsApp Concierge**: Located in `src/lib/ai-intake.ts`, this agent acts as a marketplace-wide assistant for clients interacting via WhatsApp. Its core responsibility is to help users discover professionals, inquire about their services and availability, and book appointments across the entire Odys platform. It operates with a broad view of the `professionals` and `availability` tables, facilitating client-side interactions.
2.  **Professional Assistant**: Implemented in `src/app/api/ai/chat/route.ts`, this agent provides data-driven insights directly to authenticated professionals within their dashboard. It helps professionals understand their `appointments`, `clients`, and revenue trends by querying their specific data.

Both agents utilize an OpenAI-compatible tool-calling interface, allowing the LLM to interact with the Odys backend services and database. The underlying LLM infrastructure, managed by `chatWithFallback`, employs a provider chain (Groq, Cerebras, Gemini) to optimize for cost and latency.

## WhatsApp Concierge Agent

The WhatsApp Concierge agent is the public-facing AI, designed to guide clients through the process of finding and booking a professional. It manages a conversation state machine that transitions between discovery (searching for professionals) and focused interaction (booking with a selected professional).

### Tool Definitions

The agent's capabilities are exposed through a set of `OpenAI.Chat.Completions.ChatCompletionTool` definitions. These tools are intentionally terse in their descriptions to conserve tokens, as the full `TOOLS` array is sent with every LLM request. Key tools include:

*   `search_professionals`: This tool is fundamental for client discovery. It allows the AI to search the `professionals` table based on `profession`, `city`, `name`, and `service_type` (e.g., "online" or "in_person"). It filters for active professionals and can resolve Portuguese profession aliases like "psicologa" to canonical English keys.
*   `list_professions`: Provides a dynamic list of professions that currently have active professionals on the platform, preventing the AI from suggesting unavailable service types.
*   `select_professional`: Allows the AI to "focus" the conversation on a specific professional by setting their `professional_id`.
*   `get_professional_info`: Retrieves detailed information about a selected professional, including their `bio`, `address`, `schedule` (from the `availability` table), `sessionDuration`, `sessionPrice`, and aggregated `reviews` data.
*   `get_available_slots`: Crucial for booking, this tool computes actual available time slots for a given professional and date, considering their `availability` rules and existing `appointments`. It also proactively suggests alternative dates if the requested date has no slots.
*   `book_appointment`: Facilitates the creation of a new `appointment` in the database. It includes logic for checking conflicts, creating new `clients` if necessary, and handling `autoConfirm` settings for professionals.
*   `list_my_appointments`, `cancel_appointment`, `reschedule_appointment`: These tools allow clients to manage their existing appointments.

### Core Logic and Interactions

The `ai-intake.ts` file orchestrates complex interactions:

*   **Database Operations**: It heavily uses Drizzle ORM to query and update tables like `professionals`, `availability`, `appointments`, `clients`, `notifications`, and `reviews`. Transactions with `isolationLevel: "serializable"` are used for `bookAppointment` to prevent race conditions.
*   **Date and Time Handling**: Brazilian timezones are explicitly managed using `saoPauloDate`, `formatSaoPauloTime`, and `formatSaoPauloDate` functions, ensuring accurate scheduling. The `parsePtDate` and `parsePtTime` utilities help interpret natural language date/time inputs.
*   **Geocoding and Ranking**: For `searchProfessionalsTool`, it uses `geocodeCity` to find city centroids and `distanceKm` to calculate distances, influencing the ranking of professionals via `rankScore`. This helps prioritize professionals closer to a user's implied location.
*   **Notifications**: After booking, the agent sends WhatsApp messages using `sendWhatsApp` (e.g., `msgBookingConfirmed`, `msgBookingRequest`) and emails via `sendBookingRequestEmailToProfessional` to both clients and professionals, depending on the `autoConfirm` setting.
*   **Payment Policy**: The `buildPaymentPolicy` function determines payment instructions, including generating PIX payloads for upfront or percentage-based payments.
*   **Metrics**: The agent logs detailed metrics to the `agentMetrics` table, capturing `totalCostUsd`, `totalLatencyMs`, `toolCallCount`, and `outcome` for each conversation, providing valuable insights into AI performance and cost.

## Professional Assistant Agent

The Professional Assistant agent, exposed via the `/api/ai/chat` route, is designed to be an internal tool for professionals. It provides quick access to their business data through a chat interface.

### System Prompt and Tools

The agent's behavior is guided by a `SYSTEM_PROMPT` that instructs it to act as the Odys assistant, focusing on `appointments`, `clients`, and `revenue`. It emphasizes using tools for data retrieval and formatting values in BRL.

The `TOOLS` available to this agent are tailored for business insights:

*   `get_stats`: Retrieves comprehensive statistics for the last six months, including global summaries (total appointments, no-shows, revenue) and a month-by-month breakdown. This tool is used for queries about "Taxa de no-show" or "resumo do mês".
*   `get_upcoming`: Lists appointments scheduled for the next seven days, providing client names, dates, and times.
*   `get_no_show_clients`: Identifies clients with the highest number of no-shows over the past six months, including their individual no-show rates.

### API Route Logic

The `/api/ai/chat` route handles the interaction:

*   **Authentication and Authorization**: It uses `getUser` and `getProfessional` to ensure the request comes from an authenticated professional. A `canUseFeature` check verifies if the professional's `plan` (e.g., "Pro" or "Premium") or `trialEndsAt` date allows access to the AI assistant.
*   **Rate Limiting**: To prevent abuse and control costs, `getAiChatLimiter` applies a rate limit of 20 requests per hour per `user.id`.
*   **Two-Pass Tool Calling**: Similar to the WhatsApp Concierge, this agent also employs a two-pass approach. The first LLM call determines if a tool is needed. If so, the tool is executed, and its JSON result is fed back into a second LLM call to generate the final, human-readable response.
*   **Database Queries**: The tool implementations (`getStats`, `getUpcoming`, `getNoShowClients`) directly query the `appointments` and `clients` tables using Drizzle ORM to aggregate the requested data.

## Design Decisions

*   **Two Dedicated Agents**: The decision to implement two separate AI agents (`ai-intake.ts` and `ai/chat/route.ts`) reflects a clear separation of concerns. The WhatsApp Concierge is designed for public, unauthenticated client interactions across the entire marketplace, while the Professional Assistant is for authenticated, internal professional use, focused on their specific business data. This allows for tailored prompts, toolsets, and access controls for each persona.
*   **Two-Pass Tool Calling**: Both agents utilize a two-pass tool-calling mechanism. This pattern allows the LLM to first decide *if* a tool is necessary and *which* tool to call, then execute that tool, and finally, generate a coherent, natural language response using the tool's output as context. This improves the reliability and quality of responses, especially for complex queries requiring data retrieval.
*   **Terse Tool Descriptions**: The `description` fields for tools are kept intentionally short. This is a token-saving strategy, as the entire tool schema is sent with every LLM request. The expectation is that the main system prompt provides sufficient context for the LLM to understand when to use each tool.
*   **Multi-Provider LLM Fallback**: The `chatWithFallback` utility abstracts away the choice of LLM provider. By chaining providers like Groq, Cerebras, and Gemini, the system gains resilience and can potentially optimize for cost or latency depending on the specific request and provider performance.
*   **Drizzle ORM**: The use of Drizzle ORM across both agents provides a type-safe and expressive way to interact with the PostgreSQL database. This reduces the likelihood of SQL injection vulnerabilities and improves developer experience by providing strong typing for database schemas and queries.
*   **Rate Limiting and Plan Guard for Professional Assistant**: The `/api/ai/chat` route includes explicit rate limiting (`getAiChatLimiter`) and plan-based feature gating (`canUseFeature`). These are critical for managing infrastructure costs associated with LLM usage and enforcing monetization strategies for different subscription tiers.

## Potential Improvements

1.  **Consistent `agentMetrics` Logging**: The `src/lib/ai-intake.ts` agent explicitly uses `createLogger` and `calculateCost` to log detailed metrics to the `agentMetrics` table. The `src/app/api/ai/chat/route.ts` agent, however, does not show explicit logging to `agentMetrics` in the provided code. Implementing similar metric collection for the Professional Assistant would provide a holistic view of AI usage, costs, and performance across both agents.
2.  **Enhanced `searchProfessionalsTool` Location Precision**: The `searchProfessionalsTool` in `src/lib/ai-intake.ts` currently uses `geocodeCity` to find a city's centroid for distance-based ranking. The code comments suggest that "When iter N adds a `near` (neighborhood) parameter, this same path will use that point instead." Implementing this `near` parameter and using it for more precise `distanceKm` calculations would significantly improve the relevance of professional search results for clients specifying neighborhoods.
3.  **Standardized Error Handling for Tool Results**: In `src/lib/ai-intake.ts`, several tool implementations (e.g., `searchProfessionalsTool`, `getAvailableSlots`) return structured error objects like `{ error: string }`. In contrast, the tools within `src/app/api/ai/chat/route.ts` (e.g., `getStats`, `getUpcoming`) do not explicitly return error structures. Adopting a consistent error return format across all tools would allow the LLM to interpret and communicate tool failures more gracefully to the user.
