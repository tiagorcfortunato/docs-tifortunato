# AI Layer

The AI layer in Odys introduces conversational interfaces powered by large language models, enabling both client-facing concierge services and internal professional assistance. This layer is designed around the principle of tool-calling, allowing the AI to interact with the Odys platform's data and external services to fulfill user requests. The primary language model provider is Groq, chosen for its inference speed, with a fallback mechanism to ensure reliability.

## Overview

Odys employs two distinct AI agents, each with a specialized persona and set of capabilities, reflecting the different needs of external clients and internal professionals. Both agents utilize a "two-pass tool-calling" mechanism, where the language model first decides if a tool is needed, executes it, and then uses the tool's output to formulate a final, context-aware response. This approach provides greater control over tool execution and allows for more nuanced replies.

The core of this system relies on an OpenAI-compatible tool definition format, which facilitates interoperability across various language models, including Groq, Cerebras, and Gemini via the `chatWithFallback` utility. This design choice ensures flexibility and resilience in the face of evolving LLM landscapes.

## AI Intake Agent

The `src/lib/ai-intake.ts` file defines the Odys WhatsApp Concierge, a multi-professional discovery and booking agent. This agent serves as the primary interface for clients interacting with the Odys platform through the corporate WhatsApp number. Its purpose is to guide clients through finding a suitable professional, checking their availability, and ultimately booking appointments across the entire marketplace.

The agent maintains a conversation state machine, transitioning between a "Discovery" phase (where it helps clients find professionals based on criteria like profession, city, or name) and a "Focused" phase (once a professional is selected, it assists with scheduling and booking). Clients can "reset" the conversation to clear their selection and search for another professional.

### Tools and Capabilities

The AI Intake Agent is equipped with 9 distinct tools, each designed to perform a specific action or retrieve particular information from the Odys database:

*   `search_professionals`: This tool is fundamental for discovery, allowing the AI to search the `professionals` table based on `profession`, `city`, `name`, and `service_type` (online, in-person, or both). It filters for active professionals and incorporates a ranking system that considers average rating, review count, completed appointment count, and plan tier. For in-person searches, it can also leverage geocoding to find professionals nearest to a requested city's centroid, even if no direct matches are found in that city.
*   `list_professions`: Provides a dynamic list of professions that currently have active professionals on the platform, preventing the AI from suggesting unavailable services. This queries the `professionals` table.
*   `select_professional`: Allows the AI to "focus" the conversation on a specific professional by setting their `professional_id` in the conversation state.
*   `get_professional_info`: Retrieves detailed information about a selected professional, including their `bio`, `address`, `schedule` (from the `availability` table), `avg_rating`, `review_count`, `completed_count` (derived from `reviews` and `appointments`), and `payment_policy`. It also fetches recent review snippets from the `reviews` and `clients` tables.
*   `get_available_slots`: Crucial for scheduling, this tool computes actual available appointment slots for a given professional and date, considering their weekly `availability` rules and existing `appointments`. It also proactively suggests alternative dates if the requested date has no openings.
*   `book_appointment`: Facilitates the creation of new appointments in the `appointments` table. It handles client creation (if new) or lookup (if existing in the `clients` table), checks for time conflicts, and manages the initial `status` and `paymentStatus`. It also triggers notifications (WhatsApp messages using templates like `msgBookingRequest`, `msgBookingConfirmed`, `msgBookingConfirmedReceipt`, and emails via `sendBookingRequestEmailToProfessional`) to both the client and the professional, and generates PIX payment instructions if applicable.
*   `list_my_appointments`: Retrieves future appointments for the current client, querying the `appointments` table.
*   `cancel_appointment`: Allows the AI to cancel an existing appointment.
*   `reschedule_appointment`: Enables rescheduling an appointment, typically after `get_available_slots` has been used to find new times.

### Data Interactions and External Services

The AI Intake Agent interacts extensively with the Odys database schema, primarily using the `professionals`, `availability`, `clients`, `appointments`, `reviews`, and `notifications` tables. It also logs metrics to the `agentMetrics` table. Beyond the database, it integrates with:

*   **WhatsApp**: For sending various templated messages to clients and professionals.
*   **Email**: For sending booking-related notifications to professionals.
*   **Geocoding**: To resolve city coordinates for professional search and ranking.
*   **Payment Processing**: Generates PIX payloads using `buildPixPayload` and constructs payment policies via `buildPaymentPolicy`.

## Professional Assistant Agent

The `src/app/api/ai/chat/route.ts` file implements an internal AI assistant accessible to professionals via the `/api/ai/chat` API route. This agent's persona is tailored to help professionals understand their business data, such as appointments, clients, and revenue.

### Tools and Capabilities

This agent provides 3 specific tools to query a professional's data:

*   `get_stats`: Retrieves comprehensive statistics for the last 6 months, including global summaries (total appointments, completed, no-shows, no-show rate, revenue) and a month-by-month breakdown. This tool queries the `appointments` table.
*   `get_upcoming`: Lists a professional's appointments for the next 7 days, including client names (from the `clients` table), dates, and statuses.
*   `get_no_show_clients`: Identifies and ranks clients who have missed the most appointments over the last 6 months, providing details on total sessions and individual no-show rates. This tool performs an aggregate query on `appointments` and `clients`.

### Access Control and Rate Limiting

Access to the Professional Assistant is restricted:

*   **Authentication**: Requires an authenticated user, who must also be a registered professional.
*   **Plan Guard**: The `canUseFeature` utility ensures that only professionals on "Pro" or "Premium" plans, or those within their trial period, can use this feature.
*   **Rate Limiting**: To manage costs and prevent abuse, the `aichat` rate limiter restricts each authenticated user to 20 requests per 1 hour.

## Design Decisions

### Separation of Agents

The decision to implement two distinct AI agents (`ai-intake.ts` and `ai/chat/route.ts`) stems from their fundamentally different use cases and user bases. The Intake Agent is a public-facing concierge, requiring a broad understanding of the marketplace and client-centric tools. The Professional Assistant, conversely, is an internal tool, needing deep access to a single professional's specific business data and a more analytical persona. Separating them allows for tailored system prompts, toolsets, and access controls, preventing feature creep and maintaining clear responsibilities for each AI persona.

### Groq as Primary LLM with Fallback

Groq is chosen as the primary LLM provider due to its exceptional inference speed, which is critical for conversational interfaces like the WhatsApp Concierge where low latency directly impacts user experience. The `chatWithFallback` utility provides a safety net, allowing the system to gracefully degrade to other LLM providers (Cerebras, Gemini) if Groq experiences issues or rate limits. This design prioritizes both performance and reliability.

### OpenAI-Compatible Tool Definitions

Adopting OpenAI's tool definition format for `TOOLS` arrays in both agents is a strategic choice for portability and future-proofing. This standard is widely supported across various LLM providers, meaning the underlying language model can be swapped or augmented without requiring significant changes to the tool definitions or the tool-calling logic. This reduces vendor lock-in and simplifies integration with new models as they emerge.

### Terse Tool Descriptions

The `description` fields within the `TOOLS` array are intentionally kept brief. This is a token-saving optimization. Since the entire `TOOLS` array is sent with every LLM request, verbose descriptions would unnecessarily increase token consumption and, consequently, cost and latency. The system prompt for each agent is responsible for providing more detailed instructions and context on when and how to use each tool effectively.

### Two-Pass Tool-Calling Mechanism

Both agents employ a two-pass approach for tool execution. In the first pass, the LLM receives the user's message and the available tools, then decides whether to call a tool. If a tool is called, the system executes it, and the tool's output is then injected back into the conversation history. The second pass involves the LLM receiving the original messages, its own tool call, and the tool's result, allowing it to generate a final, informed response. This pattern provides several benefits:

*   **Contextual Responses**: The LLM has the concrete results of the tool execution when formulating its final reply, leading to more accurate and relevant answers.
*   **Error Handling**: It allows the application to intercept and handle tool execution errors (e.g., "slot taken," "professional not found") before the LLM attempts to generate a response, preventing the AI from hallucinating or providing incorrect information.
*   **Complex Workflows**: It supports more complex interactions where the AI might need to process information from a tool before deciding on the next step or formulating a complete answer.

## Potential Improvements

1.  **AI Intake Agent - Enhanced Professional Search and Geocoding**: The `searchProfessionalsTool` currently handles zero results in a specific city by falling back to `findNearestProfessionals`. This involves a second geocoding call if the initial city search fails. Consolidating the geocoding logic and potentially pre-calculating nearest professionals more efficiently could reduce latency and API calls in these fallback scenarios.
2.  **Professional Assistant Agent - Expanded Toolset for Actions**: The current `api/ai/chat` agent is primarily read-only, providing data summaries. Expanding its toolset to include actions like `update_appointment_status` (which is present in the `mcp` facts but not in the `api/ai/chat` code) or `send_message_to_client` could significantly increase its utility for professionals, allowing them to manage their practice more directly through the AI interface.
3.  **AI Intake Agent - Dynamic Payment Integration**: While `bookAppointment` generates PIX instructions, a more direct integration with payment gateways (e.g., initiating a Stripe payment link) could streamline the booking process for clients, especially for professionals requiring upfront payments. This would involve adding a tool to interact with the `/api/stripe/checkout` route.
4.  **Centralized Tool Registry**: As the number of agents and tools grows, managing tool definitions across multiple files (`src/lib/ai-intake.ts`, `src/app/api/ai/chat/route.ts`) could become cumbersome. Implementing a centralized tool registry or a more modular approach for defining and registering tools could improve maintainability and prevent duplication.
