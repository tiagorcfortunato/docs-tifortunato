# AI Layer

Odys integrates artificial intelligence to streamline interactions for both clients seeking services and professionals managing their practice. This layer is built around two distinct AI agents, each tailored to a specific user persona and set of tasks, leveraging advanced language models like Groq and a sophisticated tool-calling mechanism to interact with the Odys platform's data and services.

## Overview

The AI layer in Odys is designed to provide intelligent, conversational interfaces. It comprises two primary agents:

1.  **WhatsApp Concierge (`src/lib/ai-intake.ts`)**: This agent serves as a marketplace-wide assistant, handling inbound WhatsApp messages on the main Odys corporate number. Its core function is to help clients discover professionals, browse their availability, and book appointments across the entire network of `professionals`.
2.  **Professional Assistant (`src/app/api/ai/chat/route.ts`)**: This agent acts as a personal business assistant for individual `professionals`. It helps them understand their practice's performance by providing insights into `appointments`, `clients`, and `revenue` based on their historical data.

Both agents utilize a "two-pass tool-calling" pattern, where the Language Model (LLM) first decides if a tool is needed, and then, with the tool's results in context, generates a final, informed reply. This approach enhances the reliability and accuracy of AI-driven interactions. The system also tracks AI interactions and costs in the `agentMetrics` table, which records details like `traceId`, `promptVersion`, `totalCostUsd`, `totalLatencyMs`, and `toolCallCount`.

## WhatsApp Concierge Agent

The `ai-intake.ts` file defines the logic for the Odys WhatsApp Concierge. This agent is a multi-professional discovery and booking system, designed to guide clients through a conversation flow that can span finding a professional, checking their schedule, and ultimately booking a session.

### Conversation State Machine

The concierge agent manages a simple conversation state machine to adapt its behavior:

*   **Discovery**: Initially, without a `selectedProfessionalId`, the AI focuses on helping the client find a professional. It might ask about the desired profession or location and then use the `search_professionals` tool to present matches.
*   **Focused**: Once a `selectedProfessionalId` is established, the AI's interactions become scoped to that specific professional, allowing it to fetch `availability` slots or `book_appointment`s.
*   **Reset**: A client can explicitly request "outro profissional" to clear the current selection and return to the discovery state.

This state management, combined with the `getConversation` and `saveConversation` utilities, allows for persistent, context-aware dialogues over WhatsApp.

### Tool Definitions and Implementations

The concierge agent is equipped with nine distinct tools, all defined in an OpenAI-compatible format, making them usable with various LLMs like Groq, Cerebras, and Gemini via the `chatWithFallback` utility. The tool descriptions are intentionally terse to conserve tokens, as the system prompt guides the LLM on their appropriate usage.

Key tools include:

*   `search_professionals`: This tool queries the `professionals` table, filtering by `profession`, `city`, `name`, and `serviceType`. It incorporates a ranking mechanism using `getProStats` and `rankScore` to prioritize professionals based on `avgRating`, `reviewCount`, `completedCount`, and `plan` tier. For in-person services, it can also apply a distance penalty using `geocodeCity` and `distanceKm` to favor professionals closer to a city's centroid. If no professionals are found in a requested city, it attempts to find `nearestProfessionals` in surrounding areas.
*   `list_professions`: This tool dynamically lists only those professions that have at least one active professional registered in the `professionals` table, preventing the AI from suggesting unavailable service types.
*   `select_professional`: This simple tool updates the conversation state to focus on a specific professional by their `professional_id`.
*   `get_professional_info`: Retrieves detailed information about a professional from the `professionals` table, including their `bio`, `address`, `schedule` (from `availability`), `avg_rating`, `review_count`, `completed_count` (from `getProStats`), `payment_policy` (from `buildPaymentPolicy`), and recent `reviews` (from the `reviews` and `clients` tables).
*   `get_available_slots`: This critical tool calculates available appointment slots for a given `professionalId` and `date`.
*   `book_appointment`: This tool orchestrates the booking process.
*   `list_my_appointments`, `cancel_appointment`, `reschedule_appointment`:
The agent also includes timezone helpers (`saoPauloDate`, `formatSaoPauloTime`, `formatSaoPauloDate`) to correctly handle Brazilian time, which is consistently UTC-3 since DST abolition.

## Professional Assistant Agent

The `src/app/api/ai/chat/route.ts` route implements the AI assistant for `professionals`. This assistant is designed to provide business insights and help professionals manage their practice more effectively through a conversational interface.

### System Prompt and Tools

The agent's behavior is guided by a `SYSTEM_PROMPT` that establishes its persona as the "assistente do Odys" and sets expectations for language (Portuguese), tool usage, and specific output formatting for statistics like no-show rates and monthly summaries.

It uses three specialized tools:

*   `get_stats`: This tool fetches comprehensive statistics for the professional over the last six months. It queries the `appointments` table to calculate global and month-by-month summaries, including `totalAppointments`, `completed` sessions, `noShows`, `noShowRate`, and `revenueBRL` (derived from `sessionPrice`).
*   `get_upcoming`: This tool retrieves a list of `appointments` scheduled for the next seven days, including client names and appointment times, by querying the `appointments` and `clients` tables.
*   `get_no_show_clients`: This tool identifies and ranks `clients` who have the highest number of `no_show` appointments in the last six months, providing `totalAppointments`, `noShows`, and `noShowRate` for each client.

### Access Control and Rate Limiting

Access to the professional assistant is carefully controlled:

*   **Authentication**: The `getUser()` and `getProfessional()` helpers ensure that only authenticated and registered `professionals` can use the assistant.
*   **Plan Guarding**: The `canUseFeature()` utility checks the professional's `plan` and `trialEndsAt` date, restricting access to users on "Pro" or "Premium" plans, or those within a valid trial period.
*   **Rate Limiting**: A dedicated `getAiChatLimiter()` is applied per authenticated `user.id` (not per IP address). This prevents a single professional from inadvertently or maliciously exhausting the LLM budget by making too many requests, with a limit of 20 requests per hour.

Similar to the concierge, this agent also uses the two-pass tool-calling pattern to ensure that tool outputs are properly integrated into the final response.

## Design Decisions

The AI layer's architecture reflects several deliberate design choices:

*   **Agent Specialization**: Creating two distinct agents, one for client-facing concierge services (`ai-intake.ts`) and another for professional business insights (`src/app/api/ai/chat/route.ts`), allows for highly tailored prompts, toolsets, and access controls. This separation of concerns prevents a monolithic AI that might struggle to balance conflicting objectives or personas.
*   **Two-Pass Tool Calling**: The explicit two-pass approach (LLM requests tool, tool executes, LLM generates final reply with tool output) is a common pattern for improving the reliability of tool use. It gives the LLM a chance to "think" about the tool's output before formulating a user-facing response, reducing hallucinations and improving the quality of answers.
*   **Terse Tool Descriptions**: The `TOOLS` arrays in both agents use minimal descriptions. This choice prioritizes token efficiency, as the entire tool schema is sent with every LLM request. The system relies on comprehensive system prompts to guide the LLM on *when* to use each tool, rather than verbose in-tool descriptions.
*   **Drizzle ORM for Database Interactions**: The use of Drizzle ORM provides type safety and a fluent API for building SQL queries. This reduces the likelihood of runtime errors and makes database interactions more maintainable, as seen in complex queries within `searchProfessionalsTool` and `getStats`.
*   **Proactive Information Retrieval**: Tools like `get_available_slots` proactively fetch "alternative dates" if the initial query yields no results. Similarly, `bookAppointment` includes `paymentInstructions` and `appointmentAddress` in its return. This design minimizes round-trips between the LLM and the user, allowing the AI to provide a more complete and helpful response in a single turn.
*   **Robust Booking Logic**: The `bookAppointment` tool employs a Drizzle transaction with `serializable` isolation and multiple conflict checks (past dates, existing appointments, concurrent bookings) to ensure data integrity and prevent double-bookings, which is critical for a scheduling system.
*   **Rate Limiting and Plan-Based Access**: Implementing `getAiChatLimiter` and `canUseFeature` directly within the API routes (`src/app/api/ai/chat/route.ts`) is a pragmatic way to manage operational costs associated with LLM usage and to enforce feature gating based on subscription plans.

## Potential Improvements

1.  **Enhanced Profession Matching in `searchProfessionalsTool`**: In `src/lib/ai-intake.ts`, the `searchProfessionalsTool` falls back to an `ilike` (substring match) on `professionals.profession` if `resolveProfessionAlias` doesn't find a direct match. While pragmatic, this could lead to less precise search results or missed opportunities for more nuanced aliases. An improvement could involve integrating a more sophisticated fuzzy matching algorithm or expanding the `resolveProfessionAlias` dictionary to cover a wider range of Portuguese terms and common misspellings, providing more accurate initial search results.
2.  **Dynamic Alternative Slot Search in `getAvailableSlots`**: This fixed window might not always align with user preferences or professional availability. A potential enhancement would be to make this search more dynamic, perhaps by allowing the LLM to specify a longer lookahead if the user expresses flexibility, or by prioritizing specific days of the week if the user indicates a preference (e.g., "Can you find me something on a Tuesday, even next month?").
3.  **Refined Revenue Calculation in `getStats`**: The `getStats` function in `src/app/api/ai/chat/route.ts` calculates `revenueBRL` based on `completed` appointments multiplied by the professional's `sessionPrice`. This assumes all completed appointments are paid at the full standard price. If Odys introduces features like discounts, variable session pricing, or partial payments, this calculation would become inaccurate. An improvement would be to fetch actual payment records or integrate a more granular pricing model into the `appointments` table (e.g., an `actualPricePaid` column) to ensure the revenue figures provided by the AI assistant are precise.
