# AI Layer

The AI layer in Odys introduces intelligent agents to streamline interactions for both clients and professionals. This system is built around the concept of tool-calling, allowing large language models (LLMs) to interact with the application's backend services and database to retrieve or manipulate data. The current implementation features two distinct agents, each tailored to a specific user persona and set of tasks, powered by a flexible LLM provider chain that includes Groq, Cerebras, and Gemini via the `chatWithFallback` utility.

## Overview

Odys employs two primary AI agents, each serving a distinct purpose and audience:

1.  **WhatsApp Concierge (`ai-intake.ts`)**: This agent acts as a public-facing assistant, handling inbound WhatsApp messages on the main Odys corporate number. Its core function is to help clients discover professionals across the entire marketplace, browse their schedules, and book appointments. It operates with a broader scope, facilitating client-to-professional matching and booking.
2.  **Professional Assistant (`src/app/api/ai/chat/route.ts`)**: This agent is an internal tool for professionals, accessible via the `/api/ai/chat` endpoint. It provides professionals with insights into their own business, such as appointment statistics, client no-show rates, and upcoming schedules. Its scope is limited to the data of the authenticated professional.

Both agents utilize an OpenAI-compatible tool-calling interface, allowing them to execute predefined functions to interact with the Odys database and external services. This architecture enables the LLM to perform complex, multi-step operations by chaining tool calls and generating natural language responses based on the results.

## WhatsApp Concierge (`src/lib/ai-intake.ts`)

The `ai-intake.ts` module defines the Odys WhatsApp Concierge, a sophisticated agent designed to guide clients through the process of finding and booking appointments with professionals. This agent manages a conversation state machine, transitioning between discovery (when no professional is selected) and a focused mode (when a professional is chosen).

The agent's capabilities are exposed through a set of nine distinct tools, each with a specific function:

*   `search_professionals`: This tool is fundamental for client discovery. It queries the `professionals` table, allowing searches by `profession`, `city`, `name`, and `service_type` (online, in-person, or both). It incorporates a ranking system using `getProStats` and `rankScore` to prioritize results based on average rating, review count, completed appointments, and plan tier. For location-based searches, it can use `geocodeCity` to find a city's centroid and `distanceKm` to penalize distant professionals, even offering `findNearestProfessionals` as a fallback if no local matches are found.
*   `list_professions`: This tool dynamically lists only those professions that have at least one active professional registered in the `professionals` table, preventing the AI from suggesting unavailable services.
*   `select_professional`: This tool allows the AI to "focus" the conversation on a specific professional by setting their `professional_id` in the conversation state.
*   `get_professional_info`: Once a professional is selected, this tool fetches detailed information from the `professionals` table, including their `bio`, `addressLine`, `sessionDuration`, `sessionPrice`, and `serviceType`. It also retrieves `availability` rules, `reviews` (joining with `clients` for client names), and `getProStats` for social proof.
*   `get_available_slots`: This critical tool calculates actual available appointment slots for a given `professionalId` and `date`. It considers the professional's `availability` rules and existing `appointments` to prevent conflicts. If no slots are found for the requested date, it proactively searches for alternatives in the next seven days.
*   `book_appointment`: This tool handles the core booking logic. It creates a new entry in the `appointments` table, linking it to a `professionalId` and a `clientId` (creating a new client in the `clients` table if necessary). It includes checks for past dates, duplicate bookings, and concurrent slot filling using Drizzle's transaction capabilities with `serializable` isolation. Upon successful booking, it triggers notifications via WhatsApp (`sendWhatsApp` using templates like `msgBookingConfirmed` or `msgBookingRequest`) and email (`sendBookingRequestEmailToProfessional`), and generates `notifications` records. It also computes `payment_policy` and `pix_payload` if applicable.
*   `list_my_appointments`: This tool retrieves future appointments for the current client.
*   `cancel_appointment`: This tool updates the status of an existing appointment in the `appointments` table.
*   `reschedule_appointment`: This tool allows modifying an existing appointment's date and time, typically after `get_available_slots` has been used to find new suitable times.

The agent employs a "two-pass tool-calling" mechanism: the LLM first decides if a tool is needed, and if so, executes it. The results are then fed back into the LLM's context for a second pass, allowing it to generate a coherent, informed final reply. This approach helps the AI to reason over tool outputs before formulating a user-facing message.

## Professional Assistant (`src/app/api/ai/chat/route.ts`)

The `src/app/api/ai/chat/route.ts` file defines the API endpoint for the Professional Assistant. This agent is designed to provide professionals with quick access to their business data through a conversational interface. It is secured by `getUser` and `getProfessional` checks, ensuring that only authenticated professionals can access their specific data. Access to this feature is also gated by the `canUseFeature` utility, requiring a "Pro" or "Premium" plan.

This agent uses a more focused set of three tools:

*   `get_stats`: This tool retrieves comprehensive statistics for the professional over the last six months. It queries the `appointments` table to calculate global and month-by-month summaries of total appointments, completed sessions, no-shows, no-show rates, and estimated revenue based on the professional's `sessionPrice`.
*   `get_upcoming`: This tool fetches a list of appointments scheduled for the next seven days, joining `appointments` with `clients` to display client names.
*   `get_no_show_clients`: This tool identifies clients with the highest number of no-shows over the past six months, querying `appointments` and `clients` to provide a ranking with individual no-show rates.

A rate limit (`aichat` with `20` requests per `1 h`) is applied per authenticated user (`user.id`) to prevent abuse and manage LLM costs. Similar to the Concierge, this agent also uses a two-pass tool-calling approach to ensure that tool results are properly integrated into the final response.

## Design decisions

The architecture of the AI layer reflects several deliberate design choices:

*   **Separation of Concerns**: Two distinct agents (`ai-intake.ts` and `src/app/api/ai/chat/route.ts`) were created to serve different user types (clients vs. professionals) and use cases (discovery/booking vs. business analytics). This separation allows each agent to have a highly specialized prompt, toolset, and data access patterns, reducing complexity and improving the relevance of responses for each persona.
*   **Two-Pass Tool-Calling**: Both agents implement a two-pass tool-calling mechanism. The LLM first generates a tool call, and only after the tool's output is available does it generate the final user-facing response. This design choice provides the LLM with the full context of the tool's execution, including any errors or specific data, before formulating its reply. This helps prevent "hallucinations" about tool results and allows for more nuanced, data-driven conversations.
*   **Terse Tool Descriptions**: The `description` fields for the tools are intentionally kept short (e.g., "Busca pros. SEMPRE antes de listar."). This is a token-saving optimization. The expectation is that the main system prompt provides the detailed instructions and examples for when and how to use each tool, making the verbose descriptions in the tool schema redundant and costly on every LLM call.
*   **Flexible LLM Provider Chain**: The use of `chatWithFallback` in `src/lib/llm` allows the system to dynamically switch between different LLM providers (Groq, Cerebras, Gemini). This provides resilience and cost optimization, ensuring that conversations can continue even if one provider experiences issues or if a more cost-effective option is available for certain types of requests.
*   **Database Interaction via Drizzle**: All database operations within the tools are performed using Drizzle ORM. This provides type safety and a consistent interface for interacting with the PostgreSQL database, abstracting raw SQL queries and improving developer experience. The use of `serializable` isolation for `bookAppointment` transactions is a critical choice to prevent race conditions during concurrent booking attempts.

## Potential improvements

1.  **Optimizing `getAvailableSlots` Database Calls**: In `src/lib/ai-intake.ts`, the `getAvailableSlots` function, when finding no slots for a requested date, iterates through the next seven days, calling `computeSlotsForDate` for each. Each `computeSlotsForDate` call then re-queries the `availability` table for the professional's rules. To reduce database load, the professional's `availability` rules could be fetched once at the beginning of `getAvailableSlots` and then passed as an argument to `computeSlotsForDate` for each date calculation.
2.  **Database-level Aggregation in `getStats`**: The `getStats` function in `src/app/api/ai/chat/route.ts` fetches all appointments for the last six months and then performs in-memory filtering and aggregation to build per-month summaries. For professionals with a high volume of appointments, or if the reporting period were to be extended, this could become inefficient. Drizzle's SQL aggregation functions could be used to perform the monthly grouping and counting directly within the database query, offloading computation to the database and reducing the amount of data transferred.
3.  **Robust Notification Delivery**: The `bookAppointment` function in `src/lib/ai-intake.ts` sends WhatsApp messages and emails using `sendWhatsApp` and `sendBookingRequestEmailToProfessional` with `.catch()` blocks for error logging. While this logs failures, it does not guarantee delivery or provide retry mechanisms. For critical notifications, integrating a dedicated message queue or a more robust notification service could ensure higher reliability and better error handling, such as automatic retries or dead-letter queues.
