# WhatsApp AI Intake

The `ai-layer/whatsapp-intake` component serves as the central intelligence for handling all inbound WhatsApp messages directed to the corporate Odys number. It acts as a multi-professional discovery and booking agent, guiding clients through finding a suitable professional, browsing their availability, and ultimately scheduling appointments across the entire marketplace. This agent operates with a single AI persona, ensuring a consistent user experience regardless of the client's specific needs.

## Overview

The core of this system is an AI agent designed to manage complex conversational flows. It leverages a "two-pass tool-calling" mechanism: the Large Language Model (LLM) first determines if a tool is needed, and then, with the tool's results in context, formulates the final reply. This approach allows the LLM to plan its actions and integrate external information effectively. The agent uses a fallback chain of LLM providers, including Groq, Cerebras, and Gemini, orchestrated by the `chatWithFallback` utility.

Conversation state is managed using Redis, allowing the agent to maintain context across multiple turns. The `ConversationState` object, stored in Redis, tracks details like the client's phone number, name, and crucially, a `selectedProfessionalId` to indicate when the conversation has narrowed its focus to a specific professional. This state also includes a history of `messages` and a `context` object for transient information like `pendingDate` or `userCity`.

Database interactions are handled via Drizzle ORM, querying tables such as `professionals`, `availability`, `appointments`, `clients`, `notifications`, `reviews`, and `agentMetrics`. These interactions are fundamental for searching professionals, checking schedules, creating bookings, and logging agent performance.

The entry point for inbound WhatsApp messages is expected to be an API route, likely `/api/whatsapp/webhook`, which would receive messages and pass them to this AI intake logic for processing.

### Timezone Helpers

Given that Odys operates in Brazil, the system includes specific utilities for handling the "America/Sao_Paulo" timezone, which is consistently UTC-3 since Brazil abolished Daylight Saving Time in 2019. Functions like `saoPauloDate`, `formatSaoPauloTime`, and `formatSaoPauloDate` ensure that all date and time operations, especially those related to appointment scheduling, are accurately represented in the local time of São Paulo. This prevents common timezone-related bugs and ensures clarity for both professionals and clients.

### Tool Definitions

The AI agent's capabilities are exposed through a set of OpenAI-compatible function `TOOLS`. These tools are intentionally designed with terse descriptions to minimize token usage on every LLM request, as the entire `TOOLS` array is sent with each turn. The prompt itself is responsible for teaching the LLM when and how to use each tool.

The defined tools include:

*   **`search_professionals`**: Used to find professionals based on criteria like `profession`, `city`, `name`, and `service_type` (online, in-person, or both).
*   **`list_professions`**: Provides a list of professions that have at least one active professional on the platform, preventing the AI from suggesting unavailable services.
*   **`select_professional`**: Sets the `selectedProfessionalId` in the conversation state, focusing the AI's subsequent actions on a specific professional.
*   **`get_professional_info`**: Retrieves detailed information about a professional, including their bio, address, schedule, ratings, and payment policy.
*   **`get_available_slots`**: Fetches real-time available appointment slots for a given professional and date, with an option for `time_preference`. It also suggests alternative dates if the requested date has no availability.
*   **`book_appointment`**: Creates a new appointment after confirming details with the client.
*   **`list_my_appointments`**: Lists future appointments for the current client.
*   **`cancel_appointment`**: Cancels an existing appointment.
*   **`reschedule_appointment`**: Modifies an existing appointment to a new date and time.

### Tool Implementations

Each tool definition is backed by a corresponding implementation that interacts with the database and other services:

*   **`searchProfessionalsTool`**: This function queries the `professionals` table, filtering by `active` status and applying conditions from the arguments. It uses `resolveProfessionAlias` to map common Portuguese terms (e.g., "psicologa") to canonical English profession keys. For ranking, it fetches `avgRating`, `reviewCount`, and `completedCount` using `getProStats`. If a `city` is provided and multiple matches are found, it attempts to `geocodeCity` to find the city's centroid and applies a distance penalty in the `rankScore` calculation, favoring professionals closer to the city center. If no professionals are found in a specific city, it falls back to `findNearestProfessionals` to suggest options in nearby locations.
*   **`listProfessionsTool`**: This implementation queries the `professionals` table to identify all distinct `profession` values for active professionals, ensuring that the AI only suggests professions that are actually available on the platform.
*   **`getProfessionalInfo`**: This function performs parallel database queries to fetch a professional's details from the `professionals` table, their `availability` rules, and recent `reviews` from the `reviews` and `clients` tables. It then formats this information, including a human-readable schedule, a concatenated address, and a summary of social proof (average rating, review count). It also integrates `buildPaymentPolicy` to inform the client about payment terms.
*   **`getAvailableSlots`**: This function first normalizes the `dateStr` input, attempting to parse natural language dates like "amanhã" using `parsePtDate`. It then calls `computeSlotsForDate` to determine raw availability based on the professional's `availability` rules and existing `appointments`. `computeSlotsForDate` iterates through potential slots, checking for conflicts with already booked appointments and ensuring slots are in the future. If no slots are found for the requested date, `getAvailableSlots` proactively checks the next 7 days to suggest up to three alternative dates with available slots.
*   **`bookAppointment`**: This is a critical function that orchestrates the creation of a new appointment. It operates within a Drizzle `db.transaction` with `serializable` isolation to prevent race conditions, especially when multiple clients might try to book the same slot concurrently. It first checks for existing active appointments for the same client and professional to prevent duplicates. Inside the transaction, it checks for slot conflicts, either creates a new client entry in the `clients` table or retrieves an existing one, and then inserts the new appointment into the `appointments` table. The `status` of the appointment (`confirmed` or `pending_confirmation`) depends on the professional's `autoConfirm` setting. After a successful booking, it triggers a series of notifications: an entry in the `notifications` table, WhatsApp messages to both the client and professional (using templates like `msgBookingConfirmed` or `msgBookingRequest`), and an email to the professional. It also generates `paymentInstructions` and `appointmentAddress` if applicable, to be included in the AI's reply.

### Conversation State Management

The `src/lib/conversation.ts` module is responsible for managing the state of each WhatsApp conversation in Redis.

*   **`ConversationState`**: This interface defines the structure of the data stored for each conversation, including `clientPhone`, `clientName`, `selectedProfessionalId`, a history of `messages`, and a `context` object. A `version` field is included for optimistic concurrency control.
*   **`getConversation` and `saveConversation`**: These functions retrieve and persist the `ConversationState` to Redis. `saveConversation` implements optimistic concurrency: if the `version` in the in-memory state does not match the `version` in Redis, a `ConversationStaleError` is thrown. This prevents a later write from silently overwriting changes made by a concurrent process. Conversations are stored with a `TTL` of 30 minutes, and the `messages` array is capped at `MAX_MESSAGES` (12) to manage context window size and token costs.
*   **`acquireMessageLock` and `releaseMessageLock`**: To prevent race conditions when multiple messages from the same phone arrive in quick succession, a per-phone processing lock is used. This lock ensures that only one message from a given client is processed by the AI at a time, maintaining deterministic state transitions. The lock has a `LOCK_TTL` of 45 seconds, designed to cover the slowest LLM round-trip. It is designed to "fail open" on Redis errors, prioritizing message processing over strict locking in case of cache layer issues.
*   **`markClientActive` and `isClientActive`**: A `client_active` key is set in Redis with an `ACTIVE_TTL` of 15 minutes whenever a conversation is saved. This mechanism allows cron jobs, such as `/api/cron/reminders`, to check if a client is currently engaged in a conversation with the AI. If active, transactional reminders are deferred to avoid interrupting an ongoing dialogue.
*   **`setOutboundContext` and `getOutboundContext`**: These functions store and retrieve `OutboundContext` for transactional messages sent to the client. This context, which includes `professionalId` and `appointmentId`, is stored with an `OUTBOUND_TTL` of 2 hours and can be used to link subsequent client replies to specific prior interactions.

## Design Decisions

*   **Two-Pass Tool Calling**: The decision to use a two-pass approach for tool calling (LLM requests tool, then LLM generates reply with tool results) allows the AI to reason about the outcome of a tool call before formulating a user-facing response. This improves the quality and relevance of the AI's replies, as it can incorporate real-time data from the tools.
*   **Terse Tool Descriptions**: The `TOOLS` array uses minimal descriptions to save tokens. This is a direct trade-off between LLM understanding (which might benefit from more verbose descriptions) and operational cost, as the entire tool schema is sent with every LLM request. The prompt is relied upon to provide the necessary context for tool usage.
*   **Optimistic Concurrency for Conversation State**: The `version` field and `ConversationStaleError` in `src/lib/conversation.ts` are crucial for maintaining data integrity in a distributed environment. This design prevents a stale `ConversationState` from overwriting a newer version, which could lead to lost conversational turns or incorrect state.
*   **Per-Phone Message Lock**: The `acquireMessageLock` mechanism is a pragmatic choice to prevent race conditions and non-deterministic behavior when a client sends multiple WhatsApp messages rapidly. While a small TOCTOU (Time-of-Check to Time-of-Use) window exists, the lock significantly reduces the likelihood of concurrent processing and state corruption. Its "fail open" design prioritizes availability over strict consistency in the face of Redis outages.
*   **Brazil-Specific Timezone Handling**: Hardcoding UTC-3 for São Paulo and providing dedicated timezone helpers simplifies date and time calculations, eliminating the complexities of dynamic DST rules. This ensures that appointment times are always correctly interpreted and displayed to users in the local context.
*   **Profession Alias Resolution**: The `resolveProfessionAlias` utility is a user-centric design choice. It allows clients to use natural language and common Portuguese terms for professions, reducing friction and improving the success rate of professional searches, rather than requiring them to know canonical English keys.
*   **Professional Ranking**: The composite `rankScore` in `searchProfessionalsTool` (considering rating, popularity, plan tier, and optional distance) provides a nuanced way to present search results. It balances objective metrics with business logic (plan tier) and user convenience (proximity), offering a more relevant list of professionals.
*   **Transactional Booking**: The use of `db.transaction` with `serializable` isolation for `bookAppointment` is a critical decision for data consistency. It ensures that appointment slots are reserved atomically, preventing double-bookings and maintaining the integrity of the schedule even under concurrent load.

## Potential Improvements

1.  **Enhanced Tool Descriptions**: While terse tool descriptions save tokens, they might occasionally lead to LLM misinterpretations. Experimenting with slightly more descriptive tool descriptions, perhaps with examples, could improve LLM accuracy and reduce the need for extensive prompt engineering, even if it incurs a minor increase in token cost. This could be A/B tested to measure the trade-off.
2.  **Standardized Date/Time Input for Tools**: The `getAvailableSlots` and `bookAppointment` tools include defensive parsing for natural language dates (`parsePtDate`, `parsePtTime`). While helpful, standardizing the LLM's output to ISO 8601 (`YYYY-MM-DD`, `HH:mm`) for date and time parameters would simplify tool implementations and reduce potential parsing errors. The prompt could be refined to strictly enforce this format.
3.  **Unified Error Handling for Booking Conflicts**: The `bookAppointment` function currently throws a custom `SLOT_TAKEN` error and also catches Drizzle-specific error codes (`40001`, `23505`). Consolidating these into a more generic, application-level error type (e.g., `BookingConflictError`) would make error handling more consistent and easier to manage across the codebase.
4.  **`ConversationStaleError` Reconciliation**: When a `ConversationStaleError` occurs in `saveConversation`, the current behavior is to abort the save. Since the AI's reply has likely already been sent, this means a turn is lost from the persisted history. For critical conversations, exploring strategies to reconcile the state (e.g., merging messages, re-attempting the save with the latest version, or logging the discrepancy for manual review) could prevent data loss, even if it adds complexity.
5.  **Dynamic `MAX_MESSAGES`**: The `MAX_MESSAGES` constant (12) for conversation history is a fixed limit. For more complex or longer-running dialogues, this might lead to loss of crucial context. Consider making this limit dynamic based on conversation complexity, professional settings, or even LLM capabilities, potentially using a token-aware truncation strategy rather than a fixed message count.
