# WhatsApp AI Intake

The WhatsApp AI Intake system serves as Odys's central AI concierge, designed to handle all inbound messages to the corporate WhatsApp number. Its primary function is to guide clients through a discovery and booking process across the entire marketplace of professionals, rather than being scoped to a single provider. This document explores the architecture, design decisions, and operational flow of this critical AI component, from message reception to appointment creation and notification.

## Overview

The core of the WhatsApp AI Intake system is the `src/lib/ai-intake.ts` module, which orchestrates the interaction between incoming WhatsApp messages, a large language model (LLM), and the Odys database. Inbound messages are received via the `/api/whatsapp/webhook` API route, which then dispatches to the AI agent logic.

The agent operates on a conversation state machine, allowing it to adapt its behavior based on whether a client is in a "Discovery" phase (searching for a professional), a "Focused" phase (interacting with a selected professional), or initiating a "Reset" to search for another. This state, along with the conversation history, is managed in Redis by the `src/lib/conversation.ts` module, ensuring continuity across turns.

The AI agent utilizes a "two-pass tool-calling" strategy. In the first pass, the LLM (powered by `chatWithFallback` which chains Groq, Cerebras, and Gemini) analyzes the user's intent and determines if a specific tool is required. If a tool is called, its results are then fed back to the LLM in a second pass, allowing it to generate a contextually rich and accurate reply. This approach separates intent recognition from response generation, leading to more precise and reliable interactions.

The system interacts with several database tables to fulfill its functions, including `professionals`, `availability`, `appointments`, `clients`, `notifications`, `reviews`, and `agentMetrics`. These interactions are facilitated by a suite of specialized tools that the LLM can invoke. For instance, when a client requests to book an appointment, the `book_appointment` tool is called, which then handles the creation of records in the `appointments` and `clients` tables, and triggers outbound notifications via WhatsApp and email. The system also records detailed metrics about each AI interaction in the `agentMetrics` table, capturing data such as `totalCostUsd`, `totalLatencyMs`, and `toolCallCount`.

## Conversation Management

The `src/lib/conversation.ts` module is responsible for maintaining the state of each client's interaction with the AI agent. This state is crucial for enabling multi-turn dialogues and ensuring the AI remembers context across messages.

Each conversation is represented by a `ConversationState` object, stored in Redis using a key derived from the client's normalized phone number. Key fields within this state include `clientPhone`, `clientName`, `selectedProfessionalId` (tracking the professional currently in focus), a `messages` array for conversation history, and a `context` object that holds transient information like `pendingDate` or `userCity`.

To prevent conversations from growing indefinitely and consuming excessive memory or LLM tokens, the `messages` array is capped at `MAX_MESSAGES` (currently 12). Older messages are automatically truncated. Furthermore, conversations are ephemeral, with a `TTL` of 30 minutes, meaning inactive conversations are automatically purged from Redis.

A critical aspect of conversation management is handling concurrent messages. To prevent race conditions and non-deterministic state updates, a per-phone message lock is implemented using `acquireMessageLock` and `releaseMessageLock`. This lock ensures that only one message from a given phone number is processed by the AI agent at a time. The lock has a `LOCK_TTL` of 45 seconds, designed to be long enough for even the slowest LLM round-trip. In the event of Redis errors, the lock is designed to "fail open," prioritizing message processing over strict concurrency control to avoid silently dropping user input.

Additionally, the `ConversationState` includes a `version` field, which facilitates optimistic concurrency. Each successful save increments this version. If a concurrent write attempts to save an older version of the state, a `ConversationStaleError` is thrown, preventing data corruption. This acts as a defense-in-depth mechanism, complementing the message lock.

The module also manages a `client_active` key in Redis, updated via `markClientActive` on every conversation save. This key, with an `ACTIVE_TTL` of 15 minutes, indicates if a client is currently engaged in a dialogue with the AI. This is used by other parts of the system, such as cron jobs, to defer transactional reminders and avoid interrupting an active conversation. Finally, `OutboundContext` is used to store information about the last transactional message sent to a client, such as `professionalId` and `appointmentId`, with a `OUTBOUND_TTL` of 2 hours.

## AI Intake Agent Core

The `src/lib/ai-intake.ts` file contains the core logic for the WhatsApp AI concierge. It integrates with various utilities and the database to provide a comprehensive booking and discovery experience.

### Timezone Handling

Brazil abolished DST in 2019, and São Paulo operates on UTC-3. To ensure accurate date and time handling, the module provides helper functions like `saoPauloDate`, `formatSaoPauloTime`, and `formatSaoPauloDate`. These functions are crucial for correctly interpreting user-provided dates and times and presenting them back in a localized format.

### Tool Definitions

The agent's capabilities are exposed to the LLM through an array of `OpenAI.Chat.Completions.ChatCompletionTool` definitions. These tools are intentionally designed with terse descriptions to minimize token usage, as the entire `TOOLS` array is sent with every LLM request. The prompt itself guides the LLM on when to use each tool.

The available tools include:

*   `search_professionals`: Used to find professionals based on criteria like `profession`, `city`, `name`, and `service_type`.
*   `list_professions`: Provides a list of active professions available on the platform.
*   `select_professional`: Allows the AI to "focus" on a specific professional by setting their ID in the conversation state.
*   `get_professional_info`: Retrieves detailed information about a selected professional, including their bio, address, schedule, and social proof (ratings, reviews).
*   `get_available_slots`: Computes and returns real-time available booking slots for a professional on a given date, considering their `availability` rules and existing `appointments`.
*   `book_appointment`: Facilitates the creation of a new appointment after confirming details with the client.
*   `list_my_appointments`: Fetches future appointments for the current client.
*   `cancel_appointment`: Allows the client to cancel an existing appointment.
*   `reschedule_appointment`: Enables rescheduling an existing appointment to a new date and time.

### Tool Implementations

Each tool definition is backed by a corresponding asynchronous function that interacts with the database and other services.

The `searchProfessionalsTool` function queries the `professionals` table, filtering by `active` status and applying conditions based on user input. It uses `resolveProfessionAlias` to map Portuguese profession terms to canonical English keys. A sophisticated ranking mechanism, leveraging `getProStats` and `rankScore`, sorts results by factors like average rating, review count, completed appointments, and the professional's `plan` tier. When a city is provided, `geocodeCity` is used to find its centroid, allowing for a distance penalty in the ranking via `distanceKm`, which favors professionals closer to the city center. If no professionals are found in the requested city, the system attempts to `findNearestProfessionals` to offer alternatives.

The `listProfessionsTool` ensures that only professions with at least one active professional are presented to the user, preventing dead-end searches.

`getProfessionalInfo` fetches comprehensive details about a professional, including their `availability` rules, aggregated `reviews` and `clients` data via `getProStats`, and recent `reviews`. It also constructs a `payment_policy` and a direct `profile_url`.

The `getAvailableSlots` function is central to the booking flow. It first normalizes the input `dateStr` using `parsePtDate` if necessary. It then calls `computeSlotsForDate`, which calculates available slots by comparing the professional's `availability` rules with existing `appointments` for the specified date. If no slots are found on the requested date, the function proactively looks for and suggests `alternatives` over the next 7 days, improving the user experience by reducing round-trips.

The `bookAppointment` function is a complex operation that handles the creation of new appointments. It performs input validation, rejects past dates, and checks for existing active appointments to prevent duplicates. The booking itself occurs within a Drizzle `db.transaction` with a `serializable` isolation level, ensuring atomicity and preventing race conditions where two clients might try to book the same slot simultaneously. It specifically handles `SLOT_TAKEN` errors, as well as database-level `40001` (serialization failure) and `23505` (unique violation) codes. Upon successful booking, it inserts a record into the `notifications` table and dispatches outbound messages via `sendWhatsApp` (using templates like `msgBookingConfirmed` or `msgBookingRequest`) and `sendBookingRequestEmailToProfessional`, depending on the professional's `autoConfirm` setting. It also generates `paymentInstructions` and a `pix_payload` if the professional has upfront or percentage payment requirements and a PIX key.

## Design decisions

Several key design decisions shape the WhatsApp AI Intake system:

*   **Two-Pass Tool Calling**: The separation of tool selection from response generation allows the LLM to first focus on understanding user intent and identifying the correct action, then to craft a precise, context-aware response using the tool's output. This reduces hallucination and improves the reliability of the agent's actions.
*   **Terse Tool Descriptions**: By keeping tool descriptions minimal, the system reduces the token count sent with each LLM request. This optimizes cost and latency, as the full `TOOLS` array is part of every prompt. The LLM is trained via the main prompt to understand when to use each tool, making verbose descriptions redundant.
*   **Redis for Conversation State**: Using Redis for `ConversationState` provides a fast, in-memory store for ephemeral chat context. This is ideal for maintaining conversational flow without incurring the latency of a full database lookup on every message. The `TTL` mechanism ensures that stale conversations are automatically cleaned up.
*   **Optimistic Concurrency with `version`**: The `version` field in `ConversationState` and the `ConversationStaleError` provide a robust mechanism to prevent data loss or corruption from concurrent writes. While a message lock handles the common case, optimistic concurrency acts as a crucial defense-in-depth, especially if the lock mechanism were to fail.
*   **Per-Phone Message Lock**: The `acquireMessageLock` and `releaseMessageLock` functions are fundamental for ensuring that messages from the same user are processed sequentially. This prevents the LLM from receiving interleaved inputs or generating conflicting responses, which would lead to a chaotic user experience. The "fail open" strategy for Redis errors prioritizes availability, accepting a small risk of occasional double-processing over dropping messages.
*   **Filtered `listProfessionsTool`**: By only listing professions with active professionals, the system prevents users from embarking on searches that are guaranteed to yield no results. This improves user satisfaction and reduces wasted LLM turns.
*   **Comprehensive `bookAppointment` Logic**: Consolidating client creation, conflict checking, appointment creation, and notification triggering into a single `bookAppointment` tool minimizes the number of LLM calls and database transactions required for a booking. This reduces latency and complexity in the AI's decision-making process.
*   **Professional Ranking in `searchProfessionalsTool`**: The use of `getProStats` and `rankScore` to sort search results ensures that the most relevant and high-quality professionals are presented first. Incorporating factors like average rating, review count, and even geographical proximity (when a city centroid can be resolved) directly impacts the quality of recommendations.
*   **Transactional Booking**: Wrapping the `bookAppointment` logic in a Drizzle `db.transaction` with `serializable` isolation guarantees that appointment creation is an atomic operation. This is critical for preventing double-bookings and maintaining data integrity, especially in a concurrent environment.

## Potential improvements

1.  **Enhanced Profession Resolution**: In `src/lib/ai-intake.ts`, the `searchProfessionalsTool` falls back to an `ilike` (substring) match on `professionals.profession` if `resolveProfessionAlias` does not find a direct match. While this provides some flexibility, it can lead to less precise results. A more robust solution could involve integrating a fuzzy matching library or expanding the `PROFESSIONS` mapping with more aliases and synonyms, potentially leveraging a dedicated knowledge base or a more sophisticated LLM-driven entity extraction for professions.
2.  **Dynamic Slot Alternative Search**: The `getAvailableSlots` function in `src/lib/ai-intake.ts` currently looks only 7 days ahead for alternative slots if the requested date has no availability. This fixed window might not always be optimal. An improvement could be to dynamically adjust this search window based on the professional's typical availability patterns or to allow the LLM to request a broader search if the initial alternatives are insufficient, perhaps by calling the tool with a different `date` range.
3.  **Centralized Error Handling for Database Conflicts**: The `bookAppointment` function in `src/lib/ai-intake.ts` explicitly checks for `SLOT_TAKEN`, `40001` (serialization failure), and `23505` (unique violation) errors. While effective, this pattern could become repetitive if similar transactional logic is introduced elsewhere. A more centralized Drizzle error handling utility or a custom error type for common database conflicts could simplify the `try/catch` blocks and improve consistency across the codebase.
4.  **Configurable Conversation Context Window**: The `MAX_MESSAGES` constant in `src/lib/conversation.ts` is fixed at 12. For very complex or long-running conversations, this might lead to the AI losing crucial context from earlier turns. Consider making this limit configurable per professional or conversation type, or implementing a summarization step that periodically condenses older messages into a concise summary to maintain context without exceeding token limits.
5.  **Robust Redis Lock Failure Handling**: The `acquireMessageLock` function in `src/lib/conversation.ts` is designed to "fail open" on Redis errors. While this prevents message drops, it means that during a Redis outage, multiple messages from the same client could be processed concurrently, potentially leading to inconsistent conversation state. For higher criticality, a more robust error handling strategy could be implemented, such as a retry mechanism with exponential backoff, or a circuit breaker pattern to temporarily halt processing until Redis recovers, coupled with a clear error message to the user.
