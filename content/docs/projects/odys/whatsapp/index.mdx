# WhatsApp

Odys integrates deeply with WhatsApp to facilitate communication between professionals and their clients, managing everything from appointment confirmations to direct messaging. This integration is a cornerstone of the platform's user experience, providing a familiar and immediate channel for critical updates and interactions. The system relies on a corporate WhatsApp number, orchestrated through the Evolution API, to send and receive messages, ensuring that all communications are structured and purposeful.

## Overview

The WhatsApp integration within Odys is primarily managed by the `src/lib/whatsapp.ts` module, which acts as a client for the Evolution API. This external API handles the complexities of sending and receiving WhatsApp messages, allowing Odys to focus on the business logic. The local development environment, as defined in `docker-compose.evolution.yml`, illustrates this architecture by spinning up `postgres` and `redis` containers alongside the `evolution-api` service itself.

Odys defines 19 distinct message templates, all pre-formatted as functions within `src/lib/whatsapp.ts`. These templates cover a wide range of transactional and conversational needs, from booking requests and reminders to payment confirmations and client reviews. Incoming messages are handled by the `/api/whatsapp/webhook` route, which is rate-limited to 10 requests per minute to prevent abuse and manage load. The `messages` table in the database serves as the central repository for all WhatsApp conversations, linking them back to specific professionals and clients.

## Evolution API Integration

The core of Odys's WhatsApp functionality resides in `src/lib/whatsapp.ts`. This file encapsulates the logic for interacting with the Evolution API, an external service chosen for its capabilities in managing WhatsApp communications. The API's endpoint, key, and specific instance are configured via environment variables: `EVOLUTION_API_URL`, `EVOLUTION_API_KEY`, and `EVOLUTION_INSTANCE`. A preliminary check, `isConfigured()`, verifies that these essential variables are present before any message is attempted, preventing runtime errors due to misconfiguration.

The `sendWhatsApp` function is the primary mechanism for dispatching messages. It accepts a `phone` number, the `text` content, and an optional `context` object. The `phone` number is first normalized using `normalizeBrazilianPhone` to ensure it adheres to the international format expected by the Evolution API. The message payload is then sent as a JSON object to the Evolution API's `/message/sendText/{INSTANCE}` endpoint. A `delay` of 1200 milliseconds is included in the payload, likely to simulate more natural human-like typing or to space out messages in a conversation.

A key aspect of the `sendWhatsApp` function is its `context` parameter. When provided, this context—containing `professionalId` and optionally `appointmentId`—is stored in Redis via `setOutboundContext`. This mechanism is crucial for routing subsequent client replies back to the correct professional and appointment, addressing the stateless nature of WhatsApp conversations and enabling a continuous, context-aware dialogue. This allows the `/api/whatsapp/webhook` to correctly associate incoming messages with ongoing interactions.

## Phone Number Normalization

Reliable message delivery hinges on correctly formatted phone numbers. The `normalizeBrazilianPhone` function in `src/lib/whatsapp.ts` addresses this by converting various input formats into a standardized international format without the leading `+`. The function intelligently handles numbers that already include the Brazilian country code (`55`), numbers with other international country codes (e.g., `49` for Germany), and local Brazilian numbers that require the `55` prefix to be added. This normalization step is vital for the Evolution API to correctly identify and deliver messages to recipients globally.

## Structured Message Templating

To maintain consistency, clarity, and brand identity across all automated communications, Odys centralizes its WhatsApp message content as functions within `src/lib/whatsapp.ts`. This approach prevents ad-hoc message construction in various parts of the application, reducing the likelihood of errors and simplifying content updates.

A visual templating system is employed for client-facing transactional messages. Functions like `transactionalHeader` and the `TRANSACTIONAL_FOOTER` constant add rule lines and branding information to messages. This visual distinction helps users differentiate automated notifications (such as reminders or confirmations) from direct conversational replies, especially when the same Odys WhatsApp number is used for both automated alerts and AI-driven or human agent interactions.

Odys utilizes 19 distinct message templates, each serving a specific purpose:

*   **Booking Management:** `msgBookingRequest` notifies professionals of new requests, while `msgBookingConfirmed`, `msgBookingRejected`, and `msgBookingCancelled` inform clients about their appointment status.
*   **Reminders:** `msgReminder24h` and `msgReminder1h` are sent to clients before appointments, likely triggered by the `/api/cron/reminders` cron job. The `appointments` table tracks `reminderSent24h` and `reminderSent1h` flags to prevent duplicate reminders.
*   **Cancellations:** `msgCancelledByClientToPro` and `msgCancelledByProToClient` handle notifications when either party cancels an appointment. The client-facing message includes a link to reschedule via `${APP_URL}/p/{slug}`.
*   **Receipts:** `msgBookingConfirmedReceipt` and `msgBookingRejectedReceipt` provide internal confirmations to professionals after they act on a booking request.
*   **Onboarding:** `msgRegistrationInvite` is appended to confirmation messages for new clients, offering a link to create an account via `${APP_URL}/register`.
*   **Payments:** `msgPaymentConfirmedToClient` and `msgPaymentConfirmedToPro` inform both parties about payment status.
*   **Post-Appointment:** `msgAppointmentCompletedToClient` prompts clients for reviews, linking to `${APP_URL}/c`, while `msgAppointmentCompletedToPro` confirms the professional's action.
*   **No-Shows:** `msgNoShowToClient` and `msgNoShowToPro` manage communications when a client misses an appointment, with the client receiving a link to reschedule.
*   **Direct Messaging:** `msgNewMessageToClient` and `msgNewMessageToPro` facilitate notifications when a new message is exchanged between a client and a professional within the Odys platform.

The `clients` and `professionals` tables store the necessary `phone` numbers and `name` details to personalize these messages.

## Design Decisions

The decision to centralize all WhatsApp message templates as exported functions in `src/lib/whatsapp.ts` was made to enforce consistency and maintainability. By defining messages in one place, the system avoids scattered string literals, making it easier to update messaging content, ensure correct formatting, and prevent typographical errors across the application. This separation of concerns also keeps communication logic distinct from the business processes that trigger these messages.

Choosing the Evolution API, as evidenced by its presence in `docker-compose.evolution.yml` and the specific `evoapicloud/evolution-api:v2.3.7` image, suggests a preference for a self-hostable or highly controllable WhatsApp gateway. This approach can offer greater flexibility and potentially lower operational costs compared to relying solely on official WhatsApp Business API providers, especially for an application like Odys that requires fine-grained control over message sending and webhook processing.

The implementation of `transactionalHeader` and `TRANSACTIONAL_FOOTER` for automated messages is a deliberate user experience choice. In a scenario where a single WhatsApp number handles both automated notifications and interactive AI or human conversations, visually distinguishing system-generated messages from conversational ones is critical. The rule lines and consistent branding help users quickly understand the nature of the message, reducing confusion and improving overall clarity in the chat thread.

The `context` parameter in `sendWhatsApp` and its subsequent storage in Redis via `setOutboundContext` addresses a fundamental challenge of WhatsApp integration: maintaining conversation state. Since WhatsApp messages are inherently stateless from the application's perspective, this mechanism provides a temporary, time-bound link between an outbound message and the professional/appointment it relates to. This allows the incoming webhook to intelligently route client replies, creating the illusion of a continuous conversation thread and enabling features like AI agent responses or direct professional replies to be correctly attributed.

## Potential Improvements

1.  **Externalize Message Templates:** The current message templates are hardcoded strings within `src/lib/whatsapp.ts`. As the platform grows or if multi-language support becomes a requirement, managing these 19 templates directly in code could become cumbersome. Moving these templates to a database, a dedicated content management system, or an i18n library would allow for dynamic updates, A/B testing of message content, and easier localization without requiring code deployments. This would involve refactoring the `msgBookingRequest` and similar functions in `src/lib/whatsapp.ts` to fetch content dynamically.

2.  **Enhanced `sendWhatsApp` Return Value:** The `sendWhatsApp` function currently returns a simple boolean indicating success or failure. While it logs errors, the calling code receives limited information. Modifying `sendWhatsApp` to return a more detailed result object (e.g., `{ success: boolean, messageId?: string, error?: string }`) would allow upstream services to implement more sophisticated error handling, such as specific retry logic based on the type of failure, or to track message delivery status more precisely.

3.  **Configurable Outbound Context Expiration:** The `setOutboundContext` mechanism, as described in the `sendWhatsApp` documentation, stores context for a fixed "next 2h". This duration might not be optimal for all use cases or user behaviors. Introducing a configurable expiration time, or even a dynamic one based on factors like the type of message sent or historical client response times, could improve the accuracy of reply routing. This would involve modifying the `setOutboundContext` function (which is not directly visible but implied by the `context` parameter) to accept or derive a variable expiration.
