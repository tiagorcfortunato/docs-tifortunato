# WhatsApp

Odys integrates deeply with WhatsApp to facilitate communication between professionals and clients, sending automated notifications, reminders, and enabling direct messaging. This integration is a cornerstone of the platform's user experience, ensuring timely updates and conversational capabilities. The system relies on a self-hosted instance of the Evolution API, a third-party solution that abstracts away the complexities of the official WhatsApp Business API.

## Overview

All outbound WhatsApp messages from the Odys application are managed through the `src/lib/whatsapp.ts` module. This file serves as the central hub for defining, formatting, and sending messages, ensuring consistency and maintainability across the platform. The actual message transmission is handled by the Evolution API, which is configured using environment variables such as `EVOLUTION_API_URL`, `EVOLUTION_API_KEY`, and `EVOLUTION_INSTANCE`.

For local development and deployment, the Evolution API runs as a Docker service, defined in `docker-compose.evolution.yml`. This setup includes a `postgres` database for Evolution API's internal data storage and a `redis` instance for caching and session management. The `evolution-api` service itself uses the `evoapicloud/evolution-api:v2.3.7` image, exposing port `8080` for communication.

Inbound WhatsApp messages are processed by the `/api/whatsapp/webhook` API route, which is configured to receive events from the Evolution API. To prevent abuse and manage resource usage, WhatsApp-related API calls are subject to a rate limit of `10` requests per `1 m`, identified by the `rl:whatsapp` prefix. Additionally, a daily cron job, `/api/cron/whatsapp-watchdog`, runs at `0 9 * * *` to monitor the WhatsApp integration's health and status.

## Message Templating

A core principle of the WhatsApp integration is the use of predefined message templates. The `src/lib/whatsapp.ts` file defines `19` distinct message templates, such as `msgBookingRequest`, `msgBookingConfirmed`, and `msgReminder24h`. This approach ensures that all automated messages adhere to a consistent tone and structure, preventing ad-hoc message strings from appearing throughout the codebase.

To visually distinguish automated transactional messages from conversational AI replies within the same WhatsApp chat thread, a specific visual templating system is employed. The `transactionalHeader` function and `TRANSACTIONAL_FOOTER` constant wrap client-facing notifications with rule lines (`━━━━━━━━━━━━━━━━━`) and include branding information (e.g., "Odys · agenda inteligente · odys.com.br"). This helps users quickly identify the nature of the message.

Before sending any message, phone numbers are normalized using the `normalizeBrazilianPhone` function. This utility converts various phone number formats into a standardized international format, specifically handling Brazilian numbers by prepending "55" if the country code is missing, while preserving other international formats.

## Outbound Messaging

The primary function for sending messages is `sendWhatsApp`. This asynchronous function takes a `SendTextParams` object, which includes the `phone` number, the `text` content, and an optional `context` object. The `context` object, containing `professionalId` and `appointmentId`, is crucial for maintaining conversational state. When a transactional message is successfully sent to a client, this `context` is stored in Redis using `setOutboundContext`. This allows subsequent client replies within a 2-hour window to be automatically routed by the `/api/whatsapp/webhook` to the correct professional and, if applicable, the specific appointment. This mechanism is vital for enabling seamless follow-ups and for the AI agent to understand the conversation's context.

The `sendWhatsApp` function first checks if the Evolution API is configured via `isConfigured()`. If not, it logs a warning and returns `false`. It then normalizes the phone number and attempts to send the message via a `POST` request to the Evolution API's `/message/sendText/{INSTANCE}` endpoint. The request includes the `number`, `text`, and a `delay` of `1200` milliseconds. Error handling is built-in, logging any failed API calls or network issues without throwing exceptions, ensuring the application remains stable even if the WhatsApp service experiences outages.

## Evolution API Infrastructure

The `docker-compose.evolution.yml` file orchestrates the local environment for the Evolution API. It defines three services:

1.  **`postgres`**: A `postgres:15` container named `evolution-postgres` serves as the database for the Evolution API. It's configured with a specific user (`evolution`), password (`odys-pg-2026`), and database (`evolution`). A health check ensures the database is ready before the API service starts.
2.  **`redis`**: A `redis:7-alpine` container named `evolution-redis` provides caching and session storage for the Evolution API.
3.  **`evolution-api`**: This service runs the `evoapicloud/evolution-api:v2.3.7` image. It depends on `postgres` and `redis` being healthy and started, respectively. Key environment variables configure its behavior:
    *   `AUTHENTICATION_API_KEY`: Set to `odys-local-key-2026` for local authentication.
    *   `DATABASE_PROVIDER`: Explicitly set to `postgresql`, with `DATABASE_CONNECTION_URI` pointing to the `postgres` service.
    *   `DATABASE_SAVE_DATA_INSTANCE`, `DATABASE_SAVE_DATA_NEW_MESSAGE`, `DATABASE_SAVE_MESSAGE_UPDATE`, `DATABASE_SAVE_DATA_CONTACTS`, `DATABASE_SAVE_DATA_CHATS`, `DATABASE_SAVE_IS_ON_WHATSAPP`: These are all set to `true` to enable comprehensive data persistence within the Evolution API's database.
    *   `CACHE_REDIS_ENABLED`: Set to `true`, with `CACHE_REDIS_URI` pointing to the `redis` service.
    *   `WEBHOOK_GLOBAL_ENABLED`: Set to `false`, indicating that webhooks are configured per-instance via the API rather than globally.
    *   `TELEMETRY_ENABLED`: Set to `false` to disable telemetry.

This Docker Compose setup provides a self-contained, reproducible environment for running the WhatsApp integration locally, mirroring production infrastructure patterns.

## Design decisions

The decision to centralize all WhatsApp message definitions within `src/lib/whatsapp.ts` was made to ensure consistency and ease of maintenance. By exporting functions for each message type (e.g., `msgBookingConfirmed`), developers are encouraged to reuse these templates rather than embedding message strings directly into business logic. This approach simplifies updates to message content or branding, as changes only need to be made in one place.

The visual distinction between transactional messages and AI agent replies, achieved through `transactionalHeader` and `TRANSACTIONAL_FOOTER`, addresses a common challenge in hybrid communication systems. When a single WhatsApp number handles both automated notifications and interactive AI conversations, users can become confused about the source and nature of messages. The clear visual cues help users understand whether they are receiving an automated update or interacting with an AI.

The `context` parameter in `sendWhatsApp` and its interaction with `setOutboundContext` in Redis represents a deliberate choice to manage conversational state. WhatsApp's stateless nature means that each incoming message is independent. By storing the `professionalId` and `appointmentId` associated with the last outbound message, the system can intelligently route subsequent client replies, enabling a more coherent and personalized conversational flow, especially for the AI agent. This trade-off involves adding a Redis dependency for state management but significantly improves the user experience for multi-turn interactions.

Choosing to self-host the Evolution API, as evidenced by `docker-compose.evolution.yml`, rather than using a managed WhatsApp Business API solution or a different provider, likely reflects a trade-off between control, cost, and feature set. Self-hosting provides greater control over the infrastructure, data, and specific API version (`v2.3.7`), potentially reducing ongoing operational costs compared to some managed services. However, it introduces the overhead of managing and maintaining the Evolution API's dependencies (Postgres, Redis) and the API service itself.

## Potential improvements

1.  **Internationalization (i18n) for Message Templates**: The current message templates in `src/lib/whatsapp.ts` are hardcoded in Portuguese. For a global application, these templates would need to support multiple languages. A concrete improvement would be to refactor these functions to accept a locale parameter or to load message strings from a dedicated i18n framework, rather than embedding the text directly.
2.  **Structured Date/Time Objects in Templates**: Functions like `msgBookingConfirmed` accept `date: string` and `time: string`. This forces the calling code to pre-format dates and times. Passing structured `Date` objects or a dedicated date/time library's objects (e.g., `luxon` or `date-fns`) to the template functions would allow the template itself to handle formatting based on locale or specific display requirements, making the templates more flexible and less prone to formatting errors.
3.  **Consistent URL Generation**: The `APP_URL` constant is imported from `constants`, but some templates, like `msgBookingRequest`, hardcode paths like `/dashboard`, while `msgCancelledByProToClient` constructs a full URL using `APP_URL/p/${opts.slug}`. For consistency and easier management of application routes, a helper function could be introduced to generate all internal application URLs, ensuring they correctly use `APP_URL` and handle path concatenation uniformly.
4.  **Robustness of `msgRegistrationInvite` Parameters**: The `msgRegistrationInvite` function expects `phone` and `name` as non-nullable options, while `email` is nullable. If `name` is not always available when this invite is generated, it could lead to incomplete messages. Reviewing the call sites for this function and ensuring `name` is always provided, or making `name` nullable and handling its absence gracefully within the template, would improve its robustness.
5.  **Error Handling for `setOutboundContext`**: In `sendWhatsApp`, the call to `setOutboundContext` is not wrapped in a `try...catch` block, meaning potential errors during Redis operations would not be caught by the `sendWhatsApp` function's existing error handling. While `setOutboundContext` might have its own internal logging, ensuring `sendWhatsApp` explicitly handles or logs failures from this critical context-setting step would make the outbound messaging more resilient.
