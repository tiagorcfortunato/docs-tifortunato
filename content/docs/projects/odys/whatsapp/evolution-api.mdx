# Evolution API

Odys relies on the Evolution API to manage all WhatsApp interactions, serving as the primary communication channel between the platform, professionals, and clients. This integration is central to Odys's "WhatsApp-first" philosophy, enabling automated reminders, booking confirmations, and conversational AI interactions without requiring professionals to connect their personal WhatsApp accounts.

## Overview

The Evolution API integration is handled primarily by the `src/lib/whatsapp.ts` module, which defines the client for sending messages and a collection of 19 pre-formatted message templates. For local development and production deployment on Railway, the Evolution API runs as a Docker container, specifically using version `v2.3.7`. This setup allows Odys to manage a single corporate WhatsApp number, from which all outbound messages are sent and all inbound messages are received, processed by the `POST /api/whatsapp/webhook` endpoint.

The system is designed to differentiate between automated transactional messages and conversational AI replies within the same WhatsApp thread, using distinct visual formatting. It also incorporates a mechanism to route client replies to the correct professional and appointment context, even when a client interacts with multiple professionals on the platform.

## WhatsApp Messaging Core

The `src/lib/whatsapp.ts` file is the heart of Odys's WhatsApp communication. It encapsulates the logic for interacting with the Evolution API and defines all the message content sent through the platform.

The core functionality resides in the `sendWhatsApp` function, which abstracts away the underlying API calls. This function takes a `phone` number (which is normalized to an international format using `normalizeBrazilianPhone`), the `text` content, and an optional `context` object. The `context` is crucial for inbound message routing: when provided, it stores the `professionalId` and `appointmentId` in Redis, allowing subsequent client replies to be correctly associated with an ongoing conversation. This design choice prevents the AI agent from needing to re-identify the professional or appointment for every follow-up message, streamlining the user experience.

The `sendWhatsApp` function is built to be resilient, catching network errors and API failures, logging them via `logger.error`, and returning `false` rather than throwing exceptions. This approach allows the application to continue operating even if a message fails to send, which is important for non-critical notifications. The current implementation targets Evolution API v2.3+, noting a change in payload structure from earlier versions (v1.8) where the message content was nested under `textMessage`.

A notable design element within `src/lib/whatsapp.ts` is the visual templating for client-facing transactional messages. Functions like `transactionalHeader` and the `TRANSACTIONAL_FOOTER` constant are used to prepend and append distinct rule lines and professional names to messages. This visual separation helps clients distinguish automated notifications (like reminders or confirmations) from direct conversational AI replies within the same WhatsApp chat, which is critical for clarity when a single Odys number handles both channels.

All 19 message templates, such as `msgBookingConfirmed` or `msgReminder24h`, are defined as exported functions. This centralizes message content, preventing message strings from being scattered across various API routes and ensuring consistency in tone and branding.

## Local Development and Deployment

The Evolution API is deployed as a self-hosted Docker container, managed by `docker-compose.evolution.yml` for local development and on Railway for production. This choice was made because Evolution API acts as a WhatsApp Web shim, providing a way to send messages from a dedicated corporate WhatsApp number without the complexities and restrictions of Meta's official WhatsApp Business Cloud API for smaller-scale operations.

The `docker-compose.evolution.yml` configuration defines three services:
*   `postgres`: A PostgreSQL 15 database, used by Evolution API for its internal data storage. It's configured with a health check to ensure readiness before the Evolution API starts.
*   `redis`: A Redis 7 instance, used for caching and session management by Evolution API.
*   `evolution-api`: The core Evolution API service, using the `evoapicloud/evolution-api:v2.3.7` Docker image. It depends on both `postgres` and `redis` being healthy and started.

Key environment variables are set within the `evolution-api` service to configure its behavior:
*   `SERVER_URL`: Points to `http://localhost:8080` for local access.
*   `AUTHENTICATION_API_KEY`: Set to `odys-local-key-2026` for local authentication.
*   `DATABASE_CONNECTION_URI`: Specifies the connection string for the PostgreSQL database.
*   `CACHE_REDIS_URI`: Connects to the local Redis instance.
*   `WEBHOOK_GLOBAL_ENABLED`: Explicitly set to `false`, indicating that webhooks are configured per-instance via the API rather than globally.
*   `TELEMETRY_ENABLED`: Disabled to prevent data collection.

This Docker Compose setup provides a complete, isolated environment for running the Evolution API locally, mirroring the production setup on Railway.

## Integration with Odys

Odys integrates with the Evolution API for both outbound and inbound message flows.

For outbound messages, any part of the application needing to send a WhatsApp message calls one of the 19 message template functions in `src/lib/whatsapp.ts`, which then delegates to `sendWhatsApp`. This includes automated reminders (handled by the `GET /api/cron/reminders` cron job), booking confirmations, professional alerts, and AI agent replies.

Inbound messages are received by the `POST /api/whatsapp/webhook` API route. This webhook is responsible for processing incoming client messages, routing them to the AI intake agent (`src/lib/ai-intake.ts`), and leveraging the `last_outbound:{phone}` context stored in Redis to maintain conversation state. This context allows the AI to understand which professional or appointment a client's reply pertains to, avoiding repetitive clarification questions.

The system also includes a `GET /api/cron/whatsapp-watchdog` cron job, scheduled daily at 9 AM, to perform a health check on the Evolution API instance, ensuring its operational status.

## Design decisions

The decision to use Evolution API stems from the need for a WhatsApp integration that is more flexible and less restrictive than Meta's official WhatsApp Business Cloud API, especially for a platform serving independent professionals. Evolution API, by acting as a WhatsApp Web shim, allows Odys to operate a single corporate WhatsApp number that serves all professionals and clients, abstracting away the need for individual professionals to manage their own WhatsApp integrations. This simplifies onboarding and reduces operational overhead.

The `sendWhatsApp` function in `src/lib/whatsapp.ts` serves as a critical abstraction layer. By centralizing all outbound message logic, Odys can swap the underlying WhatsApp engine (e.g., migrating to Meta's WhatsApp Business Cloud API) without modifying every call site in the application. This forward-thinking design prepares the platform for future scaling and compliance requirements.

The visual templating, using `transactionalHeader` and `TRANSACTIONAL_FOOTER`, addresses a key user experience challenge. In a system where a single WhatsApp number handles both automated alerts and conversational AI, distinguishing between these message types is paramount. The clear visual cues prevent confusion and help clients quickly understand the nature of each message.

The use of `docker-compose.evolution.yml` for local development, mirroring the Railway deployment, ensures consistency between development and production environments. This reduces "it works on my machine" issues and simplifies the deployment process.

## Potential improvements

1.  **Configurable Message Delay**: The `sendWhatsApp` function in `src/lib/whatsapp.ts` currently hardcodes a `delay: 1200` milliseconds for all messages. While a delay can help mimic human-like typing or prevent rate-limiting issues, a fixed value might not be optimal for all message types or network conditions. Introducing a configurable delay, perhaps as an optional parameter to `sendWhatsApp` or through environment variables, could allow for fine-tuning message delivery behavior based on urgency or context.
2.  **Dynamic `APP_URL` in Message Templates**: Several message templates, such as `msgBookingRequest` and `msgCancelledByProToClient` in `src/lib/whatsapp.ts`, directly embed `APP_URL` from `lib/constants.ts`. While functional, this approach means that if the application were to be deployed under different domains (e.g., for white-labeling or regional instances), these URLs would need to be updated in the constants. Passing `APP_URL` as an argument to the message template functions, or making it a dynamic configuration loaded at runtime, would make the templates more flexible and reusable across different deployment contexts.
3.  **Refined Phone Number Normalization**: The `normalizeBrazilianPhone` function in `src/lib/whatsapp.ts` attempts to handle both Brazilian and other international phone numbers. The logic for identifying "other country codes" (`if (digits.length >= 12 && !digits.startsWith("55"))`) might be overly broad. A 12-digit number not starting with "55" could still be a Brazilian number with an omitted country code, or a valid international number that is shorter than 12 digits. Implementing a more robust phone number parsing library (e.g., `libphonenumber-js`) could provide more accurate normalization, handling edge cases and varying international formats more reliably.
