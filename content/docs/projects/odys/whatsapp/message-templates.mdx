# WhatsApp Message Templates

The `src/lib/whatsapp.ts` file serves as the central hub for all WhatsApp communication within Odys. It encapsulates the integration with the Evolution API and, critically, defines the standardized message templates used across the application. This centralization ensures consistency in messaging, simplifies maintenance, and prevents ad-hoc message strings from proliferating throughout the codebase.

## Overview

At its core, `src/lib/whatsapp.ts` provides the `sendWhatsApp` function, which acts as the primary interface for dispatching messages through the Evolution API. This function handles the underlying network request, error logging, and phone number normalization via `normalizeBrazilianPhone`. Before any message is sent, the system checks if the Evolution API is properly configured using `isConfigured`, relying on environment variables like `EVOLUTION_API_URL`, `EVOLUTION_API_KEY`, and `EVOLUTION_INSTANCE`.

The file defines a total of 19 distinct message template functions, each prefixed with `msg` (e.g., `msgBookingRequest`, `msgBookingConfirmed`, `msgReminder24h`, `msgNewMessageToClient`). These functions are responsible for generating the exact text content sent to clients or professionals, ensuring that all transactional and conversational messages adhere to a consistent brand voice and structure.

## Evolution API Integration

The `sendWhatsApp` function is the single point of contact with the external WhatsApp service provider, the Evolution API. It constructs a `POST` request to the `/message/sendText/{INSTANCE}` endpoint, including the recipient's normalized phone number and the pre-formatted message text. A small `delay` of 1200 milliseconds is intentionally added to the payload, likely to prevent rate-limiting issues or to simulate a more natural, human-like message delivery pace.

Error handling within `sendWhatsApp` is designed to be resilient. Instead of throwing exceptions, it logs failures using `logger.error` and returns a boolean indicating success or failure. This pattern allows calling code to react to delivery status without needing complex `try/catch` blocks for network or API-specific errors.

A notable feature of `sendWhatsApp` is its optional `context` parameter. When provided, this context—containing `professionalId` and optionally `appointmentId`—is stored using `setOutboundContext` after a successful send. This mechanism is crucial for routing subsequent inbound replies from clients back to the correct professional or appointment, effectively maintaining conversational continuity within the WhatsApp thread.

## Message Templating Strategy

All 19 message templates are implemented as simple JavaScript functions that accept an `opts` object and return a formatted string. This approach keeps the message content close to the sending logic and allows for dynamic insertion of data like client names, dates, and times.

A key aspect of the templating strategy is the visual distinction between automated transactional messages and more conversational AI replies. This is achieved through the use of `HEADER_RULE` (`━━━━━━━━━━━━━━━━━`) and `TRANSACTIONAL_FOOTER` (`_Odys · agenda inteligente · odys.com.br_`). Functions like `transactionalHeader` combine an emoji, a label, and the professional's name with the `HEADER_RULE` to create a clear, visually segmented header.

For instance, `msgBookingConfirmed` and `msgReminder24h` utilize `transactionalHeader` and `TRANSACTIONAL_FOOTER` to frame their content. This visual framing helps users quickly identify automated notifications, which is particularly important when the same WhatsApp number might also be used for direct, free-form conversations with an AI agent or a human.

The templates are grouped logically within the file:
*   **Client-facing transactional messages**: These include confirmations (`msgBookingConfirmed`), rejections (`msgBookingRejected`), cancellations (`msgBookingCancelled`), and reminders (`msgReminder24h`, `msgReminder1h`). These typically use the full `transactionalHeader` and `TRANSACTIONAL_FOOTER`.
*   **Cancellation notifications**: `msgCancelledByClientToPro` and `msgCancelledByProToClient` inform parties about appointment cancellations.
*   **Receipts for professionals**: `msgBookingConfirmedReceipt` and `msgBookingRejectedReceipt` provide internal confirmations to professionals about actions they've taken.
*   **Registration invite**: `msgRegistrationInvite` is a special suffix that can be appended to other messages, offering clients without an account a link to register, pre-filling details like `email`, `phone`, and `name`.
*   **Payment confirmations**: `msgPaymentConfirmedToClient` and `msgPaymentConfirmedToPro` handle notifications related to payment status.
*   **Appointment completion**: `msgAppointmentCompletedToClient` and `msgAppointmentCompletedToPro` are sent when an appointment is marked as finished.
*   **No-Show notifications**: `msgNoShowToClient` and `msgNoShowToPro` inform about missed appointments.
*   **New message notifications**: `msgNewMessageToClient` and `msgNewMessageToPro` alert users to new messages in their conversation threads, including a `preview` of the message content.

## Design decisions

The design choices in `src/lib/whatsapp.ts` reflect a pragmatic approach to managing external communication and user experience:

*   **Centralized Message Definitions**: By defining all 19 message templates as exported functions within a single file, the codebase achieves a high degree of consistency and maintainability. This prevents message strings from being scattered across various routes or services, making it easier to review, update, or audit all outbound communications. The alternative—embedding strings directly in business logic—would lead to fragmentation and potential inconsistencies.
*   **Visual Cues for Transactional Messages**: The use of `HEADER_RULE` and `TRANSACTIONAL_FOOTER` is a deliberate choice to enhance user experience. In a world where a single WhatsApp thread might contain both automated notifications and free-form conversational AI, these visual separators clearly delineate system-generated messages. This design decision prioritizes clarity for the end-user, helping them quickly understand the nature of the message they are receiving.
*   **Resilient Error Handling**: The `sendWhatsApp` function's choice to return a boolean and log errors, rather than throwing exceptions, simplifies error management for callers. This pattern is suitable for non-critical background tasks where a failure to send a message should be logged but might not require immediate, synchronous interruption of the application flow. The trade-off is that calling code must explicitly check the return value, but it avoids the overhead of `try/catch` blocks at every call site.
*   **Phone Number Normalization**: The `normalizeBrazilianPhone` function addresses the common challenge of inconsistent phone number formats. By centralizing this logic, Odys ensures that all numbers sent to the Evolution API conform to the expected international format, reducing potential delivery failures due to malformed inputs. This decision prioritizes reliability and reduces friction with the external API.

## Potential improvements

While the current implementation is functional, several areas could be enhanced to improve maintainability, flexibility, and developer experience:

*   **Type Safety for Template Options**: The `opts` parameters for all `msg*` functions, such as `msgBookingConfirmed`, currently lack explicit type definitions. This means the TypeScript compiler cannot verify that all required properties (e.g., `professionalName`, `clientName`) are provided or that their types are correct at compile time. Introducing interfaces for each template's options would significantly improve type safety and reduce runtime errors.
*   **Internationalization (i18n) Support**: All 19 message templates, including `msgBookingRequest` and `msgReminder24h`, are hardcoded in Portuguese. As Odys expands, supporting multiple languages will require a robust internationalization strategy. This could involve externalizing message strings into JSON files or using an i18n library, rather than embedding them directly in the `msg*` functions.
*   **Structured Template Definitions**: The current approach uses string concatenation within functions, which can become cumbersome for complex messages or when introducing new formatting requirements. Consider defining message templates as structured objects or using a dedicated templating library (e.g., Handlebars, Nunjucks) that separates template logic from data. This would make templates easier to read, test, and manage, especially for messages like `msgCancelledByProToClient` which combine multiple lines and dynamic data.
*   **Evolution API Client Abstraction**: The `fetch` call within `sendWhatsApp` directly interacts with the Evolution API. While functional, abstracting this into a dedicated client class or module could centralize API-specific logic (e.g., header management, base URL construction, error parsing) and make `sendWhatsApp` cleaner. This would also simplify potential future migrations to different API versions or providers.
