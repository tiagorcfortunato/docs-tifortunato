# Booking API

The `/api/booking` endpoint serves as a central hub for managing appointment scheduling within Odys. It exposes two primary functionalities: a `GET` request for clients to query a professional's available time slots, and a `POST` request for creating new appointments. This endpoint is critical for the core business logic, connecting client interactions with professional availability and managing the lifecycle of a booking from request to confirmation.

## Overview

This API route, located at `src/app/api/booking/route.ts`, orchestrates interactions across several key database tables, including `professionals`, `availability`, `appointments`, `clients`, and `notifications`. It integrates with external services for communication (WhatsApp, email), subscription plan enforcement (Stripe), and behavioral analytics. To maintain system stability and prevent abuse, the endpoint also incorporates rate limiting and bot detection mechanisms. The design prioritizes data integrity, concurrency control, and a smooth user experience while safeguarding sensitive information.

## GET Method: Fetching Availability

The `GET` method of the `/api/booking` endpoint allows prospective clients to retrieve a professional's scheduling rules and existing appointments for a specific date. This information is then used by the frontend to display available booking slots.

A client initiates this request by providing a `slug` to identify the professional and a `date` string for the desired day. The endpoint first validates these parameters, returning a `400` status if they are missing.

Upon successful validation, the system queries the `professionals` table to find the professional associated with the provided `slug`. Crucially, it only selects the `id` and `sessionDuration` columns. This selective retrieval is a deliberate design choice to prevent accidental data leakage; earlier versions might have returned all professional details, exposing sensitive information like `email`, `phone`, `userId`, `plan`, `trialEndsAt`, `stripeCustomerId`, and `stripeSubscriptionId` to unauthenticated users. If no professional is found, a `404` status is returned.

Next, the endpoint concurrently fetches two sets of data:
1.  **Availability Rules**: From the `availability` table, it retrieves the `dayOfWeek`, `startTime`, and `endTime` for the professional, which define their general working hours.
2.  **Existing Appointments**: From the `appointments` table, it queries all appointments for the professional within the specified `date` range, specifically between `startOfDay(date)` and `endOfDay(date)`. Importantly, it filters out appointments with a `status` of `rejected` or `cancelled`, as these slots are effectively available.

Finally, the `GET` request returns a JSON object containing both the `rules` and `existingAppointments`, allowing the client-side application to compute and display the actual bookable time slots. Any unexpected errors during this process are caught and returned as a `500` server error.

## POST Method: Creating a Booking

The `POST` method handles the creation of new appointments, a more complex operation involving validation, concurrency control, plan enforcement, and multiple notification steps.

Before processing the request, the endpoint applies a rate limit using `getBookingLimiter()`, configured to allow 5 requests per 10 minutes (`rl:booking`). If the limit is exceeded, a `429` status is returned.

To mitigate timing oracle attacks, a `respondAfterFloor` function is employed. This function ensures that all responses, regardless of the underlying database operation's speed, take at least 250 milliseconds. This blunts the ability of an attacker to distinguish between different database states (e.g., an existing client vs. a new client) by timing the response.

The incoming request body is validated using `zod` against the `bookingSchema`, which ensures the presence and correct format of `slug`, `startsAt`, `clientName`, `clientPhone`, and optionally `clientEmail`. It also includes a `website` field as a honeypot; if this hidden field is populated, the request is identified as a bot submission, and a fake success response is returned without touching the database.

After validation, the professional's details are fetched from the `professionals` table using their `slug`. If the professional is not found, a `404` error is returned.

A critical step involves checking the professional's subscription plan limits. The `effectivePlan` function determines the active plan, considering any `trialEndsAt` date. The system then checks if the professional has exceeded their `plan.limits.clients` or `plan.limits.appointmentsPerMonth`. If the client limit is reached, it verifies if the booking is for an *existing* client (by phone number); if not, a `403` error is returned. Similarly, if the monthly appointment limit is hit, a `403` error is returned.

The core booking logic is wrapped in a Drizzle `transaction` with `isolationLevel: "serializable"`. This is a crucial design decision to prevent race conditions where two simultaneous booking requests might attempt to reserve the same time slot.
Within this transaction:
1.  **Conflict Check**: The system checks for any existing appointments that would overlap with the proposed `startsAt` and `endsAt` times, excluding `rejected` or `cancelled` appointments. If an overlap is found, a custom error "SLOT_TAKEN" is thrown.
2.  **Client Upsert**: The system attempts to find an existing client for the professional using the `clientPhone` or `clientEmail`. If a client is found, their `email` is updated if it was previously `null` and a new email is provided. If no client is found, a new entry is inserted into the `clients` table.
3.  **Appointment Creation**: Finally, a new appointment is inserted into the `appointments` table. The `status` is set to `confirmed` if `professional.autoConfirm` is true, otherwise it's `pending_confirmation`. The `paymentStatus` is initialized to `none`.

If the "SLOT_TAKEN" error is thrown or a `SQLSTATE 40001` (serialization failure) occurs due to a concurrency conflict, the transaction is rolled back, and a `409` status is returned to the client, informing them that the slot was just taken.

Upon successful booking, a series of notifications are triggered:
*   A new `notification` is inserted into the `notifications` table for the professional, indicating a `booking_confirmed` or `booking_request` depending on the `autoConfirm` setting.
*   WhatsApp messages are sent via `sendWhatsApp`:
    *   If confirmed: `msgBookingConfirmed` to the client and `msgBookingConfirmedReceipt` to the professional.
    *   If pending: `msgBookingRequest` to the professional.
*   If the professional has an `email` configured, an email notification is sent using `sendBookingRequestEmailToProfessional`.

Finally, analytics events are captured using `capture` and `setOnce` to track `booking_received_server` and the `first_booking_at` for the professional. The endpoint then returns a generic `success: true` response, again respecting the `respondAfterFloor` delay, and intentionally omitting sensitive appointment details to avoid leaking information that could aid attackers.

## Design decisions

Several key design decisions shape the `/api/booking` endpoint:

*   **Preventing Data Leakage in GET**: The `GET` method explicitly selects only `id` and `sessionDuration` from the `professionals` table. This choice was made to prevent sensitive professional data (like `email`, `phone`, `userId`, `plan`, `trialEndsAt`, `stripeCustomerId`, `stripeSubscriptionId`) from being exposed to unauthenticated users who might query the endpoint. It adheres to the principle of least privilege, only returning data strictly necessary for the client to calculate available slots.

*   **Concurrency Control with Serializable Transactions**: The `POST` method wraps the critical booking logic (conflict check, client upsert, appointment insert) in a Drizzle `transaction` with `isolationLevel: "serializable"`. This is a fundamental choice to prevent race conditions. Without it, two users could simultaneously check for an available slot, both find it free, and then both attempt to book it, leading to a double-booking. A serializable transaction forces the database to execute these operations as if they happened one after another, detecting and rolling back one of the conflicting transactions (often with `SQLSTATE 40001`), which is then gracefully handled by returning a `409` status.

*   **Bot and Timing Oracle Mitigation**: The `POST` endpoint employs two strategies against malicious actors:
    1.  **Honeypot Field**: The `website` field in `bookingSchema` acts as a honeypot. Bots often fill all available form fields, including hidden ones. If this field is populated, the request is immediately discarded, and a fake `200 OK` response is returned. This prevents bots from learning that the field is a trap and reduces database load from spam.
    2.  **Response-Time Floor**: The `respondAfterFloor` utility introduces a minimum 250ms delay for all `POST` responses. This is a countermeasure against timing oracle attacks, where an attacker might infer information about the backend state (e.g., whether a client already exists) by precisely measuring response times. By normalizing response times, this signal is obscured.

*   **Unified Notification Flow**: The notification logic (WhatsApp, email, in-app notifications) is designed to branch based on `professional.autoConfirm`. This ensures that whether a booking is immediately `confirmed` or `pending_confirmation`, the appropriate messages are sent to both the client and the professional, maintaining a consistent communication experience regardless of the booking channel (web form or AI concierge).

*   **Robust Input Validation**: The use of `zod` for schema validation (`bookingSchema`) provides a clear, declarative way to define expected input shapes and types. This prevents malformed data from reaching the business logic and database, improving reliability and security.

## Potential improvements

1.  **Server-Side Time Slot Generation for `GET`**: The `GET` method currently returns raw `availability` rules and `existingAppointments`. The client-side application is then responsible for calculating the truly available time slots. Moving this logic to the server, perhaps into a dedicated utility function, would centralize the business logic for slot calculation. This would ensure consistency across different client applications, simplify frontend development, and make it easier to introduce more complex scheduling rules (e.g., buffer times between appointments, lunch breaks) without requiring client-side updates.

2.  **Enhanced Client Upsert Logic in `POST`**: In the `POST` method's transaction, the client upsert logic only updates a client's `email` if it was previously `null`. Consider whether `client.name` or `client.phone` should also be updated if the incoming `clientName` or `clientPhone` differs from the existing record. For instance, if a client books with a slightly different name spelling, the system might create a duplicate client or miss an opportunity to update the existing record. A more comprehensive upsert strategy could involve comparing all relevant fields and updating them if the incoming data is newer or more complete, or introducing a separate endpoint for client profile updates.

3.  **Payment Integration in `POST`**: The `POST` method currently sets `paymentStatus` to "none" and does not interact with a payment gateway. If Odys intends to support upfront payments or deposits at the time of booking, this endpoint would need to be extended. This would involve integrating with a service like Stripe to create a `PaymentIntent` and potentially handle payment confirmation or pre-authorization, updating the `paymentStatus` column in the `appointments` table accordingly. This would add complexity but enable new monetization strategies.
