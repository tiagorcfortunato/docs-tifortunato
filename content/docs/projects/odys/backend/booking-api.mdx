# Booking API

The `/api/booking` endpoint serves as the central hub for managing appointments within the Odys platform. It exposes two primary functionalities: a `GET` request for querying a professional's available time slots and a `POST` request for creating new appointments. This API is critical for both clients seeking to book services and professionals managing their schedules, integrating deeply with the platform's database, communication channels, and business logic.

## Overview

This API route orchestrates the complex process of scheduling appointments. It interacts with several core database tables, including `professionals`, `availability`, `appointments`, `clients`, and `notifications`. The `GET` method focuses on providing the necessary data for a client-facing booking widget to display available slots, while the `POST` method handles the creation of an appointment, including client management, plan limit checks, concurrency control, and multi-channel notifications. The `POST` endpoint is also protected by a rate limiter to prevent abuse.

## GET /api/booking

The `GET` request to `/api/booking` allows an unauthenticated user to retrieve a professional's scheduling rules and existing appointments for a specific date. This information is then used by the frontend to calculate and display available booking slots.

Upon receiving a request, the endpoint expects two query parameters: `slug`, which uniquely identifies the professional, and `date`, specifying the day for which availability is requested. If either parameter is missing, the API responds with a `400` status code, indicating invalid parameters.

The system first queries the `professionals` table, filtering by the provided `slug`. Crucially, it only selects the `id` and `sessionDuration` columns. This is a deliberate design choice to prevent sensitive professional data, such as `email`, `phone`, `userId`, `plan`, `trialEndsAt`, `stripeCustomerId`, or `stripeSubscriptionId`, from being exposed to anonymous visitors. If no professional is found for the given slug, a `404` status is returned.

Once the professional's basic details are retrieved, the API concurrently fetches two sets of data:
1.  **Availability Rules**: It queries the `availability` table for entries associated with the professional's `id`. These rules define the professional's general working hours for each `dayOfWeek`, specified by `startTime` and `endTime`.
2.  **Existing Appointments**: It queries the `appointments` table for all appointments linked to the professional's `id` that fall within the `startOfDay` and `endOfDay` of the requested `date`. Importantly, appointments with a `status` of `rejected` or `cancelled` are explicitly excluded, as they do not represent occupied slots.

The endpoint then returns both the `rules` and `existingAppointments` to the client. The frontend is responsible for processing this raw data to determine the actual bookable time slots, taking into account the `sessionDuration` and any overlaps with existing appointments.

## POST /api/booking

The `POST` request to `/api/booking` is responsible for creating a new appointment. This is a more complex operation, involving several layers of validation, business logic, and external integrations.

The process begins with a rate limit check using `getBookingLimiter` based on the client's IP address. If the limit of 5 requests within 10 minutes (as defined by the `booking` rate limit prefix `rl:booking`) is exceeded, a `429 Too Many Requests` response is returned.

To mitigate potential timing attacks, particularly a timing oracle that could distinguish between existing and new clients, the endpoint introduces a response-time floor. All responses are delayed to ensure a minimum processing time of 250ms, making it harder for an attacker to infer information based on response latency.

The request body is first validated using `bookingSchema`, a `zod` schema. This ensures that required fields like `slug`, `startsAt`, `clientName`, and `clientPhone` are present and correctly formatted. An optional `clientEmail` is also validated. A special `website` field acts as a honeypot; if a bot populates this hidden field, the request is silently discarded with a fake success response, preventing it from interacting with the database.

Next, the professional is retrieved from the `professionals` table using the provided `slug`. If the professional is not found, a `404` error is returned.

The system then checks the professional's subscription plan against the `PLANS` defined in `@/lib/stripe`. The `effectivePlan` function determines the active plan, considering any `trialEndsAt` date. If the plan has limits on `clients` or `appointmentsPerMonth`, these are enforced:
*   **Client Limit**: If the professional has reached their `clients` limit, the system checks if the booking client (identified by `clientPhone`) is already an existing client. If not, the booking is rejected with a `403 Forbidden` status.
*   **Monthly Appointment Limit**: If the professional has reached their `appointmentsPerMonth` limit for the current month, the booking is rejected with a `403 Forbidden` status.

The core booking logic is wrapped in a Drizzle `transaction` with `serializable` isolation level. This is a critical design choice to prevent race conditions and ensure data consistency. Without it, two simultaneous booking requests for the same slot could both pass initial checks and create conflicting appointments. The `serializable` isolation level forces the database to re-evaluate conditions if underlying data changes, leading to a `40001` SQLSTATE error if a conflict is detected.

Inside the transaction:
1.  **Conflict Check**: The `appointments` table is queried to check for any existing appointments for the professional that overlap with the proposed `startsAt` and `endsAt` times. Appointments with `rejected` or `cancelled` status are ignored. If an overlap is found, a custom `SLOT_TAKEN` error is thrown, which is later caught and translated into a `409 Conflict` response.
2.  **Client Upsert**: The system attempts to find an existing client for the professional based on `clientPhone` or `clientEmail`. If a client is found, their `email` is updated if it was previously null and a new email is provided. If no client is found, a new entry is inserted into the `clients` table.
3.  **Appointment Insert**: Finally, a new entry is inserted into the `appointments` table, linking the professional and client, and setting the `startsAt`, `endsAt`, and `paymentStatus` (defaulting to `none`). The `status` is set to `confirmed` if `professional.autoConfirm` is true, otherwise it's `pending_confirmation`.

After a successful transaction, the system proceeds with notifications and analytics:
*   An in-app `notification` is created for the professional, indicating either a `booking_confirmed` or `booking_request`, depending on the `autoConfirm` setting.
*   WhatsApp messages are sent via `sendWhatsApp`. If the appointment is confirmed, the client receives a `msgBookingConfirmed` message, and the professional receives a `msgBookingConfirmedReceipt`. If pending, the professional receives a `msgBookingRequest` message.
*   If the professional has an `email` configured, an email notification is sent using `sendBookingRequestEmailToProfessional`.
*   Analytics events are captured using `capture` and `setOnce` from `@/lib/analytics`. A `booking_received_server` event is recorded, and `first_booking_at` is set for the professional if it's their first booking.

The endpoint concludes by returning a generic `{ success: true }` response, again using the `respondAfterFloor` utility to maintain the timing oracle mitigation. This equalized response prevents an attacker from inferring details about the newly created appointment or client ID.

## Design decisions

The design of the `/api/booking` endpoint reflects a careful balance between functionality, security, and user experience.

1.  **Data Minimization in GET**: The `GET` endpoint explicitly selects only `id` and `sessionDuration` from the `professionals` table. This choice was made to prevent accidental data leakage of sensitive professional information (like `email`, `phone`, `userId`, `plan`, `trialEndsAt`, `stripeCustomerId`, `stripeSubscriptionId`) to unauthenticated users. It adheres to the principle of least privilege, only exposing what is strictly necessary for the booking widget to function.
2.  **Concurrency Control with Serializable Transactions**: The `POST` endpoint's use of a `serializable` Drizzle transaction for the conflict check, client upsert, and appointment insert is a critical decision. This ensures that concurrent booking attempts for the same time slot are properly handled, preventing double-bookings. By forcing the database to detect phantom reads and fail one of the conflicting transactions with a `40001` SQLSTATE, the system maintains data integrity, even under high load.
3.  **Multi-layered Security for POST**:
    *   **Rate Limiting**: Implementing `getBookingLimiter` protects against brute-force attacks and general API abuse, ensuring fair usage for all clients.
    *   **Honeypot Field**: The `website` field in `bookingSchema` is a simple yet effective bot detection mechanism. By returning a fake success response, it discourages bots from further interaction without incurring database load.
    *   **Timing Oracle Mitigation**: The `respondAfterFloor` utility addresses a subtle security vulnerability. Without it, an attacker could potentially time the response to infer whether a client's phone number or email already exists in the database for a given professional. By normalizing response times, this side-channel attack is blunted.
    *   **Equalized Success Response**: Returning a generic `{ success: true }` for successful bookings, rather than the full appointment object, prevents information leakage. This ensures that an attacker cannot use the API to enumerate client IDs or other internal identifiers.
4.  **Multi-Channel Notifications**: The system integrates with WhatsApp and email for notifications, alongside in-app notifications. This provides a comprehensive communication strategy, ensuring that both clients and professionals receive timely updates regardless of their preferred communication channel. The branching logic based on `professional.autoConfirm` ensures consistent messaging whether the booking is immediately confirmed or requires manual approval.
5.  **Analytics Integration**: The inclusion of `capture` and `setOnce` calls demonstrates a commitment to understanding user behavior and business performance. Tracking `booking_received_server` and `first_booking_at` provides valuable data for funnel analysis and professional cohort tracking.

## Potential improvements

1.  **Backend Availability Calculation**: The `GET` endpoint currently returns raw `availability` rules and `existingAppointments`. The frontend then calculates the actual available slots. Moving this calculation logic to the backend (e.g., into a dedicated service or utility function) would centralize the business logic, reduce client-side complexity, and ensure consistent availability calculations across different client applications. This would also simplify testing and potentially improve performance by offloading computation from the client.
2.  **Explicit Timezone Handling**: The `date-fns` functions like `startOfDay` and `endOfDay` operate based on the server's local timezone. If professionals or clients are in different timezones, this could lead to discrepancies in how "today" is interpreted or how appointment times are stored and displayed. Implementing explicit timezone handling, perhaps by storing all timestamps in UTC and converting them to the professional's or client's local timezone for display and rule application, would prevent potential scheduling errors.
3.  **Robust Notification Retry Mechanism**: The `sendWhatsApp` and `sendBookingRequestEmailToProfessional` calls are wrapped in `.catch()` blocks, which log warnings if the sending fails. However, there is no retry mechanism. For critical communications like booking confirmations, a more robust system would queue these messages for asynchronous processing and implement retries with exponential backoff. This could involve using a dedicated message queue or a cron job to re-attempt failed notifications, improving the reliability of communication.
4.  **Structured Error Responses**: While `zod` validation errors provide detailed `fieldErrors`, other application-level errors like `SLOT_TAKEN` return a generic string message. Introducing structured error codes or more detailed error objects for these scenarios would allow the frontend to provide more specific user feedback, localize messages more effectively, or trigger different UI flows based on the error type.
