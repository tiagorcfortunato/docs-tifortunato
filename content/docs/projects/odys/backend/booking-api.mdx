# Booking API

The `/api/booking` endpoint serves as a central hub for managing appointment scheduling within the Odys platform. It allows clients to view a professional's available slots and subsequently book appointments. This endpoint is critical for the core functionality of the platform, bridging the gap between a professional's defined availability and a client's desire to schedule a session.

## Overview

The `src/app/api/booking/route.ts` file defines a Next.js API route that handles both `GET` and `POST` requests for the `/api/booking` path. The `GET` method is responsible for retrieving a professional's availability and existing appointments for a specific date, enabling clients to see open slots. The `POST` method facilitates the creation of new appointments, incorporating robust validation, plan-based limits, and concurrency control to ensure data integrity.

This endpoint interacts with several key database tables: `professionals`, `availability`, `appointments`, `clients`, and `notifications`. It uses Drizzle ORM for all database operations, ensuring type safety and a consistent data access layer. Beyond database interactions, the route integrates with external services for communication, sending WhatsApp messages via `sendWhatsApp` and emails via `sendBookingRequestEmailToProfessional`. It also incorporates rate limiting using `getBookingLimiter` to prevent abuse and analytics tracking with `capture` and `setOnce` for business insights.

## Retrieving Availability (GET)

The `GET` handler in `src/app/api/booking/route.ts` is designed to provide clients with the necessary information to choose an appointment slot. It expects two query parameters: `slug`, which identifies the professional, and `date`, specifying the day for which availability is requested.

If `slug` or `date` query parameters are missing, a `400` error is returned. Upon receiving a request, the system first queries the `professionals` table to find the professional associated with the provided `slug`. Crucially, it only selects the `id` and `sessionDuration` columns. This is a deliberate security measure to prevent sensitive professional data, such as `email`, `phone`, `userId`, `plan`, `trialEndsAt`, `stripeCustomerId`, or `stripeSubscriptionId`, from being exposed to unauthenticated users. If no professional is found, a `404` error is returned. Any other unexpected errors during the `GET` request processing are caught by `serverError` and result in a `500 Internal Server Error`.

Next, the handler performs two parallel database queries using `Promise.all` for efficiency. It fetches the professional's general `availability` rules from the `availability` table, which define their working hours for each `dayOfWeek`. Concurrently, it retrieves all existing `appointments` for that professional within the specified `date` range, specifically from `startOfDay` to `endOfDay`. Appointments with a `status` of `rejected` or `cancelled` are explicitly excluded, as these slots are considered available.

The response then combines these two sets of data: the `rules` (general availability) and `existingAppointments` (occupied slots), allowing the client-side logic to calculate and display the truly available time slots.

## Creating Appointments (POST)

The `POST` handler is responsible for processing new appointment requests. It begins by applying a rate limit using `getBookingLimiter` based on the client's IP address, returning a `429 Too Many Requests` if the limit is exceeded.

A notable design choice here is the `respondAfterFloor` function, which introduces a minimum response time of 250ms. This is a countermeasure against timing oracle attacks, where an attacker might infer information (e.g., whether a client already exists) by observing subtle differences in response times between database operations. By normalizing the response time, this signal is effectively blunted.

The incoming request body is validated using `bookingSchema`, a Zod schema that ensures `slug`, `startsAt`, `clientName`, and `clientPhone` are present and correctly formatted. If validation fails, a `400` error is returned with details about the invalid fields. An optional `clientEmail` is also validated. The schema includes a `website` field, which acts as a honeypot: if this hidden field is populated by a bot, the request is silently dropped, returning a fake success response to mislead the bot without interacting with the database.

After validation, the system retrieves the professional's full details from the `professionals` table using the `slug`. If the professional is not found, a `404` error is returned.

Before proceeding with the booking, the system checks the professional's subscription plan limits. It uses `effectivePlan` to determine the active plan (e.g., `basic`, `pro`, `premium`) and then consults the `PLANS` configuration, defaulting to `PLANS.free` if the effective plan does not map to a defined plan. It verifies if the professional has exceeded their `clients` limit or `appointmentsPerMonth` limit. If the client limit is reached, it checks if the current booking client is already an existing client of that professional. If limits are exceeded for a new client or monthly appointments, a `403 Forbidden` error is returned.

The core of the booking logic resides within a Drizzle `db.transaction` block, configured with a `serializable` isolation level. This is crucial for preventing race conditions. Inside the transaction:
1.  **Conflict Check**: The system first checks for any existing `appointments` that would overlap with the proposed `startsAt` and `endsAt` times, excluding `rejected` or `cancelled` appointments. If an overlap is detected, it throws a `SLOT_TAKEN` error, which is then caught and translated into a `409 Conflict` response.
2.  **Client Upsert**: It attempts to find an existing client in the `clients` table for the professional using either the `clientPhone` or `clientEmail`. If a client is found, it's used; otherwise, a new client record is inserted. If an existing client is found but their `email` is null and a `clientEmail` is provided in the request, the client's email is updated.
3.  **Appointment Insert**: Finally, a new record is inserted into the `appointments` table with the professional's ID, client's ID, start and end times, and a `status` determined by the professional's `autoConfirm` setting (either `confirmed` or `pending_confirmation`). The `paymentStatus` is initially set to `none`.

Following a successful transaction, the system dispatches various notifications. A new entry is added to the `notifications` table for the professional, alerting them of the new booking. Depending on whether the appointment was `autoConfirm`ed, different WhatsApp messages are sent: a confirmation to the client and a receipt to the professional if confirmed, or a booking request to the professional if pending. An email notification is also sent to the professional if their `email` is configured.

Finally, analytics events (`booking_received_server` and `first_booking_at`) are captured to track booking activity. The `POST` endpoint concludes by returning a generic `success: true` response, again equalized by `respondAfterFloor`, to avoid leaking any specific client or appointment details that could be exploited. Any other unexpected errors during the `POST` request processing are caught by `serverError` and result in a `500 Internal Server Error`.

## Design decisions

The design of the booking API prioritizes several key aspects:

*   **Security by Default**: The `GET` endpoint explicitly selects only the `id` and `sessionDuration` columns from the `professionals` table. This prevents accidental exposure of sensitive professional data to unauthenticated clients, adhering to the principle of least privilege.
*   **Concurrency Safety with Serializable Transactions**: The `POST` endpoint wraps its critical operations—conflict checking, client upsert, and appointment insertion—within a Drizzle `db.transaction` with a `serializable` isolation level. This is a strong guarantee that prevents race conditions where two simultaneous booking requests might otherwise successfully book the same slot. If a conflict occurs, one transaction will fail with a `40001` SQLSTATE, which the application translates into a user-friendly `409 Conflict` message.
*   **Timing Oracle Mitigation**: The `respondAfterFloor` utility on the `POST` endpoint adds a minimum delay to all responses. This design choice aims to obscure any timing differences that might arise from database operations (e.g., a faster lookup for an existing client versus an insert for a new one), making it harder for attackers to infer information about the system's state.
*   **Bot Detection with Honeypot**: The `website` field in the `bookingSchema` acts as a simple yet effective honeypot. Bots often fill all available form fields, including hidden ones. By checking if this field is populated, the system can identify and silently discard bot submissions, returning a fake success to prevent the bot from learning the trap.
*   **Plan-based Feature Gating**: The integration with `effectivePlan` and `PLANS` allows the system to dynamically enforce business rules, such as limits on the number of clients or monthly appointments, based on the professional's subscription tier. This is a fundamental aspect of the platform's monetization strategy.
*   **Unified Notification Flow**: The logic for sending WhatsApp and email notifications is centralized within the `POST` handler. This ensures that regardless of whether an appointment is auto-confirmed or pending, the correct sequence of communications is triggered, providing a consistent experience for both clients and professionals.

## Potential improvements

1.  **Availability Time Representation**: In the `availability` table, `startTime` and `endTime` are stored as `text`. While this works, using a dedicated `time` type (if supported by the database and Drizzle) or storing them as integers representing minutes from midnight could offer better type safety, easier comparison, and prevent potential parsing issues or inconsistencies if different text formats are used. This would affect the `availability` table schema and the logic within the `GET` handler that processes these times.
2.  **Refined Client Upsert Logic**: The current client upsert logic in the `POST` handler searches for an existing client by `phone` OR `email`. If a client is found by phone but has no email, and the booking request provides an email, that email is added to the existing client. This might lead to scenarios where a professional intends to have two distinct clients (e.g., a client with phone A and no email, and a new client with phone A and email B) but they are merged. Consider if `phone` should be the primary unique identifier for a client, or if a more explicit "find or create" strategy is needed that prioritizes `phone` and only creates a new client if no match is found by phone, regardless of email. This would involve reviewing the `clientConditions` array and the subsequent `if (!client)` and `else if (!client.email && clientEmail)` blocks.
3.  **Centralized Error Handling for Transactions**: The `POST` handler explicitly catches `SLOT_TAKEN` and the `40001` SQLSTATE for serializable transaction failures. While effective, other potential transaction-related errors might not be caught as specifically. A more centralized error handling strategy for Drizzle transactions could involve a dedicated utility function that maps common Drizzle/Postgres error codes to specific HTTP responses and user-friendly messages, reducing repetition and ensuring all transaction failures are handled gracefully. This would primarily impact the `catch (err)` block surrounding the `db.transaction`.
