# Booking API

The `/api/booking` endpoint serves as the central hub for managing appointment scheduling within Odys. It provides two primary functions: allowing clients to query a professional's availability and existing bookings for a specific date, and enabling the creation of new appointments. This dual functionality is critical for the user experience, supporting both the discovery of open slots and the finalization of a booking.

## Overview

The `/api/booking` route handles both `GET` and `POST` requests. The `GET` method is designed for clients to retrieve a professional's scheduling rules and currently booked appointments for a given day, enabling them to see available time slots. The `POST` method facilitates the actual booking process, encompassing input validation, professional and client data management, plan limit enforcement, and the atomic creation of the appointment itself.

This endpoint interacts with several Drizzle ORM tables: `professionals` to fetch details about the service provider, `availability` for their general working hours, `appointments` to check for existing bookings and record new ones, `clients` to manage client information, and `notifications` to alert professionals about new bookings. It also integrates with external services like WhatsApp for real-time messaging, email for professional notifications, and a rate limiting system to prevent abuse.

## GET Request: Fetching Availability

The `GET` request to `/api/booking` allows any visitor to query a professional's schedule. It expects two URL parameters: `slug`, identifying the professional, and `date`, specifying the day for which availability is requested.

Upon receiving a request, the system first queries the `professionals` table, selecting only the `id` and `sessionDuration` columns for the professional identified by the `slug`, limiting the result to one entry. This selective retrieval is a deliberate design choice to prevent the accidental exposure of sensitive professional data, such as `email`, `phone`, or `stripeCustomerId`, to unauthenticated users. If the professional is not found, a 404 error is returned.

Next, the endpoint concurrently fetches two sets of data:
1.  **Availability Rules**: It retrieves all entries from the `availability` table associated with the professional's `id`. These rules define the professional's general working hours for each `dayOfWeek`, specified by `startTime` and `endTime`.
2.  **Existing Appointments**: It queries the `appointments` table for all bookings linked to the professional's `id` within the specified `date`. Crucially, it filters out appointments with a `status` of `rejected` or `cancelled`, ensuring that only active or pending bookings are considered when determining available slots.

The response combines these `rules` and `existingAppointments`, allowing the client-side application to calculate and display the actual available booking slots.

## POST Request: Creating a Booking

The `POST` request to `/api/booking` is responsible for processing new appointment requests. This is a more complex operation, involving several steps to ensure data integrity, adherence to business rules, and proper notification.

### Rate Limiting and Timing Oracle Mitigation

Before processing the request body, the endpoint applies a rate limit using `getBookingLimiter` based on the client's IP address, obtained via `getIp(req)`. If the limit is exceeded, a `tooManyRequests` response is returned.

A notable design decision here is the implementation of `respondAfterFloor`. This utility introduces a minimum response time of 250 milliseconds. This is a countermeasure against timing oracle attacks, where an attacker might try to infer whether a client (identified by phone or email) already exists in the system by observing subtle differences in response times between database `SELECT` (faster) and `SELECT` + `INSERT` (slower) operations. By flooring the response time, this signal is obscured, making such enumeration attempts more difficult.

### Input Validation and Honeypot

The incoming request body is validated against the `bookingSchema` using Zod. This schema enforces requirements for `slug` (min 1 char), `startsAt`, `clientName` (min 2 chars), `clientPhone` (min 10 chars), and optionally `clientEmail`.

A `website` field is included in the `bookingSchema` as a honeypot. If this hidden field is populated in the request, it indicates a bot submission. In such cases, the endpoint immediately returns a fake success response (`{ success: true }`) after the `respondAfterFloor` delay, without interacting with the database. This strategy aims to trick bots into believing their submission was successful, preventing them from learning that the field is a trap and reducing database load from malicious requests.

### Professional Lookup and Plan Limits

The professional is retrieved from the `professionals` table using the provided `slug`, limiting the result to one entry. If not found, a 404 error is returned.

The system then checks the professional's subscription plan against booking limits. Using `effectivePlan` and the `PLANS` configuration, it verifies if the professional has exceeded their allowed number of `clients` or `appointmentsPerMonth`. If a limit is reached, and the booking is for a new client or would exceed the monthly appointment count, a 403 Forbidden response is returned.

### Atomic Transaction for Booking

The core of the booking logic resides within a Drizzle `db.transaction` with an `isolationLevel` of `"serializable"`. This is a critical design choice to prevent race conditions. In a serializable transaction, concurrent transactions appear to execute one after another, ensuring that if two users attempt to book the same slot simultaneously, one will succeed and the other will fail with a `SQLSTATE 40001` error (serialization failure).

Inside the transaction:
1.  **Conflict Check**: The system checks the `appointments` table for any existing appointments that would overlap with the proposed `startsAt` and `endsAt` times for the professional. Appointments with `rejected` or `cancelled` statuses are ignored. If a conflict is found, a custom `"SLOT_TAKEN"` error is thrown, which is then caught and translated into a 409 Conflict response.
2.  **Client Upsert**: The system attempts to find an existing client in the `clients` table for the given `professionalId` using either the `clientPhone` or `clientEmail`. If a client is found, their `email` is updated if it was previously null and a new email is provided. If no client is found, a new entry is inserted into the `clients` table.
3.  **Appointment Insert**: Finally, the new appointment is inserted into the `appointments` table, linking it to the professional and the (new or existing) client. The `status` of the appointment is set to `"confirmed"` if `professional.autoConfirm` is true, otherwise it's set to `"pending_confirmation"`, and `paymentStatus` is set to "none".

### Notifications and Analytics

After a successful booking, the system dispatches several notifications:
*   An entry is added to the `notifications` table for the professional, indicating a `"booking_confirmed"` or `"booking_request"` depending on the `autoConfirm` setting.
*   WhatsApp messages are sent via `sendWhatsApp`. If `autoConfirm` is true, the client receives a `msgBookingConfirmed` and the professional receives a `msgBookingConfirmedReceipt`. If `autoConfirm` is false, the professional receives a `msgBookingRequest` to prompt their action.
*   If the professional has an `email` configured, an email notification is sent using `sendBookingRequestEmailToProfessional`.

Finally, analytics events are captured using `capture` and `setOnce`. A `"booking_received_server"` event is recorded, attributed to the `professional.id`, along with properties like `slug`, `plan`, and `auto_confirmed`. A `first_booking_at` property is set once for each professional to track their initial booking timestamp.

The `POST` request concludes by returning `{ success: true }` after the `respondAfterFloor` delay. This response intentionally omits specific appointment details like `clientId` or `appointmentId` to avoid leaking information that could be used by an attacker to enumerate client lists.

## Design decisions

*   **Selective Column Retrieval in GET**: In the `GET` request, the `professionals` table query explicitly selects only `id` and `sessionDuration`. This was a conscious decision to prevent sensitive data like `email`, `phone`, `userId`, `plan`, `trialEndsAt`, `stripeCustomerId`, and `stripeSubscriptionId` from being exposed to unauthenticated clients, which was a potential vulnerability in previous iterations.
*   **Serializable Transaction for POST**: The `POST` request wraps the conflict check, client upsert, and appointment insertion in a Drizzle `db.transaction` with `isolationLevel: "serializable"`. This choice directly addresses the challenge of concurrent booking requests. By forcing transactions to behave as if they execute sequentially, it eliminates race conditions where multiple users might simultaneously pass a conflict check and then attempt to book the same slot, ensuring data consistency and preventing double-bookings.
*   **Timing Oracle Mitigation with `respondAfterFloor`**: The introduction of a 250ms response time floor via `respondAfterFloor` is a security-conscious design. It blunts the timing oracle signal that could arise from the performance difference between a database `SELECT` (for an existing client) and a `SELECT` followed by an `INSERT` (for a new client). This makes it harder for malicious actors to infer client existence based on response times.
*   **Honeypot Field for Bot Detection**: The `website` field in the `bookingSchema` acts as a simple, yet effective, honeypot. By returning a fake success response for submissions that populate this hidden field, the system can silently discard bot traffic without revealing its detection mechanism, thus reducing noise and protecting database resources.
*   **Unified Notification Logic**: The branching logic based on `professional.autoConfirm` for sending WhatsApp and in-app notifications ensures a consistent communication flow, while email notifications are always sent as booking requests. This mirrors the behavior of the AI concierge bot, providing a uniform experience regardless of how the booking was initiated.

## Potential improvements

*   **Backend-Driven Availability Calculation**: The `GET` endpoint currently returns raw `availability` rules and `existingAppointments`. The client-side then interprets these to determine available slots. Moving the slot calculation logic to the backend (e.g., a dedicated function that takes rules and existing appointments and returns concrete available time slots) could simplify client-side code, centralize complex scheduling logic, and make it easier to implement more sophisticated availability rules (e.g., lunch breaks, irregular exceptions) without requiring client-side updates. This would involve modifying the `GET` handler in `src/app/api/booking/route.ts`.
*   **Enhanced Error Detail for Plan Limits**: When a professional hits a plan limit (e.g., `clientCount >= plan.limits.clients`), the current `POST` request returns a generic "Limite de clientes atingido para este profissional." error. While functional, providing more specific details in the error response (e.g., the exact limit, the current count, or a link to upgrade) could improve the user experience for both the client attempting to book and the professional managing their account. This would involve refining the `NextResponse.json` calls within the plan limit checks in `src/app/api/booking/route.ts`.
*   **Explicit Timezone Handling**: The `date-fns` functions like `startOfDay` and `endOfDay` used in the `GET` request and `startOfMonth`, `endOfMonth` in the `POST` request operate based on the server's local timezone. For a global application or one where professionals and clients might be in different timezones, this could lead to subtle bugs or misunderstandings. Implementing explicit timezone handling, perhaps by storing all timestamps in UTC and converting them to the professional's or client's local timezone for display and calculation, would make the system more robust. This would require changes to how `Date` objects are constructed and manipulated throughout `src/app/api/booking/route.ts`.
