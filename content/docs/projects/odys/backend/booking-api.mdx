# Booking API

The `/api/booking` endpoint serves as the central hub for managing appointment bookings within Odys. It handles two primary operations: allowing clients to query a professional's availability for a specific date via a `GET` request, and enabling the creation of new appointments through a `POST` request. This dual functionality is critical for the user experience, providing both the necessary information to schedule and the mechanism to finalize a booking.

## Overview

This API route, located at `src/app/api/booking/route.ts`, orchestrates interactions with several core database tables to facilitate the booking process. It relies on the `professionals` table to identify the service provider, the `availability` table to understand their working hours, the `appointments` table to manage scheduled sessions, and the `clients` table to track customer information. New bookings also trigger entries in the `notifications` table to alert professionals.

The implementation uses Drizzle ORM for database operations, ensuring type safety and a consistent interface for data manipulation. Beyond database interactions, the endpoint integrates with external services for communication, such as WhatsApp for sending booking confirmations and requests, and an email service for professional notifications. It also incorporates a rate limiter to prevent abuse and analytics tracking to monitor booking activity.

## GET Request: Fetching Availability

The `GET` method for `/api/booking` is designed to provide a professional's available time slots for a given day. Clients typically use this to display a calendar interface where they can select a suitable appointment time.

The request expects two URL parameters: `slug`, which uniquely identifies the professional, and `date`, specifying the day for which availability is being queried. If either of these parameters is missing, the API responds with a `400 Bad Request` error.

Upon receiving a valid request, the system first queries the `professionals` table to retrieve the professional's `id` and `sessionDuration` based on the provided `slug`. A deliberate design choice here is to select only these two columns, rather than all professional data. This prevents sensitive information like `email`, `phone`, `userId`, `plan`, `trialEndsAt`, `stripeCustomerId`, or `stripeSubscriptionId` from being exposed to unauthenticated users, which was a potential data leak in previous iterations.

Next, the API concurrently fetches two sets of data using `Promise.all`:
1.  **Availability Rules**: It retrieves the `dayOfWeek`, `startTime`, and `endTime` from the `availability` table for the identified professional. These rules define the professional's general working hours.
2.  **Existing Appointments**: It queries the `appointments` table for all existing appointments for that professional within the specified date range (from `startOfDay` to `endOfDay`). Crucially, it filters out appointments with `rejected` or `cancelled` statuses, as these slots are considered available.

The response then combines these `rules` and `existingAppointments`, allowing the client-side application to calculate and display the actual available booking slots by subtracting occupied times from the general availability rules.

## POST Request: Creating a Booking

The `POST` method at `/api/booking` is responsible for processing new appointment requests, handling everything from input validation to database persistence and notification delivery.

The process begins with **rate limiting** using `getBookingLimiter` and `getIp(req)`. This mechanism helps protect the endpoint from excessive requests, returning a `429 Too Many Requests` response if limits are exceeded.

To mitigate potential **timing oracle attacks**, a `respondAfterFloor` function is employed. This function ensures that the API response time is artificially padded to a minimum of 250ms. This design choice aims to obscure timing differences between database operations (e.g., a faster lookup for an existing client versus a slower insert for a new one), preventing attackers from inferring information based on response latency.

The request body undergoes strict **validation** using `bookingSchema`, a Zod schema. This schema ensures that `slug`, `startsAt`, `clientName`, and `clientPhone` are present and correctly formatted. `clientEmail` is optional. A notable inclusion in the schema is a `website` field, which acts as a **honeypot**. If this hidden field is populated by a bot, the request is immediately discarded, and a fake `success: true` response is returned, preventing database interaction and signaling to the bot that the submission was "successful."

After validation, the professional's full record is retrieved from the `professionals` table using the provided `slug`. If the professional is not found, a `404 Not Found` error is returned.

**Plan limits** are then checked using `effectivePlan` and `PLANS`. The system verifies if the professional's current plan (e.g., `free`, `basic`, `pro`, `premium`) allows for new clients or additional monthly appointments. If the `clientCount` or `monthlyCount` exceeds the plan's limits, and the client is new, a `403 Forbidden` error is returned.

The core of the booking creation happens within a **database transaction** with a `serializable` isolation level. This is a critical design decision to prevent race conditions. Previously, conflict checks, client upserts, and appointment inserts were separate queries, which could lead to two concurrent requests successfully booking the same slot. By wrapping these operations in a `serializable` transaction, the database guarantees that concurrent transactions will not interfere with each other, and one will fail with a `40001` SQLSTATE if a conflict is detected.

Inside the transaction:
1.  **Conflict Check**: The system verifies that the proposed `startsAt` and `endsAt` times do not overlap with any existing, non-rejected or non-cancelled appointments for the professional. If a conflict is found, a `SLOT_TAKEN` error is thrown, which is then caught and translated into a `409 Conflict` response.
2.  **Client Upsert**: The system attempts to find an existing client associated with the professional using either the `clientPhone` or `clientEmail`. If a client is found, their `email` is updated if it was previously null. If no existing client is found, a new entry is created in the `clients` table.
3.  **Appointment Insert**: Finally, the new appointment is inserted into the `appointments` table, with its `status` set to `confirmed` if `professional.autoConfirm` is true, or `pending_confirmation` otherwise. The `paymentStatus` is initialized to `none`.

Following a successful appointment creation, the system dispatches various **notifications**:
*   A new entry is added to the `notifications` table for the professional, alerting them of a new booking.
*   WhatsApp messages are sent via `sendWhatsApp` using templates like `msgBookingConfirmed` (to client), `msgBookingConfirmedReceipt` (to professional), or `msgBookingRequest` (to professional for pending bookings). These are handled asynchronously with `.catch` blocks to prevent blocking the main request flow if a WhatsApp message fails.
*   An email notification is sent to the professional using `sendBookingRequestEmailToProfessional` if their `email` is available.

Finally, **analytics events** are captured using `capture` and `setOnce` from `@/lib/analytics`. These events track `booking_received_server` and record the `first_booking_at` timestamp for the professional, aiding in funnel analysis and understanding professional engagement.

The `POST` request concludes by returning an **equalized success response** (`{ success: true }`). This generic response is another security measure, preventing the leakage of specific appointment details (like `clientId`) that could be exploited by an attacker to infer information about existing clients.

## Design decisions

The `/api/booking` endpoint incorporates several deliberate design choices to enhance security, data integrity, and user experience:

*   **GET: Selective Column Retrieval**: The `GET` request for availability explicitly selects only `id` and `sessionDuration` from the `professionals` table. This was a conscious decision to prevent the accidental exposure of sensitive professional data (e.g., `userId`, `email`, `stripeCustomerId`) to unauthenticated clients, which was a vulnerability in an earlier version of the code.
*   **POST: Serializable Transaction for Booking**: The entire booking creation process, encompassing conflict checking, client upsert, and appointment insertion, is wrapped in a Drizzle `transaction` with a `serializable` isolation level. This is crucial for preventing race conditions. Without it, two users could simultaneously check for availability, find a slot open, and both attempt to book it, leading to a double-booking. The `serializable` isolation level forces the database to re-evaluate conditions, ensuring that only one booking succeeds for a given slot, with the other failing gracefully with a `409 Conflict` error.
*   **POST: Timing Oracle Mitigation**: The `respondAfterFloor` function introduces an artificial delay to the `POST` response. This design choice aims to obscure any timing differences that might arise from database operations (e.g., a faster `SELECT` for an existing client versus a `SELECT` followed by an `INSERT` for a new client). By normalizing response times, it becomes harder for an attacker to use timing analysis to infer whether a client's phone number or email is already registered with a professional.
*   **POST: Honeypot Field for Bot Detection**: The `website` field in the `bookingSchema` acts as a simple yet effective honeypot. It's a hidden field on the frontend that legitimate users won't fill. If a bot populates this field, the server immediately detects it and returns a fake success response without processing the booking or interacting with the database. This efficiently filters out automated spam without requiring complex CAPTCHAs.
*   **POST: Equalized Success Response**: The `POST` endpoint returns a generic `{ success: true }` upon successful booking, regardless of whether a new client was created or an existing one was used. This prevents the response body from leaking information such as the `clientId`, which could be used by an attacker to map phone numbers or emails to existing client records.

## Potential improvements

1.  **Asynchronous Notification Processing**: The `sendWhatsApp` and `sendBookingRequestEmailToProfessional` calls in the `POST` handler are dispatched asynchronously with `.catch` blocks. While `catch` blocks handle individual failures, these operations can add latency to the API response. Moving these to a background job or message queue (e.g., using a dedicated worker or a serverless function triggered by a database event) would decouple the notification process from the main request, reducing response times and improving the overall resilience of the booking flow. This would involve modifying `src/app/api/booking/route.ts` to dispatch events instead of directly calling `sendWhatsApp` and `sendBookingRequestEmailToProfessional`.
2.  **GET: Caching Availability Data**: The `GET` endpoint queries `availability` rules and `existingAppointments` on every request. For popular professionals, this could lead to repeated database load. Implementing a short-term cache (e.g., 5-10 minutes) for availability rules and upcoming appointments for a given professional and date could significantly reduce database hits. This would involve introducing a caching layer (e.g., Redis) and modifying the `GET` function in `src/app/api/booking/route.ts` to check the cache before querying the database.
3.  **POST: Enhanced Payment Integration**: The `paymentStatus` column in the `appointments` table is currently set to `none`. While the system has Stripe integration (as indicated by `stripeWebhookEvents` and `PLANS`), the booking flow does not yet initiate a payment. Integrating a payment intent creation or checkout session directly into the `POST` transaction, perhaps conditionally based on the professional's `paymentType` or `sessionPrice`, would allow for immediate payment processing upon booking. This would involve extending the transaction logic in `src/app/api/booking/route.ts` to interact with the Stripe API.
4.  **POST: Granular Analytics Events**: The `booking_received_server` event is a good start, but more granular events could provide deeper insights. For instance, separate events like `booking_confirmed_server` and `booking_pending_server` could be emitted based on `professional.autoConfirm`. Additionally, tracking the source of the booking (e.g., "web form", "concierge bot") could be added as a property to these events. This would involve modifying the `capture` calls in `src/app/api/booking/route.ts` to include more specific event names or properties.
