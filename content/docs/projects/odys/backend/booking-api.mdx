# Booking API

The `/api/booking` endpoint serves as a critical interface for managing appointments within the Odys platform. It facilitates two primary operations: allowing potential clients to query a professional's availability for a specific date and enabling the creation of new appointments. This endpoint interacts extensively with the core scheduling and client management tables, including `professionals`, `availability`, `appointments`, `clients`, and `notifications`, ensuring that the booking process is both functional and well-integrated into the broader system.

## Overview

This API route is central to the client-facing booking experience. The GET request provides the necessary data for a user interface to display available time slots, while the POST request handles the complex logic of creating a new appointment, managing client records, enforcing subscription plan limits, and triggering various notifications. The design prioritizes data integrity, security, and a smooth user experience, even under concurrent booking attempts.

## GET /api/booking

The GET method of the `/api/booking` endpoint is designed to provide a professional's scheduling rules and existing appointments for a given day. This information allows a client-side application to render an accurate calendar of available booking slots.

A request to this endpoint expects two query parameters: `slug`, which uniquely identifies the professional, and `date`, specifying the day for which availability is being queried. If either of these parameters is missing, the API responds with a `400` status, indicating invalid parameters.

Upon receiving a valid request, the system first queries the `professionals` table to retrieve the professional's `id` and `sessionDuration`. This is a deliberate choice to select only the strictly necessary columns, preventing the accidental exposure of sensitive professional data such as `email`, `phone`, `userId`, `plan`, `trialEndsAt`, `stripeCustomerId`, or `stripeSubscriptionId` to unauthenticated users. If no professional matches the provided `slug`, a `404` status is returned.

Subsequently, two parallel database queries are executed:
1.  The `availability` table is queried to fetch all scheduling rules (`dayOfWeek`, `startTime`, `endTime`) associated with the professional. These rules define the professional's general working hours.
2.  The `appointments` table is queried to retrieve all existing appointments for the professional within the specified `date`. Crucially, this query filters out appointments with a `status` of `rejected` or `cancelled`, ensuring that only active or pending bookings are considered when determining available slots.

The endpoint then returns a JSON object containing both the `rules` and `existingAppointments`, allowing the client application to combine this information and present the user with the actual available time slots.

## POST /api/booking

The POST method is responsible for the creation of new appointments. This is a more complex operation, involving several steps to ensure data validity, prevent conflicts, and integrate with other system components like notifications and analytics.

The process begins with a rate limit check using `getBookingLimiter` and the client's IP address (`getIp(req)`). If the rate limit is exceeded, a `429` (Too Many Requests) response is immediately returned.

To mitigate timing attacks, particularly those that could infer whether a client already exists in the database, the system introduces a response-time floor. All successful or "fake-successful" responses are delayed to ensure a minimum response time of 250ms, making it harder for attackers to distinguish between different database operations based on response latency.

The incoming request body is first validated against `bookingSchema` using Zod. This schema enforces requirements for `slug`, `startsAt`, `clientName`, `clientPhone`, and optionally `clientEmail`. It also includes a `website` field, which acts as a honeypot: if this field is populated, the request is identified as a bot submission, and a fake success response is returned without any database interaction.

Next, the professional is retrieved from the `professionals` table using the provided `slug`. If the professional is not found, a `404` error is returned.

Before proceeding with the booking, the system checks for plan-based limits. It determines the `effectivePlan` for the professional, considering their current `plan` and `trialEndsAt` date. Based on the limits defined in `PLANS`, it checks:
*   The total number of clients associated with the professional against `plan.limits.clients`. If the limit is reached, a new client cannot be added unless the booking is for an existing client.
*   The number of appointments booked within the current month against `plan.limits.appointmentsPerMonth`.

If any of these limits are exceeded for a new client or appointment, a `403` (Forbidden) status is returned.

The core booking logic is wrapped in a Drizzle ORM database transaction with `isolationLevel: "serializable"`. This is a critical design choice to prevent race conditions. In a serializable transaction, concurrent transactions appear to execute serially, preventing phantom reads and ensuring that if two users attempt to book the same slot simultaneously, only one will succeed.

Inside the transaction:
1.  A conflict check is performed on the `appointments` table. It verifies that no existing, non-rejected, non-cancelled appointment for the professional overlaps with the proposed `startsAt` and `endsAt` times. If a conflict is detected, a custom error "SLOT_TAKEN" is thrown, which is then caught and translated into a `409` (Conflict) HTTP response.
2.  The client record is upserted. The system attempts to find an existing client for the professional using either the `clientPhone` or `clientEmail`. If a client is found, their record is updated (e.g., adding an email if it was previously null). If no client is found, a new entry is inserted into the `clients` table.
3.  Finally, the new appointment is inserted into the `appointments` table. The `status` is set to `confirmed` if `professional.autoConfirm` is true, otherwise it defaults to `pending_confirmation`. The `paymentStatus` is initialized to `none`.

After the transaction commits, a series of post-booking actions are triggered:
*   A notification is inserted into the `notifications` table for the professional, informing them of a new booking request or a confirmed appointment.
*   WhatsApp messages are sent via `sendWhatsApp` to the client (if confirmed) and the professional (either a booking request or a confirmation receipt), using templates like `msgBookingRequest`, `msgBookingConfirmed`, and `msgBookingConfirmedReceipt`.
*   If the professional has an `email` address, an email notification is sent using `sendBookingRequestEmailToProfessional`.
*   Analytics events are captured using `capture` and `setOnce` to track "booking_received_server" and the `first_booking_at` for the professional.

The final response for a successful POST request is an equalized `{ success: true }` JSON object, again to avoid leaking information (like the newly created `clientId`) that could be exploited by an attacker.

## Design decisions

*   **Selective Column Retrieval in GET**: The GET endpoint explicitly selects only `id` and `sessionDuration` from the `professionals` table. This was a deliberate choice to prevent information leakage, as the previous implementation returned all professional data, including sensitive fields like `email`, `phone`, and `Stripe` IDs, to any unauthenticated caller.
*   **Rate Limiting**: The `getBookingLimiter` is applied to the POST endpoint to prevent abuse, such as denial-of-service attacks or rapid-fire booking attempts, by restricting the number of requests from a single IP address within a given window.
*   **Response-Time Floor**: The `respondAfterFloor` utility introduces a minimum response time for POST requests. This design choice directly addresses the risk of timing side-channel attacks, where an attacker might infer information (e.g., whether a client already exists) by measuring subtle differences in response times between different database operations.
*   **Honeypot Field**: The `website` field in `bookingSchema` acts as a simple yet effective bot detection mechanism. Bots often fill all available form fields, including hidden ones, allowing the system to silently discard malicious submissions without engaging in complex CAPTCHA challenges.
*   **Zod Validation**: Using Zod for schema validation (`bookingSchema`) provides a clear, declarative way to define expected input shapes and types. This improves code readability, maintainability, and ensures that only well-formed data proceeds to the business logic.
*   **Atomic Transaction with Serializable Isolation**: The entire booking process within the POST endpoint is wrapped in a Drizzle transaction with `isolationLevel: "serializable"`. This is a crucial decision for data consistency, especially in a multi-user environment. It guarantees that concurrent booking attempts for the same time slot or client upserts do not lead to race conditions or inconsistent data, effectively preventing double-bookings. The explicit handling of `SLOT_TAKEN` and the `40001` SQLSTATE code (serialization failure) ensures a clear error response to the user.
*   **Plan Limit Enforcement**: Integrating `effectivePlan` and `PLANS` directly into the POST flow ensures that subscription tier limits (e.g., `clients` count, `appointmentsPerMonth`) are respected at the point of booking, preventing professionals from exceeding their plan's allowances.
*   **Unified Notification Flow**: The system ensures consistent communication by triggering notifications (in-app, WhatsApp, email) regardless of whether the booking was auto-confirmed or requires manual approval. This mirrors the behavior of the AI concierge, providing a cohesive experience.
*   **Equalized POST Response**: The POST endpoint returns a generic `{ success: true }` without including details like the `clientId` or the full appointment object. This is a security measure to prevent an attacker from using the API to enumerate existing client IDs by observing differences in the response body.

## Potential improvements

*   **Server-Side Availability Calculation**: The GET endpoint currently returns raw `rules` and `existingAppointments`. The client-side application is then responsible for calculating the actual available time slots. Moving this calculation logic to the server could centralize the business logic, reduce client-side complexity, and ensure consistent availability determination across different client applications.
*   **Client ID in POST Response for Authenticated Users**: While the equalized response for POST requests is a good security measure against anonymous attackers, it might complicate client-side workflows for *authenticated* users (e.g., a professional's dashboard) who might need the `clientId` or `appointmentId` immediately after booking for follow-up actions. A conditional response that includes these IDs for authenticated requests could improve UX without compromising public security.
*   **Internationalization of Error Messages**: The error messages, such as "Parâmetros inválidos" or "Este horário acabou de ser preenchido por outra pessoa. Por favor, escolha outro horário.", are hardcoded in Portuguese. Implementing an internationalization (i18n) system would allow these messages to be dynamically translated based on the client's locale, improving the user experience for a global audience.
*   **Structured Time Representation for Availability**: The `availability` table stores `startTime` and `endTime` as `text`. While functional, using a more structured data type (e.g., a dedicated `TIME` type in PostgreSQL or storing minutes from midnight as an `integer`) could simplify time-based calculations, prevent parsing errors, and improve database query efficiency for time-based operations.
