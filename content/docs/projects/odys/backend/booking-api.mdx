# Booking API

The `/api/booking` endpoint is a critical component of the Odys platform, serving as the gateway for clients to view a professional's availability and schedule new appointments. It encapsulates the core logic for managing time slots, handling client information, enforcing business rules, and orchestrating various notification mechanisms. This endpoint is designed to be both publicly accessible for availability checks and securely managed for booking submissions, integrating with several backend services to provide a cohesive scheduling experience.

## Overview

This endpoint provides two primary functionalities:
*   **GET requests** allow any visitor to query a professional's available time slots for a specific date. This is essential for the booking widget on a professional's public profile.
*   **POST requests** facilitate the creation of new appointments. This involves validating the booking request, checking against the professional's plan limits, ensuring no time conflicts, managing client records, and triggering a cascade of notifications.

The implementation relies heavily on Drizzle ORM for interacting with the PostgreSQL database, specifically targeting the `professionals`, `availability`, `appointments`, `clients`, and `notifications` tables. Beyond database operations, it integrates with external services for communication (WhatsApp, email) and internal systems for analytics and rate limiting. The design prioritizes data integrity, concurrency safety, and a degree of bot mitigation.

## GET Request: Fetching Availability

The GET handler for `/api/booking` is responsible for providing the necessary data for a client-side booking widget to display available time slots.

A client initiates this request by providing a professional's `slug` and a `date` string as URL search parameters. The system first queries the `professionals` table to retrieve the `id` and `sessionDuration` for the specified professional. A deliberate design choice here is to select only these two columns, preventing the accidental exposure of sensitive professional data like `email`, `phone`, `userId`, or `plan` to unauthenticated users. If the professional is not found, a `404` error is returned.

Once the professional is identified, the endpoint performs two concurrent database queries using `Promise.all`:
1.  It fetches the professional's `availability` rules from the `availability` table, which define the general working hours for each `dayOfWeek` with `startTime` and `endTime` values.
2.  It retrieves all `existingAppointments` for the given `date` from the `appointments` table. Crucially, it filters out appointments with a `status` of `rejected` or `cancelled`, ensuring that only genuinely occupied or pending slots are considered.

The response then bundles these `rules` and `existingAppointments`, allowing the frontend to calculate and display the actual bookable slots based on the professional's `sessionDuration` and the defined availability.

## POST Request: Creating a Booking

The POST handler for `/api/booking` is a more complex operation, orchestrating several steps to securely and reliably create a new appointment.

Upon receiving a request, the system first applies a rate limit using `getBookingLimiter` and the client's IP address obtained via `getIp`. If the limit is exceeded, a `429 Too Many Requests` response is returned. To mitigate timing oracle attacks, where an attacker could infer information based on response times, the `respondAfterFloor` utility ensures a minimum response time of 250ms, making it harder to distinguish between different backend processing paths.

The incoming request body undergoes strict validation using `bookingSchema`, a Zod schema. This ensures that `slug`, `startsAt`, `clientName`, and `clientPhone` are present and correctly formatted, with `clientEmail` being optional. A "honeypot" field named `website` is also included in the schema; if this hidden field is populated by a bot, the request is silently dropped, returning a fake success response to deter further attempts without engaging the database.

After validation, the system fetches the full `professional` record using the provided `slug`. It then checks the professional's current plan and its associated limits using `effectivePlan` and `PLANS`. If the professional's plan has limits on the number of `clients` or `appointmentsPerMonth`, the system queries the `clients` and `appointments` tables to verify that the new booking would not exceed these thresholds. If a client limit is hit, a `403 Forbidden` response is returned only if the booking is for a new client that would exceed the threshold.

The core of the booking creation is wrapped in a Drizzle `transaction` with `serializable` isolation level. This is a critical design choice to prevent race conditions. Without it, two simultaneous booking requests for the same slot could both pass initial checks and attempt to insert, leading to double-bookings. The `serializable` isolation level forces the database to re-evaluate reads if the underlying data changes, causing one of the conflicting transactions to fail with a `40001` SQLSTATE, which is then caught and returned as a `409 Conflict` error with a user-friendly message.

Inside the transaction:
1.  A `conflict` check is performed on the `appointments` table to ensure the requested `startsAt` and `endsAt` (calculated using `professional.sessionDuration`) do not overlap with any existing, non-rejected/cancelled appointments for the professional. If a conflict is found, a `SLOT_TAKEN` error is thrown, which the outer `try-catch` block handles.
2.  The client is then "upserted." The system attempts to find an existing client associated with the professional using either the `clientPhone` or `clientEmail`. If a client is found, and their `email` is missing but provided in the current request, the client's email is updated. If no existing client is found, a new entry is inserted into the `clients` table.
3.  Finally, the new appointment is inserted into the `appointments` table, linking it to the professional and the (new or existing) client. The `status` of the appointment is set to `confirmed` if `professional.autoConfirm` is true, otherwise it defaults to `pending_confirmation`.

Following a successful transaction, a series of notifications are dispatched:
*   An in-app notification is created in the `notifications` table for the professional, indicating a `booking_confirmed` or `booking_request` depending on the `autoConfirm` setting.
*   WhatsApp messages are sent via `sendWhatsApp` using templates like `msgBookingConfirmed`, `msgBookingConfirmedReceipt`, or `msgBookingRequest`, tailored to whether the booking was auto-confirmed or requires professional approval.
*   If the professional has an `email` configured, an email notification is sent using `sendBookingRequestEmailToProfessional`.

To provide valuable insights, analytics events are captured using `capture` and `setOnce`. A `booking_received_server` event is recorded, attributing it to the `professional.id`, and `first_booking_at` is set once for new professionals to track their initial booking activity.

The final response to the client is an equalized `success: true` message, regardless of whether a new client was created or an existing one was found. This prevents information leakage that could be exploited by attackers trying to enumerate existing client records.

## Design decisions

*   **Clear Separation of Concerns**: The GET and POST methods are distinctly separated, reflecting their different purposes: querying information versus modifying state. This aligns with REST principles and makes the API easier to understand and maintain.
*   **Selective Data Retrieval for GET**: By explicitly selecting only `id` and `sessionDuration` from the `professionals` table in the GET request, the system minimizes the risk of inadvertently exposing sensitive professional data to unauthenticated users. This is a strong security and privacy measure.
*   **Robust Input Validation with Zod**: The use of Zod for schema validation (`bookingSchema`) provides a declarative and type-safe way to ensure incoming data meets expectations. This prevents common vulnerabilities like injection attacks and improves data quality.
*   **Rate Limiting**: Implementing `getBookingLimiter` protects the endpoint from abuse, such as brute-force booking attempts or denial-of-service attacks, by restricting the number of requests from a single IP address within a given time window.
*   **Honeypot for Bot Mitigation**: The `website` field acts as a simple yet effective honeypot. Bots often fill all available form fields, including hidden ones. By detecting a populated `website` field, the system can discard bot submissions early without consuming significant resources or polluting the database, while still returning a `200 OK` to avoid signaling the bot that the field is a trap.
*   **Timing Oracle Mitigation**: The `respondAfterFloor` function is a subtle but important security enhancement. By ensuring a minimum response time, it obscures whether a client record already exists in the database, preventing attackers from using timing differences to enumerate client information.
*   **Atomic Transactions for Concurrency**: Wrapping the conflict check, client upsert, and appointment insertion in a Drizzle `transaction` with `serializable` isolation level is crucial for data integrity. This prevents race conditions where multiple concurrent requests might attempt to book the same slot, ensuring that only one succeeds and maintaining the consistency of the `appointments` table.
*   **Comprehensive Notification Strategy**: Utilizing multiple channels (in-app notifications, WhatsApp, email) for booking confirmations and requests enhances reliability and user experience. If one channel fails, others might still succeed, and users receive information through their preferred medium.
*   **Plan-Based Feature Gating**: Integrating `PLANS` and `effectivePlan` directly into the booking logic allows the system to enforce business rules and subscription limits dynamically. This ensures that professionals on different plans adhere to their respective client and appointment quotas.
*   **Equalized POST Response**: The POST endpoint returns a generic `success: true` without including the newly created appointment details (like `clientId`). This prevents an attacker from using the response body to infer information about existing clients, further enhancing privacy.

## Potential improvements

1.  **Backend Availability Calculation**: The GET endpoint currently returns raw `availability` rules and `existingAppointments`. The logic to combine these and calculate truly available slots for a given `sessionDuration` resides on the client side. Moving this calculation to the backend, perhaps into a dedicated service function, would centralize the business logic, ensure consistency across different client interfaces, and reduce the potential for client-side bugs or discrepancies in availability display. This would involve modifying the `GET` handler in `src/app/api/booking/route.ts` to return pre-calculated slots.
2.  **Enhanced Client Upsert Logic**: The current client upsert logic in the `POST` handler in `src/app/api/booking/route.ts` primarily uses `phone` or `email` to identify existing clients. For users who are logged in, incorporating `userId` into the client identification process could provide a more robust way to link bookings to authenticated users, preventing the creation of duplicate client records for the same user across different professionals or booking channels. This would require adjustments to the `client` upsert section within the `db.transaction` block.
3.  **Granular Error Handling**: The `serverError` helper in `src/lib/api.ts` provides a generic catch-all for errors. While useful, it can obscure the root cause of issues. Implementing more specific error types or codes for different failure scenarios (e.g., database connection issues, external API failures, unexpected data states) would significantly improve debugging and allow for more informative error messages to be returned to the client, enhancing the developer and user experience. This would involve refining the `catch (err)` blocks in `src/app/api/booking/route.ts` to differentiate error types.
4.  **Explicit Timezone Management**: The `date-fns` functions like `startOfDay` and `endOfDay` used in the GET request, and `new Date(startsAt)` in the POST request, operate based on the server's local timezone. If professionals, clients, and the server are in different timezones, this can lead to subtle and hard-to-debug issues with appointment scheduling and availability. Adopting a consistent timezone strategy, such as storing all timestamps in UTC and performing explicit timezone conversions for display and input, would make the system more resilient to global usage. This would impact how `dateStr` and `startsAt` are parsed and manipulated in `src/app/api/booking/route.ts`.
