# Booking API

The `/api/booking` endpoint serves as the central hub for managing appointment bookings within Odys. It exposes both a `GET` method for querying professional availability and existing appointments, and a `POST` method for submitting new booking requests. This endpoint is critical for the core functionality of the platform, enabling clients to schedule sessions with professionals and ensuring data integrity through careful validation and concurrency control.

## Overview

The `/api/booking` route orchestrates the complex process of scheduling appointments. The `GET` request allows any visitor to inspect a professional's schedule, providing the necessary data for a client-facing booking interface. The `POST` request, on the other hand, handles the creation of new appointments, involving several steps from input validation and bot detection to plan limit enforcement, atomic transaction processing, and various notification mechanisms. It interacts primarily with the `professionals`, `availability`, `appointments`, `clients`, and `notifications` tables in the database.

## GET Method: Fetching Availability

The `GET` method for `/api/booking` is designed to provide the necessary information for a client to view a professional's available slots on a given day. It expects two query parameters: `slug` to identify the professional and `date` to specify the day of interest.

Upon receiving a request, the endpoint first validates these parameters, returning a `400` status if either is missing. It then queries the `professionals` table, selecting only the `id` and `sessionDuration` columns for the professional identified by the `slug`. This selective column retrieval is a deliberate design choice to prevent sensitive professional data, such as `email`, `phone`, `userId`, `plan`, `trialEndsAt`, `stripeCustomerId`, or `stripeSubscriptionId`, from being exposed to unauthenticated users. If no professional is found, a `404` error is returned.

Next, the system fetches two sets of data concurrently using `Promise.all`:
1.  **Availability Rules**: It retrieves all entries from the `availability` table for the professional's `id`, which define their general working hours for each `dayOfWeek` with `startTime` and `endTime` ranges.
2.  **Existing Appointments**: It queries the `appointments` table for all appointments associated with the professional within the specified `date` range. Crucially, it filters out appointments with a `status` of `rejected` or `cancelled`, ensuring that only active or pending bookings are considered when calculating available slots.

The response combines these `rules` and `existingAppointments`, allowing the client-side logic to compute the actual bookable time slots. Any unexpected errors during this process are caught and handled by the `serverError` utility.

## POST Method: Creating a Booking

The `POST` method at `/api/booking` is responsible for processing new appointment requests. This is a multi-stage operation designed to ensure data integrity, prevent abuse, and provide timely notifications.

### Rate Limiting and Timing Oracle Mitigation

Before any processing begins, the request is subjected to a rate limit using `getBookingLimiter`. This limit is configured to allow 5 requests within a 10-minute window per IP address, identified by the `rl:booking` prefix. If the limit is exceeded, a `429 Too Many Requests` response is immediately returned.

A subtle but important design choice is the `respondAfterFloor` function. This utility introduces a minimum response time of 250 milliseconds for all `POST` requests. This measure is implemented to blunt a potential "timing oracle" attack. Without it, an attacker could distinguish between requests that result in a database `SELECT` (faster, if a client already exists) and those that require a `SELECT` followed by an `INSERT` (slower, for a new client). By equalizing the response time, the system makes it harder for an attacker to infer information about existing clients based on response latency.

### Input Validation and Honeypot

The incoming request body is validated against the `bookingSchema` using Zod. This schema ensures that `slug`, `startsAt`, `clientName` (min 2 chars), and `clientPhone` (min 10 chars) are present and correctly formatted. `clientEmail` is optional but validated if provided.

A clever anti-bot mechanism is implemented using a "honeypot" field named `website`. This field is hidden in the client-side form. If a bot populates this field, the server immediately returns a fake success response (`{ success: true }`) with a `200 OK` status, without ever touching the database. This makes the bot believe its submission was successful, discouraging further attempts, while protecting the system from spam.

### Professional Lookup and Plan Limits

The professional is retrieved from the `professionals` table using the provided `slug`. If the professional is not found, a `404` error is returned.

A critical business logic step involves checking the professional's subscription plan limits. The `effectivePlan` utility determines the professional's active plan, considering their `plan` and `trialEndsAt` date. The system then checks if the professional has exceeded their `clients` or `appointmentsPerMonth` limits, as defined in the `PLANS` configuration.
*   For client limits, it counts existing clients associated with the professional. If the limit is reached, a new client cannot be added unless the booking is for an existing client (checked by `clientPhone`).
*   For monthly appointment limits, it counts appointments within the current month.

If any limit is exceeded for a new client or appointment, a `403 Forbidden` response is returned.

### Atomic Booking Transaction

The core of the booking process is an atomic database transaction, executed with a `serializable` isolation level. This is a crucial design decision to prevent race conditions where two simultaneous booking requests might try to reserve the same time slot.

Within this transaction:
1.  **Conflict Check**: The system first checks for any existing appointments that would overlap with the proposed `startsAt` and `endsAt` times for the professional. It specifically excludes `rejected` and `cancelled` appointments from this check. If an overlap is detected, a `SLOT_TAKEN` error is thrown, which is then caught and translated into a `409 Conflict` response, informing the user that the slot was just taken. The `serializable` isolation level ensures that if two transactions try to read and then write to the same time slot, one will fail with a `40001` SQLSTATE error, preventing a phantom read.
2.  **Client Upsert**: The system attempts to find an existing client for the professional using either the `clientPhone` or `clientEmail`. If a client is found, their record is updated (e.g., adding an email if it was previously null). If no client is found, a new entry is inserted into the `clients` table.
3.  **Appointment Insertion**: Finally, a new record is inserted into the `appointments` table, linking it to the professional and client. The `status` of the appointment is set to `confirmed` if `professional.autoConfirm` is true, otherwise it's set to `pending_confirmation`. The `paymentStatus` defaults to `none`.

### Notifications and Analytics

After a successful booking, the system dispatches several notifications:
*   An entry is inserted into the `notifications` table for the professional, indicating a `booking_confirmed` or `booking_request` depending on the `autoConfirm` setting.
*   WhatsApp messages are sent:
    *   If `autoConfirm` is true, a `msgBookingConfirmed` message is sent to the client and a `msgBookingConfirmedReceipt` to the professional.
    *   If `autoConfirm` is false, a `msgBookingRequest` message is sent to the professional, prompting them to confirm the booking.
*   If the professional has an `email` configured, an email notification is sent to them with the booking details.

Finally, analytics events are captured using `capture` and `setOnce`. A `booking_received_server` event is recorded, attributing it to the professional's `id` and including properties like `slug`, `plan`, and `auto_confirmed`. The `first_booking_at` property is set once for each professional to track their initial booking timestamp.

The `POST` method concludes by returning an equalized `NextResponse.json({ success: true })` after the `respondAfterFloor` delay, ensuring consistency and preventing information leakage.

## Design decisions

The `/api/booking` endpoint incorporates several key design decisions to balance functionality, security, and performance:

*   **Minimal Data Exposure (GET)**: The `GET` endpoint explicitly selects only `id` and `sessionDuration` from the `professionals` table. This prevents accidental leakage of sensitive professional details to unauthenticated users, adhering to the principle of least privilege.
*   **Rate Limiting**: Implementing `getBookingLimiter` directly at the start of the `POST` handler protects the endpoint from brute-force attacks and excessive requests, preserving server resources.
*   **Timing Oracle Mitigation**: The `respondAfterFloor` function is a subtle but important security measure. By normalizing response times, it makes it significantly harder for attackers to infer information about the existence of client records through timing differences, enhancing privacy.
*   **Honeypot for Bot Detection**: The `website` field acts as a simple yet effective honeypot. This low-overhead mechanism allows the system to filter out automated bot submissions early in the `POST` request lifecycle, saving database operations and reducing spam.
*   **Atomic Transaction with `serializable` Isolation**: The use of `db.transaction` with `serializable` isolation for the booking creation process is critical. It guarantees that concurrent attempts to book the same slot will not lead to data corruption or double-bookings. The `serializable` level specifically prevents "phantom reads," ensuring that the conflict check remains valid throughout the transaction.
*   **Conditional Notifications**: The system intelligently branches its notification logic based on the `professional.autoConfirm` setting. This mirrors the behavior of the AI concierge bot, providing a consistent notification experience regardless of the booking channel.
*   **Equalized POST Response**: Similar to the timing oracle mitigation, the `POST` endpoint returns a generic `{ success: true }` without including specific appointment details like `clientId`. This prevents an attacker from using the response body to confirm whether a submitted phone/email pair corresponds to an existing client.

## Potential improvements

1.  **Centralize Client Upsert Logic**: The client upsert logic within the `POST` method's transaction (`src/app/api/booking/route.ts`, inside `db.transaction`) is specific to this endpoint. Extracting this into a dedicated service function (e.g., `upsertClient(professionalId, clientName, clientPhone, clientEmail)`) would improve reusability, testability, and readability, especially if client creation/update logic is needed elsewhere.
2.  **Refine Plan Limit Checks**: The plan limit checks in the `POST` method (`src/app/api/booking/route.ts`, where `plan.limits.clients` and `plan.limits.appointmentsPerMonth` are checked) involve multiple `if` conditions and database queries. This logic could be encapsulated in a dedicated `checkProfessionalLimits` function or a service layer that returns a clear status or throws a specific error, making the main `POST` handler cleaner and easier to reason about.
3.  **More Granular GET Error Responses**: The `GET` method currently returns a generic `"Parâmetros inválidos"` for missing `slug` or `dateStr` (`src/app/api/booking/route.ts`, `if (!slug || !dateStr)`). Providing more specific error messages, such as "Slug is missing" or "Date is missing/invalid," would enhance the developer experience for clients integrating with this API.
4.  **Consider a Dedicated Booking Service**: As the `POST` method grows in complexity with validation, rate limiting, honeypot, plan checks, transaction, and notifications, it might benefit from being refactored into a dedicated booking service class or module. This would separate concerns, making the route handler thinner and the business logic more modular and testable.
