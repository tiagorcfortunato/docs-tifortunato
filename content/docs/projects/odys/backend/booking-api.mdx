# Booking API

The `/api/booking` endpoint serves as the central hub for managing appointment bookings within Odys. It exposes both a `GET` method for retrieving a professional's availability and existing appointments, and a `POST` method for creating new appointments. This API is critical for both clients seeking to book services and professionals managing their schedules, integrating with various backend services for notifications, analytics, and payment plan enforcement.

## Overview

The booking API interacts with several core database tables to fulfill its responsibilities. The `professionals` table stores details about service providers, including their `sessionDuration` and `autoConfirm` preferences. The `availability` table defines the recurring time slots a professional is generally available. Crucially, the `appointments` table records all scheduled sessions, while the `clients` table manages client information. Finally, the `notifications` table is used to alert professionals about new bookings.

Beyond database interactions, the API integrates with external services:
*   **WhatsApp**: For sending booking confirmations, requests, and receipts using templates like `msgBookingRequest`, `msgBookingConfirmed`, and `msgBookingConfirmedReceipt`.
*   **Email**: To send booking request emails to professionals via `sendBookingRequestEmailToProfessional`.
*   **Stripe**: Indirectly, through the `PLANS` configuration, to enforce booking limits based on a professional's subscription plan.
*   **Analytics**: Using `capture` and `setOnce` to track booking events.
*   **Rate Limiting**: Employing `getBookingLimiter` to prevent abuse.

## GET /api/booking

The `GET` method for `/api/booking` allows a client to query a professional's schedule for a specific date. This is typically used by the booking widget on the frontend to display available slots.

A request to this endpoint requires two query parameters: `slug` to identify the professional and `date` to specify the day for which availability is being checked. If either of these parameters is missing, the API responds with a `400` status code, indicating invalid parameters.

Upon receiving a valid request, the system first queries the `professionals` table. A key design choice here is to select only the `id` and `sessionDuration` columns. This prevents sensitive professional data, such as `email`, `phone`, `userId`, or `stripeCustomerId`, from being exposed to unauthenticated users who might simply know a professional's `slug`. If no professional matches the provided `slug`, a `404` status is returned.

Next, the API concurrently fetches two sets of data:
1.  **Availability Rules**: It retrieves all entries from the `availability` table associated with the professional's `id`. These rules define the professional's general working hours for each `dayOfWeek`, specified by `startTime` and `endTime`.
2.  **Existing Appointments**: It queries the `appointments` table for all bookings linked to the professional within the `dayStart` and `dayEnd` of the requested date. Importantly, it filters out appointments with a `status` of `rejected` or `cancelled`, ensuring that only active or pending bookings are considered when determining available slots.

The endpoint then returns these `rules` and `existingAppointments` to the client, allowing the frontend to calculate and display the actual bookable time slots. Any unexpected errors during this process are caught and returned as a `500` server error.

## POST /api/booking

The `POST` method for `/api/booking` is responsible for creating new appointments. This is a more complex operation, involving validation, rate limiting, plan enforcement, and atomic database transactions.

The process begins with rate limiting, using `getBookingLimiter` and the client's IP address obtained via `getIp(req)`. If the rate limit is exceeded, a `429` status code is returned.

A notable design decision immediately following rate limiting is the implementation of a "response-time floor" using `respondAfterFloor`. This mechanism ensures that all responses, regardless of the underlying processing time, take at least 250 milliseconds. This is a countermeasure against timing oracle attacks, where an attacker might infer information (e.g., whether a client already exists) by observing subtle differences in response times between different database operations (like a `SELECT` versus a `SELECT` followed by an `INSERT`).

The request body is then validated using `zod` against the `bookingSchema`. This schema enforces requirements for `slug`, `startsAt`, `clientName`, `clientPhone`, and optionally `clientEmail`. It also includes a `website` field, which acts as a honeypot. If this hidden field is populated by a bot, the API returns a fake success response (`200 OK`) without touching the database, effectively discarding the bot's submission.

After validation, the professional is retrieved from the `professionals` table using the provided `slug`. If not found, a `404` error is returned.

Next, the system checks for plan-based booking limits. It determines the `effectivePlan` of the professional, considering their `plan` and `trialEndsAt`. If the plan has limits on `clients` or `appointmentsPerMonth`, the API performs `count()` queries on the `clients` and `appointments` tables. If a limit is exceeded, and the booking is not for an existing client (in the case of client limits), a `403` status code is returned.

The core of the booking logic resides within a Drizzle `db.transaction` block, configured with `isolationLevel: "serializable"`. This is a critical design choice to prevent race conditions. Without it, two simultaneous booking requests for the same slot could both pass an initial availability check and then both attempt to insert an appointment, leading to a double-booking. The `serializable` isolation level forces the database to re-evaluate conditions if underlying data changes, causing one of the conflicting transactions to fail with a `40001` SQLSTATE, which the API catches and translates into a `409` conflict error.

Inside the transaction:
1.  **Conflict Check**: The system checks for any existing appointments that overlap with the proposed `startsAt` and `endsAt` times for the professional, excluding `rejected` or `cancelled` appointments, using the conditions `lt(appointments.startsAt, endDate)` and `gt(appointments.endsAt, startDate)`. If an overlap is found, a `SLOT_TAKEN` error is thrown, which triggers the `409` response.
2.  **Client Upsert**: The API attempts to find an existing client associated with the professional using either the `clientPhone` or `clientEmail`. If a client is found, their `email` is updated if it was previously null and a new email is provided. If no client is found, a new entry is inserted into the `clients` table.
3.  **Appointment Insertion**: Finally, a new appointment is inserted into the `appointments` table, linking it to the professional and the (new or existing) client. The `status` of the appointment is set to `confirmed` if `professional.autoConfirm` is true, otherwise it's `pending_confirmation`. The `paymentStatus` defaults to `none`.

Following a successful transaction, the API initiates a series of notifications:
*   A new entry is added to the `notifications` table for the professional, indicating either a `booking_confirmed` or `booking_request` depending on the `autoConfirm` setting.
*   WhatsApp messages are sent: a confirmation to the client (if auto-confirmed) and a receipt/request to the professional.
*   An email notification is sent to the professional if their `email` is available.

Finally, analytics events (`booking_received_server`, `first_booking_at`) are captured using `capture` and `setOnce` to track professional activity. The response is an equalized `success: true` JSON object, again avoiding the inclusion of sensitive data like the `clientId` to prevent information leakage.

## Design decisions

*   **Data Minimization in GET**: The `GET /api/booking` endpoint explicitly selects only `id` and `sessionDuration` from the `professionals` table. This was a deliberate choice to prevent accidental leakage of sensitive professional data (like `email`, `phone`, `userId`, `plan`, `stripeCustomerId`) to unauthenticated clients, which was a vulnerability in a previous iteration that returned all columns.
*   **Rate Limiting**: The `getBookingLimiter` is applied to the `POST` endpoint to prevent abuse and denial-of-service attacks, ensuring fair usage of the booking system.
*   **Timing Oracle Mitigation**: The `respondAfterFloor` function in the `POST` endpoint introduces a minimum response time. This decision was made to obscure timing differences between database operations (e.g., finding an existing client versus inserting a new one), thereby blunting potential timing oracle attacks that could reveal information about existing client data.
*   **Honeypot Field**: The `website` field in `bookingSchema` acts as a simple, yet effective, bot detection mechanism. By returning a fake success response for submissions that populate this hidden field, the system avoids processing spam while appearing successful to automated bots.
*   **Atomic Transaction with Serializable Isolation**: The `POST` endpoint wraps the conflict check, client upsert, and appointment insertion in a `db.transaction` with `serializable` isolation. This is crucial for data integrity, specifically to prevent race conditions where multiple concurrent requests might attempt to book the same time slot. The `serializable` level ensures that transactions behave as if they were executed sequentially, preventing phantom reads and ensuring that only one booking can succeed for a given slot.
*   **Client Upsert Logic**: The system attempts to find an existing client by `phone` or `email` before creating a new one. This prioritizes client continuity and avoids duplicate client entries for the same professional. The update of a missing `email` for an existing client also helps enrich client profiles over time.
*   **Equalized POST Response**: The `POST` endpoint returns a generic `{ success: true }` response, even after a successful booking. This decision, similar to the timing oracle mitigation, prevents the API from leaking specific details (like the newly created `clientId`) that could be used by an attacker to infer information about the system's internal state or client relationships.
*   **Unified Notification Flow**: The `professional.autoConfirm` flag streamlines the notification logic. Whether an appointment is immediately confirmed or pending, the system uses a consistent notification path (WhatsApp, email, internal notifications) but adapts the message content and type based on the confirmation status.

## Potential improvements

1.  **Server-Side Availability Calculation**: The `GET /api/booking` endpoint currently returns raw `availability` rules and `existingAppointments`. The client-side (`booking-widget.tsx`) is then responsible for calculating the actual available time slots. Moving this calculation to the server would centralize the logic, reduce client-side complexity, and ensure consistent slot determination across all clients. This would involve adding a utility function on the server to process `rules` and `existingAppointments` into a list of bookable slots.
2.  **Granular Error Responses**: The `serverError` helper in `src/lib/api.ts` provides a generic `500` response for unexpected errors. While useful, more specific error codes or structured error objects could be returned for different types of internal failures (e.g., database connection issues, external service integration failures). This would allow the frontend to provide more tailored feedback to users and aid in debugging.
3.  **Professional Data Minimization in POST**: Similar to the `GET` endpoint, the `POST /api/booking` endpoint currently fetches *all* columns from the `professionals` table using `db.select().from(professionals)`. This could be optimized by selecting only the necessary columns (`id`, `sessionDuration`, `autoConfirm`, `plan`, `trialEndsAt`, `phone`, `email`, `name`, `slug`, `userId`) required for the booking logic and notifications. This reduces the amount of data retrieved from the database and minimizes the risk of accidentally exposing sensitive data within the backend context.
4.  **Client Upsert Strategy Review**: The current client upsert logic in `POST /api/booking` updates a client's email if it was previously null. Consider if other client details (like `name` or `phone` if they differ from an existing record) should also be updated, or if the API should strictly prevent updates to existing client records via this booking flow to maintain data integrity and prevent accidental overwrites. A dedicated client profile update endpoint might be a cleaner separation of concerns.
